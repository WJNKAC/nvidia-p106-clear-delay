# 580.178.04 补丁说明

**驱动**：NVIDIA 580.178.04（P106-100，x86_64）
**验证环境**：**kernel 6.12.113+deb13-amd64** + 驱动 580.178.04，内核与用户态均 gcc-14.2.0
**库文件**：`libnvidia-glcore.so.580.178.04`（37,062,312 字节）
**改动**：**1 个字节**

---

## 一、改了什么

| 偏移 | 原值 | 新值 | 指令变化 | 含义 |
|---|---|---|---|---|
| `0xb51c82` | `0x74` | **`0xeb`** | `je` → `jmp` | 无条件跳过 gr3d 延迟命令的发射 |

**为什么原地替换安全**：`74 xx` / `eb xx` 都是 **2 字节 rel8 短跳转**，长度一致，
替换后指令边界与后续偏移都不变。（换 `e9` rel32 会破坏布局，**禁止**。）

**文件 md5**

| | md5 |
|---|---|
| 原版（`before/`） | `18f43321d6fcf95524cfb7e12cb221f2` |
| 补丁版（`after/`） | `45b06947204cbd586a5d45a463bb69ba` |

## 二、和 525 的关系

**同一个问题，580 没修。** 580 依然在每个批次边界写入 `method 0x3998 = 0xF0(240)`。

| 判据 | 515.105.01 | 525.116.03 | **580.178.04** |
|---|---|---|---|
| 文件大小 | 35.07 MB | 42.23 MB | 35.35 MB |
| `movabs 0x...20010E66`（那条命令） | 0 处 | 2 处 | **2 处** |
| 实参值 | — | 240 / 240 | **240 / 240** |
| 策略位 `cmp [rax+0xc18],0` | 0 处 | 4 处 | **0 处** |
| 策略位 `cmp [rax+0x20b],0` | 0 处 | 0 处 | **1 处** |

**⇒ 策略位结构体偏移从 `0xc18` 变成了 `0x20b`，其余同构。**

### 已打补丁的那一处

`0xb51c84`，所在函数 `0xb51600`（13040 字节，大状态机，对应 525 的 `0x15c2e50`）

```asm
0xb51c74  mov  rax, [r14 + 0x1240]
0xb51c7b  cmp  byte [rax + 0x20b], 0      ; 判据位（525 是 +0xc18）
0xb51c82  je   0xb51cb0                   ; 74 2c  ← ★ 补丁点
0xb51c84  mov  rax, [r14 + 0x80]
0xb51c8b  movabs rcx, 0xF020010E66        ; 实参 0xF0 + 命令头 0x20010E66
0xb51c95  mov  [rax], rcx
```

**与 525 的 `0x15c375e` 逐条一致**（连 `je` 的目标偏移都是 `+0x2c`）。

### 没打补丁的第二处（`0xde855e`）

580 还有第二处发射点，在函数 `0xde81e0` 内，但它**结构与 525 不同**：
没有策略位判据，是无条件循环发射（空间不足 → `0xde8860` 更新指针 → `jmp` 回 `0xde855e` 继续发），
且 `mov eax,1` 作为返回值。改 `je`→`jmp` 会破坏返回值语义，nop 掉又会让 put 指针空推 8 字节留下垃圾。

**实测结论：本负载下它不被调用。**
- 在 `0xde81e0` 入口下硬件断点，5 秒采样 **命中 0 次**
- 补丁后 pushbuffer 里 `method 0x3998` **样本 0 条**

**⇒ 只改第一处就够了。** 但要注意：**其他应用/负载可能走到第二处**，那时这条命令仍会发出。
如果遇到"某些程序还是慢"，可以回头查这个函数。

## 三、实测效果

### 性能与正确性（`n83b -M 7 -c 400 -n 400`，带回读模式）

| 配置 | `map_p50` | `fps` | **像素校验 `chk`** |
|---|---|---|---|
| 580 原版 | **52.195 ms** | **18.98** | 5150 |
| **580 + 本补丁** | **3.434 ms** | **259.79** | **5150** |
| 525 原版（对照） | 52.276 ms | 18.96 | 5150 |
| 525 + 补丁（对照） | 3.448 ms | 256.56 | 5150 |
| 515 原版（对照） | ≈3.4 ms | ≈258 | 5150 |

**580 原版与 525 原版的数字几乎完全一样（52.195 vs 52.276 ms）**，
补丁后也一样（3.434 vs 3.448 ms）—— 说明这是**同一个问题在两个版本里延续**，不是新问题。

`chk` 全部 5150，**画面正确**。

### 命令确实消失
补丁后扫描 pushbuffer：`method 0x3998` **样本 0 条**。

### 一个有意思的对照：跨内核跨驱动，性能完全一致
- 525 补丁后：3.448 ms（kernel 6.1.0-50）
- 580 补丁后：3.434 ms（kernel 6.12.113）

**差了整整一个大版本的内核和一个大版本的驱动，补丁后性能差异 <0.5%。**
⇒ 这条延迟命令就是全部原因，内核与驱动版本对这部分没有其他影响。

## 四、如何使用

```bash
# 查看状态
sudo ../tools/patch_glcore.py check \
     /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.580.178.04 --spec patch.json

# 应用（自动备份为 .orig）
sudo ./apply.sh

# 回滚
sudo ./revert.sh
```

或直接复制现成文件：

```bash
sudo cp after/libnvidia-glcore.so.580.178.04 \
        /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.580.178.04
# 恢复原版
sudo cp before/libnvidia-glcore.so.580.178.04 \
        /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.580.178.04
```

**生效时机**：改的是磁盘文件，**已在运行的程序不受影响**，需重启程序或重新登录。

## 六、风险与限制

| 项 | 说明 |
|---|---|
| **驱动升级即失效** | 偏移随版本变化。新版本按第七节重定位，**不要硬套** |
| **重装同版本驱动会覆盖** | 安装器写回原版，补丁失效（这也是最可靠的恢复手段） |
| **包校验会报** | `dpkg -V` 会显示该文件被修改，属预期 |
| **未做长时间稳定性测试** | 只跑了 `n83b` 短时，**没有跑 Heaven 长时间或数小时压力测试** |
| **第二处未打补丁** | 本负载下不被调用，但其他应用可能走到 |

## 七、换驱动版本时怎么重新定位

```bash
1. 搜字节串 66 0e 01 20 f0 00 00 00
   = movabs 立即数（高32位实参 0xF0 + 低32位命令头 0x20010E66）
   → 命中处即发射点

2. 每个发射点前几字节找 "cmp byte [reg+偏移], 0" 的模式
   525 是 80 b8 18 0c 00 00 00   (偏移 0xc18)
   580 是 80 b8 0b 02 00 00 00   (偏移 0x20b)
   → 偏移本身会变，要看"cmp 后跟条件跳转"这个结构

3. 紧随其后的条件跳转 74 xx (je) / 75 xx (jne)
   → 换成 eb xx (jmp)，只改首字节

4. 搜不到这些特征 → 说明机制已变（可能修了），必须重新分析
```

工具：`xcall.py`（funcs / who / imm / callers / dis）、`tools/pbargs.py`（确认命令是否还在发）。

## 附：6.12 内核的一个好消息

| 项 | 6.1.0-50 | **6.12.113** |
|---|---|---|
| 内核编译 GCC | gcc-12 (12.2.0) | **gcc-14 (14.2.0)** |
| 系统默认 gcc | 14.2.0 ❌ 不匹配 | **14.2.0** ✅ 匹配 |
| 装驱动要 `CC=gcc-12` 吗 | **要** | **不需要** |

6.12 内核本来就是 gcc-14.2.0 编译的，所以装 580 时**不需要**手动指定 `CC`，
之前 6.1 上那个 `dma_is_direct` + GCC 14 的编译坑不会出现。
