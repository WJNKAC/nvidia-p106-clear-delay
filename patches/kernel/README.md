# 内核侧补丁：把 P106 从「受限设备表」里抹掉

**这是治本方案，但影响面比用户态补丁大，请读完风险再动手。**

## 它做什么

NVIDIA 内核模块 `nv-kernel.o_binary` 里有一张按 device id 索引的表，
P104 / P106 / CMP 等矿卡列在其中。卡命中这张表就会被判为「受限 SKU」，
用户态驱动随后在每个批次边界写 `0x3998 = 240`。

把表里对应条目改成无效值（`0x0007FFFF`），卡就不再命中 ——
**那条命令根本不会生成**，而不是生成后被跳过。

## 实测

| 配置 | `map_p50` | `fps` | `method 0x3998` |
|---|---|---|---|
| 原版 | 52.202 ms | 18.98 | 40+ 条 |
| 仅打内核补丁 | **3.668 ms** | **243.78** | **0 条** |
| 仅打用户态补丁 | 3.434 ms | 259.79 | 0 条 |
| 两个都打 | 3.667 ms | 246.64 | 0 条 |

**两种补丁不叠加** —— 打了内核补丁，用户态那个就多余了。

## 580.178.04 的位置

| 项 | 值 |
|---|---|
| 文件 | `/usr/src/nvidia-<版本>/nvidia/nv-kernel.o_binary` |
| 原 md5 | `caa613d35d8bdfd615cee91e932689b5` |
| 表偏移 | `0x5cfdfcc`（`.rodata` 段内嵌入 blob，该区域无独立符号） |
| 本机条目 | `0x00071C07`（P106-100 = `10DE:1C07`）在 `0x5cfdfd8` |
| 改动 | 5 个 dword 的低 16 位 → `FFFF`，共 **10 字节** |

## 用法

```bash
# 1) 看状态
sudo python3 patch_kblob.py check <blob路径> --spec patch.json

# 2) 打补丁（自动备份 .orig）
sudo python3 patch_kblob.py apply <blob路径> --spec patch.json

# 3) 重建并替换模块（★ 会中断图形会话）
cd /usr/src/nvidia-<版本> && sudo make -j$(nproc)
sudo cp nvidia.ko /lib/modules/$(uname -r)/updates/dkms/nvidia.ko
sudo depmod -a
# 停 sddm → 卸载 4 个 nvidia 模块 → 重载 → 起 sddm

# 4) 回滚
sudo python3 patch_kblob.py revert <blob路径>
```

## 风险（比用户态方案大）

| 项 | 说明 |
|---|---|
| **改的是设备身份** | 不只影响 GL 性能路径，可能影响其他依赖「受限 SKU」判断的功能 |
| **没有像素级校验** | 用户态补丁能用像素校验值证明画面没变，这个只能看性能数字 |
| **需要重建内核模块** | 依赖内核头文件和匹配的 gcc；换内核要重做 |
| **中断图形会话** | 卸载模块 = 桌面消失 |
| **NVENC / 电源管理 / 多卡均未验证** | 只跑了短时 GL 测试 |

## 为什么仍然把它写进这个项目

因为它证明了**根因**：那条命令的开关在内核侧，用户态补丁只是在下游拦截。
没有这组对照，就说不清"到底是谁的问题"。

日常使用建议优先用户态方案（改动小、可验证画面），
内核方案适合"想从根上解决"或做研究结论的场景。
