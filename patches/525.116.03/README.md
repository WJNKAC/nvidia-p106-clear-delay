# 525.116.03 补丁说明

**驱动**：NVIDIA 525.116.03（P106-100，x86_64）
**库文件**：`libnvidia-glcore.so.525.116.03`（44,282,616 字节）
**改动**：**2 个字节**

---

## 一、改了什么

| 偏移 | 原值 | 新值 | 指令变化 | 含义 |
|---|---|---|---|---|
| `0x15c375e` | `0x74` | **`0xeb`** | `je` → `jmp` | 无条件跳过发射点 1 |
| `0x1841fe0` | `0x75` | **`0xeb`** | `jne` → `jmp` | 无条件跳过发射点 2 |

**为什么原地替换安全**：`74 xx` / `75 xx` / `eb xx` 都是 **2 字节 rel8 短跳转**，
长度完全一致，替换后指令边界与后续所有偏移都不变。
（若换成 `e9`（rel32，5 字节）会破坏布局，**禁止**。）

**文件 md5**

| | md5 |
|---|---|
| 原版（`before/`） | `276992071408f0828704f12827c85ae1` |
| 补丁版（`after/`） | `84bff6eb3940df59ee607dc117223334` |

## 二、为什么要这么改

### 问题

525 在**每个批次边界**向 GPU 命令流写入一条：

```
method 0x3998,  arg = 0xF0 (240)
```

240 是「延迟单位数」。按实测换算：

```
240 单位 × 0.91 µs/单位 ≈ 218 µs / 批
```

每次切批都付这一笔，于是帧时间随**批次数**线性增长：

```
T_frame = T_base + 批次数 × 218 µs
```

用 `n83b -M 7 -c 400`（每帧 400 批）测：`map_p50 = 52.276 ms`，其中绝大部分是这一项。

### 关键事实：515 里这套机制**不存在**

| 判据 | 515.105.01 | 525.116.03 |
|---|---|---|
| `movabs 0x...20010E66`（那条 240 命令） | **0 处** | **2 处** |
| `cmp byte [rax+0xc18], 0`（策略位检查） | **0 处** | **4 处** |
| 发射函数 `0x15c2e50` 的机器码 | **找不到** | 存在（11,856 字节） |

**⇒ 不是"525 的 240 设太大了"，而是"525 多了这条命令，而它本不该发"。**

### 代码结构

两个发射点检查**同一个全局策略位 `+0xc18`**：

```
发射点1  0x15c3767   在函数 0x15c2e50 内（legacy 状态机）
发射点2  0x1842131   在函数 0x1841fb0 内

两者都是：
    cmp  byte [obj + 0xc18], 0
    je/jne  skip                 ← ★ 本补丁改的就是这里
    movabs reg, 0xF020010E66     ← 高32位=实参0xF0, 低32位=命令头0x20010E66
    mov  [pushbuf], reg          ← 8 字节一次写入
```

策略位由 `0x15bc880` 内设置（`0x15bd014` / `0x1452693` 两处写 1），
判据是 `r8d` 不为 `0x200`/`0x201`/`0x204` 时置位；调用点 `0x15cecee` 传 `xor r8d,r8d`（=0）
⇒ **必然置位**，这就是"每批都发"的原因。

### 为什么改成"跳过发射"而不是"把 240 调小"

| 手段 | 改动 | `map_p50` |
|---|---|---|
| 治标：把实参 240 改成 16 | 立即数 2 字节 | 52.3 → **7.0 ms** |
| **治本：让这条命令根本不发** | 跳转 2 字节 | 52.3 → **3.45 ms** |
| 515 原版参考 | — | **≈3.4 ms** |

**治标只能恢复一半多，治本才能完全追平 515。**
另外"把实参设成 0"没有意义 —— 实测 `0` 是特殊值，效果等价于 240。

## 三、实测效果

### 性能与正确性（`n83b -M 7 -c 400 -n 400`，带回读模式）

| 配置 | `map_p50` | `fps` | **像素校验 `chk`** |
|---|---|---|---|
| 525 原版 | **52.276 ms** | **18.96** | 5150 |
| **525 + 本补丁** | **3.448 ms** | **256.56** | **5150** |
| 515 参考 | ≈3.4 ms | ≈258 | 5150 |

`chk` 是真实 `glReadPixels` 回读的像素值累加。**三组完全一致（5150）⇒ 画面正确。**

### 目标命令确实消失

补丁后扫描 pushbuffer：`method 0x3998` **样本 0 条、活跃段命中 0**。
（补丁前可抓到 40 条以上）

### Heaven

GPU 利用率 91~95%、功耗 93~107 W（原版是 100% / 55~70 W）、31 线程、画面持续推进。
**功耗接近翻倍 = GPU 从空转等待变成真在渲染。**

> ⚠ 未取到 Heaven 的屏幕 FPS 读数：`-benchmark` 模式会隐藏 FPS 叠层，日志也从不写 FPS。
> 所以 Heaven 侧只有功耗/利用率证据，**精确帧率数据以上面的 `n83b` 为准**。

## 四、如何使用

```bash
# 1) 查看状态（不改动）
sudo ../tools/patch_glcore.py check \
     /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03 --spec patch.json

# 2) 应用（自动备份为 .orig）
sudo ./apply.sh

# 3) 回滚
sudo ./revert.sh
```

或者直接复制现成文件：

```bash
# 用补丁版
sudo cp after/libnvidia-glcore.so.525.116.03 \
        /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03
# 恢复原版
sudo cp before/libnvidia-glcore.so.525.116.03 \
        /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03
```

**生效时机**：改的是磁盘文件，**已在运行的程序不受影响**，需重启程序或重新登录。

## 六、风险与限制（务必读完）

| 项 | 说明 |
|---|---|
| **驱动升级即失效** | 偏移随版本变化。新版本需按下面的"重定位方法"重新找地址，**不要硬套本补丁** |
| **重装同版本驱动会覆盖** | 安装器会写回原版文件，补丁失效（这也是最可靠的回滚方式） |
| **包校验会报** | `dpkg -V` 等会显示该文件被修改，属预期 |
| **未做长时间稳定性测试** | 只验证了 `n83b` 与 Heaven 短时运行，**没有跑数小时的 Xid/稳定性测试** |
| **可能有未验证的副作用** | `+0xc18` 还被另外 4 处检查引用，那些代码路径的影响**未逐一验证** |
| **不是厂商修复** | 这是在别人的二进制里跳过一段逻辑，属逆向研究成果的固化 |

**结论**：适合"我就是想在这台机器上用 525 跑起来"的场景。
正式环境建议优先：
- **整套用 515.105.01**（本项目已验证该版本没有此问题）
- **或在应用层合批**（把每帧批次数压进性能预算，代价是实现成本）

## 七、换驱动版本时怎么重新定位

判据只依赖**语义特征**，不依赖绝对地址：

```
1. 在 .so 里搜字节串 66 0e 01 20 f0 00 00 00
   = movabs 的立即数（高32位实参 0xF0 + 低32位命令头 0x20010E66）
   → 命中处就是发射点

2. 每个发射点前几字节应能看到 80 b8 18 0c 00 00 00
   = cmp byte [rax+0xc18], 0

3. 紧随其后的条件跳转：
     74 xx  (je)  或  75 xx  (jne)
   → 改成 eb xx (jmp)，只改首字节

4. 新版本若搜不到上面任一特征，说明机制已变（可能修了、也可能换了实现）
   → 必须重新分析，不能套用
```

配套工具（本项目工作区）：
- `xcall.py`（funcs / who / imm / callers / dis）—— 静态定位
- `tools/pbmeth.py` / `pbargs.py` —— 从 pushbuffer 确认命令是否还在发
