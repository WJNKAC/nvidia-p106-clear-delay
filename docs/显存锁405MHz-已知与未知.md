# 显存锁 405 MHz 现象 —— 已知与未知

**日期**：2026-11-03
**状态**：**间歇性，当前未复现**
**性质**：与 N186~N190 的受限 SKU 课题**无关**，是独立问题

---

## 0. 先分清两个概念

这个卡（P104-100 / vBIOS 86.04.7A.00.19）**显存只有两档**：

```
405 MHz   空闲档（P8）
5005 MHz  负载档（P0）
```

| 状态 | 空闲 | 负载 | 判断 |
|---|---|---|---|
| **正常** | 405 | **5005** | ✅ |
| **异常** | 405 | **405** | ❌ 这才是问题 |

⇒ 「空闲时看到 405」**不是问题**，别误判。

**异常的定义：负载下（显存利用率 >50%）仍停在 405，持续 >10 秒。**

---

## 1. 异常时的完整特征（2026-11-02 23:22 抓到）

```
100 %, 50.82 W, P0, 1911 MHz, 405 MHz, 2871 MiB
        ↑功耗低     ↑SM满频  ↑显存锁死
显存利用率 83~85%
```

用同一个探针（128 MB buffer copy，显存利用率 94%）复现：

```
01  405 MHz, 1911 MHz, 94 %, 43.68 W
...
20  405 MHz, 1911 MHz, 94 %, 43.93 W
```

**20 秒一次没升。功耗 43 W（上限 180 W），温度 41~43 °C。**

关键签名：**SM 满频 + 显存利用率高 + 功耗只有正常值的 1/3**（正常 131 W，异常 43 W）。

---

## 2. 已排除的原因

| 假设 | 怎么排除的 | 结论 |
|---|---|---|
| 补丁丢失 | 四处白名单 `P104 x1`、glcore `0xeb` 全在 | ❌ |
| PCIe 链路回落 | 异常期间链路仍 5.0 GT/s（Gen2） | ❌ |
| ASPM 省电 | `LnkCtl: ASPM Disabled` | ❌ |
| runtime PM | `power/control = on` | ❌ |
| 功耗墙 | 43 W vs 180 W 上限 | ❌ |
| 热降频 | 41~43 °C（阈值 93/96） | ❌ |
| 观察者效应（NVML 轮询） | A/B 对照：只在第 30 秒查 1 次 vs 每秒查 1 次，**两组都 405** | ❌ |
| 探针污染（残留进程） | 干净环境（`pkill -9 -x` 确认无残留）复测，仍 405 | ❌ |
| gen2kr 影响 | **`rmmod gen2kr` 后仍 405**；加载 gen2kr 后负载正常 5005 | ❌ |
| gen2kr 的 unbind/bind | 加载流程含 unbind/bind，之后负载仍 5005 | ❌ |
| `nvidia-smi -lmc 5005` 锁频 | 返回 "All done" 但时钟不变；`-rmc` 报 **"Setting locked Memory clocks is not supported"**（矿卡 vBIOS 不支持） | ❌ |
| `nvidia-smi -rgc` 重置 | 无效 | ❌ |
| `nvidia-smi -pm 1` 持久模式 | 无效 | ❌ |
| vBIOS 被改 | `GPUMemoryTransferRateOffsetAllPerformanceLevels = 0`（未改过） | ❌ |
| 驱动模块文件损坏 | md5 `65cd1c3277e838dd0810f2ed031af6f4`，与 10-31 一致 | ❌ |

## 3. 已验证有效的恢复方式

| 方式 | 效果 |
|---|---|
| **重启** | ✅ 有效（2026-11-02 23:45 实测，重启后负载立刻回到 5005 / 131 W） |
| **unbind/bind 重载驱动** | ✅ 用户反馈有效（「unbind 后 bind 一段时间是 5005」） |
| `rmmod` gen2kr | ❌ 无效（P-State 已卡死，模块层面改不回来） |

⇒ **P-State 管理器卡死在最低档，只有重新初始化驱动才能复位。**

## 4. 尚未确认

### 4.1 触发条件未知

时间线上的**相关性**（不是因果）：

- 2026-10-31 09:43 测到正常 5005 —— 当时 GPU 上只有探针，**没跑过游戏**
- 2026-11-02 23:09 / 23:18 跑过两次七日世界 → 23:22 首次观测到 405
- 2026-11-02 23:45 重启 + 加载 gen2kr → 恢复正常 5005
- 2026-11-03 00:20 空闲 405（**正常**），未跑游戏

**弱怀疑：跑游戏（DXVK/Vulkan）后触发。但样本只有 1 次，不足以定论。**

### 4.2 没有对应的「设置位」

- `nvidia-smi -q -d CLOCK` 的 `Applications Clocks` / `Default Applications Clocks` 全为 **N/A**
- `Clocks Event Reasons` 全部 `Not Active`（没有任何降频原因被触发）
- 矿卡 vBIOS **不支持** `-lmc` 锁显存（`-rmc` 明确报 not supported）
- 没有 `~/.drirc`、`dxvk.conf`、`vkd3d.conf` 之类会改时钟的配置

⇒ **没有任何用户可调的开关与这个现象对应**，它是驱动内部状态机卡住，不是某个设置被改。

### 4.3 是不是 P104-100 矿卡特有

无法判断。本机没有第二张卡做对照；
`nvidia-smi` 报的全部降频原因都未激活，说明驱动自己也「认为」没在限速 ——
**状态机内部不一致**，这本身是个可疑点。

## 5. 下次复现时怎么抓（命令已备好）

```bash
# ① 先确认是真异常（不是空闲 405）
nvidia-smi --query-gpu=utilization.memory,clocks.mem,power.draw --format=csv,noheader
#    memory 利用率 >50% 且 clocks.mem=405 持续 >10s ⇒ 异常

# ② 立即看降频原因（对照正常时全部 Not Active）
nvidia-smi -q -d PERFORMANCE | sed -n '/Clocks Event Reasons/,/Counters/p'

# ③ 看 P-State
nvidia-smi --query-gpu=pstate,clocks.sm,clocks.mem --format=csv,noheader
#    异常特征：P0 + SM 1911 + MEM 405（P0 却不升显存）

# ④ 抓驱动日志（看有没有 NVRM 报错）
sudo dmesg | grep -iE "NVRM|Xid|clock|pstate" | tail -30

# ⑤ 保存现场后，用 unbind/bind 复位（比重启快）
#    注意必须先确认 GPU 空闲：memory.used=0 且无 compute apps
```

**关键判据（一眼分辨）**：

| 指标 | 正常 | 异常 |
|---|---|---|
| 负载功耗 | **130 W 左右** | **43 W 左右** |
| P-State | P0 | P0（也是 P0） |
| SM 时钟 | 1911 | 1911 |
| 显存时钟 | 5005 | **405** |

⇒ **功耗是最快的判据：负载下 43 W 就是异常，130 W 就是正常。**

## 6. 与受取 SKU 课题的关系

**无关。** N186~N190 证明的是「每批次/render pass 固定延迟」，
那个现象在 Vulkan/GL 都有，且内核白名单一打就消失。

显存锁 405 是**另一个独立的 P-State 问题**：
- 与 GPU 提交批次无关
- 与受限设备表无关（打不打白名单都会出现）
- 只影响带宽敏感负载
