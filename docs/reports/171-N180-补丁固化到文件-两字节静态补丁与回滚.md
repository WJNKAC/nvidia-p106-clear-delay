# N180 — 补丁固化到文件：`libnvidia-glcore.so` 两字节静态补丁 + 完整回滚

**日期**：2026-10-27
**驱动**：525.116.03（P106-100）
**目标**：把已验证有效的运行时补丁固化进 `.so` 文件，使驱动每次加载都自动生效

---

## 0. 结果

| 项 | 值 |
|---|---|
| 目标文件 | `/usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03` |
| 原 md5 | `276992071408f0828704f12827c85ae1` |
| 新 md5 | `84bff6eb3940df59ee607dc117223334` |
| 备份 | `/usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03.orig`（md5 同上原值） |
| 改动 | **2 个字节** |

| 偏移 | 原 | 新 | 含义 |
|---|---|---|---|
| `0x15c375e` | `0x74`（`je`） | **`0xeb`（`jmp`）** | 无条件跳过发射点 1 |
| `0x1841fe0` | `0x75`（`jne`） | **`0xeb`（`jmp`）** | 无条件跳过发射点 2 |

**为什么原地替换是安全的**：`74 xx` / `75 xx` / `eb xx` 都是 **2 字节 rel8 短跳转**，
长度完全一致，替换后指令边界与后续代码偏移都不变。
（换成 `e9`（rel32，5 字节）会破坏布局，绝不能那么干。）

## 1. 验证（全部在**不加载任何 LD_PRELOAD** 的情况下）

0x1841fe0: 0xeb  [已打补丁]
```

### 1.2 进程内存（关键：确认加载的是新文件、且字节已生效）
```
进程实际映射：/usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03
读 /proc/<pid>/mem：

  0x1841fe0 = 0xeb  已改

**这一步不能省** —— 磁盘改了不等于进程用的是新文件（可能有别的副本/缓存）。

## 2. 工具：`patch_glcore.py`

```
patch_glcore.py apply  <so路径>   # 先备份，再打补丁
patch_glcore.py revert <so路径>   # 从 .orig 备份恢复
patch_glcore.py check  <so路径>   # 只检查当前状态
```

设计要点（都是踩过的坑换来的）：

| 要点 | 为什么 |
|---|---|
| **改写前逐字节核对"期望原值"** | 位置不匹配就中止，防止补丁漂移到别的驱动版本 |
| **备份只在首次创建** | 否则重复 apply 会把"已打补丁的文件"当成备份，回滚就回不去原版 |
| **原子写（临时文件 + `os.replace`）** | 避免写到一半中断导致 `.so` 损坏、整个图形栈起不来 |
| **`check` 能区分"未打/已打/未知"** | "未知值"是位置漂移的告警信号 |

## 3. 回滚（必须记住）

```bash
sudo python3 <workdir>/analysis/tools/patch_glcore.py \
     revert /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03
```

或手动：
```bash
sudo cp /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03.orig \
        /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03
```

**回滚后需要重启使用该库的进程**（新进程才会重新加载；已经跑着的进程不受影响）。

**注意：重装驱动会覆盖这个文件**（安装器会写入原始 `.so`），补丁自动失效 ——
这既是"升级后需要重打"的麻烦，也是"出问题重装驱动即可恢复"的安全网。

## 4. 这个固化补丁的性质（必须说清）

### 它解决什么
- **不再需要 `LD_PRELOAD`**：任何程序（包括经 `primusrun` 启动的）都自动生效
- **不依赖程序如何加载 GL**：绕过了之前"Unigine 用 dlopen、钩子拦不到"的问题
- **每次驱动加载自动生效**：只要文件还是这个版本

### 它不解决什么
| 限制 | 说明 |
|---|---|
| **驱动一升级就失效** | 偏移量随版本变化，新版本需重新定位（判据见报告 170） |
| **重装同版本驱动会被覆盖** | 需要重打 |
| **包的完整性校验会报错** | `dpkg -V` / md5 校验会显示该文件被修改 |
| **未做长时间稳定性测试** | 只验证了 n83b 与 Heaven 短时运行，**没有跑数小时的 Xid/稳定性测试** |
| **可能影响其他路径** | 我们只确认"这条延迟命令不发"对当前负载无害，`+0xc18` 还被其他 4 处检查引用，未逐一验证 |

### 它不是"修好了驱动"
**这是在别人的二进制里跳过一段逻辑，属于逆向研究成果的固化，不是驱动修复。**
真正的修复应当是 NVIDIA 提供行为正确的版本，或在应用层合批（报告 166 §6）。

## 5. 复现步骤（换机器/换版本时）

```bash
# 1) 备份并确认原始状态
sudo python3 patch_glcore.py check /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.<版本>
#    期望两个字节分别是 0x74 / 0x75

# 2) 打补丁
sudo python3 patch_glcore.py apply /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.<版本>

# 3) 验证磁盘
sudo python3 patch_glcore.py check <路径>   # 应显示"已打补丁"

# 4) 验证内存（起一个 GL 程序，读它的 /proc/pid/mem）
#    不要只看磁盘，见 §1.2

# 5) 验证正确性：必须用带回读的程序看像素校验值
#    n83b -M 7 -c 400 -n 400 → chk 应与原版一致
```

**换版本时的偏移怎么找**（判据来自报告 170）：
1. 搜 `movabs` 立即数 `66 0e 01 20 f0 00 00 00`（即 `0x...20010E66`）→ 得到发射点
2. 每个发射点前几字节应能看到 `80 b8 18 0c 00 00 00`（`cmp byte [rax+0xc18],0`）
3. 紧随其后的条件跳转（`74 xx` 或 `75 xx`）就是补丁位置
4. **改 `74/75` → `eb`，只改首字节，长度不变**
