# P106-100 3D 功耗限制问题 — 驱动版本静态定位报告

- **日期**: 2026-10-24
- **状态**: 静态分析进行中（版本边界已锁定，待 vBIOS 解析 + 上机执行签名验证）
- **目标机器**: <testhost>（P106-100 位于第二 PCIe 槽位，现役驱动 580.178.04）
- **问题现象**: P106-100 在 3D 负载下功耗被钳制在 60-70W，性能随之受限
- **用户经验**: 该问题在 515 驱动下不存在；515 已不适配机器当前内核，现用 580

---

## 1. 结论摘要（TL;DR）

**功耗管理行为的变化精确锁定在 `515.105.01` → `525.116.03` 之间（即 520/525 这一代驱动）。**

| # | 发现 | 证据 |
|---|------|------|
| 1 | NVPCF 客户端功耗限制接口 `rm_get_clientnvpcf_power_limits` 被整体移除 | nv.h API 声明、RM blob 符号表、nv-procfs.c 三处同时消失 |
| 2 | NVPCF 交互模型重构为 `nvpcf_dsm_in_gpu_scope`（DSM 在 GPU scope 内评估） | okm 源码：520.56.06 仅有结构体字段，525.60.11 有完整赋值/使用逻辑 |
| 3 | procfs `/proc/driver/nvidia/gpus/*/information` 的 "Power Limits"（Default/GPU Boost）显示被删除 | nv-procfs.c 源码对比 |
| 4 | RM 核心大改但 Rated TDP 机制保留 | `nv-kernel.o_binary` 46.6MB→63.1MB；`RmPerfRatedTdpLimit`/`CTRL_PERF_RATED_TDP_*` 两代均在 |
| 5 | 新增 `RMForcePstateBug3811584War`（强制 P-state 的 bug 规避） | RM blob 字符串 diff |
| 6 | NVML 层：525 仅多 `SetNvLinkDeviceLowPowerThreshold`；`SetPowerManagementLimit_v2` 到 535 才有 | nm -D 符号对比 |
| 7 | **不是日历时间问题，是分支拓扑问题**：515.105.01（2023-04）仍是旧画像 | 515 长期分支全程保留 client NVPCF 路径；重构落在 520+ 主线 |

### 4.2 符号表 diff（515.105.01 vs 525.116.03）

原始数据：`analysis/syms/`，diff 产物：`analysis/diffs/`

**defined（RM 内部函数）**：525 新增 6509 个、515 独有 1293 个。按功耗/性能关键词（perf/pstate/power/tdp/nvpcf/dsm/board/limit/throttle/volt/clk）过滤后：

- 525 新增仅：`rm_power_source_change_event`（+ 3 个 `.cold` 变体）
- 515 独有仅：`rm_get_clientnvpcf_power_limits`

→ 功耗相关的**具名**函数变化极少；RM 的 16MB 增长主要是新 GPU 架构支持（`_nv*rm.c` 系列，抽样见 `analysis/diffs/defined-only-in-525.txt`）。

**undefined（blob 对胶水层的导入）**：525 新增 17 个：

```
nv_cancel_nano_timer / nv_create_nano_timer / nv_destroy_nano_timer / nv_start_nano_timer
nv_match_gpu_os_info / nvswitch_os_get_platform_time_epoch / nvswitch_os_strncat
os_acquire_rwlock_read / os_acquire_rwlock_write / os_alloc_rwlock
os_cond_acquire_rwlock_read / os_cond_acquire_rwlock_write / os_enable_pci_req_atomics
os_free_rwlock / os_get_max_user_va / os_release_rwlock_read / os_release_rwlock_write
```

515 独有 1 个：`__x86_indirect_thunk_rdi`（编译产物差异）。

→ 这解释了"胶水源文件只差 2 个 vs RM 二进制 +16MB"的矛盾：新增导入正好对应新胶水文件 `nv-nano-timer.c`（515→525 内核源文件差异仅：新增 nv-nano-timer.c、移除 nv-procfs-utils.c）。
→ `nvpcf_dsm_in_gpu_scope` **不在** undefined 中：它是 `nv_state_t` 结构体字段（胶水层 nv.h 声明），blob 内部直接使用，复用既有 ACPI DSM 管道（nv-acpi.c），无需新导入。

**RM blob 功耗字符串 diff**（`analysis/diffs/rm-strings-diff.txt`）：全部差异仅两行——

```
< rm_get_clientnvpcf_power_limits      （仅 515 有）
> RMForcePstateBug3811584War           （仅 525 有）
```

## 6. 互证与边界说明

- 用户"515 无 / 580 有"的观察与静态锁定的 515.105.01→525.116.03 边界吻合。
- 515.105.01 发布于 2023-04 仍是旧画像，说明 515 长期分支全程保留 client NVPCF 路径——用户侧"515 是最后好版本"的经验与分支拓扑一致。
- **静态分析的边界**：60-70W 上限的最终执行在闭源 RM（`nv-kernel.o_binary`）内部 + 卡本身 vBIOS，静态可见接口重构但看不到内部阈值逻辑；需 vBIOS 数值 + 上机执行签名补全。
