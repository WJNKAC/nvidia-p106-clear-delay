## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **wait_ms 确实是条件插入的**，受三个门控制 | 静态：`123b2f0-123b314` |
| 2 | 其中**唯一可外部影响的开关是全局 flags 的 bit5**（`0x2a70528`），由 **regkey** 初始化 | 静态：`14c13ff/14c159e-14c15ac`，三个 regkey `ThreadControl`/`ThreadControl2`/一个混淆名 |
| 3 | **但关不掉**：bit5 同时门控 `signal`，强制置位 → **fps 38 → 3** | 实测 `n7_flagpoke.sh` |
| 4 | 另一个候选（把"预先睡"改回"轮询"）也会走通，但 **fps 只 +15% 而 CPU 涨到 266%** | 实测 `n8_spinpatch.sh`（1 字节 0x75→0xeb） |
| 5 | **★ 因此报告 35 的分叉虽然真实存在，但它不是性能主因** | 4 的定量 |
| 6 | **★ 525 慢的瓶颈在上游（工作只按帧到达），不在队列处理器的等待策略** | 5 + N6 的 90% 空转 |

## 2. 静态：三个门，以及唯一的外部开关

### 2.1 门在哪儿

```
123afae: je     123b2f0            ; 队列"仍然空" → 进 Path B
123b2f0: cmpb   $0x0,0x17(%rsp)    ; 门1: giveup（10 万轮询预算耗尽才置 1）
123b2f5: jne    123b309            ;    为真 → 直接去等（两版都有这条兜底）
123b2f7: mov    0x2c(%rsp),%eax    ; 门2: = 全局 flags & 0x20
123b2fb: test   %eax,%eax
123b2fd: jne    123b32f            ;    ★ 为真 → 跳过 wait_ms
123b2ff: cmpb   $0x0,0x8e0dc8(%r15) ; 门3: ctx 标志
123b307: jne    123b32f            ;    为真 → 跳过 wait_ms
123b309: mov    0x8e0950(%r15),%rdi ; cond 指针
123b310: mov    0x28(%rsp),%esi     ; ms
123b314: call   *0x2d0(%rbp)        ; wait_ms
```

所以**不是无条件插入**。wait 只在「giveup」或「两个 flag 都为 0」时执行。

### 2.2 门 2 的来源：一个全局 flags 字

```
123ac89: lea    0x1834c90(%rip),%r12        # 2a6f920  (= _nv026glcore+0x8f0)
123ac90: mov    0xc08(%r12),%eax            ; flags 字
123ac98: mov    %eax,%ecx
123ac9a: and    $0x20,%ecx                  ; 只取 bit5
123aca5: mov    %ecx,0x2c(%rsp)
```

这个对象在 `0x14c13f0` 处初始化（`14c13ff: lea # 2a6f920 → %rbx`），flags 字的取值来自**三次 regkey 读取**：

```
14c1555: call 151c060   ; 读 "ThreadControl"  → 0xc(%rsp)
14c156d: call 151c060   ; 读 "ThreadControl2" → 0x10(%rsp)
14c1585: call 151c060   ; 读 混淆名(0x1d44c28) → 0x14(%rsp)
14c158a: mov 0x14(%rsp),%ecx ; test ecx,ecx
14c1590: je  14c17a4
    ; 第三个 regkey 非 0 →
14c159e: movl $0x51020,0x10(%rsp)
14c15a6: movl $0x51021,0xc08(%rbx)     ; 直接用常量
    ; 否则 →
14c17a4: mov 0xc(%rsp),%eax
14c17a8: or  0x10(%rsp),%eax
14c17ac: mov %eax,0xc08(%rbx)          ; flags = ThreadControl | ThreadControl2
```

`0x151c060` 是 `__glReadRegkeyInt(name, id, default, out)`（经 `_nv014glcore+0x320` 分发），
`rdi` = 名字串、`esi` = 32 位 key id、`edx` = 默认值、`rcx` = 输出。

读到的名字（`analysis/probes` 里的 ELF 直读）：

| vaddr | 内容 | 用作 |
|---|---|---|
| `0x1d40011` | `ThreadControl` | flags 低字节来源 |
| `0x1d3ff96` | `ThreadControl2` | flags 来源 |
| `0x1d44c28` | `0x555237`（混淆） | **决定是否用常量 0x51021** |
| `0x1d44c38` | `ThreadAffinity` | 线程绑核 |

> `0x51020` / `0x51021` 的低字节是 `0x20` / `0x21`——**两者 bit5 都是 1**。
> 也就是说走"常量"那条路时 bit5 恒为 1（= 关等待）；走"OR"那条路时 bit5 取决于前两个 regkey，
> 默认都是 0 → **bit5 = 0，wait 生效**。这与实测的 live 值一致（见 §3）。

### 2.3 门 3：`ctx+0x8e0dc8`

全库只有一处写：`123819f: mov %al,0x8e0dc8(%rbx)`，在 `0x1237xxx`（state=3 那条流）里。
没有发现外部可影响的入口，暂不作为开关。

## 3. 实测 bit5：能置位，但置了就废

`n7_flagpoke.sh`（读 → 测 fps → 置 bit5 → 测 fps → 还原）：

| 阶段 | flags | fps |
|---|---|---|
| 基线 | `0x0fc00009`（**bit5=0**，与静态推断一致） | **32.00** |
| 置 bit5 | `0x0fc00029`（bit5=1） | **3.00** |
| 还原 | `0x0fc00009` | 29.83 |

**置位后 fps 掉到 3**，因为 bit5 不只门控 wait，还门控 **signal**：

```
1238d9c: testb $0x20,0xc08(%rax)
1238da3: jne   1238dbc            ; bit5=1 → 跳过下面的 signal
1238dac: mov   0x8e0910(%rdi),%rdi
1238db3: call  *0x2d8(%rax)        ; signal

1238d3d: testb $0x20,0xc08(%rax)
1238d44: je    1238d50             ; bit5=0 才去 signal
...
1238d50: mov 0x8e0910(%rbp),%rdi
1238d57: mov 0x2d8(%rax),%rax
1238d5f: jmp *%rax                 ; signal

1237644: testb $0x20,0xc08(%rax)
123764b: je    1237670
123764d: lea   2a6e7e0,%rbp        ; 走另一条（vtable+0x1e0）
```

**bit5 的真实语义 = "没有别的线程要唤醒"**（单消费者/无需跨线程通知模式）。
在当前多线程架构下强行置位 → 消费者永远等不到通知 → 退化成全靠超时，fps 3。

> **这条路的判决：不是开关，是"模式"。**
> 想靠它关掉 wait，等于同时关掉 signal，等价于把流水线拆掉。

## 4. ★ 副产品：cond 拓扑更正报告 33

`ctx+0x8e0950` 全库只有两处引用：`123b309`（当作 cond 传给 `wait_ms`）和 `123c3ea`（初始化写入）。
后者是 8 字节 `mov %rax` → 说明这些字段是**指向 cond 对象的指针**，不是对象本身：

```
123c3c6: call *0x2c0(%rbx)  → rax = 新 cond
123c3cc: mov  %rax,0x8e0918(%r12)
123c3d4: mov  %rax,0x8e0958(%r12)      ; 一对（A）
123c3dc: call *0x2c0(%rbx)  → rax = 新 cond
123c3e2: mov  %rax,0x8e0910(%r12)
123c3ea: mov  %rax,0x8e0950(%r12)      ; ★ 一对（B）—— 我们等的和 signal 的是同一个对象
123c3f2: call *0x2c0(%rbx)  → rax = 新 cond
123c40b: mov  %rax,0x8e0948(%r12)
123c413: mov  %rax,0x8e0908(%r12)      ; 一对（C）
```

**ctx 里是三对 cond，不是一堆独立 cond。** 而：

| 用途 | 用哪个槽 | 指向 |
|---|---|---|
| **等待**（`wait_ms`） | `0x8e0950` | 对象 **B** |
| 队列处理器的 notify（`123af7f`） | `0x8e0948` | 对象 **C** |
| 另一处 notify（`1238d57` / `14a6696`） | `0x8e0910` | 对象 **B** ✅ |

**所以报告 33 的"cond 路由有选择性"要更正为：不是选择性，是根本不同的对象。**
`123af7f` 的那次 notify 走的是 pair-C，永远不可能唤醒等 pair-B 的线程——这不是 bug，
是"完成通知"与"有活可干"两件事分属不同 cond。

**真正能唤醒该等待的是 `0x14a669d` 的 `call *0x2d8`**（同样受 bit5 门控），
它在 `0x14a6670` 附近，功能是置 `ctx+0x8e0924=1`、`ctx+0x8e0964=1` 然后 signal。
→ 这就是用户要追的"8838 那条链"的**正确起点**（报告 33 追的 `123af7f` 是错的对象）。

## 5. ★ 一字节补丁：把"预先睡"改回"轮询"——只值 15%

报告 35 找到的分叉是：**525 一看到队列空就睡，515 先轮询（10 万次预算）再睡。**
这个分叉可以用 1 个字节直接测：`123b2fd` 的 `jne 123b32f`（0x75）改成 `jmp`（0xeb），
即**无条件跳过 wait**，giveup 那条兜底仍保留 → 不会死锁。

`n8_spinpatch.sh`（**补丁字节已读回验证** `75 → eb → 75`）：

| 阶段 | 字节 | fps | 进程 CPU |
|---|---|---|---|
| 基线 | `75 30 41 80` | **32.00** | 74% |
| 补丁 | `eb 30 41 80` | **36.67**（+15%） | **266%** |
| 还原 | `75 30 41 80` | 27.17 | 71% |

（首轮 `n8a` 得 38.00 → 27.83 / 270%，字节读回因 `sudo -S` 吃掉 heredoc 的 stdin 而失败；
修复后 `n8b` 数据如上。两轮方向不一致但都说明"没有数量级提升"，CPU 4 倍是硬信号。）

**判读**：改回轮询确实能拿回一点（+15%），但**代价是 CPU 从 74% 涨到 266%**，
而且离 515 的 ~108 fps 差了 3 倍。**所以"525 预先睡"不是主因。**

> 这是本轮最重要的一刀：**报告 35 的分叉真实存在，但它解释不了 3 倍差距。**
> 分叉只是"同一个上游瓶颈下，两种不同的等待写法"。

## 6. 重新定位：瓶颈在上游，队列处理器是症状

三条独立证据指向同一处：

| 证据 | 含义 |
|---|---|
| N6：队列上下文 **90~93% 墙钟在等**，每帧一次、每次 23~28ms | 它没活干 |
| 补丁：让它**别睡**（改轮询）→ 只 +15%、CPU 4 倍 | 不是它睡太早，是**真没活** |
| 报告 31：Heaven 下 GPU **48~68W ≈ 空转**、41°C | GPU 也没活干 |

→ **工作只按"一帧一次"的节奏到达**。队列处理器等、GPU 空转、fps 34，都是这一个事实的不同侧面。

那么"一帧 30ms 是怎么来的"就回到报告 26 的 D（回读数据可见延迟 29ms）——但这次有了新解释框架：
**不是"某个东西慢了 29ms"，而是整条链每帧只转一圈，单圈的固有延迟被 90% 的空转放大成了帧周期。**

**这个框架的预测**（下一轮可验证）：若把应用每帧提交的工作量翻倍而帧数不变，等待占空比应基本不变；
若让应用**每帧提交多次**（提高提交频率），等待应被打碎成多段、单段变短，而 fps 上升。

## 7. 所以"N3 要不要做"——结论变了

用户原判断：N3 是"验证修复方向"，不是"解决问题"。现在可以更准确地说：

**N3 已经不是"验证方向"，而是"换个基线看同一个症状"。**
因为：
- 修 525 的两条"开关"路都已实测关闭（§3、§5）；
- 剩下的唯一解释是上游节奏，而**515 的上游节奏为什么快**，恰恰只有 N3 能回答
  （515 的队列上下文占空比是多少？如果是 90% → 515 也空转，那差异在别处；如果是 10% → 515 的工作到达频率高 3 倍）。

**建议：N3 仍然值得做，但目的改为"测 515 的占空比"**，一条命令即可（脚本已备）。

**两个新踩的坑**：

1. **`printf "pw\n" | sudo -S python3 - <<'PY'`**：`sudo -S` 会用管道当 stdin，
   **heredoc 被丢掉**，python 读到的脚本是 "desktop" → 静默失败、输出为空。
   → 必须把 helper 落成文件再 `sudo python3 file.py`。
2. **gdb `x/1dw` 输出的是十进制**（可能是负数），`grep -oE "0x[0-9a-f]+" | tail -1` 会抓到**地址**而不是值。
   → 用 `x/1xw`，或干脆走 `/proc/PID/mem` 自己解。
   （这是"读数抓错行"这类错误的第三次出现——前两次是 `Counter` 取错字段、`ns/us/cn` 同批嵌套。）

## 9. 一句话

**`wait_ms` 是有条件的，条件也找到了（全局 flags 的 bit5，由 `ThreadControl` 系列 regkey 初始化）；
但它和 `signal` 共用一个 bit，关掉 wait 就同时关掉唤醒，实测 fps 3。
退一步的"改轮询"补丁也只值 +15%、CPU 4 倍。
→ 525 的病根不在队列处理器的等待策略，而在上游只按帧喂活。**
