## 1. 假说 1 否证：中断是物理 GPU 的真实 MSI-X

### 1.1 源码：注册在物理 GPU 的中断向量上

`nvidia-vgpu-vfio.c:2986`（`vgpu_msix_set_vector_signal`）：

```c
trigger = eventfd_ctx_fdget(fd);                    /* QEMU 传进来的 eventfd */
if (IS_ERR(trigger)) return -EBADF;

irq = pci_irq_vector(pdev, vector);                 /* ★ 物理 GPU 的中断向量 */

ret = request_irq(irq, vgpu_msix_handler, 0, "nvidia", vgpu_dev);
if (ret) return ret;

vgpu_dev->intr_info.msix[vector].allocated_irq = irq;
vgpu_dev->intr_info.msix[vector].trigger = trigger;

/* APICv 直通：连内核都不用过 */
vgpu_dev->intr_info.msix[vector].producer.token = trigger;
vgpu_dev->intr_info.msix[vector].producer.irq   = irq;
ret = irq_bypass_register_producer(&vgpu_dev->intr_info.msix[vector].producer);
```

### 1.2 源码：中断处理函数就是"物理中断 → eventfd"

`nvidia-vgpu-vfio.c:2953`（`vgpu_msix_handler`）：

```c
static irqreturn_t vgpu_msix_handler(int irq, void *arg)
{
    struct eventfd_ctx *trigger = NULL;
    if (atomic_read(&vgpu_dev->intr_info.ignore_interrupts)) return IRQ_NONE;

    for (i = 0; i < vgpu_dev->intr_info.max_num_vectors; i++)
        if (vgpu_dev->intr_info.msix[i].allocated_irq == irq) {
            trigger = vgpu_dev->intr_info.msix[i].trigger;
            break;
        }

    if (trigger != NULL)
        eventfd_signal(trigger, 1);       /* ★ 直接把 guest 的 irqfd 点起来 */
    else
        return IRQ_NONE;

    return IRQ_HANDLED;
}
```

### 1.3 判定

**中断链：物理 GPU 发 MSI-X → 内核 `vgpu_msix_handler` → `eventfd_signal` → QEMU irqfd → guest。**

- **不是定时器**：`request_irq` 的 handler 只能由该 IRQ 触发
- **不是后台线程**：`vgpu_msix_handler` 在中断上下文执行，返回 `IRQ_HANDLED`
- **没有"算个时间提前发"的可能**：handler 里没有任何时间逻辑
- 更进一步：**`irq_bypass_register_producer`（APICv）会让中断绕过内核直达 guest**，
  这是**比物理机更快的路径**，但不改变"由硬件触发"这一点

**⇒ 用户假说 1（虚假完成）被源码直接否证。vGPU 不是靠"骗 guest 说完成了"来提速。**

> 附：另有一个 `NV_VFIO_VGPU_INJECT_INTERRUPT (0x09)` ioctl，让 vgpu-mgr 主动注入中断。
> 但那是**辅助路径**（INTx / 无 MSI-X 时用），主路径是上面这个真实 IRQ。

## 3. 但"门铃被模拟"这条是真的 —— 只是位置在用户态

`libnvidia-vgpu.so.550.144.02` 的字符串里：

```
error querying doorbell emulation support from RM        ← 门铃模拟
Failed to construct doorbell PF region / VF region       ← 门铃区域是"构造"出来的
Failed to submit doorbell token 0x%x. error:0x%x         ← ★ 提交的是"门铃 token"
failed to send doorbell event with error %x
Timeout waiting for GSP Plugin before triggering doorbell  ← ★ GSP 插件
trigger doorbell interrupt failed, status = 0x%x          ← 由 Host 去触发真实门铃
emulate_channels
channel_usage_threshold_percentage
```

**⇒ 流程是：guest 写门铃（落进被 `remap_pfn_range` 映射的宿主内存页）→ Host 侧 RM 发现 → 提交一个"doorbell token" → 经 GSP Plugin 触发物理 GPU 的真实门铃。**

**这条确实是"异步化"**，但它**不在内核里**，在用户态 RM。而且
**`doorbell token` + `GSP Plugin` 这两个词说明它不是直接写寄存器，而是往一个队列里放条目** ——
**队列天然就有合并/批处理的可能**（这与假说 3 的方向一致，但位置在用户态）。

**注意 §5：这条仍属推断，我没有证明它真的合并了。**

## 4. ★ 最重要的架构修正：Host 内核不在命令路径上

用户设想的模型是"Host 的 vGPU 模块处理 Guest 的 PCI BAR 访问，然后把任务塞进 workqueue"。

**实际不是。NVIDIA 的 vGPU 是三层：**

```
┌─ guest ───────────────────────────────────────────────┐
│  glcore → 写 pushbuffer 到 guest 内存                  │
│         → 写门铃（落在被 remap_pfn_range 映射的宿主页） │
└───────────────────────────────────────────────────────┘
                    ↓ 无 VM exit（稀疏映射窗口内）
┌─ host 内核：nvidia-vgpu-vfio.ko ──────────────────────┐
│  只做五件事，没有一件与"命令"有关：                     │
│   ① mdev 生命周期   ② BAR 稀疏映射（remap_pfn_range）  │
│   ③ 中断转发（真实 IRQ → eventfd）                     │
│   ④ 页钉住（translate_gfn_to_pfn）                     │
│   ⑤ 窗口外的寄存器访问转发（REG_ACCESS_GET/SET ioctl）  │
│  ★ 0 队列 / 0 定时器 / 0 内核线程 / 0 doorbell          │
└───────────────────────────────────────────────────────┘
                    ↓ ioctl
┌─ host 用户态：nvidia-vgpu-mgr + libnvidia-vgpu.so ────┐
│  nvidia-vgpu-mgr (175 KB) = VMIO 插件框架              │
│    只导出 vmiop_* 符号（vmiop_deliver_message /        │
│    vmiop_control_interrupt / vmiop_cv_wait ...）       │
│  libnvidia-vgpu.so (4 MB) = ★ RM 本体                  │
│    6879 个具名 _nvXXXXXXvgpu 符号（后缀 vgpu 而非 rm）  │
│    只依赖 libc/libstdc++，不依赖 libcuda               │
│    引用 /dev/nvidia%d → 通过 nvidia.ko 的 ioctl 操作物理 GPU │
│    只有 3 个 ioctl 调用点（一个通用包装 _nv004229vgpu）  │
└───────────────────────────────────────────────────────┘
                    ↓
              物理 GPU（P106 / GRID P40）
```

### 4.1 为什么这个修正重要

- **想挖"命令怎么被处理"，挖内核模块是白费** —— 它压根不处理命令
- **真正的处理在 `libnvidia-vgpu.so`（用户态 RM）**，6879 个函数，无名字
- 这解释了为什么"内核 blob 对比"（报告 111）一无所获：**方向本身就错了**

### 4.2 `libnvidia-vgpu.so` 的实证数据

| 项 | 值 |
|---|---|
| 大小 | 4,042,872 B |
| 依赖 | **仅** `libstdc++` / `libm` / `libgcc_s` / `libc`（**不含 libcuda**） |
| 动态导出符号 | **7036**（6879 个 `T` 类，即代码） |
| 符号命名 | `_nv000743vgpu` … `_nv004229vgpu` —— **与内核 `_nvXXXXXXrm` 同一套编号风格，后缀换成 `vgpu`** |
| `vmiop_*` 导出 | 8 个（插件 ABI） |
| `ioctl@plt` 调用点 | **3 个**（其一为通用包装，含 EINTR/EAGAIN 重试 + >4 KB 走 `0xc01046d3` 大缓冲变体） |

**⇒ Host 侧 RM 与物理驱动是同一套代码谱系，编译成用户态、通过 `/dev/nvidia0` 的 ioctl 驱动物理 GPU。**

## 5.5 本轮另外排掉的两条候选（都是实测/静态硬否证）

### 5.5.1 GSP 假说 —— 死了（这张卡没有 GSP 硬件）

本机实测：

```
nvidia-smi -q | grep "GSP Firmware"
  → GSP Firmware Version : N/A
/proc/driver/nvidia/params | grep Firmware
  → EnableGpuFirmware: 18
```

`EnableGpuFirmware` 是个位掩码且非零，但 **`GSP Firmware Version: N/A`** ——
**GSP 没有加载，因为 P106 是 Pascal（GP106），根本没有 GSP 硬件**（GSP 自 Turing TU1xx 起才有）。

⇒ `libnvidia-vgpu.so` 里的 `GSP Plugin`、`Timeout waiting for GSP Plugin before triggering doorbell`
是**给 Turing 及以后显卡用的通用代码路径，在这张 Pascal 卡上不会被走到**。

**⇒ "vGPU 用 GSP 异步调度所以快" 这条假说被排除。**

### 5.5.2 "guest 侧 glcore 按设备分流" —— 死了（glcore 不分流）

| 检查项 | 525 glcore |
|---|---|
| 含 `vgpu` 的字符串 | **0 个** |
| `$0x1c07`（P106）作为立即数 | **0 处** |
| `$0x1bb0`（P40）作为立即数 | **0 处** |
| `cmp $0x1b38`（P106 的另一写法） | **1 处**（不构成分流） |

**⇒ guest 的 glcore 在物理与 vGPU 下发出的是同一套命令，它不认识设备型号、也不认识 vGPU。**

> 注：报告 96 说的 `LOGVGPU` 检测在 **`nv-kernel.o_binary`（guest 内核模块）** 里，**不在 glcore**。
> 所以"按 vGPU 分流"如果存在，位置只能是 **guest 的 nvidia.ko**，不是用户态。

### 5.5.3 "guest 内核按 vGPU 分流" —— 追下去发现是**命名**，不是分支

用重定位反查 `.rodata` 里所有 vGPU 字符串的引用（**注意：`R_X86_64_32S .rodata+N` 的 addend 是段内偏移，
不是绝对地址** —— 我第一次算错了，和报告 102 同一个坑）：

| 字符串 | 引用数 | 位置 |
|---|---|---|
| `VGPU%d` | 1 | `_nv031372rm+0x155` |
| `RMVGPUGpInBAR0` | 1 | `_nv028486rm+0x5a` |
| `LOGVGPU` | **0** | 无直接引用（可能在指针表/宏里） |
| `VGPU_CONFIG` / `VGPU_PF_REG_READ32` / `CTRL_SET_VGPU_FB_USAGE` / `VGPU_GSP_PLUGIN_TRIGGERED` | **0** | — |

`_nv031372rm+0x155` 处的实际代码：

```asm
57fb8b: mov  %rdx,0x128d0(%rax)
57fb92: mov  $0x0,%rdx
         R_X86_64_32S  .rodata+0x25d85d7        ← "VGPU%d"
57fb9b: call _nv034705rm                         ← snprintf 类
```

**⇒ `VGPU%d` 是传给格式化函数的字符串，用来拼出 "VGPU0" 这类名字，不是控制流分支。**

**⇒ "guest 内核检测到 vGPU 后走不同提交路径" 这条，也没找到证据。**
（真正的 vGPU 判定大概率是某个结构体里的 bool/位域，不会以字符串形式出现 —— 这解释了为什么字符串层查不到。）

## 8. 一句话

**你的三条假说，静态验证的结果是"全部不成立于内核层，且第 1 条被源码正面否证"：**
**中断是 `request_irq` 注册在物理 GPU MSI-X 上的真实硬件中断（`vgpu_msix_handler` → `eventfd_signal`，还能走 APICv 绕过内核），不存在"Host 自己算时间提前发完成"。**
**内核模块里 workqueue / timer / kthread / tasklet 全部为 0，且完全不碰 doorbell —— 它只是 vfio/mdev 的薄壳：映射内存、转发中断、钉页、转发窗口外寄存器访问。**
**命令处理全在用户态 `libnvidia-vgpu.so`（4 MB、6879 个 `_nvXXXXXXvgpu` 函数，是 RM 本体的 vGPU 编译版，经 `/dev/nvidia` ioctl 驱动物理 GPU）。**
**"门铃被模拟 + GSP token 队列"这条是真的，但它在用户态，而且我没有证据证明它做了合并。**
**⇒ 挖内核模块这条路从一开始就是错的 —— 这也是报告 111 一无所获的真正原因。**
