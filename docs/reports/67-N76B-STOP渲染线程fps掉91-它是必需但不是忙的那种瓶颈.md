# 67 · N76-B：STOP 渲染线程 → fps 掉到 2.9（-91%）—— 它是**必需**的，但**不是"忙"的那种瓶颈**

> 2026-10-26 10:40
> 用户判据表：
> | STOP 渲染线程后 | 判读 |
> |---|---|
> | **fps = 0** | 必需线程，但「必需」≠「瓶颈」 |
> | **fps 不变或略降** | 它不决定 fps —— 87% futex 是「没事干在等」 |
> | fps 反而升 | 它在拖后腿 |
>
> **结果落在第一格偏下：fps 从 32.6 掉到 2.9（-91%），不是 0 也不是不变。**
> **但它只占 12.4% CPU —— 所以是"卡在等"的必需，不是"忙不过来"的必需。**

---

## 1. 实测数据

用 primus 自带的 profiler（`PRIMUS_VERBOSE=2`，每轮打印一次）取时间序列：

| 轮次 | 阶段 | fps | app | sleep | map | wait |
|---|---|---|---|---|---|---|
| 1 | 启动 | 0.3 | 96.5% | 3.5% | 0.1% | 0.0% |
| 2 | 基线 | 32.6 | 35.2% | 52.4% | 6.4% | 5.9% |
| 3 | 基线 | 27.9 | 0.0% | 89.9% | 9.9% | 0.2% |
| 4 | 基线 | 30.7 | 0.0% | 89.9% | 9.9% | 0.2% |
| 5 | 基线 | 34.3 | 0.0% | 89.9% | 9.8% | 0.3% |
| **6** | **STOP 期间** | **2.9** | **0.0%** | **99.2%** | **0.7%** | **0.0%** |
| 7 | 恢复 | 34.2 | 0.2% | 89.5% | 10.1% | 0.2% |
| 8 | 恢复 | 29.5 | 0.0% | 89.8% | 10.0% | 0.2% |
| 9 | 恢复 | 26.3 | 0.0% | 89.9% | 9.8% | 0.2% |

**STOP 期间 fps = 2.9（基线的 8.9%），CONT 后完全恢复到 26~34。**

### 1.1 同时观测到的其它量

| 量 | 基线 | STOP 期间 |
|---|---|---|
| GPU util | **100%** | **0%** |
| GPU 功耗 | 54.9 W | **36.4 W** |
| 进程状态 | R | **TLl**（T=stopped, L=有线程停, l=多线程） |
| **display worker 的 `draw+swap`** | 17.7% | **94.1%** |
| display worker 的 `wait` | 77.9% | **5.6%** |

### 1.2 ★ 一个意外收获：STOP 后 display worker 卡在 `draw+swap`

```
基线    : display 32.6 fps, 77.2% wait, 4.5% upload, 18.3% draw+swap
STOP 期间: display  2.9 fps,  5.6% wait, 0.4% upload, 94.1% draw+swap
```

**它从"77% 在等"变成"94% 卡在 draw+swap 里"。**

说明 display worker 拿不到新数据时，不是干脆不干活，而是**陷在 `draw+swap` 内部**（大概率是在 `glXSwapBuffers(ddpy)` 上）。

**→ 链条是串行的：渲染线程 → display worker → 上屏。断掉第一段，后两段都停。**

## 2. 按用户判据读

| 用户判据 | 实测 | 判定 |
|---|---|---|
| fps = 0 | 2.9（不是 0） | 接近但不完全相同 |
| fps 不变/略降 | -91% | ❌ |
| fps 反而升 | — | ❌ |

**落在第一格**：**它是必需线程，在关键路径上。**

但用户自己那句「**必需 ≠ 瓶颈**」是本报告最该接下去的地方。

### 2.1 为什么"必需"还不够

把三条已知量摆在一起：

| 量 | 值 | 来源 |
|---|---|---|
| STOP 它 → fps | **掉 91%** | 本报告 |
| 它占的 CPU | **12.4%**（3.82ms/帧） | 报告 64（utime 差分） |
| 它等的时间 | **87%**（27.0ms/帧，`futex_wait_queue`） | 报告 64 |

**"掉 91%"和"只占 12.4% CPU"同时成立，只有一种解释：**

**它不是"忙不过来"，是"卡在等"。整条帧流水线被它这一段的等待串起来了。**

**如果它是"忙"的瓶颈，它应该接近 100% CPU。它只有 12.4%。**

### 2.2 那 27ms 的等，是"没事干"还是"被挡住"

用户原话有两种可能：

| 可能 | 特征 | 本例 |
|---|---|---|
| (a) 没事干在等（上游喂得慢） | 上游也没有满速 | 主线程 16.2%、上屏线程 18.6%、全进程 **72.6%**（8 核） |
| (b) 被挡住（下游不接） | 下游也满速 | 同上，下游也很空 |

**两种都不是——是"全都很空"。**

| 线程 | CPU |
|---|---|
| 上屏线程 | 18.6% |
| 主线程 | 16.2% |
| **渲染线程** | **12.4%** |
| 其余 | 各 ≤10% |
| **全进程合计** | **72.6%**（8 核理论 800%） |

**→ 整机 CPU 空闲、GPU 只有 55W（TDP 120W）、fps 32。**

**这是典型的"流水线串行 + 每段都有固定延迟"，不是"某一段算得慢"。**

## 3. 完整图景：这是一条**串行流水线**

把报告 57 / 64 / 66 / 67 拼起来：

```
主线程  ──glXSwapBuffers──► sem_wait(&di.r.relsem) ──等──► readback worker 提交 glReadPixels
   ▲                                                            │
   │                                                            │ 提交后 sem_post
   └────────────────────────────────────────────────────────────┘
                                                                │
readback worker ── glReadPixels ──► 驱动队列空？──等──► 上游填队列
                                                                │
display worker ── glTexSubImage2D + glXSwapBuffers(ddpy) ──► Intel 上屏
```

### 3.1 关键：**每帧要跑完这一整圈**

- 主线程等 readback worker（报告 57 的 `sem_wait`，实测 `st` 段 5.34ms）
- readback worker 等驱动队列（报告 66，实测 27.0ms/帧，2.86 次/帧）
- display worker 等数据（报告 67，`wait` 77.9%）

**三段都是等，加起来 ≈ 30.84ms = 一帧。**

**没有任何一段是"算得慢"——都是"在等下一段"。**

### 3.2 这解释了为什么前面所有优化都无效

| 已做的尝试 | 为什么无效 |
|---|---|
| 改 primus 4 个可动点（报告 58/59） | 少了某段的数据搬运，但**串行结构没变** |
| 改 GLX 层 | 协议转发不是瓶颈 |
| 换 zink（GL→Vulkan） | **zink 也是同一套"提交→等待"串行结构** |
| 把 `wait_ms` 改回轮询（报告 37） | **+15%** —— 消除等待不改变串行依赖 |
| 改队列处理器（报告 66） | 两版同构，没法改 |

**单点优化对串行流水线无效。** 这是本报告最重要的结论。

### 3.3 primus 已经做了部分重叠，但不够

primus 用**双 PBO**（`cbuf ^= 1`）+ fence 做了流水线重叠：

```c
// readback_work:
glWaitSync(di.sync, ...);          // 等主线程的 fence
glReadPixels(..., NULL);           // 读进当前 PBO
if (!primus.sync) sem_post(&di.r.relsem);   // 立刻放行主线程
usleep(sleep_usec);
pixeldata = glMapBuffer(...);      // 映射上一个 PBO
...
cbuf ^= 1;                          // 换 PBO
```

**理论上主线程可以在 readback worker 处理上一帧时渲染下一帧。但实测主线程仍在等（`st` 段 5.34ms）。**

→ **重叠不充分：`sem_post` 之后主线程还是要等一个几乎整帧的时间才能下次 swap。**

## 4. 结论

| # | 结论 | 强度 |
|---|---|---|
| 1 | **STOP 渲染线程 → fps 32.6 → 2.9（-91%）** | **铁证** |
| 2 | GPU util 100% → 0%、功耗 55 → 36W | **铁证** |
| 3 | **display worker 从 77% wait 变成 94% draw+swap（卡住）** | **铁证** |
| 4 | 它是**必需**线程，在关键路径上 | **铁证** |
| 5 | **但它只占 12.4% CPU —— 是"卡在等"而非"忙不过来"** | **强** |
| 6 | 全进程 CPU 72.6%（8 核）、GPU 55W/120W → **全线空闲** | **强** |
| 7 | **这是一条串行流水线：主线程 → 渲染线程 → display worker → 上屏** | **强（由 1/3/5 推出）** |
| 8 | **单点优化对串行流水线无效** —— 解释了既往所有排除 | **强** |

### 4.1 对"能不能修"的回答

**如果瓶颈是"串行流水线的总延迟"，那优化方向只有两个：**

| 方向 | 可行性 |
|---|---|
| **减少段数**（去掉某一段的往返） | 需要改 primus 架构，且**两版 primus 相同**，不解释 3 倍差异 |
| **加深重叠**（让多帧同时在流水线里） | primus 已用双 PBO；加到 N 个 PBO 可能有效，但同样**不解释 3 倍差异** |

**关键矛盾**：串行流水线这个结构，**515 和 525 是同一套 primus，结构一样**。
→ **串行结构解释"为什么只有 32fps"，但不解释"为什么 515 有 108fps"。**

**所以 3 倍差异仍然是"每段延迟在 525 上更长"，而不是"结构不同"。**

而每段延迟更长的候选，现在只剩：

| 候选 | 状态 |
|---|---|
| 渲染线程等队列的时间（27.0ms） | 515 未测 ← **N76-A** |
| 主线程 `sem_wait` 的时间（5.34ms） | 515 未测 |
| display worker 的 wait（77.9%） | 515 未测 |

**三个都是"515 未测"。** 这就是为什么 N76-A 现在是唯一的下一步。

## 5. 下一步

**N76-B 的结论是"它是必需的，且瓶颈是整条串行链"，这没有推翻 N74/N75 的方向，但把问题重新表述了：**

> 不是"渲染线程慢"，而是"这条链的每一段在 525 上都更长"。

| 选项 | 内容 | 代价 | 回答 |
|---|---|---|---|
| **A（推荐，需换驱动）** | **N76-A**：515 上补同一套三段测量 —— 渲染线程 utime/wchan/futex、主线程 `st` 段、display worker 的 profiler 分解 | 换驱动 ~15min | **三段里哪一段在 525 上变长了** ← 现在这是唯一能定位的 |
| B（零成本） | 在 525 上再做一个 STOP：STOP **display worker**，看 fps | 一次 2min | 补全"三段各自必需性"的图；但不太可能改变结论 |
| C（零成本） | 用 `PRIMUS_SYNC=1` 强制同步模式，看 fps | 一次 2min | 换一种重叠策略，看结构本身有多少余量（报告 57 测过：fps 不变 32.8 vs 32.6） |

**建议 A**。因为 B 和 C 都做过了或信息量低，而"哪一段变长"是唯一还没答的问题。

### 5.1 一个必须先接受的可能

**如果 515 上也测出三段同样长、同样串行，那么 3 倍差异就不在 primus 链条的任何单段里。**

那时唯一的解释是：**同样的代码，在 525 上每次往返都更贵** —— 而"每次往返"的成本由谁决定？

| 可能 | 判据 |
|---|---|
| 内核调度延迟（futex 唤醒 → 被调度上 CPU 的间隔） | 测 `sched_wakeup` → `sched_switch` 的间隔 |
| 驱动内部的 signal 延迟 | 测 signal 发出 → 等待方被唤醒的间隔 |
| CPU 频率/缓存 | 两版对比 CPU 频率（但实测都是 1911MHz、满频） |

**"唤醒延迟"是唯一还没测过的量。** 这也可能是 N76-A 之后的下一个方向。

### 6.1 方法论（三条，已入技能库）

1. **STOP 实验要配"它占多少 CPU"一起读。**
   只看"STOP 后 fps 掉 91%"会得出"它是瓶颈"；
   配上"它只占 12.4% CPU"才知道是"卡在等"而非"忙不过来"。
   **判据：STOP 掉 fps + 高 CPU → 真是瓶颈；STOP 掉 fps + 低 CPU → 是串行链的一环。**

2. **STOP 一个线程时，要同时观测**其它线程的相对状态**。**
   本例 display worker 从 `77.9% wait` 变成 `94.1% draw+swap` —— 这个变化暴露了"串行依赖"关系。
   **只测 fps 会漏掉"谁卡在哪"这个信息。**

3. **`ps -o stat` 的 `T` 标志能确认 STOP 真的生效。**
   本例 `TLl` = `T`(stopped) + `L`(有线程停) + `l`(多线程)。
   如果只看到 `R` 而 fps 掉了，说明 STOP 没打中目标线程。
