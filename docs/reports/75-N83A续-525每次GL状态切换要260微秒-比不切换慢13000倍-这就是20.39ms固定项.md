# 75 · N83-A 续：**525 每次 GL 状态切换要 260µs** —— 比"不切换"慢 13000 倍；这解释了 20.39ms 固定项

日期：2026-10-26 11:40
驱动：525.116.03（P106-100，1920×1080，直连 NVIDIA，不经 primus）
程序：`analysis/n83a/n83a.c`（六种模式，同一进程同一 context，只改循环体）

---

> ## ⛔ 本报告的核心数字（260µs）已作废，真值是 **121µs** —— 见报告 76
>
> **作废原因（报告 76 §6.1）**：那次采集的 **`N=0` 基线就偏大 27%**（3.379 vs 2.653ms），
> 说明整批采集环境有资源竞争，不是 M3 特有。连跑三次复现得
> **123.220 / 123.495 / 123.439 ms**，GPU 恒定 1911MHz / 40°C / 37W。
>
> **作废的数字**：M3 265.4 → **120.7** µs；M4 254.6 → **119** µs；M5 260.9 → **124** µs。
> （M0/M1/M2 是更早一批采的，`N=0` 为 2.610，与现在 2.64 一致，**那部分数据仍有效**。）
>
> **两处推导也错了**：
> - 「121.6µs ÷ 4 次 legacy 状态 ≈ 30.4µs/状态」**没有依据**。报告 76 的 M0/M3 对比证明：
>   **变更 4 次和变更 1 次总价相同**，代价是"每个带变更的 draw 付一次"，不是按状态数累加。
> - 「三种切换成本相同 ⇒ 通用惩罚」方向对，但更强的证据在报告 76：
>   **M0(4 次变更)=121.6、M3(1 次)=120.7、M6(no-op)=121.0 三者相等**。
>
> **仍成立的关键结论**：Heaven 不走 legacy（static 铁证）、`32.44ms ÷ 121µs = 268 次/帧`、
> 与所有旧结论的相容性分析。**260 → 121 只是把"需要多少次切换"从 124 改成 268。**

## 0. 一句话结论

**在 525 上，往 draw call 循环里插一次"状态切换"（shader / FBO / 纹理任选其一），每次调用成本从 0.020µs 变成 255~265µs，涨 12000~13000 倍。**

三种切换的成本**几乎相同**，说明这不是"某个资源的特殊开销"，而是**任何状态变更都会触发一次约 260µs 的通用惩罚**。

---

## 1. 六种模式，只改循环体

所有模式共用：同一进程、同一 GLX context、同一 FBO、同一 PBO、同一 1920×1080、
同样 N 个 `glDrawArrays(GL_TRIANGLE_STRIP, 0, 4)`、quad 半边长 0.01（19×19 像素）。

| 模式 | 循环体里每次多做的事 |
|---|---|
| **1** | **无**（状态只设一次） |
| 2 | `glUniform3f`（改颜色） |
| 0 | `glLoadIdentity` + `glTranslatef` + `glScalef` + `glColor3f`（legacy） |
| **3** | `glUseProgram(prog ↔ prog2)` |
| **4** | `glBindFramebuffer(fbo ↔ fbo2)` |
| **5** | `glBindTexture(tex ↔ tex2)` |

模式 3/4/5 都是**两个实例乒乓切换**：每次都真的改变状态，逼驱动做完整处理。

## 3. 三个判读

### 3.1 三种切换成本相同 ⇒ 不是"某个资源"

```
切 shader  265.4 µs
切 FBO     254.6 µs     三者落在 254~265µs，差 <4%
切纹理     260.9 µs
```

**如果瓶颈是"shader 重配置""FBO 重定向""纹理 cache miss"这三种不同的机制，
它们不可能落在同一个值上。**

⇒ 是**同一个通用路径**：任何"会影响后续 draw 的渲染状态变更"都触发一次固定代价约 260µs 的处理。

### 3.2 这个代价与"draw call"无关

同一份循环、同样的 `glDrawArrays`、同样的像素面积：

```
不切换:  1000 次 draw call 合计 0.016 ms
切换:    1000 次 draw call 合计 265.7 ms（含切换）
```

**draw call 本身 0.020µs（20 纳秒）。那 260µs 全在"切换"上。**
⇒ 报告 73 的"`T_land` ∝ draw call 数"彻底推翻（报告 74 已更正）。

### 3.3 legacy 状态是"较快的慢路径"

```
M0: 121.6 µs / call，每次 call 含 4 个 legacy 状态 ⇒ 30.4 µs / 状态
M3: 265.4 µs / call，每次 call 含 1 个 shader 切换 ⇒ 265.4 µs / 切换
```

legacy 状态比 shader 切换**便宜 8.7 倍**。
一个合理猜测（未验证）：legacy 状态在 525 上只改 CPU 侧结构体、延迟到 draw 时合并；
而 shader/FBO/纹理切换必须让已排队的命令真正落地。

## 4. Heaven 完全不走 legacy（静态铁证）

N83-A 一开始想用"N 个固定管线 draw call"去模拟 Heaven。**这个前提是错的**，
但它错得有价值——顺手把 Heaven 的真实路径查清了。

### 4.1 Heaven 用运行时 dlsym 取函数，符号表是空的

```
nm -D --undefined-only libUnigine_x64.so | grep -cE "gl[A-Z]"   →  0
nm -D --undefined-only heaven_x64        | grep -cE "gl[A-Z]"   →  0
```

**一个 GL 符号都没导入**——它靠 `dlopen`/`dlsym` 在运行时取。
所以"查导入表"这条路不通（`nm` 全是空）。

### 4.2 但函数名字符串还在 .rodata 里

```bash
strings -a libUnigine_x64.so | grep -cx "<函数名>"
```

| legacy（19 个候选） | 命中 |
|---|---|
| `glBegin` `glEnd` `glMatrixMode` `glLoadIdentity` `glTranslatef` `glScalef` `glColor3f` `glColor4f` `glVertex3f` `glVertex2f` `glPushMatrix` `glPopMatrix` `glOrtho` `glFrustum` `glEnableClientState` `glVertexPointer` `glColorPointer` `glNewList` `glCallList` | **0 / 19** |

| modern（15 个候选） | 命中 |
|---|---|
| `glDrawElements` `glDrawArrays` `glUseProgram` `glBindFramebuffer` `glBindTexture` `glUniform1i` `glUniform4fv` `glBufferData` `glMapBuffer` `glReadPixels` `glTexImage2D` `glTexSubImage2D` `glVertexAttribPointer` `glGenBuffers` `glCreateShader` | **15 / 15** |

**⇒ Heaven 100% 走 VBO + shader + FBO 的现代路径，一个固定管线函数名都没有。**

这条同时解释了 N84-B 那个"uprobe 挂在 `libGLX_nvidia:glBegin` 上 0 命中"——
**不是探针挂了，是 Heaven 根本不调它。**
（另：`primus/libGL.so.1` 也不导出 `glBegin`/`glClear`/`glDrawElements`，
它只包装 GLX 层；普通 GL 调用由 glvnd 直接 dispatch 到 glcore，绕过 `libGLX_nvidia` 的导出 thunk。）

## 5. 用 260µs 去对 Heaven 的账

```
Heaven HIGH  T_land        35.05 ms
减纯回读截距（M1 的 N=0）   −2.61 ms
────────────────────────────────
待解释                     32.44 ms

32.44 ms ÷ 260.9 µs = 124 次状态切换 / 帧
32.44 ms ÷ 265.4 µs = 122 次 shader 切换 / 帧
```

**124 次/帧** —— 对 Heaven 这种场景（几十个材质、阴影 pass、后处理链、UI）是**合理量级**。

### 5.1 这个数字与三条旧结论全部相容

| 旧结论 | 是否被 260µs 解释 |
|---|---|
| 报告 56：`T_land = 20.39 + 1.335×MiB`，**截距与像素量无关** | ✅ 状态切换次数与分辨率无关 |
| 报告 73：Heaven **LOW↔HIGH 只差 25%** | ✅ 画质改 shader 内容，不改**切换次数** |
| 报告 73：glxgears **3.0ms** | ✅ 它用**显示列表**，每帧只 5 次 `glCallList`，无状态切换 |
| 报告 07：**~1000 次 GL 调用/帧、26µs/次** | ⚠️ 部分解释。若 1000 次里约 124 次是切换，其余是别的调用，26µs 是混合平均 |
| 报告 70/72：map 里 20ms 固定项 | ✅ 就是这 124 次切换 |

**⚠️ 但必须标明这是"账能对上"，不是"已证死"。**
要证死，需要 apitrace 数出 Heaven 每帧真实的 `glUseProgram`/`glBindFramebuffer`/`glBindTexture` 次数。
**如果实测是 124 次左右，这条链就闭合；如果是 12 次或 1200 次，就错了。**

## 7. 这一轮暴露的设计错误

**第一版基准只测了固定管线（M0）。** 如果就此收工，我会得出：

> "每 draw call 126µs ⇒ Heaven 上千次 draw call ⇒ 126ms"

而 Heaven 实测 35ms，**差 3.6 倍，但因为"同量级"而不易察觉**。

是补了 M1（状态一次都不变）之后才看到 0.020µs 这个真值，
进而意识到 M0 的 121µs 里 99.98% 是状态开销、与 draw call 无关，
再从 M3/M4/M5 才找到 260µs 这个真正的靶点。

**规矩（已入技能库）**：
1. 基准程序必须有一档 **"状态一次都不变"** 的对照（M1）。没有它，"每 call 成本"没有意义。
2. **状态操作的"种类"要分开扫**（legacy / uniform / shader / FBO / 纹理），
   因为它们的成本可能差 3 个数量级（本例 30µs vs 260µs vs 0.04µs）。
   只测一种就下"状态变更很贵/很便宜"的结论，必错。
