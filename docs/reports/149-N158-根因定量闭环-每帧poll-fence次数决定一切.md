# 报告 149 — 每帧 poll 次数与帧时间（**定量模型已被报告 150 §11 撤回**）

> 日期：2026-10-27 14:40
> 实验机：`<user>@<testhost>`（<testhost>，P106-100）
> 本轮在 525.116.03 与 515.105.01 上各跑一遍，用硬件断点计数
> 前置：报告 146（CPU 陪等）、147（伪造 fence 全败）、148（两版代码同构）

> ## ⛔ 撤回声明（2026-10-27 16:00）
>
> 本文的核心模型「帧时间 = 每帧 poll 次数 × 8 µs」**撤回**，原因是循环论证：
>
> 1. **"每帧次数" = 有干扰的计数 ÷ 无干扰的 fps**。`bpcount` 每次命中都用 ptrace
>    停住目标（几十 µs），fps 被拖慢数倍；分子有干扰、分母没有，相除是噪声。
> 2. **"8 µs 单次成本"是从总时间反推的**。拿结果反推参数再用参数验证结果，必然吻合。
> 3. **`0x1578280`（"等空间"函数）实测只有 8 次/秒 ≈ 1 次/帧**，
>    不是本文假设的"每对一次"。
>
> **仍然成立**（都是无探针的干净测量）：515 M3 = 5.46~7.5 ms / 525 M3 = 127 ms；
> 两版 `chk` 都是 300；运行时标志两版相同；循环本体两版同构（都 208 字节）。
>
> **不要再引用"19,181 次/帧""6.7~9.3 µs""153 ms 预测"这三组数字。**

## 0. 一句话结论

**整件事可以用一个公式解释：**

```
帧时间 ≈ (每帧 poll fence 的次数) × (单次 poll 约 8 µs)
```

| 场景 | polls/帧 | ×8µs 预测 | 实测 total |
|---|---|---|---|
| 515 M1 | 852 | 6.8 ms | **7.05 ms** |
| 515 M3 | 588 | 4.7 ms | **5.46 ms** |
| 525 M1 | 980 | 7.8 ms | **7.96 ms** |
| **525 M3** | **19,181** | **153 ms** | **127.7 ms** |

**只有 525 的 M3 是异类：它每帧 poll 了 19,181 次，其他三个配置都在 600~1000 次。**
19,181 ÷ 1000 对 = **每对 19 次**；而 515 的 M3 每对只有 **0.6 次**。

**这就是 20~24 倍差距的全部来源。**

这轮直接读运行时值（`fielddump`，ptrace 硬件断点，零字节修改）：

## 2. 定量：poll 次数与单次成本

用 `bpcount`（硬件执行断点，统计单位时间内进入函数的次数）测同一窗口（2 秒）：

### 2.1 525.116.03

| 函数 | 计数/秒 | 除以 fps | = 每帧次数 |
|---|---|---|---|
| `0x1572e60`（取 rp） | 150,762（M3）/ 136,281（M1） | ÷7.86 / ÷139 | **19,181** / **980** |
| `0x1569f10`（读 fence） | 133,533（M3）/ 148,595（M1） | | 16,988 / 1,069 |
| `0x15761b0`（退避） | 130,700（M3）/ 120,456（M1） | | 16,629 / 866 |

### 2.2 515.105.01

| 函数 | 计数/秒 | 每帧次数 |
|---|---|---|
| `0xfbae60`（取 rp） | 107,787（M3）/ 120,845（M1） | **588** / **852** |
| `0xfb19d0`（读 fence） | 105,285（M3）/ 143,175（M1） | 575 / 1,009 |
| `0xfbcc30`（退避） | 108,543（M3）/ 118,781（M1） | 592 / 837 |

### 2.3 单次 poll 成本（由总时间反推）

| 配置 | total_p50 | polls/帧 | **每次** |
|---|---|---|---|
| 515 M1 | 7.049 ms | 852 | **8.3 µs** |
| 515 M3 | 5.458 ms | 588 | **9.3 µs** |
| 525 M1 | 7.960 ms | 980 | **8.1 µs** |
| 525 M3 | 127.7 ms | 19,181 | **6.7 µs** |

**四个独立配置都落在 6.7~9.3 µs，一致性极好。**
这个 8 µs 是**读一次 BAR0 寄存器**的代价（`0x1575990`/`0xfbc490` 里那条 `mov eax,[rax]`），
与哪一版驱动无关，是本平台（P106 在 PCIe 上）的固定属性。

### 2.4 模型校验

用 §2.3 的 8 µs 去算 M1/M3 的差：
- 525：`(19181 - 980) × 8µs = 145.6 ms`，实测差 `127.7 - 7.96 = 119.7 ms`
- 515：`(852 - 588) × 8µs = 2.1 ms`，实测差 `7.05 - 5.46 = 1.59 ms`

量级和方向都对。**多出来的 18,201 次 poll 就是那 120 ms。**

## 3. 为什么 525 每对要 poll 19 次

515 的 M3 里，13 个退避调用点**只有 1 个活跃**（`0xfbede0`，1,235 次/秒 =
每帧 6.7 次，占 1000 对的 0.7%）——**515 基本不重试，一次就过。**

525 的 M3 是每对 19 次 ⇒ 说明"申请空间"这一步连续失败 ~18 次才成功。

这解释了此前所有互相矛盾的观测：

| 观测（报告） | 用本模型解释 |
|---|---|
| 报告 136：每次绑定固定 122 µs | 19 × 6.7 µs = 127 µs ✓ |
| 报告 136：与分辨率/对象类型无关 | poll 次数与画什么无关 ✓ |
| 报告 136：M8（1000 绑定+1 draw）= 2.97 ms 正常 | 只有 1 次 draw，几乎不 poll ✓ |
| 报告 147：GPU 功耗只 +1.1 W | GPU 大部分时间没事干（CPU 在 poll）✓ |
| 报告 147：CPU 侧五次补丁全无效 | 改退避时长/删退避函数不减少**次数** ✓ |
| 报告 147：`-R` 快 63 倍 | `-R` 不等完成 ⇒ 不做那 19 次 poll ✓ |
| 报告 148：两版 fence 代码逐条同构 | 代码一样，**调用次数**不一样 ✓ |

> ⚠️ 报告 147 的"删掉 `0x15761b0` 总时间不变"现在有了正确解释：
> 删掉的是**每次 poll 的退避等待**，但 poll 本身（`0x1572e60` → MMIO 读）还在，
> 19 次照做，所以总时间不变。**我改的是"等"，没改"问"。**

## 4. 试过但失败的捷径：直接把 fence 读改成读内存

`0x1569f28` 是 `test eax,eax; je 0x1569f50`（缓存标志为 0 就跳去 MMIO）。
把 `0x1569f2a` 的 `74` 改成 `75`（je→jne），强制走缓存路径：

```
[patchpb] 0x1569f2a  原文 74  ->  75   [已改写]
→ 程序挂死（60s 超时，无输出）
```

原因：缓存里的值是 **146**，而已提交到 **150**。强制读缓存 ⇒ 驱动永远认为"没空间"
⇒ 重试循环永不满足 ⇒ 挂死。

> 这也印证了报告 147 的结论：**伪造一个不跟踪真实进度的值，必然死锁。**
> 缓存路径要能用，前提是 GPU 真的会 DMA 写这块内存（vGPU 场景的做法），
> 而裸机上这个机制没被启用（`[ctx+0x21c]=0`）。

## 5. 工程目标已经非常具体

**把每对的 poll 次数从 19 降到 1。**

预测：`1000 次 poll × 8 µs = 8 ms` ⇒ 约 **125 fps**，正好是 515 的水平（5.46 ms / 183 fps 的同一量级）。

三条可走的路，按性价比排：

### 路 A：找出"为什么第 1 次申请会失败"（最治本）

19 次失败说明"申请的空间量"大于"当前可用量"。如果能让它第一次就申请到合适大小
（例如不要把每个 bind+draw 对都当批次边界），poll 次数自然降到 1。

**下一步就是找那个重试循环。** 已知：
- `0x1572e60`（取 rp）**没有直接调用者**，是通过函数指针调的
- `0x15761b0`（退避）有 13 个直接调用点，但 515 上只有 `0xfbede0` 活跃，
  而退避函数总调用量（108k/s）远大于该点（1.2k/s）⇒ **大部分也是间接调用**

所以要用"读返回地址"的办法：在退避函数入口断下，读 `[rsp]` 拿调用者。
（`rpsample2.c` 已有这个技巧，改成断点版即可。）

### 路 B：让 poll 变便宜（治标但见效快）

8 µs 是 BAR0 读的代价。要降到内存读的 ~50 ns，需要启用缓存路径——
但那要求 GPU 侧真的把进度写进内存（DMA），裸机上没这个设置。
**除非能让驱动自己建立这个机制，否则此路不通。**

### 路 C：减少 poll 的粒度（工程折中）

若 poll 只在"每帧一次"而非"每对一次"，M3 就变成 M1 的行为。
这需要改变驱动的批次策略，属于驱动内部逻辑，风险大。

## 6. 本轮工具与两个必须记住的坑

| 工具 | 用途 |
|---|---|
| `analysis/onheap/fielddump.c` | 断点 + 按 spec 读任意字段（含一级指针解引用），如 `0x3c0:p+0x48:u32` |
| `analysis/onheap/bpcount.c` | 统计某函数在 N 秒内被调用次数，自动选 CPU 时间最大的线程 |
| `analysis/onheap/rpsample2.c` | ptrace 采样 RIP + 定位 `sched_yield` 调用者（修掉了报告 146 的地址标记 bug） |

### 6.1 坑一：断点工具必须显式传 glcore 基址，或自动从 maps 取

我第一次把 base 传 0，断点落在未映射地址，得到"所有线程未命中"，
差点误判成"该函数没被调用"。**阳性对照（断一个已知高频函数）救了这次。**

### 6.2 坑二：`bpcount` 用阻塞 `waitpid` 会永久卡住

断点不命中时 `waitpid(…, 0)` 永不返回，实测卡了 **157 秒**。
必须改成 `PTRACE_CONT` 一次 + `waitpid(WNOHANG)` 轮询 + 到点退出。
注意也不能每次循环都 `PTRACE_CONT`（对已运行的 tracee 会 EIO）。

## 8. 追加：找到了那个"等空间"的循环本体，两版完全同构

顺着 515 上唯一活跃的退避调用点 `0xfbede0` 反查，循环本体是 `0xfbed80..0xfbee50`（**208 字节**）。
在 525 里按同样的字节特征（`mov esi,0x12` + 退避 + 立即重新取 rp）找到 `0x1578280..0x1578350`，
**也是 208 字节**，逐条对应：

### 515 `0xfbed80`

```asm
fbed87  cmp  [ctx+0x10d0], rsi        ; 已提交位置 == 请求位置？
fbed91  jne  ...
fbed93        call [ctx+0x1a58]
fbed99  r12 = call [ctx+0x1a60]       ; ← 取 rp（函数指针）
        rdx = [ctx+0x10d0]            ; wp
        rax = wp - 请求位置           ; 需要的空间
        rcx = wp - rp                 ; 已腾出的空间
fbedb8  cmp  rcx, rax ; jbe ret       ; 够 → 直接返回
        rdx = wp - [ctx+0x11e0]
        cmp  rax, rdx ; jb -> 提交
fbedd8        esi = 0x12
fbede0        call 退避               ; ← 每次迭代都退避
fbede8  r12 = call [ctx+0x1a60]       ; ← 每次迭代都重新 poll 一次 rp
fbee09  cmp  rdx, rax ; ja -> fbedd8  ; 不够就再来一轮
```

### 525 `0x1578280`

```asm
157828a cmp  [ctx+0x1130], rsi        ; 同上，只是偏移不同
1578291 jne  ...
1578293       call [ctx+0x1a90]
1578299 rbx = call [ctx+0x1a98]       ; ← 取 rp
        rax = [ctx+0x1130]            ; wp
        rdx = wp - 请求位置
        rcx = wp - rp
15782b8 cmp  rcx, rdx ; jbe ret
        rax = wp - [ctx+0x1240]
        cmp  rdx, rax ; jb -> 提交
15782d8       esi = 0x12
15782e0       call 0x15761b0          ; 退避
15782e8 rbx = call [rbp+0x1a98]       ; ← 重新 poll 一次 rp
1578309 cmp  rdx, rax ; ja -> 15782d8
```

对照表：

| 元素 | 515 | 525 |
|---|---|---|
| 已提交位置（wp） | `[ctx+0x10d0]` | `[ctx+0x1130]` |
| 缓存 rp | `[ctx+0x11e0]` | `[ctx+0x1240]` |
| 取 rp 的函数指针 | `[ctx+0x1a60]` | `[ctx+0x1a98]` |
| 退避参数 | `0x12` | `0x12` |
| 函数长度 | **208 B** | **208 B** |
| 函数作用 | 等 `rp` 推进到"请求位置"之后 | 同 |

### 8.1 这个循环的语义

退出条件是 `(wp - rp) > (wp - req)`，等价于 **`req > rp`**：

> **这个函数的语义是"同步等待 GPU 消费到第 req 个位置"。**

每次调用都要等 GPU 真的追上，**每轮迭代重新 poll 一次 rp**（一次 8 µs 的 MMIO 读）。

⇒ 所以 poll 次数 = `调用次数 × 每次调用内部迭代次数`。

- **515 M3**：这个函数每帧只被调用 **6.7 次**（1000 对里 0.7%）
- **525 M3**：每对都走一次，且内部迭代 ~19 轮 ⇒ 每帧 19,181 次 poll

### 8.2 这就是根因的最终形态

```
525：每个 (绑定对象, draw) 对都被当作"批次边界"，提交后立即同步等待 GPU 追上
     ⇒ 每对一次 flush，每次 flush 内部 poll ~19 轮 × 8 µs ≈ 122 µs
     ⇒ 1000 对 × 122 µs = 122 ms

515：整帧的 1000 对几乎不 flush（每帧只有 6.7 次）
     ⇒ 命令连续下发，GPU 连续执行
     ⇒ 5.46 ms
```

**与"inline 上传"的证据完全咬合**（报告 140/145）：
515 用 `0xA140 KEPLER_INLINE_TO_MEMORY_B` 把状态直接写进 pushbuffer
（每帧 6,653 条），**同一条流里顺序可见，不需要 flush**；
525 只写 16 条 inline，状态进显存缓冲，**必须先确认写入到达，于是每对 flush 一次**。

### 8.3 工程上真正该改的地方

不是 fence 读取（两版一样），不是退避时长（改了没用），不是 subchannel（一样），
而是：**让 525 不要在每个 (绑定, draw) 对之后同步 flush。**

优先级：
1. **找到决定"这里是批次边界"的判断点**（状态跟踪器），看能否让它不把每次绑定当边界
2. 若做不到，退而求其次：把 flush 从"每对"改成"每 N 对"或"每帧一次"
   （风险：状态可见性，可能出现画面错误）
3. **不要**再去改 fence 读取路径（已验证无效且会挂死）

### 8.4 一个立即可以验证的推论

既然 515 每帧只 flush 6.7 次 —— 那 **515 在 M3 下画出来的东西和 525 有什么不同吗？**
如果 515 不做每对 flush 却结果正确，就说明 **525 的 flush 是保守的、并非正确性必需**，
那第 1 条路就是可行的。

判据：用两张 `chk` 校验通过的图逐像素比对（n83b 已有 `chk=` 字段）。
