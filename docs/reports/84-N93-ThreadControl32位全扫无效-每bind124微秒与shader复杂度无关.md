# 84 · N93：ThreadControl 32 位全扫无效；每 bind 的 124µs 与着色器复杂度无关（固定握手）

日期：2026-10-26 13:40
驱动：525.116.03（现役）
方法：运行时写 `/proc/pid/mem` 改全局 flags（报告 37 的地址），逐位扫描；`pair_flush` 变参测试

---

## 0. 结论

1. **ThreadControl 全局 flags 的 32 位全扫，无一能让 124µs 消失**（含清掉唯一置位的 bit1）。
   ⇒ **开关型规避方案不存在**（与报告 37 的 bit5 结论一致，现在扩展到全 32 位）。
2. **124µs 与着色器复杂度无关**：`loops=1 / 50 / 500` → 125.3 / 125.7 / 135.9 ms
   （500 那次多出的 10.7ms 是**真实渲染时间**，不是握手）
   ⇒ **是固定握手，不是"重校验/重编译"类计算**。
3. 附带修正一处口径：**直接 GL 进程里这个 flags 字的 live 值是 `0x2`**（bit1），
   不是报告 37 在 Heaven+primus 里看到的 `0x0fc00009`。⇒ 该字内容随路径/配置变化，但**都与 124µs 无关**。

## 1. 位扫描（525，`pair_flush kind=1 N=1000`，基线 124.16 ms）

工具：`n94_scan.py`（定位 glcore 的 .bss 全局 + 读/改位）+ `n94_bitpoke.sh`（逐位跑，poke 后取后 20 帧中位）

| bits | 结果（post-poke map_p50） |
|---|---|
| 0,2,3,4,5,6,7 | 124.11 / 124.14 / 123.99 / 124.13 / 124.13 / 124.15 / 123.99 |
| 8–15 | 123.97 / 124.14 / 124.12 / 124.01 / 124.00 / 124.14 / 123.99 / 123.99 |
| 16–21 | 124.15 / 124.16 / 124.00 / 124.12 / 124.14 / 124.00 |
| 22–27 | 124.18 / 124.17 / 124.18 / 124.01 / 124.18 / 124.17 |
| 28–31 | 125.03 / 125.07 / 125.21 / 125.04（+0.9ms，噪声级） |
| **清 bit1**（0x2→0x0） | **125.14** |

**全部 ~124–125ms，无一有效。**

> 地址换算注意：`0x2a70528` 在 **.bss**（超出文件大小 0x2A40000），必须用 load bias
> （`bias = 第一个 mapping 的 start − 其 file offset`）换算，不能拿"第一个 glcore mapping 的 start"直接加。
> 首次尝试就踩了这个坑（读到 0x2 但地址错位）。修正后读到的仍是 0x2 —— 即**值本身**就是 0x2。

## 2. 着色器复杂度不改变每 bind 成本

`pair_flush kind=1 N=1000`，只改 fragment shader 的循环次数（每像素）：

| shader loops | map_p50 | 相对 loops=1 |
|---|---|---|
| **1** | **125.256 ms** | — |
| **50** | **125.682 ms** | +0.4 ms（0.3%） |
| 500 | 135.940 ms | +10.7 ms（8.5%） |

- loops 1→50（50 倍计算量）几乎不动 ⇒ **不是"按 shader 规模重校验"**；
- loops=500 的 +10.7ms 与"1000 个 quad × 500 次 sin"的渲染时间同量级 ⇒ 那部分是**真渲染**，不是握手。

⇒ **124µs 是一个与"绑什么"无关的固定握手。**

## 2bis. ★ 三种绑定同价：这是"批次断开"的通用成本，不是分类型校验

`n83a -S`（单进程扫 N=0..2000，程序自算斜率），525：

| 模式 | 每次迭代变什么 | N=1000 时 map | N=2000 时 map | 每单位 |
|---|---|---|---|---|
| **M3** | `glUseProgram`（program 切换） | 123.268 ms | 243.603 ms | **120.3 µs** |
| **M4** | `glBindFramebuffer`（FBO 切换） | 121.874 ms | 240.917 ms | **120.1 µs** |
| **M5** | `glBindTexture`（纹理切换） | 123.999 ms | 245.268 ms | **122.1 µs** |

**三种完全不同的绑定，每单位成本一致（120.1~122.1µs，差 <2%）。**

⇒ **这是"任何管线状态绑定 → 批次断开"的通用成本，与绑的是什么无关。**
同时**更正报告 75 的 254/260µs**：那次的口径有偏（当时还没做单进程扫描），正确值是 ~122µs，
与 program 的 120.8µs 同一量级。

配合 §2 的"shader 复杂度无关"、报告 83 的"批大小无关"、报告 76 的"几何/负载无关"，
现在可以下一个很硬的判断：

> **525 的每次"批次断开"固定收 ~122µs，且这 122µs 是 GPU 在等（37W 空转），不是任何形式的计算。**

## 3. 现在这条链的完整表述（修正措辞）

```
525：每次 glUseProgram 调用（不论是否真变、绑哪个 program、shader 多复杂）
     → 驱动强制结束当前批次并等它完成
     → 等的过程：应用线程自旋，每对 ~42 次 sched_yield（报告 83）
     → 等的时间：≈124µs（GPU 在此期间 util 100% 但只有 37W —— 在等不在算）
     → 每帧 268 次 → 33ms → 30~34fps

515：同样的调用不强制结束批次（异步流水）→ 0.03µs/次 → 101fps
```

**已被排除的解释（累计）**：CPU 提交、ioctl、提交器用户态逻辑、命令字/大块上传、
"等 GPU 完成"（真同步 9.6µs）、GPU 忙/排队、515 可开关项、**ThreadControl 全 32 位**、
**着色器重校验（规模无关）**。
