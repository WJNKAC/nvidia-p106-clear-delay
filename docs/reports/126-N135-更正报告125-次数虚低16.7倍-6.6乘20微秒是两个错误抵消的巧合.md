# 报告 126 / N135：**更正报告 125 —— 次数虚低 16.7 倍，"6.6 次 × 20 µs"是两个错误抵消的巧合**

> 时间：2026-10-27
> 环境：<user>@<testhost>（`<testhost>`），P106-100，**525.116.03**，headless X `:2`
> 触发：用户「继续」—— 继续读 pushbuffer 边界常数时，撞出一个必须先修的测量错误
> **性质：自我更正。报告 125 的绝对数字全部作废，比例结论保留。**

---

## 0. 三句话

**① 报告 125 的"525 M3 每对 6.61 次"错了，真实是 108.3 次/对 —— 虚低了 16.7 倍。**

**② 原因是 perf stat 同时挂了 4 个事件，触发 multiplexing，计数被按时间分片缩放了。**

**③ "6.61 × 20 µs = 132 µs ≈ 实测 127 µs"这个"完美闭合"是巧合：次数错小 16.7 倍、单价错大 17 倍，两个错误相乘恰好抵消。**

---

## 1. 怎么发现的

本来在按计划读 pushbuffer 边界常数。先用 tracefs 手写 uprobe（因为 perf probe 的 fetchargs 对 uprobe 不支持，而 tracefs 支持内存解引用）：

```sh
echo 'p:spin525 $SO:0x15761b0 ctx=%di wp=+0x1130(%di):u64 bd=+0x1240(%di):u64' \
     >> /sys/kernel/debug/tracing/uprobe_events
```

读数成功，但顺手数了一下次数，和报告 125 对不上：

| 来源 | 525 M3 spin 次数 |
|---|---|
| 报告 125（perf probe，4 事件同开） | **793,170** |
| tracefs 单事件 | **13,197,448** |

**差 16.6 倍。**

**判据是时间闭合**：
```
13,197,448 × 20 µs = 264 秒 / 120 帧 = 2.2 秒/帧   ← 实测 127 ms/帧，差 17 倍，不可能
793,170 × 20 µs = 15.9 秒 / 120 帧 = 132 ms/帧     ← "吻合"
```

**第一反应是"perf probe 对、tracefs 错"。但用单事件 perf probe 复测，得到 13,283,479 —— 与 tracefs 一致。**

⇒ **13.2M 是真的；793K 是那个被 multiplexing 缩放过的假数。**

⇒ 而"793K × 20 µs ≈ 127 ms"之所以看着吻合，是因为**次数被缩放 1/16.7、单价被错估成 20 µs（实际约 1.18 µs，差 17 倍），两个误差几乎完全抵消**。

## 2. 干净的单事件数据（525.116.03，`-n 1000`，120 帧，只挂 1 个事件）

| 模式 | total_ms | µs/对 | spin 次数 | **spin/对** | 平摊 ns/次 |
|---|---|---|---|---|---|
| M1 只画 | 7.187 | 7.19 | 776,428 | **6.47** | 9.3 |
| M2 改 uniform | 7.205 | 7.21 | 746,681 | 6.22 | 9.7 |
| M3 切不同 prog | 127.073 | 127.07 | 12,996,418 | **108.30** | 9.8 |
| M6 切同一 prog | 129.619 | 129.62 | 13,489,560 | **112.41** | 9.6 |
| M8 只切不画 | 2.972 | 2.97 | 274,208 | 2.29 | 10.8 |
| M9 先切后画 | 7.542 | 7.54 | 749,955 | 6.25 | 10.1 |

**注意最后一列是"平摊"，不是单价** —— 不能用 `total / 次数` 算单价，因为总时间里包含了不归这个函数的部分。

**正确算法是差商：**

```
单价 = (127.07 − 7.19) µs/对 ÷ (108.30 − 6.47) 次/对
     = 119.88 / 101.83
     = 1.177 µs/次
```

**回代验算（这是关键）：**

| 模式 | spin/对 | × 1.177 µs | 实测 µs/对 | 误差 |
|---|---|---|---|---|
| M1 | 6.47 | **7.62** | 7.19 | −5.6% |
| M3 | 108.30 | **127.5** | 127.07 | **+0.3%** |
| M8 | 2.29 | **2.70** | 2.97 | −9.1% |
| M9 | 6.25 | **7.36** | 7.54 | −2.4% |

**全部闭合。⇒ 整条渲染路径的成本几乎全部是这个函数，单价恒为 1.177 µs。**

## 3. 修正后的模型

```
每对时间 = 进入该函数的次数 × 1.177 µs
```

| | M1 | M3 | 倍数 |
|---|---|---|---|
| 525 | 6.47 次 ⇒ 7.6 µs | **108.30 次 ⇒ 127.5 µs** | **16.7×** |
| 515（报告 125 的比例换算） | ~6.45 次 | **~3.84 次** | 0.6× |

> 515 的数字是按报告 125 的比例（515 M3 = 525 M3 的 1/28.7）反推的：`108.30 / 28.7 ≈ 3.8`。
> **515 尚未做单事件实测**（需换驱动），这是本轮唯一的待验项。

**关键结论没变、反而更硬了**：
- **515 M1 与 525 M1 几乎相同**（6.45 vs 6.47）⇒ 基线一致
- **只有 M3/M6 分叉**（515 ~3.8 次 vs 525 108.3 次）⇒ **29 倍差距全部来自调用次数**
- **单价两版相同**（同一个函数，同一段代码）

## 4. 1.177 µs 是什么

函数体（两版同构）：

```
入口: 读 [ctx+0x1300] → 检查 [obj+0x2850] == 1 ? 是则立即返回
      取时 t0；deadline = t0 + 0x14 (20µs)
循环: sched_yield → 取时 → 与 deadline 比较
      未到点则 9×pause → 再取时 → 继续
```

- 纯"取时 + 检查 + 9 pause + 返回" ≈ 50~100 ns
- **实测 1.177 µs，高出一个数量级**

**解释**：`sched_yield` 的返回时机由调度器决定，**耗时是变长的**。
若约 6% 的进入真的走到 yield 并等满接近 20 µs，其余 94% 快速返回：
`0.94 × 0.1 + 0.06 × 20 ≈ 0.094 + 1.2 = 1.29 µs` ≈ 实测 1.177 µs ✓ **量级吻合**

与报告 124 的 `sched_yield` = 7,979,358 次对照：`7.98M / 13.0M 次进入 = 0.61 yield/次`
⇒ **约 39% 的进入至少跑一圈 yield，其余 61% 立即返回**。这个比例与上面的估算同量级。

## 5. 顺带拿到的运行时字段值（这次是真的）

tracefs 计数不可信，但**内存解引用读到的值可信**（与静态代码吻合）：

```
ctx=0x56474f28ce40 (heap)
[ctx+0x1130] = 572      ← 全程恒定
[ctx+0x1240] = 571      ← = 572-1，与静态初始化 `[0x1130]-1 → [0x1240]` 完全一致 ✓
```

另在 pushbuffer 预留入口（0x1578280）读到：

```
size = 0x21e → 0x23a   （542 → 570 字节，每次 +4）
```

**⇒ `bd = wp - 1` 的静态推断被运行时证实。**
**⇒ 但 `[ctx+0x1130] = 572` 全程不变，说明它不是我以为的"动态写指针"** ——
报告 125 里"写指针/读指针比较"的解读需要修正：**动态的那个值是 `call *0x1a98` 的返回值（读指针），不是这个常量字段。**

这一条本轮**未查清**（`0x1578280` 的真实调用频率因 tracefs 计数不可信而无法确定，perf probe 又数出 140 次这个同样可疑的数）。**不编。**

## 7. 方法论教训（最重要的一条）

**perf stat 挂多个事件时，software PMU 事件也会被 multiplexing，显示的计数是按启用时间比例缩放后的估计值。**

本案：4 个 uprobe 同开，得到 793,170；单开得到 12,996,418。**差 16.4 倍，且没有任何警告。**

**规矩**：
1. **要绝对次数，就只挂一个事件。** 多事件只用于求比例。
2. **绝对次数必须做时间闭合检验**：`次数 × 已知单价 ≈ 总时间`。
   本案如果没有这一步，就会带着 16.7 倍的错误继续推下去。
3. **"完美闭合"要反复怀疑**：`6.61 × 20 = 132 ≈ 127` 太巧了，
   而真相是 `108.30 × 1.177 = 127.5`。**两个错误可以互相抵消，闭合本身不证明正确。**
4. **交叉验证要换实现**：perf probe 和 tracefs uprobe 是两套代码路径，
   它们的计数一致才可信（本案 tracefs 和单事件 perf 一致，暴露了多事件 perf 的问题）。

## 8. 一句话

**报告 125 的数字错了 16.7 倍 —— 4 个事件同开触发了 multiplexing。**
**真实是：525 M3 每对进入 108.3 次，每次 1.177 µs，合计 127.5 µs（实测 127.07）。**
**而"6.6 次 × 20 µs = 132 µs"之所以看着闭合，是因为次数被缩小 16.7 倍、单价被放大 17 倍，两个错误相互抵消。**
**结论的方向没变（差距在调用次数，不在单次时长），但以后所有绝对次数都要按 ×16.7 修正，且必须单事件重测。**
