## 3. 修正报告 132

### 3.1 报告 132 说了什么

> "每帧能耗：525 = 9.956 J，515 = 0.305 J，差 32.7 倍 ⇒ GPU 在干 30 倍的活"

### 3.2 哪里错了

**两个错误：**

**错误 A：515 的功耗被低估。**
报告 132 用 1 Hz 采样 6 次取中位数，得到 515 = 36.53 W。
但 515 的帧只有 8.3 ms（占采样周期 1%），1 Hz 采样绝大部分落在空闲，
所以 36.53 W 实际是**空闲功耗**，不是运行时功耗。

**本轮密集采样（0.15s）测到 515 M3 运行中是 58.24 W。**

**错误 B：把"低功耗 × 长时间"误解成"高工作量"。**
525 是 37.4 W（≈空闲）× 261 ms。
**能量确实花掉了 9.9 J，但那不是"计算耗能"，是"空转的基础功耗 × 被拖长的时间"。**

### 3.3 修正后的表述

| | 报告 132 | **修正后** |
|---|---|---|
| 525 状态 | GPU 干了 30 倍的活 | **GPU 几乎空闲（37.4 W ≈ 36.9 W）** |
| 515 状态 | — | GPU 满负荷（58 W）干活 8.3 ms |
| 能耗差 20 倍的含义 | 工作量差 20 倍 | **时间被拖长 31 倍 + 空转基础功耗** |
| 结论 | 工作量问题 | **卡住问题** |

**⇒ 方向又改回来了：这确实是"卡住/等待"，只是卡的方式比原先以为的更具体 ——
不是 CPU 在等 GPU，而是"CPU 和 GPU 互相等"。**

## 4. 修正后的因果模型

### 4.1 三个事实放在一起

| 事实 | 出处 |
|---|---|
| 525 M3 时 GPU 功耗 37.4 W ≈ 空闲 36.9 W | 本轮密集采样 |
| 525 M3 时 fence 推进极慢（gap 98.3% 恒为 5） | 报告 131 |
| 525 M3 时 CPU 在 pushbuffer 预留处每对自旋 108 次 | 报告 126 |

### 4.2 唯一自洽的解释：互相等待

```
CPU 写一批命令 → 需要空间 → 读 fence → 发现没前进 → 等 20 µs → 再读
                                              ↑
GPU 手上有 draw 命令 → 但没执行 → fence 不前进 ┘
```

**为什么 GPU 不执行那些 draw？**

最可能：**GPU 在等 pushbuffer 里某个"可见性/同步"条件**，
而这个条件需要 CPU 做下一步（比如 kick 下一批），
但 CPU 正卡在"等上一批完成"的自旋里，走不到下一步。

**⇒ 一个典型的"生产者-消费者互等"，靠 20 µs 超时一小步一小步地解套。**

**这解释了全部现象：**
- GPU 功耗 ≈ 空闲 ✓（它在 stall，不是在算）
- fence 推进极慢 ✓（每次超时只推进一点）
- CPU 大幅自旋 ✓（在等）
- 515 没事 ✓（它的提交机制不产生这种依赖闭环）
- **M6（切同一 program）比 M3 更糟（15.16 J vs 9.90 J）** ✓ —— 切同一个 program 时，
  驱动的"状态变化检测"可能走了一条更保守的路径，使互等更容易发生

### 4.3 为什么 M1/M8 单独做都正常

- **M1 只画**：命令流是连续的 draw，没有"切换导致的批次边界"，GPU 可以一路跑，不需要等 CPU。
- **M8 只切**：命令流是纯状态设置，GPU 很快处理完，也不产生深依赖。
- **M3 交替**：每一对"切+画"都产生一个**新的批次边界**，边界处需要同步 ⇒ 互等的机会被放大 1000 倍/帧。

**⇒ "批次边界"是关键词。515 的批次边界处理方式不同（可能更粗、更少），所以 8 ms 就干完。**

## 6. 下一步（方向再调整）

**不再是 shader 对比。** 现在该查的是**批次边界处的同步机制**：

| 候选 | 怎么验 |
|---|---|
| **批次数不同**（525 每对开一个新批次） | 已排除：req 两版都是 140（报告 130） |
| **批次边界的 fence 语义不同** | 反汇编 525 里 `0x1578280` 之后的"kick"路径，看它每次 kick 提交什么 |
| **GPU 在等 pushbuffer 的某个同步命令** | 反解 M3 那段 pushbuffer 里的 `0x2001c00d` 类命令 |
| **M6 比 M3 更糟的原因** | 反汇编 glUseProgram 在"同 program"与"不同 program"时的分岔 |

**最有价值的是第 4 条**：M6（切同一个 program）应该是最容易的（等于没切），
但它反而最慢（396 ms / 15.16 J）。**这个反常最可能直接指向缺陷所在。**

## 7. 一句话

**上一轮我说"GPU 在干 30 倍的活"，错了。密集采样显示：525 跑 M3 时功耗 37.40 W，而 P106 空闲是 36.9 W —— GPU 几乎全空，却拖了 261 ms。**
**而同一个 525 跑 M1（同样 shader）是 60~64 W、7.96 ms。⇒ M3 里那些 draw 根本没被 GPU 执行。**
**再加上 M6（切同一个 program）比 M3 还慢一倍（396 ms / 15.16 J）—— 这个反常最可能直接指向缺陷。**
**所以方向从"shader 对比"改回"批次边界处的同步"，下一个靶点是 M6 反常。**
