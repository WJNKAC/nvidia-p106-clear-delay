# 报告 123 / N132：**515 上 `wait_ms` 在全部 6 个模式下调用次数 = 0**（含一次差点毁掉整轮数据的陷阱）

> 时间：2026-10-26
> 环境：<user>@<testhost>（`<testhost>`），P106-100，**515.105.01**，headless X `:2`
> 方法：`perf probe -x libnvidia-glcore.so.515.105.01 --add wm=0xeb8b90` + `perf stat -e probe_...:wm`
> 触发：用户「在 515 上跑 perf probe，数调用」

---

## 0. 结论

**515 里 `wait_ms`（0xeb8b90）在 M1/M2/M3/M6/M8/M9 六个模式下的调用次数全部是 0。**
**它的包装函数（0xeba100）也全部是 0。**
**而同一套探针在 515 的热点函数上能命中 715 万次 —— 探针机制确认有效，0 是真的 0。**

**⇒ 515 的"快"不是因为"等得更聪明"，是因为它根本不走这条等待路径。**
**⇒ 下一步必须到 525 上数同一个地址，才知道 121µs 是不是"每对一次 wait"。**

---

## 1. 探针有效性：三层验证（缺一层这个 0 就不可信）

### 1.1 第一层：机制本身 —— 用 `malloc` 打样

```
$ perf probe -x /lib/x86_64-linux-gnu/libc.so.6 --add mc=malloc
$ perf stat -e probe_libc:mc -- /bin/ls /usr/bin
             2,488      probe_libc:mc
$ perf stat -e probe_libc:mc -- python3 -c "print(1)"
             2,353      probe_libc:mc
```

✅ uprobe 计数机制可用。

> ⚠️ 我第一次用的是 `/bin/true`，结果 0 —— 因为 `/bin/true` 根本不调 `malloc`。
> **阴性对照选错会得出"机制坏了"的错误结论。**

### 1.2 第二层：同一个文件（glcore）—— 用采样热点打样

先用 `perf record -e cycles:u` 采样，拿到 glcore 的热点地址，再挂探针：

```
$ perf probe -x .../libnvidia-glcore.so.515.105.01 --add hot=0x100690d
```

| 模式 | `hot` 命中 |
|---|---|
| M1 n=100 | 511 |
| **M3 n=100** | **7,154,511** |
| M9 n=100 | 72,051 |

✅ 同一个 `.so`、同一个 `perf probe -x` 路径、能正常触发。

### 1.3 第三层：每次跑都打印 `GL_RENDERER`（这一层救了一整轮）

**见 §2。这是本轮最重要的教训。**

## 2. 差点毁掉整轮数据的陷阱：`sudo` 会吃掉 `__GLX_VENDOR_LIBRARY_NAME`

第一版命令：

```sh
sudo perf stat -e probe_libnvidia:wm -- ./n83a -M 1 -n 1000
```

结果：`total_p50 = 57.4 ms`，全部模式计数 **0**。

**看起来像"515 也不调 wait"——差点就这么写了。**

实际上：

```
GL_VENDOR   = Intel
GL_RENDERER = Mesa Intel(R) HD Graphics P4600/P4700 (HSW GT2)
map_p50     = 57.361        ← 核显的数
```

**`sudo` 默认 `env_reset`，把 `__GLX_VENDOR_LIBRARY_NAME` 清掉了**，
GLX 于是回落到核显（Xwayland/headless 环境下的默认行为）。5 个模式全是核显在跑，0 自然是 0。

**修法**：显式保留环境变量

```sh
sudo --preserve-env=DISPLAY,__GLX_VENDOR_LIBRARY_NAME perf stat -e ... -- ./n83a ...
```

修好后同一命令给出 `GL_RENDERER = NVIDIA P106-100/PCIe/SSE2`，M1 = 7.05 ms（与历史基线 7.298 吻合）。

**判据（必须写进每个脚本）**：跑之前先看 renderer，**`GL_VENDOR=Intel` 一律作废**。
这就是 SKILL §39.6 立过的规矩，这次以更隐蔽的形态又出现了一次（不是忘加变量，是变量被 sudo 吃了）。

## 3. 主表：515 六模式 × 三个探针（`-n 1000`，120 帧）

| 模式 | total_ms | fps | `wm` 计数 | `wrapper` 计数 | `clk` 计数 | clk/对 |
|---|---|---|---|---|---|---|
| M1 只画 | 7.055 | 141.8 | **0** | **0** | 1,233,321 | 10.3 |
| M2 改 uniform | 7.082 | 141.2 | **0** | **0** | 1,211,072 | 10.1 |
| M3 切不同 prog | 5.270 | 189.7 | **0** | **0** | 696,001 | 5.8 |
| M6 切同一 prog | 7.384 | 135.4 | **0** | **0** | 1,107,439 | 9.2 |
| M8 只切不画 | 2.860 | 349.6 | **0** | **0** | 421,290 | 3.5 |
| M9 先切后画 | 7.412 | 134.9 | **0** | **0** | 1,211,282 | 10.1 |

探针：
- `wm` = `0xeb8b90`（`wait_ms` 函数入口，报告 122 定位）
- `wrapper` = `0xeba100`（唯一会调 `wait_ms` 的包装函数）
- `clk` = `0xeb2fb0`（取时钟函数；`0xeb8800` 只是 16 字节跳板，`jmp 0xeb2fb0`）

`clk` 的语义由指令坐实：间接 `call` 后使用魔术数 `0x20c49ba5e353f7cf`（÷1e9），
与 525 里 `*0x290 = 0x146d240` 那个微秒时钟同源。

## 4. 两条读数

### 4.1 `wm` 与 `wrapper` 全 0：515 完全不走这条等待路径

六个模式涵盖"不切 / 切同一 / 切不同 / 只切不画 / 先切后画"，
**没有任何一种会进入 `wait_ms`**。

所以 515 的 K 无关性（报告 120：K 从 1 到 1000 全程 4.8~5.3 ms）**不是"等得少"，是"根本不等"**。

### 4.2 `clk` 次数与成本**负相关**，说明它也不是原因

| | M1（快，7.06 ms） | M3（快，5.27 ms） |
|---|---|---|
| `clk` 次数 | **1,233,321** | **696,001** |

**M1 的时钟读取比 M3 多 77%，可 M1 还更慢一点、M3 更快。**
⇒ 515 里"读时钟"是普发的（约 10,000 次/帧），**与"是否交替切换"无关，与成本也无关**。

这顺带否掉一个可能的直觉：**"515 靠频繁轮询提前返回所以快"—— 不成立，它轮询得更凶。**

---

## 5. 现在能说什么、不能说什么

### 能说

1. **515 的 `wait_ms` 与它的包装函数，在全部 6 个模式下调用次数 = 0。**（强，三层验证）
2. **这个 0 不是探针失效。**（强，同一文件另挂一点命中 715 万次）
3. **515 的时钟读取次数与成本负相关。**（强，M1 1.23M vs M3 0.70M）

### 不能说

- **"525 也不会调 wait"** —— 完全没测。这是唯一能定性的一句话，而它必须在 525 上测。
- **"121µs 是自旋"** —— 报告 114 的 CPU 侧证据（user+sys≈wall、`/proc/PID/syscall` running）支持，
  但本轮没测 525，且 `clk` 数据显示 515 的高频轮询并不带来成本，所以"自旋"不能作为默认结论。

## 6. 下一步：同一命令换驱动，30 分钟内可闭环

```sh
# 换 525 后（地址 0x146d280，报告 122 已定位）
sudo modprobe -r nvidia_drm nvidia_modeset nvidia     # 或直接 isolate + 装 525
perf probe -x /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03 --add wm=0x146d280
sudo --preserve-env=DISPLAY,__GLX_VENDOR_LIBRARY_NAME \
     perf stat -e probe_libnvidia:wm -- ./n83a -M 3 -n 1000
```

**判据（对照本次 515 的 0）：**

| 525 的 `wm` 计数 | 结论 |
|---|---|
| **≈ 120,000**（120 帧 × 1000 对） | ⇒ **每对一次 wait**，121µs 就是它，机制闭环 |
| ≈ 120,000 ÷ 121µs/帧 ≈ 每帧 1~3 次 | ⇒ 与报告 33 一致（"每帧 wait 中位 3 次"），**wait 出局**，121µs 在别处 |
| **0** | ⇒ wait 与本案彻底无关（515/525 都不调），只剩"提交后的自旋/GPU 侧"一类解释 |

**还要顺手加一个探针**：525 的 `clk`（375 已在报告里给过 `0x146d240`），
与本次 515 的 1.23M/0.70M 直接对比 —— 若 525 的 `clk` 在 M3 上暴涨到 ~120,000×N，
那"自旋轮询"就能被量化证实。

## 7. 各条证据强度

| 结论 | 强度 | 依据 |
|---|---|---|
| `wait_ms` 在 515 六模式全 0 | **强** | 三层验证 + renderer 逐次核对 |
| `wrapper` 在 515 六模式全 0 | **强** | 同上 |
| 探针机制有效 | **强** | `malloc` 2,488 次 + glcore `hot` 715 万次 |
| 515 时钟读取与成本负相关 | **强** | M1 1.23M vs M3 0.70M |
| **`sudo` 会吞掉 `__GLX_VENDOR_LIBRARY_NAME` ⇒ 静默落到核显** | **强（实测踩坑）** | 57.4 ms / `GL_VENDOR=Intel` 对照 7.05 ms / NVIDIA |
| 525 的 `wm` 次数 | **未测** | 下一轮 |
| 121µs 的机制 | **仍未定** | 本轮只排除了 515 侧的等待路径 |

---

## 8. 一句话

**515 上数出来了：`wait_ms` 六个模式全是 0，包装函数也全是 0 —— 而同一探针在别处能命中 715 万次，所以这个 0 是真的。**
**它意味着 515 的快不是"等得聪明"，是"根本不等"。**
**至于 525 是不是"每对等一次"，只有到 525 上数同一个地址才知道；本轮一个字都没测它。**
**另外记住这个坑：`sudo` 会把 `__GLX_VENDOR_LIBRARY_NAME` 清掉，程序静默跑到 Intel 核显上，5 个模式白测一轮。**
