# 报告 147 — 「伪造 fence」五次尝试全部失败，以及为什么这条路在用户态走不通

> 日期：2026-10-27 13:20
> 实验机：`<user>@<testhost>`（<testhost>，P106-100，525.116.03）
> 前置：报告 146（122 µs 真面目：GPU 空转 + CPU 陪等）

> ## ⛔ 更正（2026-10-27 18:10，见报告 152 §3）
>
> 本文 §3 写"`-R` 快 63 倍：7.83 → 498.89 fps"。**这个数字是错的。**
>
> 498.89 fps 是用程序自报的 `t_all`（CPU 侧每帧耗时）折算的。
> `-R` 跳过了 map，`t_all` 里只剩 2 ms 的提交时间，除出来就是 500 fps。
> **但真实帧率没有变化。**
>
> 用外部墙钟测（42 帧）：
> ```
> SYNC    5.410 s → 128.81 ms/帧 → 7.76 fps
> NOREAD  5.260 s → 125.23 ms/帧 → 7.99 fps   ← "-R 快 63 倍"
> ```
> **两者真实吞吐几乎相同。** 等待并没有消失，只是从"显式 map"变成了
> "driver 队列满时的隐式反压"。
>
> **仍然成立的部分**：伪造 fence/进度值必然死锁（§4 的三次实验、原理推导）；
> CPU 侧五次补丁全无效（§4 表格）。这些结论不受影响。
>
> **纪律**：引入"跳过某步骤"的开关后，任何帧率结论都必须用外部墙钟复核。

## 0. 用户给的路线与本轮结论

用户路线：

> `glMapBuffer` → 提交器 → `rp` 检查 → `0x1569f10`（读 `0x800000ba`）
> → 确认返回值 → 写 Hook 让它返回"已完成" → 帧率暴涨

本轮逐段核实后，**分析部分全部成立**（见 §1、§2），
但**工程部分（Hook 伪造）五次尝试全部失败**，原因在 §4 逐条列。

核心结论一句话：

> **122 µs 不是"CPU 在等一个没更新的 fence"，而是"GPU 每对之间真的要停 122 µs"。
> CPU 侧伪造改变不了 GPU 的节奏——除了干脆不等它（这正是 `-R` 做的事）。**

## 1. 坐标核实（全部脚本计算）

| 地址 | eh_frame 边界 | 长度 | 入口 |
|---|---|---|---|
| `0x1569f10` | `..0x1569fb0` | 160 B | ✓ |
| `0x1572e60` | `..0x1572eb0` | 80 B | ✓ |
| `0x1238920` | `..0x1238c30` | 784 B | ✓ |
| `0x1575990` | `..0x15759d0` | 64 B | ✓（BAR 读原语） |
| `0x1581460` | `..0x15814a0` | 64 B | ✓（读后一致性） |

用户给的四个坐标**全部正确**。

### 1.1 `0x1569f10` 返回什么

**返回 fence / 同步点序号（32 位单调递增），不是布尔。**

```asm
eax = [ctx+0x21c]          ; 开关 A
r14d = [ctx+0x22f2c]       ; 引擎个数 N
if (开关A != 0)  return [[ctx+0x3c0]+0x48]     ; 缓存副本，零 MMIO
else {
    r12 = MMIO(0x800000ba)                     ; 第 1 个引擎
    for (reg = 0x800000bb; reg < 0x800000ba+N; reg++)
        r12 = min(r12, MMIO(reg));             ; 取最小
    return r12;
}
```

**取最小值 = "所有引擎都至少推进到这里"。**

### 1.2 一处必须纠正的读法

`1569f6b: sub r14d, 0x7fffff46` 不是"减大数"，而是编译器把
`add r14d, 0x800000ba` 优化成了减补数：

```
0x800000ba + 0x7fffff46 = 0x1_0000_0000  ≡ 0 (mod 2³²)
⇒ -0x7fffff46 ≡ 0x800000ba
```

所以 `r14d = N + 0x800000ba`，循环上界 `0x800000ba + N`，`ebp` 从 `0x800000bb` 起。
配合 `cmp r14d,1; jle`（N=1 跳过循环），**确认 `[ctx+0x22f2c]` = 引擎个数**。

### 1.3 `0x1572e60` 返回 64 位复合值

```asm
if ([ctx+0x320] & 1) return [ctx+0x1240];      ; 开关 C：缓存
fence = 0x1569f10(ctx);
rcx   = [ctx+0x1130];                          ; 高32=上界，低32=基准
hi    = rcx >> 32;
if (fence > (uint32)rcx) hi -= 1;              ; 超过基准则上界回退
return ((uint64)hi << 32) | fence;
```

**低 32 位是 fence，高 32 位是"上界"，这是一个带回绕处理的 64 位进度值。**

## 2. 三个"免 MMIO"开关（这是 515/525 差异的候选位）

| 位置 | 作用 |
|---|---|
| `[ctx+0x320]` bit0 | 置位 → 直接返回 `[ctx+0x1240]`，零 MMIO |
| `[ctx+0x21c]` | 非 0 → 读 `[[ctx+0x3c0]+0x48]`，零 MMIO |
| `[ctx+0x12b0]` bit15/14/12 | fence 缓存机制 / 缓存总有效 / 需 clflush |

**若 515 命中任一缓存路径而 525 不命中，机制就完全不同。**
这一条尚未在运行期读值比对，标为待办（需要先定位 `ctx` 指针）。

## 3. 决定性实验：`-R` 等价于"伪造 fence 已完成"

n83b 的 `-R` 跳过 `glReadPixels`/`glMapBuffer`，即"完全不等完成"。

| 场景 | total_p50 | fps |
|---|---|---|
| M3 完整 | 127.733 ms | 7.83 |
| **M3 `-R`** | **2.004 ms** | **498.89** |
| M3 `-G`（glFinish 代替回读） | 124.694 ms | 8.02 |
| M1 完整 | 7.956 ms | 125.69 |

**提交 1000 对只要 2 ms；125.8 ms 全在等完成；`glFinish` 等的一样久（123.6 ms）。**

⇒ **用户目标在"效果"上已经达成**：不等 = 63 倍。
但 `-R` 的 `chk = 0`，意味着**回读数据没有被校验**，画面数据不保证正确。

## 4. 五次 Hook 尝试：全部失败，逐条给原因

| # | 目标 | 补丁 | 结果 | 失败原因 |
|---|---|---|---|---|
| ① | `0x15761b0` 的 20 µs deadline | `0x15761e9: 14→00` | 127.33→127.27 | M3 走 `[rbx+0x2850]==1` 分支，**不经过这条 deadline** |
| ② | 睡眠时长 `0x17`(=23) | `0x1576267: ...00000000` | 126.98 | 总时间由外层 deadline 主导，改单次睡眠无效 |
| ③ | 睡眠调用本身 | `0x157629c: 6×90` | 127.18 | CPU 只是陪等，删掉不改变 GPU 节奏 |
| ④ | **整个 `0x15761b0` → `ret`** | `0x15761b0: 31c0c3` | **127.07** | **同上：74% 采样在这个函数里，但删掉它总时间不变** |
| ⑤ | `wp==rp` 死等循环 | `0x123874a/73: 4839c090` | 127.56 | 该循环不是 M3 的等待点 |
| ⑥ | **BAR 读原语返回 0** | `0x15759bc/cd: 31c0` | **卡死** | fence=0 恒定 ⇒ "永远没完成" ⇒ 死循环 |
| ⑦ | **BAR 读原语返回 0x7fffff** | `0x1575990: b8ffff7f00c3` | **卡死** | 该函数是**通用** BAR 读，波及别的寄存器 |
| ⑧ | fence 函数恒返 0x7fffff | `0x1569f10: b8ffff7f00c3` | **卡死** | **恒定值不递增 ⇒ 进度永不推进 ⇒ 死锁** |
| ⑨ | `rp := wp` | `0x1572e60: 488b87000a8e00c3` | **卡死** | 返回值是 `{上界, fence}` 复合值，纯 wp 让上界变成 0 |

### 4.1 为什么"伪造"必然失败——三次死锁给出同一个答案

⑥⑧ 用**恒定值** → 死锁。原因很直接：

> **进度值必须单调递增。** 恒定值意味着"GPU 永远停在同一格"，
> 消费者算 `可用空间 = wp - rp` 永远是常数，于是永远"空间不够"，死循环。

**这正好印证了用户的判断**："伪造的值应该是当前 CPU 写指针 W（或者比 W 大 1）"——
因为只有跟着 wp 走，`wp - rp` 才会随提交而增长。

⑨ 按这个思路做了（`rp := wp`），仍然死锁，原因是**返回格式**：
`0x1572e60` 返回 `((uint64)上界 << 32) | fence`，直接返回 wp 会让高 32 位（上界）变 0，
下游的回绕判断全部失效。

**正确写法应是**（保留上界、只替换低 32 位）：

```asm
mov rax, [rdi+0x1130]     ; 48 8b 87 30 11 00 00   原 {上界, 基准}
mov rcx, [rdi+0x8e0a00]   ; 48 8b 8f 00 0a 8e 00   wp
mov eax, ecx              ; 89 c8                  低32位 := wp 低32
ret                       ; c3
```

**但这条没继续试，因为 §5 的理由——即使不崩，也解决不了问题。**

## 5. 根本原因：等待不在 CPU 侧，所以 CPU 伪造无效

三条独立证据指向同一结论：

### 证据 A：功耗

| 场景 | GPU 功耗 | 相对空闲 | total |
|---|---|---|---|
| 空闲 | 36.28 W | — | — |
| **M1（1000 draw）** | **52.84 W** | **+16.6 W** | 7.96 ms |
| **M3（绑定+draw）** | **37.42 W** | **+1.1 W** | 127.24 ms |

**M1 是 GPU 真在算；M3 的 GPU 几乎不耗电，却等 16 倍时间。**

### 证据 B：删掉"占比最高"的函数，总时间不变

`rpsample` 采样显示 **74% 的 rip 停在 `0x15761b0` 内**（其 `call [rbp+0x288]` 深入 `__sched_yield`）：

```
次数   rip                 归属
 224   0x..d4c647          libc+0xf8647  = __sched_yield 内
 224   0x..f762a2          glcore+0x15762a2  ← 调用者（0x15761b0 内）
```

`strace -c`：3 帧 33,986 次 `sched_yield` = **11,329 次/帧 = 11.3 次/对**，
每次 1.78 µs，**合计只占墙钟 16%**。

**把整个 `0x15761b0` 改成 `ret`（实验④）→ 127.07 ms，一点没变。**

> **方法论：`rip 采样占比高` ≠ `是瓶颈`。必须用"删掉它，看总时间"来判，
> 而不是看占比。这跟"等红灯时刷手机"一样——关掉手机不会更快到目的地。**

### 证据 C：`glFinish` 和 `glMapBuffer` 等得一样久

125.8 ms vs 123.6 ms。如果是"回读路径的 fence 没更新"，两者不该相同。
**相同 ⇒ 等的是同一个 GPU 进度，与回读无关。**

### 结论

```
525 每提交一个 (绑定, draw) 后，GPU 侧需要约 122 µs 才能推进一格进度。
这 122 µs 里 GPU 不耗电（空转），CPU 只是陪着 yield。
⇒ 在 CPU 侧无论怎么改（改常量、删函数、伪造返回值），都不会让 GPU 更快。
   唯一的"效果"是干脆不等它 —— 那就是 -R（63 倍），代价是数据未就绪。
```

## 6. 那 122 µs 到底是什么（当前最强假设）

与报告 140/145 的 inline 上传差异合并，得到一个自洽的解释：

```
515：状态参数 ——inline 写进 pushbuffer（sub6:0x0034，每帧 6,653 条）
     GPU 顺序执行，写和读在同一流里，天然可见  → 不需要同步点 → 5.26 ms
525：状态参数 ——写进显存缓冲（inline 只有 16 条）
     每个 (绑定,draw) 前必须确认"写已到达 GPU" → 一次同步 ≈ 122 µs
     1000 对 × 122 µs ≈ 122 ms ≈ 实测 127 ms
```

这解释了全部已知事实：
- M8（1000 绑定 + 1 draw = 2.97 ms 正常）：绑定被合并，只有 1 个同步点
- M9/M10（绑定与 draw 分开）：同步点被合并到帧末
- M1（只 draw 不绑定）：没有状态写，不需要同步
- 与分辨率无关、与对象类型无关：是固定同步开销，不是带宽

## 7. 工程上真正可用的两条路

### 路 A：异步回读（合法，推荐）

不等当前帧完成，而是**map 上一帧已经完成的 PBO**（double buffering）。
效果接近 `-R`（帧率大幅提升），数据仍然正确（只是延迟一帧）。
这是任何流式回读程序的标准做法，不是作弊。

### 路 B：继续追同步点的生成处（研究路线）

- 目标：找到 525 在每对之间插入的那条"确认写已到达"的命令
- 手段：`wk/dump_pb.py` 的命令头判据需要先修好（当前解出的是顶点数据）
- 判据：515 的对应位置应当没有这条命令

### 明确不做

- ~~伪造 fence 返回值~~：⑧⑨ 两次实证失败，且原理上无效（§5）
- ~~改 CPU 侧任何常量/函数~~：①②③④⑤ 五次实证无效

## 9. 事故记录：实验机在最后一次死锁实验后失联

**时间**：2026-10-27 13:20 左右（实验 ⑨ `rp := wp` 之后约 10 分钟）

**现象**：

```
ping <testhost>  → 3 packets transmitted, 0 received, 100% packet loss
ssh                → No route to host
arp <testhost>   → Flags 0x0（条目未完成，即不响应 ARP）
```

对照：同时 `ping <gateway>`（网关）2/2 通、1.25 ms ⇒ **本机网络正常，是那台机器本身没了响应。**

**最可能的原因**（按可能性排序）：

1. **实验 ⑧⑨ 往 fence 函数里写了假值，GPU 进入不可恢复状态**
   `0x1569f10` 恒返 `0x7fffff`、`0x1572e60` 返回纯 wp——
   这两种都会让驱动认为"进度已到 0x7fffff"或"上界为 0"，
   驱动可能据此提交了越界的 pushbuffer 地址，导致 GPU 侧挂死（Xid / FIFO 停摆）。
   **X 的显示输出走 nvidia 驱动，驱动挂死会连带整个图形栈卡住。**
2. 死锁的 `n83b` 进程（`timeout 90` 只杀了外层）可能仍有子进程占满 CPU，
   叠加 X 卡死，导致 SSH 连接建立后无法 fork shell。
3. 硬件/供电偶发问题（可能性最低，之前几十次实验都稳）。

**恢复方式**：需要**手动重启那台机器**（`<testhost>`，`<testhost>`）。

**重启的附带好处**：tracefs 里那 7 条悬空 `uprobe_events`（一直 `EBUSY` 清不掉）
会一并消失，`uprobe` 计时能力恢复——这正是报告 146 §11 想做的下一步。

**纪律补充（本轮教训）**：

> 往**驱动内部函数**注入假返回值（尤其涉及 GPU 进度的），风险等级等同于改内核。
> 应该在实验前就：
> 1. 确认那台机器能远程重启（`ssh` 之外的带外手段，或至少有人在旁边）
> 2. 优先用 `-R` 这类"不改代码、只改调用路径"的对照，而不是改返回值
> 3. 一次只跑短帧数（`-f 4`），并给 `timeout` 留足余量后**显式 kill 全部子进程**

**数据完整性**：本轮所有结论都基于失联**之前**已完成并回传的测量
（基线、`-R`、`-G`、功耗、rpsample、9 次补丁的结果都已落盘在本报告与报告 146），
失联不影响这些数值。
