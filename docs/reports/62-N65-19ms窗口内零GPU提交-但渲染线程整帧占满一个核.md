# 62 · N65：19ms 窗口里**没有一次 GPU 提交** —— 但渲染线程**整帧占满一个核**

> 2026-10-26 09:40
> 用户判据（逐字）：
> > 如果窗口里有同期 GPU 提交，说明 525 在等 GPU 排队；如果没有，说明是纯固定延迟（定时器/轮询/同步原语），那才需要往内核驱动查。
>
> **结果落在"没有"这一档，但结论不是"纯固定延迟"——而是判据之外的第三档。**

---

> **⚠️ 2026-10-26 10:05 重大更正（报告 64）**
> 本报告的核心结论「渲染线程整帧占满一个核 → CPU 在生成 GL 命令」**已被推翻**。
> 用 `/proc/PID/task/TID/stat` 的 utime 差分直读：**渲染线程只占 12.4% 的 CPU = 3.82ms/帧**，
> 且 **80% 的采样点在 `futex_wait_queue` + `state=S`**，每帧自愿切换 2.86 次。
> **真实情况是"在等"，不是"在算"。**
>
> 错误根源：本报告用 ftrace `sched_switch` 的"切出间隔 ÷ 帧时间 = 0.95/0.98"判"整帧连续"，
> 但同一份报告已量化 `sched_switch` 有大量丢失（21846 条 vs 931k 次 yield）。
> 丢事件使间隔偏大 → 比值趋近 1 → 误判"整帧连续"。
> **"用比值绕过丢事件"这个论证只在"间隔 ≥ 帧时间"方向成立，反用会得出相反的错误结论。**
>
> 仍然成立的：窗口内 ioctl = 0（20.55ms 真空）、futex 1 次/帧（那是"进入次数"，不是停留时长）。


## 1. 一句话结论

**19~21ms 窗口内确实 0 次 GPU 提交（ioctl 计数精确到个位，无丢失）。**
**但同一时间，渲染线程正在连续占用一个 CPU 核（切出间隔 ÷ 帧时间 = 0.98）。**

→ **不是 GPU 排队，也不是定时器/同步原语等待，而是"CPU 在准备下一帧的 GL 命令"。**
→ **不需要往内核驱动查**，该查的是 **glcore 用户态的每帧 CPU 开销**。

## 2. 判据回答表

| 用户判据 | 实测 | 判定 |
|---|---|---|
| 窗口内有同期 GPU 提交 → 等 GPU 排队 | **窗口内 0 次 ioctl** | **❌ 排除** |
| 窗口内没有 → 纯固定延迟（定时器/轮询/同步原语） | 0 次 ioctl ✓，**但 CPU 在满负荷跑** | **❌ 不是"纯等待"** |
| ——判据之外—— | **CPU 在跑，且不产生 ioctl** | **✅ 实际落点** |

**"没有 ioctl"有两种完全不同的解释，用户的判据只覆盖了第一种：**

| 解释 | 特征 | 本次实测 |
|---|---|---|
| (a) 线程在睡/等 | CPU 空闲，只有定时器事件 | ❌ |
| (b) **线程在用户态算** | **CPU 占用高，但无 syscall** | ✅ |

**GL 的命令是攒在用户态缓冲区里的**，只有 flush/swap 才落到 ioctl。所以"无 ioctl"完全不能推出"没在干活"。

## 3. 数据来源：零成本，复用 n27 的旧 trace

用的是 **2026-10-25 22:27 采的 `traces/n27/n27a.trace`**（78MB）和 `n27d.trace`（49MB）。
这两份 trace 当时是为测 map 窗口采的，但**同时记录了 `sys_ioctl`**，正好能答这个问题。**没有重新上机。**

### 3.1 为什么 ioctl 计数可信（不受 ftrace 丢事件影响）

`n27a.trace` 头部写 `entries-in-buffer/entries-written: 1058146/1058146` → **缓冲区满了，有事件丢失**。

但 **ioctl 没丢**，可以用两条内部一致性校验：

```
ioctl 进入事件 = 5340
帧数（mb_in）  = 267
5340 / 267     = 20.0   ← 整数，一帧不差
```

且 7 个 cmd 的种类计数：`2132 / 1601 / 536 / 266 / 266 / 266 / 266`，其中后 4 个**各等于 266 = 帧数−1**。

**丢事件不可能凑出这么整齐的整数。** 所以 ioctl 侧完整，结论不受丢事件影响。

（**sched_switch 则确实丢了**：21846 次 / 8s = 2730/s，而同期 `sys_sched_yield` 有 931k 次。所以**不能**用 sched_switch 做时长积分——本报告 §5 用的是**区间比值**，不是绝对时长，见 5.2 说明。）

### 3.2 窗口定义

一次 prune 后的帧结构（见 §4）：

```
[上一帧 mb_out] ──(ioctl 群)──> 最后一次 ioctl ──(20.5ms 真空)──> [本帧 mb_in → mb_out]
```

本报告的"窗口" = **最后一次 ioctl → 本次 `mb_in`**，即"最后一个 GPU 提交之后，到下一次 map 开始之前"。

## 4. 核心数据

### 4.1 每帧 20 次提交，全部挤在 6.76ms 内

| 指标 | n27a | n27d（独立复采） |
|---|---|---|
| 帧间隔中位 | **30.84 ms** | **31.22 ms** |
| **ioctl 进入 / 帧** | **20.0** | **20.0** |
| **ioctl 群跨度**（首→末） | **6.76 ms** | — |
| **无 ioctl 真空**（末次→下次 mb_in） | **20.55 ms** | **20.72 ms** |
| 真空占全帧 | **66.6%** | 66.4% |

### 4.2 真空内有 41.8 次 `clock_nanosleep`，**ioctl 0 次**

| 事件 | 每帧次数 | 主要归属 |
|---|---|---|
| `sys_clock_nanosleep` | **41.8** | tid 19721（36.9）、tid 19720（4.0） |
| `sys_sched_yield` | 3.0 | tid 19715 |
| `sys_futex` | **1.0** | tid 19715 |
| `sys_poll` | 0.1 | tid 19732 |
| **`sys_ioctl`** | **0.0** | — |

**futex 只有 1 次/帧** → **不是条件变量等待**。真空里主要是 nanosleep。

### 4.3 那个 1ms 线程是心跳，不是渲染

`tid 19721`：`sleep→sleep` 间隔中位 **1081µs**，p10 1059，p90 1088。
减去 1000µs 的设定值，**每圈实际只干 81µs 的活**（p90 88µs）。

→ **它是 1ms 心跳（引擎 tick / 音频），20.5ms 里跑 18.5 圈、总共约 1.5ms。不是渲染。**
→ 与 README 既有结论一致：那个 1ms `usleep` 来自应用引擎（`libUnigine+0x26a7fd`），不是驱动。

## 5. ★★★ 关键：渲染线程整帧占满一个核

### 5.1 ioctl 的归属 —— 20 次里 19 次来自同一个 tid

| tid | ioctl 次数 | 每帧 | fd |
|---|---|---|---|
| **19732** | 5074 | **19.0** | `0x2f`（nvidia） |
| 19715 | 266 | 1.0 | `0x32`（另一个 fd，cmd `c020462a`） |

7 个 cmd 的每帧次数：`8 + 6 + 2 + 1 + 1 + 1 = 19`，外加 tid 19715 的 1 次。

→ **tid 19732 = 渲染/提交线程**。

### 5.2 它在那 20.55ms 里在干什么：**一直在 CPU 上**

| tid | 切出间隔中位 | 帧时间 | **比值** | 判读 |
|---|---|---|---|---|
| **n27a · 19732** | **29.40 ms** | 30.84 ms | **0.95** | **整帧连续在跑** |
| **n27d · 21494** | **30.72 ms** | 31.22 ms | **0.98** | **整帧连续在跑** |

**两次独立采集（不同 PID、不同帧率 33fps / 20fps）都给出 0.95~0.98。**

**为什么用"比值"而不是"绝对时长"**：`sched_switch` 有丢事件，绝对积分不可信。
但**"某个 tid 两次被切出之间的间隔"**受丢事件影响的方向是**偏大**（丢了中间那次切换，间隔就被合并）——
若实际更频繁，比值只会更小，**"整帧连续跑"这个结论不会被丢事件夸大**。所以用比值是安全的。

### 5.3 真空期它更"连续"，不是更闲

| 指标 | n27a | n27d |
|---|---|---|
| 真空占全帧 | 66.6% | 66.1% |
| 渲染线程在真空内被切出的比例 | **5.6%** | **22.2%** |
| 若切出均匀分布，应该占 | 66.6% | 66.1% |

**真空内切出次数比"均匀分布"少 3~12 倍** → **真空期它比提交期更连续地占着 CPU**。
（提交期频繁切出，是因为 ioctl 会阻塞。）

### 5.4 真空内被调入的 pid 全是 0（idle）

`next_pid` 在真空内的分布：**tid 0 = 6225 次，进程内所有线程 = 0 次**。

结合 5.2：渲染线程在自己的核上跑，**别的核在 idle**。整个进程只有它在动。

## 7. 下一步（方向变了）

用户的判据说"没有 GPU 提交 → 往内核驱动查"。**现在数据表明不用先去内核**，因为：

- 窗口内 GPU 空着（无提交、无同期队列）
- CPU 满着（渲染线程整帧占核）
- **瓶颈在用户态的 CPU 一侧**

### 7.1 建议的两个动作

| 选项 | 内容 | 代价 | 回答什么 |
|---|---|---|---|
| **A（推荐）** | 把 `perf record` 挂到**渲染线程 tid** 上跑 10 秒，看那 30ms 花在哪些函数 | 一次 10s 采集 | **哪段 GL 用户态代码在烧 CPU**（这是唯一还没看过的层） |
| **B（零成本）** | 用报告 51/55 已有的 `$rip` 采样法，对渲染线程做 12 次 gdb attach | 零成本 | 同 A，但精度低、无调用栈 |

**A 的关键**：之前的 perf 都是全进程采样，会混入那个 20µs 自旋线程。
这次要**按 tid 过滤**（`perf record -t <渲染线程tid>`），才能看到渲染线程自己的热点。

### 7.2 一个必须先排除的替代解释

**"渲染线程占满一核"也可能是因为它在跑那个 20µs 自旋循环**（报告 51/52 的 `0x15761b0`）。

判据：**看渲染线程有没有 `sched_yield`**。
- 本次统计：`sched_yield` 按 tid 是 **19734（837480）、19733（90555）、19685（2590）、19715（1099）**
- **渲染线程 19732 一次都没有**

→ **它不是在自旋 yield，是在跑实际代码。**这个替代解释可以排除。

### 7.3 不要再做的

| 不要做 | 原因 |
|---|---|
| 继续在 GLX / primus 里找 | 报告 58/59/60/61 已全层排除 |
| 优先查内核驱动 | 本报告显示窗口内 GPU 空着、CPU 满着，先查用户态 CPU |
| 再改数据搬运（FBO/异步/多缓冲） | 改的是搬运，不是命令生成 |

### 8.1 方法论（三条，已入技能库）

1. **"没有 ioctl"不能推出"没在干活"**。GL 命令攒在用户态缓冲区，只有 flush/swap 才落到 ioctl。
   要定性必须同时看 **CPU 占用**。本例靠"切出间隔 ÷ 帧时间"拿到 0.95/0.98。
2. **ftrace 缓冲满时，按"内部一致性"筛出可信的事件**。本例 `ioctl 5340 / 帧 267 = 20.0` 整数、
   7 个 cmd 中 4 个各等于 266 → **ioctl 侧没丢**；而 `sched_switch` 21846 次对 931k 次 yield → **丢了**。
   **不能因为一份 trace 部分丢了就整份不用。**
3. **用"比值"代替"绝对时长"绕过丢事件**。丢事件只会让间隔**偏大**，
   所以"间隔 ≥ 帧时间"这类结论不会被夸大（方向安全）。**结论方向与丢失偏置同向时才可用。**

### 8.2 环境坑

`/tmp` 是 **10MB 的 tmpfs**，`sort` 会报 `设备上没有空间`。
处理 GB 级 trace 时必须 `export TMPDIR=<工作区目录>`。
