## 2. 阈值常量（全部读自 ELF）

| 字段 / 常量 | 值 | 说明 |
|---|---|---|
| `ctx+0x8e0e00` | `1.0 + ctx+0x8e0dc0` | **单调累加器**（见 §3） |
| `ctx+0x8e0c60` | 累加器，初值 0（`123737f: movl $0,0x8e0c60`） | 另一个累加器 |
| `0x1c52238` | **2,097,152** = 2²¹ | 上界 |
| `0x195d5c8` | **10.0** | 下界 |
| `0x1c5223c` | **10,000** | 比例因子 |
| `0x1ad8748` | **1,000,000** | 另一门槛 |
| `0x1c52228` | 0.7 | （相邻，用途未定） |

### 2.1 处理分支（`1238aa0`）的进入条件

`comiss` + `jbe` 逐条翻译（AT&T 顺序，`jbe` = 源 ≤ 目的）：

| 指令 | 含义 | 跳走（不处理）的条件 |
|---|---|---|
| `comiss %xmm1(f), %xmm3(2²¹)` | `2²¹ − f` | **f ≥ 2,097,152** |
| `comiss 10.0, %xmm1(f)` | `f − 10.0` | **f ≤ 10.0** |
| `comiss %xmm1(f×10000), %xmm0(g)` | `g − f×10000` | **g ≤ f×10000** |
| `comiss 1e6, %xmm0(g)` | `g − 1e6` | **g ≤ 1,000,000** |

**只有同时满足 `10 < f < 2,097,152` 且 `g > f×10000` 且 `g > 1e6` 才会去"处理一批"。**

## 3. ★ 更正：`f` 和 `g` 从未填充到阈值以上——处理分支是死代码

### 3.1 我原来的假设（错误）

看到 `f = 1.0 + counter` 且 `counter` 是 `addss` 自累加，我推断"f 单调增长到 2²¹ 后永久失效"。

### 3.2 实测推翻了它

| 字段 | 实测值 | 阈值要求 | 判定 |
|---|---|---|---|
| `ctx+0x8e0dc0`（counter） | **0.00** | — | **从未增长** |
| `ctx+0x8e0e00`（f） | **0.00** | `f > 10` | **❌ 立刻失败** |
| `ctx+0x8e0c60`（g） | **1,440.00** | `g > 1e6` | **❌ 失败** |
| `ctx+0x30`（状态字） | `0x00002200`（bit0=0） | — | 不走"跳过处理"那条 |

### 3.3 静态也支持"从未执行"

`0x8e0e00` 全库只有两个写点：

```asm
12373c0: movl  $0x0, ctx+0x8e0e00      ; 初始化为 0
1237e01: movss %xmm3, ctx+0x8e0e00     ; 唯一更新点（xmm3 = 1.0 + counter@0x8e0dc0）
```

**实测 `0x8e0e00 == 0` 且 `0x8e0dc0 == 0`** → **`1237e01` 那条路径从未执行过。**

### 3.4 所以真正的结论

```
f = 0  →  f > 10 失败  →  第一个阈值比较就 jbe 到 1238b08
g = 1440  →  g <= 1e6  →  jbe 到 1238b2a
bit1 = 0  →  je 到 1238ab1
0x8e0c70 = 0  →  直接 wait_ms(2ms)
→ 回循环
```

**每一轮都是这个固定路径，处理分支 `call 12386d0` 一次都不走（实测 proc=0，完全吻合）。**

**这不是"溢出失效"，而是"从未启用"。** 两种可能：

| 可能 | 含义 |
|---|---|
| (a) 死代码 / 未激活的优化路径 | `f`/`g` 由某个当前不发生的场景填充；这条分支是给那种场景准备的 |
| (b) 依赖一个从未满足的前置条件 | 需要先满足某条件才会走到 `1237e01` 去填 `f` |

**无论哪种，可观测事实是：这个循环每 2ms 醒一次，检查一个永假的条件，然后继续睡。**

## 4. 动态验证：处理分支确实一次没走

`n33_verify.sh`（uprobe `0x1238aa8` 与 `0x1238acc`，PRIMUS_SLEEP=0，8s）：

| 事件 | 次数 |
|---|---|
| `proc`（`call 12386d0`，处理一批） | **0** |
| `wait`（`wait_ms(2ms)`） | **3896** |
| map 窗口 | 261 个，中位 30.834ms |

**`proc = 0`** → 三条路径里只走了 `1238ab1`（阈值不满足或 `0x30` bit0 置位 → 直接等）。

**这与 §3 的推断一致：阈值条件已经不满足了。**

### 4.1 一个必须承认的替代解释

`proc = 0` 也可能是**第一个分支就跳走**：
`[1238a3b] testb $0x1, 0x30(ctx)` 置位 → `jne 1238ab1`，**完全不看阈值**。

`0x30(%rbx)` 的 bit0 是什么还没查。**若它置位，那 §3 的"阈值失效"就不是原因**，
而是"某个状态位让代码跳过整个阈值/处理段"。

**两个解释都能产生 `proc=0`，需要对 `0x30(%rbx)` 再查一次才能分开（N36）。**
这是本报告最重要的不确定点，不能含糊过去。

## 5. 这对"能不能拿到数量级收益"的判决

用户的目标是判断"关掉这个循环是否可行"。**分三种情况：**

| 情况 | 判定 | 可行动作 | 收益 |
|---|---|---|---|
| ~~**A. 阈值失效**~~ **已排除（N35）** | ~~累加器越过 2²¹ 永久跳过~~ → 实测 `f=0`，是"从未填充"不是"溢出" | — | — |
| **B. `0x30` bit0 置位（§4.1）** | 代码主动跳过处理段 → **这是设计上的"此刻不要处理"状态** | 需先搞清该位代表什么 | 未知，可能无收益 |
| **C. 阈值正常但确实不满足** | 条件真没到 → **等是必需的** | 只能优化超时值（2ms → 更小） | 有限（省的是"落地了还在睡"） |
| **★ D. 条件从未满足（N35 实测）** | `f=0` / `g=1440` 都远低于阈值 → **处理分支是死代码，循环在空转** | **找到 `f`/`g` 由谁填充（或为什么不填充）** | **待定**：若它们本应被填充而没填 → 修它能恢复处理；若这条分支本就未启用 → 该循环的设计意图需重读 |

**N35 已做：A 排除，B 排除（`0x30` bit0=0），落到 **D**（条件从未满足）。**

所以现在的核心问题变成：**`f`(`0x8e0e00`) 和 `g`(`0x8e0c60`) 为什么没被填充到阈值以上？**

它们各自的填充点：
- `f` ← `1237e01`（`1.0 + counter`），实测 counter=0 → **该路径从未执行**
- `g` ← `12389a4/12389b3`（累加），实测 1440 → **执行过，但量级差 3 个数量级**

**这两个是我下一步要查的对象（N37）。**

### 7.1 一条方法论修正

上一轮（报告 45）我写的判据是"`wait` 返回后无条件跳回检查 → 不是事件等待"。
**这条正确但不够**——因为"跳回检查"之后**可能立刻进入处理分支**。

本轮完整状态机显示：真正要区分的是**"检查→等→检查"这个循环里有没有实质工作**。
本例 `proc=0` 证明**没有**，循环是纯空转。
所以判据应补一条：**数一下循环体内的"实质工作调用"次数**（本例 `call 12386d0`），
若为 0 而 wait 上千次，那就是**空转确认**。
