# 80 · N89 静态对照：提交器用户态逐条等价 ⇒ 121µs 不在提交路径，是「每对一次的 GPU 等待」

日期：2026-10-26 12:55
对象：`libnvidia-glcore.so` 515.105.01 vs 525.116.03（两版均已解压，`drivers/` 下）
方法：**纯静态**（objdump + 字节模式搜索 + 调用点统计）+ 一条零侵入动态验证（LD_PRELOAD 数 ioctl，515 上跑）
前序：报告 76/77/78（121µs/对）、报告 62/63（525 Heaven 仅 1.4 NVIDIA ioctl/帧）、报告 31（525 GPU 几乎空闲）

---

## 0. 结论（五条）

1. **提交路径的五段代码在两版间逐条等价**（不是"相似"，是指令序列一致，只有结构偏移/寄存器分配不同）。
2. **调用点数几乎相同**：提交器 123（525）vs 122（515）；`sfence` 1161 vs 1155。⇒ **不存在"525 每对多提交一次"这类结构性变化。**
3. **动态反证（515，零改动）**：1000 对/帧与 0 对/帧的 ioctl 总数 **446 vs 453**（提交类 196 vs 199）⇒ **515 把 1000 对全部批处理，零额外系统调用**。
4. 配合报告 62/63 在 525 上实测的 **1.4 NVIDIA ioctl/帧**（Heaven，268 对/帧）⇒ **525 同样不是"每对提交"**。
5. ⇒ **121µs/对 既不是 ioctl 成本、也不是提交器用户态逻辑，而是「每对一次的 GPU 侧等待」**——这与报告 31 的「GPU 100% util 但只有 48~64W / 41°C」完全一致：**GPU 在等，不在算**。报告 76/77 的「≈231k GPU 周期」是**等待的量化**，不是计算量。

## 1. 五段静态对照（525 → 515）

| 部件 | 525 地址 | 515 地址 | 判定 |
|---|---|---|---|
| **提交器入口** | `0x1238920` | `0xc83500` | **逐条等价**：`push r13/r12/rbp/rbx` → `mov esi,r13d` → `sub $0x18,rsp` → 计时记账（`call *0x290` / 515 `*0x280`，累加 float `0x8e0c50` / `0x55efd0`）→ `call` kick → 记账 → **`sfence`**（525 `+0xa3`=0x12389c3 / 515 `0xc835aa`）→ 跳入队列检查循环 |
| **kick** | `0x1238d80` | `0xc83970` | **等价**：保存写指针到两个字段（`0x8e0900/0x8e0940` ↔ `0x55ec80/0x55ecc0`）→ `testb $0x20` 全局位 → `call *0x2d8`（515 `*0x2c0`）signal → 算剩余空间，`>0x4088` 就推进 `0x4000` 返回，否则走 grow |
| **process($7)** | `0x12386d0` | `0xc83320` | **等价**：同一守卫（`testb $1,0x30` + `cmpl $1,<field>`）→ 同一 `bt $rsi,0x1a01` 白名单 → kick → **`yield(4)` 自旋等队列排空**（525 `0x1238760` / 515 `0xc83398`，都是 `mov $4,edi; call *0x280/0x270`）→ 同一提交序列（置两字段=2、`call *0x1c0/0x1b0`、TLS 存、`call *0x1b8`）→ 同一 post-submit 块（`movb $1,0x4b158/0x4b1e8`、`movq $0,0x4b160/0x4b1f0`） |
| **块管理（grow）** | `0x1238c30` | `0xc83820` | **等价**：free-list 弹出用 `lock cmpxchg`、63 块阈值、`yield(4)` 重试、无块时尾调用提交器 |
| **notify** | `0x146c680` | （同构，未逐址定位） | `lock(ctx+0x30)` → `movb $1,0x58(ctx)` → `signal(ctx)` → `unlock`：**主机侧 cond 信号，µs 级**，不可能是 121µs |

> 说明：515 的 `sfence` 位点由特征 `83 84 c3 <disp32> 01 0f ae f8`（`addl $1, disp(%rbx,%rax,8); sfence`）唯一命中 → `0xc835a2`，据此锚定整个函数；两版该特征都**唯一**。

**调用点统计**（`e8 rel32` 指向提交器）：

| | 525 | 515 |
|---|---|---|
| 提交器调用点 | **123** | **122** |
| `sfence` 总数 | 1161 | 1155 |
| `.text` 大小 | 23.42 MB | 17.42 MB（+34%，主要是 Vulkan 新增区） |

⇒ 差 1 个调用点，**量级上不可能解释 4000 倍**。525 的那 1 个额外调用点在 `0x123a555`（报告 49 记的 `movl $0x8704; call 提交器`），属"写完一条命令查一次队列"的常规形态，不是新增的每对路径。

## 2. 动态反证：515 上 1000 对 = 0 个额外 ioctl

工具：`analysis/probes/ioctl_count.c`（LD_PRELOAD 拦截 `ioctl`，按 cmd 聚合，exit 打印；开销 ~ns，不改变测量）

```bash
LD_PRELOAD=/tmp/ioctl_count.so ./n83a -M 1 -n 1000 -s 0.01 -f 20 -W 5   # 0 对
LD_PRELOAD=/tmp/ioctl_count.so ./n83a -M 3 -n 1000 -s 0.01 -f 20 -W 5   # 1000 对/帧
```

| | ioctl 总数 | 提交类 `cmd=0xc020462a` | map_p50 |
|---|---|---|---|
| **M1（0 对）** | **446** | 196 | 2.60 ms |
| **M3（1000 对/帧）** | **453** | 199 | 2.54 ms |

**1000 对只多 7 个 ioctl（提交类 +3）**，而 map 完全不变 ⇒ **515 的每对成本是纯 CPU 记账（1.04µs/对 submit），GPU 侧为零**。

对照 525：报告 62/63 实测 Heaven 下 NVIDIA 渲染线程 **1.4 次 ioctl/帧**（268 对/帧）⇒ 525 也是批处理的。
**"每对一次 ioctl"在两版都不成立**，所以 121µs 不可能来自 ioctl/提交。

## 3. 推理链（把 121µs 钉成"等待"）

```
525 每对 121µs（报告 76/78，n=5 档 × 3 种变更，程序自计数）
  ├─ 不是 CPU：submit 0.14~4.11µs/对（报告 76）
  ├─ 不是 ioctl：Heaven 1.4 ioctl/帧（报告 62/63）；515 上 1000 对 = 0 额外 ioctl（本报告 §2）
  ├─ 不是提交器用户态：五段逐条等价（本报告 §1）
  ├─ 不是几何/填充：面积 ÷160 → 差 0.02%（报告 76）
  ├─ 不是负载/队列深度：空闲也一样（报告 77）
  ├─ 不是变更数量：M0=M3=M6（报告 78）
  ├─ GPU 侧、固定 ≈231k 周期（报告 77）
  └─ ★ GPU 几乎空闲：48~64W / 41°C / util 100%（报告 31）
        ⇒ util 100% 是"有 kernel 在等"，不是算力饱和
        ⇒ **121µs = 每对一次的 GPU 等待（等主机侧完成握手）**
```

**为什么这会撑满一帧**：268 对 × 121µs = 32.4ms，而回读 DMA 排在这些批次之后 ⇒ map 等 32.4ms ⇒ 34fps。
**515 没有这个握手** ⇒ 同样 268 对只 0.008ms ⇒ 回读窗口 2.6ms < 渲染 9.9ms ⇒ 101fps。

> 修正报告 76/77 的一处表述：当时写「批次开始代价 ≈231k 周期」容易读成"GPU 在算"。
> 准确说法是「**批次开始时的等待代价**」——GPU 在这 121µs 里没有做几何/着色工作。

## 4. 剩下唯一没定位的：那个"每对一次的握手"在命令流里长什么样

用户态等价 + 无额外 ioctl ⇒ 差异只能在**写进 push buffer 的命令内容**里：525 在每个"状态调用 + 紧跟 draw"的边界多写了一个需要等主机应答的命令（semaphore acquire/release 一类），515 不写。

三条可选路径（按成本排序）：

| 优先级 | 动作 | 判据 | 成本 |
|---|---|---|---|
| **1** | **静态找批边界命令发射器**：从 `process` 的提交序列（`call *0x1c0`）往里追，找"写 batch-begin/release 命令"的函数，对比两版该函数写出的命令字 | 若 525 多写一条 release/acquire，即命中 | 零上机，1~2h |
| **2** | **抓 push buffer 内容对比**（需 525）：定位 PBO 同款的 push buffer 映射地址（`/proc/pid/mem`），跑 M1/M3 各抓一块 16KB，逐字 diff | 直接看到 525 多出的命令字 | 需换回 525（用户在場） |
| 3 | 内核源码 diff（`okm/` 515.48.07 vs 525.60.11）的 submit/notify 路径 | 若内核侧加了"等完成"，即命中 | 零上机，但 okm 只含 glue，RM 在闭源 blob 里，收益不确定 |

**建议先走 1**（纯静态、无风险）；若 1 卡住再走 2。
