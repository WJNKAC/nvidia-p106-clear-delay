## 0. 头条

**① 525 的 `wait_ms` 和它的包装函数，六个模式全部为 0。和 515 一样。**
**⇒ 至此"条件变量等待"在两个版本、六个模式下被彻底排除。**

**② 但 525 的 121 µs 找到了去处：CPU 在做纯自旋 —— vDSO `gettimeofday` 占 43% 样本，`sched_yield` 全程 7,979,358 次（每对 213 次），sys 时间占 36~45%。**

**③ 而 `ioctl` 全程只有 605 次、`futex` 只有 1 次 ⇒ 整个 121 µs 里没有任何一次阻塞。**

**④ 决定性对照：M1 与 M3 的 CPU 占用同为 80~82% 单核** ⇒ 两个模式跑的是**同一段自旋代码**，只是等待时长不同。

## 2. 自我更正：那个"16.8 倍时钟暴涨"是归一化假象

我第一眼把这列看成"525 在 M3 里时钟读取暴涨 16.8 倍 = 自旋证据"。**按时间归一后不成立：**

| | M1 速率 | M3 速率 |
|---|---|---|
| 515 | 174.8 M/s | 132.1 M/s |
| 525 | 90.3 M/s | 86.1 M/s |

**两者都在持续高频读时钟，515 甚至更猛。** 525 的 16.8× 只是因为 M3 的墙钟比 M1 长 17.6 倍。

**采样独立印证**：M1 自旋区样本占 23.94%，M3 占 25.42%，几乎相同。

⇒ **计数类指标必须除以墙钟再比，否则"随耗时累积"会被误读成"随工作量累积"。**

## 3. 121 µs 的真实去处：纯自旋

### 3.1 CPU 剖面（525，M3，`cycles:u`）

```
26.30%  [vdso]                        0x6b8
12.72%  [vdso]                        __vdso_clock_gettime
 3.92%  libc.so.6                     clock_gettime
 2.45%  libnvidia-glcore.so.525.116.03 0x146d25d   ← wait_ms 的时钟换算
 2.10%  libnvidia-glcore.so.525.116.03 0x146d240   ← clk 函数入口
 2.04%  libnvidia-glcore.so.525.116.03 0x15759be   ← 报告 52 那个 20µs 自旋区
```

**vDSO 取时合计 39.02% + libc 包装 3.92% = 42.9%。**
另外 `0x15759be / 0x15762a2 / 0x1576210 / 0x1576227`（报告 52 定位的 `0x15761b0` 自旋，含 9 个 `pause`、`lea 0x14(%rax)` 20µs deadline）合计约 5.3%。

### 3.2 sys 时间不是 ioctl，是 `sched_yield`

先用系统调用计数排除两个常识候选：

| 模式 | total_ms | `ioctl` | `futex` |
|---|---|---|---|
| M1 | 4.046 | **501** | **1** |
| M3 | 40.265 | **605** | **1** |
| M6 | 40.962 | **605** | **1** |

**全程 605 次 ioctl（约 5 次/帧）、1 次 futex ⇒ 没有任何阻塞点。**

但 `sys` 时间却占 36~45%，那它去哪了？答案：

| 模式 | total_ms | **`sched_yield`** | `nanosleep` | `clock_nanosleep` |
|---|---|---|---|---|
| M1 | 3.983 | **796,097** | 0 | 0 |
| M3 | 40.273 | **7,979,358** | 0 | 0 |

`sched_yield` 速率恒定为 **约 1.7 M/s**：
- M1：796,097 / 0.49 s = 1.62 M/s
- M3：7,979,358 / 4.84 s = 1.65 M/s

每次 `sched_yield` 约 250 ns 内核开销 ⇒ `1.65M × 250ns = 0.41 s/s` ≈ **41% 单核**，正是测到的 sys 份额。

**⇒ 121 µs = `gettimeofday` 轮询 + `sched_yield` 让出，一遍又一遍，纯粹烧时间，没有一次真正的阻塞。**

### 3.3 决定性对照：M1 与 M3 的 CPU 占用相同

| 模式 | 墙钟 | user | sys | 合计 | 占单核 |
|---|---|---|---|---|---|
| M1（快，7.2 ms/帧） | 625 ms | 280 ms | 230 ms | 510 ms | **81%** |
| M3（慢，127 ms/帧） | 6766 ms | 3570 ms | 2050 ms | 5620 ms | **83%** |
| M6 | 6974 ms | 3510 ms | 2220 ms | 5730 ms | **82%** |

**三个模式占用率一模一样。**

⇒ **它们跑的是同一段自旋循环，唯一差别是"循环了多久"。**
⇒ 这同时否掉了"525 换了一种等待策略"这类说法：策略没变，时长变了。

## 4. 那个 121 µs 是个"固定量子"，而不是"真的在等某个具体事件"

### 4.1 与队列深度无关

`M3`，只改 n：

| n | total_ms | µs/对 | `sched_yield` | yield/s |
|---|---|---|---|---|
| 100 | 15.069 | 150.7 | 3,104,355 | 1.72 M |
| 300 | 40.136 | 133.8 | 8,060,647 | 1.68 M |
| 1000 | 127.075 | 127.1 | 25,553,074 | 1.68 M |

线性拟合 `total = 2.62 ms + n × 124.4 µs`（每帧），与报告 120 的 `5.15 + K×121.8` 同构。

**yield 速率三档恒为 1.68~1.72 M/s** ⇒ 每对成本差异完全由时长解释。

### 4.2 每对 ≈ 213 次自旋迭代 × 约 0.58 µs

```
127.1 µs / 213 次 ≈ 0.60 µs/次
每次 = gettimeofday(~17ns) + sched_yield(~250ns) + 9×pause + 循环开销 ≈ 0.5~0.6 µs  ✓
```

**自洽。** 所以 121 µs 就是"约 213 次空转"的累加，而不是某一次真实的等待。

### 4.3 三个已知事实拼起来

| 事实 | 出处 | 含义 |
|---|---|---|
| 与队列深度线性、截距固定 | 报告 120 + 本轮 §4.1 | 每对固定量子 |
| 像素多 506 倍只涨 8% | 报告 116 | 与工作量几乎无关 |
| 三种状态类型成本相同（program/FBO/texture） | 报告 116 | 与操作类型无关 |

**⇒ 这是一个"到点就走"的超时，而不是"等到了才走"的通知。**

## 5. 现在能确定否掉什么（全部有硬数字）

| 候选 | 状态 | 依据 |
|---|---|---|
| 条件变量等待（`wait_ms`/`cond_timedwait`） | **⛔ 排除** | 两版六模式全 0 |
| 阻塞 `ioctl` | **⛔ 排除** | 全程 605 次，无阻塞 |
| `futex` 线程同步 | **⛔ 排除** | 全程 1 次 |
| `nanosleep` / `clock_nanosleep` 睡眠 | **⛔ 排除** | 均为 0 |
| "525 换了等待策略" | **⛔ 排除** | M1/M3 CPU 占用同为 80~82% |
| "525 时钟读取暴涨所以慢" | **⛔ 排除（我的误读）** | 归一化后 515 更猛 |

**至于这个超时在等什么 —— 我没测出来。到这里，用户态能给的信息基本用尽了。**

## 6. 下一个该测什么（判别力排序）

### N133-A（最直接）：这个超时循环是谁的？
把 `0x15761b0`（报告 52 的自旋）与 `0x146ec00`（wait 包装）都挂探针，看 M3 里各自被进入多少次。
若 `0x15761b0` 每对进入 ~213 次 ⇒ 它就是那 213 次空转的本体，可以反推它在等哪个内存地址/标志位。

### N133-B（换 515 做对称对照）
本轮 525 有 `sched_yield` = 7.98M；**515 的同名计数还没有**。
若 515 的 M3 是 0.5M（即每对 ~12 次），则"同样的循环、不同迭代数"完全成立，
并可算出 515 每次等待只有约 5 µs。

### N133-C（唯一能定性"等什么"的）
既然 `ioctl` 只有 5 次/帧、`futex` 1 次，而 CPU 全程自旋，
那被等的标志位一定在**用户态可见的内存**（BAR0 映射页 / 共享内存）。
用 `perf mem` 或 `gdb watchpoint` 定位那个被反复读的地址 —— 这是唯一能回答"等什么"的路径。

## 8. 一句话

**525 的 `wait_ms` 也是 0 —— 和 515 一样，条件变量这条路在两个版本、六个模式下全断。**
**那 121 µs 是纯自旋：vDSO 取时占 43% 样本，`sched_yield` 全程 798 万次（每对 213 次）吃掉 36~45% 的 sys 时间。**
**而 `ioctl` 605 次、`futex` 1 次 —— 整个 121 µs 里一次阻塞都没有。**
**最能说明问题的是：M1 和 M3 的 CPU 占用都是 80~82%。同一段代码，只是转了更久。**
**所以它是"到点就走"的超时，不是"等到了才走"的通知；至于到点前在等谁，用户态已经给不出更多线索了。**
