> **⚠️ 2026-10-26 11:10 更正（报告 69）**
> 本报告把「72.5% 的唤醒来自 `swapper`(tid 0)」解读为「**定时器超时**」——**这个解读是错的**。
>
> 拿到 `sched_wakeup` 的**内核栈**后真相是：
> ```
> ttwu_do_wakeup > sched_ttwu_pending > flush_smp_call_function_queue > do_idle
> ```
> 含义是「**另一个 CPU 发起唤醒，目标 CPU 当时在 idle，通过 IPI 的 pending 队列处理**」。
> **`swapper` 只代表"目标 CPU 空闲"，不代表"唤醒源是定时器"。**
>
> 因此本报告 §2「72.5% 是白叫的超时唤醒」**作废**。
> 主线程更是 **100% 跨 CPU 唤醒、0 次 `futex_wake`**，且它的栈在 primus 的 `sem_wait`（**无超时**），
> 只能被 `sem_post` 唤醒 —— 与"超时"完全无关。
>
> **仍然成立的部分**：唤醒延迟中位 **3.0µs**、全系统 2~4µs、off-CPU 双峰（19.7% 次数占 85.7% 时间）、
> 主线程/渲染线程的 off-CPU 分布。
> **另外本报告的「渲染线程」实为 `readback_work`**（报告 69 §4 的命名纠正）。

## 2. ★★★ 但发现了一件更关键的事：唤醒者是谁

| 唤醒者 | tid | comm | 次数 | 占比 |
|---|---|---|---|---|
| **中断上下文** | **0** | **`swapper`** | **214** | **72.5%** |
| 主线程 | 64765 | `heaven_x64` | **79** | **26.8%** |
| 其它 | 2588 / 54697 | — | 2 | 0.7% |

原始行样例：

```
swapper   0 [007] 50437.616708: sched:sched_wakeup: comm=heaven_x64 pid=64795 prio=120 target_cpu=007
swapper   0 [000] 50437.624085: sched:sched_wakeup: comm=heaven_x64 pid=64795 prio=120 target_cpu=000
```

**`swapper`(tid 0) 发出 `sched_wakeup` = 唤醒发生在 idle 上下文 = 中断/软中断里。**

对 `pthread_cond_timedwait` 来说，这只有一种来源：**hrtimer 超时到期，在中断上下文把等待者唤醒。**

### 2.1 换算

```
3.03 秒内：
  真正被主线程唤醒（投递了命令）: 79 次 = 26.1 次/秒
  被定时器超时唤醒           : 214 次 = 70.6 次/秒
```

**26.1 次/秒 ≈ 实测 fps 32。**

**→ 主线程每秒只投递 26 次命令，这就是 fps 的来源。**

而其余 70.6 次/秒的超时唤醒，全部是**空转**——队列仍然是空的。

### 2.2 与报告 65 推断的矛盾解决了

报告 65 留了一个矛盾：

| 说法 | 值 | 来源 |
|---|---|---|
| `wait_ms` 的超时值（报告 45） | **2ms** | `mov $0x2,%esi`（全库仅 2 处） |
| `wait_ms` 的超时值（报告 66） | **25** | `mov $0x19,%eax` + `cmove` |
| 实测单次长睡眠 | **22.6 ms** | 本报告 |

**22.6ms 与 25 吻合（等到接近超时），与 2ms 差了 11 倍。**

→ **渲染线程这条链上用的是 25ms 那个超时。报告 45 的 2ms 是另一处调用点。**
→ 而 `22.6ms < 25ms` 说明**大部分不是跑满超时，而是在超时前被唤醒**（但唤醒者 72.5% 是定时器…）

**这里有个细节**：hrtimer 唤醒时可能不是因为"超时到期"，也可能是"定时器被重新设置"。但至少可以确定：**这些唤醒不是由主线程投递命令触发的。**

## 4. 完整归因：现在的图景

### 4.1 三层数据闭合

| 层 | 量 | 值 |
|---|---|---|
| **调度** | 唤醒延迟中位 | **3.0 µs**（正常） |
| **睡眠** | off-CPU 占 | **79.2%**，其中 85.7% 是 ≥10ms 的长睡眠 |
| **投递** | 主线程投递命令 | **26.1 次/秒 ≈ fps 32** |

### 4.2 时间线重建

```
t = 0        主线程投递命令 → 渲染线程被唤醒（26.8% 的唤醒）
t = 0..~5    渲染线程处理命令（约 3.8ms CPU，报告 64）
t = ~5       队列空 → cond_wait(25ms)
t = 5..~30   渲染线程睡（这是那 22.6ms 的长睡眠）
             期间 70.6 次/秒 的超时唤醒把它短暂叫醒，看一眼队列还空，继续睡
t = 30.84    主线程投递下一帧
```

**→ 那 22.6ms 的长睡眠，就是"两帧之间的间隔"。**

### 4.3 所以

| 问题 | 答案 |
|---|---|
| 渲染线程为什么等 27ms？ | **因为帧率只有 32fps，帧间隔就是 30.84ms。它等的是下一帧。** |
| 是调度慢吗？ | **不是，唤醒延迟 3µs** |
| 是被抢占吗？ | **不是，`R` 只占 2.3%** |
| 是超时轮询浪费吗？ | **部分**：70.6 次/秒的空转唤醒，但每次只消耗几 µs 的 CPU |

**→ 渲染线程的"87% 在 futex"不是原因，是结果。**

**它在等一个 30.84ms 才来一次的东西，那它当然 87% 的时间在睡。**

### 4.4 这修正了报告 64 的表述

报告 64 说"3.82ms 在算 + 27.0ms 在 futex 等"，暗示"27ms 是可以省掉的等待"。

**现在看：那 27ms 是帧间隔本身，省不掉——除非帧率提高。而帧率提高的前提是先解决别的东西。**

**这是一个循环依赖：要提速必须先缩短帧时间，但渲染线程的等待只是帧时间的一部分。**

### 8.1 环境坑（本轮踩了两个）

| 坑 | 表现 | 根因 | 解法 |
|---|---|---|---|
| **`perf record -p PID` 漏掉大部分 wakeup** | 切出 1236 次，但只记录 38 次 `sched_wakeup`（漏 97%） | `-p` 按 `common_pid`（事件发生的线程）过滤；**由其它上下文触发的 wakeup 被丢** | **改用 `-a` 全系统采集**，事后按 pid 筛 |
| **`perf record` 不带 `-p` 也不带 `-a`** | 只有 3 行（采的是 `sleep` 本身） | 默认只采当前进程 | **全系统必须显式 `-a`** |

### 8.2 方法论（三条，已入技能库）

1. **★ `perf -p PID` 采 `sched_wakeup` 会漏掉大部分唤醒。**
   本例 1236 次切出 vs 38 次记录（漏 97%）。因为 wakeup 的 `common_pid` 是**触发者**，由其它线程/内核唤醒的都被过滤掉。
   **判据：切出次数 ≫ wakeup 次数 → 立刻改用 `-a`。**
   **数字不闭合（切出 ≠ 切入 ≈ wakeup）就是采集漏了，不是现象本身。**

2. **★ 唤醒延迟和 off-CPU 时长是两个独立的量，必须分开看。**
   本例：唤醒延迟中位 **3µs**（极快），但 off-CPU 中位 **0.32ms**、p90 **21.6ms**。
   **"唤醒快"完全不妨碍"睡得久"** —— 前者是调度器能力，后者是条件何时满足。

3. **★ 看 `sched_wakeup` 的 `common_pid` 是 `swapper`(0) 还是真实 tid，能区分"超时唤醒"和"事件唤醒"。**
   本例 **72.5% 是 `swapper`** → 定时器超时；只有 26.8% 是主线程投递。
   **这个比例直接给出"有多少次唤醒是白叫的"。**
