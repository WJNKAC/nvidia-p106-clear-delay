# 81 · N90：静态比对到底，差异只剩「命令字」；515 上强制每对提交也不复现 121µs

日期：2026-10-26 13:05
对象：`libnvidia-glcore.so` 515.105.01 vs 525.116.03 + 515 上动态实验（不换驱动）
前序：报告 80（用户态五段逐条等价）、76/78（121µs/对）、31（525 GPU 几乎空闲）

---

## 0. 三条结论

1. **glcore uprobe 在 515 上同样挂不上**（注册成功、跑 M3 两秒 0 命中），与报告 77 在 525 上的结果一致 ⇒ **指令级动态探针这条路两版都封死**，只能走 libc 级或内存级观测。
2. **两版都有「16 字节指针载荷记录 + 尾调提交器」的发射器**，结构对应，只有命令字不同：

| | 525 | 515 |
|---|---|---|
| 发射器 1 | `0x123a540`：`movl $0x8704,(%rax)` → payload=0 | `0xa8dd79`：`movl $0x80e3,(%rax); mov %ebp,0x4(%rax)` → payload=ptr |
| 发射器 2 | `0x123a65e`：`movl $0x8704,(%rax)` → payload=obj ptr | `0xa9c417`：`movl $0x8200,(%rax); mov %ebp,0x4(%rax)` → payload=ptr |
| 后续 | `add $0x10,%rax; mov %rax,(%rbx)`（推进 16B）| 同 |
| 提交 | `call 0x1238920`（esi=1）| `jmp 0xc83500`（esi=1，尾调用）|

   ⇒ **命令流的形状相同，命令字被改号**（跨版本方法号重编是常态）。这一条本身**不能**证明差异。
3. **515 上强制"每对一次提交"也不复现**：

| 515，20 帧，1080p | map_p50 | ioctl 总数 |
|---|---|---|
| N=0，不 flush | 2.496 ms | 378 |
| N=1000，不 flush | 2.590 ms | 408 |
| **N=1000，每对 glFlush** | **5.891 ms** | 432 |

   1000 次强制 flush/帧只把 map 抬高 **+3.3ms（3.3µs/对）**，ioctl 只多 1.2 次/帧。
   **525 的 121µs 是它的 36 倍** ⇒ **121µs 不是"提交次数"造成的，是 525 侧某个"每对一次"的等待**（与报告 80 的结论一致）。进一步量化见 §3bis：连"每对 glFinish"也只要 9.6µs/对。

---

## 1. 为什么这两条负结果重要

- 报告 80 证明**提交器用户态逻辑等价**；
- 本报告证明**命令流的记录形状也等价**（只是号不同）、**515 的提交路径即便每对强制也只要 3.3µs**；
- 三者合起来：**121µs 既不在"提交逻辑"、也不在"提交次数"，只能来自 525 对某条命令的 GPU 侧处理/等待**。

这就把靶点从"驱动调度策略"缩小到**一条命令的语义**：
525 的 `0x8704`（或它引用的对象 `ctx+0x8e0880`）与 515 的 `0x80e3/0x8200`（对象 `ctx+0x55...`）在 GPU 上做的不是同一件事——**若 525 的那条命令带"等完成"语义，121µs 就是它**。

---

## 2. 静态还能做的一步（零上机）

| 动作 | 目的 | 可行性 |
|---|---|---|
| **解码 `0x8704` / `0x80e3` / `0x8200`** | 确认是不是同一类命令（如"写时间戳/释放信号量"），还是语义不同 | 三个值都不在 `okm/*/cl*.h` 的常见类表里（grep 无命中）⇒ 更像**驱动内部 record 类型**，需要看 `0x8e0880` 对象的分配/使用路径 |
| **追 `ctx+0x8e0880` 对象的生命周期**（525） | 对象由 `call *0x2a6ec40` 分配、`call 0x147eb00` 初始化；若它是**同步对象**（semaphore/timestamp），则命令语义即"等它" | 静态可追，但要知道对象类型需看初始化函数 `0x147eb00` |
| 追 `0x147eb00`（初始化） | 看它是否往对象里写"完成标记"地址 | 同上 |

**这三步是纯静态、可立即做的**，但收益上限是"知道命令语义"，**不能直接证明 GPU 在等**。

## 3. 需要 525 的三个决定性测量（换驱动前必须先做完 §2）

| 优先级 | 测量 | 判据 |
|---|---|---|
| **1** | n83a `-M 1` vs `-M 3` 下 **`wait_ms`（`glcore+0x146d280`）与 notify（`0x146c680`）的每帧次数** | M3 若 ~1000/帧 ⇒ 每对一次等待被证实；若 ~1/帧 ⇒ 等待在别处 |

| 3 | M3 下 **ioctl 计数**（验证报告 80 §2 的推论"525 也不是每对提交"） | 若 ~0 额外 ⇒ 确认批处理，等待在 GPU 侧 |

## 3bis. ★ 新量化：121µs 是「一次完整 GPU 完成往返」的 12.6 倍

`pair_flush` 增加三种「每对强制同步」模式（N=1000 对，20 帧，1080p，515）：

| 模式 | map_p50 | **整帧墙钟 p50** | 每对增量 |
|---|---|---|---|
| 0 不干预 | 2.592 ms | **2.692 ms** | — |
| 1 每对 `glFlush` | 5.807 ms | 7.855 ms | **+5.2 µs/对** |
| 3 每对 `glFenceSync`+`glClientWaitSync(0)` | 7.360 ms | 9.984 ms | **+7.3 µs/对** |
| 2 每对 `glFinish`（**等 GPU 完全完成**） | 2.487 ms | **12.257 ms** | **+9.6 µs/对** |

（mode 2 的 map 反而变短是正常的：等待被挪进循环体，整帧墙钟才是口径。）

**⇒ 在这块卡上，"每对一次完整 GPU 完成往返"只值 9.6µs。525 的 121µs 是它的 12.6 倍。**

这条量化把几个假说同时排掉：

| 假说 | 判定 |
|---|---|
| 525 每对等 GPU 完成（同步提交） | ❌ **不够解释**：真同步只要 9.6µs，差 12.6 倍 |
| 525 每对提交一次（ioctl） | ❌ 报告 80 §2 + 本报告 §0.3：515 每对强制提交只 5.2µs；且 525 的 submit 仅 0.14~4.11µs/对 |
| 525 每对做**主机侧轮询/MMIO 往返** | ◑ **成为唯一量级对得上的候选**：121µs ≈ 60~100 次 PCIe 非Posted 读（每次 1~2µs）。这类读**不进 ioctl 统计、不进 uprobe**（MMIO 不是系统调用），正好躲过前面所有测量 |

**为什么这条能同时解释旧观测**：
- GPU "util 100% 但 48~64W/41°C"（报告 31）= GPU 在等主机喂下一条命令，自己没活干；
- 121µs 与几何/负载/变更数/队列深度全无关（报告 76/77）= 纯往返延迟的特征；
- 515 的 0.03µs/对 = 515 不做这个往返（或做了但不需要每对一次）。
