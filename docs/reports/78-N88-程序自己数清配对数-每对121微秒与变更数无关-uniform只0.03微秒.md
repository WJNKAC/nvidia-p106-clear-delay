# 78 · N88：程序自己数清了配对数 —— **每对 121µs，与"变更多少"无关；uniform 只是 0.03µs**

日期：2026-10-26 12:05
驱动：525.116.03（P106-100，1920×1080，直连 NVIDIA）
工具：`analysis/n83a/n83a.c`（**新增 `-S` 单进程扫描 + 全程自计数**）

---

## 0. 结论

**用户要的"钉死"做到了，而且比预期更强：**

1. **程序自己数出配对数，精确等于 N**（`pairs/frame = 100 / 200 / 500 / 1000 / 2000`），
   每对成本由程序当场相除得出，**不依赖任何外部工具、不用事后拟合**。
2. **三种完全不同的状态变更，每对成本完全一致**：

| 模式 | 每次迭代变什么 | 每对成本（5 个 N 点） | 斜率 |
|---|---|---|---|
| **M6** | `glUseProgram(**当前已绑定的** prog)` —— **实际什么都没变** | 120.63 / 121.34 / 121.26 / 121.03 / 120.90 | **120.78 µs** |
| **M3** | `glUseProgram(另一个 prog)` —— **变 1 个** | 120.44 / 121.08 / 121.08 / 120.83 / 120.82 | **120.81 µs** |
| **M0** | `LoadIdentity`+`Translate`+`Scale`+`Color` —— **变 4 个** | 120.49 / 121.13 / 121.49 / 121.57 / 121.62 | **121.67 µs** |
| **M2** | `glUniform3f(改颜色)` | −0.14 / 0.01 / 0.03 / 0.04 / 0.03 | **0.02 µs** |
| **M1** | **什么都不变** | （pairs=0，map 恒 2.644~2.674） | — |

**变 0 个、变 1 个、变 4 个，价格一样（120.8~121.7，差 <0.8%）。uniform 差 4000 倍。**

3. **M7 固定 draw 数、只变配对数**：`pairs` 从 1 扫到 999，`draws` 恒为 1000，
   **每对成本恒定 120.7~122.2 µs** ⇒ **121µs 完全由配对数决定，与 draw 数无关。**

## 1. 方法改进：单进程内扫完整条曲线

报告 76 的教训是"批间污染"（那次 `N=0` 偏大 27%，整批作废）。
所以这次给 n83a 加了 `-S`：

```bash
./n83a -M 3 -S -s 0.01 -f 12 -W 3
```

**同一进程、同一 GLX context、同一 FBO/PBO/VBO，依次跑 N=0/100/200/500/1000/2000，
每个 N 跑 12 帧，程序自己算 `(map − map@N0) × 1000 / pairs` 并打印。**

输出（M3 实例）：

```
=== SWEEP (单进程内) driver/ctx 不变 ===
N        map_p50(ms)    pairs/frame      us/pair_vs_N0
0        2.625          0.00             0.00
100      14.670         100.00           120.44
200      26.842         200.00           121.08
500      63.164         500.00           121.08
1000     123.454        1000.00          120.83
2000     244.263        2000.00          120.82
斜率(N=1000→2000): 120.81 us/对
```

**`pairs/frame` 精确等于 N（100.00/200.00/500.00/1000.00/2000.00）** —— 这是计数器的自检：
如果数错了，这一列立刻会偏。

## 2. 三种变更同价：这一条最有说服力

`M6` 是关键对照：**`glUseProgram(prog)` 在已经绑定 `prog` 的情况下再调**，
理论上什么都没改变，但驱动照样收 120.78µs。

```
M6 (变 0 个，no-op)  : 120.78 µs/对
M3 (变 1 个)         : 120.81 µs/对      ← 差 0.03%
M0 (变 4 个)         : 121.67 µs/对      ← 差 0.7%
```

**⇒ "121µs ÷ 4 次状态 = 30µs/次" 这个除法是错的（报告 75 曾这么写，已更正）。**
**真实结构是：一个「状态调用 + draw」的配对，付一次 121µs；不管状态调用有几个、有没有真变。**

### 2.1 为什么 M0 略高（121.67 vs 120.81）

M0 的 4 次 legacy 调用（`LoadIdentity`/`Translatef`/`Scalef`/`Color3f`）本身有极小的 CPU 开销
（报告 74 测得 submit 段 0.027ms/1000 次 ≈ 0.027µs/次），4 次约 0.1µs，解释不了 0.86µs 的差。
更可能是 legacy 路径多写了一个命令包（4 个 vs 1 个），进入同一批次的字节数略多。

**方向不变：121µs 是"配对"的价格，不是"状态数"的价格。**

## 3. M7：配对数独立于 draw 数（直接证据）

固定 `-n 1000`（1000 个 draw），只改 `-c`（插入的配对数）：

| c | map_p50 | **pairs/frame** | **draws/frame** | us/pair |
|---|---|---|---|---|
| 0 | 2.646 | 0 | **1000** | — |
| 1 | 2.653 | 0 | **1000** | — |
| 2 | 2.746 | 1 | **1000** | 126.00 |
| 5 | 3.123 | 4 | **1000** | 125.75 |
| 10 | 3.719 | 9 | **1000** | 122.11 |
| 50 | 8.610 | 49 | **1000** | 122.24 |
| **124** | **17.608** | **123** | **1000** | **121.85** |
| 300 | 39.032 | 299 | **1000** | 121.78 |
| 600 | 75.231 | 599 | **1000** | 121.22 |
| 1000 | 123.191 | 999 | **1000** | **120.69** |

**`draws/frame` 全程恒为 1000，`pairs/frame` 从 0 扫到 999，每对成本稳定 120.7~122.2µs。**

⇒ **同一份 draw 工作量，只因为插了配对，时间从 2.65ms 涨到 123.2ms（46 倍）。**

（`pairs = c−1` 是因为循环条件 `i > 0` 跳过第一个位置，属预期行为。）

**c=2/5 时略高（126/125.8）**：分母只有 1~4，基线 2.62ms 的 ±0.02ms 误差就被放大成 ±5µs。**不是真实差异。**

## 4. 修掉的两个计数器 bug（这轮的实际价值）

用户提"加计数器"是对的，但**加完之后必须先验证它数得对**。这轮抓出两个 bug：

### bug 1：warmup 被计入分子，但分母只除测量帧数

```c
// 错：n_swap 累加了 total = WARM + FRAMES 帧，却除以 m = FRAMES
n_swap / m
```

**后果**：`-W 10 -f 40` 时虚高 **25%**（报告 76 输出的 `swaps=1250` 而 N=1000，就是这个）。

### bug 2：M7 分支漏加 `if (f >= WARM)`

```c
p_UseProgram(...); n_swap++;          // 错：warmup 也计数
p_UseProgram(...); if (f >= WARM) n_swap++;   // 对
```

**后果**：`-W 3 -f 20` 时虚高 **15%**（`pairs=1148.85` 而 c=1000）。

### 4.1 为什么必须抓这个

两个 bug 都会让**分母偏大**，于是"每对成本"偏低：

```
修正前：105 µs/对   （分母虚高 14.7%）
修正后：120.7 µs/对  ← 与 -S 扫描的 120.81 一致
```

**如果没查这两个 bug，M7 会给出 105µs，与 M3 的 121µs 冲突，然后我就会去编一个"为什么两种模式不同"的解释——而真相只是计数器错了。**

**规矩**：计数器加完后，**必须让它在已知答案的场合自检**。
本例的自检就是 `-S` 模式：`pairs/frame` 必须精确等于 N（100.00、200.00…）。

## 5. 现在的完整图景

```
525 上一帧的回读落地时间（1080p, 8.29MiB）：
    T_land = 2.61 ms（纯带宽，M1 的 N=0）
           + 121 µs × 配对数
           + 0.03 µs × uniform 变更数（可忽略）

  配对数 = "状态调用 + 紧跟 draw" 的次数
```

**各项都已由程序自计数验证：**

| 项 | 数值 | 验证方式 |
|---|---|---|
| 纯带宽 | 2.61~2.67 ms | M1 的 N=0..2000 全程恒定（2000 个纯 draw 只多 0.03ms） |
| 每对成本 | **120.7~121.7 µs** | M0/M3/M6 三种变更 × 5 个 N 点，程序自算 |
| 配对数独立性 | draws 恒 1000、pairs 0→999，成本不变 | M7 十档扫描 |
| uniform 例外 | **0.02~0.04 µs** | M2 × 5 个 N 点 |

**对 Heaven 的推论不变**：`32.44ms ÷ 121µs = 268 次配对/帧`。

## 6. 下一步（仍然只有那一个数）

N88 把 `121µs` 从"拟合出来的斜率"变成了"程序自己数出来的、十档扫描一致的常数"。
**但它不能告诉我们 515 的这个常数是多少。**

```
525:  -M 1 → 2.64 ms     -M 3 → 123.4 ms   （pairs=1000）
515:  -M 1 → ?            -M 3 → ?          （预测 34 ms）
```

| 515 的 `-M 3` | 判读 |
|---|---|
| **≈ 34 ms** | 每对 31.3µs vs 120.8µs，**3.9 倍 ⇒ 3 倍差距的全部**，收口 |
| ≈ 123 ms | 常数相同 ⇒ 121µs 与版本无关，靶点回到 Heaven 的配对数 |
| 其它 | 按 `(M3−M1)/pairs` 算，再 `32.44 ÷ 该值` 反推配对数 |

**换驱动会黑屏几分钟，需要你在场确认。** 只需跑两条曲线（`-M 1 -S` 和 `-M 3 -S`），2 分钟出结果。
