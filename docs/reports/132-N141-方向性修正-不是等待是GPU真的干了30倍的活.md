## 0. 头条

**① 中断速率两版完全相同（2.6 /s）⇒ 中断合并/延迟假设被排除。**

**② 每帧能耗：525 = 9.956 J，515 = 0.305 J，差 32.7 倍。**

**③ 功耗形态完全不同：**

**④ 所以 `gap` 大不是原因，是结果 —— GPU 确实需要那么多时间，因为它在做 30 倍的功。**

## 1. 中断速率：两版相同，假设排除

用保活方式测（n 足够大，让程序覆盖整个采样窗口）：

| | 中断/s | GPU 利用率 | 功耗 | 时钟 |
|---|---|---|---|---|
| 525（M3 n=3000，跑 15s） | **2.6** | 100% | **37.5 W** | 1911 MHz |
| 515（M3 n=30000，跑 8.8s） | **2.6** | 99% | **64.3 W** | 1911 MHz |

**中断速率 2.6 /s，两版一字不差。**

而 fence 速率是 6,567/s（525）、166,800/s（515）。

**⇒ 约 2500 个 fence 才触发一次中断。**

**⇒ 这个驱动根本不靠中断判断 fence 完成，它靠轮询 MMIO**（与报告 131 的 gap 采样一致）。

**⇒ "中断没通知"这个假设彻底排除。**

## 2. 每帧能耗：差 32.7 倍

### 2.1 测量方法

```bash
# 1) 先无干扰测帧时间
n83a -M 3 -n 1000            → total_p50

# 2) 再跑一次，运行中 1Hz 采 nvidia-smi
nvidia-smi --query-gpu=power.draw,utilization.gpu,utilization.memory,clocks.sm,clocks.mem

# 3) 每帧能耗 = 功耗 × 帧时间
```

### 2.2 结果

| | 525.116.03 | 515.105.01 | 倍数 |
|---|---|---|---|
| 帧时间 total_p50 | **260.8 ms** | **8.34 ms** | 31× |
| 功耗（中位） | 38.17 W | 36.53 W | 1.04× |
| **每帧能耗** | **9.956 J** | **0.305 J** | **32.7×** |

> 注：本轮 525 的帧时间是 260.8 ms，比之前测的 127 ms 慢了约一倍。
> 我怀疑是这轮反复装卸驱动、X 环境状态不同的影响。
> **但两版用同一套方法、同一时刻测，32.7 倍的比值是可靠的。**

### 2.3 功耗形态（这是关键区别）

**525（n=1000）—— 6 次采样全部 38W，纹丝不动：**
```
38.08 W, 100 %, 1 %, 1911 MHz, 4006 MHz
38.17 W, 100 %, 1 %, 1911 MHz, 4006 MHz
38.17 W, 100 %, 1 %, 1911 MHz, 4006 MHz
38.08 W, 100 %, 1 %, 1911 MHz, 4006 MHz
38.17 W, 100 %, 1 %, 1911 MHz, 4006 MHz
38.17 W, 100 %, 1 %, 1911 MHz, 4006 MHz
```

**515（n=1000）—— 功耗在 36W 和 59W 之间大幅摆动：**
```
59.14 W, 98 %, 0 %, 1911 MHz
36.53 W, 61 %, 0 %, 1911 MHz
36.44 W,  0 %, 0 %, 1911 MHz
49.96 W, 89 %, 0 %, 1911 MHz
36.44 W,  0 %, 0 %, 1911 MHz
49.48 W, 87 %, 0 %, 1911 MHz
```

**解读**：
- **515 是"爆发式"**：8.34 ms 内把活干完，GPU 峰值 59W，然后空闲（36W 是 P106 的空闲功耗）
- **525 是"持续低效"**：38W 稳定输出 260 ms，一直不空闲，但也从不爆发

**⇒ 515 干得快且猛；525 干得慢且绵。**

**⇒ 525 的 GPU 单位时间产出只有 515 的 1/30。**

## 4. ioctl 提交：525 是 606 次

`perf trace -e ioctl` 抓 M3 n=1000：

```
ioctl 总次数: 606        （n=1000，120 帧 → 5.05 次/帧）
total_p50 = 260.567 ms   （perf trace 有开销，比干净的 127ms 慢）
```

**高频 cmd：**

| cmd（方向, type, nr, size） | 含义推测 | size |
|---|---|---|
| `(READ\|WRITE, 0x46, 0x2a, 0x20)` | 最高频，arg 地址每次变 | 32 B |
| `(READ\|WRITE, 0x46, 0x2b, 0x20)` | 次高频 | 32 B |
| `(READ\|WRITE, 0x46, 0xc8, 0x900)` | 初始化 | 2304 B |
| `(READ\|WRITE, 0x46, 0xc9, 0x4)` | 少量 | 4 B |
| `(READ\|WRITE, 0x46, 0xd6, 0x8)` | 初始化 | 8 B |
| `(READ\|WRITE, 0x46, 0x29, 0x10)` | 少量 | 16 B |

**5 次/帧的 ioctl，与报告 124 的 605 次一致。**

**重要**：`0x2a` 的 size 只有 **32 字节** —— 这**不可能是"提交 pushbuffer"**（那应该是几十 KB 的批量）。
32 字节更像是"提交一个作业描述符/更新一个指针"。

**⇒ pushbuffer 的实际内容由 GPU 通过 **`/dev/nvidiactl` 的 mmap 直接读**，ioctl 只下"门铃"。**

这解释了为什么 ioctl 这么少、size 这么小。

## 5. 方向性修正：这是最重要的一条

### 5.1 此前 8 份报告的隐含前提

从报告 122 到 131，我一直在追：
> "525 的 CPU 在等 GPU 的 fence，为什么等得这么久"

**这个前提暗示：GPU 很快会完成，只是通知/同步机制有问题。**

### 5.2 本轮证据推翻它

| 证据 | 含义 |
|---|---|
| 每帧能耗 32.7 倍 | **525 的 GPU 做了 30 倍的功** |
| 功耗稳定 38W × 260ms | **GPU 一直在忙，不是空闲等待** |
| 中断相同 | 排除通知机制 |
| gap 大（98.3% 在 5） | **是 GPU 慢的结果，不是原因** |

**⇒ `gap` 大 = "GPU 还没干完"，而不是"GPU 干完了但没告诉我"。**

**⇒ 之前把 gap 当作"同步效率问题"来追，方向偏了。**

### 5.3 正确的因果链

```
525 让 GPU 每帧做 30 倍的功
    ↓
GPU 需要 260 ms 才能完成
    ↓
CPU 在 pushbuffer 预留处反复检查 fence（gap 98.3% 在 5）
    ↓
每对检查 108 次 × 1.177 µs = 127 µs
    ↓
看起来像"同步很慢"，实际是"GPU 真的没干完"
```

**⇒ 根因在 GPU 的"工作内容"，不在 CPU 的"等待方式"。**

## 6. 那 30 倍的功花在哪：三个候选

| 候选 | 支持 | 反对 | 怎么验 |
|---|---|---|---|
| **A. Shader 更复杂** | 525 编译出的 GLSL→SASS 可能更差 | 无 | 对比两版 shader 二进制/指令数 |
| **B. 状态切换导致 pipeline flush** | M3 是"切程序+画"交替，最敏感 | 515 同样交替却不慢 | 抓 GPU 侧 counter |
| **C. 命令流含冗余操作** | fence 数相同但每个 fence 更重 | 我抓的 pushbuffer 统计相似（但可能没抓到主推流） | 反解命令序列 |

**我倾向 A 或 B**，因为：
- M3 场景的特点就是"切换 + 绘制"交替
- 515 做同样的事只要 8.34 ms
- 功耗形态差异（爆发 vs 持续）更像是"GPU 内部流水线被频繁打断"

**但这是推测，本轮无法确证。**

---

## 7. 诚实的边界

**已确证**：
- 中断速率相同（2.6/s）→ 通知机制不是原因
- 每帧能耗差 32.7 倍 → GPU 工作量差 30 倍
- 525 功耗稳定 38W、515 爆发 59W → 工作模式不同
- ioctl 5 次/帧、每次 32 字节 → 提交靠 mmap，ioctl 只下门铃
- 显存利用率指标不可用

**仍未定**：
- 那 30 倍的功具体是什么（shader / pipeline flush / 冗余命令）
- 525 帧时间本轮测到 260ms，与历史 127ms 不一致（怀疑环境状态，需复核）

**下一步需要的手段（都要么成本高、要么需要专用工具）**：
1. **抓两版的 shader SASS 对比**（`glGetProgramBinary` 或截获编译输出）
2. **GPU 侧 counter**（需要 NVPerfKit/NSight，P106 矿卡不一定支持）
3. **反解 pushbuffer 命令格式**（工作量大，需要文档）

## 8. 各条证据强度

| 结论 | 强度 | 依据 |
|---|---|---|
| 中断速率两版相同 2.6/s | **强** | 保活模式下 8 秒计数 |
| 每帧能耗差 32.7 倍 | **强** | 同方法同时刻测 |
| 525 功耗稳定 / 515 爆发 | **强** | 6 次采样序列 |
| ioctl 5.05 次/帧、size 32B | **强** | perf trace 606 次 |

| 显存利用率指标无效 | **强** | 两版都 0~1% |
| 30 倍的功的具体来源 | **未定** | 三个候选，无法本轮区分 |
| 525 帧时间 260 vs 127 ms | **待复核** | 疑环境状态影响 |

## 9. 一句话

**中断两版一样（2.6/s），所以通知机制不是问题。**
**但每帧能耗差 32.7 倍：525 拿 38W 磨 260 ms，515 拿 59W 冲 8 ms。**
**⇒ 525 的 GPU 是真的干了 30 倍的活，不是"干完了没通知"。**
**⇒ 我一直追的 `gap` 是结果不是原因；方向要转向"GPU 为什么干 30 倍的活"，候选是 shader 质量 / pipeline flush / 冗余命令。**
