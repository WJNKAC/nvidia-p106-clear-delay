## 1. 先说方法缺陷：`fill` 负载测的不是 GPU

看到第一组数据就该警觉：

| 负载 | D | 功耗 |
|---|---|---|
| `fill` LOAD=200（200 个全屏 quad，逐个 `glBegin/glEnd`） | 9.78 ms | **61 W** |
| `shader` LOAD=60（60 个全屏 quad + 64 次 sin/cos/像素） | **41.0 ms** | **110 W** |
| `tex` LOAD=120（120 个全屏 quad + 8 次 texture2D/像素） | 37.2 ms | **112 W** |

**D 更大（41ms）的负载反而功耗更高（110W），D 更小（9.8ms）的负载功耗只有 61W。**

原因：`fill` 用 `glBegin/glEnd` 循环 200~800 次，**每次都是一个独立的驱动调用**。
CPU 提交速度（约 2~3µs/quad）成了瓶颈 → GPU 一直在等 CPU → 功耗低、D 反映的是 CPU 提交时间。

**这也解释了为什么 515 和 525 的 `fill` 曲线几乎重合**（差 0.28ms）：CPU 提交速度两版当然一样。

### 1.1 修正：`vbofill`（一次 draw call 提交 N 个全屏 quad）

| `vbofill` LOAD | D（525） |
|---|---|
| 20 | 3.212 ms |
| 60 | 4.145 ms |
| 120 | 5.549 ms |
| 240 | 8.342 ms |

CPU 只走一次 `glDrawArrays`，斜率 0.023 ms/quad —— 这才是"纯 GPU 填充能力"。

> **教训**：测 GPU 负载时，**必须确认 CPU 提交不是瓶颈**。
> 最快的自检：同时看 **功耗**。GPU 真在忙，功耗会上去；CPU 提交瓶颈时功耗会掉。

## 3. 修正报告 30：不是"渲染慢 3.5 倍"

报告 30 由 `D ≈ 纯传输 + 渲染时间` 推出"515 渲染 7.6ms / 525 渲染 26.9ms"。
**这个推论的前提是"GPU 满负荷"，而 Heaven 下 GPU 是空闲的，所以前提不成立。**

正确的图景（用 §2 的功耗观测修正）：

```
525 + Heaven 的一帧（28.8ms）：
  GPU 实际工作时间：很短（功耗接近 idle，估计只有几 ms）
  GPU 空闲时间：大部分
  主线程：在 sem_wait 里等 22ms
  → 帧时间 28.8ms 由【同步/提交流程】决定，不是 GPU 算力
```

所以报告 30 的公式不是错，而是**只在"GPU 满负荷"时成立**：

| 情形 | D 由什么决定 |
|---|---|
| GPU 满负荷（rb_lat5 大负载 / Heaven @515） | `D ≈ 传输 + 渲染时间 ≈ 1/fps` ✓ |
| **GPU 空闲（Heaven @525）** | **D 由同步机制决定，与 GPU 工作量无关** |

## 4. 3 倍差距的完整算式（把之前所有观测串起来）

关键：**`D` 的拍数决定一切**，而 `usleep` 把拍数放大 9 倍。

```
525：map_time ≈ 3 ms（3 个 1ms tick）
     → autosleep 稳态：sleep = 9 × map_time = 27 ms
     → worker 一轮 = 3 + 27 = 30 ms
     → fps ≈ 33-34  ✓（实测 34.7）

515：map_time ≈ 1 ms（1 个 tick）
     → sleep = 9 × 1 = 9 ms
     → worker 一轮 = 1 + 9 = 10 ms
     → fps ≈ 100         ✓（实测 108）
```

**数值吻合到 5% 以内。**

### 4.1 剩下的核心问题收窄成一句

> **为什么 525 的 `map_time` 是 3 个 tick，而 515 是 1 个？**

已知：
- 纯传输时间两版**相同**（PCIe Gen1×16，2.5ms @1080p，隔离实测）
- 525 的 GPU 在 Heaven 下**空闲**（§2）→ 不可能是"GPU 算得慢"
- 525 的 `glWaitSync` 只有 5µs（fence 早已完成，报告 26）
- 525 的 1ms 量化有对照证据（515 在 640×360 最大 0.81ms 够不到第 1 拍，报告 29）

所以：**525 下 PBO 拷贝的"数据可见"事件，晚了 2 个 tick。**

而 GPU 空闲说明这 2 个 tick **不是在等 GPU 算**，而是在等**驱动察觉到拷贝完成**（或等驱动的提交/完成检测机制走完 2 轮）。

这与报告 10 在 580 上的观测同构（GPU 2.64ms 完成 / 驱动 30.24ms 才察觉）：
**GPU 干得快，驱动报得慢。**

### 4.2 为什么"驱动报得慢"在 Heaven 下才明显

隔离环境（rb_lat5）两版都正常 → 说明这个"察觉延迟"需要**特定条件**才触发。
Heaven 与隔离环境的差别：大量 shader、多 pass、多次 state 切换、多个 context/drawable。

一个自洽的解释（未验证）：**Heaven 的提交节奏让驱动的完成检测轮次被"错过"**——
每帧有大量提交，fence/拷贝的完成落在两次 1ms 轮询之间，于是要等下一轮甚至下两轮。

## 7. 本轮踩的坑

**唯一但重要的一个：把 CPU 瓶颈当成了 GPU 负载。**

诊断方法（成本极低，应该成为习惯）：**测 GPU 负载曲线时同时读 `power.draw`**。

| 现象 | 含义 |
|---|---|
| D 涨了，**功耗也涨** | GPU 真在忙 → 负载有效 |
| D 涨了，**功耗不涨** | **CPU 提交是瓶颈**（或 GPU 在空等）→ 负载无效 |

本例：
- `fill` LOAD=800 → D=30.6ms 但功耗 61W → **CPU 瓶颈**（800 次 `glBegin/glEnd`）
- `shader` LOAD=60 → D=41ms 且功耗 110W → **GPU 真在忙**

**同一轮里，正是靠这个功耗差分才发现 `fill` 曲线不能用。**
