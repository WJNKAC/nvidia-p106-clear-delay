## 2. 三条判读

### 2.1 不是合成器 / 不是 vsync / 不是显示管线

**同一时刻、同一个 `DISPLAY=:1`、同一个 Xwayland**：

```
Intel 核显  clear  4747 fps  (0.211 ms)
P106  525   clear    64 fps  (15.625 ms)
```

如果是 Xwayland 合成器限制或 vsync，**核显不可能跑 4747 fps**。

⇒ 报告 07 用 "Vulkan 358 fps" 排除的那一串（PRIME present / DMA-BUF / PCIe / 供电 / 合成器）
**在 525 上仍然是有效的排除**，但**结论要改**：排除这些之后，剩下的不是"GL 用户态前端"，
而是 **NVIDIA 在这台 P106 上的整条 present/完成路径**。

### 2.2 `clear` 与 `vertex` 几乎一样 ⇒ 是**每帧固定等待**，不是"每批次成本"

| 场景 | GPU 实际工作量 | 帧时间 |
|---|---|---|
| `clear` | 一次清屏（≈0 draw call） | 15.625 ms |
| `vertex` | 大量 draw call | 15.15 ms |

**几乎相同。** 而分辨率从 320×240 到 1920×1080（像素 ×27）：

```
320×240    13.333 ms
1920×1080  15.873 ms      差 2.5 ms
```

**⇒ 主体是一个与像素、与 draw call 数都无关的「每帧 ≈13.3 ms 固定等待」。**

这与之前 GL 侧测到的"每批次 121µs"是**不同的量**：
- GL（Heaven，268 批次/帧）：`268 × 121µs = 32.4ms` → 30fps
- Vulkan（clear，≈0 批次）：**固定 13.3ms** → 75fps
- Vulkan（vertex，多批次）：15.2ms（批次成本被 13.3ms 固定项盖住，看不太出增量）

**两个数字（121µs/批 与 13.3ms/帧）在同一台机器上并存，不能用同一个模型解释。**
这是本轮最重要的一条负面结果：**之前的"批次成本"模型不完备**。

### 2.3 我上一轮的三个建议全部作废

| 建议 | 状态 |
|---|---|
| **换 Vulkan** | ❌ **作废**。525 下 Vulkan 同样受钳（66fps vs 580 的 358fps） |
| 换 515 | ⚠️ **仍可试，但不再是"唯一解"**。用户指出 **525/535/570 在 vGPU 下都不回退** ⇒ 不是版本回归，是"驱动 × 这块物理卡"的组合 |
| 接受现状 | ⚠️ 前提变了：如果 vGPU 下正常，说明**有可用的配置**，"现状"不是物理必然 |

## 3. 用户那条 vGPU 线索为什么是关键（以及报告 05 当时为什么错了）

`grep -rn -iE "vgpu|pve|virtual" reports/` 全部命中只有 **报告 05 第 158 行一条**：

> | **B. Xwayland 合成器交互** | … | 全屏与窗口化均复现；**vGPU（同样是 Wayland+核显直通）能跑 132.9fps** | **vGPU 用的是 PVE 虚拟显卡，路径不同，不构成同条件对照** | … |

**当时把唯一的反证判成了"不构成对照"，这是错的。**

在"525/535/570 全线回退、515 正常"的情况下，vGPU 跑 132.9fps 恰恰说明：
- **同样的 5xx 驱动代码，换一个环境就不慢** ⇒ 不是驱动代码的普遍回归；
- 变量落在 **"物理 P106 + PRIME 回传"** 与 **"vGPU（虚拟显卡）"** 的差异上。

而本轮 Vulkan 实测（核显 4747 / P106 64）说明这个差异**不在 GL 层**，在 **NVIDIA present/完成路径**：

| 候选变量 | 状态 |
|---|---|
| vBIOS 功耗表（报告 01 H1/H2） | ❌ **已排除**：实测 `power.limit=120W`（min 60 / max 140），`SwPowerCap` 未激活；报告 04 也测到 79W > 70W |
| GSP 固件（本轮新查） | ❌ **已排除**：`nvidia-smi -q` 报 `GSP Firmware Version: N/A`，未加载 |
| P-state 钳制（报告 01 H3，`RMForcePstateBug3811584War`） | ⚠️ **未验证**。该符号 **525 独有**（报告 18 已修正：580 没有）。但时钟实测满频 1911MHz、无 throttle reason |
| **P106 无显示引擎 ⇒ present 必须经核显回传** | ⚠️ **最可疑**。vGPU 有虚拟显示设备，不走这条路 |
| 降频/过热 | ❌ 已排除（37~48℃，满频，无限流） |

## 4. 下一步（按判别力排序）

| 编号 | 做什么 | 判据 |
|---|---|---|
| **N103-A（★ 决定性，需换 515）** | **在 515 下跑同一个 `vkmark -D <P106> -p immediate -b clear`** | ①**≈4747 或 ≈358fps** → 525 连 Vulkan 一起坏，**问题在 present/完成路径的驱动实现**，与 GL 无关；②**≈64fps** → **与驱动版本无关**，是这台机器（P106 无显示引擎 + PRIME 回传）的固有限制，那"换 515"从一开始就不是解，用户的 vGPU 线索才是主线 |
| **N103-B（零成本）** | 查 `vkmark` 在 **580** 下 358fps 那次的环境：是不是也走 Xwayland、有没有 PRIME 回传（报告 07 说"DMA-BUF 回传"，需确认 present 路径） | 若 580 也走同一条 PRIME 回传却快 5.4×，则**是驱动实现差异**；若 580 那次其实是核显直出，则报告 07 的 358fps **不可比**，需重测 |
| **N103-C（零成本，静态）** | 对比 515/525 的 **Vulkan present 路径**（`libGLX_nvidia` 的 `vkGetDeviceProcAddr` 面 + `libnvidia-vulkan-producer`），找每帧同步点 | 解释 13.3ms 固定项在哪 |
| **N103-D（需用户确认）** | **vGPU 环境的具体配置**（哪台机、什么虚拟化、什么虚拟显卡、什么驱动版本） | 这是唯一已知"5xx 不慢"的配置，值得作为参照系而不是排除项 |

**建议先做 N103-B（零成本）**：确认报告 07 的 358fps 到底可比不可比。
若不可比，则"580 下 Vulkan 正常"这个前提本身就要重测，整个对照表要重画。

## 6. 教训（已入技能库）

1. **★★ "某后端不受影响"必须实测，不能引用旧报告**。报告 07 的 Vulkan 数据是 **580** 的，
   我把它当成"Vulkan 普遍正常"写进建议，属于**跨版本外推**。
2. **★★ 反证不能因为"环境不同"就排除**。报告 05 把 vGPU 132.9fps 判为"不构成同条件对照"，
   结果那是唯一指向真因的线索。**"条件不同"恰恰是要研究的变量，不是丢弃的理由。**
3. **★ 换一个 API（GL→Vulkan）不等于换一条路径**。同一驱动的 present/完成路径是共用的。
   在动手换后端之前，先用**最小场景**分别测两个 API 的**绝对帧率**，并与**核显**对照。
   核显是免费的、同机、同时刻的"健康基准"——本例一举把合成器/vsync/显示管线全部排除。
