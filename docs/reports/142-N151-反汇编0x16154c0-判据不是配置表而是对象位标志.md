# 报告 142 — 反汇编 0x16154c0：`== 8` 不是读配置表，是读对象的位标志字段

> 编号：142（对应 N151）
> 日期：2026-10-27
> 目标：`<workdir>/drivers/525.116.03/.../libnvidia-glcore.so.525.116.03`
> 所有地址均由脚本计算（`n131b_ehframe.py` + `capstone`），无手算。

---

## 0. 直接回答：`== 8` 读的是什么

**不是配置表。** 它读的是 `[ctx+0x1300]` 这个指针所指向对象的 **`+0x104` 位标志字段**：

```
rdi  = ctx
r13  = [rdi + 0x1300]              ← 一个堆对象指针
cmp  dword [r13 + 0x104], 8        ← 判据在这里（0x16154f1）
```

### 三个决定性事实

| # | 事实 | 证据 |
|---|---|---|
| 1 | **全 .so（44 MB）里没有任何 `mov dword [reg+0x104], 8`** | 字节预筛 1741 处 disp32=0x104 → capstone 验证 1306 条指令 → `imm=8` 只有 `test`/`or`/`cmp` 三种，**没有 mov** |
| 2 | **唯一的"8"来源是位或，不是赋值** | `0x112c4a5  or dword [r10+0x104], 8` / `0x176f12a  or byte [rsi+0x104], 8` |
| 3 | **同字段在别处都用 `test ...& 8`，只有 2 处用 `cmp == 8`** | `test`: `0x10ee787` `0x116c442` `0x116e06e` `0x1239c11`；`cmp`: `0x16154f2` `0x17d689b` `0x17d68de` |

⇒ **`+0x104` 是一个位标志 dword，bit3 由 `or` 置起。
`cmp == 8` 要求"**恰好只有 bit3**"（bit0/bit1 必须为 0）。
实测值是 3（bit0+bit1）→ `3 != 8` → 永远不成立。**

## 1. 函数全貌（266 条指令，1200 字节）

函数边界由 `n131b_ehframe.py` 算出：`0x16154c0 .. 0x1615970`。

```asm

16154d8: mov  r13, [rdi+0x1300]                  ; ★ r13 = 目标对象
```

## 2. 对象 `[ctx+0x1300]` 是什么（已知与未知）

### 2.1 已知：从字段用法推断

| 偏移 | 用法 | 证据 |
|---|---|---|
| `+0x14` | **循环计数**（`mov eax,[r13+0x14]; test eax,eax; je`） | `0x1615531` |
| `+0x18` | 位标志（`test byte [r13+0x18], 1`） | `0x1615526` |
| `+0x104` | **位标志 dword**（bit0/bit1 常见，bit3 = "类型 8"） | 本报告 §0 |
| `+0xbf8` | 位标志（`test byte [r13+0xbf8], 2`） | `0x1615850` |

- 该对象 `[ctx+0x1300]` 在**整个 .so 里被 490 处引用** ⇒ ctx 的核心对象之一
- 相邻的 `[ctx+0x1100]`（判空）、`[ctx+0x1558]`（元素 16 字节的数组基址，见 `0x1615550` 的 `shl rcx,4; add rcx,rax`）

### 2.2 未知：对象的具体语义

**没有任何 `mov qword [reg+0x1300], reg` 直接赋值**（capstone 验证后为 0 处），
说明它由 `memcpy`/结构体整体初始化/或父结构内嵌方式建立。
**本轮未定位到对象的创建点，因此给不出它的语义名称。** 这一点必须诚实标注。

## 3. 515 侧的同一判据：完全一致

```asm
515 0x1054a01: cmp dword [rbp+0x64], 8      ; rbp = [rdi+0x12a0]
515 0x1054a08: je  0x1054c20
```

| | 525 | 515 |
|---|---|---|
| 对象指针 | `[ctx+0x1300]` | `[ctx+0x12a0]` |
| 判据字段 | `+0x104` | `+0x64` |
| 比较方式 | **`cmp == 8`** | **`cmp == 8`** |
| 该字段的 `mov ...,8` | **0 处** | **0 处** |

**两版判据在语义上完全相同，连"没有代码写 8"这一点也一样。**

⇒ **这不是版本差异。** 两版都在检查"这个对象是不是恰好只有 bit3"，
而 Heaven 场景下两版的对象都不是（这就是报告 141 实测"A 路径两版都 0 次"的结构性原因）。

## 4. `+0x104` 的位语义（从所有访问反推）

### 4.1 谁置 bit3（唯一来源）

**A. `0x112c4a5` — 浮点相等时置位**

```asm
112c481: ucomiss xmm0, [rcx]
112c484: jp      112bfd8           ; 无序 → 跳过
112c48a: jne     112bfd8           ; 不等 → 跳过
112c490: movss   xmm0, [rax+4]
112c495: ucomiss xmm0, [rsi+4]
112c499: jp      112bfd8
112c49f: jne     112bfd8
112c4a5: or      dword [r10+0x104], 8      ; ★ 两个 float 都相等才置 bit3
112c4ad: movss   xmm0, [rsi]
112c4b1: movss   [r10+0xf4], xmm0          ; 把值存到 +0xf4
```

⇒ **"两组 2D 坐标/颜色完全相同时，给对象打上 bit3 标记，并把值缓存到 `+0xf4`"。**
这是**去重/合并标记**的典型形态。

**B. `0x176f12a` — 上层对象带某标志时置位**

```asm
176f118: mov  rax, [rdi+0x30]
176f11c: mov  qword [rdi+0x30], 0          ; 取走并清零
176f124: test byte [rdi+0x28], 4
176f128: je   176f140
176f12a: or   byte [rsi+0x104], 8          ; ★ 条件置 bit3
176f131: mov  [rsi+0x108], rax             ; 把刚才取的值存到 +0x108
```

⇒ **"搬运一个值到 `+0x108`，同时打 bit3 标记"。**

### 4.2 谁只看 bit3（`test`）

| 地址 | 指令 |
|---|---|
| `0x10ee787` | `test byte [rbx+0x104], 8` |
| `0x116c442` | `test byte [rbp+0x104], 8` |
| `0x116e06e` | `test byte [rbp+0x104], 8` |
| `0x1239c11` | `test byte [rdi+0x104], 8` |

⇒ 大多数地方只关心"有没有 bit3"（`test`），
**只有 `0x16154f1` 和 `0x17d68*` 要求"整个 dword 恰好等于 8"（`cmp`）**。

### 4.3 `cmp == 8` 在另一处产出的值

```asm
17d689b: cmp  dword [rbx+0x104], 8
17d68a2: setne al            ; al = (x != 8)
17d68a5: add  eax, 1         ; eax = 2 或 1
17d68a8: mov  [r12+0x8a8], eax
```

⇒ `== 8 → 1`，`!= 8 → 2`。**这是个二选一的枚举选择**，
进一步印证 `+0x104` 是"对象类别/状态"的编码，`8` 是其中一类。

## 5. 结论

1. **`== 8` 不读配置表。** 它读 `[ctx+0x1300] + 0x104` —— 一个**运行时对象的位标志 dword**。
2. **`8` 不可能由赋值产生**：全 .so 无 `mov [..+0x104], 8`，只有两处 `or ..., 8`（置 bit3）。
   ⇒ `== 8` 要求"**恰好只有 bit3，其它位全 0**"，是个**极窄的条件**。
3. **实测值 3（bit0+bit1）**，所以条件不成立，A 路径（写 `sub6:0x0034`）从不执行。
4. **两版判据完全一致**（`cmp == 8`，同样没有 `mov ...,8`）—— 这不是版本差异，是**对象类别不匹配**。
5. 函数开头的全局 `0x2a61470` 在 **`.bss`**（未初始化，运行时才填），
   且它的分支**最终仍回到同一个 `cmp`** ⇒ 它不是"配置表"，只是多一步取值的旁路。

**所以：报告 140 里 `sub6:0x0034` 的 416× 差异，与本函数无关。**
它是"另一种对象类型"的处理路径，Heaven 用的是另一条。

## 7. 工具与方法（可复用）

### 7.1 字节预筛 + capstone 验证（本报告的关键手法）

全量 capstone 反汇编 23 MB 的 `.text` **会超时**（>30 分钟）。正确做法：

```python
# 1) 字节预筛：按 disp32 找候选
pat = struct.pack("<i", 0x104)
cands = [所有出现位置]

# 2) 对每个候选，从 pos-15 开始尝试解码 1 条指令
#    找到"结束地址覆盖 pos"且 mem.disp == 0x104 的那条
for back in range(1, 16):
    for ins in md.disasm(d[pos-back:pos+8], pos-back, count=1):
        ...
```

**为什么必须验证**：纯字节匹配会误报。本轮踩过 ——
`48 c7 00 13 00 00 60`（`mov qword [rax], 0x60000013`）里的 `00 13 00 00`
被当成 `[rax+0x1300]`，实际是立即数的一部分。
**判据：必须检查 ModRM 的 mod 位，或者直接用反汇编器。**

### 7.2 用"没有写"来证明"这是常量比较"

想确认一个 `cmp X, 8` 是否在比较配置值：

```python
# 搜所有写该字段的指令，看有没有写 8 的
写操作 = {"mov","xor","add","or","sub","and"}
if ins.mnemonic in 写操作 and ins.operands[0].type == MEM and ins.operands[0].mem.disp == 0x104:
    ...
```

**结果：0 处 `mov ...,8`，只有 `or ...,8`（2 处）。**
⇒ 该字段是位标志，`8` 是 bit3，`cmp == 8` 是"恰好只有 bit3"的窄条件。

**这个手法比"看代码逻辑猜"可靠得多**，值得记住。
