## 1. 静态验证

### 1.1 先确认"是同一个函数"

两版的命令队列分发循环**逐条等价**，只是 ctx 偏移不同：

| | 525 | 515 |
|---|---|---|
| 读队头 | `123b2aa: mov 0x8e0988(%r13),%rax` | `c81c82: mov 0x55ed08(%r13),%rax` |
| 读状态字 | `123b2b1: mov (%rax),%eax` | `c81c89: mov (%rax),%eax` |
| 测 0x1000 位 | `123b2b3: test $0x10,%ah` | `c81c8b: test $0x10,%ah` |
| 未完成→分发 | `123b2b6: je 123b288` | `c81c8e: je c81c60` |
| 取 opcode | `123b288: and $0x7ff,%eax` | `c81c60: and $0x7ff,%eax` |
| 跳转表分发 | `123b293: call *(%r14,%rax,8)` | `c81c6b: call *(%r12,%rax,8)` |

**结构完全一致。** 定位方式：用 `call *(%reg,%rax,8)` + 附近 `test $0x10,%ah` 的组合签名，
515 唯一命中 `0xc81c6b`，525 命中已知的 `0x123b293`。

> ctx 偏移对照：**515 用 `0x55exxx` 段，525 用 `0x8e0xxx` 段**。做跨版本静态对比时必须先换算。

### 1.3 全局计数（三个独立指纹都指向同一结论）

| 指纹 | 515 | 525 | 说明 |
|---|---|---|---|
| **两参数 `wait_ms`**（cond+ms） | **4** | **17** | 525 多了 13 处 cond 等待点 |

—— **都不在命令队列处理器（`0xc8xxxx`）里**。

**→ 515 的命令队列处理器不睡，只自旋；525 给它加了 cond 等待。**

## 2. 动态验证（525）

8 秒采集，263 个 map 窗口：

| 事件 | 次数 | 折算 |
|---|---|---|
| **pathA**（`0x123b288` 分发） | **2,325,745** | **~290,000 次/秒** |
| **pathB**（`0x123b2f0` 进 wait 分支） | **1,933** | 242 次/秒 |
| `wcall`（`0x123b314`） | 1,933 | — |
| `sig`（`0x123af7f`） | 1,946 | — |
| **pathC**（`0x123b322` 计数++） | **0** | `wait_ms` 从不返回 0 |

### 2.1 Path B 与 map 窗口严格对齐

| 指标 | 值 |
|---|---|
| 每帧 wait 次数 | **中位 3.0**（均值 2.8） |
| 每帧 wait 总时长 | **中位 3089 µs** |
| **占 map 窗口比例** | **101.4%** |
| 覆盖窗口的线程 | **tid 9506（99.6% 的窗口）** |
| `sig` 落在窗口内 | 262/263 个窗口，**恰好每窗口 1 次** |

**这是报告 33 结论的动态确认：map 的 3ms 就是这些 wait_ms。**

### 2.2 等待从不超时

| tid | 总次数 | 中位 | 其中 >7ms 的 | 那是多少 |
|---|---|---|---|---|
| 9506 | 1144 | 51 µs | **260 次**（≈每帧 1 次） | 中位 **10.4 ms**，max 13.3 |
| 9524 | 788 | 53 µs | **262 次**（≈每帧 1 次） | 中位 **27.8 ms**，max 29.9 |

**>90ms 的：0 次。** 超时上限是 100ms，从未触发 → **每次都是被 signal 唤醒**。

### 2.3 一个需要标注的观察：每帧有两次长等待

- tid 9506：每帧一次 ≈ **10.4 ms**
- tid 9524：每帧一次 ≈ **27.8 ms**

两者合计超过帧时间（28.8ms），说明**它们重叠**，不是串联。

而且 map 窗口只有 3ms —— 它只是这两次长等待里**被重叠的那一段**。
换句话说：**3ms 是"落在 map 窗口内的那部分"，不是任何一次 wait 的全部。**

> 报告 33 说"窗口内最长的那次 wait 中位 3037µs = 窗口的 100%"，
> 这和本节不矛盾：那次 wait 的总长可能是 10ms，但只有 3ms 落在窗口内。
> **讲"3ms"时要说明它是"窗口内的重叠量"，不是"一次等待的全程"。**

#### 2.3.1 补一个口径说明：为什么 §2.1 的 101.4% 与 §2.2 的 10.4/27.8ms 不打架

把两个数放一起算会立刻发现矛盾：

```
260 次 × 10.4ms / 263 帧 ≈ 10.3 ms/帧
262 次 × 27.8ms / 263 帧 ≈ 27.7 ms/帧
相加 ≈ 38 ms/帧  ≫  §2.1 报的每帧 wait 总时长 3089µs，也 > 帧时间 28.8ms
```

**原因在对齐脚本的口径**（`t9_paths_align.py` 第 66 行）：

```python
per_tot.append(sum(min(e,b)-max(s,a) for _t,s,e in ins))   # 按窗口裁剪后求和
```

它把每次 wait **裁剪到窗口边界**再累加，而且**不区分是否已被别的 wait 覆盖过**。
于是一次 27.8ms 的长 wait 在 3ms 窗口里只贡献 3ms；两次重叠的 wait 各自贡献一份，
**同一段时间被计了两次** → 覆盖率可以 >100%。

所以：

| 数字 | 正确读法 | 不能读成 |
|---|---|---|
| §2.1 "覆盖 101.4%" | **占用率（含重叠重数）**：窗口在时间上被 wait 铺满，且局部有两次叠加 | "一次等待盖满了窗口" |
| §2.1 "每帧 3 次 wait / 3089µs" | 窗口内**相交**的 wait 个数与裁剪后总和 | "这三个 wait 总共只花了 3089µs" |
| §2.2 "10.4ms / 27.8ms" | **单次 wait 的真实全长** | 不能与 3089µs 相减或相加 |

**规则**：报窗口覆盖率时，必须同时给"窗口内次数"与"单次最长中位"；
若 `Σ(单次全长) / 帧 > 帧时间`，就说明有重叠，覆盖率是**带重数的占用率**，不是时长。

## 3. 两版对照的结论（静态+动态合起来）

| | 515 | 525 |
|---|---|---|
| 命令队列分发循环 | 自旋（10 万次上限） | **自旋 + cond 等待** |
| 两参数 `wait_ms` 调用点 | 4（都不在队列处理器） | **17（含队列处理器内 1 处）** |
| `signal` 调用点 | 6 | **48** |
| "置标志+signal" | 0 | **3** |
| 每帧长等待次数 | ？（未测动态） | **2 次（10.4 + 27.8ms）** |
| 该线程在等时的状态 | 自旋烧 CPU | **睡在 futex（报告 32：98.3%）** |

**核心差异可以一句话表述：**

> **525 把命令队列处理器的"未完成"处理，从"自旋轮询状态字"改成了"在 cond 上等通知"。**
> 自旋版**发现完成是即时的**（下一圈就能看到状态字变化）；
> cond 版**依赖发通知的那一方什么时候跑到** —— 于是多出了通知链的延迟。

这也解释了报告 31 的功耗观测：**525 在 Heaven 下 GPU 只有 48~68W（≈空转）**，
因为队列处理器在睡，没人持续喂 GPU；515 自旋时反而会不断推进。
