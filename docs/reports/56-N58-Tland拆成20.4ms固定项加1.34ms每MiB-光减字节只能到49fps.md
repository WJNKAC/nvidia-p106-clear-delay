# 56 · N58：T_land 拆成两项 —— **20.4ms 固定项 + 1.34ms/MiB**，光减字节最多只能到 49fps

> 2026-10-26 12:30
> 用户指定 N58：查 `glReadPixels` 每帧调几次、参数是不是 1920×1080、提交时机是否在渲染完成前。
> 同时要求先解决 `n53a`/`n57a` 关于 C 计数的方向矛盾。
>
> **三个问题都有明确答案，而且顺带把 T_land 拆成了一个非常干净的二元式：**
> **`T_land = 20.39ms + 1.335 ms/MiB × bytes`**（三点拟合，残差 ≤0.03ms）
> **→ 即使字节数降到 0，fps 上限也只有 49。**

---

## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **每帧 `glReadPixels` 恰好 1 次** | 131 帧 / 131 次、183/183、176/176 → 1.00 次/帧 |
| 2 | **参数就是全屏，起点 (0,0)** | `1920x1080 ×131`、`640x360 ×183`、`960x540 ×176`，**全部 (0,0)** |
| 3 | **→ 没有重复拷贝、没有多余区域。减字节只剩 34% 空间** | 由 1、2 推出 |
| 4 | **`RP→MB` 只有 127~178µs** | 拷贝提交很早，不是"提交太晚" |
| 5 | **★ `T_land = 20.39ms + 1.335ms/MiB × bytes`** | 三点拟合，残差 −0.03/+0.03/−0.01 ms |
| 6 | **★ 20.4ms 固定项与字节数完全无关，占 1080p 帧时的 66%** | 由 5 推出 |
| 7 | **斜率 785 MB/s = PCIe Gen1 物理下限（3.15GB/s）的 1/4** | 1.335 vs 0.333 ms/MiB |
| 8 | **→ 字节降到 0 也只能到 49fps** | `1000/20.39` |
| 9 | **C（队列检查）的计数不是像素的稳定函数** | 49 / 2700 / 3110 / 4412 次/帧 都出现过 |

**一句话**：**拷贝本身没问题（1 次、全屏、提交快）。问题是两条：①每帧固定 20.4ms 的延迟（占 2/3），②带宽只有线速的 1/4。两个都要打，只打一个都不够。**

## 2. 三个指定问题的答案

`n58_readpixels.sh`：7 个探针（`RP` 含参数、`RPO`、`WS`、`MB`、`W`、`C`、`S`），3 档分辨率。

### 2.1 每帧调用几次？

| 分辨率 | `W`（帧） | `RP`（调用） | **次/帧** |
|---|---|---|---|
| 1920×1080 | 131 | 131 | **1.00** |
| 960×540 | 176 | 176 | **1.00** |
| 640×360 | 183 | 183 | **1.00** |

**每帧恰好 1 次，无重复拷贝。**

### 2.2 参数是不是 1920×1080？

`uprobe ... x=%di y=%si w=%dx h=%cx`（`glReadPixels(x,y,w,h,...)` 前四个参数）：

| 分辨率 | `(w,h)` 分布 | `(x,y)` 分布 | 单次字节 |
|---|---|---|---|
| 1920×1080 | `1920x1080 ×131` | `(0,0) ×131` | 7.91 MiB |
| 960×540 | `960x540 ×176` | `(0,0) ×176` | 1.98 MiB |
| 640×360 | `640x360 ×183` | `(0,0) ×183` | 0.88 MiB |

**就是全屏，起点 (0,0)，没有读多余区域。**
（注意：`w=%dx h=%cx` 里的 `w=`/`h=` 是我给的标签，对应的是第 3、4 个参数 width/height。）

### 2.3 提交时机是否在渲染完成前？

| 间隔 | 1080p | 960×540 | 640×360 |
|---|---|---|---|
| **`RP→MB`**（提交 → 开始等落地） | **137 µs** | **127 µs** | **178 µs** |
| **`RP→W`**（提交 → 落地） | **30,935 µs** | **23,063 µs** | **21,533 µs** |
| `RP→WS`（到下一帧 waitSync） | 30,974 µs | 23,101 µs | 21,626 µs |

**拷贝提交后 137µs 就开始 `glMapBuffer` 等了，然后等 30.8ms 才落地。**

→ **不是"提交太晚"，是"落地太晚"。**（这排除了用户列的第三条候选。）

## 3. ★ T_land 的二元式

### 3.1 三点拟合

| 分辨率 | MiB/次 | 实测 `map` | 拟合值 | 残差 | fps |
|---|---|---|---|---|---|
| 640×360 | 0.88 | 21.53 ms | 21.56 ms | **−0.03** | 45.8 |
| 960×540 | 1.98 | 23.06 ms | 23.03 ms | **+0.03** | 44.0 |
| 1920×1080 | 7.91 | 30.94 ms | 30.95 ms | **−0.01** | 32.8 |

```
T_land = 20.39 ms + 1.335 ms/MiB × bytes
```

**三个点、残差 0.03ms 以内 —— 这个线性关系非常硬。**

### 3.2 两个成分的分量

| 成分 | 1080p 下的值 | 占比 |
|---|---|---|
| **固定项** | **20.39 ms** | **66%** |
| 传输项（7.91 MiB） | 10.56 ms | 34% |

**→ 减字节最多只能削掉那 34%。**

### 3.3 带宽也没跑满

| | 数值 |
|---|---|
| 拟合斜率 | **1.335 ms/MiB** = **785 MB/s** |
| PCIe Gen1 x16 物理下限 | 0.333 ms/MiB = 3150 MB/s |
| **比值** | **慢 4.0 倍** |

**即使只看随字节变的那部分，也只跑到线速的 25%。**

### 3.4 最硬的推论：光减字节到不了 50fps

```
传输 0 字节的极限帧时 = 20.39 ms  →  fps 上限 49
50 fps 需要 20.0 ms  <  20.39 ms  →  ✗ 不可能
60 fps 需要 16.7 ms  <  20.39 ms  →  ✗ 不可能
```

**→ 无论怎么优化分辨率/色深/区域，只要那 20.4ms 还在，就上不了 50fps。**

### 3.5 与隔离环境的对照（关键）

| | T_land | 固定项 | 斜率 |
|---|---|---|---|
| **隔离环境**（rb_lat5/6，报告 40） | **2.62 ms** | **≈0** | 0.32 ms/MiB（≈线速） |
| **真实 primus**（本轮） | 30.94 ms | **20.39 ms** | 1.335 ms/MiB |

**隔离环境两项都正常**：没有固定项、斜率贴线速。
**→ 这两个数字（20.4ms 和 4× 带宽损失）都是真实进程特有的，不是硬件极限。**

## 4. 20.4ms 是什么（新问题，但范围已很小）

几个可疑点，按可能性排：

| 候选 | 为什么可疑 | 怎么验 |
|---|---|---|
| **★ 报告 38 的"一帧 = 1 次真等约 20ms"** | 数值**完全吻合** 20.39ms | 报告 38 的 `t8` 数据里，把那个 20ms 等待的时间戳与 `RP` 对齐 |
| **等待下一次 present/swap** | 若 DMA 只在 `glXSwapBuffers` 后才启动，就会有一个"等下一帧"的整周期延迟 | 对比 `RP` 与 `swap`（`0x19220`）的时间戳顺序 |
| 驱动内部的 20ms 定时器/超时 | 20ms = 50Hz 周期，也可能是某处 `msleep(20)` | 静态找 `mov $0x14` 附近的 sleep/超时 |
| 调度延迟（CPU 被挤） | 12 核但全进程 209%，worker 可能被延迟调度 | 已排除大半：隔离环境同样线程数但只有 2.62ms |

**注意 3.4 的推论把优先级改了**：20.4ms 是 66%，**它比带宽问题更重要**。

## 5. C 的矛盾解决了（答案是"它不稳定"）

用户要求的零成本重测，用同一套 7 探针方法采了 4 次：

| 运行 | 分辨率 | `C` 次数 | **`C`/帧** |
|---|---|---|---|
| n58a-m6-r1 | 1920×1080 | 407,446 | **3,110** |
| n58a-m6-r2 | 1920×1080 | 353,748 | **2,700** |
| n58b-m1-r1 | 960×540 | 776,452 | **4,412** |
| n58a-m0-r1 | 640×360 | 8,980 | **49** |

### 5.1 判读

- **不是单调函数**：640×360 是 **49**，960×540 是 **4,412**（比 1080p 还高），1080p 是 2,700~3,110
- **同一配置（1080p）两次差 15%**：3,110 vs 2,700
- **范围跨 90 倍**（49 ~ 4,412）

**→ `n53a`（降 33 倍）和 `n57a`（升 18%）都没错，它们各自抓到了不同状态。
但"C 与像素相关"这个命题不成立——它不是像素的稳定函数。**

### 5.2 那 C 是什么

`0x1238a28` 的循环入口计数取决于**队列里有没有活**：
- 队列空时走"查一下就返回"的短路径（计数多）
- 队列非空时走"处理一批"的长路径（计数少，但每轮做更多事）

**→ 用"次数"衡量它的工作量是错的指标。** 应该用**它占的 CPU 时间**衡量。

（这也解释了为什么 960×540 的 C 反而最高：可能那一轮 Heaven 的队列状态不同。）

## 6. 现在能给出的一条明确优化路线

### 6.1 不能做的事（已被数据排除）

| 想法 | 为什么不行 |
|---|---|
| 减少 `glReadPixels` 调用次数 | **已经是 1 次/帧** |
| 缩小读取区域 | **已经是全屏 (0,0)-(W,H)** |
| 让拷贝更早提交 | **提交后 137µs 就开始等了**，不是提交问题 |
| 只降分辨率 | **降到 0 字节也只能到 49fps** |

### 6.2 该做的事（按收益排）

| 优先级 | 目标 | 预期 |
|---|---|---|
| **★ 1** | **消掉 20.4ms 固定项** | 若能降到 ~0：会回到 `1.335ms/MiB` 主导 → 1080p 从 30.94→10.6ms，**fps 32.8 → ~94** |
| **2** | **把 1.335ms/MiB 拉到 0.33**（线速） | 1080p 传输项 10.56→2.64ms，配合 1 项 → **fps ~330**（接近隔离环境的 380） |
| 3 | 减字节（降色深/区域） | 单独做：34% 的份额，**上限 49fps** |

**顺序很重要**：单独做 2 或 3 都被 20.4ms 卡在 49fps 以下；只有先解决 1，2 和 3 才有意义。

## 7. 下一步（一条，且是唯一指向 20.4ms 的）

**N60：把 `RP` 的时间戳与 `glXSwapBuffers`（`0x19220`）对齐，看 20.4ms 是不是"等下一次 present"。**

判据：

| 观察 | 结论 |
|---|---|
| `RP` 到下一个 `swap` 的间隔 ≈ 20ms，且 `map` 恰好在 swap 后完成 | **→ DMA 只在 present 后启动**，这是可改的（改 primus 的调用顺序，让拷贝在 swap 前提交） |
| `map` 的完成时刻与 swap **无固定关系** | → 20ms 来自别处（驱动内部定时器），需回到 glcore 静态找 |

**这是唯一能定位 20.4ms 来源的实验，而且只用已有的探针偏移（`0x19220` 已在 `primus_probe_offsets.md` 里）。**

### 8.1 三个方法论要点

1. **`uprobe` 可以直接读函数参数**：`w=%dx:s32 h=%cx:s32` 就把"拷多大区域"这个问题变成了一个打印。
   比事后推算（`bytes = W*H*4`）可靠——它验证了"实际参数"而不是"假设的参数"。

2. **要拆"固定项 vs 比例项"，至少需要 3 个不同负载点。**
   2 个点只能算斜率，无法判断是否有截距；3 个点还能看残差，本例残差 0.03ms 说明线性模型成立。

3. **"次数"不是工作量的可靠指标。** C 的计数在 49~4412 之间波动（90 倍），
   原因是循环有两条路径（队列空/非空），次数多不代表工作多。**用 CPU 时间或"处理了多少条"才对。**
