# 51 · N47：栈拿到了 —— 是 **glcore 自己在 `sched_yield()` 自旋**，不是 malloc

> 2026-10-26 07:50
> 用户要求 N47：抓那个线程的栈，判定调用者是不是 glcore 记账。
>
> **答案：调用者是 glcore，但不是"记账"，是 glcore 的 `sched_yield` 重试循环。**
> **同时必须纠正报告 50 的一个错误解读**——我把 `sched_yield` 的入口当成了 `lock cmpxchg`。

---

## 1. 栈（两次 attach，完全一致）

```
#0  0x...ef04647  sched_yield ()            ← 停在 libc 的 sched_yield
#1  0x...a5762a2  glcore +0x15762a2
#2  0x...a4d66ca  glcore +0x14d66ca
#3  0x...a486c99  glcore +0x1486c99
#4  0x...a48756b  glcore +0x148756b
#5  0x...a113962  glcore +0x1113962
#6  0x...a07f178  glcore +0x107f178
#7  0x...a23b297  glcore +0x123b297   ← ★ 就是我们查了十几轮的队列处理器
#8  0x...a4702fa  glcore +0x14702fa
#9  0x...ee9e8bb  libc
#10 0x...ef1c538  libc
```

寄存器：`rip=sched_yield+7`、`rbp=0x7f550ba6e7e0` = **`_nv014glcore` 基址**（glcore 自己的 vtbl 指针）。

**关键帧**：`#7 = 0x123b297`

```asm
123b297: mov  0x8e0988(%r13),%rcx
123b29e: mov  0x8e0940(%r13),%rax      ; ← 队列尾（报告 43 里那个 0x8e0940）
123b2a5: cmp  %rax,%rcx                ; ← 队列判空
```

**这正是 `1238a28` 循环所在的那个函数**（`0x1238920` 函数体，报告 46 的完整状态机）。
`#8 = 0x14702fa` 是它的调用者。

---

## 2. `#1` 才是关键：`sched_yield` 由哪调用

`sched_yield` 在 glcore 里只有 **3 处**被调用：

| 位置 | 形式 | 上下文 |
|---|---|---|
| `146cae9` | `call sched_yield@plt` | `semctl` 失败重试（SysV 信号量初始化） |
| **`146ccc0`** | **`jmp sched_yield@plt`** | **cond 等待函数的跳转表分支（尾调用）** |
| `1476ad8` | `call sched_yield@plt` | 另一处 |

`146cae9` 可以排除（它有 `call semget/semctl`，栈上会看到）。

**`#1 = 0x15762a2` 是"返回地址"，实际落点在其前一条指令 `1576203: jmp 1576203` 循环体**
——而 `146ccc0` 是 `jmp`（尾调用），**它的调用者栈帧不会被保留**，所以 `#1` 显示的是
`sched_yield` 返回后 glcore 恢复执行的位置，即 `15762a2`。

**这段（`15761b0` 函数）是一个典型的自旋等待**：

```asm
15761dd: call  *0x290(%rbp)      ; 取时
...
1576203: mov   %r14,%rbx
1576206: jmp   1576227
1576210: pause                   ; ← 9 条 pause
1576212: mov   %rax,%rbx
1576215-1576225: pause × 8
1576227: call  *0x290(%rbp)      ; 再取时
157622d: cmp   %r12,%rax         ; 与截止时间比
1576230: jge   1576237           ; 超时 → 走
1576232: cmp   %rax,%rbx
1576235: jl    1576210           ; 未到时 → 继续 pause 循环
```

**9 条 `pause` + 反复 `call *0x290`（取时）+ 比较截止时间** = **用户态有界自旋**。

---

## 3. ★ 必须纠正报告 50 的解读

报告 50 我写：

> 10/12 次采样停在 `libc+0xf8040`，反汇编是 `lock cmpxchg %edx,0x1ec660` → **malloc 全局锁竞争**

**这个解读是错的。** 现在有了栈就清楚：

| 报告 50 说 | 实际 |
|---|---|
| `libc+0xf8040` = `__libc_lock_lock` 的 cmpxchg | **`libc+0xf8047` = `sched_yield+7`**（同一页内两个不同函数） |
| 符号标成 `__register_atfork+0x380` | 符号表在这个区段整体不可靠（glibc 段合并），**两个函数共享一页** |
| 是 malloc 锁竞争 | **是 glcore 主动调 `sched_yield` 让出 CPU** |

**为什么会被误导**：`0xf8040` 那一页里确实有 `lock cmpxchg 0x1ec660`（malloc 的锁），
但采样点 `0xf8047` 落在**同一页的 `sched_yield` 函数体内**。
**我把"同页里有 cmpxchg"当成了"采样点就是 cmpxchg"，跳过了核对采样点是否落在那个函数的地址范围内。**

**正确做法（已入技能库）**：采样得到 `<module>+<offset>` 后，**必须用 `objdump` 从该偏移往前找最近的函数入口**，
确认采样点属于哪个函数，不能因为"附近有某个特征指令"就下结论。

## 4. 那么"烧满一核"到底是什么

**是 glcore 的有界自旋等待，不是 malloc，也不只是 worker 的一次轻循环。**

```
#8  0x14702fa  ← 调用者
#7  0x123b297  队列处理器（1238920）—— 查队列空
#6  0x107f178
#5  0x1113962
#4  0x148756b
#3  0x1486c99
#2  0x14d66ca
#1  0x15762a2  自旋等待（9×pause + 取时 + 比截止时间）
#0  sched_yield
```

**一条 8 层的 glcore 调用链，最终在内核态 `sched_yield`。**

这意味着：

| 之前以为 | 现在 |
|---|---|
| worker 在"问队列空不空"（6.6µs/次 × 4698 次） | 它在**自旋等一个截止时间**，期间反复 `sched_yield` |
| 是"记账开销" | 记账只是路过；**主体是自旋等待** |
| 报告 50 说是 malloc 锁 | **是 glcore 的 `sched_yield` 重试** |

**`sched_yield` 在 98.8% 的时间里被调用**——这说明它在**主动把 CPU 让出去又立刻拿回来**，
是"有界自旋 + 让出"的混合策略，CPU 时间全记在它自己头上。

## 5. 对"改记账"的最终回答

| 问题 | 答案 |
|---|---|
| 调用者是 glcore 记账吗？ | **不是记账，是 glcore 的自旋等待循环**（`15761b0`） |
| 改记账能修它吗？ | **不能**。记账在 `#7` 那一层，自旋在 `#1` 那一层，两者是调用关系不是同一段 |
| 这条支线的性质 | **"有界自旋等待"** —— 这是 glcore 在等某个条件（很可能是 GPU 完成），用 `pause + sched_yield + 取时比较` 的混合策略 |

**所以：不改记账。这条支线的落点是"为什么这里要自旋这么久"。**

## 6. 明确结论

| 项 | 结论 |
|---|---|
| N47 的答案 | 调用者**是 glcore**，但**不是记账**，是 `0x15761b0` 的自旋等待函数 |
| 改记账 | **不做**。不在同一层 |
| 报告 50 | **解读错误**（把同页的 cmpxchg 当成采样点），已在本报告 §3 更正 |
| 这条支线的落点 | **glcore 的自旋等待策略**：`pause × 9 + sched_yield + 取时比较`，等到某个 deadline |

## 7. 唯一剩下要查的（一条）

**`0x15761b0` 在等什么。** 它有一个"截止时间"（`r12`）和"取时函数"（`*0x290`），
循环 `pause → 取时 → 比较 → 未到就再 pause`。

要查的只有一件事：**`r12`（deadline）是谁设的、等的是什么条件。**

**方法**：读 `0x15761b0` 的调用者（`#2 = 0x14d66ca` 那层）传进来的参数，
或用 uprobe 在那个函数入口读 `%rdi/%rsi`（**低频**，这里不是高频点）。

**这一步会回答**：
- 若 deadline = "GPU 完成 + 超时上限" → **这是正常的 GPU 等待，不是 bug**，优化空间在别处
- 若 deadline 是个短值而条件总不满足 → **和报告 46 的"从未满足的阈值"同构**，是同一类问题

### 8.1 方法论（三条）

1. **`<module>+<offset>` 必须核对"最近的函数入口"，而不是"附近有什么指令"。**
   本轮报告 50 就栽在这：`libc+0xf8047` 落在 `sched_yield` 里，
   而同一页的 `0xf8077` 才是 `lock cmpxchg`。**差 0x30 字节，结论完全相反。**

2. **`jmp` 尾调用会在栈上"吃掉"一层**。`sched_yield` 是尾调用进来的，
   所以栈里看不到它的直接调用者，只有返回地址（`#1`）。
   **遇到 `jmp <plt>` 形式的尾调用，要知道回溯会少一层。**

3. **9 条 `pause` + `sched_yield` 是"有界自旋"的签名**。
   看到这个组合就别再找"锁竞争"了——它在等一个 deadline，不是在抢锁。
