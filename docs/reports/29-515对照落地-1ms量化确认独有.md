# 29 · 515 对照落地：1ms 量化确认为 525 独有，525 的 map 多出 1~2 个 tick

> 2026-10-25 20:10
> 机器已切回 **515.105.01**。用同一 primus 二进制、同一套 16 个 libGL 探针、同一 heaven 场景、
> 同一采集脚本（`c1_mode.sh`）、同一分析器，对 515/525 做完全同构的对比。
> **五条结论：**
> 1. **515 的 D 比 525 小 2.9×（1080p）/ 9.0×（640×360）**，与用户实测的 108fps vs 34fps 方向一致。
> 2. **515 在 640×360 下完全没有 1ms 量化**：83.2% 的帧 map **立即返回**（<0.3ms），**最大值仅 0.81ms —— 连第一个 1ms 边界都没碰到**。
> 3. **525 在所有分辨率下「立即返回」比例 = 0%**，最小值 2.03ms（1080p）/ 0.74ms（640×360），且 640×360 呈 1.0/2.1/3.0ms 三簇。
> 4. **把 map 耗时与纯传输时间对比**（隔离测试测得 0.285ms @640×360、2.5ms @1080p）：
>    515 的 map ≈ 纯传输；**525 的 map 多出 1.88ms（640×360）≈ 2 个 1ms tick**。
> 5. **报告 28 的「1ms 量化」从推测升级为对照确认**；"2ms 固定项 = 2 个 tick"成立。
> 6. **★ 追加实验（§6）：把 `PRIMUS_SLEEP` 加大到 99，515 的 map 从 1070µs 掉到 8µs，而 D 不变（11.0→11.2ms）。**
>    → **D 就是"数据真正可见的时刻"**，睡眠只决定 map 要不要补等。
>    → 差异浓缩成一个数：**T_完成 从 515 的 11.0ms 推迟到 525 的 29.4ms**。
>    → 且 **525 在两个分辨率下都 `D ≈ 1/fps`（零重叠），515 则 D 与帧时间脱钩（有重叠）**。

## 3. ★ 1ms 量化：对照确认是 525 独有

### 3.1 640×360（最干净的判据）

**515**（n=1836，中位 0.219ms，范围 **[0.01, 0.81] ms**）：

```
  <0.3ms（立即返回）: 1528  83.2%
  >=0.3ms 部分：0.3ms 256 | 0.4ms 220 | 0.5ms 29 | 0.6ms 6 | 0.8ms 1
```

**最大值 0.81ms < 1.0ms** —— 意味着 515 的 map **从未碰到第一个 1ms 边界**，
所以根本不可能出现 1ms 量化。这是本条结论最硬的证据。

**525**（n=462，中位 2.165ms，范围 [0.74, 3.52] ms）：

```
  <0.3ms（立即返回）: 0   0.0%
  0.9-1.2ms   86  ← 簇①  ~1.05
  1.4-1.8ms    6  ← 空洞
  1.9-2.3ms  178  ← 簇②  ~2.1
  2.4-2.7ms    6  ← 空洞
  2.8-3.2ms  107  ← 簇③  ~3.0
```

**0% 立即返回，三簇间距 1.0ms。**

### 3.2 1080p

| | 515 | 525 |
|---|---|---|
| 中位 | 1.036 ms | 3.099 ms |
| **最小** | **0.01 ms** | **2.03 ms** |
| **<0.3ms 比例** | **18.5%** | **0%** |
| 分布覆盖 | 0.01 → 3.56（**连续全铺**） | 2.03 → 3.78（**有下限**） |

515 在 1080p 有一个 1.0–1.1ms 的峰（35%）。但它**同时有 18.5% 完全不等（<0.3ms）**，
且从 0.01 连续覆盖到 3.56 —— 这是"数据在 9ms 睡眠里传了不同进度、map 补剩余"的自然分布。

**525 则完全缺少"早到"这一支**：最小 2.03ms，没有一帧能免于等待。

### 3.3 判读

**最硬的两个数：**
- 515 640×360 的 **最大值 0.81ms** → 够不到第 1 个 tick
- 525 两个分辨率的 **<0.3ms 比例都是 0%** → 每一帧都被迫去等 tick

**1ms 量化是 525 独有的。报告 28 的推测成立。**

## 4. 定量：525 的 map 比「纯传输」多出 1~2 个 tick

用隔离测试（`rb_lat2 fbo`）测得的纯传输时间作基准：

| 分辨率 | 纯传输（隔离） | **515 map** | **525 map** | 525 多出 |
|---|---|---|---|---|
| 1920×1080 | 2.49 ms | 1.036 ms | 2.864 ms | +0.37 ms（≈½ 拍） |
| 640×360 | 0.285 ms | **0.219 ms**（≈纯传输） | **2.165 ms** | **+1.88 ms（≈2 拍）** |

**515 的 map ≈ 纯传输时间**（640×360：0.219 vs 0.285，甚至略小，因为部分已传）。
**525 的 map = 纯传输 + 1~2 个 1ms tick 的额外等待。**

这解释了报告 27 那个"2.05ms 固定项"：**它就是 tick 等待，不是带宽、不是 DMA 开销。**

### 4.1 为什么 1080p 只多 ½ 拍、640×360 多 2 拍

一个自洽的解释（未直接验证）：额外等待 = "从传输完成时刻到下一个 1ms 边界"的距离。
- 1080p：传输 2.5ms 完成 → 下一个边界 3.0ms → 等 ~0.5ms ✓（实测 0.37）
- 640×360：传输 0.285ms 完成 → 下一个边界 1.0ms → 只该等 0.7ms，**实测 1.88ms** ✗

**640×360 对不上**，说明除了"等边界"还有别的成分（可能是"完成检测要连续确认两次"或"tick 起点与传输起点不同相"）。
**这是下一步的具体靶点。**

## 6. ★ 追加实验：把睡眠加长，map 会归零，但 D 不变

这条是本轮最有价值的补充。在 **515** 上扫 `PRIMUS_SLEEP`（autosleep 的比例），1080p：

| `PRIMUS_SLEEP` | 理论稳态 | 实测 `usleep` | **`glMapBuffer`** | **D** | 主线程 `sem_wait` |
|---|---|---|---|---|---|
| 90（默认） | 9×map | 9.90 ms | **1 070 µs** | 11.00 ms | 2.94 ms |
| 97 | ~32×map | 10.73 ms | **171 µs** | 11.07 ms | 2.84 ms |
| 99 | ~99×map | 11.10 ms | **8 µs** | 11.21 ms | 3.00 ms |

**睡眠只多了 1.2ms，`map` 掉了 130 倍（1070µs → 8µs），而 D 几乎不动（11.00 → 11.21ms）。**

### 6.1 这说明了什么

`map` 的耗时**不是**一个固定的"tick 等待"，而是：

```
map 耗时 ≈ max(0, T_完成 − 睡眠结束时刻) + 少量收尾
```

其中 `T_完成` 是**数据真正在主机内存可见的时刻**（相对 rp_out）。

- 睡眠短于 `T_完成` → map 要补等（515 @PS=90：补 1070µs）
- 睡眠长于 `T_完成` → map 秒回（515 @PS=99：8µs）
- **`D = rp_out → map 返回` 在两种情况下都 ≈ `T_完成`** → **D 就是 `T_完成`**

### 6.2 于是 515/525 的差异可以浓缩成一个数

| | `T_完成`（= D） | 纯传输时间（隔离） | 额外延迟 |
|---|---|---|---|
| **515 · 1080p** | **≈11.0 ms** | 2.49 ms | **≈8.5 ms** |
| **525 · 1080p** | **≈29.4 ms** | 2.49 ms | **≈27 ms** |
| **515 · 640×360** | **≈2.37 ms** | 0.285 ms | **≈2.1 ms** |
| **525 · 640×360** | **≈21.3 ms** | 0.285 ms | **≈21 ms** |

**525 的 PBO 回读完成时刻从 515 的 11ms 推迟到了 29.4ms。**

### 6.3 与帧率的对应关系（强提示）

| | D | 1/fps | 关系 |
|---|---|---|---|
| 515 · 1080p | 11.0 ms | 9.26 ms（108fps） | **D > 帧时间** → 有部分重叠 |
| 525 · 1080p | **29.4 ms** | **28.8 ms（34.7fps）** | **D ≈ 帧时间** → **几乎零重叠** |
| 515 · 640×360 | 2.37 ms | 5.5 ms（183fps） | D < 帧时间 → 重叠明显 |
| 525 · 640×360 | **21.3 ms** | **21.7 ms（46fps）** | **D ≈ 帧时间** → **几乎零重叠** |

**525 在两个分辨率下都满足 `D ≈ 1/fps`，即 readback 与渲染完全串行化。**
515 则 `D 与帧时间脱钩`（1080p 甚至 D > 帧时间，说明回读被上一轮的渲染遮住）。

> **这是目前最能解释"3 倍慢"的定量关系，但它仍是相关而非因果**：
> 也可能反过来——是 D 变长导致 fps 下降（D 就是瓶颈）。两种说法在数学上等价，
> 要区分需要看"主线程在 D 期间到底在做什么"（渲染下一帧？还是空等？）。

### 9.1 本轮踩的两个坑

1. **低分辨率下 GPU util 门限失效**：515 在 640×360 跑 183fps，GPU 反而空闲（CPU 瓶颈），
   原"util ≥ 50% 连续 5 次"的稳态门会误判"未达稳态"而中止。
   → **稳态判据要按场景选**：高帧率低分辨率时用帧数或固定等待，不要只信 GPU util。
2. **glcore 探针偏移随版本变**：`c1_register.sh` 里的 `abs_146c680` 是 525 的地址，
   515 上必须跳过（否则注册到错误位置或失败导致整批注册中断）。已改成按 `nvidia-smi` 版本分支。
