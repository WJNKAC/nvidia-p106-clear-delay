# 报告 119 · N128：报告 118 的带宽结论被实测推翻，但留下一条更强的东西

> 日期：2026-10-26
> 触发：报告 118 把 dmon 实测的 **445 MB/s 当成了链路容量**，据此得出"Gen1 只有 445 MB/s ⇒ 121 µs"。
> 本轮直接测这张卡的真实 DMA 带宽，并做 PCIe 争用对照。
> 结论：**带宽论作废；但"121 µs 路径确实走在 PCIe 上、且是延迟敏感"被两个独立实验证实。**

---

## 0. 一句话

**445 MB/s 是我测出来的吞吐，不是链路的容量。这张卡真实 H2D 是 3.303 GB/s，52.6 KB 纯传输只要 23.95 µs。**
**所以"Gen1 带宽不够"是错的 —— 报告 118 的因果链断在第一步。**
**但争用实验给了新证据：4 个进程把 PCIe 打满时，M3 从 125.9 ms 涨到 147.0 ms（+16.8%），M1 一动不动（7.31 ms）。**
**⇒ 121 µs 这条路确实占用 PCIe，但它是"延迟/串行事务"受限，不是"带宽"受限。**

---

## 1. 先修错：445 MB/s 到底是什么

| 项 | 报告 118 的说法 | 实际 |
|---|---|---|
| 445 MB/s | "Gen1 只有 445 MB/s"（当成容量） | **实测吞吐**，是结果不是上限 |
| Gen1 x16 容量 | — | 5.0 GT/s÷8×16 = **5.0 GB/s 裸**，8b/10b 后 **4.0 GB/s** |
| 445 MB/s 占容量 | 暗示 100% | **11.1%** |
| 真实 H2D（本轮实测） | 未测 | **3.303 GB/s**（64 MiB × 20，`cuMemcpyHtoD`+sync） |
| 真实 D2H | 未测 | **3.324 GB/s** |

**445 MB/s ＝ 52.6 KB ÷ 121 µs 恒等式的结果**，把它读成"链路上限"是纯粹的读数错误，
而且犯了 SKILL §38.5 的同一条：**拿一个恒等式当因果**。

---

## 2. 决定性实测：52.6 KB 在这张卡上只要 23.95 µs

探针：`analysis/probes/n128a_pciebw.c`（CUDA Driver API + dlopen，不需要 nvcc、不需要显示）
运行：`<user>@<testhost>`，P106-100 / 525.116.03 / Gen1 x16

```
== A. 大块顺序传输 (64 MiB x 20) ==
  H2D :    3.303 GB/s   (52.6 KB 需   16.27 us)
  D2H :    3.324 GB/s

== B. 单次传输 + 每次 cuCtxSynchronize（强制往返，不允许排队） ==
       bytes      iters       us/次         MB/s
        4096       2000         6.34        646.2
       16384       2000        10.52       1558.0
       53760       2000        23.95       2244.4     ← 就是"52.6 KB 一次"
      262144        500        98.47       2662.3
     1048576        500       380.75       2754.0

== C. 同尺寸但不每次同步（可排队） ==
        4096       2000         5.56        736.3
       53760       2000        23.13       2323.8
```

**关键**：`53,760 B` 一次带同步的往返 = **23.95 µs**。
而驱动每对花的是 **121~127 µs**，是它的 **5.1 倍**。

> 也就是说：**即使 525 真的每对往显存写 52.6 KB，PCIe 也只该收 24 µs。剩下的 ~100 µs 不是传输。**

线性拟合这张卡的"小传输定价"：

```
单次代价 ≈ 5.5 µs（固定往返） + 字节数 / 2.7 GB/s
52.6 KB 一次  = 5.5 + 19.5 = 25.0 µs   （实测 23.95 ✓）
```

**用它反解"121 µs 需要几次往返"**：

```
121 = 5.5·N + 52.6KB/2.7GBps = 5.5·N + 19.5
  ⇒ N ≈ 18.5 次
```

⇒ **候选机制：每对 ~18 次串行往返，每次约 2.8 KB**（不是一次大 DMA）。
这是假设，但它给出可检验的预言（见 §5）。

## 2.5 本轮重测的六模式全表（`GL_RENDERER = NVIDIA P106-100/PCIe/SSE2`）

为避免再测到核显，这次在同一个 `ssh` 里带了 `__GLX_VENDOR_LIBRARY_NAME=nvidia` 并逐个打印 renderer。

| 模式 | 做了什么 | total_p50 (ms) | 每对/每 draw (µs) | 判读 |
|---|---|---|---|---|
| M1 | 只画 1000 | **7.298** | 7.3 | 基线 |
| M2 | 改 1000 次 uniform（不切对象） | **7.299** | 7.3 | **免费 ⇒ uniform 不触发同步** |
| M3 | 切 program 与 draw 交替 1000 对 | **127.187** | 127.2 | 收费 |
| M6 | 切到**同一个** program 与 draw 交替 | **268.001** | 268.0 | 收费，且 **2.1× M3** ⚠️ |
| M8 | 切 500 次 + 只画 1 次（不相邻） | **2.982** | — | 免费（只有 1 次生效） |
| M9 | 先连切 1000 次，再连画 1000 次 | **7.540** | 7.5 | ≈M1，只多 1 次同步 |

两条新信息：

1. **M2 = M1（7.299 vs 7.298，差 0.01%）** ⇒ 只有"绑定对象"类变更才置 dirty，改 uniform 不算。
   这与报告 116 的"uniform 内联在 pushbuffer"一致。
2. **⚠️ M6 这次是 268 ms，而报告 114 测的是 128.453 ms（≈M3）。同一台机、同一驱动、同一参数。**
   我没有解释。可能原因：M6 的"切到同一 program"在这版 n83a 里等价每次绑定 2 个对象，
   或上一次测量时 GPU 处于不同功耗态。**这条不一致我留着，不掩。**
   它不影响主结论（两者都是"每对 ~120~270 µs"，都远超 24 µs 的传输代价），
   但它说明**每对代价不是严格常数，会随操作形态变化约 2 倍** —— 这本身也否证了
   "固定量子（如固定 ctxsw 时长）"这类最简单的解释。

## 3. 争用实验：121 µs 这条路确实在 PCIe 上

做法：4 个 `n128a` 死循环进程把链路打满（每个约 3.3 GB/s，合计远超 4 GB/s ⇒ 饱和），
同时跑 n83a。

必须用 `__GLX_VENDOR_LIBRARY_NAME=nvidia`（否则 Xwayland 会落到 Intel 核显上，
本轮第一次就踩了：`GL_VENDOR=Intel`、`map_p50=29.153 ms`，那是核显的数，不是本案的数）。

| 模式 | 无争用 | 争用中 | 变化 |
|---|---|---|---|
| **M3 n=1000**（每对都切 program） | map_p50 **125.867** ms | **147.09 / 147.00** ms | **+16.8%** |
| **M1 n=1000**（只画，0 次同步） | map_p50 7.394 ms | **7.311** ms | **0%（还略低）** |

原始：
```
M3 base       submit_p50=1.378  map_p50=125.867  total_p50=127.253  fps=7.86
M3 争用 #1     submit_p50=2.425  map_p50=147.090  total_p50=149.531  fps=6.69
M3 争用 #2     submit_p50=2.409  map_p50=147.005  total_p50=149.397  fps=6.69
M1 争用        submit_p50=0.068  map_p50=7.311    total_p50=7.406    fps=135.03
```

两条读数：

1. **M1 完全不受影响** ⇒ 争用不是把 CPU 或 GPU 拖慢了，是专挑"有同步"的那条路。
2. **M3 只涨 17%** ⇒ 如果它是带宽受限，链路从 11% 打到 100% 该涨成倍，而不是 17%。

**M3 的等效带宽：125.9 µs → 418 MB/s；147.0 µs → 358 MB/s。**
链路被打满，它只从 418 掉到 358（-14%）。
⇒ **它拿的是"优先通行 + 每次都要排一个队"的待遇，是延迟受限（queueing delay），不是抢带宽。**

## 4. 修正后的完整图景

```
每对（一次状态变更 + 紧随其后的 draw）
  ├── 固定写出 52.6 KB          ← dmon 实测（445 MB/s ÷ 8264 对/秒），强
  ├── 纯传输只值 23.95 µs        ← 本轮实测，强
  ├── 实际花 121~127 µs          ← 反复实测，强
  └── 差额 ~100 µs ≈ 18 次串行往返 × ~5.5 µs  ← 拟合推断，中
          └── 这些往返走在 PCIe 上（争用 +17%，M1 不动）  ← 本轮实测，强
```

**报告 118 中"Gen1 的 445 MB/s"整段作废**，替换为：

> 每对要往显存写固定的 52.6 KB，而且是以**一串串行小事务**写的（约 18 次往返）。
> P106 的价值不在"带宽比别人小 8 倍"，而在**这条链路上的每次往返都贵**（5.5 µs 固定开销，
> 大块 DMA 才 2.7 GB/s，小事务只有 0.65 GB/s）。

## 5. 三个可以直接证伪的预言

| 编号 | 实验 | 若预言成立 | 若不成立 |
|---|---|---|---|
| **N128-A** | 把每次同步上传的块**变小**（例如只改一个 UBO 而不切 program） | 每对代价应 ∝ 往返次数，明显下降 | 若仍是 121 µs ⇒ "往返次数"错，是固定量子 |
| **N128-B** | 装 515 跑 M3 + `dmon` | PCIe tx = **0**（515 不写这 52.6 KB） | 若 515 也有 445 MB/s 却仍是 0.03 µs ⇒ 流量与代价脱钩 |
| **N128-C** | 把链路降到 Gen1 x1（或用 `setpci` 限速） | 若代价与"每次往返"成正比，应再涨 16 倍 | 若几乎不变 ⇒ 连延迟都不是，PCIe 彻底出局 |

**N128-C 判别力最强**（不需要换驱动、不需要改代码）。但它要求 host 侧有权限动链路训练，
在本机只能靠 BIOS/`nvidia-smi -lgc` 之外的开关，未确认可行。

| 结论 | 强度 | 依据 |

## 7. 对"有输出的 Pascal 为什么没事"的重新表态

报告 118 说"Gen3 快 8 倍 ⇒ 15 µs ⇒ 不显眼"，**这条作废**（延迟不随代数 8 倍改善）。

现在的诚实说法是：**不能解释。** 只留下一个边界估算：

- 若 Gen3 的每次往返比 Gen1 便宜约 2×（典型链路延迟差），则每对约 60 µs，268 对 ≈ **16 ms**
  —— 正好压在 60 fps 的 16.7 ms 预算上。
- 这能解释"有输出的 Pascal **看起来**没事"（勉强够），但解释不了"社区一次都没报"。

**所以这条仍是本案最大的空白**，我不再给它编机制。

---

## 8. 一句话收尾

**报告 118 错了，错在把实测吞吐当成链路上限。**
**它站得住的部分只有两条，但这两条是硬的：**
**① 每对同步固定写 52.6 KB 到显存；不同步时精确为 0。**
**② 这条写路径只有 24 µs 是"传输"，其余 ~100 µs 是串行往返，而且确实走在 PCIe 上（争用 +17%，M1 不动）。**
**"P106 特殊在哪"这个问题，从"带宽小 8 倍"退回"每次往返都贵"，量级从 8× 降到 ~2× —— 我不再声称它能解释所有现象。**
