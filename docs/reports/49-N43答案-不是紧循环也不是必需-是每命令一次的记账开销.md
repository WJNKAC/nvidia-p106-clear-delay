# 49 · N43 答案：既不是"紧循环"也不是"必需"——是**每条命令一次的记账开销**（并修正 N40 的被污染数据）

> 2026-10-26 06:10
> 用户要求 N43 答"紧循环还是必需"，二选一。
>
> **答案落在选项之外，但更有用：**
> **① 4700 次是结构性的（每命令/每批次一次），改不了"次数"；**
> **② 但每次调用都在做一遍"计时记账"（2 次间接取时 + 浮点累加 + 比较），而这份记账喂的阈值实测从未触发。**
> **→ 可改的不是循环结构，是那段无条件的记账。**
>
> **另外必须修正报告 48 的一个数据错误**：那个 37.1% 是被 uprobe 自己抬起来的。干净测量是 **58.4%**，而且**另有一个线程烧满 100.9% 一个核**。

## 1. N43 的答案

| 用户的二选一 | 实际情况 |
|---|---|
| 调用者是个紧循环（`while(!done) check();`）→ 每帧 4700 次是多余的 | **不完全是**。123 个静态调用点，其中 22 个在循环上下文里，但没有一个是"纯自旋等这个函数返回" |
| 4700 次是必需的（≈ draw call / buffer 数）→ 忙等是设计行为 | **次数上是的**：它是"每提交一批命令就查一次队列"的路径，次数由命令数决定 |
| **★ 真正的答案** | **次数改不了，但每次调用的"记账"开销可以去掉** —— 记账喂的阈值（`g > 1e6`）实测**从未触发过** |

**一句话**：**问题不在"调用了 4700 次"，在"每次调用都无条件做一遍 profiling 记账"。**

---

## 2. 静态：123 个调用点，没有一个是纯自旋

`grep "call 1238920"` → **123 处**。用"call 后 40 条内有回边"的启发式筛出 22 处疑似循环，逐个看：

| 调用点 | 循环体 | 实情 |
|---|---|---|
| `0x123a555` | 5 字节 | **误判**：`jmp 123a4e9` 跳进的是收尾路径（查完就 `ret`），不是循环 |
| `0x1377731` / `0x1377adb` / `0x1768fca` / `0x176ac18` | 5 字节 | 同类"跳进收尾"，均非真循环 |
| `0x1030777` / `0x1030a5c` / `0x1030cc7` / `0x1031126` / `0x103207d` | 0x17~0x88 | 是循环，但循环变量不是"等这个函数返回" |
| `0x10403a0` / `0x1041eec` / `0x1065f4a` 等 | 0x26~0x33 | 同上 |

**关键：没有一个调用点长成 `while(cond) { call; }` 这种纯自旋。**
它们是"在处理第 N 条命令的路径上顺带调一次"。

### 2.1 一个具体的调用点（`0x123a4e0`）

```asm
123a538: mov  (%rdi),%rax            ; rax = 命令缓冲写指针
123a540: movl $0x8704,(%rax)         ; 写入命令码 0x8704
123a546: add  $0x10,%rax             ; 前进 16 字节
123a552: mov  %rax,(%rdi)            ; 更新写指针
123a555: call 1238920                ; ← 查一次队列
123a55a: jmp  123a4e9                ; 查 0x8e0880，为 0 就 ret
```

**这是"写完一条命令 → 查一次队列"的形态。** 次数 = 命令数。

## 3. 每次调用在做什么：无条件记账

`1238a28` 循环里"队列空"的那条路（99.7% 走这条）：

```asm
1238b48: ; 队列空分支
1238b65: movslq %r12d,%r12
1238b68: add    $0x4000,%rax
1238b72: mov    %rax,0x8(%rbx)
1238b76: cmpb   $0x0,0x8e0c4c(%rbx)
1238b7d: movss  0x8e0c40(%rbx,%r12,4),%xmm2
1238b99: call   *0x290(%rax)          ; ★ 取时 #1（vtable 间接调用）
1238bb3: sub    0x8e0c40(%rbx),%rcx   ; elapsed = now - last
1238bba: cvtsi2ss %rcx,%xmm0
1238bbf: addss   0x8e0c50(%rbx,%rdx,4),%xmm0   ; ★ 累加到 float 数组
1238bc8: movss   %xmm0,0x8e0c50(%rbx,%rdx,4)
1238bd1: mov     %rax,0x8e0c40(%rbx)  ; 更新 last
1238bec: ...
1238bf7: subss   %xmm2,%xmm0
1238c11: comiss  %xmm1,%xmm0          ; 与阈值比较
1238c14: setb    0x8e0c70(%rbx)       ; 存一个 bool
1238c1b: add $0x18,%rsp ... ret
```

**每次调用 = 1 次间接取时 + 1 次整数减法 + 2 次 float 转换/累加 + 1 次比较 + 1 次 store + 函数进出。**

而且函数入口 `123894e` 还有**另一次** `call *0x290` —— **每次调用 2 次取时**。

### 3.1 这份记账服务谁？一个从未触发的阈值

累加的两个 float 正是报告 46 里那两个：

| 字段 | 累加自 | 阈值 | 实测值 | 触发过吗 |
|---|---|---|---|---|
| `0x8e0c50[idx]` | 本函数每次调用 | 汇总到 `g=0x8e0c60` | — | — |
| `g` (`0x8e0c60`) | `12389a4` 累加 | **> 1,000,000** | **1,440 / 2,157** | **否** |
| `f` (`0x8e0e00`) | `1237e01`（另一个 ctx） | `10 < f < 2²¹` | **0（本 ctx）** | **否** |

**→ 每帧 4,700 次记账，喂的是一个从来没满足过的条件。**

## 4. 必须修正报告 48：37.1% 是被 uprobe 自己抬起来的

我在 N40 里一边开着 1,235,751 次命中的 uprobe、一边测 CPU。**每次 int3 陷门约 1~2µs**，
1.23M × 1.5µs ≈ **1.85 CPU 秒** —— 而 N40 报的"3.010 CPU秒"里有一大半是这个。

### 4.1 干净复测（无任何探针，N44）

| tid | CPU秒 | 占1核 |
|---|---|---|
| **25461** | **7.970** | **99.5%** |
| 25460 | 2.530 | 31.6% |
| 25459 | 1.740 | 21.7% |
| 25414（主线程） | 1.490 | 18.6% |
| 全进程 | 16.100 | **201.0%** |

### 4.2 用低频探针（只开 1 秒，263 次命中）认出 worker 身份（N45）

| tid | CPU秒 | 占1核 | |
|---|---|---|---|
| **25771** | **8.070** | **100.9%** | ← 烧满一个核 |
| **25770** | 4.670 | **58.4%** | ← **readback worker（mb_out 所在）** |
| 25769 | 1.840 | 23.0% | |
| 25725（主线程） | 1.680 | 21.0% | |
| 全进程 | 18.940 | **236.8%** | |

### 4.3 修正结论

| 报告 48 说 | 修正后 |
|---|---|
| worker 占 37.1% | **58.4%**（N40 的 37.1% 被 uprobe 抬高，且方向是"低估"了真实占用） |
| 只有一个线程忙 | **不止**：另有 **25771 烧满 100.9% 一个核** |
| 11.4ms CPU/帧 | **约 17.9ms CPU/帧**（4.670s ÷ 261 帧）——**比我原来报的更大** |

> 修正的方向是**让问题更严重**，不是更轻。但归因错了：不是只有 worker，是两个线程。

**未定**：`25771` 是谁（tid 紧邻 worker，很可能是 primus 的 display worker）。

## 5. 所以"可改吗"——可改，但不是改次数

| 方案 | 可行性 | 预期 |
|---|---|---|
| **改循环结构**（把 4700 次变成 1 次） | **不可行**：次数由"每命令查一次队列"决定，属结构 | — |
| **★ 去掉/采样化每调用记账** | **可行**：那段记账喂的阈值从未触发 | 每调用省 2 次取时 + 浮点运算；若占 2.4µs 的一半 → **每帧省 ~5.6ms** |
| 让"队列空"时直接 `wait` 而不是返回 | 可行但**有害**：会让每命令都睡 2ms | 不可取 |

**关键判断：这段记账是 profiling/统计代码，不是功能代码。**
它累加的 `0x8e0c50[]` → `g` 只被一个 `> 1e6` 的阈值消费，而 `g` 实测 1440/2157。
**去掉它不影响正确性，只影响一份从未被使用的统计。**

## 6. 明确结论（不再"下一步再说"）

| 问题 | 答案 |
|---|---|
| 是紧循环吗？ | **不是**。123 个调用点无一长成纯自旋 |
| 4700 次是必需吗？ | **次数是结构性的**（每命令一次），但**每次的开销不是必需的** |
| 可改吗？ | **可改，改"记账"不改"次数"** |
| 预期收益 | 每帧 5~8ms（30.9 → 23~26ms，32 → 39~43fps）**这是估算，需实测** |
| 这条支线 | **可通，但落点从"循环结构"改成"记账开销"** |

## 7. 唯一剩下要查的（一条，不是清单）

**`25771` 是谁？** 它烧满 100.9% 一个核，比 worker 还多。
在动手改记账之前必须先知道它——因为**如果它才是瓶颈，改记账的收益会被它吃掉**。

查法：用低频探针认身份（同 N45 的方法，探针开销可忽略），或读它的 `wchan` / `stack`。

**在此之前不该开始改代码**：现在的收益估算是基于"worker 58.4% 全是记账"，而 25771 的存在说明这个估算的前提可能不成立。

### 8.1 方法论（三条，都已入技能库）

1. **★★ 用 uprobe 测 CPU 会污染结果。** 本例 1.23M 次命中 ≈ 1.85 CPU秒，
   而"被测对象"只有 3 秒。**要么不开探针，要么用低频探针只认身份、另测 CPU。**
2. **"循环检测"启发式（call 后有回边）会误判**：`jmp` 跳进收尾路径也算"回边"。
   本例 22 个候选里至少 5 个是这种假阳性。**必须读循环变量的来源，不能只看跳转。**
3. **归因到一个线程之前，先看全进程的 CPU 排名。** 本例盯着 worker 时，
   另一个线程正烧满 100.9% 一个核——只看单线程会漏掉更大的那个。
