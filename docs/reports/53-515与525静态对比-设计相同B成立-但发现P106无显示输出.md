# 53 · 515/525 静态对比：**设计相同（B 成立）**，但发现更根本的差异——`display_mode=Disabled`

> 2026-10-26 09:30
> 用户提出的关键反驳：如果 20µs 轮询是全局设计，1060 也该受影响；但社区证据显示有输出的 1060 不受影响。
> 要求静态对比 515/525 的 `0x15761b0` 是否存在、deadline 是否相同。
>
> **答案：515 有，deadline 也相同（都是 0x14 = 20µs）→ B 成立。**
> **但顺手查到一件更根本的事：`nvidia-smi` 显示 `display_mode = Disabled` —— P106-100 没有显示输出。**
> **这同时回答了"P106 走哪条路、1060 不走"和"为什么 20µs 内完不成"。**

---

## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **515 里也有这个 20µs 自旋循环** | 特征字节 `f3904889c3f390×8` 在 515.105/515.48 各命中 **1 处** |
| 2 | **deadline 也相同：`lea 0x14(%rax)`** | 515.105 `0xfbcc69` / 525 `0x15761e6`，**都是 +20µs** |
| 3 | **默认超时也相同：`movl $0x17`** | 515.105 `0xfbcce1` / 525 `0x1576267`，**都是 23** |
| 4 | **vtable 静态初始化都是 `xor eax,eax; ret` 桩** | 两版一致（运行时会替换） |
| 5 | **指针指令逐条对应** | 见 §2 对照表 |
| 6 | → **B 成立**：设计两版一样 | 由 1–5 推出 |
| 7 | **★ 但 `display_mode = Disabled`**：P106-100 无显示输出，必须走 PRIME | `nvidia-smi` 实测 |
| 8 | **★ 这同时是 A 的答案**：不是"525 新增了 PRIME 路径"，而是 **P106 硬件无输出，强制走 PRIME** | 由 7 推出 |

**一句话**：**515 和 525 在这个函数上几乎是同一份源码（deadline、默认超时、指针指令全一致）。
真正的分水岭不在驱动版本，而在"这张卡有没有显示输出"——P106 没有，所以它必须走 PRIME 跨 GPU 拷贝。**

## 2. 逐指令对照（这是同一份源码）

| 525.116 | 515.105 | 语义 | 差异 |
|---|---|---|---|
| `15761d6: movl $1,0x2c(%rdi)` | `fbcc56: movl $1,0x10(%rdi)` | obj 标记"正在等" | 字段偏移（结构布局变了） |
| `15761dd: call *0x290(%rbp)` | `fbcc5d: call *0x280(%rbp)` | `t0 = now()` | vtable 槽号 |
| **`15761e6: lea 0x14(%rax),%r12`** | **`fbcc69: lea 0x14(%rax),%r13`** | **deadline = t0+20µs** | **值相同** ✅ |
| `15761f8: mov $3,%edi` | `fbcc6f: mov $3,%edi` | 等待 type=3 | 相同 |
| `15761fd: call *0x280(%rbp)` | `fbcc74: call *0x270(%rbp)` | 执行等待 | vtable 槽号 |
| **`1576210: pause ×9`** | **`fbcc85: pause ×9`** | 自旋 | **完全相同** ✅ |
| `1576227: call *0x290(%rbp)` | `fbcc9c: call *0x280(%rbp)` | `now()` | vtable 槽号 |
| `157622d: cmp %r12,%rax` | `fbcca2: cmp %r13,%rax` | 与 deadline 比 | 寄存器名 |
| `1576248: add %rax,0x6f88(%r13)` | `fbccb8: add %rax,0x6f50(%r12)` | 累加统计 | 统计字段偏移 |
| **`1576267: movl $0x17,0xc(%rsp)`** | **`fbcce1: movl $0x17,0xc(%rsp)`** | **默认超时=23** | **值相同** ✅ |

**除了结构体字段偏移和 vtable 槽号（都是布局变化），控制流和立即数完全一致。**

### 2.1 搜索方法（值得记录）

一开始用 32 字节签名搜，**两版都"未找到"**——因为签名里含 `lea 0x14f8611(%rip),%rbp`，
**RIP 相对地址在不同版本必然不同**。

改用**不含 RIP 相对地址**的特征后命中：

```
f3 90            pause
48 89 c3         mov %rax,%rbx
f3 90 × 8        pause × 8
```

→ 525 `0x1576210` / 515.105 `0xfbcc85` / 515.48 `0xfbbf75`，**各 1 处，唯一**。

## 3. ★ 更根本的差异：P106 没有显示输出

```bash
$ nvidia-smi --query-gpu=name,display_mode,display_active --format=csv
name, display_mode, display_active
NVIDIA P106-100, Disabled, Disabled        ← ★
```

DRM 设备也印证：

```
card0-HDMI-A-1  disconnected
card0-HDMI-A-2  connected      ← 显示器在 card0（Intel）
card0-VGA-1     disconnected
card1                          ← P106，只有 renderD128 / renderD129，无连接器
```

**`display_mode = Disabled` 意味着这张卡不能直接驱动显示器。**
P106-100 是矿卡，出厂就砍掉了显示输出。

### 3.1 这解释了"为什么 P106 走这条路、1060 不走"

| 卡 | display_mode | 渲染路径 |
|---|---|---|
| **GTX 1060（有输出）** | Enabled | 直接渲染到自己的 framebuffer → **上屏零拷贝** |
| **P106-100（无输出）** | **Disabled** | **必须走 PRIME**：渲染到 pbuffer → 拷到 Intel → Intel 上屏 |

**所以 A 和 B 不是对立的**：

- **A 的"为什么 P106 走这条路"** → **因为硬件 `display_mode=Disabled`，不是 525 新增的**
- **B 的"为什么 20µs 内完不成"** → **因为 PRIME 每帧要跨 GPU 拷贝 8.29MB，T_land = 30.4ms（报告 40）**

**两个问题有同一个答案：这张卡没有输出，只能跨 GPU 拷贝。**

## 4. ★ 一个必须修正的量化：4697 次/帧 × 6.6µs = 31ms

上一轮我用 `30.9ms ÷ 20µs = 1545` 估算"每帧 1545 次尝试"。
但实测是 **152,167 次/秒 ÷ 32.4 fps = 4,697 次/帧**。

**4697 ≠ 1545，差 3 倍。** 这意味着：

```
每次平均耗时 = 30.9ms ÷ 4697 = 6.6 µs   （而不是 20µs）
```

**→ 大多数尝试只花 6.6µs 就返回了，并没有等满 20µs。**

### 4.1 这个数字与报告 49 完全吻合

报告 49 的结论是"**每写完一条命令查一次队列 = 4,700 次/帧**"。
本轮实测 **4,697 次/帧**。

**两个数字独立测出来，吻合到 3/4700 = 0.06%。**

### 4.2 所以那 98.8% 的真正构成

```
4697 次/帧 × 6.6µs = 31.0 ms  ≈  一帧时间 30.9ms
```

**→ 这个自旋函数不是在"偶尔等待"，它在"填满整帧"。**

每次 6.6µs 的开销来自：`9×pause`（约 9×30 = 270ns 空转）+ `call *0x290`（取时，
含一次 `call 1467690` 读时钟 + magic 除法）+ `cmp` + 函数进出 + 可能的 `sched_yield`。

**这就是报告 49 说的"记账开销"的物理实体**——只不过它不是记账，是**每条命令一次的 GPU 状态查询**。

## 5. 那"515 为什么不烧 98.8% CPU"

用户的这个问题，现在可以给出**基于静态证据的诚实回答**：

**两版代码一样，参数一样 → 515 上也应该有这个循环。** 差异只能来自"被调用的次数"或"每次的耗时"。

按同样的公式推算：

| | 一帧 | 次数/帧（若每次 6.6µs） | 次数/秒（×fps） |
|---|---|---|---|
| 525 + P106 | 30.9 ms | 4,697 | 152,000 |
| 515 + P106 | 9.2 ms | 1,394 | 150,600 |

**次数/秒几乎一样（15 万）** —— 因为"每 6.6µs 一次"是恒定的。

**所以按纯静态推算，515 也该烧同样多的 CPU。这与"515 跑 108fps 正常"矛盾。**

**这个矛盾有两个可能解释，静态无法区分（必须诚实标注）：**

| 解释 | 判据 | 能否静态验证 |
|---|---|---|
| **(a) 515 运行时 vtable 槽指向了不同的实现**——比如真正阻塞等待，而不是 `yield` 后立即返回 | 需要读 515 进程的运行时 vtable 槽 | ❌ 需要 515 上机 |
| **(b) 515 上这个函数被调用的次数真的少**——即上层结构不同 | 需要对比上层调用者 | ⚠️ 可静态对比，但工作量大 |

**注意**：报告 40 已经测过 515 的真实 `T_land` = 10.1ms、`D` = 10.1ms。
如果 515 也这样烧 CPU，那它 108fps 就更难解释了——**说明 (a) 或 (b) 至少有一个成立**。

## 6. 对"是不是 bug"的最终表述（采纳用户的修正）

用户指出我上轮的表述问题，这个修正是对的：

> ❌ 我上轮写："20µs 是设计行为，所以不是 bug"
>
> ✅ 正确的表述：
> **525 在 PRIME 路径上选择了 20µs 轮询。这个轮询在两版里都存在（设计相同）。
> 真正的问题是两个：**
> **① 为什么 P106 走 PRIME 路径** → 因为 `display_mode=Disabled`（硬件属性，不可改）
> **② 为什么 P106 上 20µs 内完不成** → 因为 PRIME 每帧跨 GPU 拷贝 8.29MB，T_land 30.4ms（报告 40）

**所以根因是"无输出显卡必须跨 GPU 拷贝"，20µs 轮询只是把这个代价放大成 CPU 占用。**

## 7. 这条线索的最终定位

| 层 | 结论 | 可改吗 |
|---|---|---|
| `display_mode=Disabled` | P106-100 的硬件属性 | ❌ 不可改 |
| PRIME 跨 GPU 拷贝 | 无输出卡的必经之路 | ❌ 不可绕过（除非换成有输出的卡，或用其他机制上屏） |
| 每帧拷 8.29MB，T_land 30.4ms | 报告 40 | ◑ **只能优化路径**（少拷字节 / 让拷贝更早落地） |
| 20µs 轮询 × 4697 次/帧 = 31ms CPU | 本轮 | ◑ 是"每命令一次查询"的必然结果 |

**→ 结论：这条支线（驱动内部等待机制）已经挖到底。
能改的只剩"每帧拷多少字节"和"拷贝什么时候落地"，这两条都指向报告 40 的 T_land，而不是驱动实现。**

### 8.1 方法论（三条）

1. **跨版本字节签名必须排除 RIP 相对地址。**
   32 字节签名含 `lea ...(%rip)` → 两版都搜不到；去掉后 20 字节特征唯一命中。
   **通用做法**：签名只取"操作码 + 立即数（语义稳定的）+ 寄存器分配"，避开所有 `%rip` 相对偏移和结构体偏移。

2. **对比"同源不同版"时，要专门看差异是"布局变化"还是"逻辑变化"。**
   本例 `0x2c→0x10`、`0x290→0x280`、`0x6f88→0x6f50` 都是布局；
   `0x14`、`0x17`、`pause×9` 是逻辑，且**全部相同**。
   **判据**：立即数（语义常量）相同 + 控制流相同 = 同一份源码。

3. **"设计行为"不能直接推出"不是 bug"。**
   必须回答"这个设计在哪条路径上生效、这条路径是谁触发的"。
   本例设计相同、但路径不同（PRIME vs 直连），代价被放大 3 倍。
