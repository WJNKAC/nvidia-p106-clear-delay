# 报告 113 / N122：**"dirty→sync" 模型 —— 121µs 在 GPU 侧，触发条件是"状态变更后紧跟的第一个 draw"**

- 时间：2026-10-26 19:05
- 指令：用户「先静态对比，<user> 机器我要处理一下，不要连接」
- **本轮全程离线**：只用本地已有的 `glcore` asm 转储 + `n83a` 扫描数据 + 两版 `nv-kernel.o_binary`
- 结果：**用 7 个已有实验把机制刻画到全部自洽（误差 <6%），并纠正前两轮的方向错误**

---

## 0. 结论

**121 µs 不在 CPU 侧，在 GPU 侧。触发条件是精确的：**

> **状态变更置一个 dirty 标志 → 下一次 draw 看到 dirty → 做一次 GPU 侧同步（121 µs）→ 清 dirty。**

| 情形 | 同步次数 | 实测 | 模型 | |
|---|---|---|---|---|
| 只切换，不画（M8，500 次） | 1 | 2.620 ms | 2.731 | ✓ |
| 只画，不切换（M7 c=0，1000 draw） | **0** | 2.635 ms | 2.610 | ✓ |
| 先切 1000 再画 1000（M9，不相邻） | **1** | 2.640 ms | 2.731 | ✓ |
| 切+画交替 1000 次（M6，切到**同一** program） | **1000** | 123.652 ms | 123.610 | ✓ |
| 1000 draw 中插 1000 次切换（M7 c=1000） | **1000** | 123.360 ms | 123.610 | ✓ |
| 100 对（M3） | 100 | 15.170 ms | 14.710 | ✓ |
| 100 个 draw 无切换（M1） | **0** | 3.316 ms | 2.610 | ✓ |

**七个案例、跨三种操作方式、两个相差 47 倍的数量级，全部对上。**

## 1. 先把"这在 CPU 侧"排除掉（这是本轮最硬的一步）

`scan4_525.116.03.csv`，`mode=6, n=1000`：

```
submit_p50=1.290 ms      ← CPU 提交 1000 对的总时间
rp_p50    =0.017 ms      ← glReadPixels（异步，不阻塞）
map_p50   =123.652 ms    ← glMapBuffer（阻塞等回读）
```

**CPU 把 1000 对全部提交完，只花了 1.29 ms —— 每对 1.29 µs。**
**然后 `glMapBuffer` 等了 123.65 ms。**

⇒ **那 122 ms 里 CPU 什么都没干，它在等 GPU。**
⇒ **121 µs/对 是 GPU 侧的执行时间，不是 CPU 的等待开销。**

**这一条同时否掉了报告 111 和 112 两轮的方向：**

| 报告 | 当时的说法 | 为什么错 |
|---|---|---|
| 111 | "121 µs 是 futex 往返（105 µs/次）" | futex 每帧只 3 次；且 futex 是 CPU 侧 |
| 112 | "主成本在 `map` 等完成"（对）但归给 futex | `map` 等的是 **GPU**，不是 futex；`submit` 只 1.29 µs/对 已证明 CPU 不慢 |

**正确的一句话**：`map` 时间长**是因为 GPU 慢**，不是因为 CPU 在 `map` 里等锁。
`map` 只是**测量点**——它是唯一同步读取 GPU 进度的位置，所以 GPU 的成本全记在它头上。

## 2. "dirty→sync" 模型的推导

### 2.1 关键反例：切换免费、draw 免费、配对收费

| 实验 | 内容 | map 时间 | 说明 |
|---|---|---|---|
| **M8** | 500 次 `glUseProgram`，**只有 1 个 draw** | **2.610 → 2.620 ms（恒定）** | **切换本身完全免费** |
| **M7 c=0** | **1000 个 draw，0 次切换** | **2.635 ms** | **draw 本身完全免费** |
| **M9** | 1000 次切换，**然后**1000 个 draw（不相邻） | **2.640 ms** | **有变更、有 draw，但不交替 ⇒ 免费** |
| **M6** | 1000 次（切换 + draw）**交替** | **123.652 ms** | 121 µs/对 |
| **M7 c=1000** | 1000 draw 中均匀插 1000 次切换 | **123.360 ms** | 同上 |

**⇒ 收费的条件不是"有切换"、也不是"有 draw"，而是"切换之后紧跟 draw"。**

### 2.2 一个反直觉但决定性的细节：M6 切的是**同一个** program

n83a 源码（`mode == 6`）：

```c
for (int i = 0; i < NN; i++) {
    p_UseProgram(prog);              /* 每次都切到同一个 program —— 纯 no-op */
    glDrawArrays(GL_TRIANGLE_STRIP, 0, 4);
}
```

**驱动完全有能力识别"切到当前已绑定的 program"并跳过，但它没跳。**
n=1000 照样 123.652 ms。

**⇒ 525 不检查"状态是否真的变了"，只要调用了就置 dirty。**

### 2.3 模型为什么能解释 M9

M9 是"先 1000 次切换，再 1000 个 draw"：

- 1000 次 `glUseProgram` 把 dirty 置上（反复置，还是 1 个 dirty）
- 第 1 个 draw 看到 dirty → 同步一次 → 清 dirty
- 剩下 999 个 draw 看到 dirty=0 → **不同步**

**⇒ 总共只有 1 次同步 ⇒ 2.640 ms。** 与实测一致。

**这也解释了为什么报告 75 的"M9 不收费"看起来像"不相邻就免费"——真实的机制不是"相邻性"，而是"dirty 被多少个 draw 消费"。**

### 2.4 模型为什么能解释 M6 的线性

M6 每轮都是"置 dirty → draw 消费 → 清 dirty"，所以 **1000 个 draw 每个都要同步一次**。

**⇒ 同步次数 = 变更次数（当变更与 draw 交替时）。**

## 3. 这个同步动作是什么（推测，标注清楚）

**已知（硬）**：
- 它在 GPU 侧执行（CPU 提交只 1.29 µs/对）
- 每次 121 µs ≈ 231k 周期 @1911 MHz
- 与几何、像素、队列深度**全都无关**（报告 75/78 已证）
- **不检查状态是否真的变化**（M6 的 no-op 也收费）
- 只在"dirty 被 draw 消费"时发生

**推测（软）**：最可能是**在每对之后插入一个"等前序完成"的同步点**（fence / semaphore acquire），
把 GPU 流水线**串行化**了 —— 每一对都必须等前一对彻底完成才能开始。

**支持这个推测的理由**：它同时解释了"固定 121 µs"（等的是延迟，不是算力）和"与几何无关"。
**反对/未验的点**：如果真是 fence，GPU 侧应该能看到命令间隙，但**GPU 侧计数器不可用**（报告 98）。

**⇒ 这一层是推测，不作结论用。**

## 4. 静态排除的线索（本轮实际做过的，全部失败）

| 线索 | 做法 | 结果 |
|---|---|---|
| 内核等待原语 | 对比 `os_delay`/`os_wait_*`/`os_schedule` 等外部符号 | **两版完全一致** |
| 内核自旋 | 统计 `sfence/mfence/lfence`（**270→325**）、`pause` `F3 90`（**41→43**） | 同量级 |
| 内核轮询 | "读 HAL 寄存器指针 + 短回跳" 组合 | **11 → 15**，同量级 |
| 逐函数对齐 | 规范化机器码哈希（清 `.rela.text` 4 字节后取 SHA1） | **20703 vs 23185 个函数，骨架相同仅 1 个** ⇒ 整体重编译，逐函数 diff 不可行 |
| **GPU 抢占** | 搜 `CTXSW`/`PREEMPT` | glcore 里 **0 个**（都在内核），内核里两版都有 |
| **调度信用** | 发现 525 新增 `CTRL_{GET,SET}_HS_CREDITS`、`CTRL_GET_TOTAL_HS_CREDITS`，515 里 **0 个** | **.rela.text 中引用数 = 0** ⇒ 只是字符串池残留，**线索排除** |
| 命令包 opcode | 搜报告 77 的 `0x617b` | 仅 1 处真实 `movl`，不是通用写法 ⇒ 无法用立即数定位 |

**结论：静态在该查的地方都查了，但"那条让 GPU 慢 4000 倍的命令"没有定位到。**

原因是硬的：用户态 glcore 44 MB 无符号、内核 blob 整体重编译、且这条命令是**运行时按 arch 算出来的**（不是固定立即数）。

## 5. 为什么 vGPU 不慢（现在能给出自洽的解释）

有了"dirty→sync"模型之后，vGPU 的差异可以精确表述：

**同样跑这个模型，但 vGPU 上"同步"这一步的代价变了。**

| | 真机 | vGPU |
|---|---|---|
| dirty 标志的设置 | 同样 | 同样 |
| 下一次 draw 消费 dirty | 同样 | 同样 |
| **同步动作发到哪** | **真硅片的 pgraph** | **guest 的 pushbuffer，由宿主转发** |
| **同步的实际代价** | **121 µs（串行化 GPU 流水线）** | 由宿主决定 |

关键在报告 110 A 段那些**源码事实**（那部分一直没被推翻）：

- `remap_pfn_range` 把宿主内存映射进 guest BAR
- `translate_gfn_to_pfn` 让宿主直读 guest command stream
- `eventfd_signal`（KVM irqfd）由宿主决定何时注入完成

**⇒ 宿主看到 guest 的"同步点"命令时，不必真的让物理 GPU 串行化** ——
它可以（a）丢弃这条冗余同步、（b）把它合并到自己的队列、（c）用比硅片更宽松的语义满足它。

**这就是"同一份用户态代码、两种环境、两种帧率"的唯一可能解释。**

（**注意**：宿主具体怎么处理，是 blob，不可读。这一段是**推断**，不是源码事实。）

| 结论 | 强度 | 依据 |

## 8. 一句话

**静态对比做完了，结论是"不在我前两轮找的地方"。**
**`submit_p50` 只有 1.29 µs/对，而 `map_p50` 要 123.65 ms —— CPU 早交完活了，那 122 ms 是 GPU 在跑。**
**触发条件是精确的：状态变更置 dirty，下一个 draw 消费它 → 一次 121 µs 的 GPU 侧同步，然后清 dirty。**
**7 个实验（含"切到同一个 program 也收费"这个反直觉案例）全部吻合，误差 <6%。**
**至于那条让 GPU 慢 4000 倍的具体命令，静态没定位到 —— 内核七条线索全部排除（含 `HS_CREDITS` 零引用），用户态 44 MB 无符号且整版重编译。剩下的路是 Ghidra 扫"dirty 三元组"，或者需要机器做 N122-A/B。**
