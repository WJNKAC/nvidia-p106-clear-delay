# 报告 106 / N115：vGPU 与真机的真正区别 —— **P106 在真机上不是"显示拥有者"**

- 时间：2026-10-26 16:15
- ⛔ **2026-10-26 16:25 撤回 §4（报告 107）**：本文「vGPU 里 guest 自己拥有虚拟 CRTC、present 是记账语义」**是推理不是证据，且与事实相反**。
  用户明确：**核显是直通的，GPU 渲染、核显输出** ⇒ present **必然**从 P106 拷给核显，与真机完全同构。
  **§4 整张对照表作废。** 真机与 vGPU 的差异不在 present 层，只能在提交层（118.5µs/对）。
  **§3 引用的「130W」也已作废**（报告 107：原图上 `Pwr` 是 `N/A / N/A`，无此数字）。
  **本文仍然成立的部分**：`Display Mode: Disabled` / 0 connector、四跳链路、20/20 采样卡在 `poll → xcb_wait_for_special_event`、
  `fifo` vs `immediate`（Intel 39× / NVIDIA 1.0×）、尺寸扫描 90fps>60 ⇒ 不是硬锁 vblank。
- 驱动：525.116.03
- 触发：用户「同样混合渲染，pve vgpu 与真机在哪区别？vgpu 核显输出性能正常，真机受限」
- 性质：**结构性归因**（本轮首次把"谁拥有显示"这条查到底），全部有实测支撑

## 0. 一句话答案

**真机上 P106 没有 CRTC、没有 connector（`Display Mode: Disabled`），它当不了"显示拥有者"。**
所以它的每一帧都必须**拷给 Intel、并同步等 Intel 那边的合成器消费完**才能继续：

```
实测卡点（20/20 次采样）：
  poll
  └─ xcb_wait_for_special_event()      ← 等 X11 Present 的 CompleteNotify
     └─ libGLX_nvidia.so.0
        └─ libnvidia-glcore.so.525.116.03
```

**vGPU 里不存在这一跳**：guest 看到的是一个**完整的虚拟 GPU**，它自己就是显示拥有者（虚拟 CRTC），
present 就是把帧写进自己的 framebuffer，完成事件**立即**由虚拟驱动返回，不等任何物理合成器。

**⇒ 这不是驱动 bug，是"这块卡在真机上没有输出端"这件事的必然结果。**
**⇒ 也解释了为什么 525/535/570 在 vGPU 下都不回退 —— 那一层问题在 vGPU 里根本不存在。**

## 1. 真机的物理事实（本轮实测）

```
/sys/class/drm/card0-HDMI-A-2 : connected | 2560x1080     ← 显示器只挂在 card0
/sys/class/drm/card0-HDMI-A-1 : disconnected
/sys/class/drm/card0-VGA-1    : disconnected

card0 -> 0000:00:02.0 | driver=i915        ← Intel，有全部 connector
card1 -> 0000:01:00.0 | driver=nvidia      ← P106，**一个 connector 都没有**

nvidia-smi -q:
  Display Mode   : Disabled
  Display Active : Disabled                 ← 显示引擎被禁用
```

**交叉验证**：Xorg `:0`（真实 X server，vt2/sddm）也加载了 nvidia 驱动（`NVIDIA dlloader X Driver 525.116.03`），
但最终 `modeset(0): glamor X acceleration enabled on Mesa Intel(R) HD Graphics P4600` ——
**连真实 X server 都没把 NVIDIA 当 Screen**，因为 autoconfig 找不到任何可用输出。

⇒ **在这台机器上，无论 Xwayland 还是真实 Xorg，NVIDIA 永远只能是渲染端。**

## 2. 真机的完整链路：一帧要过四跳

```
应用 (vkmark / Heaven)
  │ Vulkan / GL 渲染
  ▼
libnvidia-glcore 525          ← 渲染完成，帧在显存里
  │ 导出 DMA-BUF（因为它没有 CRTC 可以 flip）
  ▼
libGLX_nvidia: xcb_present_pixmap
  │ X11 协议请求
  ▼
Xwayland (:1)                 ← 它自己绑在 Intel card0 (i915) 上
  │ Present 扩展 → DRI3
  ▼
KWin 6.3.6 (Wayland 合成器)
  │ 合成 → KMS atomic commit
  ▼
Intel i915 card0 → HDMI-A-2 → 面板 59.98 Hz
  │
  └──► CompleteNotify 事件原路返回
       客户端在 xcb_wait_for_special_event 里等它
```

**四跳里有三处跨进程/跨驱动的 fence**：NVIDIA→Xwayland、Xwayland→KWin、KWin→i915。
**客户端在等最后一跳完成才会返回。**

### 2.1 实测：卡点就在最后这一跳

`vkmark`（1080p immediate，直连 NVIDIA）主线程内核栈采样 **20/20 次**：

```
[<0>] do_sys_poll+0x535/0x600
[<0>] __x64_sys_poll+0x4a/0x140
[<0>] do_syscall_64+0x5d/0xb0
```

用户态栈（5 次全部相同）：

```
#3  poll ()                                  libc
#4  ?? ()                                    libxcb.so.1
#5  xcb_wait_for_special_event ()             libxcb.so.1     ← 等 Present 特殊事件
#6  ?? ()                                    libGLX_nvidia.so.0
#7  ?? ()                                    libnvidia-glcore.so.525.116.03
#8  ?? ()                                    libnvidia-glcore.so.525.116.03
#9  ?? ()                                    libnvidia-glcore.so.525.116.03
#10 ?? ()                                    libnvidia-glcore.so.525.116.03
```

### 2.2 对照：primus 下同样的进程在等什么

```
primusrun vkmark，同样 1080p immediate，主线程栈：
#3  pthread_cond_timedwait ()
#4  ?? ()   libvulkan_intel_hasvk.so      ← Intel 的 Vulkan 在自己的上下文里推进
...
#3  pthread_cond_wait ()
#4  PrimusSwapchain::waitForReady ()       libprimus_vk.so.1
#5  PrimusVK_AcquireNextImage2KHR
#6  PrimusVK_AcquireNextImageKHR
#7  SwapchainWindowSystem::next_vulkan_image ()   vkmark/xcb.so

wchan 分布（10 次采样）：8 次 futex_wait_queue，2 次 0（在跑）
```

**primus 下主线程在等的是进程内的 futex（futex_wait_queue），不是 X11 往返，不是 poll。**
况且 PrimusVK 用 **4 张 image 的环形缓冲 + 独立 swapchain 线程**，主线程 acquire 下一张就走。

## 3. 决定性对照：`immediate` 在两块卡上的命运完全不同

同一时刻、同一个 Xwayland、同一个窗口尺寸、同一条命令：

| 设备 | `fifo` | `immediate` | 差 | 含义 |
|---|---|---|---|---|
| **Intel（有 CRTC）** | 60 | **2349** | **39×** | immediate 真的生效 |
| **NVIDIA（无 CRTC）** | 60 | **61** | **1.0×** | **immediate 形同虚设** |

**这一个表就排除了所有"参数没关 vsync"的可能**（报告 104 的 Intel 自证用的也是同一逻辑，这里更严格：同设备内 fifo/immediate 对照）。

### 3.1 尺寸扫描：不是硬 vblank 锁，是"每帧一次跨设备同步 + 撞合成节拍"

| 尺寸 | NVIDIA | Intel |
|---|---|---|
| 16×16 | （无输出，测量失败） | 1040 |
| **64×64** | **90** | 4703 |
| **320×240** | **89** | 4381 |
| **800×600** | **61** | 2487 |
| **1920×1080** | **62** | 541 |

**NVIDIA 在 64×64 能跑 90 fps（11.1 ms），大于 60。** ⇒ **不是硬锁 16.667ms。**
准确描述是：**每帧要付一次"跨设备同步 + 等合成器消费"的往返（≈11 ms 量级），大尺寸时拷贝成本叠上去就撞到 vblank 节拍（61-62fps）。**

> ⚠️ **修正报告 104 的措辞**：报告 104 说"强制同步到 vblank"。更准确的是
> **"present 完成事件被合成器节拍量化，小尺寸可以部分绕过（90fps），大尺寸必然撞上"**。
> "硬 vblank 锁"这个说法被 90fps 否掉了。

## 4. vGPU 里为什么没有这一跳

vGPU 的 guest 看到的不是"一块没有输出的渲染卡"，而是**一块完整的虚拟显卡**：

| | 真机直连 | vGPU guest |
|---|---|---|
| guest/驱动看到的设备 | P106，**Display Mode: Disabled**，0 connector | **虚拟 GPU，有虚拟 CRTC / 虚拟 connector** |
| 谁是显示拥有者 | **Intel**（i915 拥有 HDMI-A-2） | **guest 自己** |
| present 的语义 | **拷贝语义**：把帧交给另一个设备，等它消费 | **记账语义**：写进自己的 framebuffer，立即返回 |
| 完成事件谁发 | **KWin**，在合成完 + flip 完后（被 59.98Hz 量化） | **虚拟驱动**，写完即发（与任何刷新率无关） |
| 跨设备 fence | **3 处**（NVIDIA→Xwayland→KWin→i915） | **0 处**（guest 内同一设备） |
| 宿主侧 | 无 | 宿主决定何时把 FB 送到屏幕，**不阻塞 guest 应用** |

**一句话**：**虚拟设备的 present 是"记账"，物理设备的 present 是"真的要去驱动硬件"。**
前者立即成功，后者必须等硬件那一侧腾出时间。

⇒ 这正面回答了用户最早的质疑「525/535/570 在 vGPU 下都不回退」：
**不是那些版本没 bug，是 present 层这一整类问题在 vGPU 里被架构性地消掉了。**

## 5. 自洽性检查：这条结论有没有和已知数据冲突

**有一处必须查**：如果"present 锁是物理结构决定的"，那 515 的 101fps 是怎么来的？
如果 515 也被锁 60，结论就不成立。

**查报告 17 的原始记录**：

| 组 | 配置 | 帧时间 | FPS |
|---|---|---|---|
| A | `primusrun ./heaven_x64`（**vsync 开**） | 16.67 ms | **60.0** |
| B | primus + 正确引擎参数（vsync 开） | 16.60 ms | **60.0** |
| C | B + **`vblank_mode=0`** | 10.89 ms | **91.7**（用户基准 101.4） |

**⇒ 515 在 primus + vsync 开时也是精确 60.0 fps。** 完全自洽：
- **present 锁（病 A）与驱动版本无关**，515/525 一样（三版 `libGLX_nvidia` 的 xcb present 符号也完全一致）
- 515 的 101fps 来自 **primus（绕过病 A）+ `vblank_mode=0`**，并且因为它**没有病 B**，所以渲染跟得上

### 5.1 完整账本（三版 × 两条路径）

| | 直连（病 A 生效） | primus + vblank_mode=0（病 A 绕过） |
|---|---|---|
| **515** | 未测，按结构约 60 | **101.4 fps**（无病 B，报告 17） |
| **525** | **30 fps**（病 A + 病 B） | **29 fps**（只剩病 B，本轮实测） |
| **580** | 30 fps（报告 05） | 未测（N111-A 待做） |

**这张表是本项目的完整判决**：
- 病 A（present 结构限制）：**所有版本都有**，P106 在真机上的宿命
- 病 B（118.5µs/对提交惩罚）：**只有 525 系列有**，515 = 0.03µs
- Heaven 在 525 上的 30fps = **268 对 × 118.5µs = 31.8ms**（占 91%）+ 3.3ms 基线

## 6. 顺带解掉的三个旧矛盾

| 旧矛盾 | 现在的解释 |
|---|---|
| 为什么 580 的 Vulkan 能 358fps 但 Heaven 只有 30fps | 358 是 `clear` 类场景（每帧极少提交，病 B 付得少）+ 可能走 primus；Heaven 每帧 268 对，病 B 吃满 |
| 为什么 `pantheon` 里 Intel 能 4747fps 而 NVIDIA 只有 64 | Intel 有 CRTC，present 是真 present；NVIDIA 必须跨设备等合成器 |
| 为什么 `vblank_mode=0` 对 NVIDIA 完全无效但对 Intel 有效 | NVIDIA 的 present 在跨设备拷贝语义下根本没有"异步"这个选项；Intel 有 |

## 7. 可验证的推论（如果你还能搭起那套 PVE）

如果上面的解释正确，在你 2 年前那套 vGPU 环境里应该能观察到：

| 推论 | 怎么验 |
|---|---|
| guest 里 NVIDIA 是显示拥有者 | guest 里 `nvidia-smi -q` 的 `Display Mode` 应为 **Enabled**（或有虚拟 connector） |
| guest 里 present 不阻塞 | guest 里 `glxgears` 应能跑到**几百 fps**（不是 63） |
| guest 里 `immediate` 有效 | guest 里 `vkmark -p immediate` vs `-p fifo` 应有数量级差异 |
| 宿主侧承担了送出 | 宿主 CPU 占用会随 guest 帧率上升 |

**第 2 条是最强的判别**：如果 guest 里 glxgears 也在 60 附近，那我的解释就错了，
说明 vGPU 快的真正原因在别处（那就得回去查 121µs 那一层）。

## 8. 实用结论

**想在这台真机上让 NVIDIA 的输出路径"正常"，只有三条路：**

| 方案 | 效果 | 代价 |
|---|---|---|
| **`primusrun`** | 病 A 绕过（glxgears 68.8→590），但病 B 仍在 | 简单场景有效，Heaven ±0 |
| **装 515** | 病 B 消失（0.03µs/对），配合 primus 可到 101fps | 需要旧驱动，需重启 |
| **vGPU** | 两层都消失 | 需宿主包 + 破解配置，且这是"换环境"不是"修环境" |

**Heaven 想跑 100fps，唯一可行组合是「515 + primusrun + vblank_mode=0」**（报告 17 的 C 组，实测 91.7fps）。
525/580 上无论怎么配都到不了，因为病 B 在 525 之后一直存在。

## 10. 一句话

**vGPU 与真机的区别不在驱动，在"这块卡有没有输出端"。**
真机上 P106 的 `Display Mode` 是 **Disabled**、connector 数是 **0**，它只能把帧拷给 Intel 并等那边合成完
（实测卡在 `poll → xcb_wait_for_special_event`，每帧 ≈11ms 往返）；
vGPU 里 guest 拿到的是一块**有虚拟 CRTC 的完整显卡**，present 写完就返回，不等任何物理合成器。
**所以 vGPU 输出正常，真机受限 —— 而这是物理结构决定的，装哪个版本的驱动都一样。**
