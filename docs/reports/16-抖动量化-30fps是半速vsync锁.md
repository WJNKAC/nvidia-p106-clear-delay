## 1. 测量方法（可复用、15 秒、可重复）

```bash
# 在 libGL 上建 uprobe（primus 用自己的 libGL，需单独建）
sudo perf probe -x /usr/lib/x86_64-linux-gnu/libGL.so.1 glXSwapBuffers
sudo perf probe -x /usr/lib/x86_64-linux-gnu/primus/libGL.so.1 pswap=glXSwapBuffers

# 抓 15 秒每次 swap 的时间戳
sudo perf record -o /tmp/x.data -e probe_libGL:pswap -p <pid> -- sleep 15
sudo perf script -i /tmp/x.data | awk '{print $4}' | sed 's/://' > ts.txt
```

判据（本报告新定义）：

| 指标 | 含义 |
|---|---|
| **p95 / 中位** | 帧间隔分布的不均匀度。1.0 = 完全均匀，>1.5 = 肉眼可见抖动 |
| `30–40ms` 档占比 | 掉到"每两帧一次"的比例 |
| 中位间隔 | 反映实际节拍（不是平均值，平均值会被卡顿污染） |

必做：`perf_event_paranoid` 需 ≤1；`perf` 读 data 文件需 root。

## 2. 四条路径的客观结果

显示器：**HDMI-A-2 2560×1080 @ 59.98 Hz** → 一个 vblank = **16.67 ms**。
游戏窗口 1920×1080（窗口模式，由 kwin 合成）。

| 路径 | FPS(均值) | 中位间隔 | p05 | p95 | **p95/中位** | 30–40ms 占比 | 判定 |
|---|---|---|---|---|---|---|---|
| **Intel 核显**（对照，不涉跨卡） | 6.4 | 163.28 ms | 116.0 | 186.9 | **1.14** | — | 慢但**极均匀** |
| **primus**（NVIDIA 渲染 + readback） | 29.7 | **33.40 ms** | 29.2 | 38.8 | **1.16** | 86.3% | 慢但**极均匀** |
| **vendor**（NVIDIA dmabuf 直渲） | 46.3 | 16.97 ms | 3.3 | 61.9 | **3.65** | 26.4% | 快但**明显抖动** |
| **offload**（dmabuf + PRIME 拷贝） | ~60(中位) | 16.16 ms | 2.8 | 39.4 | **2.44** | 19.6% | 快但**抖动** |

### 2.1 这张表说明什么

1. **均匀性只在 NVIDIA dmabuf 路径崩坏**（3.65 / 2.44）。
   Intel（1.14）和 primus（1.16）都极均匀。
   → **抖动不是合成器通病、不是程序本身、不是 CPU 侧 pacing**，而是**跨 GPU 交付路径**的产物。

2. **primus 的 33.40 ms = 2 × 16.67 ms**（误差 0.2%）。
   这不是"等待 30ms 随机结束"，而是**严格的 vblank 量化：每帧占 2 个 vblank**。
   → **30fps 地板的物理含义是"每一帧都错过了一次 vblank 截止"**，
   于是稳定落在 33.3ms 档。

3. **dmabuf 路径的中位是 16.16~16.97 ms（≈1 个 vblank，即 60fps 档）**，
   但 20~26% 的帧掉到 33ms，还有 5% 掉到 60–100ms。
   → 这就是用户看到的"60Hz 不断抽搐"：**大部分帧准时，五分之一迟到一拍**。

## 3. 由此得到的机制假设（替代"等 30ms"）

原命题："等待以自身节奏到期，30.24 ms"。

新命题：**每帧的端到端延迟略大于 16.67 ms，于是每次都被推到下一个 vblank，累计成 33.3 ms。**
差别在于方向：

- 旧命题认为有一个"30ms 的等待主动发生"
- 新命题认为**没有 30ms 这个量**，只有"**刚好超过 16.67ms**"这个量，
  33.3 是 16.67 的整数倍取整结果

这解释了为什么：
- 报告 10 测到 `0xffff→0` 的分布紧到 ±0.3ms（30.01–30.61）：它是**vblank 对齐的结果**，天然紧。
- 报告 12 的"固定 30ms 常数列"找不到对应物：**因为它根本不存在**。
- `(N−1)²×250µs = 30.25ms` 的 numerological 吻合：巧合同源（都接近 2 个 vblank）。

**可证伪点**：换一个刷新率（如把显示切到 50Hz 或 30Hz），若地板随之变为 40ms / 66.7ms，
则"半速 vsync 锁"成立，"30.24ms 常数"被彻底否掉。这是**一次设置变更就能做的判定**。

## 4. 仍未回答：为什么每帧会超过 16.67 ms？

已排除：功耗墙（120W）、温度、频率（P0 满频）、显存（6GiB）、PCIe 带宽饱和
（Gen1 x16 在 32fps 下 primus readback 仅 265MB/s）。

剩余候选，按可测性排序：

| 候选 | 如何测 |
|---|---|
| **primus readback 成本**（1080p×4B=8.3MB + PCIe Gen1 + 上传 Intel） | 在 primus 下测 `glReadPixels` 单独耗时；或降分辨率看是否跨过 16.7ms |
| **kwin 跨 GPU 合成的每帧开销** | Intel 对照组已证明合成本身均匀（1.14），但那时没有 NVIDIA buffer |
| **驱动侧 swap 前后的等待**（报告 10 的 30.24ms 窗口） | 与本报告的帧间隔对齐时间轴，看那 30ms 落在哪 |

**最便宜的一刀**：在 primus 下把分辨率降到 1280×720 / 960×540，看中位间隔是否从 33.3 变成 16.7。
若变 → **readback/拷贝成本是主因**（与算力无关，纯粹像素量）。
若不变 → 与像素量无关，是固定节拍/同步问题。

## 5. 关于"515 没有抖动"

用户观察：515 跑高帧率时不抽搐。这是重要线索，但按本项目 README 铁律
**"临时测试的记忆不作为锚点"**（本案已有三次记忆导致的错锚点），
它必须用同一探针验证：

- 装回 515，跑**同一个 15 秒 uprobe 测量**（不需要点基准、不需要截图）
- 判据：`p95/中位` 与 `中位间隔`
  - 515 中位 ≈16.7、p95/中位 <1.5 → **515 能按时提交，525 不能** → 真实的呈现路径回归
  - 515 中位 ≈33.3、p95/中位 <1.5 → 515 同样是半速锁，抖动差异来自别处（如 dmabuf vs primus）

这条测量比 E4 的基准对比**更便宜也更有判别力**：15 秒、无交互、不依赖相机路径。

## 7. 方法论增量

**判断"卡不卡"必须用帧间隔分布，不能用平均帧率，也不能用肉眼。**

- 平均帧率相同（60 vs 60）可以是"完全均匀"或"五分之一迟到一拍"，观感天差地别。
- `p95/中位` 是一个便宜且稳定的抖动指标；本机实测能区分 1.14 / 1.16（均匀）
  与 2.44 / 3.65（抖动），区分度足够。
- **中位间隔揭示节拍本质**：33.40 vs 2×16.67 的 0.2% 吻合，
  直接把"等待 30ms"改写成"错过 vblank 截止"。**平均值做不到这件事。**
