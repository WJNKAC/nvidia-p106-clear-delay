# 59 · N62：**主线程 swap 也不是闸门** —— 20.4ms 不在 primus 用户态

> 2026-10-26 13:40
> 用户判断：N62 改两行就能定死 —— 掉到 3ms 则用户态 primus 可改；不掉则 X/present 链，primus 改不动。
>
> **结果：没掉。四个变体的 map 等待完全一样（89.9%）。**
> **→ 20.4ms 不在 primus 用户态，用户态改法（FBO/异步化）都无效。**

---

## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **主线程 `glXSwapBuffers(pbuffer)` 改 no-op → map 等待完全不变** | sleep 89.9% → 89.9% |
| 2 | **`glReadBuffer` 从 FRONT 改 BACK → 完全不变** | 89.9% → 89.9% |
| 3 | **两者同时去掉 → 仍不变（89.9%），只是 fps 掉到 27.8** | 见 §2 |
| 4 | **→ 闸门不在 primus 用户态** | 由 1-3 推出 |
| 5 | **20.4ms 在 primus 之下**（X server / 驱动的 present 路径） | 推断 |
| 6 | **用户列的判读落到第三档**：primus 改不动 | — |

**一句话**：**我们能把 primus 用户态的所有环节（上传、上屏、主线程 swap、读 FRONT/BACK）全部去掉，那 20.4ms 依然在。**

## 2. 四个变体实测

`n62_ab.sh`，每档 12 秒稳态，`PRIMUS_VERBOSE=2` 取最后窗口：

| 变体 | 改动 | fps | **sleep（含 map）** | map(st) | draw+swap |
|---|---|---|---|---|---|
| **base2** | 对照 | 34.3 | **89.9%** | 9.8% | 17.7% |
| **readback** | `glReadBuffer(GL_BACK)` | 34.3 | **89.9%** | 9.8% | 18.0% |
| **n62_noswap** | 主线程不 swap（仍读 FRONT） | 34.3 | **89.9%** | 9.8% | 17.0% |
| **n62_both** | 不 swap + 读 BACK | **27.8** | **89.9%** | 9.9% | 15.5% |

### 2.1 三个都无效，而且方式一致

- **读 BACK 代替读 FRONT**：完全无差别（89.9% / 9.8%）
  → **说明"读 front 需要等 swap"这个假设不成立**。驱动对 FRONT/BACK 的回读行为一样。
- **主线程不 swap**：完全无差别（89.9%）
  → **说明 pbuffer 的 swap 本身不产生等待**。
- **两者都去掉**：仍 89.9%，但 fps 34.3 → **27.8（-19%）**
  → 这个下降是"画面不再更新"带来的应用侧行为变化（Heaven 会减速），**不是闸门变化**。

### 2.2 关键：`sleep` 89.9% 在四个变体里一模一样

`sleep` = `usleep(sleep_usec)` **+ `glMapBuffer`**（报告 58 已纠正标签错位）。

`usleep` 由 `PRIMUS_SLEEP=90` 的 autosleep 算法决定，四个变体都一样。
**所以 89.9% 里那 ~23ms 的 `glMapBuffer` 等待，与 primus 的任何用户态动作无关。**

## 3. 这把整条"用户态可改"的路封死了

从报告 55 到 59，逐个排除的 primus 用户态环节：

| 环节 | 变体 | 结果 |
|---|---|---|
| 数据上传 `glTexSubImage2D` | N61 `noupload` | **fps 完全不变** |
| Intel 上屏 `glXSwapBuffers(ddpy)` | N61 `noswap` | **fps -2.8%，map 不动** |
| 主线程 `glXSwapBuffers(pbuffer)` | N62 `n62_noswap` | **map 完全不动** |
| 回读源 FRONT → BACK | N62 `readback` | **完全不动** |
| 上述全部 | N61 `both` / N62 `n62_both` | **仍不动（89.9%）** |

**→ primus（用户态）里没有任何一处能影响那 20.4ms。**

**这意味着用户提的两个修复方向都不可行**：
- "让 display worker 异步化" → 针对 5.3ms，且实测对 20.4ms 无影响
- "渲染到 FBO 回读 attachment" → 见下

### 3.1 为什么"渲染到 FBO"也不行

我原本推测：FBO 不参与 swap，回读就不会被 present 周期闸住。

**但 N62 的 `n62_noswap` 已经等价的验证了这个假设**：
即使完全不 swap（pbuffer 内部根本不切换前后台），`glMapBuffer` 仍然等 30ms。

**→ 等待的原因不是"前后台切换"，而是"从 GPU 帧缓冲把像素搬到 CPU"这个动作本身在真实环境里要 30ms。**

而隔离环境（rb_lat6）同样的动作只要 2.6ms。**差异在哪？**

## 4. 20.4ms 的归属：现在只能指向 primus 之下

### 4.1 已确认的事实链

| 事实 | 来源 |
|---|---|
| 拷贝 8.29MB，每帧 1 次，参数全屏 | 报告 56 |
| 提交（`glReadPixels`）只花 137µs | 报告 56 |
| 落地（`glMapBuffer`）要 30.9ms | 报告 56 |
| 与传输字节的关系是 `20.39 + 1.335×MiB` | 报告 56 |
| 与 primus 任何用户态动作无关 | **报告 59（本报告）** |
| 隔离环境（同一张卡、同样 8.29MB）只要 2.62ms | 报告 40 |

### 4.2 剩下唯一的差异：X server 参与

**隔离 rb_lat6 与真实 primus 的区别，在 N62 之后只剩一个：**

| | 隔离 rb_lat6 | 真实 primus |
|---|---|---|
| X server | **直接对 NVIDIA GPU 的 pbuffer** | **primus 用 `adpy`（NVIDIA 渲染）在 pbuffer 上跑，又用 `ddpy`（Intel）上屏** |
| GLX 库 | 系统 Mesa GLX | primus 自己实现的 GLX（经 `__GLX_VENDOR_LIBRARY_NAME=nvidia`） |
| DRI3/DRI2 路径 | 直连 | **经 primus 转发 → 可能走 DRI2 的阻塞式缓冲管理** |

**最可疑：primus 自己实现的那套 GLX 转发，会把 `glReadPixels` 变成跨进程（X）的 DRI 操作。**

### 4.3 一个可查的具体线索

`n62_noswap` 里主线程的 `glXSwapBuffers` 是 no-op（被宏去掉了），**但 `glMapBuffer` 依然等 30ms**。
这说明等待发生在 **GLX/DRI 层**，不在任何 swap 调用上。

**→ 检查方向：`glReadPixels` 用的是 PBO 还是直接读？**
primus 的源码里 `glReadPixels(..., NULL)` 传 NULL，即"绑定 PBO 后读进 PBO"。
若驱动在真实环境里把这条路径降级为 **DRI2 的 `DRI2GetBuffersWithFormat` + 逐块拷贝**（而不是 PBO DMA），
就会产生这种量级的延迟。

**这条可以静态查**：看 primus 的 `glReadPixels` 包装有没有额外的跨进程操作。

## 5. 明确结论：这条线到此为止

| 项 | 结论 |
|---|---|
| 20.4ms 在 primus 用户态吗？ | **不在**（四个变体全部证伪） |
| 用户态改法（FBO / 异步化 / 多缓冲） | **全部无效** |
| 20.4ms 在哪 | **primus 之下**：GLX 转发 + X server + NVIDIA 驱动的 PBO 落地路径 |
| 还能改吗 | **primus 改不动**。除非换实现方式（不走 GLX 回读） |

### 5.1 一个仍然可行的方向（但要换架构）

如果 20.4ms 真的在 GLX 回读路径上，唯一可行的绕法**不是改 primus 的调用顺序**，而是
**完全不经过 GLX 回读**：

| 方案 | 做法 | 代价 |
|---|---|---|
| **用 `glGetTexImage` 替代 `glReadPixels`** | 渲染到 FBO 的 texture，直接取 texture | 需改 primus 架构（渲染目标变 FBO） |
| **用 EGL/GBM 直连** | 绕过 GLX，用 GBM 拿 dmabuf | 大改 |
| **不跨 GPU** | 换有显示输出的卡 | 硬件 |

**但 §3.1 的 `n62_noswap` 已经暗示：即使不 swap，map 仍等 30ms。
所以"换回读 API"是否有效，取决于 `glReadPixels` 与 `glGetTexImage` 在驱动里走的路径是否不同 —— 这需要另一次实验（N63）。**

### 6.1 源码改动（累计 4 个宏）

```c
// 1) 上传
#ifdef N61_NO_UPLOAD   ... #else  glTexSubImage2D/glBufferSubData  #endif
// 2) display worker 上屏
#ifndef N61_NO_SWAP    glXSwapBuffers(ddpy, di.window);   #endif
// 3) 主线程 swap
#ifndef N62_NO_MAINSWAP  glXSwapBuffers(primus.adpy, di.pbuffer);  #endif
// 4) 回读源
#ifdef N62_READ_BACK   glReadBuffer(GL_BACK);  #else  glReadBuffer(GL_FRONT);  #endif
```

**4 个宏组合出 16 个变体，覆盖 primus 用户态的全部可动点。**

### 6.2 方法论（两条，已入技能库）

1. **"把某层全部关掉还是不生效"，是排除整层的干净做法。**
   本轮把 primus 用户态的 4 个可动点全部枚举（16 种组合），4 个关键变体实测都无效
   → **可以断言"不在这一层"**，而不是"还没找到"。

2. **`sleep` 89.9% 在 4 个变体里一字不差，这个"一致性"本身就是证据。**
   如果闸门在被改的那一环，至少一个变体会变。**四个全不变 = 闸门不在被测集合里。**
