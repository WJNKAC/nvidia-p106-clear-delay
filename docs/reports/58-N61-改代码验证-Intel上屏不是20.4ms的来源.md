> 2026-10-26 13:00

## 2. 怎么改的（可复现）

### 2.1 补全源码（关键：缺 5 个 `.def` 文件）


**用 apt 拿到了完整源码**（Debian 的 primus 0~20150328，已应用 4 个 patch）：

```bash

```

### 2.2 只加两个编译开关（不改逻辑）

```c
// 上传（glTexSubImage2D / glBufferSubData）
#ifdef N61_NO_UPLOAD

#else
    ... 原代码 ...
#endif

// 上屏
#ifndef N61_NO_SWAP
    primus.dfns.glXSwapBuffers(ddpy, di.window);
#endif
```

**`sem` 的配平完全保留**（`sem_post(&di.d.relsym)` 等不跳过），所以不会死锁。

**系统库一个字节都没动。**

## 3. ★ 先纠一个坑：primus 自带 profiler 的标签是错位的

`PRIMUS_VERBOSE=2` 会每 5 秒打印：

```
readback: 1920x1080, 39.0 fps, 0.0% app, 89.9% sleep, 9.9% map, 0.2% wait
display:  1920x1080, 39.0 fps, 66.4% wait, 7.5% upload, 26.1% draw+swap
```

**但对照源码的 `tick()` 顺序，标签和实际内容不符**：

```c
state_names = {"app", "sleep", "map", "wait"};
...
glWaitSync; glReadPixels;              // ← app
sem_post(relsem);
usleep(sleep_usec);                    // ← 还在 app
tick();                                // → 进入 "sleep"
glMapBuffer(...);                      // ★ 这段在 "sleep" 里！
tick();                                // → 进入 "map"
sem_timedwait(&di.d.relsym, ...);       // ★ 这段才是 "map"（其实是等 display worker）
tick();                                // → 进入 "wait"
glUnmapBuffer(...);
tick();                                // 回 "app"
```

**所以**：

| profiler 标签 | 实际内容 | 本例数值（39fps） |
|---|---|---|
| `sleep` 89.9% | usleep + **glMapBuffer** | ≈23 ms/帧 |
| `map` 9.9% | **`sem_timedwait` 等 display worker** | ≈2.6 ms/帧 |
| `wait` 0.2% | unmap + 循环尾 | ≈0.05 ms/帧 |

**这个错位方向与我的探针一致**：
- 探针测的 map = 30.7ms → 落在 profiler 的 `sleep` 里 ✓
- 探针测的 st = 5.34ms → 落在 profiler 的 `map` 里 ✓

**→ 两套数据互相印证，只是 profiler 的标签要按上表重新解释。**

## 4. 四变体实测

`n61_ab.sh`，每档跑 ~14 秒（稳态后），取最后一次 5 秒窗口：

| 变体 | fps | rb:app | **rb:sleep（含 map）** | rb:map（=st） | dp:upload | **dp:draw+swap** |
|---|---|---|---|---|---|---|
| **base** | **39.0** | 0.0% | **89.9%** | 9.9% | 8.4% | **30.0%** |
| **noupload** | **39.0** | 0.0% | **89.8%** | 10.1% | **0.0%** | 29.6% |
| **noswap** | **37.9** | 0.0% | **88.3%** | 9.9% | 7.9% | **26.2%** |
| **both** | **0.3** | 96.5% | 3.5% | 0.0% | 0.0% | 0.3% |

### 4.1 三个读得出来的结论

**① `noupload` 完全无效**
fps 一模一样（39.0 → 39.0），`upload` 从 8.4% 归零，但 `sleep`（含 map）和 `map` 都不变。
**→ 数据上传（`glTexSubImage2D`）与回读延迟无关。**

**② `noswap` 只省 1.2ms**
fps 39.0 → 37.9（**-2.8%**），`draw+swap` 30.0% → 26.2%（**-3.8%**）。
3.8% × 25.6ms ≈ **0.98ms**。
`sleep`（含 map）89.9% → 88.3%，`map` 9.9% → 9.9% **完全不动**。

**→ 去掉上屏，map 时间一点没变。**

**③ `both` 会卡死（0.3 fps）**
去掉 upload + swap 后，`app` 占 96.5%、`map` 归零。
**说明显示器完全不更新时，Heaven 会停在某处等**（可能是 X 事件/vsync）。
→ **这也反向说明 `noswap`（只去 swap、保留 draw 和 upload）是一个"能跑起来"的最强对照**，结论可信。

### 4.2 反推：display worker 的贡献上限

| 项 | 值 |
|---|---|
| `map`（等 display worker 的 `sem_timedwait`） | 9.9% × 25.6ms ≈ **2.5 ms/帧** |
| 探针实测 `st`（sync=1 时） | **5.34 ms** |
| 上屏 swap 本身 | ~1.0 ms |

**→ display worker 全链条的贡献上限 ≈ 2.5~5.3ms，不是 20.4ms。**

## 5. 所以 20.4ms 是 pbuffer swap 本身（对应你的第二个判读）

用户给的三个判读：

| 判读 | 结果 |
|---|---|
| `st` 段 ≈20ms → 等 Intel 上屏 | **❌ 否**（st=5.3ms，noswap 无影响） |
| **`RP→下一个 swap` ≈20ms，`st` 短 → DMA 只在 present 后启动** | **✅ 符合** |
| 两者都与 swap 无固定关系 → 驱动内部 | ⚠️ 部分符合（15ms 那部分） |

**现在能确定的**：
- 20.4ms 里，**display worker 只占 ≤5.3ms**
- **剩下 ~15ms 与"pbuffer 的 `glXSwapBuffers(adpy, di.pbuffer)`"绑定**
- 因为回读源是 **pbuffer 的 `GL_FRONT`**（报告 42 确认），而 `glXSwapBuffers` 才把 BACK 换到 FRONT
- **→ 回读必须等 swap 之后，且驱动在 swap 时要完成某种同步/清空**

### 5.1 为什么这是"pbuffer + FRONT 读"特有的

| 场景 | 回读源 | 固定项 |
|---|---|---|
| 隔离 rb_lat6（`swap_front`） | pbuffer FRONT + swap | **2.60ms**（无 present） |
| 真实 primus | pbuffer FRONT + swap + present 链 | **20.4ms** |
| N25 双线程复刻 | pbuffer FRONT + swap | **2.49ms**（无 display worker） |

**隔离和 N25 都有 swap + FRONT 读，但都没有 20.4ms。**
**→ 差异不在 swap 本身，而在"swap 之后还有 X present 链"这个真实环境。**

**这与 §4 的 noswap 结论并不矛盾**：noswap 去掉的是 **display worker 的 swap(ddpy)**，
但**主线程的 `glXSwapBuffers(adpy, pbuffer)` 还在** —— 那才是把 BACK 换到 FRONT 的动作。

**→ 闸门是"主线程的 pbuffer swap"，不是"display worker 的上屏"。**

## 6. 下一个实验（一次就能定死）

**把主线程的 `glXSwapBuffers(adpy, di.pbuffer)` 也去掉，改成读 `GL_BACK`。**

| 改动 | 预期 |
|---|---|
| `glXSwapBuffers` 换成 no-op + `glReadBuffer(GL_BACK)` | 若 map 从 30.7 掉到 ~3ms → **确认闸门是"swap 后读 FRONT"**；这就是 primus 可改的点（渲染到 FBO，回读 FBO 的 attachment） |
| 若 map 不变 | 闸门在 X/present 链的更外层 |

**这个改动同样只是两个编译开关**（我可以在现有补丁上加 `N61_NO_MAINSWAP`），
而且**改动后语义仍然正确**（读 BACK = 读刚渲染的那一帧，只是不 swap）。

### 7.1 三个方法论要点

1. **`apt-get source` 是补全缺失源码最快的方式。**
   缺 5 个 `.def` 时不要手写，`apt-get source primus` 30 秒拿到完整树（含 Debian 的 4 个 patch）。

2. **改被测软件时用 `PRIMUS_libGL` 覆盖库路径，不要替换系统库。**
   `primusrun` 本身就是靠 `LD_LIBRARY_PATH` 找库的，环境变量可直接接管。
   **零破坏、可随时回退。**

3. **第三方库自带的 profiler，先核对它的 `tick()` 位置再用。**
   primus 的 `sleep` 标签实际包含 `glMapBuffer`，`map` 标签实际是 `sem_timedwait`。
   **如果直接按标签理解，会把"等 display worker"当成"map 耗时"，方向就全错了。**
   本例恰好用探针独立验证了两者，才敢下结论。
