# 82 · N91：0x8704 是大块上传不是每对标记；MMIO 一次 977ns；满载复现是假象

日期：2026-10-26 13:20
方法：静态（字节定位/语义判定）+ 515 上动态（MMIO 校准、满载对照、驱动开关扫描），**不换驱动**
前序：报告 80（用户态等价）、81（121µs = 12.6× 完整 GPU 往返）

---

## 0. 四条结论

1. **更正报告 81 的一个误判**：`0x8704` 不是「每对一次的同步标记」，而是**大块数据上传**——
   它所在函数有长度门 `(len−0x1000) ≤ 0x7ff000`（**4KB ~ 8MB**），流程是 `malloc(len)` → `memcpy` → 写 `[0x8704][ptr]` 记录 → 提交器。
   对 `ctx+0x8e0880` 的**全部 7 处访问都在同一个函数内**（`0x123a4e0–0x123a730`），没有任何回读/等待点 ⇒ **它不是信号量**。
   ⇒ **命令字这条线作废**，不再追。
2. **PCIe MMIO 读的实测成本 = 977.5 ns/次**（BAR1，2000 次串行读；链路确认 **Gen1 2.5GT/s ×16**）。
   ⇒ **121µs ≈ 124 次 MMIO 读**。这是"主机侧轮询往返"假说的量级依据（此前只是估算）。
3. **满载复现是假象（重要负面结果）**：515 上另起一个进程把 GPU 打到 100%（64W），M3 的 map 从 2.54ms 跳到 108ms——
   但**对照实验否掉了"每对成本"**：

| 515 + 竞争负载 | map_p50 |
|---|---|
| M1（**0 对**，1000 draw） | **109.376 ms** |
| M1（100 对） | 109.352 ms |
| M1（1000 对） | 109.327 ms |
| M3（0 对） | 109.366 ms |
| M3（1000 对） | 107.969 ms |

   **与配对数完全无关、恒 ~109ms** ⇒ 那是"回读等竞争进程的一整帧"，不是每对成本。**不能当作 121µs 的复现。**
4. **驱动开关扫描**：`__GL_FLUSH_CONTROL=1..4` 让 map 变 0.000ms，但 **`chk=0`（读回数据无效）** ⇒ 坏模式，排除；
   `__GL_THREADED_OPTIMIZATIONS=1`（2.554ms）、`__GL_SINGLE_THREADED=1`（2.539ms）均无变化。
   ⇒ **515 上没有可切到"525 行为"的开关。**

## 3. 需要 525 的三个测量（换驱动前静态已做完，现在只剩这一步）

| 优先级 | 测量 | 判据 | 耗时 |
|---|---|---|---|
| **1** | n83a `-M 1` vs `-M 3` 下，**glcore 的 `wait_ms`（`0x146d280`）与 notify（`0x146c680`）每帧次数**（uprobe 挂 libc 侧可用的 `sem_*`/`futex`，glcore 内部靠 `perf probe` 不可用 ⇒ 改用 **`/proc/pid/mem` 读驱动自记时 `ctx+0x8e0d10[]`**，报告 36 的方法） | M3 若 ≈1000/帧 ⇒ 每对一次等待被证实 | 10 分钟 |
| 2 | **M1 vs M3 的 push buffer 内容 diff**（先定位映射，再 `/proc/pid/mem` 抓块） | 直接看到 525 每对多写什么 | 20 分钟 |
| 3 | M3 下 **ioctl 计数**（LD_PRELOAD，工具已备） | 若 ~0 额外 ⇒ 确认批处理，等待在 GPU 侧 | 5 分钟 |

三项都在同一次 525 会话里做完，**换驱动 → 重启 → 采集 → 换回**约 30 分钟，需要用户在場。
