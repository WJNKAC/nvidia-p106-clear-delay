# 09 · 渲染期真相：futex 分账、dlsym 盲区、以及"两边都在空转"

> 2026-10-24 深夜 ~ 10-25 凌晨
> 设备：P106-100 / 580.126.18 / PRIME offload / Xwayland
> 本轮起点：回答"到底谁在 futex-wait，主线程等 worker 还是双向乒乓"
> 结论先说：**问题问对了，但答案不在线程之间——渲染期 worker 全在睡，主线程在自旋等 GPU 的 fence；
> 而 GPU 同时以 92% SM 占用、6% 显存带宽、47 W 在空转。两边都没有在算，时间花在一次 CPU↔GPU 的握手上。**

---

## 1. 先认一次事故：此前所有"稳态"数字都可能落在加载期

这一轮开头我做了三件事，其中两件是错的，必须先讲清楚，否则后面的表格不可信。

### 1.1 遗留进程污染

开工时发现**上一轮（`-k` 那次）的 `strace` 和 `heaven_x64` 根本没死**，已经跑了 582 秒；
更早那次 `fwst` 的 `heaven_x64` 跑了 840 秒。三个实例在抢同一张 GPU。
在这期间取到的 `nvidia-smi` 读数（利用率、功耗、频率）全部作废。

清理后基线恢复正常：`0%, 6.31 W, 139 MHz, 8 MiB`。

### 1.2 采样窗口落在加载期

一直沿用"`sleep 16~22` 后开始采样"的老习惯。本轮第一次截图核验：

```
t=20s 的窗口截图 → 黑底 + "LOADING" + 一行进度点
```

也就是说，**此前 `-k` 与 `-T` 两轮 30 秒 trace 里 t=15~30 s 那段"8 线程 56% 阻塞"，
是加载期的 shader/material 编译，不是渲染期。**

干净环境下重新测定：**画面在 t≈15.1 s 从 LOADING 切到场景**
（判定方法：窗口截图 resize 50% 后的 PNG 体积，加载屏 6.8 KB，进场景后 607 KB）。

### 1.3 这也解释了此前一个对不上的数

上一轮 `-k` 只抓到 4602 次 `FUTEX_WAIT`/30 s，而更早的 `strace -c` 报 1212 次/秒。
两者相差 8 倍——不是口径问题，是**两次采样落在不同阶段**。

> **教训（已写入 §7）**：任何"每帧"数字必须先证明采样落在渲染期；判定手段就用窗口截图体积，
> 或者直接读 Heaven 右上角自带的 `FPS:`。

## 2. futex 分账：谁在等、等多久、和谁配对

采集方式改为 `strace -f -ff -k -tt -e trace=futex`（每线程一个文件）。
**`-ff` 是关键**：上一版用 `grep -A 10` 抓，会把"进入等待时打印的栈"和"被唤醒时打印的栈"
混到别的线程的记录上，导致 3157 条 WAIT 记录没有栈。

### 2.1 所有 condvar 等待都汇入同一个函数

按 `pid × glcore 调用链` 聚合（`0xf...` 是该函数在 `.eh_frame` 里的起始地址）：

| 次数 | 线程 | glcore 调用链 | 性质 |
|---|---|---|---|
| 2004 | 28846 | `a102f0 ← 814b30+0x792 ← a10510` | worker 等活 |
| 1040 | 28824 | `a102f0 ← a1ae90 ← a10840 ← 810500 ← 816210`（`pthread_once`） | 主线程初始化 |
| 1005 | 28842 | `a102f0 ← a10410` | 1000 次踢-等循环 |
| 87 | 28824 | `a102f0 ← 7fef30` | — |
| 120 | 28846 | `a04980 ← a05ab0 ← …`（`pthread_mutex_lock`） | 普通互斥，非条件变量 |

**`0xa102f0` 是所有条件等待的唯一出口。** 它的反汇编（§3.2）显示这是一个
`CondVar::waitFor(int ms)` 包装。

### 2.2 超时是 60 ms / 100 ms，不是 250 µs

从 `deadline - 调用时刻` 的分布直方图：

```
n=3864  中位 59.2 ms
  10-70ms : 1998 (51.7%)     ← 60 ms 档
   >70ms  : 1847 (47.8%)     ← 100 ms 档
  1-3ms   :   16 ( 0.4%)
```

两个档位在代码里能对上：

- `0xa10454: mov $0x3c,%esi` → `waitFor(60)`
- `0x8152b6: mov $0x64,%esi` → `waitFor(100)`

> **"250 µs pacer"要拆成两半，不能整句作废：**
> - 作为**条件变量的超时/睡眠间隔**，它不存在——condvar 超时是 60/100 ms，事件驱动，
>   被唤醒的间隔中位 5.8~7.1 ms，与 250 µs 无关。
> - 但 250 这个常数确实存在，在**另一条路径**上：
>   `0xb0fec0: imul $0xfa,0x22e0c(%rbx),%eax; sub $0xfa` → `ctx+0x6e48 = now_ms + 250*(N-1)`，
>   N = 待完成对象数。`ctx+0x6e41` 计数 >3 次后放弃，转 `0xb0ff30` 强制 kick。
>   它是**自旋循环里的"该强制踢一脚了"的截止时刻**，不是 sleep，也不直接决定帧时间。

### 2.3 地址级配对：谁唤醒谁

同一进程内，把 WAIT 地址与 WAKE 地址做交集（glibc 条件变量的 `wseq` / `g1` 相邻 4 字节，会成对出现）：

| 唤醒者 → 等待者 | 次数 |
|---|---|
| **28824（主）→ 28846（worker）** | **1769** |
| 28842 → 28824 | 1040 |
| 28824 → 28842 | 997 |
| 28846 → 28846（自唤醒） | 498 |
| 28846 → 28824 | 114 |

对应地在地址上：28846 在 `0x7f6d14000e00/…e04` 上等了 887+880=1767 次，
而 28824 正好向这两个地址发了 1769 次唤醒。**这是一条真实的、命中率近 100% 的 1:1 交接。**

但另一面：

```
WAKE 结果：命中 2834 次，空转（=0，无人可唤）5922 次  → 68% 是空转
```

典型例子：28846 对 `0x7148630` 发了 1794 次唤醒，而该地址上只等到 254 次。
**"设标志 + 广播，不管有没有人在睡"** 是这套同步的常态写法。

### 2.4 一条 1000 次的踢-等循环

`0xa10410` 的完整逻辑（反汇编还原）：

```c
for (i = 0; i < 1000; i++) {          // mov $0x3e8,%ebx
    lock(o->mtx);                     // o+0x30
    o->flag = 1;                      // o+0x58
    pthread_cond_broadcast(o);        // *0x2368570
    unlock(o->mtx);
    waitFor(o->peer, 60);             // mov $0x3c,%esi; call 0xa102f0
}
```

线程 28842 在 16.13→22.08 s 之间产生 **1005 次**等待、中位间隔 5.78 ms，
正好是 1000 次迭代 × 5.78 ms ≈ **5.8 秒**。
即：**启动阶段有 5.8 秒耗在这个"踢一下、等 60 ms、再踢"的循环里**，
而它每次都在 5.78 ms 就被唤醒——说明对面有回应，但回应不是它要的那个条件。

## 3. 静态侧的重大更正：`pthread_cond_*` 是通过 dlsym 调用的

### 3.1 此前结论有误

上一轮我据 `readelf --dyn-syms` 里查不到 `pthread_cond_wait/timedwait`，
判定"condvar 假说已死"。**这个判定是错的。**

运行时栈是铁证：

```
futex(0x6c92090, FUTEX_WAIT_BITSET_PRIVATE|FUTEX_CLOCK_REALTIME, 0, {...}, ...) = 0
 > libc.so.6()                                         [0x9a72e]
 > libc.so.6(pthread_cond_timedwait+0x14d)             [0x9205d]
 > libnvidia-glcore.so.580.126.18()                    [0xa103ac]
 > ...                                                 [0xa1af2b]
```

`0xa103ac` 正是 `0xa102f0+0xbc`，即 `waitFor` 里 `call *0x2368538(%rip)` 的返回地址。

### 3.2 为什么符号表里查不到

四条证据拼起来：

1. `readelf --dyn-syms | grep pthread_cond` → **0 条**（只有 mutex/nanosleep/usleep）
2. 但 `strings` 里 **有**：`pthread_cond_timedwait`、`pthread_cond_wait`、`pthread_cond_broadcast`、`pthread_cond_init`、`pthread_cond_destroy`
3. 二进制**导入了** `dlopen` / `dlsym` / `dlvsym`
4. GOT 槽 `0x2368538 / 0x2368568 / 0x23685b0 / 0x23685c0` **没有任何重定位项**

→ 四个槽是**运行时代码写入**的，即启动时 `dlsym("pthread_cond_timedwait")` 之类填进去，
之后全部经 `call *slot(%rip)` 间接调用。

**这直接判了"PLT xref 法"的死刑**：这个方法在 515/525/580 上都会返回 0 命中，
不是因为驱动没用条件变量，而是因为它**根本不走 PLT**。
上一轮"阻塞侧跨版本从未比对过"的批评成立，而按原方案去比对也永远比不出来。

### 3.3 `waitFor` 的语义（0xa102f0）

```c
int waitFor(CondVar *c, int ms) {          // esi = ms
    lock(c->mtx);                          // c+0x30, *0x23685c0
    if (c->flag) { c->flag = 0; unlock; return 1; }   // c+0x58
    for (;;) {
        if (ms < 0) { cond_wait(c, &c->mtx); }        // *0x2368568
        else {
            struct timeval tv; gettimeofday(&tv, 0);
            ts.tv_sec  = tv.tv_sec  + ms/1000;        // imul $0x10624dd3, sar $0x26
            ts.tv_nsec = tv.tv_usec*1000 + ms%1000*1e6; // imul $0xf4240
            if (ts.tv_nsec > 999999999) { ts.tv_sec++; ts.tv_nsec -= 1e9; }
            if (cond_timedwait(c, &c->mtx, &ts)) { unlock; return 0; }  // *0x2368538
        }
        if (c->flag) { c->flag = 0; unlock; return 1; }
    }
}
```

注意它用的是 **`gettimeofday`（CLOCK_REALTIME）**，
而 strace 抓到的正是 `FUTEX_WAIT_BITSET_PRIVATE|FUTEX_CLOCK_REALTIME`。
静态与运行时在这里互证，可以确认这条链没有读错。

## 4. 渲染期到底是什么样：没有 worker 乒乓

用**完全不 ptrace** 的方式采样：每 50 ms 读 `/proc/<pid>/task/*/stat` 与 `wchan`。
窗口取画面进入场景之后 10 秒。

### 4.1 线程状态

| tid | CPU | R | S | wchan |
|---|---|---|---|---|
| 30525（主） | ~100% | **99%** | 0% | — |
| 其余 18 个 | ~0% | 0~4% | **96~100%** | `futex_wait_queue` / `hrtimer_nanosleep` |

**18 个线程全部在睡，主线程 99% 处于 R。** 渲染期没有任何 worker 交接。
"worker 自己也在等、是延迟瓶颈"——这个判断在加载期成立，在渲染期不成立。

### 4.2 主线程在自旋什么

> **⚠️ 本节已于 2026-10-25 01:05 被报告 10 §2 推翻**
> `0xae5d44` **不是热点**：gdb 断点等了 90 秒从未命中，场景期 perf 在该处也没有采样。
> 真正的热循环是 `0xb10140 ↔ 0xb102a8`，自旋者是**发起 `glXSwapBuffers` 的 GL 线程**（99.3% CPU），
> 不是主线程（15.2%）。下面的反汇编内容本身没错，但它描述的是**被调用一次**的路径，不是循环。
> 保留原文仅为记录推理过程，结论以报告 10 为准。

`0xae5c80` 是一个**用户态 fence 轮询**（无系统调用）：

```
ae5d28: call 0x1058900          ; kick / 推进提交
ae5d33: call *0x1900(%rbx)      ; get_seq()  ← 虚表槽
ae5d3c: call 0xae5c30           ; 检查完成
ae5d44: cmp  %r14,%rbp
ae5d47: js   ae5d28             ; while (current < target-1) 继续转
```

`0xae5c30` 又是两个"门位"的看守：

```
testb $0x1, global 0x235dec0    ; ← 用户此前点名的 bit0
jne   return 0
testb $0x2, 0x565(%rdi)         ; ← 用户此前点名的 ctx+0x565 bit1
jne   0xb0fd70
```

`0xb0fd70` 做两件事：
1. 扫 `ctx+0x1418` 上的待完成数组，找 `word[obj+0x5e] == 0xffff` 的项；
2. 若 `global 0x235fba0 & 7 == 0` 且若干标志成立，则 `call *0x290(vtable)`（= `clock_gettime`），
   把 `now_ms` 与 `ctx+0x6e48` 里的**毫秒级 deadline** 比较，超时才走让出分支。

> **这解释了 gate flip 为什么毫无效果**（FPS 30→31→31，CPU 126→125→126）：
> 两个位只门控"记录时间戳/扫描待完成对象"这段簿记，不是等待本身。
> 用户上一轮的判读方向是对的，flip 无效的原因现在有着落了。

### 4.3 GPU 一侧：这才是反转

同一时刻的 `nvidia-smi`：

| 项 | 值 |
|---|---|
| SM 时钟 | 1911 MHz（**满频**，max=1911） |
| 显存时钟 | 4006 MHz（**满频**，max=4004/4006） |
| 功耗上限 | 120 W（default 120 / min 60 / max 140） |
| 降频原因 | **全部 Not Active**（SW Power Cap / HW Slowdown / Thermal 皆无） |
| GPU 利用率 | 89~93% |
| **显存利用率** | **6%** |
| 功耗 | **46~52 W** |

`dmon -s u` 的分列更直白：

```
# gpu   sm   mem
    0    92    6
    0    93    6
    0    91    6
```

**SM 92%、显存 6%、功耗 47 W。** 这不是"算得很快"，是"占着 SM 但不搬数据"。

### 4.4 分辨率对照：定住了"与像素无关"

同一套流程换 320×200（像素少 32 倍）：

| 分辨率 | HUD FPS | GPU util | mem util | 功耗 |
|---|---|---|---|---|
| 1920×1080 | **31** | 90~92% | 6% | 47 W |
| 320×200 | **37** | 91% | **2%** | **41 W** |

像素少 32 倍，帧时间只从 32.3 ms 降到 27.0 ms，功耗只掉 6 W。
→ **约 27 ms/帧是像素无关的固定开销；1080p 的光栅只占约 5 ms。**

帧率是从 Heaven 右上角自带的 `FPS:` 读数直接截取的（`f1080.png` / `f320.png` 存证），
不是推算。

## 5. 修正后的模型

旧模型（报告 08）：

```
33.3 ms ≈ 40 次同步往返 × 350 µs + 应用 usleep 10 ms + 渲染 7 ms
```

新模型：

```
渲染期一帧 ≈ 27 ms（固定，像素无关）+ 5 ms（1080p 光栅）
其中那 27 ms 里：
  · CPU 主线程 100% R，在 0xae5c80 里反复"取号 → 查完成 → 比较"
  · GPU  sm 92% / mem 6% / 47 W，满频、无降频
  · 18 个 worker 线程 100% 睡在 futex / nanosleep
```

**两边都在空转，谁也不饱和。** 这不像"某一方算得慢"，更像一次
**CPU 提交 → GPU 完成 → CPU 看见** 的握手，每次要 ~27 ms。

能同时解释的四件事：
- 像素无关的地板（27 ms 与分辨率无关）；
- 功耗上不去（GPU 不搬数据，只有 47 W）；
- `__GL_YIELD=USLEEP` 只降 CPU 不改 FPS（等的长度不变，换等法没用）；
- Vulkan 358 fps（Vulkan 那条提交路径不走这个握手）。

**尚不能解释的**：为什么一次握手要 27 ms。
现在的证据只能排到"不是功耗墙、不是温度墙、不是频率、不是显存带宽"。

## 6. 排除项（本轮新增/更新）

| 假说 | 状态 | 依据 |
|---|---|---|
| 功耗墙 / 降频 | **排除** | 120 W 上限，满频，四种 throttle 全部 Not Active |
| 显存带宽瓶颈 | **排除** | mem util 2~6% |
| worker 线程是瓶颈 | **渲染期排除** | 18 线程 100% 睡姿 |
| 250 µs pacer 作为**睡眠间隔** | **作废** | condvar 超时实测 60/100 ms；250 只作为自旋里的强制 kick 截止时刻存在（见 §2.2 注） |
| condvar 不存在 | **作废（本轮更正）** | 运行时栈直接命中 `pthread_cond_timedwait` |
| 两个 gate 位决定是否等待 | **作废** | flip 后 FPS/CPU 不变；反汇编显示只门控簿记 |
| recvmsg EAGAIN ≈60/帧 | 排除 | Xlib 对 Xwayland socket 的非阻塞轮询 |

## 7. 方法与纪律（这轮踩的坑，写下来避免重犯）

1. **开测前先 `pkill -9 -x heaven_x64; pkill -9 -x strace`，并确认 `nvidia-smi` 回到 0% / 6 W / 139 MHz。**
   本轮开头有三个遗留实例在跑，最长 840 秒。
2. **不要用固定 `sleep` 猜稳态。** 用窗口截图体积判定（<10 KB = LOADING），
   或直接读 HUD 的 `FPS:`。
3. **`strace` 抓栈必须用 `-ff` 分线程文件**，不要 `grep -A`；
   `-k` 会让目标进程的系统调用频率发生数量级变化（4600 vs 20000/30s），
   **栈用于定结构，不能用于定频次。**
4. **`-c` 与 `-ff` 互斥**；`-e trace=nanosleep` 不匹配，内核入口是 `clock_nanosleep`。
5. **PLT xref 在这套库上不可用**（dlsym + GOT），跨版本比对要用**指令指纹**：
   例如 `imul $0xf4240` + `call gettimeofday@plt` 定位 `waitFor`；
   `movzwl 0x5e(...)` + `cmp $0xffff` 定位待完成对象扫描（515=9/525=7/580=11 处）。
6. **`LD_PRELOAD` 打桩对 Unigine 无效**：`nm -D` 里没有任何 GLX 符号，
   它是 dlopen+dlsym 自行解析的；强行拦 `dlsym` 会段错误。

## 8. 下一步（按性价比排序）

**P0 —— 定位那 27 ms 到底卡在哪一次握手。**
现在的证据只能说明"CPU 在等 GPU 的序号、GPU 在空转"。
需要的是**一次帧内的时序**：主线程 `get_seq()` 的返回值随时间怎么走。
做法：`gdb` 挂上，在 `0xae5d44`（比较处）下断点，采样 30 次，记录 `rbp/r14` 与时间戳；
或者在 `0x1900(%rbx)` 的 getter 上下断点看它读的是哪块内存（`ctx` 里哪个字段），
再反查这块内存是谁写的。

**P1 —— 确认 515 是否真的没有这个行为。**
本轮所有数据都在 580 上，而"525+ 都坏"仍是回忆。既然现在有了
"进场景后读 HUD FPS"这个干净口径，A/B 一次 515 的 1080p FPS 就能定案（31 vs ?）。
注意：换驱动前先把 `nvidia-smi` 归零，避免再次被遗留实例污染。

**P2 —— 把 `0xae5c80` 的 `get_seq` 追到写入方。**
如果是 GPU 写回的 semaphore，那 27 ms 就是 GPU 真的 27 ms 才完成；
如果是内核线程/中断写的，则瓶颈在中断延迟，方向完全不同。
判据：该字段所在页在 `/proc/<pid>/maps` 里是不是 `/dev/nvidia*` 的 mmap、是否 `MAP_SHARED`。

**P3 —— 用 P0 的结论回头再 diff 515/525/580 的 `0xae5c80` 同构函数。**
有了"等谁"的语义，跨版本 diff 才有意义；没有语义的 diff 只会又一次得到"逐行一致"。
