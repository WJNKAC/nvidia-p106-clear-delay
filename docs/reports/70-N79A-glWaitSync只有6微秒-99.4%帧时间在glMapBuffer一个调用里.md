# 70 · N79-A：`glWaitSync` 只有 **6 µs**（假设否定）；**99.4% 的帧时间在 `glMapBuffer` 一个调用里**

> 2026-10-26 11:30
> 用户判据表：
> | `glWaitSync` 中位 | 判读 |
> |---|---|
> | ≈20ms | 固定项 = 等 GPU fence，案子收口 |
> | **<1ms** | **`glWaitSync` 很快，缺口在别处——查 `glReadPixels` 或 PBO 落地** |
> | ≈26ms | 直接就是缺口本身 |
>
> **结果落在第二格：`glWaitSync` = 6 µs。**
> **但顺着"PBO 落地"查下去，缺口精确落到单个调用：`glMapBuffer` = 30.812 ms（1080p），占帧时间 99.4%。**
> **而且它的三点拟合公式与报告 56 的 `T_land` 逐字相同。**

---

> ## ⛔ 本报告核心结论已被 **报告 71（N80-B）** 推翻（2026-10-26 11:40）
>
> **「99.4% 的帧时间在 `glMapBuffer`」是错的。`glMapBuffer` 实测只有 2.758 ms = 帧时间的 9.9%。**
>
> 依据：同一条 trace 里同时挂两套探针交叉验证（358 次配对，差 0.012 ms）——
> `libGL.so.1:0x18902→0x18908`（primus 的 MB 探针）中位 **2.737 ms**，
> `glcore+0x103a2b0→+0x103a2e8`（glcore 的 map 真身）中位 **2.725 ms**。
>
> 正确的全帧分解：**`glMapBuffer` 2.758 / `glWaitSync` 0.008 / `glReadPixels` 0.089 /
> `usleep`（primus autosleep）24.823 = 89.2%**。
>
> 错误来源：本报告把 **primus 的 `usleep`** 算进了 `MB→W` 段（30.812 ≈ map 2.76 + sleep 24.8 + 余量），
> 而"四段之和恰好等于帧时间"这一点**不能**作为配对正确的证据——连续切分的任何方案都满足这个和。
> 旁证：报告 59（N62）早已测出「sleep 89.9% / map 9.8~9.9%」，与本报告冲突时该被推翻的是本报告。
>
> **仍成立的部分**：`glWaitSync` = 6 µs 且**不阻塞 CPU**、不能用它判 GPU 进度（§4.1）；
> 「旧 trace 的探针可重新组合」这一方法论（但要加配对完整性校验）。
>
> **作废的部分**：§5~§7 全部（`glMapBuffer = 20.25 + 1.336×MiB`、`T_land` 的实体是 `glMapBuffer`、
> `glFinish` 实验 N80）。**N80 已取消**，改为 N81-A（分解主线程的 27ms）。

## 1. 零成本：复用了 n58 的旧 trace

报告 56 当年为了测 `glReadPixels` 参数，在 primus 上挂了 7 个 uprobe，其中一个叫 `WS`，挂在 `0x18853`。

**本报告发现 `WS` 挂的正是 `glWaitSync` 的调用点**：

```asm
18846: mov  0x60(%r14),%rdi          ; di.sync
1884a: mov  $0xffffffffffffffff,%rdx  ; GL_TIMEOUT_IGNORED = -1
18851: xor  %esi,%esi                 ; flags = 0
18853: call *0x298ef(%rip)  # 42148   ; ★ glWaitSync  ← 探针 WS
18859: sub  $0x8,%rsp                 ; 返回地址
...
18876: call *0x2925c(%rip)  # 41ad8   ; ★ glReadPixels ← 探针 RP
...
18902: call *0x29820(%rip)  # 42128   ; ★ glMapBuffer  ← 探针 MB
18908: mov  0x8(%rsp),%rsi            ; ★ map 返回后第一条 ← 探针 W
```

**四个探针刚好把 readback worker 的一轮切成四段**，且 `MB→W` 就是 `glMapBuffer` 本身的完整耗时。

**没有新采集，直接分析 `analysis/traces/n58/`。**

## 2. 四段分解（三个分辨率）

| 段 | 640×360 | 960×540 | 1920×1080 |
|---|---|---|---|
| `W→WS`（进循环） | 0.032 | 0.032 | 0.037 ms |
| **`WS→RP`（`glWaitSync`）** | **0.005** | **0.006** | **0.006 ms** |
| `RP→MB`（`glReadPixels` 提交 + 走到 map） | 0.178 | 0.126 | 0.137 ms |
| **`MB→W`（`glMapBuffer`）** | **21.383** | **22.941** | **30.812 ms** |

### 2.1 1080p 的时间账

| 段 | 时间 | 占比 |
|---|---|---|
| `W→WS`（进循环） | 0.037 ms | 0.1% |
| **`WS→RP`（`glWaitSync`）** | **0.006 ms** | **0.0%** |
| `RP→MB`（`glReadPixels` 提交） | 0.137 ms | 0.4% |
| **`MB→W`（`glMapBuffer`）** | **30.812 ms** | **99.4%** |
| 合计 | 30.992 ms | 100% |

**→ `glWaitSync` 完全不是瓶颈（0.006 ms，占 0.0%）。**
**→ 提交也不晚（0.137 ms）。**
**→ 99.4% 在 `glMapBuffer` 这一个调用里。**

## 3. `glMapBuffer` 的三点拟合 = 报告 56 的 `T_land`

| 分辨率 | MiB | 实测 | 拟合 | 残差 |
|---|---|---|---|---|
| 640×360 | 0.88 | 21.383 | 21.424 | −0.041 |
| 960×540 | 1.98 | 22.941 | 22.892 | +0.049 |
| 1920×1080 | 7.91 | 30.812 | 30.820 | −0.008 |

```
glMapBuffer = 20.25 + 1.336 × MiB      等效带宽 0.78 GB/s
```

对照报告 56：

| | 截距 | 斜率 |
|---|---|---|
| 报告 56 的 `T_land` | 20.39 | 1.335 |
| **本次的 `glMapBuffer`** | **20.25** | **1.336** |
| 差 | **−0.14 ms** | **+0.001** |

**→ 两者是同一个量。**

### 3.1 这是一个重要的"收口"

报告 56 定义 `T_land` = "从提交 `glReadPixels` 到 `glMapBuffer` 可读"的时长，那是**从事件间隔推出来的抽象量**。

**本报告证明：`T_land` 就是 `glMapBuffer` 这一次调用的阻塞时间。**

因为 `RP→MB` 只有 0.137ms（提交瞬间完成），所以"从提交到可读"几乎全部落在 `glMapBuffer` 里。

**→ 20.4ms 固定项从此有了具体的指令级归属：它是 `glMapBuffer` 内部的等待。**

## 4. 判据对照

| 用户判据 | 实测 | 判定 |
|---|---|---|
| `glWaitSync` ≈20ms → 固定项 = 等 GPU fence | **0.006 ms** | **❌ 否定** |
| **`glWaitSync` <1ms → 缺口在 `glReadPixels` 或 PBO 落地** | **0.006 ms**，且 `glReadPixels` 提交只要 0.137ms | **✅ 命中，且精确落到 PBO 落地 = `glMapBuffer`** |
| `glWaitSync` ≈26ms | — | ❌ |

### 4.1 为什么 `glWaitSync` 快是**预期行为**

`glWaitSync`（client-side）的语义是：**把"等待 sync 对象"这条命令插入 GPU 命令流**，CPU **立即返回**。
真正阻塞 CPU 的是 `glClientWaitSync`。

**primus 用的是 `glWaitSync`（源码 566 行，参数 `GL_TIMEOUT_IGNORED = -1`）→ 它本来就不该阻塞。**

所以 6µs 不是"GPU 很快"，而是"这个调用设计上就不等"。
**用它来判断 GPU 是否完成，是错的工具。**

真正等数据的是 `glMapBuffer`——CPU 要读这块内存，必须等 DMA 落地。

## 5. 那 `glMapBuffer` 在等什么

### 5.1 已知的三条约束

| 约束 | 来源 |
|---|---|
| **与拷贝字节无关**：字节→0 时上限仍只有 49fps | 报告 56（`20.39` 是截距） |
| **与主线程 swap 无关**：不 swap 时 map 仍等 30ms | 报告 59 |
| **与读 FRONT/BACK 无关**：读 BACK 也等 30ms | 报告 59 |

**三条合起来只能得出一个结论：**

> **`glMapBuffer` 等的不是"这次拷贝的数据"，而是"GPU 命令队列排空"。**

因为它即使读一个没被更新的 buffer、即使根本不 swap，也照样等 30ms。

### 5.2 队列里有什么

`glReadPixels` 是 GL 命令，它依赖**之前所有渲染命令的结果**（GL 语义要求返回已完成的渲染）。
`glMapBuffer` 又依赖 `glReadPixels`。

所以 `glMapBuffer` 的等待 = **主线程这一帧渲染在 GPU 上执行完的时间 + 拷贝时间**。

| 项 | 估计 | 来源 |
|---|---|---|
| 1080p 纯渲染量 | **~7 ms** | 报告 07（`3.5 ns/px` 拟合） |
| 拷贝（7.91 MiB @ 0.78GB/s） | **~10.6 ms** | 本报告斜率 |
| 固定项 | **~20.3 ms** | 本报告截距 |
| **合计** | 37.9 ms | 实测 30.8 ms（有重叠） |

**→ 三项量级相当，但"固定项 20.3ms"没有对应到任何已知的物理量。**

### 5.3 与"GPU 空转"的矛盾

| 观测 | 值 | 来源 |
|---|---|---|
| GPU util | **100%** | nvidia-smi |
| GPU 功耗 | **55 W**（TDP 120W） | nvidia-smi |
| SM 时钟 | **1911 MHz**（满频） | nvidia-smi |
| 温度 | 41 °C | 报告 07 |

**满频 + util 100% + 只有 55W + 41°C = GPU 在"占位"而不在"算"。**

报告 07 记过同样的矛盾（Vulkan 37W 跑 358fps，GL 48W 跑 30fps），当时的结论是"GL 每帧被一段等待串行化"。

**现在这段等待被精确定位到 `glMapBuffer`。**

---

### 5.4 ★ 固定项 20.25ms **与像素量完全无关** —— 这排除了"等 GPU 填充"

用本报告自己这三个点就能验证：

| 分辨率 | 像素 | 固定项（截距） | 若固定项 ∝ 像素，应为 |
|---|---|---|---|
| 640×360 | 0.23 M | **20.25 ms** | 20.25 ms（基准） |
| 960×540 | 0.52 M | 20.25 ms | 45.56 ms |
| 1920×1080 | 2.07 M | 20.25 ms | **182.25 ms** |

**像素量差 9.0 倍，固定项都是 20.25 ms。**

→ **固定项不是"等 GPU 光栅化/填充"。** 如果是，1080p 应该比 640×360 慢 9 倍。

### 5.5 它更像是"每帧 GL 调用数的固定成本"

报告 07 当年用完全不同的方法（像素扫描 + 帧时间拟合）得出：

> `26 ms ÷ 每帧约 1000 次 GL 调用 ≈ 26 µs/次`

本报告：`20.25 ms ÷ 1000 次 ≈ 20.2 µs/次`

**两次独立测量（一个是改分辨率扫像素，一个是拟合 `glMapBuffer` 截距）落在同一个量上：每次 GL 调用的固定成本约 20~26 µs。**

这解释了：

| 现象 | 解释 |
|---|---|
| 降分辨率只从 32→42 fps | 只减少了**斜率项**（拷贝字节），固定项不动 |
| 报告 07 的 `3.5 ns/px` 只值 7ms | 1080p 的纯填充时间确实只有 7ms，剩余 20ms 与像素无关 |
| 报告 49 的"每命令一次的记账开销" | **同向**：都是"按调用次数收费"的成本 |
| 报告 22/27 的"像素扫描从未生效" | 那次降的是 `-video_width` 而非 `-video_mode`，像素没变 → 固定项当然不变 |

### 5.6 但仍不能确定"等渲染"还是"等拷贝"

固定项与像素无关，**但降分辨率不减少 draw call 数**。

所以 20.25ms 仍可能是：

- **(a) 等 GPU 逐个处理 ~1000 次 draw call**（与像素无关，与调用数相关）
- **(b) 拷贝路径的固定建立延迟**（与字节无关，与是否跨内存域相关）

**两者都与"像素"和"字节"无关，所以用分辨率扫描区分不开。**
**必须用 §7 的 `glFinish` 实验才能分开。**

（`glFinish` 放在 `glReadPixels` 之前：若它吃掉 ~20ms，是 (a)；若它 ~0 而 `glMapBuffer` 仍 30ms，是 (b)。）

### 6.1 这条对"能不能修"的意义

`glMapBuffer` 是 primus 里正常的使用（双 PBO + `GL_STREAM_READ`），**没有改错**。

- 改成 `glGetTexImage` 也一样要等（都是等队列）
- 加更多 PBO 也只能掩盖，不能消除"队列里那一帧渲染要 20ms"这个事实

**→ 如果队列排空真的要 20ms，primus 用户态改不动。这与报告 59/60/61 的结论一致。**

## 7. 下一步：把"等队列排空"拆成"等渲染"和"等拷贝"

现在的问题很具体：**`glMapBuffer` 的 20.3ms 固定项，是等渲染完成，还是等拷贝完成？**

### 7.1 一个干净的实验（改 primus 一行 + uprobe）

在 readback worker 的 `glReadPixels` **之前**插入 `glFinish()`，并挂 uprobe 测它的耗时：

```c
#ifdef N80_GLFINISH
    primus.afns.glFinish();     // ← 新加
#endif
    primus.afns.glReadPixels(0, 0, width, height, GL_BGRA, GL_UNSIGNED_BYTE, NULL);
```

| `glFinish` 耗时 | `glMapBuffer` 耗时 | 判读 |
|---|---|---|
| **≈20ms** | **降到 ~10ms** | **等的是渲染** → 20ms = GPU 执行这一帧的时间 |
| ≈0 | 仍 ~30ms | **等的是拷贝/DMA** → 20ms 在驱动拷贝路径里 |
| 两者都 ≈0 | 仍 ~30ms | 等的是别的东西（fence 语义/驱动内部批处理） |

**这个实验的关键是"两个都测"**——只看 `glFinish` 快不能说明问题，因为时间会被推到 `glMapBuffer` 里。

### 7.2 为什么这个实验值得做

因为它的两个结果指向完全不同的结论：

| 结果 | 结论 | 可修性 |
|---|---|---|
| 等渲染（20ms 是 GPU 执行时间） | **GPU 执行这一帧就要 20ms** → 与 525 的 GPU 调度/限频有关 | 用户态改不动 |
| 等拷贝（20ms 是 DMA 固定延迟） | **跨 GPU/跨内存域的拷贝有 20ms 建立延迟** | 也许能换路径 |

**而"等渲染"这一支与外部证据完全对得上**：rexpulli 测到 515 >100W、525 ≤70W，且频率都是满的 → **515 时 GPU 真在出力，525 时满频空转**。若 525 执行同一帧要 20ms（而 515 只要 5ms），功耗低、util 假高就都解释通了。

### 8.1 方法论（五条，已入技能库）

1. **★ 旧 trace 里的探针可能比你记得的更有用。**
   报告 56 的 `WS` 探针本意是"标记 wait sync 开始"，但它正好挂在 `glWaitSync` 的 `call` 上，
   加上 `MB`/`W` 一对，**四个探针刚好把一轮切成四段**。
   **做新实验前，先检查旧 trace 里已有哪些事件点、能不能重新组合出答案。**

2. **★ `glWaitSync` 不阻塞 CPU，不能用它判断 GPU 进度。**
   它只是把 wait 插进命令流；真正阻塞的是 `glClientWaitSync` 或 `glMapBuffer`（要等数据落地）。
   **测出 `glWaitSync` 很快，不能推出"GPU 已完成"。**

3. **★ 三个分辨率拟合出的公式与之前某个"抽象量"的公式重合，说明找到了那个量的实体。**
   本例 `glMapBuffer = 20.25 + 1.336×MiB` ≡ 报告 56 的 `T_land = 20.39 + 1.335×MiB`（截距差 0.14、斜率差 0.001）。
   **这比"数值接近"强得多：它证明两者是同一个可观测事件，抽象量有了 mechanism 级归属。**

4. **★ 拟合能分开「固定项 vs 线性项」，但分不开固定项内部的两支。**
   固定项 20.25ms 与像素量无关（差 9 倍仍不变）只排除了"等 GPU **填充像素**"，
   而"等 ~1000 次 draw call **逐个处理**"同样与像素无关。**降分辨率这个测法到此失效**，
   必须换一个只对其中一支敏感的变量：**渲染完成时刻**（插 `glFinish`），不是像素数。

5. **★ 判断"哪个线程是主线程"不能看 ioctl/syscall 数量。**
   本例"NVIDIA ioctl 最多"的线程是 `readback_work`（每帧 map + readPixels + 多次 glcore ioctl，
   数量天然最多）。**主线程 = `tid == pid`**。这个误判的代价是报告 63~67 全部要加更正横幅。
