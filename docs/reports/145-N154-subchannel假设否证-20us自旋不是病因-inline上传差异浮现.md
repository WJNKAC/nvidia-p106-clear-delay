1. `NK_DUMP` 支持**逗号分隔多个 nr**（原来只能填一个）

## 2. 第 2 步（对比 hClass 与 pAllocParms）——**假设被否证**

### 2.1 先搞清楚 alloc 的语义分层

从日志本身可以无歧义地读出对象树（不靠猜）：

| class | 角色 | 判据 |
|---|---|---|
| `0x00000080` | client 下的 root 对象 | parent 是 client handle |
| `0x00002080` | device | 挂在 root 下 |
| `0x0000A06C` | channel group | 挂在 root 下 |
| `0x0000C06F` | **channel** | 挂在 group 或 root 下 |
| 其余 | **引擎对象 = 绑定一个 subchannel** | `hParent` 是 channel |

脚本 `wk/submap.py` 按这个判据还原绑定表，**subchannel 编号 = 引擎对象在该 channel 上的分配顺序**。

### 2.2 两版的绑定表：逐项相同

**515.105.01**（channel `beef0100`）

| sub | class | hObject | 首次 alloc 耗时 |
|---|---|---|---|
| 0–3 | `0x009072` ×4 | `beef4901..04` | 38 / 18 / 17 / 17 µs |
| 4 | `0x00902D`（3D） | `beef502d` | **405 µs** |
| 5 | `0x00C1B5` | `beefa0b5` | 22.5 µs |
| **6** | **`0x00A140`** | **`beef3901`** | 30.1 µs |
| 7 | `0x00C197` | `beef9097` | 28.0 µs |

**525.116.03**（channel `beef0100`）

| sub | class | hObject | 首次 alloc 耗时 |
|---|---|---|---|
| 0–3 | `0x009072` ×4 | `beef4900..03` | 39 / 21 / 18 / 18 µs |
| 4 | `0x00902D`（3D） | `beef502d` | **405.7 µs** |
| 5 | `0x00C1B5` | `beefa0b5` | 23.8 µs |
| **6** | **`0x00A140`** | **`beef3901`** | 30.1 µs |
| 7 | `0x00C197` | `beef9097` | 28.0 µs |

**8 个 subchannel，class 序列、对象句柄、连初始化耗时都一一对应。**

### 2.3 `0x2a` 控制面也同构

`cmd` 分布逐条对比（前 18 名）：

| cmd | 515 | 525 |
|---|---|---|
| `20800406` | 194 | **196** |
| `00000202` | 63 | 63 |
| `90960107` | 45 | 45 |
| `00000201` | 35 | 35 |
| `00000d01` | 34 | **33** |
| `20801701` | 23 | 23 |
| `00800289` | 22 | 22 |
| 其余 | 全部逐条相同 | |

差异只有 ±1~2 条的计数噪声。

### 2.4 判决

> **"525 没给 sub6 绑对象，所以只能在用户态改命令号"这个假设不成立。**
> 525 的 RAMHT 里 sub6 绑的是 `0xA140`，句柄 `beef3901`，与 515 完全一致。

连带推论（重要）：

- 报告 143 里"改 sub→6 报 Xid 32"**不是**因为内核没绑 sub6。
  Xid 32 是 **INVALID_METHOD**（方法不在该 class 的方法表里），
  它恰恰证明 **sub6 的对象存在并且被 GPU 认到了**，只是被塞进去的 method 号对 `0xA140` 非法。
- 也就是说，**那次实验的前提反了**：不是"没绑"，是"绑了但方法不对"。

## 3. 顺手否证我自己上一轮的候选：20 µs 自旋不是病因

报告 138 找到 525 每帧 270 次"等待函数"（`0x15761b0`），515 零次。
报告 136 又算出"每次绑定 122 µs"。两者一乘就对上了（7 × 20 µs ≈ 140 µs），
于是形成过一个很自然的因果链：**绑定 → 空间不够 → 自旋 7 次 → 122 µs**。

### 3.1 静态：它确实是个纯延迟，不是等待条件

`0x15761b0..0x15762d0`（288 B）反汇编要点：

```
mov  rbx,[rdi+0x1300]        ; 那个一直没定语义的对象
mov  dword [rdi+0x2c],1
call [rbp+0x290]             ; 取时钟(µs)
lea  r12,[rax+0x14]          ; ← deadline = now + 20µs   （ctx 为空时是 +0x2710 = 10 ms）
loop: call [rbp+0x290]
      cmp rax,r12 ; jge out  ; 只比时间
      9 × pause
      jmp loop
out:  add [r13+0x6f88],rax   ; 把耗时累加进统计计数器
```

**循环体里没有任何"等某个变量变化"的判断**，纯粹烧掉 20 µs。
它不是"等条件满足"，而是"固定退避"。

### 3.2 动态：把这个 20 µs 改成 0，性能一点没变

只改一个立即数（地址由脚本从 eh_frame 边界算出，不口算）：

```
0x15761e6:  4c 8d 60 14    lea r12,[rax+0x14]
                    ↑
0x15761e9:        ^^ 这个 0x14 改成 0x00
```

用 `LD_PRELOAD` 的 `nodelay.so` 在 glcore 加载后（后台线程轮询 `dl_iterate_phdr`）就地改写。
运行确认补丁真的写进去了：

```
[nodelay] base=0x7f3a49c00000 off=0x15761e9 addr=0x7f3a4b1761e9  上下文: 4c 8d 60 | 14
[nodelay] 已写入：14 -> 00
```

结果（n83b, `-M 3 -f 6 -n 1000`）：

| | total_p50 | total_p10 | map_p50 | fps |
|---|---|---|---|---|
| 基线 run1 | 127.334 ms | 127.126 | 125.828 | 7.85 |
| 基线 run2 | 127.291 ms | 127.173 | 125.713 | 7.86 |
| **延迟改 0** | **127.266 ms** | 127.156 | 125.671 | 7.86 |
| **延迟改 0（复测）** | **127.141 ms** | 127.056 | 126.016 | 7.87 |

**差异 < 0.2%，在噪声内。**

### 3.3 判决

> 那 270 次/帧的自旋是**伴随现象**，不是病因。
> 525 慢不是因为它在这 20 µs 里烧了时间——去掉它一点没变快。

同时这条也说明：**CPU 侧的提交节奏不是瓶颈**。
时间全部落在 `map`（`glMapBuffer` 等 GPU 完成）：`map_p50 = 125.7 ms / total 127.3 ms = 98.7%`。
**GPU 本身就是慢的，慢在 GPU 执行，不在 CPU 提交。**

## 4. 新线索：两版的数据上传机制不同

上一轮的报告 140 有一组一直没解释的数字：

| method | 515 中位 | 525 中位 |
|---|---|---|
| `sub6:0x0034` | **6,653** | **16** |
| `sub0:0x1b00` | **3,855** | **34** |

在这一轮把 subchannel 的身份查清楚之后，这两条终于能读了（class 名来自 OKM 的 `src/common/sdk/nvidia/inc/class/`）：

| class | 名字 | 用途 |
|---|---|---|
| `0xA140` | **`KEPLER_INLINE_TO_MEMORY_B`** | 把 pushbuffer 里的数据**内联写进显存** |
| `0xC1B5` | `PASCAL_DMA_COPY_B` | DMA 拷贝引擎 |
| `0x902D` | 3D 引擎 | 绘制 |

于是：

- **`sub6` = 内联上传通道。515 每帧发 6,653 条内联写；525 只发 16 条。**
- `sub0:0x1b00` 落在 3D class 的 **inline data 段**。515 用 3,855 次；525 用 34 次。

**两版对"把小数据交给 GPU"这件事选了完全不同的机制：**

```
515：绑定参数 ──inline──▶ 直接进 pushbuffer ──▶ GPU 读命令时就地拿到   （无同步、无 fence）
525：绑定参数 ──写缓冲──▶ 显存缓冲 ──▶ 需要一个"确保 GPU 已读/已写完"的同步点
```

这与所有已知判据自洽：

- 报告 136：**M8（1000 次绑定 + 只 1 次 draw）= 2.97 ms 正常** ⇒ 绑定本身没有 GPU 代价
- 报告 136：**M9/M10（绑定与 draw 分开）= 7.5 ms 正常** ⇒ 只有"绑定紧跟 draw"才触发
- 报告 136：**M3 = 127 ms，与分辨率无关、与对象类型无关** ⇒ 是固定开销，不是带宽
- 报告 138：525 每帧 270 次进入"等待"而 515 零次 ⇒ 525 需要一个同步点，515 不需要
- 报告 140：525 命令**更少**却更慢 ⇒ 少掉的那 ~17,000 条正是 inline 上传，替换成了代价更高的缓冲同步

### 4.1 但 M8 把假设收窄了——同步只能发生在 draw 之前

必须先把一条反例摆出来，否则这个假设站不住：

> **M8 = 1000 次绑定 + 只 1 次 draw = 2.97 ms（≈3 µs/次），完全正常。**

如果"绑定"本身要付同步代价，M8 就该是 122 ms。它没有。
所以同步**不挂在绑定上**，只能挂在 **draw 读状态** 这个动作上：

```
M8  绑定 ×1000 ····················· draw ×1     → 只在最后同步一次，快
M9  绑定 ×1000 → draw ×1000（全部画完）          → 同理，快
M3  绑定, draw, 绑定, draw, ... ×1000            → 1000 次同步，每次 122 µs，慢
M1  draw ×1000（不绑定）                          → 状态没变，无需同步，快
```

自洽的解释只有一种：

> **525 的状态写进显存缓冲，draw 要想看见它必须等一个 fence；
> 515 的状态用 inline 直接写进同一条 pushbuffer，GPU 顺序执行天然可见，不需要 fence。**

而 `122 µs` 就是一次这种同步往返的固定代价（与分辨率、对象类型无关——报告 136 已测）。

> 这一条目前是**强假设，还没被实验证实**。它可证伪的预测很具体：
> **525 的每一个 draw 之前，应当存在一条固定的同步/fence 类命令；515 的对应位置没有。**
> 反过来说，如果把那条命令从命令流里去掉而 fps 不变，这个假设也就死了。
