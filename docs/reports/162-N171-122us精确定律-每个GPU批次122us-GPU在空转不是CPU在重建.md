# N171 — 122 µs 精确定律：**每个 GPU 批次固定 122 µs，是 GPU 在空转，不是 CPU 在重建状态**

**日期**：2026-10-27
**驱动**：525.116.03
**起点**：项目最初的问题「525 每对 (bind,draw) 慢 122 µs」；此前的解释是「每次 draw 触发约 18 次 legacy 状态机重建」（报告 155）

---

## 0. 一句话结论

**122 µs 不是"每次 legacy 调用"的成本，也不是"CPU 重建状态"的成本，而是「一个 GPU 批次的启动成本」。**

```
T_frame = T_base(N) + B × 122 µs        B = 批次数（状态变更之后紧跟的那个 draw 起新批）
                拟合 R² = 0.999998 / 1.000000（两组独立数据）
```

**而且这 122 µs 是 GPU 在空转：CPU 提交一个批次只要 1.5 µs，GPU 利用率 98% 但功耗反而从 46.7 W 掉到 37.3 W。**

---

## 1. 触发条件：不是 legacy，是「批次边界」

### 1.1 先推翻"legacy 专属"

同一程序、同样 400 个 draw，只改"每次 draw 前做什么"：

| 模式 | draw 前做什么 | 有无 legacy | total_p50 | map_p50 |
|---|---|---|---|---|
| `-M 1` | 什么都不做 | 无 | **4.459** | 4.428 |
| `-M 2` | `glUniform3f` 改颜色 | 无 | **4.518** | 4.438 |
| `-M 3` | `glUseProgram` 在两个 program 间交替 | **无** | **52.823** | 52.087 |
| `-M 4` | `glBindFramebuffer` 交替 | 无 | 54.323 | 51.038 |
| `-M 5` | `glBindTexture` 交替 | 无 | 53.237 | 53.085 |
| `-M 6` | `glUseProgram` 切到**同一个** program（语义空操作） | 无 | **53.883** | 53.300 |
| `-M 0` | `glLoadIdentity`+`glTranslatef`+`glScalef`+`glColor3f` | **有（固定管线）** | 55.262 | 55.095 |

**`-M 3` 是纯 shader、零 legacy 调用，一样慢 12 倍。**
**`-M 6` 切换到一个完全相同的 program（驱动完全可以识别为 no-op），一样慢。**

⇒ **惩罚与 legacy 无关，与"切换了什么"也无关。**

### 1.2 关键：切换本身免费，但"切换之后的那个 draw"要钱

| 模式 | 结构 | total_p50 |
|---|---|---|
| `-M 8` | 400 次切换 + **1 个** draw | **2.650** ← 最快 |
| `-M 9` | 400 次切换 **全部做完**，再 400 个 draw（不相邻） | **4.470** |
| `-M 10` | 400 个 draw 先做完，再 400 次切换 | 4.761 |
| `-M 3` | 切换与 draw **交替** | **52.823** |

**400 次切换单独做完全免费（2.65 ms，比基线还快）。**
**只有当"状态变更"和"draw"交替出现时才慢。**

⇒ **成本在「新批次的第一个 draw」上。** 400 次切换如果后面只跟 1 个 draw，就只起 1 个新批次 → 只付 1 次钱。

### 1.3 `glUniform` 为什么豁免

`-M 2`（每次 draw 前改 `glUniform3f`）**完全免费**。
原因：uniform 值可以作为 pushbuffer 里的**内联数据**写下去，不需要结束当前批次；
而 program / FBO / texture 的绑定变更需要重新绑定状态对象，**必须切批**。
legacy 矩阵/颜色会弄脏固定管线状态 → 也要切批。

## 2. 定律：成本 = 批次数 × 122 µs，与 draw 数无关

### 2.1 固定 N=400，扫批次数 B

| B | total_p50 | 相对基线 |
|---|---|---|
| 0 | 4.477 | — |
| 1 | 4.551 | +0.07 |
| 10 | 4.715 | +0.24 |
| 25 | 6.587 | +2.11 |
| 50 | 9.643 | +5.17 |
| 100 | 15.782 | +11.31 |
| 200 | 28.178 | +23.70 |
| 400 | 52.821 | +48.34 |

**最小二乘（B≥25）：`T = 3.48 ms + B × 123.4 µs`，R² = 0.999998**

### 2.2 固定 B=100，扫 draw 数 N（100 → 1600，16 倍）

| N | total_p50 |
|---|---|
| 100 | 18.337 |
| 200 | 17.194 |
| 400 | 16.293 |
| 800 | 16.762 |
| 1600 | 18.553 |

**N 变 16 倍，耗时纹丝不动（16.3~18.6 ms）。**
⇒ **成本只看批次数，与每个批次里有多少 draw 完全无关。**

### 2.3 第二组独立数据（N=1600）

| B | 每批 draw 数 | total_p50 | fps |
|---|---|---|---|
| 0 | 1600 | 9.981 | 100.19 |
| 10 | 160 | 7.467 | 133.91 |
| 40 | 40 | 11.113 | 89.99 |
| 200 | 8 | 30.880 | 32.38 |
| 800 | 2 | 104.105 | 9.61 |
| 1600 | 1 | 201.688 | 4.96 |

**最小二乘（B≥200）：`T = 6.49 ms + B × 122.0 µs`，R² = 1.000000**

**两组独立的 N、两条拟合，斜率 123.4 / 122.0 µs —— 同一个常数。这就是项目最初追的那个 122 µs。**

> 小异常：B=10（7.467 ms）比 B=0（9.981 ms）还快。差 2.5 ms，且 B=0 时 1600 个 draw 挤在一个批次里，
> 可能有别的效应（批次过大/缓存）。不影响主结论（B≥200 的线性段斜率精确）。

## 3. ★ 这 122 µs 不是 CPU 干的

### 3.1 去掉回读，同一个负载 CPU 1 ms 内就排完了

| 配置 | 带回读（等 GPU） | 仅提交（`-R`，不等） |
|---|---|---|
| B=0 | 4.459 ms | **0.014 ms** |
| B=400 | **52.869 ms** | **0.586 ms** |

**400 个批次，CPU 侧一共只花 0.586 ms = 1.5 µs/批次。**
**但带回读就变成 52.9 ms。**

⇒ **CPU 驱动为每个批次只做 1.5 µs 的活。那 122 µs 不在 CPU 上。**

**这一条直接否掉了「CPU 重建状态表」的解释**：如果真是 CPU 在重建 18 次状态表，
那 `-R` 也必须花同样的时间（重建是同步的 CPU 工作，与回不回读无关）。
实测 `-R` 只用 0.586 ms。

### 3.2 GPU 侧证据：利用率 98%，但功耗**下降**

同一负载，跑的时候用 `nvidia-smi` 每 100 ms 采样：

| 配置 | 帧时间 | GPU 利用率 | SM 时钟 | 功耗 |
|---|---|---|---|---|
| B=0 | 4.470 ms | 85% | 1911 MHz | **46.7 W** |
| B=400 | 52.768 ms | **98%** | 1911 MHz | **37.3 W** |

**GPU "忙" 98%，时钟顶格 1911 MHz，但功耗反而掉了 9.4 W。**

这是**空转（spin）**的典型特征：占用率高、功耗低、不出活。
渲染是真的在发生（pixel 正确），但 122 µs 里绝大部分时间 GPU 不在着色，而在等某个条件。

**⇒ 这同时解释了项目最开始的现象「525 下 3D 功耗上不去」：
GPU 把时间花在批次栅栏上空转，而不是花在渲染上。**

> 时钟锁定实验（`nvidia-smi -lgc`）在这张 P106-100 上没生效（实际时钟始终 1911 MHz），
> 所以"122 µs 是否随时钟缩放"仍未知。若要继续，需换 `-ac` 或确认卡是否支持。

## 4. 与 515 的对照（历史数据重新解释）

报告 79 测过：同一 `n83a` 二进制，**515 的每对成本 0.03 µs，525 = 121 µs**。

按本轮定律重述：**515 的批次启动成本 ≈ 0，525 = 122 µs。**
这不是"525 每次 legacy 调用多做功"，而是"**525 每个 GPU 批次要多付 122 µs**"。

515 上 `n83a` 101 fps / 525 上 34 fps 的差距，也应按批次数重算：
**515 的 `T = T_base(N)`（无 B 项），525 的 `T = T_base(N) + B × 122 µs`。**

## 5. ★ 更正报告 155 的机理表述

报告 155 §8 写的是：

> 「只要上下文里存在 legacy 固定管线状态，每一次 `glDrawArrays` 都会触发约 18 次状态机重建」

**这条现在需要更正**，原因有三：

| 原表述 | 实测 |
|---|---|
| 是 legacy 专属 | ✗ `-M 3` 纯 shader、零 legacy，一样慢 12 倍 |
| 每个 draw 都触发 | ✗ 400 个 draw 在同一批次里完全免费（`-M 1` = 4.46 ms） |
| 是 CPU 重建状态表 | ✗ `-R` 下 CPU 只花 0.586 ms/400 批次 |

**正确的表述**：

> **每次"状态变更之后紧跟一个 draw"会开启一个新的 GPU 批次，每个批次固定多花 ~122 µs 的 GPU 时间。**
> 与批内 draw 数无关、与被切换的状态种类无关（program / FBO / texture / legacy 都算），
> 但 `glUniform` 不算（可作为内联数据写入，不切批）。

报告 155 里"18 次/对"这个数字仍然是对的**观测**（152k 次/秒 ÷ 8 fps ÷ 1000 对 ≈ 18），
但它描述的是**某条状态机函数被调用的频次**，不是成本来源 ——
和报告 161 里 `sched_yield` 被误读成"调度开销"是同一类错误：**观测到的高频 ≠ 成本**。

## 6. 唯一有效的优化方向：减少批次数

不用改驱动、不用 hook、不用伪造 fence。**把状态变更集中，让 draw 成批。**

实测（1600 个 draw，只改批次划分）：

| 批次数 | 每批 draw | 帧时间 | fps | 相对最优 |
|---|---|---|---|---|
| 1 | 1600 | 9.981 ms | 100.19 | 1.0× |
| 10 | 160 | **7.467 ms** | **133.91** | **1.3×** |
| 40 | 40 | 11.113 ms | 89.99 | 0.9× |
| 200 | 8 | 30.880 ms | 32.38 | 0.32× |
| 800 | 2 | 104.105 ms | 9.61 | 0.096× |
| 1600 | 1 | **201.688 ms** | **4.96** | **0.049×** |

**同样的 1600 个 draw，只因为批次划分不同，帧率差 20 倍。**

工程含义：
- **状态排序（state sorting）/ 合批**在 525 上不是"优化"，是**决定性**的。
  把"逐物体设状态再画"改成"按状态分组后成批画"，直接消掉 122 µs × B。
- **每帧批次数就是你的性能预算**：60 fps（16.67 ms）下，若 base 占 6 ms，
  则 B 必须 ≤ 87 批；30 fps 下 B ≤ 175 批。
- **`glUniform` 可以放心用**，它不切批；`glUseProgram` / `glBindTexture` / `glBindFramebuffer` 都要算钱。
- 这也解释了为什么"减少 legacy 调用数（4→1）没用"（报告 155 实测）：
  **只要还在每次 draw 前动状态，批次数就是 draw 数**，改幅度不改次数。

## 7. 与 zink 结果的一致性

报告 156：zink 让 M3 从 127.90 → 18.59 ms（6.9×）。

按本轮定律：zink 走 Vulkan，**command buffer 由 Mesa 合并**，
"状态切换 + draw"在 Vulkan 里表现为 pipeline/descriptor 绑定 + `vkCmdDraw`，
**不会为每个 draw 起一个新的 GPU 批次** ⇒ B 项消失，只剩 `T_base` 与少量 pipeline 切换。

⇒ 与"zink 消除了 B×122 µs"完全一致。**这也解释了为什么 zink 对这种 workload 有效、
而对 Heaven（自己就有大量状态切换但被 vsync 压住）看不出收益。**

## 8. 结论

1. **122 µs = 一个 GPU 批次的启动成本**，定律 `T = T_base(N) + B × 122 µs`，R² = 0.999998 / 1.000000。
2. **成本与批内 draw 数无关**，与"切换什么状态"无关（legacy / program / FBO / texture 都算，`glUniform` 不算）。
3. **不是 CPU 成本**：CPU 每批次只花 1.5 µs（`-R` 实测 0.586 ms / 400 批）。
4. **是 GPU 空转**：利用率 98%、时钟 1911 MHz 顶格、功耗却从 46.7 W 降到 37.3 W。
   **这也收口了项目最初的「525 下 3D 功耗上不去」。**
5. **515 与 525 的差别就是这一项**：515 的批次启动成本 ≈ 0，525 = 122 µs。
6. **可操作的解法是合批**：1600 个 draw 从 1600 批降到 1 批，5 → 100 fps（20 倍）。
7. **更正报告 155**：不是"legacy 专属"、不是"每个 draw 都触发"、不是"CPU 重建状态表"。
