# 14 · 525 安装失败诊断：编译器不匹配 + 版本装错

> 2026-10-25 10:00–10:30
> 现象：用户尝试安装 525，安装器失败，且 **515 已被卸载**（`nvidia-smi` 不存在，无任何 nvidia 模块/库残留）
> 结论：**两个独立问题。根因是 C 编译器不匹配（gcc-14 vs 内核的 gcc-12）；另一个更关键——装的是 525.89.02，不是我们分析的 525.116.03。**
> 已验证：**525.116.03 + `CC=gcc-12` 在 6.1.0-50 上编译通过**（`nvidia.ko` 与 `nvidia-uvm.ko` 都生成了）。

---

## 1. 报错原文

```
Warning: Compiler version check failed:
The major and minor number of the compiler used to compile the kernel:
gcc-12 (Debian 12.2.0-14+deb12u1) 12.2.0, GNU ld (GNU Binutils for Debian) 2.40
does not match the compiler used here:
cc (Debian 14.2.0-19) 14.2.0
...
*** Failed CC version check. ***

  MODPOST .../kernel/Module.symvers
ERROR: modpost: "nvUvmInterfaceDisableAccessCntr" [.../nvidia-uvm.ko] undefined!
ERROR: modpost: "nvUvmInterfaceChannelDestroy"   [.../nvidia-uvm.ko] undefined!
... (共 59 条同类)
ERROR: The nvidia-uvm kernel module was not created.
```

### 1.1 这是一个**误导性**报错

59 条 `nvUvmInterface* undefined` 看起来像"`nvidia-uvm.ko` 找不到 `nvidia.ko` 导出的符号"，
很容易让人去查符号导出、`EXPORT_SYMBOL`、模块依赖顺序。

实际不是。`nvUvmInterface*` 是 `nvidia.ko` 里 `EXPORT_SYMBOL` 出来的，正常情况 modpost 从
`nvidia.ko` 的 `Module.symvers` 读取。这里报 undefined 的真实原因是
**gcc-14 编出来的产物与 gcc-12 编出的内核/头文件在 modpost 阶段对不上**，
导致符号表没被正确消费——**症状伪装成了"符号缺失"**。

> 记一条：`modpost: "xxx" undefined!` 出现在"内核与外部模块编译器不一致"的现场时，
> **先看 CC 版本警告，不要从符号下手。**

---

## 2. 第二个问题（更要紧）：装错版本

安装日志里出现的版本号：

```
NVIDIA-Linux-x86_64-525.8       ← 日志里的截断匹配
NVIDIA-Linux-x86_64-525.89.02   ← 实际安装的
```

**我们全部分析的对象是 525.116.03**（`drivers/525.116.03/NVIDIA-Linux-x86_64-525.116.03.run`）。

这直接影响 E4 的可用性——报告 12/13 里那套静态定位全部只对 **525.116.03** 成立：

| 项 | 525.116.03 的值 | 是否适用于 525.89.02 |
|---|---|---|
| 排空函数入口 | `0x1577a90` | **否** |
| deadline 字段 | `ctx+0x6fc8` | **否** |
| N（挂起计数） | `ctx+0x22edc` | **否** |
| 门位 | `ctx+0x5ad` | **否** |
| retry 计数 | `ctx+0x6fc1` | **否** |

而且 525.89.02（2023-02）比 525.116.03（2023-04）更早，行为未测量过。
**即使 525.89.02 装成功，`e4_window.sh` 传 `0x1577a90 0x6fc8` 也会锚错地方**，
测出来的东西不能与 515/580 对比。

→ **必须换回 525.116.03 再装。**

## 3. 已验证：525.116.03 + gcc-12 能编译

动手装之前先做了一次**只编译、不安装**的验证（避免再失败一次）：

```bash
cd /tmp/v525/NVIDIA-Linux-x86_64-525.116.03/kernel
make -k -j8 NV_EXCLUDE_KERNEL_MODULES="" \
     SYSSRC=/lib/modules/6.1.0-50-amd64/source \
     SYSOUT=/lib/modules/6.1.0-50-amd64/build \
     NV_KERNEL_MODULES="nvidia nvidia-uvm" CC=gcc-12
```

结果：

```
  LD [M]  .../kernel/nvidia.ko
  LD [M]  .../kernel/nvidia-uvm.ko
  BTF [M] .../kernel/nvidia.ko
Skipping BTF generation ... due to unavailability of vmlinux
make[1]: 离开目录"/usr/src/linux-headers-6.1.0-50-common"
```

- **`nvidia.ko` 与 `nvidia-uvm.ko` 都生成**
- `MODPOST` 顺利通过，**零 undefined**
- 唯一警告是 BTF 跳过（缺 `vmlinux`），与功能无关

`gcc-12` 在系统里现成存在（`/usr/bin/x86_64-linux-gnu-gcc-12`），无需安装。

## 4. 安装命令

前置状态已确认干净：**无 nouveau、无残留 nvidia 模块/库、无 nvidia-installer、`/sys/module/` 下无 nvidia**。
所以不需要 `--disable-nouveau`，保持最小改动。

```bash
cd <workdir>/drivers/525.116.03
sudo env CC=gcc-12 sh ./NVIDIA-Linux-x86_64-525.116.03.run \
     --silent --no-questions
```

要点：

1. **`env CC=gcc-12`** 必须写在 `sudo` 之后——`CC=gcc-12 sudo sh ...` 会被 sudo 剥掉。
   这是本轮的根因修复。
2. **不加 `--dkms`**：dkms 会用自己的编译流程，可能又走默认 `cc`（gcc-14），二次踩坑。
   研究机短期用，编当前内核即可。
3. 不加 `--disable-nouveau`：nouveau 当前未加载，无冲突。
4. `--silent` 下失败不会停在那里等输入，日志在 `/var/log/nvidia-installer.log`。

装完 **必须重启**（内核模块需重新加载）。重启后三个已知环境陷阱（见报告 11 §1）：

| 陷阱 | 表现 | 处理 |
|---|---|---|
| Xwayland 授权 | `glxinfo` 报 `Authorization required` | 脚本已自动 `export XAUTHORITY=$(ls -t /run/user/1000/xauth_* \| head -1)` |
| `perf_event_paranoid` | 新内核重置为 3，perf 采不到样且不报错 | `e4_window.sh` 内自动降为 1、结束恢复 |
| 休眠封锁 | 手动设置随重启失效 | 需重新挂（或用户手动） |

## 7. 方法论增量（并入 README 铁律的候选）

**用 .run 安装闭源驱动时，必须显式钉住 `CC`，且与内核的编译器同大版本。**

本案内核是 `gcc-12`，系统默认 `cc` 已是 `gcc-14`（Debian 13/14 的默认）。
这类失败的特征是：

1. 报错**指向符号**（`modpost ... undefined!`），而根因在**工具链版本**；
2. 只在模块链接阶段爆，`conftest` 全过，给人"这版驱动不兼容新内核"的错觉；
3. 换个 gcc 就好，驱动版本本身没问题。

→ 排查顺序应该是：**先读 CC 版本警告 → 再读真正的 make 错误 → 最后才怀疑驱动与本核的兼容性**。

顺带一提，这也解释了为什么"525 装不上"的第一直觉（conftest 过不了 6.1 内核）是错的：
**conftest 全过了，卡在 modpost**。这与报告 12 预测的"conftest 大概率失败"相反，记录在案。
