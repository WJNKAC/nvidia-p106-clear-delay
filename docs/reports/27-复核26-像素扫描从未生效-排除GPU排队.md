## 1. 先认错：独立复核确认报告 26 是对的

我不看报告 26 的分析器，自己写 `verify26.py`（按 tid 分组、按时间做栈式配对，避开它 §7.2 说的索引错位陷阱），从 `c1_clean.script` 重算：

| 量 | 报告 26 声称 | 我独立重算 | 判定 |
|---|---|---|---|
| `glWaitSync` 中位 | 0.005 ms | **0.005 ms** | ✓ |
| `glReadPixels` | 0.119 ms | **0.119 ms** | ✓ |
| `usleep` | 26.434 ms | **26.441 ms** | ✓ |
| `glMapBuffer` | 2.862 ms | **2.864 ms** | ✓ |
| `sem_wait(relsem)` 主线程 | 22.000 ms | **22.009 ms** | ✓ |
| **D = mb_out−rp_out** | 29.369 ms | **29.369 ms** | ✓ |
| **msw_out − rp_out** | 0.057 ms | **0.0570 ms** | ✓ |

**报告 26 全对。报告 25 §3「24.77ms 基本全在 glWaitSync」是错的**（已给它加作废横幅，逐条列明）。

### 1.1 我为什么会错（三条，已写入技能）

1. **数量级自相矛盾没抓住（最要命）**：我自己测出 `sem_wait` = 26.92ms，又断言"在 glWaitSync"。但 worker 本轮 `glWaitSync+glReadPixels` 合计仅 **0.124ms**——**26.9ms 装不进 0.12ms，差 200 倍**。这个矛盾当时就摆在数据里。
2. **把异步流水线的相位搞错了**：以为主线程等的是 worker **本轮**；实际 worker 是循环的，主线程相位**落后一轮**，等的是 worker 上一轮的尾巴（usleep+map）。
3. **有能直接测的量却用推理**：`ws_in`/`ws_out` 两个探针就能夹住 `glWaitSync`，我给 glcore 的 `wait_ms`、`sem_wait`、`usleep` 都挂了探针，**唯独漏了最关键的 glWaitSync**。

## 2. 查出两轮实验的共同前提是坏的：分辨率参数从未生效

复核报告 21（T4 像素扫描）和报告 25 §5.1（525 分辨率扫描）时，我怀疑参数没生效，于是直接验证：

```
heaven 启动参数: ... -video_width 960 -video_height 540
日志:           Set 1920x1080 windowed video mode     ← 忽略了我的参数
xdotool 几何:    1920x1080
```

**`-video_mode 6` 覆盖了 `-video_width/-video_height`。** 加 `-video_mode 0` 才能改：

| 参数 | 实际分辨率 |
|---|---|
| `-video_width 960 -video_height 540` | **1920×1080**（参数被忽略） |
| `-video_mode 0 -video_width 960 -video_height 540` | **640×360** |
| `-video_mode 6`（一直在用的） | 1920×1080 |

### 2.1 后果：两条"已确立事实"其实从未被测

- 报告 21「像素降 4 倍 fps 不变（108.7→108.1），回读不是真凶」→ **三档全是 1080p，测的是同一件事**
- 报告 25 §5.1「26.92/25.98/27.24ms，与像素量无关」→ **三档也全是 1080p**

**"与像素量无关"这个被反复引用的结论，从头到尾没有真实测过。**
（报告 21 里那句 fps 完全不变，其实是"同一配置重复三次"的正常波动。）

> 教训：**跑参数扫描前，必须验证参数真的生效**（日志/窗口几何/一处独立读数）。
> 一个被忽略的参数会让"扫了三档"变成"同一档跑三次"，而结果看起来非常"稳定"——这正是它骗过两轮的原因。

## 3. 真做一次像素扫描：D 只降 31%，并拟合出 2ms 固定项

用 `-video_mode` 真改分辨率，17 探针采 D（每组 10s）：

| video_mode | 实际分辨率 | 像素 | `glMapBuffer` | `usleep` | **D** | 帧数/10s |
|---|---|---|---|---|---|---|
| 6 | 1920×1080 | 2.07 M | **3.099 ms** | 27.997 | **31.091 ms** | 190 |
| 0 | 640×360 | 0.23 M | **2.165 ms** | 19.149 | **21.265 ms** | 462 |

**像素降到 1/9，D 只从 31.09 降到 21.27（−31%）。**

对 `map_time` 两点拟合：

```
3.099 = a + b × 2.07
2.165 = a + b × 0.23
→ b = 0.51 ms/Mpx，  a = 2.05 ms

map_time = 2.05ms（固定） + 0.51ms/Mpx × 像素
D = 10 × map_time         （autosleep 的 IIR 放大）
```

验算：1080p 10×(2.05+1.06)=31.1 ✓；640×360 10×(2.05+0.12)=21.7 ≈ 21.3 ✓

**这解释了为什么降分辨率救不了 525：有个 2.05ms 的固定项，占了 1080p map_time 的 66%。**

## 4. 隔离测试的对比：那个 2ms 固定项是 primus/525 语境特有的

同一台机、同一驱动，用 `rb_lat2` FBO 模式（隔离、单线程、无 usleep）扫分辨率：

| 分辨率 | 像素 | D (=map_time) | 折算带宽 |
|---|---|---|---|
| 1920×1080 | 2.07 M | **2.527 ms** | 8.3MB / 2.527ms = **3.28 GB/s** |
| 1280×720 | 0.92 M | **1.348 ms** | 3.69MB / 1.348ms = 2.74 GB/s |
| 960×540 | 0.52 M | **0.754 ms** | 2.07MB / 0.754ms = 2.75 GB/s |
| 480×270 | 0.13 M | **0.197 ms** | 0.52MB / 0.197ms = 2.63 GB/s |

**严格 ∝ 像素量，带宽稳定 2.6~3.3 GB/s。** 拟合 `0.05ms + 1.2ms/Mpx`——**几乎没有固定项，纯带宽。**

### 4.1 PCIe 是 Gen1，所以 2.7GB/s 就是上限

```
nvidia-smi --query-gpu=pcie.link.gen.current,pcie.link.gen.max,pcie.link.width.current
→ 1, 1, 16        ← Gen1 ×16，最大也只有 Gen1
```

Gen1 ×16 有效带宽约 3.2 GB/s。**实测 2.7 GB/s 是硬件极限，不是"回读变慢"。**

### 4.2 两边一比，问题就清楚了

| | 固定项 a | 带宽项 b |
|---|---|---|
| 隔离 FBO（rb_lat2） | **0.05 ms** | 1.2 ms/Mpx |
| primus 里（§3） | **2.05 ms** | 0.51 ms/Mpx |

**primus 的 map 多出 ~2ms 固定开销，且带宽项反而更低（说明真实拷贝时间被这个固定项掩盖/并行掉了）。**

这 2ms 与像素无关、与 GPU 负载无关（§5）、与 vblank 无关（报告 24）→ 是一个**纯粹的同步/协议开销**。
2ms ≈ 2 × 1ms，而报告 23 已知驱动有 **1ms 轮询线程**。

**这是目前最具体的靶点：525 在 `glMapBuffer`（或它触发的 flush）处有约 2ms 的固定等待。**

## 5. 排除「GPU 忙导致拷贝排队」：报告 26 的主嫌被推翻

报告 26 §6 把「GPU 忙 → 拷贝排队/铺开」列为主嫌（◑）。我写了 `rb_lat3.c`：
在 `glReadPixels` 之后**立刻提交 K 批全屏渲染**（模拟主线程 57µs 后醒来渲染下一帧），再 map。

| K（后续渲染批次） | 后续渲染 GPU 时长 | **D（map 等待）** |
|---|---|---|
| 0（对照） | 0.001 ms | **2.593 ms** |
| 4 | 1.739 ms | 2.546 ms |
| 16 | 6.433 ms | 2.507 ms |
| **48** | **19.510 ms** | **2.456 ms** |

**让 GPU 满负荷跑 19.5ms 的后续渲染，D 一点没变（甚至略降）。**

再用 `--nofinish`（不清空起点，队列持续积压）复测：K=48、burden 19.5ms，**D 仍是 2.624ms**。

→ **拷贝命令不受后续渲染阻塞，拷贝引擎与图形队列独立。**
「GPU 忙导致拷贝排队」这条**在隔离条件下被明确排除**。

> 保留的余地：真实场景是**双线程 + 两个 context**，我的测试是单线程单 context。
> 若仍要查队列效应，需要写双线程版本（下一步候选）。但就"后续渲染是否拖慢拷贝"这个具体机制而言，答案是否。

## 6. 一个意外发现：map 前插入 usleep 会让 map_time 掉到 6µs

给 `rb_lat3` 加 `RL3_SLEEP`（在 `glReadPixels` 与 `glMapBuffer` 之间睡）：

| readPixels→map 之间 | map_time |
|---|---|
| 无 usleep | **2.498 ms** |
| usleep(26000) | **0.006 ms** |

**睡了 26ms 之后 map 几乎秒回**——因为数据在睡眠期间就传完了。

**但 primus 真的在 map 前睡 27.997ms，map_time 却是 3.099ms。**

差异找到了：**我的测试在 readPixels 之后调了 `glQueryCounter`（会 flush 命令队列）；而 primus 的 worker 在 usleep 期间没有任何 GL 调用 → 不 flush → 拷贝根本没开始。map 才触发 flush，于是 map_time 里包含"flush + 拷贝"。**

这与报告 26 §4 的 `pbo_watch` 观测（"84% 在 usleep 中段落地"）**冲突**。
而 `pbo_watch` 用的是 `/proc/uptime`，**分辨率只有 10ms**（报告 26 §4.1 自己标注了）。
16.5ms ± 10ms 覆盖 [6.5, 26.5]，"在 usleep 中段落地"**很可能是量化伪影**。

→ **建议重测数据落地时刻，用 µs 级时钟（clock_gettime 而非 /proc/uptime）。** 这能一锤定音区分：
- 若数据真在 map 时才传 → map_time 就是"flush+拷贝"，2ms 固定项在 flush 里
- 若数据真在 usleep 中段到 → 那 2ms 是 map 自身的协议开销

## 8. 下一步（按价值）

| 优先级 | 动作 | 能答什么 |
|---|---|---|
| **1** | **µs 级重测数据落地时刻**（`clock_gettime` + PBO 轮询，不用 /proc/uptime） | 数据是在 usleep 期间到，还是 map 时才到。**这决定 2ms 固定项在 flush 还是 map** |

### 9.1 两个必须记住的坑

1. **`-video_width/-video_height` 会被 `-video_mode` 忽略**。改 heaven 分辨率必须用 `-video_mode N`（0→640×360，6→1920×1080），且**每次都要用窗口几何或日志复核**。

3. **`perf record -o /tmp/c1.data` 若 `/tmp/c1.data` 属主是 root**，desktop 无法覆盖 → **静默复用旧数据**（我第一次就中招：两个 script 字节数完全相同）。
