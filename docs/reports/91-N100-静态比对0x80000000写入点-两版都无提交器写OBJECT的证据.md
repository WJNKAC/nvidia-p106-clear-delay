# 91 · N100：静态比对 `0x80000000` 写入点 —— **两版都没有"提交器在批次断开处写 OBJECT"的证据**

日期：2026-10-26 15:10
对象：两版 `libnvidia-glcore.so`（515.105.01 / 525.116.03，均已从 .run 解出）
方法：字节级搜索 + objdump 上下文 + 按 **demmt/pushbuf.c 的官方解码规则**复算命令字
（用户建议 Ghidra：本任务只需字节定位与短上下文，objdump 更快；Ghidra 的价值在需要函数边界时）

---

## 0. 结论（含对报告 90 的更正）

1. **更正报告 90 的解码**：`0x80000000` 不是"非增量 count=1 method 0"，
   按 demmt 的规则（`mode=(w>>29)&7`；`method=(w&0x1fff)<<2`；`subchan=(w&0xe000)>>13`；`size=(w>>16)&0x1fff`）：

| 命令字 | 正确解码 |
|---|---|
| `0x80000000` | **mode 4 = 单条 method 写入（data 在头里）**：subchan 0、**method 0x0000、data 0** |
| `0x20010d2a` | mode 1（增量，size 在头里）：method 0x34A8、size 1 → 后跟 2 个数据字 `80000000 80000587` |
| `0x80110810` | mode 4：method 0x2040、data 17 |
| `0xa0050e04` | mode 5（增量）：method 0x3810、size 5 |

   ⇒ `80000000` **确实是**一条"method 0x0000 ← 0"的命令（puller 表里 0x0000 = OBJECT），
   但**data=0**（不是绑定某个具体对象句柄），更像"解绑/批次标记"。

2. **静态搜索不支持"525 特有"**：

| 搜索 | 525 | 515 |
|---|---|---|
| 字面量 `movl $0x80000000,(%rax/%rcx/%rdx/%rbx/%rsi/%rdi)` | **7 处** | **5 处** |
| 其中位于提交/批次路径的 | **0**（7 处上下文分别是数组初始化、`memset` 式循环、符号扩展钳位） | **0** |
| 通用头构造 `or reg,0x80000000`（mode4 发射器） | **114 处** | **117 处** |

   **⇒ 两版都没有"提交器在批次断开处直接写 0x80000000"的代码**；
   `80000000` 是**通用发射器**按 method 号生成出来的，两版的发射器数量与形态一致（114 vs 117）。

3. **因此报告 90 的推断要降级**：
   - 已证：525 的命令流里，**每 224 字节（56 字）单元恰好一条 `method 0x0000 ← 0`**；
   - 未证：**515 是否也这样**（这需要跑 515 抓流，静态比不出来，因为发射器是通用的）；
   - 未证：`method 0x0000 ← 0` 的语义（是"解绑对象"还是"批次标记"）。

## 1. 为什么静态比不出来（方法学结论）

`0x80000000` 这类命令头**不是常量写死**的，而是：
```c
header = 0x80000000 | (method >> 2) | (data << 16);
```
所以同一段代码既写 `80000000`（method 0，data 0）也写 `80000587`（method 0x161C，data 0）、
`80110810`（method 0x2040，data 17）——**差异在 method 号参数里，不在立即数里**。
想静态判断"515 是否也发这条命令"，必须定位**发射器**并看它的调用点，而不是搜立即数。

**可行的静态替代**：找到 `or reg,0x80000000` 的通用发射器（114/117 处里挑出被大量调用的那个），
再统计它的调用点里有没有"method=0 且 data=0"的常量组合——工作量较大，收益低于直接跑 515。
