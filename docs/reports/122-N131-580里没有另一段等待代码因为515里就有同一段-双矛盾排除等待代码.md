# 报告 122 / N131：**580 里没有"另一段等待代码"—— 因为 515 里已经有和 525 一模一样的那段**

> 时间：2026-10-26
> 方式：**纯本地静态**（未连接 <user>，未改动任何文件）
> 触发：用户「静态抓 580 的现行（纯本地）… 580 里一定有另一段代码在执行这个每批次等 121µs 的逻辑。去找 580 的 glcore 里，有没有类似 525 里那个"写 dirty → 消费 dirty → 等待"的循环。对比 515 是怎么处理 M6 这种情况的。」
> 结论：**前提不成立。等待代码在 515 里就存在，而且和 525 的包装函数逐条对应。两个独立矛盾把"等待代码本身"彻底排除。**

## 0. 先回答第一个问题：580 的转储

| 文件 | 大小 | 架构 | 可用性 |
|---|---|---|---|
| `full-515.105.01.asm` | 137 MB | **elf64** | ✅ |
| `full-525.116.03.asm` | 308 MB | **elf64** | ✅ |
| `full-535.129.03.asm` | 334 MB | **elf64** | ✅ |
| `full-580.126.18.asm` | 202 MB | **elf64** | ✅ |
| `full-580.178.04.asm` | 126 MB | **elf32-i386** | ⚠️ **32 位，错的目标** |

**`full-580.178.04.asm` 是从安装包的 `32/libnvidia-glcore.so` 转的**，架构不对，直接拿它对比会得到一堆假的"结构差异"。

**修法**（本轮已做）：不必重转 200MB 转储 —— 直接从 64 位 `.so` 上用 `objdump --start-address/--stop-address` 定点反汇编即可。
但前提是**得先知道地址**，而 glcore 是 stripped 的。于是本轮补了一个新工具（见 §1）。

## 1. 新工具：从 `.eh_frame_hdr` 还原函数边界

stripped 的 `.so` 没有 symtab，也**没开 CET**（没有 `endbr64` 可扫，我试了，0 个）。
但 `.eh_frame_hdr` 里有一张**已排序的 FDE 二分表**，每个 FDE 对应一个函数。

```
$ python3 n131b_ehframe.py libnvidia-glcore.so.525.116.03 --callers 0x146d280
# .eh_frame_hdr: ver=1 enc_frame=0x1b enc_count=0x3 enc_table=0x3b count=79245
# 函数数 = 79245  首个 0x2d93f0 末个 0x1952e40

函数 0x146d280 起=0x146d280 终=0x146d3a0 长=288 B
直接 call 处数 = 3
```

| 版本 | 合成函数数 |
|---|---|
| 515.105.01 | 58,145 |
| 525.116.03 | 79,245 |
| 580.126.18 | 46,990 |
| 580.178.04 | 46,993 |

（`enc_frame=0x1b`=sdata4|pcrel，`enc_table=0x3b`=sdata4|datarel，datarel 基准是 `.eh_frame_hdr` 段起点。）

**这个工具是本轮最有复用价值的东西** —— 以后任何 stripped `.so` 都能直接查"某个地址属于哪个函数、被谁调用"。

## 2. 各版本 `wait_ms` 的确切地址（后续动态实验可以直接用）

| 版本 | `wait_ms` 起址 | 长度 | 特征指令位置 |
|---|---|---|---|
| 515.105.01 | **0xeb8b90** | 304 B | 0xeb8b92 |
| 525.116.03 | **0x146d280** | 288 B | 0x146d291 |
| 535.129.03 | **0x1511280** | — | 0x1511291 |
| 580.178.04 | **0xa103f0** | 288 B | 0xa10401 |
| 580.126.18 | **0xa102f0** | 288 B | 0xa10301 |

函数体的语义（三版一致，已逐条核对）：

```
push r14/r13/r12/rbp/rbx
movslq %esi,%r13            ; ms 参数
lea 0x30(%rdi),%r12         ; mutex 在对象 +0x30
imul $0x10624dd3 / sar $0x26 ; ms/1000 → 秒
imul $0xf4240               ; ms*1e6  → 纳秒
call gettimeofday
imul $0x3e8, usec           ; usec→nsec
cmp $0x3b9ac9ff             ; nsec 溢出检查
call *(...)                 ; pthread_cond_timedwait
```

**525 与 580 的 `imul $0x10624dd3,%r13,%r13` 是逐字节相同的指令（`4d 69 ed d3 4d 62 10`）。**

## 3. 决定性的一步：两个独立矛盾，把"等待代码"排除

我原以为会看到"525/580 有、515 没有"的东西。**实际拿到的是相反的。**

### 3.1 515 与 525 的 wait **包装函数**逐条对应

515 `0xeba100`（320 B）vs 525 `0x146ec00`（320 B）：

```
                         515 0xeba100           525 0x146ec00
push r12 / rbp / rbx      ✓                        ✓
mov  $0x1,%ebp            ✓                        ✓
sub  $0x30,%rsp           ✓                        ✓
call <helper> ×2          eba0c0 ×2                146e8e0 ×2
存到 0x20/0x28(%rsp)      ✓                        ✓
构造 timespec + 间接调用    ✓                        ✓
mov  $0x2,%esi            eba142  ●  ms=2           146ec42  ●  ms=2
call wait_ms              eba147                   146ec47
mov  $0x3e8,%ebx          eba167  ●  重试 1000 次   146ec67  ●  重试 1000 次
mov  $0x1,%r12d           ✓                        ✓
循环: wait_ms(...,2)      eba18c                   146ec8c
test/cmove %r12d,%ebp     ✓                        ✓
sub $1,%ebx; jne          ✓                        ✓
```

**同 ms=2、同 1000 次重试、同 `cmove` 判成功、同栈布局。只有指令调度顺序不同。**

### 3.2 两个矛盾

| | 515 | 525 | 580.178.04 |
|---|---|---|---|
| `wait_ms` 长度 | 304 B | 288 B | 288 B |
| **包装函数** | 320 B，**同 525** | 320 B | **496 B（另一支，ms=60）** |
| 9 连 pause 自旋 | **1 处** | **1 处** | **1 处** |
| `wait_ms` 直接调用点 | 3 | 3 | 3 |
| **实测** | **快（K 无关）** | **慢（121.8µs/对）** | **慢** |

- **矛盾一（515 vs 525）**：包装函数**几乎相同**，行为却完全不同 ⇒ 包装函数不是原因。
- **矛盾二（525 vs 580）**：包装函数**不同**（320 B vs 496 B，ms=2 vs ms=60），行为却相同 ⇒ 包装函数也不是原因。

**两条互相独立的反向矛盾，唯一交集是"等待代码无关"。**

**⇒ 你假设的"580 里一定有另一段代码在等"—— 不成立。515 里就已经有同一段代码了。**

## 4. 为什么"找一段新增代码"这个方法本身会失效

跨版本搜 `wait_ms` 的代码生成形态，得到一个**完美对应症状的指纹**：

| 版本 | `imul` 型（新） | `mov` 型（旧） | 实测 |
|---|---|---|---|
| 515.105.01 | 0 | **2** | 快 |
| 525.116.03 | **1** | 0 | 慢 |
| 535.129.03 | **1** | 0 | 慢 |
| 580.178.04 | **1** | 0 | 慢 |

```
旧型（515）：mov $0x10624dd3,%edx ; imul %edx
新型（525+）：imul $0x10624dd3,%r13,%r13
```

**这不可能是"原因"，它只是编译器/编译选项的指纹。** 但它说明了一件重要的事：

> **glcore 在 515→525 之间被整体重编译了。**

这与报告 111 在**内核 RM** 上的结论完全一致（"规范化机器码哈希对齐：20703 个函数里骨架相同只有 1 个"）。
**⇒ 两个库里都不存在"在某函数里插几行"这种形态，指令级 diff 找"新增的等待循环"注定一无所获。**

这条值得单独记住：**整体重编译会让"按差异找代码"整类方法失效**，只能改用"结构/行为/计数"的判据。

## 5. 静态这边到此为止：触发频率数不出来

想量化"谁在什么时机调 wait"，失败了，三条路都堵：

| 尝试 | 结果 |
|---|---|
| 直接 `call` 指向包装函数 | **0 处**（515/525/580 全是 0） |
| `jmp`（尾调用）指向包装函数 | **0 处** |
| 8 字节绝对函数指针登记 | **0 处** |

**⇒ 它是被热冷分割拆出去的冷块，或经 vtable 间接进入。静态无法定位触发者。**

这一点必须明说：**我没有找到机制。** 我只证明了"机制不在等待代码里"。

## 6. 关于你问的"515 怎么处理 M6"

**静态上我给不出答案** —— 因为 515 里存在与 525 完全相同的 wait 包装函数，
M6（绑同一个 program 再画）和 M3（绑不同）在 515 里走的是同一条路，而 515 两条都免费（平坦）。

能确定的只有实测事实：

| | M3（绑不同） | M6（绑同一个） |
|---|---|---|
| 515 | 5.27 ms @K=1000 | 5.26 ms，同量级 |
| 525 | 126.99 ms | **268.00 ms**（报告 119 测到 128.45，**两次不一致**） |
| 580 | 慢 | 慢 |

**M6 = 2.1×M3 这件事本身与"不检查状态是否真的变了"矛盾**（若不检查，两者该相等）。
所以我倾向认为 **M6=268 那次测量不可靠**（报告 119 已标注存疑），暂不作为推理依据。

## 7. 下一步：唯一能出结果的是动态，而且地址已经齐了

静态把范围收窄到"**触发频率**"这一个变量。数频率要有地址，现在有了：

```sh
# 525：统计 wait_ms 被进入多少次（M1 vs M3 vs M6 vs M9）
sudo perf probe -x /usr/lib/libnvidia-glcore.so.525.116.03 --add 'wm=0x146d280'
sudo perf stat -e probe_libnvidia_glcore:wm -- ./n83a -M 3 -n 1000

# 515 同样做一次，地址 0xeb8b90
```

**判据（这一步是判决性的）：**

| 观测 | 结论 |
|---|---|
| 525 的 `wait_ms` 进入次数 ≈ 对数，515 ≈ 0 或每帧 1~3 次 | ⇒ 机制 = **多了一个每对一次的等待入口**，接下来只需找谁调它 |
| 两版进入次数都很少（每帧 1~3 次） | ⇒ **wait 彻底出局**，121µs 不是阻塞等待（与报告 114"CPU 在自旋"一致） |
| 525 有大量进入且每次 ≈121µs | ⇒ 直接闭环，连包装函数都不用找 |

同时用同一手法给 9-pause 自旋也挂一个探针（三版各有 1 处），两个计数一比就知道是"等"还是"转"。

> 这个实验比继续挖静态强得多：**它测的正是静态唯一给不出的那个量。**

## 8. 各条证据强度

| 结论 | 强度 | 依据 |
|---|---|---|
| `full-580.178.04.asm` 是 32 位，不可用于对比 | **强** | 文件头 `elf32-i386` |
| 580.178.04 的 `wait_ms` = 0xa103f0（288 B，3 个调用点） | **强** | eh_frame + 反汇编 |
| 525 与 580 的 wait 原语特征指令逐字节相同 | **强** | `4d 69 ed d3 4d 62 10` |
| **515 与 525 的 wait 包装函数逐条对应（同 ms=2、同 1000 次重试）** | **强** | 两段反汇编并列核对 |
| 525 与 580 的包装函数不同（320 B vs 496 B，ms=2 vs ms=60） | **强** | 同上 |
| **等待代码不是 121µs 的来源** | **强（双矛盾）** | §3.2 |
| glcore 在 515→525 间整体重编译 | **中强** | 代码生成指纹全量对应症状；同内核 RM 结论 |
| 触发者无法静态定位 | **强（负面）** | call/jmp/指针/reloc 四路全 0 |
| 121µs 的真正机制 | **未知** | 本轮未找到，不编 |

## 9. 一句话

**你让我去找"580 里另一段等待代码"—— 找的结果是：不用找，因为 515 里就有和 525 一模一样的。**
**515 与 525 的包装函数逐条对应（ms=2、1000 次重试、同样栈布局），可 515 是快的 ⇒ 等待代码不是原因。**
**525 与 580 的包装函数反而不同（320B/ms=2 对 496B/ms=60），可两者都慢 ⇒ 再证一次它不是原因。**
**glcore 从 515 到 525 整体重编译过（代码生成指纹与症状 100% 对应），所以"按指令差异找新增代码"这条路本身是死的。**
**静态能给的极限是：把范围收到"触发频率"一个变量上，并交给你四个可用的地址去数。**
