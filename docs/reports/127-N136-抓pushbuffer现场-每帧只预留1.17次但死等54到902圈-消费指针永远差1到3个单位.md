# 报告 127 / N136：**抓 pushbuffer 现场 —— 每帧只预留 1.17 次，但在里面死等 54~902 圈；消费指针永远差 1~3 个单位**

> 时间：2026-10-27
> 环境：<user>@<testhost>（`<testhost>`），P106-100，**525.116.03**，headless X `:2`
> 触发：用户「如果 525 每对要申请 108 次 pushbuffer 空间，那一定是某个环节在疯狂往队列里塞东西，或者 GPU 的消费指针根本不往前推。在 525 上直接抓 pushbuffer 的写入与消费现场」
> 方法：tracefs 手写 uprobe + 内存解引用（perf probe 的 fetchargs 对 uprobe 不支持）

---

## 0. 先纠正一个前提

**"每对要申请 108 次 pushbuffer 空间"这个说法不成立。**

`108.3 次/对` 是**自旋函数被进入的次数**，不是"预留空间被申请的次数"。

真实结构是两层：

```
每帧只调 1.17 次  「预留空间」函数（0x1578280）   ← 140 次 / 120 帧
         └─ 但这 1 次调用内部，循环 54 ~ 902 圈      ← 每圈 = 调一次自旋函数
```

| | 预留函数调用 | 帧数 | 次/帧 | 内部自旋圈数/帧 |
|---|---|---|---|---|
| M1 | 140 | 120 | **1.17** | 6,470 |
| M3 | 140 | 120 | **1.17** | **108,300** |

**⇒ 预留次数完全相同（140），差别全在"这一次调用里等了多少圈"。**

所以：**不是"疯狂反复申请"，是"申请一次之后卡在里面出不来"**。

---

## 1. 现场数据：三个量永远差一点点

在循环体起点（`0x15782d8`，即 `ja` 跳回的位置）挂探针，解引用读三个字段：

```
p:loop $SO:0x15782d8 rp=%bx wp=+0x1130(%bp):u64 sz=%r12 c1240=+0x1240(%bp):u64
```

> 注意：此处 `ctx` 在 **`%rbp`**，不在 `%rdi`（循环体里 `rdi` 已被改作他用）。
> 我第一次用 `%di` 读出 `wp=0`，是假的。

**实测（525 M3，n=200）**：

```
rp=0x22f(559)  wp=564  sz=0x232(562)  c1240=563
rp=0x22f(559)  wp=564  sz=0x232(562)  c1240=563
...（大量重复）
rp=0x238(568)  wp=572  sz=0x23a(570)  c1240=571
rp=0x239(569)  wp=572  sz=0x23a(570)  c1240=571
```

**恒等关系**：
```
c1240 = wp - 1        （全程成立，与静态初始化 `[0x1130]-1 → [0x1240]` 一致）
sz    = wp - 2        （全程成立）
rp    = wp - 3 ~ wp - 13   （在追，但没追上）
```

**放行条件**（由反汇编）：
```
rdx = wp - sz     ; = 2（恒定）
rcx = wp - rp     ; = 4 → 3 → ...
cmp rdx, rcx
jbe 返回          ; 空间"够" ⇔ rcx <= rdx ⇔ wp-rp <= wp-sz ⇔ rp >= sz
```

**⇒ 放行条件是 `rp >= sz`。实测 `rp` 永远比 `sz` 小 1~3，所以永远不放行。**

最后一条 `rp=569, sz=570` —— **差 1**。

**这就是"差一点点"的现场。**

---

## 2. 消费指针推不推？推，但慢

`rp` 在 27,588 次循环里从 **559 推到 569**，**推进 11 个单位**。

```
每次循环平均推进 = 11 / 27,588 = 0.0004 个单位
```

**⇒ 假设 2（消费指针不推进）部分成立：它在推，但推进速度比 CPU 的检查速度慢 4 个数量级。**

---

## 3. 关键反常：写入只多 1.5 倍，等待多 16.7 倍

抓每次"预留请求"的 `sz` 终值（140 次 req，n=1000）：

| 模式 | total_ms | req 次数 | sz 首值 | sz 末值 | **增长** | 每帧增长 |
|---|---|---|---|---|---|---|
| M1 | 7.173 | 140 | 0xe (14) | 0x23a (570) | **556** | 4.63 |
| M3 | 127.069 | 140 | 0x10 (16) | 0x352 (850) | **834** | 6.95 |

| 比值 | |
|---|---|
| 写入量（sz 增长） | M3 / M1 = **1.50×** |
| 等待圈数 | M3 / M1 = 108,300 / 6,470 = **16.7×** |

**⇒ 写入只多 50%，等待多 1570%。这是强非线性。**

**这个非线性本身就是"队列长期饱和"的指纹**：
- M1：生产略快于消费，队列不满，随时能拿到空间 ⇒ 少量自旋
- M3：生产持续快于消费，队列被填满并维持 ⇒ **每一次检查都发现不够，每次都要等一整轮**

**⇒ 用户的假设 1（往队列里塞得太多）方向对，但更准确的说法是"塞得比 GPU 消费快"，稳定饱和。**

---

## 4. 哪个操作导致饱和：切换，不是 draw

三组对照（n=1000，单事件）：

| 模式 | 内容 | spin/帧 | spin/对 |
|---|---|---|---|
| M1 | 1000 draw，无切换 | 6,470 | **6.47** |
| M8 | 1000 切换，无 draw | 2,285 | **2.29** |
| M3 | 1000 切换 + 1000 draw（交替） | 108,300 | **108.30** |

**单独做任何一件都不饱和（6.47 / 2.29），两件交替就爆到 108.30。**

**⇒ 不是 draw 本身、也不是切换本身，而是"切换 + draw 交替"这个组合把队列压满。**

这与 515 形成精确对照：515 做同样的事只要 **3.84 次/对**（报告 126 换算）。

## 5. sz 的单位是什么：未定

`sz` / `wp` / `rp` 三个量同步 +1、+6、+7 地增长，**它们不可能是字节数**：

- 140 次 req 覆盖 24,000 个 draw（n=200 × 120 帧），若单位是字节，总量只有 834 B，一个 draw 连 1 字节都不到 —— 不可能
- 若单位是 64 KB 块：M3 每帧 7 块 = 448 KB/帧 ⇒ 3.5 MB/s，与报告 120 实测的 60 MB/s 不符

**⇒ 更可能是"提交批次序号"或"槽位号"，不是字节偏移。**
**我没有确定它的单位，这是本报告最大的未定项。**

## 6. 一个必须说明的矛盾

n=200 时：
- 帧时间 **27.6 ms**
- 自旋 27,588 次 / 120 帧 = 230 次/帧
- 230 × 1.177 µs = **271 µs**

**271 µs 只占 27.6 ms 的 1%。**

但 n=1000 时：
- 帧时间 127 ms
- 自旋 108,300 次/帧 × 1.177 µs = **127.5 ms**，占 **100%**

**⇒ 这个函数的占比随 n 剧烈变化：n=200 时 1%，n=1000 时 100%。**

这说明它**只在队列饱和时才成为主成本**。n 小的时候饱和不成立，主干在别处（本轮未查）。

**这也是"饱和"模型的强证据，但它意味着：要解释"为什么 525 慢"，不能只看这个函数，还得看"为什么 525 在 n=1000 时会饱和而 515 不会"。**

## 7. 各条证据强度

| 结论 | 强度 | 依据 |
|---|---|---|
| 预留函数每帧只调 1.17 次（不是每对） | **强** | 单事件 perf，140/120，M1/M3 相同 |
| M1/M3 预留次数完全相同（140） | **强** | 同上 |
| 放行条件 = `rp >= sz` | **强** | 反汇编 + 现场三值 |
| 实测 `rp` 永远比 `sz` 小 1~3 | **强** | 27,588 条现场记录 |
| `rp` 推进 11 个单位 / 27,588 圈 | **强** | 首尾对比 |
| `c1240 = wp - 1`、`sz = wp - 2` | **强** | 全程恒定关系 |
| 写入 1.5× / 等待 16.7× 的非线性 | **强** | 两模式对照 |
| M1/M8/M3 = 6.47 / 2.29 / 108.30 ⇒ 组合才饱和 | **强** | 单事件三组 |
| 该函数占比 n=200 时 1%、n=1000 时 100% | **强** | 时间闭合两档 |
| `sz` 的单位 | **未定** | 三种假设都与实测矛盾 |
| n=200 时主干在哪 | **未查** | 本轮未测 |

## 8. 一句话

**你的两个假设各对一半：不是"疯狂反复申请"（每帧只申请 1.17 次），而是"申请一次就卡在里面"。**
**卡的原因正是你说的第二条：消费指针 `rp` 在推，但每次检查它都还差 1~3 个单位（放行条件是 `rp >= sz`，实测最后一条 `rp=569, sz=570`）。**
**而真正的反常是：M3 只比 M1 多写 1.5 倍，却多等 16.7 倍 —— 这是队列稳定饱和的指纹，不是线性变慢。**
**组合也清楚：单独 draw（6.47）或单独切换（2.29）都不饱和，两者交替（108.30）就爆。**
**下一步该问的不再是"它在等什么"，而是"为什么 525 让队列饱和而 515 不会"——那要去数两个版本每帧往队列里到底塞了多少字节，而 `sz` 的单位我还没定出来。**
