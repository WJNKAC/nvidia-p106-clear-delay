# 77 · N87-C：121µs 的机制归属（静态定位成功，活体计数受阻于三重障碍）

日期：2026-10-26 11:55
驱动：525.116.03（P106-100，1920×1080，直连 NVIDIA）
本轮目标：**在 glcore 里找出"状态变更 → 批处理 flush"那条路径，定位 121µs**

---

## 0. 结论分三层

| 层 | 结论 | 强度 |
|---|---|---|
| **① 代码位置（静态）** | 121µs 的落点是**统一命令提交器 `glcore+0x1238920`**；它内部有 `sfence`（`+0xa3`）与 `wait_ms` 调用（`+0x1b1`）。**M9（不相邻）不收费 ⇒ 不相邻的状态变更根本不进这个提交器** | **强**（静态 + M9 双向印证） |
| **② 机制性质（已有数据推出）** | 是**GPU 侧、固定、与几何/队列深度均无关**的一次"批次开始"代价。**不是排队，不是填充，不是 CPU** | **强**（三条独立实验） |
| **③ 具体是哪条 GPU 操作** | **未能确定**。活体计数被三重障碍挡住（§3），这一层**诚实留空** | **无** |

**所以"121µs 在代码里的位置"这个问题，答到了"提交器"这一层，没能再往下切。**

## 1. 静态定位：121µs 的落点是统一提交器

### 1.1 提交器里的三条关键指令（525，`glcore+0x1238920`）

```asm
1238996: movss xmm0,[ctx+0x8e0c60]      ; 时间/字节累加器
12389bb: add   dword [ctx+rax*8+0x8e0c00],1   ; 计数器
12389c3: sfence                          ; ★ 内存屏障（+0xa3）
1238a28: cmp   [ctx+0x8e0a00],[ctx]      ; 队列读==写？（空？）
1238a35: je    1238b48
1238a41: 三档 float 预算判据
1238ab1: cmp   byte [ctx+0x8e0c70],0
1238ab8: jne   12389d0                   ; ★ 重试回环
1238abe: rdi=[ctx+0x8e0908]
1238acc: esi=2                            ; 2ms 超时
1238ad1: call  [_nv014glcore+0x2d0]      ; ★ wait_ms（+0x1b1）
1238b31: test  byte [_nv026glcore+0x8f0+0xc08],2   ; flags gate
```

三条可用的静态事实：

1. **`sfence` 在提交器里**，不在各个 GL 函数里（`glMapBuffer` 只有 11 条指令，没有 fence）。
2. **`wait_ms(x, 2)` 也在提交器里**，且**在重试回环内**（`1238ab8: jne 12389d0`）。
3. **状态变更本身不写 `sfence`、不调 `wait_ms`** —— 它们只写一个 12/16/32 字节的命令包然后 `jmp` 到提交器（`glMapBuffer` 的 `0x617b` 包就是范例）。

### 1.2 M9 的双向印证：不相邻的状态变更**根本不进提交器**

报告 76 的 M9：**先切 1000 次、再画 1000 个 = 2.640ms（与完全不切相同）**。

这条静态与实验合起来只能有一个解释：
> 驱动在**还没有 draw 需要这个新状态时**，把状态变更记在 CPU 侧结构体里，**不调提交器**；
> 一旦有 draw 要用它（相邻），才调提交器把状态+draw 一起落地，于是付一次 121µs。

**⇒ 121µs 的"扳机"是提交器被调用，不是状态变更本身。**
这也解释了 M6（切到同一 program 仍 121µs）：驱动不做 no-op 检测，照样进提交器。

## 2. 机制性质：三条独立实验一致指向"GPU 侧固定代价"

| 证据 | 数据 | 排除了什么 |
|---|---|---|
| **CPU vs GPU** | submit 每对 **0.14~4.11µs**，map 每对 **119~124µs** | **不是 CPU 在算** |
| **几何量** | quad 19×19 → 1.5×1.5 像素（面积 ÷160），map **123.265 → 123.287（0.02%）** | **不是光栅化/顶点/填充** |
| **GPU 负载** | 1.5×1.5 像素时 GPU 几乎空闲，**仍是 121µs** | **不是排队/等队列排空** |
| **与变更数量** | M0(4 次)=121.6、M3(1 次)=120.7、M6(no-op)=121.0 | **不是"每次变更累加"** |
| **与 draw 总数** | 固定 1000 draw，c=0→2.635、c=1000→123.36 | **是"配对"事件，不是 draw 工作量** |

**⇒ 121µs = 提交器每被调用一次，GPU 侧执行一次"批次开始"的固定代价。**

按 1911 MHz 换算：

```
121 µs × 1911 MHz ≈ 231,000 GPU 周期
```

231k 周期、**与工作量无关**、**GPU 空闲时也一样** —— 这个形状只对应一类操作：
**管线/上下文级别的 flush + 状态重配**（cache invalidate、constant bank 重载、pipeline state object 重建之类）。

**这一层是有把握的推断，但具体是哪一项，本轮没测出来。**

## 3. 活体计数受阻：三重障碍（这是本轮的真实产出之一）

想把"提交器被调用多少次"数出来，三条路全部堵死。逐条记录，避免后人重走：

### 3.1 障碍一：glcore 的 uprobe 挂不上（libc 可以）

```
p:bis/cmalloc  /lib/x86_64-linux-gnu/libc.so.6:0xa28d0        → 命中 20,614 次 ✓
p:bis/cfree    /lib/x86_64-linux-gnu/libc.so.6:0xa2fc0        → 命中 ✓
p:bis/gmap     libnvidia-glcore.so.525.116.03:0x103a2b0       → 命中 0  ✗
p:bis/gsubmit  libnvidia-glcore.so.525.116.03:0x1238920       → 命中 0  ✗
```

**同一次采集、同一个 trace、同一套注册方式**：libc 命中两万次，glcore 零次。

已排除的可能：
- ❌ 路径/inode 不符：`ls -i` = 700270，`/proc/PID/maps` 里也是 `700270`，且路径字面相同
- ❌ offset 算法错：`.text` 段 vaddr == file offset（`0x2fc000/0x2fc000`），`0x1238920` 两者相等
- ❌ 事件未 enable：`bis/cmalloc/enable=1`、`bis/gmap/enable` 文件存在、`uprobe_events` 注册成功
- ❌ ftrace 坏：libc 探针在同一次采集里命中两万次

**推测（未证实）**：NVIDIA 驱动对自己的 `.text` 做了页级保护，内核 uprobe 插入 `int3` 失败但**静默返回成功**。

⚠️ **但报告 71 里同一个地址在 Heaven 进程下命中过 413 次** —— 所以这不是"绝对挂不上"，而是
**"在直连 NVIDIA 的进程里挂不上"**。这个差异本轮没查清。

### 3.2 障碍二：glvnd 返回的是 dispatch stub，不是 glcore 实现

在 n83a 里打印实际函数指针（`-V`）：

```
glMapBuffer       = 0x7f84332e0420  →  libGLdispatch + 0xc420
glBindFramebuffer = 0x7f84332d4880  →  libGLdispatch + 0x880
glReadPixels      = 0x7f84336dcac0  →  libGL.so.1   + 0x14ac0
glUseProgram      = (nil)           →  该次实例初始化未完成
```

**`glXGetProcAddress` 拿到的是 glvnd 的桩，不是厂商实现。**
这本身不致命（桩会跳到真身），但它意味着：
- 想"数 API 调用"不能挂应用拿到的指针
- 更麻烦的是，**maps 里连 `libnvidia-glcore` 都没出现**（`-V` 那次实例初始化未到最后一步）
  ⇒ 说明 glcore 是**惰性加载**的，进程早期还没映射

### 3.3 障碍三：`strace` 会彻底改变被测量的行为

```
正常：  M3 (-n 1000, 30 帧) → map = 123 ms
strace: M3 (-n 1000, 30 帧) → map =   9.274 ms     ← 差 13 倍
strace: M1 (-n 1000,600 帧) → map =   2.300 ms     ← 基线也偏低
```

而且 `strace -c -f -e trace=ioctl` 汇总出 **ioctl = 0**（明显不可能是真的 —— GL 驱动必然走 ioctl）。

**⇒ 在 strace 下测 GPU 时间，数据全部作废。** 原因是 strace 的 `ptrace` 让每次系统调用往返变慢，
反而给了 GPU 更多时间"追上来"，把等待掩盖掉了。

`perf stat -e syscalls:sys_enter_ioctl` 也返回空（输出文件为空），未深究。

## 4. 一个可以不用计数就得到的判据（补做）

既然数不到调用次数，可以换个问法：**121µs 是否随"提交器被调用的密度"变化？**

若 121µs 是"每次提交一次固定代价"，那么**两次配对之间插入更多无关 draw 不应改变每对成本**。
M7 已验证：固定 1000 draw，c=100 时 14.691ms、c=1000 时 123.360ms，
`(123.360−14.691)/(1000−100) = 120.7µs` —— **每对成本恒定，与中间夹了多少 draw 无关。**

**⇒ 提交器不是"攒批到某个阈值才刷"，而是"被调用就付一次"。** 这条已经从数据确认，不需要 uprobe。

## 5. 这轮的诚实结论

**用户的原始目标（"定位 121µs 在代码里的位置"）只答到一半：**

- ✅ **落点确定**：统一提交器 `glcore+0x1238920`，且只在"状态变更与 draw 相邻"时被调用
- ✅ **性质确定**：GPU 侧、固定 ~231k 周期、与几何/负载/变更数量/队列深度全部无关
- ❌ **具体 GPU 操作未确定**：需要 uprobe 数提交器调用次数（受阻）或 GPU 侧计数器（nvidia-smi 无此能力）

**并且这轮产生了一个重要的负面结果**：在这个环境里，**glcore 的 uprobe 在直连 NVIDIA 的进程中挂不上**，
而 libc 可以。这意味着**以后想对 NVIDIA 驱动内部计数，不要走 ftrace uprobe**，要换思路
（例如：用 `LD_PRELOAD` 拦截 glvnd 桩、或改 primus、或用 `nvidia-smi dmon` 的 GPU 侧指标）。

## 6. 下一步：还是那一个数

N87-C 没有推翻报告 76 的任何结论，也没有把 121µs 再切细。
**唯一能推进的仍然是换 515 测那个数**：

```
525: n83a -M 1 → 2.64 ms    n83a -M 3 → 123.35 ms
515: n83a -M 1 → ?          n83a -M 3 → ?     （预测 34 ms）
```

| 515 的 `-M 3` | 判读 |
|---|---|
| **≈ 34 ms** | 配对成本 **31.3µs vs 120.7µs**，**3.9 倍 = 3 倍差距的全部**，案子收口 |
| ≈ 123 ms | 两版配对成本相同 ⇒ **121µs 与版本差异无关**，靶点必须回到"每帧配对数"（Heaven 的 pass/材质数） |
| 其它 | 按 `(M3−M1)/1000` 算每对成本，再用 `32.44ms ÷ 该值` 反推配对数，与 Heaven 实际结构比对 |

**换驱动会黑屏几分钟，需要你在场。** 这是目前唯一剩下的一步，且它只需要**两个数字**。

### 7.1 方法论（已入技能库）

1. **★ uprobe「注册成功」≠「能命中」**：必须做二分对照（同一 trace 里挂一个肯定被调用的 libc 函数）。
   本例 libc 命中 20614 次、glcore 0 次，一次采集就定位到"是 glcore 挂不上"而非"环境坏了"。
2. **★ 应用拿到的函数指针要通过 `/proc/PID/maps` 反查归属**：glvnd 下它是 dispatch stub，
   不是厂商实现，也不是 `libGLX_nvidia` 的导出 thunk。
3. **★★ `strace`/`ptrace` 会改变 GPU 等待的测量结果**（本例 123ms → 9.3ms，差 13 倍）。
   测 GPU 等待时**绝对不要**用 strace 包裹被测进程；要计数就用 `perf stat` 或在被测进程内埋点。
4. **★ 数不到次数时，改用"密度不变性"**：M7 的"每对成本与中间夹多少 draw 无关"
   同样能证明"被调用就付一次"，而且不依赖任何探针。
