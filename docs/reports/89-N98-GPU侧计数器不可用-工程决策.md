# 89 · N98：GPU 侧计数器不可用（三条路全封）+ 工程决策

日期：2026-10-26 14:35
驱动：525.116.03

---

## 1. GPU 侧计数器：三条路都不可用

| 途径 | 结果 |
|---|---|
| **Nsight Systems GPU Metrics**（`--gpu-metrics-devices`） | **明确拒绝**：`Pascal GP106 \| NVIDIA P106-100 PCI[0000:01:00.0] - Unsupported architecture` |
| **PerfKit / CUPTI / ncu / DCGM** | 机器上**都没有**：无 `libnvperf_host/target`、无 `libcupti`、无 `ncu`、无 `dcgmi`/`nv-hostengine`（只有 `nsys`） |
| **nsys OpenGL GPU range** | `SKIPPED: does not contain GPU KHR Extension (KHR_DEBUG) data`；sqlite 里也没有任何 GPU activity 表（只有 ENUM 表） |
| `nvidia-smi` | 只有聚合 `utilization.gpu` / `utilization.memory` / `power.draw` / `clocks`，无分引擎计数器 |

⇒ **在这块 P106（Pascal）+ 525 上，"看 GPU 内部哪个引擎在动"这件事没有工具支持。**
现有最强证据仍是三条间接量：`util.gpu=99%`、`util.memory=0%`、`power=37.7W`。

## 2. 工程决策（按代价从低到高）

### 决策 0：不要在 525+ 上"修"这个现象

它不是一个可配置项（regkey 32 位 + env 全试无效），也不是应用 API 能绕的（无对应开关），
更不是数据/带宽问题（mem util 0%）。**它是 525 起 GL 驱动对"批次断开"的串行化行为。**

### 决策 1（推荐）：GL 负载留在 515.105.01，或改走 Vulkan

| 方案 | 实测 | 代价 |
|---|---|---|
| **515.105.01 + GL** | Heaven 1080p **101 fps**（vs 525 的 34 fps） | 降级驱动，已有验证过的安装脚本 |
| **Vulkan 后端** | **358 fps / 37 W**（报告 07） | 应用侧改后端；Vulkan 提交模型不受该批次串行化影响 |
| 525 + GL | 34 fps | — |

### 决策 2（必须留在 525+ 时的唯一杠杆）：减少每帧"批次断开"次数

**定量关系**（报告 83 §2bis，六点线性）：`帧时间 ≈ 2.6ms + 122µs × 批次数`。

| 每帧批次数 | 1080p 帧时间 | fps |
|---|---|---|
| 268（Heaven 现状） | 32.4 ms | 31 |
| 200 | 27.0 ms | 37 |
| 100 | 14.8 ms | 68 |
| 20 | 5.0 ms | 200 |

**每减少 100 次绑定/帧，省 12.3ms。** 应用侧可做的：
- 按材质/shader 排序，减少 `glUseProgram`/`glBindTexture`；
- 合并 render pass，减少 `glBindFramebuffer`；
- 避免冗余绑定（注意：**驱动不做 no-op 检测**，报告 78 的 M6 已证"绑到当前已绑定的 program 也照收 122µs"）。

> 反例校准：glxgears 在 525 上只有 3.0ms/帧（报告 73）——因为它每帧仅 5 次 `glCallList`。
> **这条回归只打"每帧几百次状态切换"的 GL 应用**，不是"525 跑 GL 就慢"。

### 决策 3：如果要向 NVIDIA 报 bug，报什么

一句话可复现：
> 525.116.03 / P106-100 / 纯 GL：每次 `glUseProgram`（或 `glBindFramebuffer`/`glBindTexture`）后紧跟一个 draw，
> 该 draw 的 GPU 侧耗时固定增加 **~122µs**（util 100%、power 37.7W、mem 0%）；
> 515.105.01 上同一程序同一操作 **0.03µs**；与几何/着色器规模/CPU 负载/回读全部无关。

复现器：`analysis/probes/pair_only.c`（无 PBO、无回读，20 行核心逻辑）。

## 3. 本案最终状态（79–89 十轮）

```
525 的回归 = 每次「管线状态绑定 → 批次断开」固定 122µs
             该 122µs 是驱动对批次的串行化等待（20µs 粒度轮询队列位置）
             GPU 期间空转（util 100% / 37W / mem 0%），命令流里没有等待命令
             515 无此行为（0.03µs/次）
Heaven：268 次/帧 × 122µs = 33ms → 34fps（515：2.6ms 窗口 → 101fps）
```

**未闭合的最后一格**：为什么"队列位置写回主机"要 155µs。GL 层已无观测手段（GPU 计数器不可用）。
