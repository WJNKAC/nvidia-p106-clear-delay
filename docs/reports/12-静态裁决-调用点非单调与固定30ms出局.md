## 3. 静态第三件：排空调用点计数 **非单调**，这是对"第 7 个调用点"的裁决

用 `.eh_frame` 建函数边界 + 全库 call/jmp 扫描，统计指向排空函数的调用点：

| 版本 | 排空函数 | 调用点数 | 所在函数（按大小） |
|---|---|---|---|
| 515.105.01 | `0xfbe5b0` (271B) | **6** | 1458 / 182 / 3291×2 / 342 / 431 |
| 525.116.03 | `0x1577a90` (304B) | **6** | 1614 / 183 / 3762×2 / 417 / 441 |
| 535.129.03 | `0x161a980` (339B) | **20** | 1993×2 / 1633 / 188 / 3913×3 / 418 / 53 / 832 / 2340 / 420 / 389 / 1241×3 / 255 / 639 / 10408×2 |
| 580.126.18 | `0xb0fd70` | **7** | 1641 / 188 / 3835×2 / 418 / 61 / 71 |

**关键结构事实**：计数是 `6 → 6 → 20 → 7`，**不是单调增长**。
535 是异常高点，580 反而回落。

### 3.1 逻辑推论（对原假设的修订）

用户原假设："第 7 个调用点如果落在 prep/flush 路径，就足以构成整个回归"。

- **若 525 坏**：515 与 525 调用点数都是 6、结构同构、退避常数相同。
  那么"新增一个 prep 路径调用点"**不可能是 515→525 的判别式**——因为 525 并没有新增。
  回归的原因只能在"**同一段代码被更频繁地触达**"或"**等待出口条件变了**"。
- **若 525 好**：第七处（580 的 `0xae5c30` 小包装，71B，做"过门→排空→若 busy 则 force kick"）
  才有资格成为 525/535→580 段的嫌疑，但它解释不了 515→525，也解释不了 535 的 20 处。

→ 无论 525 落在哪一格，**"数调用点"这条路都不能给出单调解释**。
它与上一轮"逐行 diff 得到一致"是同一类结果：**结构没变多少，行为变了**。

### 3.2 一个附带的、更可疑的结构差异

排空函数**自己**读时钟、算 deadline、扫数组；而 580 多出一个 71B 的小包装 `0xae5c30`：

```
ae5c30: 门位检查（global 0x235dec0 bit0 / ctx+0x565 bit1）
ae5c59: call 0xb0fd70        ← 直接进排空
ae5c6b: jmp  0xb0ff30        ← 若排空返回 busy，强制 kick
```

515 对应的角色是一个 431B 的函数（`0xfbe6c0`），525 是 441B（`0x1577bc0`）——
**同一个功能在 580 被拆成了一个 71B 的薄包装**，而它的调用点从 515 的少数几处膨胀到 **14 处**。

这条只对"525 好"的情形有意义，先记录不下结论。

## 4. 用户提出的"地板 92% 是纯等待"——接受，并补一个措辞更正

用户的读法：`clear→set` 的 2.64 ms 装着下一帧全部 CPU prep + 提交 + GPU 执行，
所以帧周期的 92% 是纯等待；并且 **clear 不是"发现了完成"的证据，而是帧边界处 tracker 复用复位**。
真实命题是"**等待以自身节奏到期，与完成事件脱钩**"。

我接受这个更正，并确认它与我手里的数据一致：

- `rise→fall`（0xffff→0）30.24 ms，分布 p10 30.01 / p90 30.61；
- `fall→rise`（0→0xffff）2.64 ms，分布 p10 2.11 / p90 3.86（**更宽**）。

**等待段的方差比事件源更小，且不随事件源波动** —— 这是"时间型出口"的独立证据，
比我上一轮写的"驱动要 30.24 ms 才发现"准确。报告 10 的措辞按此更正。

同时"per-batch 20–30 µs × 上千次"的折算模型作废：2.64 ms 装下一整帧的 CPU 侧工作，
单批成本在 ~2 µs 量级，**地板不在提交侧**。

## 5. numerology 的地位

用户给出 `(N−1)² × 250 µs = 11² × 250 = 30.25 ms`（实测 30.24）与
`N(N−1) × 250 µs = 12×11×250 = 33 ms`（帧周期 32.87）。

按 README 铁律 5，这是**待杀的预言**，不写成结论。但可以补一条它的相容性检验：

- 它预测 wait 由 pending 的衰减积分决定 → pending ∝ 在飞批次数 ∝ GPU 每批耗时
  → **分辨率下降时 wait 应变短**。与 320×200 的 27.0 ms 帧**相容**。
- 而"固定 30 ms"与该数据**不相容**（见 §2.1）。

所以目前的证据分布是：**积分/衰减类假说存活，固定定时器假说死亡**。
但这只是"没有被数据打死"，不等于被证实。
