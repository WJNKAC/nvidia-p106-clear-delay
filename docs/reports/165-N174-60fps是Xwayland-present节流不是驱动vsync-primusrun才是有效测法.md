# N174 — ★ 60fps 是 Xwayland present 节流，不是驱动 vsync；primusrun 才是能看出真实的测法

**日期**：2026-10-27
**驱动**：515.105.01（Wayland/KWin + Xwayland，HDMI-A-2 60Hz）
**来源**：用户实测两组启动方式

---

## 0. 一句话结论

**同一台机器、同一个 Heaven、同一份 515 驱动，只换启动方式：**

| 启动方式 | 帧率 |
|---|---|
| `vblank_mode=0 primusrun ./heaven` | **100 fps+** |
| `vblank_mode=0 __NV_PRIME_RENDER_OFFLOAD=1 __GLX_VENDOR_LIBRARY_NAME=nvidia __GL_SYNC_TO_VBLANK=0 ./heaven` | **被限制在 60 fps** |

**⇒ 「60 fps」不是满帧，是天花板。**
**⇒ 此前所有 Heaven 上的 515 vs 525 对比都在这个天花板下面做的，结论全部无效。**
**⇒ 而 `primusrun` 恰好绕过了这个天花板 —— 它是我之前判为"慢、不该用"的那条路，实际上它是唯一能测出真实性能的路径。**

---

## 1. 机制：为什么 primusrun 能突破 60

两条路的呈现方式根本不同：

### NVIDIA GLX 直连（`__GLX_VENDOR_LIBRARY_NAME=nvidia`）

```
应用 glXSwapBuffers
  → libGLX_nvidia 提交
  → Xwayland 收到 PresentPixmap
  → DRI3 把 buffer 交给 KWin
  → KWin 在下一个 vblank 合成           ← ★ 60Hz 节流在这里
```

`vblank_mode=0` 和 `__GL_SYNC_TO_VBLANK=0` **都作用在 GLX 交换链内部**，
而这一个节流点在**它的下游**（Xwayland 的 present → KWin 合成）。
**所以关驱动 vsync 关不掉它 —— 这就是为什么这两个环境变量实测无效。**

### primusrun

```
应用 GL 调用 → P106-100 离屏渲染到 FBO
  → primus 的 libGL 拦截 glXSwapBuffers
  → CPU 读回像素
  → XPutImage / XShmPutImage 贴到窗口    ← ★ 不走 present/vblank 通道
  → KWin 合成
```

`XPutImage` 是传统 X11 图像传输，**不经过 DRI3/Present 这条带 vblank 节流的通道**，
所以应用侧不再被阻塞在 swap 上，帧率计数器能跑满真实渲染能力。

**验证过的证据链**（此前已确认）：
- `primusrun` 只是把 `/usr/lib/x86_64-linux-gnu/primus/libGL.so.1`（264 KB）塞进 `LD_LIBRARY_PATH` 最前；
- 它的工作方式就是"离屏渲染 + CPU 回读 + X11 传输"。

## 2. ★ 必须纠正的结论

### 2.1 报告 157「30fps 是 vsync 半速，原生 GL 是 60fps 满帧」

**「满帧」这个判断是错的。** 60 fps 是 Xwayland present 的天花板，不是渲染能力的上限。

当时的证据是"800×450 和 1920×1080 都是 60 fps，分辨率无关" ——
**我当时正确推断出"有节流"，但把节流归到了驱动 vsync，实际在合成器/Xwayland。**

### 2.2 报告 158 / 159：把 primusrun 定性为"慢的、不该用的"

**这个定性在"运行程序"的语境下没错，在"测量性能"的语境下完全错了。**

当时的数据是 `525 + primusrun = 28 fps`，我解释成"primus 的回读开销把 60 压到 28"。
**现在的数据推翻了这个解释**：

| | 515 | 525 |
|---|---|---|
| GLX 直连 | 60（被压） | 60（被压） |
| **primusrun** | **100+ fps** | **28 fps** |

**如果 28 fps 是"primus 的固定开销"，那 515 也应该是 28。但 515 到了 100+。**
⇒ **28 fps 反映的是 525 的真实渲染能力，不是 primus 的开销。**

### 2.3 报告 138「525 画面 61 / 515 画面 60，FPS 两版几乎一样」

**这个对比被天花板完全污染了。** 两版都被压在 60，当然"几乎一样"。
当时由此推出的结论"差异不在平均帧率，而在帧时间稳定性"，
**至少"平均帧率没有差异"这一半是错的** ——
真实差异是 **515 ≈ 10 ms/帧 vs 525 ≈ 35 ms/帧（3.5×）**，只是在 GLX 直连下被掩盖。

## 3. 修正后的对照表

| 配置 | 帧率 | 每帧耗时 | 说明 |
|---|---|---|---|
| 515 + GLX 直连 | 60 | ≥16.7 ms | **测不出真值** |
| 515 + primusrun | **100+** | **<10 ms** | 暴露真实能力 |
| 525 + GLX 直连 | 60 | ≥16.7 ms | **测不出真值** |
| 525 + primusrun | **28** | **35 ms** | 暴露真实能力 |

**真实差距 = 3.5×（Heaven 负载下）。**

这与 `n83b` 上测到的 **12.8×**（52.8 ms vs 4.1 ms）方向一致、倍数不同 ——
倍数不同是合理的：`n83b` 是极端合成负载（每帧 400~1200 个批次），把批次成本放大到极致；
Heaven 的批次密度低得多，所以差距收窄。

## 4. 这对整个案子的意义

### 4.1 之前的 Heaven 对比全部要重做

凡是在 **GLX 直连 + Xwayland** 下做的 Heaven 帧率对比，**都在 60 fps 天花板下面**，
包括报告 138（515 vs 525 Heaven）、报告 157/158/159 里的所有 fps 数字。

**唯一可信的例外**：报告 162 的 `n83b` 系列（那个程序自己控制帧数，不依赖 swap 呈现，
且测的是 `map`/`total` 的内部计时，不受 present 节流影响）。

### 4.2 「525 抽搐」也有了新解释

用户最早的症状是"525 在高帧率下抽搐，然后回落到 30 fps 左右"。

在 60 fps 天花板模型下：
- 525 真实每帧 35 ms > 16.7 ms → **每个 vsync 周期都赶不上** → 稳定掉到 30 fps（半速）
- 偶发的"高帧率"是少数轻负载帧赶上了节拍
- "抽搐"= 帧时间在 30/60 边界反复跨越导致的呈现抖动

**这与"525 渲染慢"是同一件事的两种表现，不需要额外机制。**

### 4.3 一个测量上的通用教训

> **用"窗口呈现的帧率"评价 GPU 性能，只要存在合成器/呈现节流，就会得到被截断的读数。**
> 判断是否被截断，最快的办法是**换一条绕过该节流的呈现路径**做同样的测试。
> 两条路径给出不同上限 ⇒ 你之前测的是节流，不是性能。

本案例里 `primusrun`（XPutImage）恰好提供了这条对照路径，**代价是它自身有回读开销**，
但**只要两条路径在同一驱动下对比，就能判断该驱动是否撞到了天花板**：
- 两路都是同一数值 → 撞天花板了，这个数值不是性能
- 某一路更高 → 那才是真实能力

## 5. 下一步（测量方法要改）

1. **所有 515 vs 525 的 Heaven 对比，一律用 `primusrun` 跑**，或换到不带合成器的 Xorg 会话。
   否则得到的永远是 60。
2. **注意 primus 的回读开销在 1080p 下不小**（1920×1080×4 B ≈ 8.3 MB/帧）。
   若要更干净的数，优先用**独立 Xorg（无合成器）**：`systemctl stop sddm` + 起一个裸 `Xorg :1`，
   这样 GLX 直连也能突破 60。
3. **重测 525 + primusrun 的帧时间分布**，确认 28 fps 是"恒定 35 ms"还是"30/60 双峰"。
   这决定 525 是"每帧都慢"还是"部分帧超时"。
4. 顺带确认：Heaven 的 `-video_vsync 0` 在这套栈下同样无效（节流点在下游），不必再试。
