## 1. 先把两个测量陷阱说清楚

### 1.1 残差法的错误（T3 §2.3 作废）

T3 用 `残差 = swap内睡眠 − (swap_in 到下一个 vblank 的距离)` 来分离"等 vblank"与"回读"。
原始事件时间线一展开就看出问题：

**1080p（vblank 在 swap 外）**
```
SWP_IN 5.253 → 11.400ms → SWP_OUT 16.653 → 0.480ms → VBLANK 17.133 → 5.130ms → SWP_IN
```

**720p（vblank 落在 swap 内）**
```
SWP_IN 12.184 → 4.473ms → VBLANK 16.657 → 5.930ms → SWP_OUT 22.980 → 6.254ms → SWP_IN
```

两种情况 `sleep` 都 ≈10.8ms，但 `swap_in→vblank` 一个是 10.4ms、一个是 4.5ms。
**同一帧里 vblank 的位置会变**，于是"残差"有时是"等 vblank 之外的部分"、有时是"vblank 之后到返回的部分"——两者混在一起。

这也解释了 T3 里为什么相关系数只有 r=0.16~0.30、残差 p10 甚至为负：**模型本身就是错的**。

统计（`t4_scan.py` 新增分类列）：

| 配置 | vblank 在 swap 内 | vblank 在 swap 外 |
|---|---|---|
| primus 1080p | 511 帧 | 390 帧 |
| primus 720p | 574 帧 | 325 帧 |
| primus 540p | 553 帧 | 348 帧 |

**大约一半一半**，所以任何假设"vblank 位置固定"的公式都不成立。

### 1.2 vsync 开启时，swap 段是无信息量的

1080p（vsync on）实测：

```
swap 段        = 10.90 ms
period         = 16.66 ms
CPU 渲染(gap)  =  5.65 ms
swap 内 CPU 忙 =  0.12 ms
```

恒等式检验：`16.66 − 5.65 − 0.12 = 10.89` vs 实测 `10.90`。**吻合到 0.01ms。**

→ **vsync 开启时，swap 段长 = "把这一帧补到 16.66ms 的剩余量"，它只反映 CPU 渲染有多快，不反映驱动/GPU 花了多少。**
任何用 vsync-on 数据做"swap 内部有 11ms 开销"的推断都是循环论证。

T3 报告里"swap 内阻塞 11ms 占一帧 2/3"这个**数值是对的**，但**解释必须改**：
不是"驱动在 swap 里花了 11ms"，而是"驱动在等 vsync，等的时间正好是补足 16.66ms 的余量"。

## 2. 真正的实验：关掉 vsync，让帧率自由浮动

只有关 vsync，帧时间才反映真实成本。primus 用 `vblank_mode=0`（Mesa 变量）。

### 2.1 主结果：fps 与像素量完全无关

| 分辨率 | 像素 | **fps** | 帧间隔 | swap 段 | swap 内 CPU | CPU 渲染(gap) |
|---|---|---|---|---|---|---|
| 1920×1080 | 2.07 M | **108.7** | 8.91 ms | 1.22 ms | 0.12 ms | 7.45 ms |
| 1280×720 | 0.92 M | **109.4** | 8.88 ms | 1.29 ms | 0.12 ms | 7.33 ms |
| 960×540 | 0.52 M | **108.1** | 8.95 ms | 1.31 ms | 0.14 ms | 7.44 ms |
| 像素比 | 1.00 / 0.44 / 0.25 | | | | | |

- **像素降 4 倍，fps 变化 −0.6%**（在噪声内，且方向是**略降**）
- **swap 段 1.22 → 1.31ms**（+0.09ms，与像素量反向）
- 拟合：`swap段 = −0.057 ms/Mpx × 像素 + 1.34ms`，R²=0.999

### 2.2 结论：回读不是真凶

primus 的 readback 数据量在 1080p 是 1920×1080×4B = **8.3MB/帧**，540p 只有 **2.1MB/帧**。
- 若瓶颈是 PCIe Gen1 x16（~4GB/s）上的回读：帧时间应当 ∝ 像素量，fps 应随降分辨率近似反比增长（4 倍）
- 实测 fps 纹丝不动

→ **回读带宽/拷贝成本在本机完全不是瓶颈。** 报告 17 遗留的"primus readback 是否为主因"这个问题，答案是**否**。

### 2.3 515 的真实成本结构（vsync off，1080p）

| 项 | 值 | 占比 |
|---|---|---|
| 帧时间 | 8.91 ms | 100% |
| **CPU 渲染（gap 内忙）** | **7.45 ms** | **84%** |
| swap 内等 GPU/回读 | 1.10 ms | 12% |
| swap 内 CPU 忙 | 0.12 ms | 1% |
| gap 内睡眠 | 0.14 ms | 2% |

**瓶颈在 CPU 侧渲染提交（84%），不在 GPU、不在回读。**
这与报告 07 的结论一致（"成本 ∝ 每帧 GL 调用密度，与像素无关"，当时 320×200 仍 26.3ms），
现在用完全不同的方法（ftrace + sched_switch，而非 perf 采样）在 515 上复现了同一结论。

### 2.4 一个未解释的副作用（诚实记录）

| | vsync on | vsync off |
|---|---|---|
| CPU 渲染(gap 忙) | **5.65 ms** | **7.45 ms** |
| GPU util / 功耗 | 79% / 95W | **100% / 116W** |

同样的渲染工作，关掉 vsync 后 CPU 忙了 1.8ms（+32%），GPU 同时满载。
合理猜测是 GPU 队列积压对 CPU 提交形成反压（缓冲区满后 `glXSwapBuffers`/后续调用更容易阻塞）。
**本装置无法区分"CPU 真的多算了"与"CPU 阻塞在驱动提交上"，需另设实验（如 GPU 侧 fence 探针）。**

## 3. dmabuf 路径的 vsync 关不掉（对照实验受限）

试了两个环境变量，dmabuf 仍是精确 60.0 fps：

| 变量 | 结果 | 原因 |
|---|---|---|
| `vblank_mode=0` | 60.0 fps（无效） | 这是 **Mesa** 变量，`libGLX_nvidia` 不读 |
| `__GL_SYNC_TO_VBLANK=0` | 60.1 fps（无效） | NVIDIA 的开关，但本机路径上也不生效 |

→ **dmabuf 直渲的 60Hz 上限来自 Xwayland/kwin 的 present 节流，不是驱动 vsync。**
这也解释了为什么 primus 能跑到 108fps 而 dmabuf 卡 60：primus 走 Mesa libGL，swap 只做 readback+blit，不等 present；
dmabuf 的 swap 要等 Xwayland 的 present 完成，被合成器钉在 60Hz。

**后果**：本想把"primus（有回读）vs dmabuf（无回读）"在 vsync off 下对比 fps，以此量化回读成本——**这个对照做不成**。
但主结论（§2.1）只依赖 primus 自身三档对比，不需要该对照。

## 4. 对 525 复测判读框架的重大修正

T3 说"判读 525 看 swap 内睡眠和残差怎么变"。**现在必须改**：

1. **残差不再是判据**（§1.1 已证伪）
2. **vsync 开启时的 swap 段不再是判据**（§1.2，它只是 period − CPU渲染）
3. **唯一干净的判据是：关 vsync 下的 fps**

### 4.1 新判读表（替换 T3 §3 的表）

前提：525 上跑 `t3_segments.sh primus 15 <tag> clean 1920x1080 vsync_off`。

| 525 vsync_off 1080p | 判读 | 结论强度 |
|---|---|---|
| **fps ≈ 108（±10）** | **性能没有回归**。30fps 完全来自 vsync/present 语义（每帧等 2 拍），不是计算变慢 | 决定性：把问题从"性能回归"彻底改写为"呈现语义回归" |
| fps ≈ 55 | 真实性能减半：CPU 渲染或 swap 内等待翻倍 | 需再分段定位（看 gap 忙 与 swap 段哪一个翻倍） |
| fps 介于 60~100 | 部分回归，需结合分段看 | 中等 |
| fps > 108 | 无回归且更快（不太可能，但有信息） | — |

**这个判据的优点是：不依赖 vblank 对齐、不依赖残差模型、不受 swap 段无信息量的影响。**
只要关掉 vsync，fps 就直接是"这台机器上这套代码能跑多快"的干净度量。

### 4.2 配套：vsync_on 下的两组数（用于确认"掉 2 拍"）

| 525 vsync_on 1080p | 预期若"每帧 2 拍" |
|---|---|
| 帧间隔中位 | ≈ 33.3 ms |
| swap 段 | ≈ 33.3 − CPU渲染（若 CPU 渲染未变，≈ 27.7ms） |
| 每帧 vblank 数 | ≈ 2.0 |

> 注意：即便 525 的 vsync_on 帧间隔是 33.3ms 且 swap 段 27.7ms，**也不能说"驱动多花了 16.7ms"**——
> 按 §1.2 的恒等式，那只是"它等了 2 个周期而不是 1 个"。真正的判别仍然只能靠 vsync_off 的 fps。

## 5. 本轮仪器与方法增量

### 5.1 新增/修改

| 文件 | 变更 |
|---|---|
| `t3_segments.sh` | 加第 5 参分辨率、第 6 参 vsync 模式（`vsync_on`/`vsync_off`/`vsync_nv`）；meta 记录 `res/pixels/vsync/venv` |
| `t4_scan.py` | **新增 vblank 位置分类**（`vb_in`/`vb_out`），输出 `pre`/`post`/`gapv`；删除错误的残差列；加像素量扫描汇总与线性拟合 |
| `t3_timeline.py` | 新增：打印连续 N 帧原始事件时间线，用于人工核对时序（本次靠它发现残差法错误的） |

### 5.2 两条方法论纪律（已入技能）

1. **任何"某段时间在等什么"的分解，必须先验证等待事件的相对位置是否稳定。**
   本例 vblank 有一半落在 swap 内、一半在外，导致线性模型失效。
   验证成本极低：打印 3 帧原始事件序列（`t3_timeline.py`）就能看出来。
2. **vsync 开启时不要用 swap 段长度做成本推断。**
   先用恒等式检验：`swap段 + CPU渲染 + swap内CPU忙 == period`？若成立，swap 段就是余量，不是开销。
