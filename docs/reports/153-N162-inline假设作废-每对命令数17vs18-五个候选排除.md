## 1. 每对命令数：515 = 17 条，525 = 18 条

用 `pbdump.py` 解两版 M3（`-n 8`）的完整命令流，以 `BEGIN`（`sub0:0x1618`）为界统计：

| | 相邻 BEGIN 间距 | BEGIN 总数（6000 条内） |
|---|---|---|
| 515 | **17**（6 个间隔全部相同） | 302 |
| 525 | **18**（6 个间隔全部相同） | 288 |

### 1.2 `0x39c0` / `0x39d0` / `0x3998` 的生成点

命令头反查（`sub0, cnt=1`）：

| method | header | 515 生成点 | 525 生成点 |
|---|---|---|---|
| `0x39c0` | `0x20010e70` | **38 处** | **0 处** |
| `0x39d0` | `0x20010e74` | 0 处 | **40 处** |
| `0x3998` | `0x20010e66` | 0 处 | **2 处** |

⇒ **是方法号跨版本重编号**，不是功能差异。

反汇编两处生成上下文（515 `0xfceaae` / 525 `0x1589006`）结构逐条对应：

```
515: mov [rsi-0x1c],eax; [rsi-0x18]=…; [rsi-0x10]=0x20010e70; [rsi-0xc]=ebx
      [rsi-0x8]=ebp; [rsi-0x4]=r15d; [rsi-0x14]=…
      test r15d,r15d; jle; 循环拷 r15 个 dword
525: mov [rdx+0x10],0x20010e74; [rdx+0xc]=ecx; [rdx+0x14]=eax; [rdx+0x18]=r8d
      [rdx+0x1c]=r15d; test r15d,r15d; jle; 循环拷 r15 个 dword
```

**同一个"上传不定长 dword 数组"的操作，只是方法号不同。**

## 2. 五个新候选，全部实测排除

### 2.1 静态命令流重放 —— `-X` 无效

假设：525 复用同一段 pushbuffer（30 ms 内只改 745 字），515 每帧重写（改 12,468 字）。
如果"重放静态流"是慢的原因，那么让每帧参数不同就该改善。

给 n83b 加 `-X`（每帧把 px 微移 `(f&0x3f)*0.001f`，破坏静态复用）：

| N | STATIC | VARY(`-X`) |
|---|---|---|
| 500 | 75.301 ms | 63.677 ms |
| 1000 | **125.929** | **125.823** |
| 2000 | **250.167** | **250.167** |

**N=1000/2000 完全一致。** ⇒ 重放不是原因。（N=500 的差异是暖机噪声，见 §2.4）

### 2.2 参数变化触发重编译 —— `-C` 无效

假设：M3 每对的颜色/矩阵都不同（`glColor3f(i%7…)`、`glTranslatef(px,py)`），
可能每对都触发固定管线的着色器变体切换。

给 n83b 加 `-C`（所有对颜色 `(0.5,0.5,0.5)`、位置 `(0,0)`）：

| N | VARY（默认） | CONST(`-C`) |
|---|---|---|
| 500 | 74.874 ms | 63.689 ms |
| 1000 | **125.761** | **125.792** |
| 2000 | **250.097** | **250.136** |

**完全一致。** ⇒ 参数变化不是原因。

### 2.3 ROP flush 命令 —— 改成 NOP 反而更慢

`0x0228 = FLUSH_AND_INVALIDATE_ROP_MINI_CACHE`，每对末尾都有一条。
假设它触发了 ROP 缓存刷新（昂贵）。

做法：把两版所有 `0x0228` 生成点（525 有 7 处）的 header 从 `0x2001008a`
改成 NOP 的 `0x20010040`：

```
[patchpb] 7 处全部 [已改写]
结果：148.153 ms/帧（基线 125.7）
```

**反而慢了 18%。** ⇒ 这条命令必需，且不是瓶颈。

### 2.4 页面/状态字段 —— 读出来全是 0

在 525 的 inline 生成函数（`0x16154c0`）入口断点，读所有候选状态字段：

| 字段 | 值 |
|---|---|
| `[ctx+0xbf8]` | **0** |
| `[ctx+0xb10]` | **0** |
| `[ctx+0x3b4]` | **0** |
| `[ctx+0x55c]` | **0** |
| `[ctx+0x5ad]` | **0** |

⇒ 这些"特性开关"全部未启用，不构成差异。

## 3. 现在的核心矛盾（必须直面的数字）

```
525：18 条命令/对  →  GPU 花 119.7 µs/对   →  6.6 µs / 条命令
515：17 条命令/对  →  GPU 花   2.6 µs/对   →  0.15 µs / 条命令
```

**命令几乎一样、GPU 是同一块、时钟满频、参数恒定也不变——
但 525 每条命令的 GPU 执行代价是 515 的 44 倍。**

### 3.1 一个更细的分解

| | 命令数 | GPU 时间 | 折算每条 |
|---|---|---|---|
| 525 M1（纯 draw） | 3 / draw | 4.57 µs | 1.5 µs |
| 525 M3（绑定+draw） | 18 / 对 | 119.7 µs | 6.6 µs |
| 515 M1 | 3 / draw | 4.36 µs | 1.5 µs |
| 515 M3 | 17 / 对 | 2.6 µs | 0.15 µs |

注意 **525 的 M1 与 515 的 M1 完全一致（1.5 µs/条）**。
只有 M3（含状态设置）才出现 44 倍差异。

⇒ **贵的不是命令条数，是"状态设置命令"这一类的执行代价。**

### 3.2 这把 115 µs 定位到"14 条状态设置命令"

M3 比 M1 多出的命令：
`0x34a8 / 0x1688 / 0x39d0×2 / 0x2144 / 0x2490 / 0x0360 / 0x1450 / 0x196c / 0x13a8 / 0x037c / 0x2044 / 0x2410 / 0x2600 / 0x0228`（14~15 条）

**这 14 条在 525 上要 115 µs，在 515 上只要 1 µs 左右。**

## 4. 一个未验证但很有力的可能性

515 每帧重写 12,468 字命令流，525 只改 745 字
⇒ **515 每帧都把命令完整写进新的 buffer 区域，525 反复提交同一段。**

在 GPU 侧，这意味着：

- **515**：命令流是"新写的"，GPU 的指令预取器/方法缓存可能走快速路径
- **525**：命令流是"同一段地址被反复提交"，GPU 每次都要重新走一遍状态恢复

但 §2.1 的 `-X` 实验否证了"改内容能改善"——
不过 `-X` 只改了少量立即数，**buffer 的物理位置和提交模式没变**。

**⇒ 要验证这条，必须让 525 每帧写到不同位置（真正的双缓冲 pushbuffer），
而不是只改内容。**

这是下一步唯一还有意义的实验方向，但需要改驱动行为（不能只改应用）。

## 5. 本轮净结论

**成立（本轮新增）：**

1. **每对命令数：515 = 17，525 = 18**（以 BEGIN 为界，6 个间隔全部一致）
2. **两版唯一差异是 `0x39c0`→`0x39d0` 重编号 + 多一条 `0x3998`**，生成代码结构逐条对应
3. **n83b M3 场景下 sub6 命令数两版相同**（76 vs 74），**inline 假设作废**
4. **排除**：静态重放（`-X`）、参数变化（`-C`）、ROP flush（改 NOP 更慢）、
   5 个状态字段（全 0）
5. **精确分解**：525 的 M1 与 515 的 M1 都约 1.5 µs/条命令；
   **差异只出现在 M3 的"状态设置命令"上，44 倍**

**已作废（不要再引用）：**

- ~~"与 inline 上传差异闭合（416×）"~~ → 那是 Heaven 场景的数，n83b M3 下两版相同

**下一步（需要动驱动，不是应用）：**
让 525 每帧把命令流写到**不同**的 pushbuffer 位置（真正的双缓冲），
而不是反复提交同一段。这是验证 §4 的唯一方法。

## 7. 追加：wp/rp 的推进模式（每帧 +6，rp 永远落后 1）

在 525 的"等空间"函数入口（`0x1578280`，实测每帧 1 次）连续采样 8 次，
即跨越 **8 帧**：

| 帧 | `[ctx+0x1130]`（wp） | `[ctx+0x1240]`（缓存 rp） | 差值 |
|---|---|---|---|
| 1 | 0x9c (156) | 0x9b (155) | 1 |
| 2 | 0xa2 (162) | 0xa1 (161) | 1 |
| 3 | 0xa8 (168) | 0xa7 (167) | 1 |
| 4 | 0xae (174) | 0xad (173) | 1 |
| 5 | 0xb4 (180) | 0xb3 (179) | 1 |
| 6 | 0xba (186) | 0xb9 (185) | 1 |
| 7 | 0xc0 (192) | 0xbf (191) | 1 |
| 8 | 0xc6 (198) | 0xc5 (197) | 1 |

### 7.1 两个稳定事实

1. **每帧 wp 恰好推进 +6**（7 个间隔全部相同）
2. **rp 永远恰好落后 1**（`rp = wp - 1`，无一例外）

### 7.2 这说明什么

**① 每帧提交量完全固定。** 不是"有时多有时少"，是精确的 6 个单位。
与"525 的命令流是静态的"一致（报告 140）。

**② GPU 只积压 1 个批次。** 这是标准的双缓冲流水：

```
本帧：提交第 N 批 → 等第 N-1 批完成
下一帧：提交第 N+1 批 → 等第 N 批完成
```

**⇒ 不是"GPU 排队积压"，而是"每帧都要等上一批画完"。**

**③ 这也解释了为什么异步回读无效（报告 152）：**
流水深度已经是 1（满配），再加 PBO 深度只是让 CPU 多跑几步，
GPU 完成一批的时间不变。

### 7.3 所以每帧 127 ms = 等 GPU 执行完一个批次（1000 对）

```
wp 每帧 +6，rp 落后 1
⇒ 每帧一次同步，同步时长 = GPU 执行 1000 对的时间 = 125 ms
⇒ 每对 125 µs
```

**这与报告 152 的线性拟合完全一致（`5.87 ms + N × 119.7 µs`）。**

### 7.4 仍未解释的

**为什么同样 18 条命令，525 的 GPU 要 6.6 µs/条、515 只要 0.15 µs/条。**

已经排除的：
- 命令条数与内容（17 vs 18，序列逐条对应）
- 参数是否变化（`-C` 有效否证）
- 静态重放（`-X` 有效否证）
- ROP flush 命令（改 NOP 更慢）
- 5 个特性开关字段（全 0）
- CPU 侧等待方式（异步回读无效）
- GPU 时钟/降频（P0 满频）
- 内核 ioctl（2.3% 墙钟）

以现有手段（用户态 hook + 静态反汇编 + nvidia-smi + ptrace）**已无法再向下**。
剩下的唯一入口是 GPU 侧性能计数器（NVPerf / Nsight），
而 P106 是矿卡 SKU，能否放行这些工具尚未验证。
