# 50 · N46：烧满一个核的不是 worker，是**多个线程在抢 malloc 全局锁**

> ⚠️ **2026-10-26 07:50 更正（报告 51，已拿到调用栈）**：本报告对 `libc+0xf8040` 的解读**是错的**。
> 该偏移实际是 **`sched_yield+7`**（同一页里 `0xf8077` 才是 `lock cmpxchg`，**差 0x30 字节**）。
> 真正情况是 **glcore 自己在调 `sched_yield` 做有界自旋**：栈上 8 层全在 glcore 内
> （`#7 = 0x123b297` 队列处理器 → `#1 = 0x15762a2` 自旋等待 → `#0 sched_yield`）。
> **不是 malloc 锁竞争。** §2.3/§3 的 malloc 结论作废；§2.1（线程列表）、§2.2（RIP 采样）仍有效。

> 2026-10-26 07:00
> 用户要求先认 25771，再决定改不改记账。**这是前提，不是可选项。**
>
> **答案落在用户列的三种可能之外，而且更重要：**
> 烧满一个核的线程 **10/12 次采样停在 `libc.so.6 + 0xf8047`**，
> 那段是 **`__libc_free` 里对 malloc 全局锁 `0x1ec660` 的 `lock cmpxchg` 重试**。
> **→ 不是"某个线程在自旋等活"，是"多个线程在抢同一把 malloc 锁"。**

---

## 1. 结论（对"改不改记账"的直接回答）

| 问题 | 答案 |
|---|---|
| 烧满 100% 一核的是谁？ | 一个 `heaven_x64` 线程（comm 未命名），**状态 `R`、`wchan=0`、用户态纯自旋** |
| 它在跑什么？ | **`libc` 的 malloc/free 锁竞争**（10/12 采样在 `lock cmpxchg 0x1ec660` 之后的重试路径） |
| 是哪个用户列的可能？ | **都不是**。不是 readback worker、不是驱动轮询线程、**不是 Heaven 渲染线程的空转**——是**所有线程共享的 libc 堆锁** |
| **对"改记账"的影响** | **记账改动的收益可能被这个锁竞争吃掉。** 但反过来说，**记账本身产生 malloc 流量**（float 数组、命令缓冲），所以改记账**可能同时缓解锁竞争** |

**一句话**：**这不再是"某个循环太多余"的问题，是"整个进程在 malloc 锁上打转"。改记账之前必须先搞清它产生了多少堆分配。**

### 2.3 libc `0xf8040` 是什么（反汇编）

符号表把它标成 `__register_atfork+0x380`——**这是新版 glibc 把多个函数拼进同一段造成的误标**。
真实内容：

```asm
f8070: xor  %eax,%eax
f8072: mov  $0x1,%edx
f8077: lock cmpxchg %edx,0x1ec660      ; ← ★ 10/12 采样停在这里附近
f807f: je   f7fd9                       ; 抢到 → 继续
f8085: lea  0x1ec660,%rdi
f808c: call __lll_lock_wait_private     ; 抢不到 → 睡等（慢路径）
f8091: jmp  f7fd9
```

`0x1ec660` 是 libc 的**全局静态锁**，被 26 处引用。
这一段的上下文（`0x1ec668` 计数、`0x1ec680`/`0x1ec690` 的 `lea (%r15,%r15,4)` + `lea -0x30(%rax,%rdx,8)`
= **每项 40 字节的数组索引**）是 **malloc/free 的 arena/tcache/tunable 管理路径**。

**判据**：`lock cmpxchg` + 失败时 `call __lll_lock_wait_private` = **`__libc_lock_lock` 的经典展开**。
`R` 状态说明它**在用户态反复重试**（短临界区、抢不到就重来），而不是睡在 futex。

## 3. 这改变了什么

### 3.1 之前以为的

报告 48/49 的框架：**"readback worker 在烧 CPU 做无用记账"** → 改记账 → 省 5~8ms/帧。

### 3.2 现在看到的是

**一个线程 98.8% 在 libc 里抢 malloc 锁**，`wchan=0`、`R` 状态。
另外 5 个线程在 `futex_wait_queue`（正常等锁/等条件）。

**这是一个"多线程 + 频繁小分配"的典型症状。**

### 3.3 三种可能的因果，必须分清

| 假设 | 含义 | 怎么区分 |
|---|---|---|
| **A. 记账本身产生 malloc 流量** | 每命令一次记账 → 若有 `std::vector`/`new` → 4700 次/帧的小分配 → 锁竞争 | 看记账路径里有没有 `malloc/free` 调用 |
| **B. 别的线程在疯狂分配** | 这个自旋线程只是受害者 | 看 26692 的调用栈有多深（是不是在 `operator new`/`free` 里） |
| **C. 堆已碎片化** | arena 多、锁多，即使分配不多也会抢 | 读 `malloc` 的 arena 数（`MALLOC_ARENA_MAX`、`/proc/PID/status` 的 VmData 增长） |

**用户原来的三种可能都不是，但用户的判断方式是对的**：
"如果它才是真正的瓶颈，改记账省下的时间会被它抵消" ——
**现在它就是瓶颈（98.8% 一核），所以必须先解决它。**

## 4. 明确结论

| 项 | 结论 |
|---|---|
| **改不改记账** | **暂缓**。先确认 malloc 锁竞争的来源 |
| 理由 | 烧满一核的是 libc 锁竞争，不是 worker 的循环。改 worker 的记账**不一定**影响这个线程（取决于记账是否分配堆内存） |
| 这条支线的状态 | **可通，但落点又换了**：从"记账"改成"堆分配/锁竞争" |
| 用户预案里对应的分支 | 最接近第二条（"CPU 已超订 → 先解决超订"），但超订的根源不是渲染，是 **malloc** |

## 5. 唯一剩下要查的（一条）

**查 `26692` 的调用栈**：它在 `free()` 还是 `malloc()`？调用者是谁？

**方法**：gdb attach 后 `bt` 取 8 层回溯（比读 `$rip` 更有信息量）。
一次就能看出：

| 栈形 | 结论 |
|---|---|
| `free` ← `operator delete` ← `std::vector::reserve/resize` ← **glcore 记账代码** | **情况 A 成立** → 改记账直接有效 |
| `free` ← `operator delete` ← **Heaven 渲染/音频/物理** | 情况 B → 换方向 |
| `malloc` ← `new` ← 频繁小对象 | 情况 B/C → 查分配点 |

**这一步是纯观测，零成本，且直接决定"改记账"是否值得。**
