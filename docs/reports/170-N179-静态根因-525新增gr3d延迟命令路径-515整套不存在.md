# N179 — 静态根因定位：525 新增的 `gr3d` 延迟命令路径，515 里整套机制不存在

**日期**：2026-10-27
**对象**：`libnvidia-glcore.so` 525.116.03 vs 515.105.01（纯静态分析，不改运行时）
**前置**：报告 169 证明了运行时改两字节能让 Heaven 25→71 FPS；本报告回答"静态驱动里是哪里的问题"

---

## 0. 结论

**这不是"525 某行代码写错了"，而是 525 新增了一整套机制，515 里根本不存在：**

| 项 | 515.105.01 | 525.116.03 |
|---|---|---|
| `movabs 0x...20010E66`（那条 240 延迟命令） | **0 处** | **2 处** |
| `cmp byte [rax+0xc18], 0`（策略位检查） | **0 处** | **4 处** |
| 发射函数 `0x15c2e50` 的机器码 | **找不到** | 存在（11856 B） |
| 置位 `mov byte [rax+0xc18], 1` | — | `0x15bd014` |

**⇒ 515 不是"延迟更小"，是"没有这个机制"。** 所以两版不是参数差异，是代码路径差异。

---

## 1. 那条命令的结构

`0x20010E66` 是 PASCAL 3D class（subchannel 0）的方法 `0x3998`：

```
header = (op=1 INC_METHOD << 29) | (cnt=1 << 16) | (sub=0 << 13) | (meth 0x3998 >> 2 = 0xE66)
       = 0x20010E66
arg    = 0x000000F0  (= 240)
```

驱动用**一条 64 位 `movabs` 同时写入头和实参**：

```asm
movabs rcx, 0xF020010E66     ; 高32位=实参(0xF0)，低32位=命令头
mov    [rax], rcx            ; 8 字节一次写入 pushbuffer
add    rax, 8
mov    [rbx+0x80], rax       ; 推进写指针
cmp    rax, [rbx+0x88]       ; 检查是否越界
jae    <扩容>
```

两处：`0x15c3767`、`0x1842131`。

**240 是"延迟单位数"**。报告 168/169 已用干预实验证明：
改小 → 耗时按比例下降，且像素校验值 `chk` 完全不变（5150 → 5150）。

## 2. 两个发射点的触发条件

### 2.1 发射点 1：`0x15c3767`（在 `0x15c2e50` 内）

```asm
0x15c3750  mov  rax, [rbx + 0x1300]        ; 取子对象
0x15c3757  cmp  byte [rax + 0xc18], 0      ; ★ 策略位
0x15c375e  je   0x15c378c                  ; 为 0 → 跳过，不发命令
0x15c3760  mov  rax, [rbx + 0x80]          ; pushbuffer 写指针
0x15c3767  movabs rcx, 0xF020010E66        ; ★ 发命令
0x15c3771  mov  [rax], rcx
0x15c3774  add  rax, 8
0x15c3778  mov  [rbx + 0x80], rax
```

**注意 `0x15c2e50` 就是报告 155 里那个"legacy 状态机"**（11856 字节，最大热点之一）。

### 2.2 发射点 2：`0x1842131`（在 `0x1841fb0` 内，512 B 的小函数）

```asm
0x1841fb7  mov  rdi, [rdi + 0x50]
0x1841fbb  mov  rax, [rdi + 0xe8]
0x1841fc2  cmp  byte [rax + 0x9330], 0
0x1841fc9  jne  0x1841fe2                  ; 不为 0 → 直接返回
0x1841fcb  mov  rax, [rax + 0x108]
0x1841fd2  mov  rax, [rax + 0xbd0]
0x1841fd9  cmp  byte [rax + 0xc18], 0      ; ★ 同一个策略位
0x1841fe0  jne  0x1841ff0                  ; 为 0 → 返回
           ... 发命令 ...
```

**两个发射点检查的是同一个 `+0xc18`**，说明这是**一个全局策略开关**，不是局部条件。

---

## 3. 策略位 `+0xc18` 的置位逻辑（核心发现）

唯一以立即数形式置位的地方：`0x15bd014`，在函数 `0x15bc880`（2304 B）内。

```asm
0x15bcfe0  test sil, sil
0x15bcfe3  je   0x15bd014                  ; ← 走这里就直接置位！
0x15bcfe5  and  r8d, 0x205
0x15bcfec  cmp  r8d, 0x200
0x15bcff3  je   0x15bc998                  ; 等于 0x200 → 跳过（不置位）
0x15bcff9  cmp  byte [rax + 0xc19], 1      ; 另一个策略字节
0x15bd000  sbb  edx, edx                   ; 若 0xc19 < 1 → edx=-1
0x15bd002  and  edx, 3
0x15bd005  add  edx, 0x201                 ; → 0x201 或 0x204
0x15bd00b  cmp  r8d, edx
0x15bd00e  je   0x15bc998                  ; 匹配 → 跳过
0x15bd014  mov  byte [rax + 0xc18], 1      ; ★★ 置位（打开延迟）
0x15bd01b  jmp  0x15bc998
```

**读法：**

- `r8d` 是一个"模式/格式"标志字（参与 `and 0x205`、与 `0x200`/`0x201`/`0x204` 比较）
- 只有当 `r8d` **恰好等于** `0x200`、或等于 `0x201`/`0x204` 时，才**跳过**置位
- **其余所有情况 → 置位 → 之后每个批次都发 240 单位的延迟**

调用点 `0x15cecee` 传参：

```asm
xor  r8d, r8d        ; ★ r8d = 0
mov  rdx, r15
mov  rsi, rbp
mov  rcx, r13
mov  rdi, rbx
call 0x15bc880
```

**`r8d = 0`：`0 & 0x205 = 0`，不等于 `0x200`，也不等于 `0x201`/`0x204` ⇒ 必然走到 `0x15bd014` 置位。**

> 这就是为什么"每个批次都发延迟命令"：**这条路径的调用方直接传 0，落进了"置位"分支。**

另一个调用点 `0x13781f7`（在 `0x13780a0` 内）还没解剖，可能传不同参数。

## 4. 为什么这是"525 新增"而不是"525 退化"

三条独立证据：

1. **立即数缺失**：515 里搜 `66 0e 01 20 f0 00 00 00`（就是那两个 `movabs` 的立即数）→ **0 处**；525 → 2 处。
2. **检查模式缺失**：515 里搜 `80 b8 18 0c 00 00 00`（`cmp byte [rax+0xc18],0`）→ **0 处**；525 → 4 处。
3. **函数消失**：发射点 1 所在函数 `0x15c2e50` 的**前 48 字节机器码**在 515 里找不到（`find` 返回 -1）。

⇒ **515 没有"策略位 + 延迟命令"这套东西**，不是"值更小"。

> **重要推论：不能通过"把 525 的这个值调小"来完全等价于 515。**
> 调到 0 也不是（报告 168 实测 `0` 是特殊值，等价于 240）。
> **要真正等价于 515，需要跳过整条路径（即不置位 `+0xc18`）。**

## 5. ★ 治本补丁实测成功：从发射点绕过判据，525 完全追平 515

### 5.1 先失败的一步（必须记录）

我最初判断"治本点"是那个置位语句，于是尝试把它改成写 0：

| 尝试 | 结果 |
|---|---|
| 只改 `0x15bd01a`（`mov [rax+0xc18],1` 的 imm8） | **完全无效**，`0x3998` 照发 |
| 再补上 `0x1452699`（`mov [rbp+0xc18],1` 的 imm8） | **仍然完全无效** |

**原因**：`+0xc18` 这个字节**不止从"写立即数"来路**。
它有 48 处引用，其中还有 `mov [reg+0xc18], <寄存器>`（`48 89 87/86/83 18 0c 00 00`，共 6 处），
以及可能来自 memcpy / 配置块批量填充的写入。**把立即数改成 0 治不了它。**

> **教训：想关掉一个"标志位"，不要从"谁写它"下手（来路太多），要从"谁读它"下手。**

### 5.2 有效做法：改读侧的跳转条件

两个发射点的判据都是"标志位为 0 就跳过"，只要把条件跳转改成**无条件跳转**，
就等价于"永远跳过发射"，且不依赖标志位的任何来路：

| 位置 | 原指令 | 改为 | 含义 |
|---|---|---|---|
| `0x15c375e` | `74 2c`（`je +0x2c`） | **`eb 2c`**（`jmp +0x2c`） | 无条件跳过发射点 1 |
| `0x1841fe0` | `75 0e`（`jne +0x0e`） | **`eb 0e`**（`jmp +0x0e`） | 无条件跳过发射点 2 |

**只改 2 个字节，`74→eb` 和 `75→eb`。**

### 5.3 实测结果：525 追平 515

`n83b -M 7 -c 400 -n 400`，带回读模式（`chk` 为真实像素累加）：

| 配置 | `map_p50` | `fps` | **`chk`** |
|---|---|---|---|
| **525 基线** | **52.276 ms** | **18.96** | 5150 |
| **525 治本（跳过发射）** | **3.448 ms** | **256.56** | **5150** |
| 525 治标（实参 240→16） | 7.016 ms | ~133 | 5150 |
| **515 参考**（报告 166） | **≈3.4 ms** | **≈258** | 5150 |

**⇒ 治本补丁后 525 = 3.448 ms / 256.6 fps，与 515 的 ≈3.4 ms / 258 fps 完全持平。**
**⇒ `chk` 全为 5150，画面一致。**
**⇒ 治标（改实参）只能到 7.0 ms，治本能到 3.4 ms —— 说明那 240 之外还有别的代价，
只有"不发这条命令"才能全部消掉。**

> 这一条同时修正了报告 168/169 的一个隐含理解：
> 之前以为"把 240 调小"就等价于消除问题，实测只能消掉一半多（52.3 → 7.0），
> **剩下那 3.4~7.0 ms 的差距必须靠"不发"才能拿到。**

| `+0xc18` 是否被其他逻辑读取（4 处检查之外） | 46~48 处 `0xc18` 引用里大部分是**别的对象的同偏移字段**，需逐个甄别 |
| 为什么 525 要引入这套机制 | 推测与"更严格的一致性/正确性"有关，但无直接证据 |

## 7. 治本补丁在 Heaven 上的表现

| 配置 | GPU 利用率 | 功耗 |
|---|---|---|
| base（未补丁） | 100% | 55–70 W |
| **治本（跳过发射）** | **90–94%** | **94–108 W** |

**功耗接近翻倍、利用率反而略降** —— 这正是"GPU 从空转等待变成真在渲染"的特征
（利用率是"有命令在跑"的比例，空转时也会显示接近 100%；真正的判据是功耗）。

> ⚠ Heaven 这一轮**没有取到屏幕 FPS 读数**：`show_fps=1` 但当前场景的 FPS 叠层没出现在
> 窗口可见区域，且全图扫描未找到"深色底 + 白字"的叠层。
> **所以 Heaven 侧只有功耗证据；精确帧率数据以 §5.3 的 `n83b` 为准。**
> （不硬凑一个 FPS 数字 —— 报告 169 的 25/71 fps 是在 benchmark 场景下截到的，
> 本次非 benchmark 场景的叠层位置不同。）

## 8. 一句话总结

**525 在 `0x15bc880` 里根据一个模式标志把一个全局策略位置 1（`0x15bd014` / `0x1452693`），
之后 `0x15c2e50` 和 `0x1841fb0` 两个发射点就会在每次切批时写入 `0x3998 = 240`；
240 个单位 × 0.91 µs ≈ 218 µs/批，乘以批次数就是那堵墙。
而 515 里这套机制整套都不存在 —— 不是它把 240 调小了，是它压根不发这条命令。**

**把两个发射点的条件跳转改成无条件跳转（2 字节：`74→eb`、`75→eb`），
525 的 `map_p50` 从 52.276 ms 降到 3.448 ms，fps 从 18.96 升到 256.56，
完全追平 515（≈3.4 ms / 258 fps），且像素校验值 `chk` 保持 5150 不变。**
