# N172 — 驱动切换踩坑与修复：默认 gcc 已是 14.2.0，内核模块必须用 gcc-12 编译

**日期**：2026-10-27
**平台**：<user>@<testhost>（P106-100），kernel 6.1.0-50-amd64，Debian
**结果**：**成功切到 515.105.01**，图形正常，模块由 gcc 12.4.0 编译

---

## 0. 一句话结论

**切驱动失败两次，两个原因完全不同：**

1. **`systemctl stop sddm` 不会结束已登录的桌面会话** —— kwin_wayland / Xwayland / plasmashell 仍持有 `/dev/nvidia*`，`nvidia_drm` 卸不掉。
2. **系统默认 gcc 已被升到 14.2.0，而内核是 gcc-12 编的** —— GCC 14 把「隐式函数声明」从警告升级为**错误**，导致 515 和 525 的内核模块**都编不过**。

**修复：`CC=/usr/bin/gcc-12`（注意：没有 `--kernel-cc` 这个选项）。**

---

## 1. 第一次失败：模块卸不掉

```
ERROR: An NVIDIA kernel module 'nvidia-drm' appears to already be loaded in your kernel.
剩余 nvidia 模块数: 3
```

停在「停 sddm」这一步是不够的。实测此时仍有：

```
nvidia_drm   73728  3
nvidia_modeset 1249280  2 nvidia_drm
nvidia       56537088  456 nvidia_modeset      ← 引用计数 456
```

`fuser` 看到持有者：

```
/dev/nvidia0:  <user> 7436 F...m heaven_x64      ← 上一轮实验的残留进程
               <user> 7995 F.... Xwayland
               <user> 8120 F.... plasmashell
               <user> 8044 F.... kded6  ...
```

**⇒ sddm 只是登录界面（greeter）。已登录用户的 X/Wayland 会话是独立于它的，
停 sddm 不会杀掉那个会话。**

### 正确顺序

```bash
systemctl stop sddm
loginctl terminate-session <seat0 的 session id>   # 真正杀掉图形会话
# 再循环强杀仍持有 /dev/nvidia* 的进程，直到为空
for i in 1..5; do
    H=$(fuser /dev/nvidia0 /dev/nvidiactl); [ -z "$H" ] && break
    fuser -k /dev/nvidia0 /dev/nvidiactl; sleep 2
done
# 逐轮确认引用计数归零
for i in 1..5; do
    modprobe -r nvidia_drm; modprobe -r nvidia_modeset; modprobe -r nvidia
    [ "$(lsmod | grep -c '^nvidia')" = 0 ] && break; sleep 2
done
```

> **选 session id 时要小心**：`loginctl terminate-user <user>` 会把**自己的 SSH 会话一起杀掉**。
> 只按 `$4=="seat0"` 挑座位会话来终止。

## 2. 第二次失败：内核模块编译不过（真根因）

模块卸载干净后，安装仍然失败，而且**两个版本都失败**：

| 尝试 | 报错 |
|---|---|
| 515.105.01 | `nv-linux.h:1215:9: error: implicit declaration of function 'dma_is_direct'` |
| 525.116.03 | `modpost: "nvidia_register_module" [nvidia-modeset.ko] undefined!`（次生） |

### 2.1 为什么两个版本都挂 —— 说明是环境问题，不是版本问题

`nvidia.ko` 编译失败后，`nvidia-modeset.ko` / `nvidia-uvm.ko` 的 modpost 就会报
「`nvUvmInterface*` / `nvidia_register_module` undefined」——
**这是次生现象，不要被它误导去查 uvm 或 CUDA。**

### 2.2 根因：默认编译器换了

| 项 | 值 |
|---|---|
| 内核编译所用 | `gcc-12 (Debian 12.2.0-14+deb12u1)`（见 `/proc/version`） |
| **之前已装模块所用** | **`gcc version 12.4.0`**（见 `/proc/driver/nvidia/version`） |
| **现在的默认 gcc** | **`gcc (Debian 14.2.0-19) 14.2.0`** |

`/usr/bin/gcc -> gcc-14`。

**GCC 14 起，`implicit-function-declaration` 默认是 error**（GCC 12 只是 warning）。
而 515 的 `nv-linux.h` 引用了本内核头里并不存在的 `dma_is_direct()`：

```bash
grep -rn "dma_is_direct" /usr/src/linux-headers-6.1.0-50-common/   # → 无结果
```

gcc-12 下这只是一条警告，编过；gcc-14 下直接中断。

> 补充：`dma_is_direct` 只出现在 `procfs_nvswitch.o` / `i2c_nvswitch.o` ——
> **NVSwitch 专用**，P106-100 根本走不到那段代码，所以那条警告无害。

### 2.3 这也解释了「之前为什么能成功」

**之前能成功不是因为我做对了什么，而是因为当时系统默认 gcc 恰好就是 12.4.0。**
`/proc/driver/nvidia/version` 里 `GCC version: gcc version 12.4.0` 是当时的铁证。
换到 gcc-14 之后，同样的命令就编不过了。

---

## 3. 正确做法

```bash
CC=/usr/bin/gcc-12 IGNORE_CC_MISMATCH=1 \
  bash NVIDIA-Linux-x86_64-<版本>.run --silent --no-questions
```

**两个坑：**

- **没有 `--kernel-cc` 这个选项**。传了会直接 `unrecognized option: "--kernel-cc"` 退出。
  安装器自己的日志里写的是：*"It is recommended to set the CC environment variable"*。
- `IGNORE_CC_MISMATCH=1` 用于压掉编译器版本比对的那道检查。

`g++-12` **不需要**（内核模块是纯 C），本机也确实没装。

## 5. 可复用的检查清单（装 NVIDIA 驱动前先跑）

```bash
uname -r                        # 内核版本
cat /proc/version               # 内核是用哪个 gcc 编的
gcc --version                   # 现在默认是哪个 gcc
ls /usr/bin/gcc-*               # 有没有匹配的旧版编译器
ls -d /usr/src/linux-headers-$(uname -r)   # 头文件是否齐全
```

**判定规则：默认 gcc 的主版本必须与内核编译所用 gcc 的主版本一致（或更旧）。**
不一致就显式指定 `CC=/usr/bin/gcc-<内核那版>`。

> **另一个高价值判据**：如果 `/proc/driver/nvidia/version` 里的
> `GCC version:` 与 `gcc --version` 不一致，说明**系统编译器在此期间被升级过**，
> 那么"同一个安装命令以前能成、现在不能"就有了直接解释 ——
> **不要再去怀疑驱动包本身或内核 API 变化。**
