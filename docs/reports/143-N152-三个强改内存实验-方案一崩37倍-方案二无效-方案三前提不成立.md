# 报告 143 — 三个"强改内存"实验：方案一让性能崩 37 倍，方案二无效，方案三前提不成立

> 编号：143（对应 N152）
> 日期：2026-10-27
> 平台：P106-100 / 525.116.03 / Heaven 4.0 OpenGL
> 前置：报告 140（指令流对比）、141（生成点定位）、142（判据是位标志）

---

## 0. 三句话结论

1. **方案一（改 `[obj+0x104]` 3→8）成功执行，结果是灾难性的**：
   fps **78.6 → 2.12（慢 37 倍）**；把第二层 `[obj+0xbf8]` 也放开后出现 **7484 ms** 的单帧。
   **这条分支不是"并行加速"开关，是"慢速/兼容"路径。**
2. **方案二（改 pushbuffer 的 subchannel 0→6）执行了但无效**：改完 fps 71→52，恢复后 118。
   三个数不可比（Heaven 场景本身 fps 波动 60~120），且事后证明**我改的那块 buffer 已不再被写**——
   改错了缓冲。
3. **方案三（扒掉命令流缓存）前提不成立**：报告 140 说"525 静态可重放"是**我的误读**——
   实际是**命令条数恒定**，不是内容不变。修正见 §4。

**附带拿到了一个之前没有的东西：ctx 与 obj 的真实地址（硬件断点法），以及 `vbf8=0x1`。**

## 1. 关键技术突破：用硬件断点读 ctx（不碰代码）

### 1.1 为什么之前拿不到

| 方法 | 结果 |
|---|---|
| `gdb -p` 设断点 | ❌ 会写 INT3 到代码段（报告 141 踩过，`41 57`→`cc 57`） |
| `perf probe` + fetch | ❌ **uprobe 不支持内存 fetch**（报 `Please upgrade your kernel to 3.14`，那是 kprobe 才有的能力） |
| tracefs `uprobe_events` + fetch | ❌ 本次被跨版本悬空事件锁死（`EBUSY`） |
| **ptrace + 硬件执行断点（DR0）** | ✅ **成功，且零字节修改** |

### 1.2 实现要点（`analysis/onheap/ctxread2.c`）

```c
ptrace(PTRACE_ATTACH, tid, NULL, NULL);
waitpid(tid, &st, 0);
ptrace(PTRACE_POKEUSER, tid, (void*)848, (void*)bp);   /* DR0 = 断点地址 */
ptrace(PTRACE_POKEUSER, tid, (void*)904, (void*)0x1);  /* DR7: L0=1, RW0=00(执行), LEN0=00 */
alarm(1);                                              /* 必须有超时！ */
while (!timeout) {
    ptrace(PTRACE_CONT, tid, NULL, NULL);
    if (waitpid(tid, &st, 0) < 0) { if (errno==EINTR) continue; break; }
    if (WIFSTOPPED(st) && WSTOPSIG(st)==SIGTRAP) { hit=1; break; }
}
/* 命中断点后 GETREGS 读 rdi，再 PEEKDATA 顺着指针链读 */
ptrace(PTRACE_POKEUSER, tid, (void*)904, (void*)0);    /* 一定清 DR7 */
ptrace(PTRACE_DETACH, tid, NULL, NULL);
```

**三个坑：**

1. **必须设超时**（`alarm`）。我第一次没设，`waitpid` 在没命中的线程上无限阻塞，
   最终被外面 120 s 的 shell 超时杀掉，**Heaven 被 ptrace 挂着**（`TracerPid` 非 0、状态 S）。
   事后 `kill -9` 掉 tracer 才恢复。
2. **多线程要遍历**。24 个线程里只有 `tid=2659742` 命中——渲染线程不是主线程。
3. **DR7 一定要清**。不然 detach 后该线程仍在被调试。

### 1.3 读到的值

```
ctx      = 0x7ff314008ad0
obj      = 0x12771b20
v104     = 3
vbf8     = 0x1          ← 关键
v14      = 1
W(fence) = 0x22f24
```

**`vbf8 = 0x1`，bit1 = 0。** 而 A 路径第二层是 `test byte [r13+0xbf8], 2`（`0x1615850`）。
⇒ **就算把 `v104` 改成 8，第二层仍然拦着。** 所以方案一必须同时改两个字段，否则测不到东西。

## 2. 方案一：改标志（阶梯实验）

### 2.1 结果

| 阶段 | v104 | vbf8 | fps | 最长帧 | >40ms 帧 | 功率 |
|---|---|---|---|---|---|---|
| **[0] 基线** | 3 | 0x1 | **78.62** | 68 ms | 8 | 52.9 W |
| **[1] 只改 v104=8** | 8 | 0x1 | **2.12** | 27 ms | 0 | 55.7 W |
| **[2] v104=8 且 vbf8\|=2** | 8 | 0x3 | **7.50** | **7484 ms** | 0 | 67.4 W |
| **[3] 恢复后** | 3 | 0x1 | 119.38 | 17 ms | 0 | 54.5 W |

### 2.2 判读

**改 `v104=8` 让 fps 从 78.6 掉到 2.12 —— 慢了 37 倍。**

这不是"场景波动"能解释的（数量级差异），也不是"没有效果"（不是持平）。
它是**明确的负面效果**：

- 命令还在发（帧仍能出），但每帧要 470 ms
- 加上第二层放开后出现 **7484 ms** 单帧 —— 相当于卡死
- 功率反而升高（52.9 → 67.4 W）—— 在忙，但产出极低

**结论：`[obj+0x104] == 8` 对应的是一条"慢速路径"**（兼容/回退/逐项处理），
不是"多通道并行加速"。**方案一的假设（这是 525 强制串行化的开关）被证伪。**

### 2.3 对整体判断的意义

这一刀很关键，因为它同时否掉了两件事：

1. **`sub6:0x0034` 不是提速手段**（走那条路的版本更慢）。
2. **515 快不是因为它进了这条路径**。报告 140 里 `sub6:0x0034` 的 416× 差异是
   **"结果"**（不同对象类型走不同代码路径），不是"原因"。

## 3. 方案二：改 pushbuffer 的 subchannel

### 3.1 结果

```
pushbuffer @ 0x7ff2b0e00000 size=0x200000
当前 subchannel 分布 {0: 38820, 1: 8, 2: 416, 3: 21, 4: 43, 5: 11, 6: 42, 7: 209}

基线        fps=71.33   功率=63.4W
改 sub0→6   fps=51.67   功率=63.7W    （改写 38820 处，全部改成 6）
恢复后       fps=118.67  功率=50.9W
```

### 3.2 这个实验失败了，原因有两个

**原因一：三个 fps 不可比。** Heaven 的 fps 在 60~120 之间大幅波动（不同场景段），
单个 3 秒窗口的 fps 没有可比性。71 / 52 / 118 完全落在正常波动范围内。

**原因二（更根本）：我改的那块 buffer 后来不再被写了。**

改完之后做高频采样：

```
1.17 秒内 40 次采样（每 5 ms 一次），变化字全部为 0
```

**说明 Heaven 已经在用另一块 pushbuffer。** 多缓冲轮转的情况下，
"扫一遍当前这块、改掉所有命令头"这种盲改，改到的多半是**已消费或已弃用**的内容。

**→ 方案二在原理上就走不通**：pushbuffer 是 GPU 直接读的 DMA 内存，
要改必须改"写指针之后、GPU 读指针之前"那一小段窗口，而这需要同时拿到读写指针
（本项目只拿到了 fence 序号 `W`，不是写指针）。

**顺带一个观察**：改完 subchannel 后 GPU **没有 hang**，画面也没错乱。
这本身就是"没真正生效"的证据——真把 3D 命令重定向到 subchannel 6（不同的 class），
GPU 会解析失败。

## 4. 方案三：前提不成立 —— 更正报告 140 的误读

### 4.1 报告 140 说错了什么

原文："525 把整个场景的命令流编码一次然后反复重放"、"525 的 pushbuffer 内容是静态的（5 秒内 6 次采样一字不差）"。

**这是我对 `pbmul.py` 输出的误读。** 该脚本统计的是**解出的命令条数**（`cmd_counts`），
不是字节内容：

```
515: [48156, 48601, 48950, ...]   ← 条数在变
525: [31156, 31156, 31156, ...]   ← 条数恒定
```

**"条数恒定" ≠ "内容静态"。** 每帧 draw call 数固定是**完全正常**的
（场景几何不变、只是相机在动），不能推断出"命令流缓存/静态重放"。

### 4.2 实测：这块 buffer 确实是静态的，但那不代表有缓存

```
1.17 秒 × 40 次采样（5 ms 间隔）：变化字 = 0
```

内容真的没变。但结合 §3.2，更合理的解释是：**这块 buffer 当前没在用**
（多缓冲轮转，活跃的是另一块）。

### 4.3 结论

**"525 有命令流缓存、强制序列化"这个假设，没有任何直接证据。**
报告 140 的相应段落应视为**未证实**。方案三因此没有可执行的靶点。

## 5. 三个方案的净结果

| 方案 | 是否执行 | 结果 | 对原假设的判决 |
|---|---|---|---|
| **一：改对象标志** | ✅ 完整执行（含第二层） | fps **78.6 → 2.12**，加第二层出现 7484 ms 卡死 | ❌ **该分支是慢速路径，不是加速开关** |
| **二：改 subchannel** | ✅ 执行（38820 处） | fps 无可比变化（波动内），GPU 未 hang | ❌ **盲改无效**（改到已弃用缓冲） |
| **三：扒掉命令缓存** | ⛔ 未执行 | 前提不成立 | ❌ **前提是误读** |

**三条"强力手段"全部走不通。** 但这轮不是白做——它把三个方向都**排除干净了**：

1. `sub6:0x0034` / `v104==8` 路径 → **不是提速手段**（反而慢 37 倍）
2. pushbuffer 的 subchannel 分布 → **不是可旋的旋钮**（是硬件 class 绑定）
3. 命令流缓存 → **不存在**（或至少无证据）

## 6. 那 515 为什么快？（回到唯一站得住的结论）

经过 136~143 八份报告，所有"软件层可改的东西"都被排除了：

| 层次 | 结论 | 报告 |
|---|---|---|
| ioctl / 内核 | 0.24% 墙钟，无睡眠 | 137/139 |
| GPU 命令数量 | 负相关（525 更少却更慢） | 140 |
| 命令流内容/路径 | 改不动，改了更慢 | 141/142/143 |
| **GPU 执行侧** | **122 µs × 270 次/帧（Heaven）** | **136/138** |

**唯一没被否掉的仍然是：525 的 GPU 在每次"绑定→draw"之后要停 122 µs，而 515 不停。**
这个停顿在 GPU 内部（功耗停在空转底噪、两进程严格 2× 串行、`-R` 不回读时 CPU 只阻塞一次
但 GPU 仍要 132 ms/帧）。**从用户态/内核/命令流三个层次都碰不到它。**
