## 0. 结论

1. **N82-B：没有 20ms/40ms 的硬编码总超时。** `wait_ms` 的三处直接调用点**全是 `esi=2`**，其本体是一次 `pthread_cond_timedwait`，**内部无重试循环、无上限**。截距 20.39ms 不是某个常数。
2. **N82-C：515 的 1.29ms 是两点精确解（残差恒为 0，无验证力），但"16 倍"量级稳健。** 要让截距升到 20.39ms，需要 640×360 那点偏 **+17ms**（→19.3ms），与 525 同分辨率的 21.5ms 无法区分——不可能。⇒ **量级可用，数字精度 ±0.5ms。**
3. **N82-A：定案落在第二档（命令流处理）。** 同一 1080p、同一 525：

| 场景 | `T_land` | 帧率 |
|---|---|---|
| **glxgears**（几个三角形） | **3.0 ms** | 140 fps |
| Heaven **LOW**（千级 draw call，轻 shader） | **26.3 ms** | 38 fps |
| Heaven **HIGH** | **35.1 ms** | 28.4 fps |

**⇒ 如果 20ms 是"fence/timer 固定延迟"，glxgears 也该 ≥20ms。它只有 3.0ms ⇒ 固定延迟假设否定。**
**⇒ T_land 与 shader 复杂度弱相关（LOW↔HIGH 只差 25%），与"场景是否有上千 draw call"强相关（glxgears↔Heaven 差 11.7 倍）。**

## 1. N82-B：`wait_ms` 的所有调用点都是 2ms

### 1.1 三处直接调用

`wait_ms` = `glcore+0x146d280`。全文件 `call rel32` 指向它的共 **3 处**，每处前面都是 `mov esi,0x2`：

| 调用点 | 前置 | 超时 |
|---|---|---|
| `0x146d3c9` | `0x146d3c4: mov esi,0x2` | **2 ms** |
| `0x146ec47` | `0x146ec42: mov esi,0x2` | **2 ms** |
| `0x146ec8c` | `0x146ec87: mov esi,0x2` | **2 ms** |

加上提交器里通过 vtable（`_nv014glcore+0x2d0` / 515 `+0x2b8`）的那处也是 `esi=2`。**没有一处是 20 或 40。**

### 1.2 `wait_ms` 本体没有总超时

```asm
146d280: push r14/r13          ; r13d = esi (ms)
146d284: movsxd r13,esi
146d291: imul r13,r13,0x10624dd3   ; ms → 秒的定点除法
146d29b: imul r14d,ebp,0xf4240     ; ms × 1000000 → ns
146d2b3: ...
146d2e9: cmp ebp,0xffffffff        ; esi == -1 ? 无限等
146d2ec: je  146d2d0
146d306: gettimeofday
146d30b: rdx = tv_sec + (ms/1000)
146d318: rax = tv_usec*1000 + (ms%1000)*1e6
146d321: cmp rax,0x3b9ac9ff        ; 进位处理（1e9）
146d33e: call [nv028glcore+0x100]  ; ★ pthread_cond_timedwait
146d340: test eax,eax
146d342: je   146d2df              ; 成功 → 检查标志 → 返回
146d344: call [nv028glcore+0x150]  ; 解锁/清理
146d350: xor eax,eax  ; return 0
```

**只叫一次 `cond_timedwait`，超时或满足就返回。没有 `N 次轮询` 的循环。**
⇒ **"多次 2ms 轮询"是调用方（提交器的重试循环）造出来的，不是 `wait_ms` 内部。**
⇒ **截距 20.39ms 与"某个 20ms 常数"无关。**

### 1.3 常数扫描（无法定案，但也不必要了）

| 形态 | 命中数 |
|---|---|
| `float 20.0f` | 66 处 |
| `float 40.0f` | 69 处 |
| `mov esi,20` | 284 处 |
| `mov esi,40` | 395 处 |
| `float 0.020f / 0.040f` | 各 2 处（`0xef2fdf`/`0xef2fec`） |

**太泛，无法定位**；而 N82-A 已用实验回答同一问题，这条线不再投入。

## 2. N82-C：`1.29ms` 是换算值，但"16 倍"稳健

### 2.1 性质确认

报告 60 §6.1 的原始表：

| 分辨率 | MiB | 515 | 525 |
|---|---|---|---|
| 1920×1080 | 7.91 | **11.00** | 30.9 |
| 960×540 | 1.98 | **—** | 23.1 |
| 640×360 | 0.88 | **2.37** | 21.5 |

**515 只有两个点。** 两点解二元一次方程是**精确解**，残差恒为 0 ⇒ **没有任何验证力**。
报告 61 §272-276 早已指出"要坐实 515 固定项 ≈1.29ms，需要补第 3 点 960×540"，即待办 **N68-A，从未执行**。

### 2.2 误差传播（这是本轮新增的定量结论）

```
a = 1.290 ms   b = 1.2276 ms/MiB
∂a/∂y1 = −0.1252   ∂a/∂y2 = +1.1252
∂b/∂y1 = +0.1422   ∂b/∂y2 = −0.1422
```

**截距对 640×360 那一点敏感度 1.13 倍**（因为它 x 很小，`a` 几乎就是 `y2` 减去一点点）。

| 单点噪声 σ | a | b |
|---|---|---|
| 0.2 ms | 1.29 ± 0.23 | 1.228 ± 0.040 |
| 0.5 ms | 1.29 ± 0.57 | 1.228 ± 0.101 |
| 1.0 ms | 1.29 ± 1.13 | 1.228 ± 0.201 |

### 2.3 关键：要让截距变到 525 的水平，需要多大的错？

```
要让 a 从 1.29 升到 20.39，640×360 的 T_land 需偏 +17.0ms → 19.3ms
（525 同分辨率实测 21.5ms；两者将无法区分）
```

**⇒ 除非 640×360 那次实测错了近 17ms，否则"截距差 16 倍"这个量级是稳健的。**
**⇒ 结论：`1.29ms` 这个数字精度约 ±0.5ms，但"515 的固定项远小于 525"成立。**

⚠️ 依然建议补 960×540（预测 **3.72ms**，报告 61 写的 3.4ms 是旧系数），这正是 N68-A。

## 3. N82-A：三场景对照，定案

### 3.1 测量方法（这次用全套 10 探针，避免上次的坑）

primus `readback_work` 的循环体（事件流实测顺序）：

```
sem_wait(acqsem) → glWaitSync → glReadPixels → usleep → glMapBuffer → sem_post(relsem) → 循环
   ws_in/out        rp_in/out       us_in/out    mb_in/out
```

探针（`libGL.so.1`）：
`ws 0x18853/0x18859`、`rp 0x18876/0x1887c`、`us 0x18890/0x18895`、`mb 0x18902/0x18908`、`msw 0x19428/0x1942d`

**`T_land` 定义为 `usleep + glMapBuffer`**（异步回读真正落地的时刻）。

### 3.2 四个配置（全部 1920×1080，525，`vblank_mode=0`）

| 场景 / 配置 | `glWaitSync` | `glReadPixels` | **`usleep`** | **`glMapBuffer`** | **`T_land`** | 帧间隔 / fps |
|---|---|---|---|---|---|---|
| **glxgears** SLEEP=90 | — | — | — | **0.266** | **3.10** ¹ | 6.57 ms / **152** |
| **glxgears** SLEEP=0 | — | — | — | **2.920** | **3.03** ¹ | 6.49 ms / **154** |
| **Heaven LOW** SLEEP=90 | — | — | — | **2.656** | **26.3** ² | 26.29 ms / **38** |
| **Heaven HIGH** SLEEP=90 | 0.007 | 0.105 | **31.396** | **3.545** | **35.05** | 35.17 ms / **28.4** |

¹ glxgears 用 4 探针采（`p_ws/p_rp/p_mb/p_mbd`），`T_land` = `p_rp→p_mb` + `p_mb→p_mbd`；两项之和在 SLEEP=90 与 SLEEP=0 下**相等**（3.10 vs 3.03ms）。
² Heaven LOW 同样用 4 探针：`p_rp→p_mb` 23.644 + `glMapBuffer` 2.656 = 26.3ms。

### 3.3 判读

用户给的两档判据：

| 判据 | 结果 |
|---|---|
| 最小场景仍有 ~20ms → **固定延迟**（fence/timer） | ❌ **glxgears 只有 3.0ms** |
| 掉到 <2ms → **命令流处理** | ✅ **落在这一档**（3.0ms，且 Heaven 高到 26~35ms） |

**三条支撑：**

1. **glxgears 的 3.0ms ≈ 纯带宽时间**。8.29 MiB / 3.0ms = 2.76 GB/s，接近 PCIe Gen1×16 有效线速（3.2 GB/s）。
   ⇒ 最小场景下 `T_land` 就是"把 8.29MB 搬过来"的时间，**没有额外固定项**。
2. **Heaven LOW vs HIGH 只差 25%**（26.3 vs 35.1ms）。LOW 大幅降低 shader/后处理负担，但 **draw call 数量不变**。
   ⇒ `T_land` 与"shader 复杂度"弱相关。
3. **glxgears vs Heaven 差 11.7 倍**。唯一显著不同的是**场景的 draw call 数量**（几个 vs 上千）。
   ⇒ **`T_land` ∝ 场景规模（draw call 数量级）**。

**⇒ 20.39ms 的截距 = "GPU 在把这一帧的上千条命令消化完"的时间，不是驱动里的固定等待。**

这与报告 70 §5.5 的估算**对上了**：`20.25ms ÷ ~1000 次 ≈ 20µs/次`。

### 3.4 附带解释了一个旧谜团：`autosleep` 为什么关不掉

`PRIMUS_SLEEP` 的机制是 `sleep = (map_time + sleep) × autosleep/100`，稳态下 `sleep ≈ 9 × map`。
Heaven HIGH：`map 3.545 × 9 = 31.9 ≈ usleep 31.396` ✓ **严丝合缝。**

但关掉它（SLEEP=0）后：

| | `usleep` | `glMapBuffer` | 帧周期 |
|---|---|---|---|
| Heaven HIGH, SLEEP=90 | 31.4 | 3.5 | 35.2 |
| Heaven HIGH, SLEEP=0 | 0 | **29.6**（trace2）/ **37.8**（trace3） | 29.8 / — |
| **glxgears, SLEEP=0** | 0 | **2.92** | 6.49 |

**Heaven 关掉 autosleep 后 `map` 涨到 29.6~37.8ms，glxgears 关掉后 `map` 只 2.92ms。**

⇒ **autosleep 那个 `usleep` 实际上在"给 GPU 让时间"**：worker 睡 31ms 的期间，GPU 在处理这一帧；等 worker 醒来 map 时数据已经好了，只要 3.5ms。
关掉它，worker 每帧立刻要数据，GPU 还没处理完 ⇒ `map` 就必须自己等满 29~38ms。

**⇒ "关掉 autosleep 无效"的真正原因：瓶颈在 GPU 处理节奏，`usleep` 只是把这个节奏包装成固定节拍。**
（报告 59/72 观察到"关掉无效"是对的，但当时的解释"让出时间被别人占走"不准确。真实机制是：**让出的时间被 `glMapBuffer` 原样吃回去了**。）

## 4. 两个对自己上轮的更正

### 4.1 报告 72 的 worker 分段表有错

报告 72 §1 的表：

```
| glReadPixels | 0.146 ms | 0.4% |
| p_rp→p_mb（= sem_post + usleep + sem_wait）| 30.191 ms | 90% |
```

**问题一**：`0.146ms` 这个数字**是错的**（来自另一次采集的 `rp` 段，被我误抄）。
**问题二**：那张表的其余项也是拿 `p_rp→p_mb` 当"glReadPixels"算的，把 `usleep` 混进去了。

**正确的 Heaven HIGH 分解（本轮全套 10 探针）**：

| 段 | 中位 | 占帧 |
|---|---|---|
| `glWaitSync` | 0.007 ms | 0.02% |
| `glReadPixels`（本体） | **0.105 ms** | 0.3% |
| **`usleep`** | **31.396 ms** | **89.3%** |
| `glMapBuffer` | **3.545 ms** | 10.1% |
| 合计 | 35.05 ms | 99.7% |

**教训**：`p_rp→p_mb` 跨了 `glReadPixels` + `sem_post` + `usleep` + `sem_wait` 四件事。
**用两个探针的间隔命名一个调用，必须确认这两点之间只有那一个调用**（这与技能库里"地址相邻 ≠ 间隔只含中间调用"是同一条，我违反了第二次）。

### 4.2 报告 72 §4 的"0 次也是 38ms"结论对、理由错

报告 72 用"`wait_ms` 次数 = 0 的 68 帧也是 38.28ms"推出"轮询不是成因"。**结论碰巧成立，但样本有问题：**

- **同一配置（SLEEP=0）两次采集，`glMapBuffer` 次数 342 vs 263（差 30%）** ⇒ **Heaven 在循环场景，两次采的不是同一段**。
- 复查那 68 帧的原始事件：`p_mb → p_mbd` 之间**确实没有本线程的 `wait_ms`**，但**全系统有 19 次**（分布在 68815/68830 上）。
- 且 `wait_ms` 被**四个线程**使用：`68829` 间隔中位 **2.069ms**（真睡），`68815` **0.191ms**、`68830` **0.082ms**、`68785` **0.119ms**（都是立刻返回）。

**⇒ 正确说法**：存在**两类帧**——一类 map 期间以 2.1ms 周期轮询 17~20 次，另一类整帧不轮询；**两类 map 时长都是 37~38ms**。所以"轮询次数不是成因"仍成立，但依据是"**两类帧时长相同**"，不是"0 次档"。

## 5. 方法论（已入技能库）

1. **★ 分析脚本必须打印它读的是哪个文件。**
   本轮 `n80b_full.py` 里路径是硬编码的，我拿四个 trace 去跑，**四次输出完全相同**——脚本一直在读同一个文件，静默给出看似合理的结果。
   **规矩：脚本第一行 `print('FILE =', path)`；批量跑时用文件名做标题。**

2. **★★ 判"固定延迟 vs 负载相关"，换负载比换参数快。**
   本轮只用 `glxgears`（140fps）就一步否掉"20ms 固定延迟"，比继续解派发表便宜得多。
   **判据：如果最小负载下那个"固定项"消失，它就不是固定项。**

3. **★ "画质"和"规模"要分开调。**
   Heaven LOW↔HIGH 只改 shader/后处理（差 25%），glxgears↔Heaven 改的是 draw call 数量（差 11.7 倍）。
   **想验证"命令流处理"，必须换数量级的场景，不是换画质档。**

4. **★ 同一配置两次测差异 >10%，先怀疑"环境在变"（场景/负载/相位），不要当成噪声。**
   本轮 342 vs 263 次 map 就是 Heaven 切场景。`glxgears` 两次测 3.10 vs 3.03ms（差 2%），是可信的基准。

5. **★★ `usleep` 关掉后时间涨到"map"上，说明 `usleep` 在给下游让时间。**
   判据：关掉后 `map` 涨幅 ≈ 睡眠时长（Heaven：31.4 → map 涨到 29.6~37.8）；
   而最小场景关掉后 `map` 不动（glxgears：0.27 → 2.92，因为本来就没睡多少）。
   **⇒ "关掉无效"不等于"它不是瓶颈"，要看它替谁挡了时间。**

## 6. 现在的收口

> **525 上，一帧的 `T_land` 与场景规模成正比：**
> **glxgears 3.0ms / Heaven-LOW 26.3ms / Heaven-HIGH 35.1ms。**
> **这不是驱动里的固定延迟，而是"GPU 消化这一帧命令流"的时间。**
> **515 在同一 Heaven 场景下 `T_land = 11.00ms` ⇒ 525 的每 draw call 开销约为 515 的 2.5~3 倍。**

**已排除（累计）**：primus 4 可动点、GLX 三层、glcore 等待机制（四项同构）、调度延迟（3µs）、`glWaitSync`、`glMapBuffer` 内部逻辑、`wait_ms` 2ms 轮询、flags gate 版本差异、GPU 降频/限流/带宽饱和、**固定延迟（本轮）**、**20/40ms 硬编码超时（本轮）**。

**唯一剩下的靶点，换了表述**：

> **同一个 Heaven 场景、同一张 P106，525 让 GPU 每帧多花 2.5~3 倍时间消化同样的命令流。**
> 这不是"回读慢"，是"**GPU 提交/处理慢**"。
