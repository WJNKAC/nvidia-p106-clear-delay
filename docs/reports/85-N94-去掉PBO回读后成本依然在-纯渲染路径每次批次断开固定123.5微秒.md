# 85 · N94：去掉 PBO/回读后成本依然在——纯渲染路径里每次「绑定+紧跟 draw」固定 123.5µs

日期：2026-10-26 13:50
驱动：525.116.03
方法：`pair_only`（自写，**无 PBO、无回读、无 fence**，只做 N 次「绑定+draw」+ 末尾一次 `glFinish`）

---

## 0. 四条结论

1. **成本与回读/PBO 完全无关**：把 PBO、glReadPixels、fence 全部去掉，只做渲染循环：

| `pair_only`，N=1000，1080p | 整帧墙钟 p50 |
|---|---|
| kind=0：`glColor3f` + draw（legacy 状态） | **0.163 ms** |
| **kind=1：`glUseProgram` 切换 + draw，k=1** | **123.876 ms** |
| kind=1，k=1000（只切 1 次） | **0.229 ms** |

   ⇒ **123µs/次 是渲染路径自身的行为**，此前所有"回读窗口"口径（报告 76/83/84）只是它的**观测窗口**，
   不是它的来源。这条把"读回/PBO/DMA"整类彻底排除。

2. **与主机调度无关**：6 个 `yes` 打满 CPU 前后 —— **123.4 / 124.8 / 123.8 ms**（±1.1%）
   ⇒ 不是"主机轮询周期/调度延迟"决定，是**固定成本**。

3. **与"绑什么"无关**（报告 84 §2bis）：program / FBO / texture 三种绑定 ~120–122µs，差 <2%。

4. **成本落在"绑定之后紧跟的那个 draw"上**（报告 76 的 M9/M8 已证：先切 1000 次再画、或切 1000 次只画 1 个，都免费）
   ⇒ 准确表述：**每次「批次断开」（绑定后第一个 draw）固定 123.5µs**。

## 1bis. ★ GPU 自己的时间轴也被拉长：不是主机在卡

在 `pair_only` 里用 timer query 夹住整个循环（q0 在循环前、q1 在 `glFinish` 前）：

| | 墙钟 p50 | **GPU_span（q1−q0）** |
|---|---|---|
| kind=0（legacy 状态） | 0.269 ms | **0.157 ms** |
| **kind=1（program 切换）** | 134.8 ms | **122.2 ms** |

⇒ **GPU 的时间戳跨度也是 122ms**：不是"主机在循环里卡住而 GPU 闲着"，
而是**GPU 自己的时间轴被拉长了**——它在每个批次断开处停住 ~122µs。
（配合报告 83 的 37.5W/100% util：GPU 在等，但计时器在走。）

这把"主机侧轮询/调度"也排掉（与 §0.2 的 CPU 满载 ±1% 互证）：
**等待发生在 GPU 内部，不是主机。**

## 2. 这条结论对"规避"的意义

- **没有任何驱动开关能关掉它**（regkey 全 32 位、env 全试）⇒ 只能从"减少批次断开次数"入手；
- **批次断开次数 = 应用每帧的管线绑定次数**（Heaven ≈268）⇒
  应用侧优化（按材质/程序排序、减少 program/texture/FBO 切换）能线性降低这项成本：
  **每减少 100 次绑定，帧时间减少 12.3ms**（1080p/Heaven 尺度）；
- 换 515 或走 Vulkan 仍是最省事的规避（515：同样负载 0.03µs/次）。
