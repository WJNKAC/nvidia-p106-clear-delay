# 报告 141 — 追 sub6:0x0034 的生成点：找到唯一调用点、读到真实标志值，但结论是"它不是主来源"

> 编号：141（对应 N150）
> 日期：2026-10-27
> 平台：P106-100 / Heaven 4.0 OpenGL 1920×1080
> 前置：报告 140（发现 515 命令多 60~100% 却快 20 倍；`sub6:0x0034` 相差 416×）

---

## 0. 三句话结论

1. **`sub6:0x0034` 的生成点被唯一定位到**：525 `0x1615870`（函数 `0x16154c0`..`0x1615970`，1200 B）/
   515 `0x1054c45`（函数 `0x10549d0`..`0x1054d60`，912 B）。**两个 .so 里各只有 1 处立即数命中。**
2. **判据相同、真实值不同**：两版都要求 `[ctx+0x1300]+0x104 == 8` 才进；**525 上实测该值恒为 3（644/644 次），
   所以那段代码一次都没执行** —— 与"函数入口 1176 次/10s、立即数点 0 次"完全吻合。
3. **但这不是答案**：515 上同样那条路径（`0x1054c20`）实测也是 **0 次/6s**（函数入口 1332 次）。
   ⇒ **两版的 `sub6:0x0034` 都不来自这段代码。** 报告 140 里 416× 的差异，来源仍在别处。

---

## 1. 定位过程与结果

### 1.1 命令头解码给出搜索键

```
sub6:0x0034 → (cnt<<16) | (6<<13) | (0x34>>2)
            → 低 16 位固定 = 0xC00D
```

搜 64 位立即数 `0x2001C00D`（cnt=1 的最常见形态），**两版各只有 1 处**：

| 版本 | 文件偏移 | 指令 | 所属函数 |
|---|---|---|---|
| 525.116.03 | `0x1615870`（在 `movabs` 内） | `movabs rax, 0x800000002001c00d` | `0x16154c0`..`0x1615970`（1200 B） |
| 515.105.01 | `0x1054c45`（在 `movabs` 内） | `movabs rdi, 0x800000002001c00d` | `0x10549d0`..`0x1054d60`（912 B） |

**一条 64 位指令同时写入命令头 + 参数**（`0x2001c00d` 是命令头，`0x80000000` 是参数）。

### 1.2 函数边界怎么定的

`n131a_funcmap.py` 靠 `endbr64` 建函数表——**本项目不可用**（glcore 没开 CET，`endbr64` 数量 = 0）。
改用 `n131b_ehframe.py`（解析 `.eh_frame_hdr` 的二分表）：525 有 **79,245** 个 FDE，515 有 **58,145** 个。

```
525: 0x1615870 ∈ 函数 0x16154c0..0x1615970  长 1200 B  内偏移 +0x3b0
515: 0x1054c45 ∈ 函数 0x10549d0..0x1054d60  长  912 B  内偏移 +0x275
```

### 1.3 两版代码逐段对照

**函数入口的判据完全相同：**

| | 525 (`0x16154f1`) | 515 (`0x1054a01`) |
|---|---|---|
| 取对象 | `r13 = [rdi+0x1300]` | `rbp = [rdi+0x12a0]` |
| 判据 | `cmp dword [r13+0x104], 8` | `cmp dword [rbp+0x64], 8` |
| 成立则跳到 | `0x1615850` | `0x1054c20` |

（`0x1300/0x104` 与 `0x12a0/0x64` 是同一个结构在不同版本里的偏移，差值都是 `0x13c0-0x6c` 的固定漂移。）

**进入之后，第二层判断的形态不同：**

| | 525 (`0x1615850`) | 515 (`0x1054c20`) |
|---|---|---|
| 测试 | `test byte [r13+0xbf8], 2` | `test byte [rbp+0xb10], 2` |
| 不满足 | `je 0x1615502` —— **整块不发** | `je 0x1054d40` —— **整块不发** |
| 满足 | `mov [rax], 0x8000c014` → `test dword [rbx], mask` → **`movabs 0xd` + `movabs 0xb` + `cmove`**（二选一，**总发一条**） | `mov [rax], 0x8000c014` → `test dword [rbx], mask` → `movabs 0xd`（直接发） |
| 掩码 | **`0x7f8ae00`** | **`0x378ae00`** |

**这里有一个真实的形态差异**：525 用 `cmove` 在 `0x2001c00d` 和 `0x2001c00b` 之间二选一（**无条件发一条**），
515 是条件跳转直接跳过。**但实测显示这段在两版上都没被执行**，所以这个差异本轮不构成解释。

## 2. 动态验证：读到真实值，结论反转

### 2.1 525 上实测

| 探针 | 结果 |
|---|---|
| 函数入口 `0x16154c0` | **1,176 次 / 10 s** |
| 立即数点 `0x1615870` | **0 次 / 10 s**（且该地址落在 `movabs` 立即数中间，uprobe 挂不上） |
| `cmp` 处 `0x16154f1` 读 `[r13+0x104]` | **644 次，全部 = 3** |

**判据要求 `== 8`，实际恒为 3 ⇒ 那条 `je` 永远不成立 ⇒ 那段代码是死路径。**

这解释了报告 140 里 525 的 `sub6:0x0034` 只有 **16 条**（全都是别的来源）。

### 2.2 515 上实测（关键的反证）

| 探针 | 结果 |
|---|---|
| 函数入口 `0x10549d0` | **1,332 次 / 6 s** |
| A 路径入口 `0x1054c20`（`test [+0xb10],2`） | **0 次 / 6 s** |

**515 的同一条路径也是 0 次。** 所以：

> **两版的 `sub6:0x0034` 都不来自这段代码。**
> 报告 140 里 515=6,653 vs 525=16 的 416× 差异，**来源仍未定位**。

## 3. 这次为什么没追到底（诚实复盘）

### 3.1 我用错了第一个判据

`sub6:0x0034` 是**从 GPU 命令流反推出来的**，但"命令头立即数"在 glcore 里可能根本不以
`0x2001C00D` 这个字面值出现 —— 完全可能由**基址 + 偏移**在运行时拼出来：

```
命令头 = base | (cnt<<16) | (sub<<13) | (meth>>2)
```

如果 `base` 是个变量、只有 `(sub<<13)|(meth>>2)` 是常量 `0xC00D`，那我搜 `0x2001C00D` 就必然漏掉。
**`0x2001C000` 在 525 里有 6 处、515 里也有 6 处** —— 这些也是候选，我只挑了"cnt=1"的那一个。

### 3.2 搜到了但没继续分

`0x2001C000` 的 6 处（525）：`0x1616cbf, 0x161748e, 0x16174eb, 0x183d9d9, 0x183d9fb, 0x25293cf`
—— **其中 2 处在 `.rodata`（`0x25293cf` 之后），4 处在 `.text`。** 我只追了 1 处就下了结论。

### 3.3 结论：这条线需要换方法

静态搜立即数只适用于"字面常量"；对"基址+偏移拼装"的命令头必须换方法：

1. **搜 `(sub<<13)|(meth>>2)` 这个 16 位常量在 .text 里的所有引用**（不只 cnt=1 的形态）
2. **动态抓 pushbuffer 写入点**：在 pushbuffer 映射区挂 uprobe 不可行（那是 mmap 的 DMA 内存），
   改为**在写 pushbuffer 的那个函数上挂**（用 `-V` / 报告的 `glprobe` 思路先找到"当前写指针"的写入者）
3. **放弃 method 级精确对应**，改用"功能性判据"：515 多用 subchannel 6、525 几乎不用 ——
   这个**结构性结论**（报告 140 §3.4）已经足够支撑"两版走了不同的队列分配策略"，
   不需要知道具体是哪条指令生成的。

## 4. 本轮确实拿到的（可用的部分）

| 项 | 值 |
|---|---|
| `sub6:0x0034` 的唯一字面生成点 | 525 `0x1615870` / 515 `0x1054c45`（函数 `0x16154c0` / `0x10549d0`） |
| 两版该函数的判据 | **完全相同**：`[ctx+0x1300]+0x104 == 8` |
| 该判据在 525 上的真实值 | **恒为 3**（644/644） |
| 该路径在两版的执行次数 | **都是 0** |
| 函数本身调用频率 | 525 1,176/10s；515 1,332/6s（≈ 222/s，**每帧约 4 次**） |
| 525 的第二层形态 | `cmove` 二选一（`0xd` / `0xb`），掩码 `0x7f8ae00` |
| 515 的第二层形态 | 条件跳过，掩码 `0x378ae00` |

**最后两条是真实的代码差异，只是它不在被执行的路径上** —— 说明两版对这个功能都有"两条路径"，
本次 Heaven 场景走的是另一条（`[0x104] != 8` 的那条），而我还没定位到它。

## 5. 操作事故：我把目标进程的代码改坏了

用 `gdb -p` 想读寄存器，遇到 `ptrace: 不允许的操作`（yama 限制）。
gdb 在 attach 失败前**已经写入了 INT3 断点字节**，于是 `0x16154c0` 的首字节被改成 `0xcc`：

```
改前（正常）: 41 57 41 56 41 55 41 54   → push r15; push r14; push r13; push r12
被 gdb 改坏: cc 57 41 56 41 55 41 54   → int3
```

后果：该地址的 uprobe 挂不上（`I/O error`），后续测量全部失效。
**已用 `/proc/PID/mem` 写回 `0x41` 修复**（`4157...` 恢复）。

**纪律**：
1. `gdb -p` 前先确认 `ptrace_scope`：`cat /proc/sys/kernel/yama/ptrace_scope`（本机为限制模式）
2. gdb attach 失败**不等于没有副作用** —— 断点字节可能已写入
3. attach 前记录目标地址的原始字节，失败后立刻核对
4. **优先用 tracefs uprobe 的内存 fetch，不要用 gdb 打断点**（不侵入、无残留）

## 6. 给下一步的具体建议

**不要再静态搜 `0x2001C00D`。** 换成：

```python
# 搜所有 (sub<<13)|(meth>>2) 形态，不限 cnt
for sub in range(8):
    for meth4 in range(0, 0x2000, 1):        # meth/4
        low16 = (sub << 13) | meth4
        if low16 == 0xC00D:                   # sub=6, meth4=0x0D
            ...
# 关键：搜的是 16 位常量 0xC00D 被 load 的位置，而不是 32 位命令头
```

即：**找 `mov cx, 0xc00d` / `or eax, 0xc00d` / `add ..., 0xc00d` 这类 16 位操作**，
而不是 `movabs 0x2001c00d`。

**或者直接放弃这条线**：报告 140 的"515 大量用 subchannel 6、525 几乎不用"这个结构性事实，
已经足够支撑结论方向；再往下挖的具体指令对应，收益/成本比不高。
