# 57 · N60：**`st` 段只有 5.3ms，不是 20ms**；但找到了真正的对应量 —— `SW→MBO` = 21~24ms

> 2026-10-26 08:45
> 用户判断：`st` 段（等 display worker 上屏）可能就是那 20.4ms 固定项，并给出修复路径（primus 异步化/多缓冲）。
>
> **结果：假设只对了一半，但这一半非常关键。**
> 1. **`st` 段实测 5.34ms，不是 20ms** —— display worker 不是主因。
> 2. **但找到了与 20.4ms 数量级吻合的量：`SW→MBO` = 21~24ms**（换到 map 完成）。
> 3. **map 完成总在下一次 swap 之后约 24ms** —— 回读被 swap 周期闸住，即**一帧流水线延迟**。

---

## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **报告 42 的 `st` 偏移（`0x18755`）是错的** | 全库 `call sem_timedwait@plt` **只有 1 处**（`0x186aa`，reinit 分支），不是每帧路径 |
| 2 | **真正的 `st` = `0x18a2d`**（`sem_wait(&di.d.relsem)`，等 display worker） | `0x189a9 sem_post(&d.acqsem)` → 查 `0x41154`(primus.sync) → `jne 18a28` → `18a2d call sem_wait` |
| 3 | **`st` 只在 `primus.sync != 0` 时走** | default/sync0 下 `ST` 命中 **0 次** |
| 4 | **`st` = 5.34 ms（不是 20 ms）** | sync1 下 164 次命中，中位 5.34ms、p90 6.77ms |
| 5 | **★ `SW→MBO` = 24.11 / 23.63 / 20.90 ms**（三种模式） | 与固定项 20.4ms **数量级吻合** |
| 6 | **map 总在"下一次 swap"之后约 21~24ms 才完成** | RP→SW 6.7ms，SW→MBO 24.1ms，RP→MBO 30.9ms |
| 7 | **sync1 让 map 从 30.6 降到 19.0ms，但 st 吃掉 5.3ms，fps 不变** | 32.8 vs 32.6 |

**一句话**：**固定项不是"等 Intel 上屏"（5.3ms），而是"回读完成被 swap 周期闸住"（21~24ms）。**

## 2. 修正报告 42 的 st 偏移

### 2.1 全库搜 `sem_*` 调用

```bash
$ objdump -d libGL.so.1 | grep "call.*<sem"
   186aa:  call sem_timedwait@plt     ← 唯一一处
   1870a:  call sem_wait@plt
   189a9:  call sem_post@plt
   18a2d:  call sem_wait@plt
   ...
```

**`sem_timedwait` 全库只有 1 处**，在 `0x186aa`。而它的上下文：

```asm
1869e: jmp  18705
186a0: mov  0x10(%rsp),%rsi
186a5: mov  0x20(%rsp),%rdi
186aa: call sem_timedwait          ← 只有 reinit 才会到这里
186b1: je   1899e
186b7: mov  0x41158,%eax           ← 检查 autosleep/log 级别
186dc: call fwrite                 ← "dropping a frame to avoid deadlock"
```

**这是 `if (di.r.reinit)` 分支里的 `sem_timedwait`（resize 用），稳态不经过。**
→ **报告 42 挂 `0x18755` 得 0 命中，不是偏移可疑，是那条路径本来就不走。**

### 2.2 真正的每帧 `st` 段

```asm
189a9: lea  0xc8(%r14),%rdi
189a9: call sem_post              ; sem_post(&di.d.acqsem) ← 把数据交给 display worker
189ae: mov  0x41154(%rip),%edx    ; 读 primus.sync
189b6: jne  18a28                 ; sync != 0 → 去等
189b8: ...                        ; sync == 0 → 直接继续（不等）
18a28: mov  0x20(%rsp),%rdi       ; = r14+0xe8 = &di.d.relsem
18a2d: call sem_wait              ; ★ st 段：等 display worker 完成上屏
18a32: lea  0x98(%r14),%rdi
18a39: call sem_post              ; sem_post(&di.r.relsem)
```

**这就是源码里 `if (primus.sync) { sem_wait(&di.d.relsem); sem_post(&di.r.relsem); }`。**

## 3. 三种 sync 模式的实测

`n60_swap_st.sh`：6 探针（`RP` 带参数 / `MB` / `MBO` / `ST` / `STO` / `SW`），每档 5 秒。

| 模式 | RP→SW | **SW→MBO** | map (MB→MBO) | **ST（等显示）** | 帧数 | fps |
|---|---|---|---|---|---|---|
| **default** | 6.70 ms | **24.11 ms** | 30.74 ms | **0 次** | 163 | 32.6 |
| **PRIMUS_SYNC=0** | 7.00 ms | **23.63 ms** | 30.61 ms | **0 次** | 164 | 32.8 |
| **PRIMUS_SYNC=1** | 30.46 ms | **20.90 ms** | **18.98 ms** | **5.34 ms** | 163 | 32.8 |

### 3.1 关键：`SW→MBO` 在三种模式下都是 21~24ms

**这个量不随 sync 模式变**：
- sync0：23.63 ms
- default：24.11 ms
- sync1：20.90 ms

**而报告 56 拟合出的固定项是 20.39ms。**

→ **`SW→MBO`（从 swap 到 map 完成）就是那个"固定项"。**

### 3.2 map 总在下一次 swap 之后

以 default 为例，一帧内部的时序：

```
t=0        RP（readPixels 提交）
t=6.70ms   SW（swap）
t=30.8ms   MBO（map 完成）      ← 在 SW 之后 24.11ms
```

**→ 帧 N 提交的回读，要等到帧 N+1 的 swap 之后 ~24ms 才可读。**

これは —— 这就是"一帧流水线延迟"的形状。

### 3.3 sync1 的特殊行为（说明 sync 改变了流水线结构）

| | default/sync0 | sync1 |
|---|---|---|
| RP→SW | 6.7 ms | **30.5 ms**（主线程被 st 卡住，swap 推迟） |
| SW→MBO | 24.1 ms | 20.9 ms |
| map | 30.6 ms | **19.0 ms** |
| ST | 0 | 5.34 ms |
| **fps** | **32.6** | **32.8** |

**sync1 把 map 从 30.6 降到 19.0（-11.6ms），但代价是主线程每帧多等 5.3ms + swap 被推迟。净 fps 不变。**

原因：sync=1 时 worker 映射的是**上一帧的 PBO**（`cbuf^1`），那份 DMA 有整整一帧时间完成，所以 map 更快。
但主线程必须在 display worker 完成后才能继续 → 串行化，省下的被吃掉。

## 4. 所以"固定项 20.4ms"到底是什么

**不是 display worker 的 `sem_wait`（5.3ms）。**

**是"从 swap 到回读数据可被 CPU 映射"的延迟（21~24ms）。**

### 4.1 这个延迟的物理含义（两种可能）

| 可能 | 含义 | 判据 |
|---|---|---|
| **A. DMA 只在 present 之后才启动** | 回读拷贝被排在 present 后面 | `SW→MBO` ≈ 24ms 且与 map 高度相关 —— **符合** |
| **B. present 到 DMA 完成之间有一段固定管线** | Intel 显示管线 / NVIDIA 合成 / X 合成器 | 若把 swap 去掉（headless）延迟应消失 |

**两种都是"回读被 present 周期闸住"，本质相同：回读没有独立于上屏。**

### 4.2 为什么隔离环境没有这 20.4ms

| | 有 swap 驱动 | 固定项 |
|---|---|---|
| 隔离环境（rb_lat5/6） | **单线程，readPixels 后立刻 map，无 present** | **≈0** |
| 真实 primus | 每帧 swap（pbuffer 前后台切换 + Intel 上屏） | **20.4ms** |

**→ 差异是"有没有 present 参与"。这与报告 55 的结论一致：结构差不在 GL 调用顺序，在"有没有上屏"。**

### 4.3 为什么 N25（双线程复刻）也没有 20ms

N25 复刻了 `render→swap→fence→post` / `wait→waitSync→readPixels→post→map`，
**但那个 swap 是 pbuffer 的 swap，没有 Intel 上屏（没有 display worker）。**

→ **说明"pbuffer swap"本身不足以产生 20ms，还需要 display worker 的 `glTexSubImage2D + glXSwapBuffers(ddpy)` 这一步。**

**这是一个新的、可检验的推论**：把 display worker 停掉（不调用 `glTexSubImage2D`/`glXSwapBuffers(ddpy)`），
`SW→MBO` 应该从 24ms 掉到接近 0。

## 5. 修复路径（比用户原来的方案更具体）

用户提的两条（display worker 异步化、双/三缓冲）**仍然对，但理由变了**：

| 用户的方案 | 针对 | 是否有效 |
|---|---|---|
| display worker 异步化 | `st` = 5.3ms | **有效但只省 5.3ms** |
| 双/三缓冲 | `st` 串行化 | **有效但同样只 5.3ms 级** |
| **★ 让回读不依赖 present** | `SW→MBO` = 24ms | **这才是 20.4ms 的靶点** |

### 5.1 具体怎么改（primus 开源，有源码）

`readback_work` 的回读源是 **pbuffer 的 GL_FRONT**（报告 42 已确认）：

```c
primus.afns.glReadBuffer(GL_FRONT);   // 读 pbuffer 前台（= swap 后的结果）
```

**主线程 swap 把 BACK 换到 FRONT → 回读读 FRONT → 而下一次 swap 会把它换走。**
所以驱动必须保证"读到的是稳定帧" → **回读被串行化到 swap 周期上。**

**改法**：让应用渲染到 **FBO**（application-owned），primus 回读这个 FBO 的 color attachment。
FBO 不参与 swap，回读就不会被 present 周期闸住。

> ⚠️ **注意**：报告 42 测过"FBO vs pbuffer"在**隔离环境**下只差 0.115ms（2.487 vs 2.602）。
> 但那是因为隔离环境**没有 present**。**在有 present 的真实环境里，两者的差别可能是 20ms 级的** ——
> 这个推论需要验证（N61）。

## 6. 下一步（一条，且能直接验证第 4.3 的推论）

**N61：把 display worker 停掉，看 `SW→MBO` 是否从 24ms 掉下来。**

两种做法，都在 primus 源码层（有源码 `analysis/src/primus_libglfork.cpp`）：

| 做法 | 改动量 | 预期 |
|---|---|---|
| **A. 让 `display_work` 直接 `return`（不调用 `glTexSubImage2D`/`glXSwapBuffers(ddpy)`）** | 1 行 | 若 `SW→MBO` → 接近 0：**确认 20.4ms 来自 Intel 上屏这一环**；若不变：说明是 pbuffer swap 本身 |
| B. 让主线程渲染到 FBO，回读 FBO | 中等 | 若 map 掉到 ~3ms：**确认"回读被 present 闸住"，且给出可用的修复** |

**A 只要 1 行改动，先做 A。**

**这是第一次真正需要改被测软件**（primus），但改动极小（注释掉两次 GL 调用），
而且能一次性确认 20.4ms 的归属。

### 7.1 三个方法论要点

1. **`sem_timedwait` 全库只有 1 处，但它在 reinit 分支** ——
   报告 42 挂 `0x18755` 得 0 命中，我当时以为"偏移可疑"，其实是**那条路稳态不走**。
   **规矩**：0 命中要先分清"偏移错"还是"路径不执行"——**看这个调用点所在的控制流**。

2. **想知道"谁在闸住谁"，要算"跨线程的事件间隔"**。
   本例 `RP→MBO`=30.9ms 只是总量；拆成 `RP→SW`(6.7) + `SW→MBO`(24.1) 才看出**闸门在 SW 之后**。

3. **换一个环境变量（`PRIMUS_SYNC`）就能改变流水线结构**，是廉价的结构探针。
   本例 sync=1 让 map 从 30.6→19.0ms，说明 map 的时长**依赖它映射的是哪一帧的缓冲**，
   进而证明"回读完成与帧序强耦合"。
