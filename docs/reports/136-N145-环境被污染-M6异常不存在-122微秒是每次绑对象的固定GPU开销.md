# 报告 136 — 环境被污染：M6"异常"不存在，122 µs 是每次"绑对象→draw"的固定 GPU 侧开销

> 编号：136（对应 N145）
> 日期：2026-10-27
> 驱动：525.116.03 / P106-100 / 内核 6.1.0-50-amd64
> 结论强度：**推翻报告 133/134 的数值与"F. M6 反常"整个候选；重写因果模型**

---

## 0. 一句话结论

**测试机上残留了 8 个我自己的 `while true; n83a -M 3` 保活循环，从 07:48 一直跑了一小时二十分钟。**
报告 133/134 里"M3 260 ms""M6 396 ms""空闲功耗 36.9 W"全部是在这堆循环同时抢 GPU 的情况下测出来的。
清干净后重测：M6 = 129.55 ms，M3 = 126.98 ms —— **只差 2%，"切同一 program 更慢 50%"这个反常根本不存在**，
`F. M6 反照`这个最有价值的靶点作废。

真正的结构（干净、可复现到 ±0.1%）：

> **每做一次"绑定对象 → draw"，就要多花 122 µs，且这 122 µs 完全发生在 GPU 侧、GPU 期间处于上电空转。
> 与对象类型（program / FBO / 纹理）无关，与渲染分辨率无关，与批次数无关，只与"绑定次数"成正比。
> 两个进程并发时严格 2× 串行。**

## 1. 污染的发现与清除

```
$ ps -eo pid,lstart,etime,args | grep "while true; do <workdir>"
  29211 二 10月 27 07:48:45 2026  01:20:32  bash -c while true; do n83a -M 1 -n 300 ...
  29226 二 10月 27 07:48:46 2026  01:20:31  bash -c while true; do n83a -M 3 -n 300 ...
  29376 二 10月 27 07:49:28 2026  01:19:49  sudo -u <user> ... while true; do n83a -M 3 -n 300 ...
  29382 / 29434 / 29438 / 29529 / 29608                                        （同上，共 8 个）
```

来源：报告 127 起为了"抓 pushbuffer 现场时进程别太快退出"做的**保活循环**，用完没有回收。
它们的启动时刻（07:48）早于 STATUS.md 生成时刻（08:30），正好覆盖 133/134 的采样窗口。

清除后 GPU 立刻回到 6.02 W / 0% / 0 MiB。**这些循环此后不再使用**（n83b 支持 `-f` 长跑，不再需要保活）。

### 污染造成的三个错数

| 报告 | 当时的数 | 干净重测 | 偏差 |
|---|---|---|---|
| 133 伪装 VGA | M3 = 260.406 / 260.782 ms | 126.98 ms | **2.05×** |
| 134 GPU 空闲判据 | "空闲 36.9 W" | 空闲 **8.18 W** | 4.5× |
| 134 F 候选 | M6 = 396 ms（比 M3 差 50%） | 129.55 ms（差 **2%**） | 结论作废 |

> 教训：**"空闲基线"必须是"系统上真的没人在用 GPU"时测的**。我用一堆 n83a 循环测"空闲功耗"，
> 得到的 36.9 W 其实是"8 个进程互相堵住时的功耗"，于是"37 W ≈ 空闲"这个错误判据被当成了铁证。

## 2. 干净重测：八个模式（n=1000，各 3 次，525.116.03）

| 模式 | 内容 | total_p50 | map_p50 | submit_p50 |
|---|---|---|---|---|
| M1 | 1000 draw | 7.159 / 7.166 / 7.159 | 7.120 | 0.030 |
| M2 | 改 uniform + draw | 7.192 / 7.194 / 7.195 | 7.120 | 0.064 |
| **M3** | **切换 + draw 交替** | **126.976 / 127.074 / 126.956** | **125.8** | **1.13** |
| **M6** | **切同一 program + draw** | **129.554 / 129.654 / 129.543** | **128.3** | **1.00** |
| M7 | 1000 draw，切换 0 次 | 7.167 / 7.163 / 7.167 | 7.122 | 0.033 |
| M8 | 1000 切换，1 个 draw | 2.974 / 2.971 / 2.969 | 2.610 | 0.355 |
| M9 | 先切完再画 | 7.524 / 7.523 / 7.527 | 7.122 | 0.383 |
| M10 | 先画完再切 | 7.648 / 7.648 / 7.648 | 7.242 | 0.384 |

**重复性 ±0.1%，可以当基准用了。**

### 2.1 M6 反常被否掉

M6/M3 = 129.55/126.98 = **1.020**。切同一 program 不但没更慢，甚至略慢 2%（在噪声边缘）。
报告 134 用来立论的"396 ms 比 261 ms 差 50%"，是两个被污染的样本相除。
**"F. M6 反常"这个候选从候选表里删除。**

### 2.2 时间其实是这么分的（关键修正）

`total = t_sub(提交循环) + t_rp(glReadPixels) + t_map(glMapBuffer)`

M3：**submit 1.13 ms，map 125.8 ms**。
也就是说：

- **CPU 把 1000 对命令全部编码进 pushbuffer 只花 1.13 ms（1.1 µs/对）**；
- 剩下 125.8 ms 是 `glMapBuffer` 在等 GPU 把这一帧算完。

> ⇒ 报告 125/126 的"每对进入等空间循环 108 次 × 1.177 µs = 127 µs"是**单位错误**：
> 108 次是**每帧**，不是每对；那 127 µs 是每帧 0.13 ms 的一部分，占整帧的 0.1%。
> **"CPU 与 GPU 互相等待、靠 20 µs 超时一小步一小步解套"这个模型在数量级上不成立。**

## 3. 这 122 µs 到底绑在什么上（六个判别实验）

### 3.1 与 program 无关：换 FBO、换纹理一样慢

| 每对做的事 | total_p50 |
|---|---|
| 切 program + draw（M3） | 126.98 |
| **切 FBO + draw（M4）** | **127.99** |
| **切纹理 + draw（M5）** | **126.65** |
| 改 uniform + draw（M2） | 7.19 |

⇒ 不是 shader/program 的问题，是**"绑定一个对象"这个动作**本身。
（改 uniform 是"改值"不是"绑对象"，免费。）

### 3.2 与切换次数严格线性，每绑一次 122~124 µs

M7（固定 1000 个 draw，均匀插入 c 次切换）：

| c | total_p50 | 增量 | 每次切换 |
|---|---|---|---|
| 0 | 4.69 | — | — |
| 30 | 6.00 | — | — |
| 100 | 14.67 | +8.7（70 次） | **124 µs** |
| 300 | 39.25 | +24.6（200 次） | **123 µs** |
| 1000 | 124.61 | +85.4（700 次） | **122 µs** |

### 3.3 与渲染量完全无关（分辨率 1/144，代价不变）

| 分辨率 | M1（纯 draw） | M3（切换+draw） |
|---|---|---|
| 1920×1080 | 4.691 | 124.632 |
| 960×540 | 1.307 | 122.996 |
| 480×270 | 0.471 | 122.560 |
| 320×180 | 0.308 | 122.465 |
| 160×90 | 0.215 | **122.493** |

⇒ 不是带宽、不是填充率、不是"刷渲染目标缓存"。**纯固定延迟。**

### 3.4 两个进程并发：严格 2×，全局串行

```
单进程 M3            : 124.77 ms
两进程并发 M3（各 40 帧）: P1 = 258.49 ms   P2 = 258.47 ms
```

⇒ 这 122 µs 占的是**全局唯一的 GPU 资源**，两个进程抢不到并行。

### 3.5 功耗：GPU 在那 122 µs 里是"上电空转"

（干净环境，`nvidia-smi --query-gpu=power.draw`，每 0.4 s 一次，取中位）

| 状态 | 功耗中位 | 说明 |
|---|---|---|
| 空闲 | **8.18 W** | 系统没人用 GPU |
| M1（1000 draw） | 55.08 W | 真在算 |
| **M3** | **38.19 W** | 127 ms 里几乎不耗电 |
| M6 | 38.63 W | 同上 |
| **M8（1000 切换，只画 1 次）** | **36.99 W** | **这就是"引擎上电但没事干"的底噪** |
| M9（先切后画） | 36.9~54.7 W | 真在算 |

每帧能量：M1 = 0.39 J；M3 = **4.85 J**。按"5 µs 干活 + 117 µs 空转"估算：
`(5/122)×55 + (117/122)×37 = 37.7 W` —— 与实测 38.19 W 吻合。

⇒ **M3 里 GPU 有 95% 的时间在上电空转，等一个 122 µs 才发生的事件。**

### 3.6 没有"每绑一次就 kick 一次"

`perf stat -e syscalls:sys_enter_ioctl`，10 帧：

| 模式 | ioctl | sched_yield |
|---|---|---|
| M1 | 456 | 181,642 |
| **M3** | **511** | **4,965,035** |
| M9 | 458 | 183,819 |

ioctl 三档一样（≈45/帧）⇒ 驱动没有在每次绑定时向内核提交。
`sched_yield` 从 1.8 万/帧涨到 **496 万/帧（每对 496 次）**——CPU 确实在每对里自旋等待。

### 3.7 把 20 µs 改成 1 µs：总时间不变

在运行中的进程里把延时立即数 `0x15761e9` 处的 `0x14`(20 µs) 改成 `0x01`(1 µs)：

```
改前: 0x14      改后: 0x01
结果: total_p50 = 124.821   （未改基线 124.63）
```

⇒ **不是"延迟粒度太大"造成的假等待**。CPU 只是用 20 µs 为一片在睡，事件本身要 122 µs 才成立。

## 4. 静态定位：122 µs 落在哪个函数

用 `perf record -g --call-graph dwarf` 采样（关 ASLR 后实测基址 `0x7ffff4a00000` 换算）：

```
hot chain（模块内偏移）
  0x1152022  →  0x15007c4  →  0x15814a0  →  0x15761b0（20 µs 延时）
```

### 4.1 `0x15814a0`：等 pushbuffer 空间的循环（就是报告 125 说的那个位置，但数字全错）

```
15814b0: test BYTE PTR [rdi+0x320],0x1        ← ctx+0x320 的 bit0
15814b7: jne  1581540                          ← bit0=1 直接跳过等待（＝报告 128 那个"85 倍"）
15814bd: call 15762d0
15814c2: lea  ebx,[r12+0x16]
15814f7: call 156a6e0                          ← 查空间，返回 0 表示不够
158150f: test eax,eax
1581511: jne  15814d0                          ← 不够 → 走重试
15814e0: call 1581460
15814e8: call 15761b0                          ← 睡 20 µs
15814f2: call 1577bc0
```

（`0x320` bit0 与 STATUS.md 地址表里"标志位 bit0 ctx+0x320"是同一个位；
报告 128 把它置 1 得到 85 倍加速、但画面错乱——现在知道原因：它把"等空间"整个跳过了，
于是驱动在 GPU 还没消费的地方继续覆盖写。）

### 4.2 `0x15761b0`：20 µs 纯延时（已确认是纯延时，不含条件）

```
15761dd: call [rbp+0x290]          ← 取时钟 t0
15761e6: lea  r12,[rax+0x14]       ← deadline = t0 + 20 µs
...
1576210: pause ×9
1576227: call [rbp+0x290]          ← 再取时钟
157622d: cmp  rax,r12 ; jge 退出    ← 只按时间退出，不检查任何条件
```

**调用次数（单事件 uprobe，每帧）**：M3 = **7211 次**（每对 7.2 次）。
`7211 × 17.6 µs ≈ 127 ms` —— **整帧时间就是这个函数花掉的**。

> 注意：报告 124 说"121 µs = 213 次 sched_yield"。今天数出来是 496 次/对，
> 且真正的时间在 `0x15761b0`（7211 次/帧），不在 sched_yield 上。这两个数都要按本报告更正。

### 4.3 515 里同一套东西都在

`grep sched_yield@plt`：

| 版本 | 调用点 |
|---|---|
| 515.105.01 | `0xeb8119` / `0xec2808` / jmp 跳板 `0xeb8278` |
| 525.116.03 | `0x146cae9` / `0x1476ad8` / jmp 跳板 `0x146ccc0` |

两版的 `sched_yield + gettimeofday + tgkill` 等待循环**逐字节同构**，连超时常量都一样：
525 的 `comisd` 目标 `0x1d40238 = 100000.0 µs = 100 ms`。

⇒ **不是"525 新增了一段等待代码"**（这一点与报告 122 的结论一致）。
差异只能是**"多久进一次"**，不是"有没有"。

## 5. 修正后的因果模型

```
每次 glUseProgram / glBindFramebuffer / glBindTexture（绑一个"对象"）
        ↓
驱动认为这里是一个批次边界 → 需要新的 pushbuffer 空间
        ↓
查空间不够（GPU 还没消费掉上一批）→ 睡 20 µs → 重试（每对约 7 次）
        ↓  合计 122 µs
GPU 在这 122 µs 里处于"引擎上电、无事可做"（38 W，接近 37 W 底噪）
        ↓
串行于整块 GPU（两进程严格 2×）
        ↓
1000 对 = 122 ms/帧；M1 没有"绑对象"所以是 7 ms；M9/M10 把绑定与 draw 分开也没有批次边界
```

**能与不能解释的，分开写清楚：**

| 事实 | 本模型能解释？ |
|---|---|
| 只有 M3/M6/M4/M5 慢，M1/M2/M9/M10 快 | ✅ 只有它们"绑对象紧跟 draw" |
| 与对象类型无关（program/FBO/纹理同样 122 µs） | ✅ |
| 与分辨率无关 | ✅ 是空间/边界握手，不是像素工作 |
| 与切换次数严格线性（122~124 µs/次） | ✅ |
| GPU 功耗停在"上电空转"底噪 | ✅ 在等 |
| 两进程严格 2× | ✅ 全局 GPU 资源 |
| `-R`（不回读）时 CPU 只阻塞一次、GPU 仍要 132 ms/帧 | ✅ 纯 GPU 侧，不需要 CPU 配合 |
| **为什么 525 的 GPU 消费一个批次要 122 µs、515 不要** | ❌ **仍未查明** |

## 6. 下一步（按性价比排序）

1. **把 515 拉回来做同一组实验**（M1/M3/M4/M5/M7 标度 + 功耗 + 两进程）。
   现在有了 n83b（`-G`/`-R`/`-f` 长跑）和一整套脚本，切换驱动后 15 分钟能出全套对照。
   只有 515 的"每次绑定要多少 µs"这个数出来，"525 多花了 N 倍"才有分母。
2. **查"空间"到底卡在哪**：`0x156a6e0`（查空间）返回 0 的判据是什么，
   以及 `W`（ctx+0x1130）与 GPU 写回的 rp 差多少。报告 131 测过 gap 分布（525 恒为 5），
   现在应当在"每次绑定"这个粒度上重测，而不是每帧。
3. **`0x15814a0` 的调用者**：谁决定了"这里要开一个新批次"。这是 525/515 真正的分岔点，
   也是唯一能通向"可配置/可绕开"的地方。
4. 遗留：`nvidia` 模块引用计数卡住的老问题，**重启后**才能做"干净 probe"类实验。

## 7. 复现命令（全部在干净环境下，无保活循环）

```bash
# 环境
export DISPLAY=:1 XAUTHORITY=$(ls /run/user/1000/xauth_* | head -1) \
       XDG_RUNTIME_DIR=/run/user/1000 \
       __GLX_VENDOR_LIBRARY_NAME=nvidia __NV_PRIME_RENDER_OFFLOAD=1
cd <workdir>/analysis/n83a

# 模式扫描（3 次取中位）
./n83b -M 3 -n 1000            # 127 ms
./n83b -M 3 -n 1000 -G         # 124.6 ms（glFinish 版，绕开 PBO，结论一致）
./n83b -M 3 -n 1000 -R         # 1.32 ms（只编码不等待；总量在退出时付）
./n83b -M 3 -n 1000 -G -w 160 -h 90   # 122.5 ms（分辨率无关）

# 功耗
nvidia-smi --query-gpu=power.draw --format=csv,noheader   # 空闲 8.2 W

# 计数（每次只开一个事件！）
echo 'p:x /usr/lib/x86_64-linux-gnu/libnvidia-glcore.so.525.116.03:0x15761b0' >> /sys/kernel/debug/tracing/uprobe_events
```

n83b 是本轮新增的 `n83a` 变体（`analysis/n83a/n83b.c`），只加了三个开关：
`-R` 跳过回读、`-G` 用 glFinish 代替回读、无其它改动（默认行为与原 n83a 一致，已用 M1/M3 校准）。
