# 99 · N109：**`GRID P40-2B` 找到了** —— 标准驱动的 vGPU type 表里有 P40，**没有 P106**

日期：2026-10-26 15:20
驱动：525.116.03（`nvidia.ko`，72MB，`.rodata` 内有 vGPU profile 表）
用户线索：「vgpu 中的 **P40-2B** 不查一下吗？」

---

## 0. 一句话：这条线索是对的，而且解释了"为什么虚拟化更快"

**标准 `nvidia.ko` 里有一张 516 条的 vGPU profile 表（`GRID <卡>-<显存><后缀>`），
里面有 `GRID P40-2B`，但整张表里 `P106`（device id `0x1c07`）出现 0 次。**

⇒ **`vgpu_unlock` 必须把 P106 的 device id 伪装成表里存在的某个 Tesla 卡（P40），
驱动才会按 P40 的能力配置工作。**

⇒ **"虚拟化下更快"不是虚拟化的功劳，是驱动以为自己在驱动 P40（GP102）而不是 P106（GP106）。**

---

## 1. `GRID P40-2B` 确实在标准驱动里（`.rodata`，真实字符串）

```bash
strings -a nvidia.ko | grep -c "^GRID"        # → 516
strings -a nvidia.ko | grep -cE "[0-9]+[ABQ]$"  # → 282 条符合 "<显存><后缀>" 格式
strings -a -t x nvidia.ko | grep "P40-2B"
#  31b21c7  GRID P40-2B
#  31b220b  GRID P40-2B4
```

**段归属确认**（关键，排除 `.debug_str` 假象）：

```
file=0x31b21c7  vaddr=0x2640477  seg=.rodata      ← 真实运行时字符串
```

### 1.1 P40 的完整 profile 列表（19 个）

```
GRID P40-1Q   GRID P40-2A   GRID P40-2B   GRID P40-2B4  GRID P40-2Q
GRID P40-3A   GRID P40-3Q   GRID P40-4A   GRID P40-4C   GRID P40-4Q
GRID P40-6A   GRID P40-6C   GRID P40-6Q   GRID P40-8A   GRID P40-8C
GRID P40-8Q   GRID P40-24A  GRID P40-24C  GRID P40-24Q
```

后缀含义（NVIDIA 约定）：
- **A** = 全功能（图形 + 计算）
- **B** = **图形**（vGPU with graphics）
- **Q** = 纯计算（vCompute）
- 数字 = framebuffer 大小（GB）

**`P40-2B` = 2GB 显存的图形类 vGPU** —— 正是用户说的那个。

---

## 2. 表项格式：`0x10de_<typeid>_<deviceid>`

在 `GRID P40-2B` 的重定位项（`vaddr 0x264a958`，`R_X86_64_64` → `.rodata+0x2640477`）附近，
读 8 字节对齐的 qword：

```
0x264a930 -> 0x000010de_11f6_1b38
0x264a940 -> 0x000010de_11f7_1b38
0x264a950 -> 0x000010de_1287_1b38      ← 对应 GRID P40-2B
0x264a960 -> 0x000010de_12b1_1b38
0x264a970 -> 0x000010de_12b2_1b38
0x264a980 -> 0x000010de_12b3_1b38
```

**拆解**（小端 u64）：

| 位段 | 值 | 含义 |
|---|---|---|
| 32–47 | `0x10de` | **NVIDIA vendor id** |
| 16–31 | `0x1287` 等 | **vGPU type id**（每个 profile 一个） |
| 0–15 | `0x1b38` | **device id = P40** |

**⇒ 每个 (device, profile) 组合 = 一个 type id。驱动用这个 type id 查 profile 记录
（`nv_vgpu_get_type_info` 里 `imul rdx,rdx,0x4488` —— 每条记录 0x4488 字节）。**

---

## 3. ★★ 决定性：表里**有 Tesla 全系，没有 P106**

扫全文件里所有 `(vendor==0x10de) && (device 在 0x0F00–0x2FFF)` 的 8 字节表项：

| device id | 型号 | 表项数 |
|---|---|---|
| `0x1e78` | (Tesla T4 变体/虚拟) | 122 |
| `0x1e30` | (Tesla) | 121 |
| `0x26b5` | (Ampere) | 80 |
| `0x2235` / `0x26b1` / `0x25b6` / `0x2230` / `0x27b8` | (Turing/Ampere 各型) | 55~79 |
| **`0x1b38`** | **P40** | **64** |
| `0x1db6` | V100 | 46 |
| `0x1eb8` | T4 | 46 |
| `0x1bb3` | P4 | 34 |
| `0x1b39` | P100 | 有 |
| **`0x1c07`** | **P106-100** | **0** ← ★★★ |

**⇒ P106 完全不在 vGPU 支持的 device 列表里。**

**这与 NVIDIA 官方立场一致**：vGPU 只支持 Tesla/GRID/Quadro 的特定型号，**GeForce/矿卡不支持**。

---

## 4. 这条发现如何解释全部现象

### 4.1 vgpu_unlock 到底做了什么

社区工具 `vgpu_unlock` 的核心，就是**绕过"device id 必须在支持列表里"这个检查**。
常见做法：
- patch 驱动的 PCI ID 表 / `nv_vgpu_get_type_info` 的 device 匹配；
- 或直接在 QEMU 里给 guest 报一个假的 `device_id`（VFIO 支持 `x-pci-device-id` 覆盖）。

**目标就是让 P106 匹配到表里某个存在的型号 —— P40 是首选**（同为 Pascal，GP102/GP106 指令集兼容）。

### 4.2 于是"快"来自哪里

| 环境 | 驱动认为的 GPU | 走的能力配置 |
|---|---|---|
| **物理机直装 525** | **P106 / GP106**（`0x1c07`） | **GP106 路径 → 慢（121µs/对）** |
| **PVE + vGPU 破解** | **P40 / GP102**（`0x1b38`）+ `GRID P40-2B` profile | **GP102 路径 → 快（130W 正常）** |

**⇒ 不是"虚拟化让 GPU 变快"，是"驱动以为自己是另一块更强的卡，于是选了另一套提交策略"。**

而且这**正面回答了你上一个问题**——「驱动按 GPU 设备 ID / 能力 选提交路径的分支」：

> **就是这张 vGPU type 表 + 它的消费方 `nv_vgpu_get_type_info`（stride `0x4488`）。**
> **device id 是这张表的索引键。**

### 4.3 与之前所有观测的相容性

| 观测 | 用这个模型解释 |
|---|---|
| 物理机 525 慢、515 快 | ~~515 无 vGPU 表~~ **（已撤回，见 §4bis：515 也有表）**。仍成立的是：515 缺 `LOGVGPU`/`rm_vgpu_vfio_set_driver_vm`，且 profile 表比 525 小 40% |
| 580 的 GL 慢、Vulkan 快 | 580 对 Vulkan 的提交路径做了重构，GL 路径未动 |
| Vulkan 也慢（报告 93） | GL/Vulkan 共用 glcore（报告 95），底层提交策略同受 device-id 影响 |
| 截图 `Compute M: N/A` | vGPU guest 里 GPU 由 vGPU manager 虚拟化，NVML 读不到 compute mode |
| 截图 130W / 99% util | 走 GP102 路径，GPU 真的在算 |

## 4bis. ⚠️ 补做跨版本对比：**515 也有这张表，我原来的推论错了**

补做 N109-C（对比 7 个版本的 `kernel-open/nvidia/nv-kernel.o_binary`，同一变体，公平可比）：

| 版本 | 文件大小 | `GRID ` 串数 | `GRID P40-2B` | **P106 表项** | **P40 表项** |
|---|---|---|---|---|---|
| **515.48.07** | 5.9M | 364 | **1** | **0** | **24** |
| **515.105.01** | 5.9M | 364 | **1** | **0** | **24** |
| 520.56.06 | 11.4M | 368 | 0 | 0 | 0 |
| **525.116.03** | 7.9M | **508** | **1** | **0** | **32** |
| **535.129.03** | 9.9M | **510** | **1** | **0** | **32** |
| 550.144.03 | 11.4M | 368 | 0 | 0 | 0 |
| 580.178.04 | 17.3M | 368 | 0 | 0 | 0 |

### 4bis.1 两条必须承认的事实

1. **515 也有 vGPU 表和 `GRID P40-2B`**（P40 表项 24 条）。
   ⇒ **"515 没有 vGPU 表"是错的**，我正文 §4.3 里"515 的 vGPU 表/逻辑不完整"这条**要撤回**。
   （报告 96 说 515 缺的是 `LOGVGPU` 日志分类器和 `rm_vgpu_vfio_set_driver_vm`，**不是这张表**。）
2. **P106 在所有 7 个版本里都是 0 条** ⇒ 这条结论**稳固**。

### 4bis.2 但仍然有一致的差异

```
515      : GRID 串 364,  P40 表项 24
525 / 535: GRID 串 508/510, P40 表项 32     ← 明显扩张
550/580  : GRID 串 368,  P40 表项 0         ← 表项编码变了（不再是 0x10de_tid_dev 打包）
```

- **515 → 525：vGPU profile 表扩张了约 40%**（364→508 串，24→32 条）。
- **550/580 用 0 条** 是因为表项格式变了（我按老格式扫，扫不到），**不代表没有表**。

### 4bis.3 修正后的因果模型

**因为 515 也有表、而 515 在物理机上快 ⇒ "表的存在"不影响物理机性能。**

所以真正起作用的不是"有没有 vGPU 表"，而是：

> **`device id` → 驱动认定的芯片型号（GP106 vs GP102）→ 芯片级提交策略。**

`vgpu_unlock` 把 device id 改成 `0x1b38`（P40/GP102）后，
**驱动按 GP102 的能力配置初始化**（vGPU profile 只是这条链路的入口条件之一）。

**⇒ 下一个该查的不是 vGPU 表，而是"device id → chip config"那张映射。**
判据：在 `nvidia.ko` 里找"由 device id 决定 chip family / 特性位"的表，
它应该同样以 `0x10de_...` 或纯 device id 数组的形式存在。

## 5. 这个发现给出**一个可执行、可逆的验证**

**不需要装 PVE，也不需要 patch 驱动。** 用 QEMU 的 VFIO device id 覆盖：

```bash
# 在 QEMU 里直通 P106，但把 device id 报成 P40 的 0x1b38
-device vfio-pci,host=01:00.0,x-pci-device-id=0x1b38
# 或（更完整地伪装）
-device vfio-pci,host=01:00.0,x-pci-vendor-id=0x10de,x-pci-device-id=0x1b38
```

**判据**：

| guest 里的表现 | 结论 |
|---|---|
| **`nvidia-smi` 显示 `Tesla P40` / `GRID P40-2B`，且 `n83a -M 3` 每对 ≈ 0.03µs** | ✅ **模型证实**：device id 决定提交路径，**根因确认** |
| 显示 P40 但仍 121µs | ❌ 模型错：不只是 device id 的问题 |
| 驱动拒绝加载（"unsupported GPU"） | 需要配合 `vgpu_unlock`（那就直接装回 PVE 更快） |

**这个实验比"装 550"更有针对性**：它直接改"驱动认为自己是哪块卡"这一个变量。

---

## 6. 仍然要诚实标注的三点

1. **`GRID P40-2B` 表的存在，只证明"驱动带这张表"**；
   **没有证明"物理机上这张表被读、且读失败导致慢"** —— 需要 §5 的实验。
2. **P106 不在表里是事实**，但"不在表里就慢"仍需验证（可能是"不在表里 ⇒ 走默认配置 ⇒ 恰好有 bug"）。
3. **`vgpu_unlock` 具体改了什么，我不知道** —— 你用的是哪个版本、改了哪几个字节、是否还改了别处。
   如果它同时 patch 了别的检查，那"快"可能来自别处。

## 8. 产物 / 复现

```bash
K=/lib/modules/$(uname -r)/kernel/drivers/video/nvidia.ko

# 1) profile 表存在且是真实字符串
strings -a $K | grep -c "^GRID"                 # 516
strings -a -t x $K | grep "P40-2B"              # 0x31b21c7
# 段归属：vaddr 0x2640477 in .rodata

# 2) 表项格式
readelf -rW $K | grep 2640477
#   000000000264a958  ... R_X86_64_64 ... .rodata + 2640477

# 3) 有没有 P106
python3 -c "
import struct
d=open('$K','rb').read(); n=0
for i in range(0,len(d)-8):
    v=struct.unpack('<Q',d[i:i+8])[0]
    if ((v>>32)&0xFFFF)==0x10de and (v&0xFFFF)==0x1c07: n+=1
print('P106 表项:',n)"
```

## 9. 教训（已入技能库）

1. **★★★ 搜 profile 名要先知道它的前缀形态。**
   我一开始搜 `P40` / `GP106` / `GP102` 全部 0 命中，因为真正的字符串是 **`GRID P40-2B`**（带 `GRID ` 前缀）。
   **教训：搜产品/型号名，先用宽松模式（`grep -i p40`）看上下文，再收紧。**
2. **★★★ 一张"看起来是字符串表"的东西，要验证它是不是**：找它的重定位项（`R_X86_64_64`），
   看指针指向哪里、相邻项是什么。本例一读就发现表项是 `0x10de_<typeid>_<deviceid>` 的打包值 ——
   **这才是"按 device id 查表"的实体**。
3. **★★ "不在支持列表里"本身就是重要信息。**
   本例 `0x1c07` 在 vGPU 表里 0 命中，直接证实了"P106 官方不支持 vGPU"，
   从而解释 `vgpu_unlock` 为什么必须伪装 device id。
   **在排查"为什么我的配置不正常"时，先查"我的配置在不在厂家的支持列表里"。**
4. **★ 用户给的型号/版本号（`P40-2B`）是**精确坐标**，不要泛化成一类去搜。**
   我如果一直搜 "GP102"、"Tesla"，永远找不到；按 `P40-2B` 搜才命中。
