# 38 · 追 waker：`0x14a669d` 不是它；真正的唤醒者每帧 24 次，而等待是纯双峰

> 2026-10-25 22:40
> 用户指令：不换驱动，追 `0x14a669d` 这个"真正的 waker"，回答两问——
> ①它自己是不是也在等（链式等待）；②它从"开始处理"到"置标志+signal"花了多久。
>
> **结果：`0x14a669d` 追错了——它是 1 秒超时兜底，实测从不触发。**
> 顺着这条线找到真正的唤醒者，并意外测出了等待的**三峰结构**，
> 这解释了报告 36 的"每次 28ms"到底是什么，也给出了"为什么慢"的微观答案。

## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **`0x14a669d` 不是正常 waker**：它受 `cmp $0xf423f`（≈1 秒）门控，是超时补救 | 静态 `14a6591`；实测 `sBset=0`、`tmo=0`（两轮） |
| 2 | **真正的 pair-B 唤醒者是 `0x1238db3`**（`0x1238d80` 函数内），**846 次/秒 = 24.4 次/帧** | 实测 `sB` 6769/6794 次，两轮 |

| 4 | **★ 等待是纯双峰**：31% 瞬间返回（<0.1ms）+ 22% 真等（15~25ms），中间 8~15ms 几乎为空 | 两轮：31.4/30.2%、22.1/21.8% |
| 5 | **tid 14548/14197 完美双峰：67% <1ms，33% ≥10ms，1~10ms 区间 0 次** | 两轮完全一致 |

| 7 | 因此报告 36 的"每次 28ms"= **一次"等待区停留"里含 2~5 次 wait**，其中仅 1 次是真等 | 与 36 的 32.8 次/s vs 本报告 290 次/s 的 8.8 倍差对应 |

**一句话**：**不是"waker 自己也在等"，也不是"一次等 28ms"，而是"每帧真等一次约 20ms + 反复几毫秒的无效重试"。**

## 2. 先纠正目标：`0x14a669d` 是 1 秒超时兜底

`0x14a669d` 所在函数从 `0x14a6370` 开始（`0x14a6250` 是**另一个**函数，`14a635f` 已 `pop %r13` 结束）。它的入口路径是：

```
14a6588: call  *0x290(%rbp)          ; 取时
14a658e: sub   %r14,%rax             ; elapsed = now - r14
14a6591: cmp   $0xf423f,%rax         ; ★ 0xF423F = 999,999（µs ≈ 1 秒）
14a6597: jg    14a6670               ; ★ 只有超过 1 秒才跳去 signal
14a659d: mov   $0x2,%edi
14a65a2: call  *0x280(%rbp)          ; 否则：让出（vtable+0x280，参数 2）
14a65a8: movzbl 0x8e0f00(%r13),%eax
14a65b0: test  %al,%al
14a65b2: je    14a6588               ; 为 0 → 继续循环

14a6670: ...                          ; ← 1 秒超时后才到这里
14a6677: movl  $1,0x8e0924(%r13)
14a6682: movl  $1,0x8e0964(%r13)
14a6689: testb $0x20,0xc08(%rax)     ; bit5 门（同报告 37）
14a6694: jne   14a66a8
14a6696: mov   0x8e0910(%r13),%rdi   ; pair-B 的 signal 侧
14a669d: call  *0x2d8(%rbp)          ; ★ 这里才是 signal
```

**所以 `0x14a669d` 是"等了 1 秒还没动静"的补救路径**，不是每帧的正常唤醒。

实测坐实（两轮）：

| 探针 | 地址 | n9w1 | n9w2 |
|---|---|---|---|
| `sBset`（超时分支的置标志） | `0x14a6677` | **0** | **0** |
| `tmo`（1 秒判定点） | `0x14a6597` | **0** | **0** |

→ **那条路一次都没走。** 报告 33 把它当成"正常唤醒者"是错的；它对 fps 无影响。

## 3. 真正的唤醒者：`0x1238db3`，24 次/帧

`0x1238d80` 是一个**"有活就唤醒消费者"**的工具函数（十几个调用者），它 signal 的是 `0x8e0910` = **pair-B**，也就是 `wait_ms` 用的那个 cond：

```
1238d8b: mov    (%rdi),%rdx
1238d8e: mov    %rdx,0x8e0900(%rdi)
1238d95: mov    %rdx,0x8e0940(%rdi)     ; 更新队列尾
1238d9c: testb  $0x20,0xc08(%rax)       ; bit5 门
1238da3: jne    1238dbc
1238dac: mov    0x8e0910(%rdi),%rdi     ; pair-B
1238db3: call   *0x2d8(%rax)            ; ★ signal —— 能唤醒 0x950 的 wait
```

实测频率（两轮）：

| 事件 | n9w1 | n9w2 | 次/秒 | 次/帧@34.7 |
|---|---|---|---|---|
| `wcall`（`wait_ms` 调用） | 2322 | 2364 | ~293 | **8.4** |
| `sB`（真唤醒） | 6769 | 6794 | ~848 | **24.4** |
| `sC`（`123af7f` 的 notify，pair-**C**） | 2342 | 2400 | ~296 | 8.5 |

`sB / wcall = 2.87~2.92` → **每次 wait 平均被唤醒近 3 次的机会**，但只有 1 次能命中（详见 §4 的相位）。

## 4. ★ 角色表：没有链式等待

两轮各 8 秒，4 个 tid 严格分工（n9w1 / n9w2 的 tid 各自变化，但结构一致）：

| n9w1 tid | n9w2 tid | wcall | sB | sC | 角色 |
|---|---|---|---|---|---|
| **14150** | **14500** | 0 | **5977 / 6003** | 0 | **主线程（=PID）**，纯 signal 者 |
| 14196 | 14547 | 0 | 792 / 792 | 0 | 纯 signal 者 |
| 14180 | 14530 | 1530 / 1572 | 0 | 1545 / 1585 | **waiter** + notifyC |
| 14197 | 14548 | 792 / 792 | 0 | 797 / 816 | **waiter** + notifyC |

**判读**：

- **发 signal 的线程一次都不 wait；wait 的线程一次都不 signal。** → **不存在链式等待**，用户猜的"waker 自己也在等"**不成立**。
- waiter 同时也发 `notifyC`（pair-C），但那是给别人的，与自己的等待无关（见报告 37 §4 的 cond 拓扑）。
- 跨线程唤醒延迟（signalB → 下一次 wcall，同 tid 配对）：

| 配对 | 中位 |
|---|---|
| `14196 → 14197` | **0.08 ms** |
| `14150 → 14180` | 0.45 ms |
| `14196 → 14180` | 3.85 ms |
| `14150 → 14197` | **25.13 ms** |

最后一行是关键：**主线程 signal 之后，那个 waiter 要 25ms 才来 wait** —— 说明 signal 发生时它还在处理别的事，或反过来，它等的时候主线程还没 signal。

## 5. ★★ 决定性发现：等待是"三峰"，不是"一个 28ms"

对每个 `wcall`，取它之后最近的 `sB` 的延迟（跨全部 tid），两轮结果几乎逐位重合：

| 区间 | n9w1 | n9w2 | 含义 |
|---|---|---|---|
| **<0.1 ms** | **729 (31.4%)** | **714 (30.2%)** | ★ cond 已置位 → `wait_ms` **瞬间返回**，根本没睡 |
| 0.1–0.5 ms | 307 (13.2%) | 356 (15.1%) | 极短睡 |
| 0.5–1 ms | 122 (5.3%) | 131 (5.5%) | 短睡 |
| **1–3 ms** | **621 (26.8%)** | **631 (26.7%)** | 中短睡 |
| 3–8 ms | 18 (0.8%) | 10 (0.4%) | — |
| 8–15 ms | 10 (0.4%) | 6 (0.3%) | **几乎为空** |
| **15–25 ms** | **513 (22.1%)** | **514 (21.8%)** | ★ **真等** |
| >25 ms | 0 | 0 | 上限 100ms 从未逼近 |

**同 tid 连续 `wcall` 的间隔更干净**（呈**纯双峰**）：

| tid | n | <1ms | 1–10ms | ≥10ms | 中位 |
|---|---|---|---|---|---|
| 14180 / 14530 | 1529 / 1571 | **52% / 53%** | 31% / 30% | **17% / 17%** | 0.42 ms |
| 14197 / 14548 | 791 / 791 | **67% / 67%** | **0% / 0%** | **33% / 33%** | 0.11 ms |

**14197 这一行是最干净的证据：67% 的间隔 <1ms，33% 的间隔 ≥10ms，中间的 1–10ms 区间一次都没有。**
这是典型的**"要么立刻重试、要么等满一帧"**两态行为。

### 5.1 这条数据改写了什么

报告 36 用驱动自记时算出"每帧进入等待区 1 次、每次 23~28ms"，我当时的表述容易读成"一次等 28ms"。
**实际情况**（把两边的数对齐就一目了然）：

```
报告 36：进入等待区 328 次 / 10s = 32.8 次/秒
本报告：wcall            2322 次 / 8s  = 290 次/秒      → 相差 8.8 倍

⇒ 一次"等待区停留"（state=1）里，包含 ~2.9 次 wait_ms 调用（14180 侧）
   其中只有 ~0.95 次是真等（15~25ms），其余是毫秒级无效重试
```

于是 36 的 28.2ms 与 37 的"每帧 9 次空转"是同一件事的两种口径：
**一帧 ≈ 1 次真等（20ms）+ 2~4 次瞬间/短重试。**

### 5.2 31% 的"瞬间返回"是怎么来的

`wait_ms(cond, 100)` 内部是 `pthread_cond_timedwait`。它瞬间返回（<0.1ms）只有一种可能：
**进入时谓词已经满足**（前面的 signal 已经把标志置上了）。

→ 这是 **signal 早于 wait 的相位错开**：主线程 / worker 在 waiter 还没睡下时就发了 signal，
等 waiter 真的睡下，那一次 signal 已经过去了，只能等下一次。

**这就是"空转"的物理来源**，也解释了 `sB/wcall = 2.9`：发了近 3 次才命中 1 次。

## 6. 所以"为什么慢"的完整答案

```
Heaven 每帧渲染 → primus glXSwapBuffers
  → 主线程提交命令 + sB（signal pair-B）
  → glcore 队列处理器醒来处理 → 处理完队列空 → wait_ms 睡
  → 主线程这一帧的活已经交完，下一帧的活要等渲染完才来
  → 队列处理器真等 ~20ms（等下一帧）
  → 期间主线程/worker 又零星 sB 几次 → 瞬间醒来、发现空、再睡（毫秒级空转）
  → 一帧 28.8ms 里，约 20ms 在真等 + 几毫秒在空转
```

**这不是"某个环节慢 28ms"，而是"活每帧只来一次，而消费者一帧只被喂到一次"。**
与报告 31 的 GPU 48~68W（空转）、36 的 90% 占空比、37 的"补丁只值 15%"完全自洽。

**同时解释了 515 为什么快**（待 N3 验证）：如果 515 也是"每帧一次活"，它的真等也应该 ~10ms
（对应 108fps 的帧周期 9.2ms），而不是 20ms —— 差别在**一帧的长度**，不在等待机制。

## 7. 对"解决 525"的直接含义

| 曾经以为 | 现在知道 | 该做什么 |
|---|---|---|
| `0x14a669d` 是晚到的 waker，追它 | 它是 1 秒兜底，从不触发 | **放弃这条线** |
| waker 自己也在链式等待 | 没有链式等待（signal 者从不 wait） | **放弃"往上追一层"** |
| 一次 wait 等 28ms | 一次真等 ~20ms + 若干毫秒级空转 | 优化目标应是**减少空转次数**，不是"缩短单次等待" |
| 空转是驱动 bug | 是 signal/wait 相位错开（`sB/wcall≈2.9`） | 治本要动**提交节奏**，不是改驱动 |

**唯一还能改的地方（且值得做）**：31% 的瞬间返回说明**有一半唤醒是白发的**。
如果能让 waiter 在"谓词已满足"时不去调 `wait_ms`（多一次前置检查），理论上能省掉这部分空转。
但按报告 37 的定价经验，**这类改动大概也只值十几个百分点**——因为真等的 20ms 不会被它缩短。

→ **结论不变、但更硬了：525 的帧时间由"每帧一次活的到达节奏"决定，而这个节奏由 primus + GPU 回读（报告 26 的 D）决定。驱动侧的等待写法是次要项。**

### 8.1 cond 配对验证（本节独立成证）

运行时直读（`n9a`），wait 与 notify 是**同一个 ctx** `0x7fa238b1f040`：

| 槽 | 值 |
|---|---|
| `+0x8e0918` / `+0x8e0958` | `0x13b83a20` / `0x13b83a20`（pair A） |
| **`+0x8e0910` / `+0x8e0950`** | **`0x13b839b0` / `0x13b839b0`（pair B ← wait 用 0x950）** |
| **`+0x8e0908` / `+0x8e0948`** | **`0x13b83ad0` / `0x13b83ad0`（pair C ← notify 用 0x948）** |

`0x13b839b0 ≠ 0x13b83ad0` → **两个不同对象**，报告 33 的"cond 路由有选择性"正式作废。
同一 ctx、同一进程，但 wait 与那个 notify 用的是**两个不同的 cond**。

## 9. 方法论收获（已入技能）

1. **"看谁 signal"必须区分"正常路径"和"超时兜底"**。本例 `0x14a669d` 所在的函数里，
   signal 前面有个 `cmp $0xf423f`（1 秒）门 —— 不读这一行就会把它当正常唤醒者（报告 33 就是这么错的）。
   **判据**：signal 点前面若出现大常数的 `cmp`/`sub`/`ja`，先假设它是超时/退避分支。
2. **"事件 A → 事件 B 的延迟"必须先做 tid 角色表**。本例 `sB` 比 `wcall` 多 3 倍，
   第一版跨 tid 配对所有事件，得到"中位 1.13ms"这种没有物理意义被混合值；
   按 tid 分开后立刻出现 67%/33% 的纯双峰。
3. **"每帧 N 次"与"每次 X ms"不能相乘当结论**。必须核对两者的计数口径是否一致
   （本例 32.8/s 与 290/s 差 8.8 倍，正是"一次停留含多次 wait"的证据）。
4. **<0.1ms 的"等待"是相位错开的指纹**，不是"等待很快"。
   判据：`pthread_cond_timedwait` 立即返回 ⇒ 谓词已满足 ⇒ signal 早于 wait。
