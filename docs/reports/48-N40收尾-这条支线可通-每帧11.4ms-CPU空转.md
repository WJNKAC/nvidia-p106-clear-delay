## 1. 明确结论（先给结果，不绕）

| 问题 | 答案 |
|---|---|

## 2. 实测数据

`n40_cpu.sh`（8.12s 窗口，PRIMUS_SLEEP=0，`utime+stime` 前后快照）：

| tid | 循环次数 | 次/秒 | CPU秒 | 占1核 | ctx |
|---|---|---|---|---|---|
| **24682** | **1,235,751** | **152,167** | 3.010 | **37.1%** | `0x...000d40`（f=0） |
| 24637（主线程=PID） | 1,081 | 133 | 1.530 | 18.8% | `0x...e040`（f=719） |

**汇总（8 核机器）**：

```
跑这个循环的线程合计: 4.540 CPU秒 = 占 1 核 55.9%
全进程合计:          16.980 CPU秒 = 占 1 核 209.1%   ← 用了 2 个多核
map 完成次数(MB): 263  ⇒ 帧率 32.4 fps
一帧 30.9ms 里有 64.6ms 是 CPU 时间（全进程/帧数）  ← CPU 超订
```

**关键身份确认**：`mb_out` 也发生在 tid 24682 上（263 次）
→ **24682 就是 readback worker 本身**，不是别的线程。

## 3. 4698 次/帧 vs 15 次 wait —— 99.7% 的循环是"问一下就走"

把两个数放在一起，机制立刻清楚：

```
1238a28 循环入口:  1,235,751 次 / 263 帧 = 4,698 次/帧
wait_ms(2ms):          3,896 次 / 263 帧 = 14.8 次/帧
                                            ─────────
                             进入 wait 的比例 = 0.3%
```

**99.7% 的循环没有进入 wait，而是走了"队列空 → 立即返回"。**

单次循环耗时：`30.9ms ÷ 4698 = 6.6µs`

### 3.1 两条路径的对比

```
[1238a28] 队列头 == 队尾?
   空  → [1238b48] 记账（取时/累加 float/比较/setb）→ ret   ← 99.7% 走这条，6.6µs
   非空 → 阈值判断 → 不满足 → wait_ms(2ms) → 回循环        ← 0.3%，21.4ms/帧
```

**所以 map 的 30.9ms 是这样构成的：**

```
21.4ms  睡在 futex（报告 44 的 70.4%）
 9.0ms  在"问队列空不空"的循环里烧 CPU（≈ 4698 × 6.6µs 减去 wait 期间）
 0.5ms  其他
```

（`11.4ms` 与 `9.0ms` 的差异来自：CPU 时间还包括进入/退出函数的开销，
以及"队列非空→记账"那部分，不影响量级判断。）

### 3.2 上下文：这个函数在做什么

函数入口约 `0x1238920`，`1238a28` 是它的等待循环。关键片段：

```asm
1238980: mov  %rax, ctx+0x8e0c40      ; 记录上次取时
1238987: mov  %r12d, ctx+0x8e0c48     ; 记录状态下标
123898e: mov  %rbx,%rdi
1238991: call 1238d80                 ; ★ signal pair-B（报告 43 的"有活就唤醒"）
1238996: mov  ctx+0x8e0c64,%eax
12389a4: addss ctx+0x8e0c60,%xmm0     ; g 累加
12389b3: movss %xmm0, ctx+0x8e0c60
        ; 然后进入 1238a28 的循环
```

**它先 signal 别人，然后进自己的循环等队列。**

→ 这个函数**每帧被调用约 4,700 次**，每次都做一遍记账 + 发 signal + 查队列。

**这是我目前看到的最可疑的一处**：一帧里重复 4,700 次同样的动作。

## 4. 但"修通知机制"仍不是答案（这条必须说清）

报告 44–47 追的是"通知为什么没送到"，结论是"送不到/没必要送"。
**N40 说明空转的成因不是"通知错"，而是"调用者在忙等"。**

| 之前的假设 | N40 的修正 |
|---|---|
| 循环在等一个会来的通知，只是通知路由错了 | **循环 99.7% 的轮次根本不等**——它查一下就走 |
| 修 signal routing 能减少等待 | **不能**，因为绝大多数轮次不涉及等待 |
| 优化超时值（2ms）能提速 | **只能影响那 21.4ms 的分配，不影响这 11.4ms** |

**所以报告 44–47 那四轮排除掉的东西（X/抢占/信号路由/钩子）确实是排除了，
但它们排除的是"等待侧"；N40 找到的是"**轮询侧**"——一个之前没人看的地方。**

## 5. 这条支线的明确方向（不是"再赌一次"）

**要回答的下一个问题很具体**：**谁在一帧里调用这个函数 4,700 次？**

三种可能，对应三种完全不同的处置：

| 可能 | 判据 | 处置 |
|---|---|---|
| **A. 调用者自己是个紧循环**（例如 `while(!done) check();`） | 找到调用者 0x1238920 的上层循环 | **这是忙等的标准形态，改成事件等待即可**，预期拿回接近 11.4ms |
| **B. 每帧真的需要 4,700 次检查**（例如每个 PBO/每个 region 一次） | 看 4,698 是否 ≈ 某物的数量（draw call 数？buffer 数？） | 若能合并检查 → 收益大；若不能 → 无收益 |
| **C. 有 4,700 个独立的等待对象各查一次** | 看 ctx 分布 | 需按对象分组（报告 47 的教训） |

**N43 就是查这个：`0x1238920` 的调用者是谁、它的循环结构是什么。**
纯静态（`grep "call 1238920"` + 读上层循环），零成本。

**这是"明确方向"，不是"可能就定了"**：
- 若是 A → **有确定的优化点，预期 30.9ms → ~20ms**
- 若是 B/C 且不可合并 → **这条线到底，但那时我们知道了确切原因**

### 8.1 方法论（本轮最该记住的一条）

**遇到"某段代码在等/在循环"，先测它占多少 CPU，再决定要不要挖它的内部逻辑。**

我没有这样做，先在 44–47 挖了四轮"它在等什么"，
最后 N40 一测才发现"它根本没在等，它在烧 CPU"——**问题的性质完全变了**。

**测 CPU 的成本**：两次 `/proc/PID/task/*/stat` 快照 + 一个 uprobe 定线程，**十分钟**。
**不测的代价**：四轮把"等待侧"挖到底，而真正的量在"轮询侧"。
