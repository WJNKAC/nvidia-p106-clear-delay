## 1. 反汇编复核你指定的两个偏移（这次看清了）

### 1.1 `glcore+0x146d340` 前后：这是 `wait_ms(mutex, cond, ms)` 的本体

函数入口 `glcore+0x146d280`：

```asm
146d280: push %r14/%r13/%r12/%rbp/%rbx
146d284: movslq %esi,%r13              ; ms
146d289: lea    0x30(%rdi),%r12        ; r12 = 对象基址+0x30  → cond
146d2a2: mov    %rdi,%rbx              ; rbx = 对象基址     → mutex
146d291: imul   $0x10624dd3,%r13,%r13  ; ms/1000 → 秒（魔数除法）
146d29b: imul   $0xf4240,%ebp,%r14d    ; 0xf4240 = 1e6 → ms*1e6 = 纳秒
146d2bd: call   *(%rax)                ; mutex lock
146d2bf: cmpb   $0x0,0x58(%rbx)        ; 检查"已取消"
146d2c3: jne    146d378                ; 取消 → unlock + 返回 1
146d301: call   gettimeofday@plt       ; ★ 取当前时间
146d30b: add    (%rsp),%rdx            ; 秒 += ms/1000
146d30f: imul   $0x3e8,0x18(%rsp),%rax ; usec*1000 → nsec
146d318: add    0x8(%rsp),%rax         ;     += ms*1e6
146d321: cmp    $0x3b9ac9ff,%rax       ; nsec > 999,999,999 ?
146d327: jg     146d360                ; 进位：秒+1、nsec-1e9
146d33e: call   *(%rax)                ; ★★★ pthread_cond_timedwait(mutex, cond, abstime)
146d340: test   %eax,%eax              ; ← 你给的偏移 = timedwait 的返回点
146d342: je     146d2df                ; 返回 0（被唤醒）→ 复查标志
146d344: ...                           ; 超时 → unlock + 返回 0
```

**确认：这是标准 `pthread_cond_timedwait` 的包装，必然产生 futex。**
gdb 栈显示 `glcore+0x146d340` 就是"卡在 futex 里"的现场，没错。

**但它是"每帧 3 次"级别的操作，不是"每对 1 次"。**

### 1.2 `glcore+0x123b31a` 之后：命令队列 worker 的等待分支

```asm
123b2f0: cmpb $0x0,0x17(%rsp)        ; 放弃标志
123b2f5: jne  123b309
123b2f7: mov  0x2c(%rsp),%eax
123b2fb: test %eax,%eax
123b2fd: jne  123b32f                 ; 有活 → 不走 wait
123b2ff: cmpb $0x0,0x8e0dc8(%r15)     ; ctx 标志
123b307: jne  123b32f
123b309: mov  0x8e0950(%r15),%rdi     ; 同步对象指针
123b310: mov  0x28(%rsp),%esi         ; ms
123b314: call *0x2d0(%rbp)            ; wait_ms
123b31a: test %eax,%eax               ; ← 你给的偏移
123b31c: jne  123afb4                 ; 超时
123b322: addl $1,0x8e0d24(%r15)       ; 被唤醒 → 等待计数++
```

**这是"没活可干时睡下去"，不是"每提交一次就等一次"。**

### 1.3 提交器 `glcore+0x1238920`：主体是自旋，futex 是兜底

```asm
12389c3: sfence                        ; ★ 提交后内存屏障
12389c6: jmp   1238a28
12389d0: movzbl 0x8e0e10(%rbx),%eax    ; ← 回环入口
12389d7: test  %al,%al
12389d9: je    1238abe                 ; 标志为 0 → 才去 wait
...
1238a28: mov   0x8e0a00(%rbx),%rdx     ; 读队列状态
1238a35: je    1238b48                 ; 空 → 退出
1238ab1: cmpb  $0x0,0x8e0c70(%rbx)     ; 放弃标志
1238ab8: jne   12389d0                 ; ★ 回环 —— 这是轮询
1238ad1: call  *0x2d0(%rbp)            ; 只有走到这里才 wait_ms(2ms)
```

**⇒ 提交路径的主体是"自旋轮询队列状态"（`jne 12389d0` 回环），`wait_ms` 只是条件退化时的兜底。**

**这解释了三个既有观测**：
- `ioctl` 只占 1%（轮询是用户态，不产生 syscall）
- CPU 100% 单核（报告 07 §4.1）—— 真在自旋
- `__GL_YIELD=USLEEP` 把 CPU 从 130% 压到 32% 而帧率不变（自旋是纯浪费）

## 2. 121 µs 到底在哪：`map`（回读）

`n83a` 的分项计时（报告 105，同一台机器，`-c 200`）：

| 分项 | M1（零变更） | M3（切 program + draw） | 差 |
|---|---|---|---|
| `submit_p50` | 0.050 ms | 0.208 ms | +0.158 |
| `rp_p50` | 0.104 ms | 0.109 ms | +0.005 |
| **`map_p50`** | **3.316 ms** | **15.170 ms** | **+11.854 ms** |
| `total_p50` | 3.413 ms | 15.547 ms | +12.134 |

**差异几乎全部落在 `map`（回读）上。** 100 对/帧：

```
11.854 ms ÷ 100 = 118.5 µs / 对
```

**`map` 是回读，它必须等这批命令在 GPU 上真的执行完。**
**⇒ 118.5 µs = "等这一对在 GPU 上完成"的时间。**

而 `submit` 只有 0.208 ms/帧（2 µs/对）—— **提交本身不慢，慢的是等它完成。**

## 3. 为什么 vGPU 上不慢（这才是要害）

既然：
- 用户态代码相同（同样是 glcore 的自旋轮询）
- 121 µs 落在"**等完成**"上

那唯一能不同的是：**完成信号从哪来、多快能来。**

```
真机：
  驱动自旋轮询 GPU 写回的内存 fence
  → 必须等真实 P106 把这一对的命令执行完、把 fence 写进内存
  → 每对 118.5 µs

vGPU：
  guest 驱动自旋轮询的，是【宿主映射进 guest BAR / 共享内存】里的 fence
  → 而这段内存由宿主 nvidia-vgpu-mgr 维护
  → 宿主可以【比真实 GPU 更早/更宽松地置位】（它只需保证语义顺序，不必等硅片真的做完）
  → 轮询很快通过
```

**这正好用上报告 110 A 段的源码事实**（那部分没被推翻）：

| 源码事实 | 在这里的作用 |
|---|---|
| `NV_VFIO_VGPU_ADD_MMIO_MAPPING` + `remap_pfn_range` | guest 自旋读的是**宿主内存页**，不是硅片寄存器 |
| `translate_gfn_to_pfn` | 宿主直读 guest 命令流，知道 guest 在等什么 |
| `nv_vgpu_inject_interrupt` → `eventfd_signal` (KVM irqfd) | **完成信号的时机由宿主决定** |

**⇒ 差异不在"用户态同步"，而在"被轮询的那个 fence 由谁写、什么时候写"。**

**你的反驳恰好把这个变量逼出来了：同样的自旋代码 + 不同的完成时延 = 不同的帧率。**

## 4. 报告 111 错在哪（以及为什么它会看起来很像对的）

它"像对的"的原因：**105 µs 和 121 µs 数值太接近（1.15 倍）**，很容易以为是同一个东西。

实际是两件不同的事，只是**数量级巧合**：

| | futex | map 等待 |
|---|---|---|
| 每次时长 | 105 µs | 118.5 µs |
| **每帧次数** | **3** | **100（n83a）/ 268（Heaven）** |
| 机制 | `pthread_cond_timedwait` | 用户态自旋轮询内存 fence |
| 产生 syscall | 是（所以 strace 看得到，占 83%） | **否**（所以 strace 完全看不到） |
| 贡献帧时间 | 3 × ~3 ms ≈ 9 ms（报告 33） | 268 × 118.5 µs = 31.8 ms |

**教训（已写进 SKILL）**：两个数字量级接近，**必须验次数**。
"每次多久"对上只是入场券，"每帧几次"才是判决。

**我上一轮刚在报告 111 里写下这条规矩，紧接着就在同一份报告里违反了它。**

## 5. 正确的模型（第三版，这次两个数都验过）

```
一帧（Heaven 1080p，268 对）
├─ 主线程：切状态 + draw，写命令到队列          ← 提交本身 2 µs/对，很便宜
├─ 每对之后：**自旋轮询 fence，等这对在 GPU 上完成**  ← 118.5 µs/对  ★ 主成本
│    （用户态自旋，无 syscall；真机要等硅片，vGPU 等宿主）
├─ 命令队列 worker：没活时 wait_ms(cond,100ms)   ← 3 次/帧，每次最长 ~3 ms
└─ present：present 层另有节拍（报告 106），但对 Heaven 份额为 0
                                    （primus 30→29 fps 已证）

合计 268 × 118.5 µs = 31.8 ms  ⇒  28.5 fps  ≈  实测 29-30 fps  ✅
```

**两个数都对上了：次数（268）× 单次（118.5 µs）= 帧时间。**
