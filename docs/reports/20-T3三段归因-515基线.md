# 20 · T3 运行时分段归因（515 基线）：一帧 = 5.5ms 渲染 + 11ms swap 内阻塞，余量 8.3ms

> # ⚠️ 本报告 §2.3 的"残差法"已作废（2026-10-25 14:35，见报告 21）
> **`残差 = swap内睡眠 − (swap_in 到下一 vblank 的距离)` 这个分解不成立。**
> 原因：vblank 会落在 swap **内部**（实测 1080p 有 511/901 帧、720p 有 574/900 帧），
> 此时该式算的是"vblank 之后到返回的部分"，与"等 vblank 之外的部分"混在一起，没有物理意义。
> 这也解释了本文 r 只有 0.16~0.30、残差 p10 为负。
> **作废的具体数字**：§2.3 表、§2.4 里"回读/额外等待"一行的 primus 2.73ms / dmabuf 0.22ms，
> 以及基于它的"余量 8.27 / 11.29ms"。
>
> **仍然有效**：§2.1~§2.2 的帧间隔、swap 段、主线程 off-CPU 分段（10.85ms 睡 / 0.14ms 忙 / 5.52ms 渲染）、
> §2.5 阴性对照（drain 90.2 次/帧、返回值全 0x0）、§1 的仪器与三个坑。
>
> **另一条更重要的修正**（报告 21 §1.2）：vsync 开启时 `swap段 + CPU渲染 + swap内CPU忙 == period`
> 恒成立（10.90 + 5.65 + 0.12 = 16.67），所以 **swap 段长度只是"补到 16.66ms 的剩余量"，
> 不携带 GPU 成本信息**。本文 §2.2 说"swap 内阻塞 11ms 占一帧 2/3"数值正确，但**解释要改**：
> 不是"驱动花了 11ms"，而是"驱动在等 vsync"。真实成本结构见报告 21 §2.3（CPU 渲染占 84%）。

> 2026-10-25 13:55
> 目的：静态与反编译已排除"swap 链里多一段等待代码"整类解释（报告 18/19），剩下只能靠运行时归因。
> 方法：**单时钟 ftrace**——所有探针（uprobe + tracepoint + sched）进同一个 buffer，无跨工具对齐问题。
> 结果：515 primus 与 dmabuf 两条路径都健康（1 vblank/帧，60.0 fps，p95/中位 1.09~1.12）。
> **关键量化：非等待工作量只占 8.4ms（primus）/ 5.4ms（dmabuf），余量 8.3ms / 11.3ms。**

## 1. 仪器设计

### 1.1 为什么用 ftrace 而不是 perf

所有探针进同一个 ring buffer，**共用 mono 时钟**，事件时间戳天然可比。
perf 多事件也能做，但 uprobe 与 tracepoint 混采时需要自己拼时间轴；ftrace 直接把对齐问题消掉，也省掉了 `trace_marker` 做锚点的必要（marker 只用来界定采集窗口）。

### 1.2 探针清单

| 段 | 探针 | 位置 | 偏移来源 |
|---|---|---|---|
| ② 提交+swap | `t3_swp_in` / `t3_swp_out`（p/r） | primus：`primus/libGL.so.1`；dmabuf：`libGLX_nvidia.so` 的 `glXSwapBuffers` | `nm -D` + 节映射算**文件偏移**（本例 vaddr==offset） |
| 阴性对照 | `t3_drain_in` / `t3_drain_ret`（$retval） | glcore `0xfbe5b0`（drain） | 报告 19 的指令指纹定位 |
| 阴性对照 | `t3_hop4_in` | glcore `0xf1ea00` | 同上 |
| ③ present→可见 | `drm:drm_vblank_event` | i915（card0） | tracefs，60.03 Hz |
| ①③ 归因 | `sched:sched_switch`（filter `prev_comm=="heaven_x64" \|\| next_comm=="heaven_x64"`） | 内核调度 | 判断"CPU 在等 vs 在干活" |

**没有采用 `drm_page_flip`**：本机 tracefs 只有 `drm_vblank_event` / `_queued` / `_delivered`（无 page_flip 事件）。
`drm_vblank_event` 已足够——它就是"vblank 心跳"，间隔 16.659ms（p05 16.639 / p95 16.680），极稳。

### 1.3 三个已修的坑（都会让数据静默失真）

| 坑 | 现象 | 修法 |
|---|---|---|
| **trace_marker 写早了** | marker 写在 `tracing_on=1` 之前 → 一个都没记下，窗口退化成全量 | 先 `tracing_on=1`，再写 START；END 后再关 |
| **uprobe 清理失败** | 上轮 5 个探针残留在 `uprobe_events`，新 run 变 7 个 → "clean 组"其实带着重探针 | 不能只写 `echo > events/enable`（多子系统下报 I/O error）；必须**逐个 disable 再清空**，否则 `Device or resource busy` |
| **探针清单没自检** | 上一坑发现得晚，白跑一轮 | 注册后比对 `uprobe_events` 里的名字集合与预期，不一致直接中止 |

第三条已经写成硬约束：脚本里 `期望/实得` 不一致就 `exit 1`。

### 1.4 为什么把"计时"和"计数"分成两次采集

第一次带 drain 探针跑 15s，得到 **159,926 次 drain 调用 / 860 帧 = 186 次/帧**。
这意味着 32 万个 uprobe 陷阱，结果**帧间隔从 16.60ms 涨到 17.12ms**——仪器改动了被测对象。

所以改为：
- `clean` 组（只挂 swap + vblank + sched）→ 用来**计时**
- `count` 组（加 drain/hop4）→ 只用来**计数**，时长压到 5s

这条纪律值得记住：**uprobe 打在 100 次/帧以上的热点函数上，本身就是负载。**

## 2. 515 基线结果

驱动 515.105.01，Heaven 1920×1080 窗口，vsync 开（默认配置），采集 15s。

### 2.1 两条路径总览

| 指标 | **primus**（readback） | **dmabuf**（直渲） |
|---|---|---|
| 帧间隔中位 | **16.60 ms** | **16.61 ms** |
| fps | 60.0 | 60.0 |
| p95 / 中位 | **1.12** | **1.09** |
| ② swap 段（in→out） | **10.98 ms** | **11.55 ms** |
| ①③ 帧内其余（out→下个 in） | 5.73 ms | 5.14 ms |
| 每帧 vblank 数 | **1.000** | **1.000** |
| 判定 | 健康 | 健康 |

> **仪器自校验**：本轮测得的 16.60ms / p95中位 1.12 与报告 16 用完全不同的探针（perf uprobe `judder.sh`）得到的 16.60ms / 1.10 一致。
> 两套独立仪器互证 → 这套 ftrace 仪器没有系统性偏差。

### 2.2 一帧的真实结构（这是本轮最重要的发现）

用 `sched_switch` 把"墙钟时间"切成"线程在跑"和"线程在睡"：

| | primus | dmabuf |
|---|---|---|
| 主线程在 **swap 内**睡了 | **10.85 ms（占 swap 99%）** | **11.41 ms（占 swap 99%）** |
| 主线程在 **swap 内** CPU 忙 | 0.14 ms | 0.14 ms |
| 主线程在 **swap 外** CPU 忙（渲染） | **5.52 ms** | **5.02 ms** |
| 主线程在 **swap 外** 睡 | 0.21 ms（占 4%） | 0.13 ms（占 2%） |

**结论：`glXSwapBuffers` 不是"提交一下就返回"，它内部阻塞了整整 11ms，占满一帧的 2/3。**
应用真正在算的只有 5.0~5.5ms。

### 2.3 那 11ms 等在什么上

对每帧算 `d = swap_in 到下一个 vblank 的距离`，与 `swap 内主线程睡眠` 比：

| | primus | dmabuf |
|---|---|---|
| swap_in → 下一 vblank | 8.57 ms | 11.09 ms |
| swap 内睡眠 | 10.85 ms | 11.41 ms |
| **残差（睡眠 − 等到 vblank）** | **2.73 ms** | **0.22 ms** |
| 相关系数 r | 0.299 | 0.158 |

- **dmabuf：残差 0.22ms** → swap 内阻塞 ≈ **纯 vblank 等待**，等完就返回（`swp_out→下一vblank` 15.79ms ≈ 一整个周期，即刚过 vblank 就返回）。干净。
- **primus：残差 2.73ms** → 除了等 vblank，**还多阻塞 2.7ms**。这与 primus 的机制吻合：它要 1080p×4B=8.3MB 回读 + blit，这段在主线程上是阻塞的。

> **诚实标注**：r 只有 0.16~0.30，"睡眠 ≈ 等 vblank"这个线性模型解释力不强（残差 p10 甚至为负）。
> 说明 vblank 等待不是唯一成分，且等待发生在 primus/NVIDIA 内部的某个不透明位置。
> 本机 12~14 个线程在 swap 窗口内都睡 ~11ms（都是空闲工作线程，且**线程名全部叫 `heaven_x64`**，无法按名字区分角色），
> 所以"具体哪个线程在等 vblank"本轮**没能确定**。

### 2.4 余量：决定"会不会掉到 2 vblank"的那个数

非等待工作量 = 渲染期 CPU 忙 + swap 内 CPU 忙 + 回读/额外等待（残差）：

| | primus | dmabuf |
|---|---|---|
| 一个 vblank 周期 | 16.66 ms | 16.66 ms |
| 渲染期 CPU 忙 | 5.52 | 5.02 |
| swap 内 CPU 忙 | 0.14 | 0.14 |
| 回读/额外等待 | 2.73 | 0.22 |
| **非等待工作量** | **8.39 ms** | **5.37 ms** |
| **余量** | **8.27 ms** | **11.29 ms** |

**这是本轮给出最有用的一个数**：515 在 primus 上有 8.3ms 余量、dmabuf 上有 11.3ms 余量。

### 2.5 阴性对照（drain / hop4）

`count` 组（5s，明确会扰动时序，只用于频次）：

| 项 | 值 |
|---|---|
| drain 调用 | **90.2 次/帧**（15s 那次是 186 次/帧，随场景负载变化） |
| hop4 调用 | **16.4 次/帧** |
| **drain 返回值** | **全部 `0x0`**（27,229/27,229） |

- drain 是**每次绘制批处理调一次**，不是每帧一次。所以报告 13 说的"deadline 几乎从不 arm"与"drain 被调用 90~186 次/帧"并不矛盾：**调用极频繁，但从不返回 1（从不放弃/超限）**。
- hop4 16.4 次/帧，也与报告 19 的"批处理提交器"身份吻合。

## 3. 预注册判读表（针对 525 复测，已按本轮数据锐化）

515 基线：swap 段 11ms、swap 内睡眠 11ms、残差 0.2~2.7ms、余量 8.3~11.3ms、1 vblank/帧。

| 525 观测（同脚本同探头） | 判读 | 下一步 |
|---|---|---|
| swap 内睡眠 ≈ **33.3ms**，**残差仍 ≈0** | **等待目标翻倍**：swap 被指示等 2 个 vblank（swap interval / present mode 语义变化），不是变慢 | 查 swap interval 解析路径 + present barrier 是否运行时激活（T5）；580 若同源则证据链闭合 |
| swap 内睡眠 ≈ 33.3ms，**残差 ≈16ms** | **工作量暴涨**：非等待部分从 8.4ms 涨到 ~25ms | 与静态结论冲突（报告 18/19 已排除），需重查回读/present 路径 |
| swap 段仍 ≈11ms，但帧间隔 33.3ms，且 swap 外睡眠 ≈16ms | **掉帧在 swap 之外**：present→可见 段多了一个 vblank（callback 延迟） | 转向"present/callback 交互型"，查 kwin/Xwayland 侧 |
| 每帧 vblank 数 ≈ 2 但 swap 段与残差都正常 | **节拍被外部锁定**：帧本身按时交付，但合成器只每 2 拍取一次 | 查合成器帧回调 / present barrier 语义 |
| drain 返回值出现 `0x1` | arm 超限真的发生，机制闭环 | 与报告 13 的 515 阴性结果对照 |

> 判读的关键分水岭是**残差**：等待目标翻倍时残差不变（仍≈0），工作量暴涨时残差跟着涨。
> 这是 T3 相比"只看帧间隔"多出来的判别力，也是"每帧吞 2 拍"这个描述第一次变得可分解。

## 4. 本轮没能做到的（诚实清单）

| 项 | 原因 |
|---|---|
| 逐段拆出"present→可见" | 本机无 `drm_page_flip` 事件，只有 `drm_vblank_event`。且 compositor（kwin）的 pageflip 与应用 swap 之间没有可关联的 id |
| 确定"哪个线程在等 vblank" | 12~14 个线程全部叫 `heaven_x64`，只能靠 off-CPU 时长猜；空闲工作线程与等待线程时长几乎相同（都是 ~11ms） |
| 分离 primus 的 2.73ms 残差成分 | 需要 primus 内部 `glReadPixels`/blit 的 uprobe，primus libGL 是 stripped 且无对应导出符号 |
| 采集期间的场景相位自动判定 | 仍靠"窗口出现 + 预热 22s"；GPU util 在 58~99W 之间波动说明相机路径仍会经过轻重段 |
