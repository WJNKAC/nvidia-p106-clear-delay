# 90 · N99：内核提交没变、等待策略没变 —— 变的是**用户态命令流：每批重绑一次引擎对象（OBJECT）**

日期：2026-10-26 14:50
驱动：525.116.03
方法：LD_PRELOAD 统计 ioctl 次数/时长（按 cmd）+ 直接 dump push buffer 尾部找重复单元

---

## 0. 回答你的问题：**都不是**

| 候选 | 实测 | 结论 |
|---|---|---|
| **内核提交批次的方式变了？** | 525 kind=1（1000 对/帧）：提交类 ioctl `0xc020462a` = **211 次 / 20 帧 ≈ 10.5 次/帧**；515 同负载 **199/20 ≈ 10 次/帧**。且 **N=100 / 1000 / 4000 都是 ~200 次**（与批次数无关） | **❌ 没变**：两版都不是"每批提交"，提交粒度相同 |
| 单次提交是否变慢？ | 525 kind=1：avg **11.2µs**、max 519µs（kind=0 avg 77.4µs、max 13.4ms） | **❌ 内核不在每批上阻塞** |
| **用户态等待策略变了？** | 提交器/kick/process/块管理/notify 五段逐条等价（报告 80）；等待原语是纯 20µs 延时轮询、两版同构（报告 53/88） | **❌ 等待代码相同** |
| **→ 剩下** | **用户态写进命令流的内容变了** | **✓ 见下** |

## 1. push buffer 里每对的"命令足迹"是 **56 字（224 字节）**，且每份都带一次 OBJECT 重绑

dump kind=1 的 push buffer 尾部，能看到**严格重复的单元**（`+0x7f5ec`、`+0x7f6cc`、`+0x7f7ac`、`+0x7f88c`…，间隔 **0xE0 = 224 字节**）：

```
+0x7f5ec: 00000004 20010d2a 80000000 80000587 20010e66 000000f0 200105a2 00000000
+0x7f60c: 80510850 80040853 20010851 00000730 20010924 00000010 800103d0 200403d1
+0x7f62c: 3f800000 3f000000 3e4ccccd 3f800000 80000084 800003c7 200200d8 20164010
+0x7f64c: 00000020 20010514 00400008 80000489 2001065b 00000000 200104ea 11111111
+0x7f66c: 200100df 00000001 8001064b 80000800 80110810 80040813 20010811 00000830
+0x7f68c: 20010904 00000010 20010980 00000001 8000047c 2001008a 00000001 a0050e04
+0x7f6ac: 00000000 00000000 04459600 00000000 04455b08 a0030e44 00000007 00000001
+0x7f6cc: 00000004 20010d2a 80000000 80000587 ...   ← 与 0x7f5ec 逐字相同（除指针）
```

按 envytools 的 header 格式（bit31:29 = 001 增量 / 100 非增量，bits28:16 = count−1，bits15:0 = method>>2）解几个：

| 命令字 | 解码 |
|---|---|
| **`80000000`** | **非增量、count=1、method `0x0000` = `OBJECT`（绑定引擎对象）** ← **每对恰好一条** |
| `20010d2a` | 增量、count=2、method `0x0A8` |
| `80000587` | 非增量、count=1、method `0x161C` |
| `80110810` | 非增量、count=18、method `0x2040`（一次写 18 个字的状态块） |
| `80040813` | 非增量、count=5、method `0x204C` |
| `a0050e04` | 非增量+imm、count=5、method `0x3810` |
| `a0030e44` | 非增量+imm、count=4、method `0x390C` |

`0x04455ae0 → 0x04455b08 → 0x04455b30`（每对 +0x28）是**顶点/常量缓冲的 GPU 地址**，说明每对还在切缓冲。

**⇒ 525 在每次"批次断开"时，往命令流里写了一条 `OBJECT` 重绑。**
按 envytools：`mthd 0x0000 OBJECT — Binds an engine object`。**重绑引擎对象 = 让 GPU 重新装载该 class 的上下文状态**，
这与"每批 122µs、GPU 空转、显存 0%、无等待命令"四条观测全部吻合。

对照：kind=0（legacy `glColor3f`）每对的足迹小得多，尾部几乎全是 0（只写少量状态），
**没有 OBJECT 重绑**，所以免费。

## 2. 因果链（更新版）

```
525：每次管线绑定 → 驱动把当前批次收尾 → 写一条 OBJECT（重绑引擎对象）→ 开新批次
        ↓
GPU：重绑对象要重新装载 class 状态 → 该批第一条 draw 前后停 ~122µs（util 100% / 37W / mem 0%）
        ↓
主机：按 20µs 粒度轮询"这批消化完没有"，问 ~8 次才见推进（报告 88）
        ↓
Heaven 268 批/帧 × 122µs = 33ms → 34fps
```

**责任层：用户态驱动（命令流），不是内核提交、不是等待策略。**

## 3. 还差最后一格（需要 515 才能做）

**515 是否也每批写 OBJECT？** 三种可能：

| 515 的行为 | 含义 |
|---|---|
| 也写 OBJECT，但 GPU 侧不慢 | 重绑本身不贵，贵的是 525 的**重绑实现**（对象不同/状态更多） |
| **不写 OBJECT**（批次之间复用同一对象） | 就是"525 新增了每批重绑" —— 与报告 35/66 的"插入一次等待"是同一次改动的两个面 |
| 写 OBJECT 但频率低（每帧一次） | 525 把重绑粒度从"每帧"改成"每批" |

验证方法（需换 515，5 分钟）：`pair_only 100 1000 1 1` + `n102_period.py` dump 尾部，看 224B 周期是否存在、`80000000` 是否每周期一条。
