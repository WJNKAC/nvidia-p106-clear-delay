## 0. 结论先说（三句）

1. **121µs 不是"等物理引擎"，是 `futex` 往返**：实测 **105 µs/次**（87,637 次，占 83.1% 的 syscall 时间）。
   121 ÷ 105 = **1.15**，同量级。
2. **内核驱动只占 1.00% 的 syscall 时间**（ioctl 62 µs/次、1761 次）。**内核不是瓶颈，那里也没有这个等待。**
3. **静态对比也证实内核没有"新增的等待机制"**（三条独立测量，见 §2）。

**⇒ 我上一轮说的"等物理引擎 arming"是错的，那是从 231k GPU 周期反推出来的措辞，没有直接证据。**
**真正在等的是驱动自己的 worker 线程。**

## 1. 静态挖内核：按指令做了三步，都不支持"内核里有这个等待"

### 1.1 第一步：等待/延时类符号，两版完全一致

| 515.105.01 | 525.116.03 |
|---|---|
| `os_delay` / `os_delay_us` / `os_schedule` | 同 |
| `os_wait_interruptible` / `os_wait_uninterruptible` | 同 |
| `os_alloc_wait_queue` / `os_free_wait_queue` | 同 |
| `os_semaphore_may_sleep` | 同 |

**没有新增任何"等待原语"。**

### 1.2 第二步：内存屏障与自旋提示（pause）密度相近

| 指令 | 515 | 525 |
|---|---|---|
| `sfence/mfence/lfence` 总数 | **270**（154 个函数） | **325**（177 个函数） |
| `pause`（`F3 90`）总数 | **41**（3 个函数） | **43**（5 个函数） |

**没有数量级差异。** 而且两版各有**两个含 20 个 `pause` 的函数**（515：`_nv035305rm`/`_nv036557rm`；525：`_nv039931rm`/`_nv041327rm`）——
那是紧凑自旋循环，**两版都有，不是 525 新增**。

### 1.3 第三步：读寄存器 + 短回跳（真轮询的结构特征）

| | 515 | 525 |
|---|---|---|
| 含"读 HAL 寄存器指针"的函数 | 44 | 106 |
| 含短回跳的函数 | 13,020 | 13,689 |
| **两者兼具（真轮询候选）** | **11** | **15** |

**11 vs 15 —— 同一量级。** 525 略多，但没有任何一个是"每批一次"的形态。

### 1.4 一个必须报告的负面结果：两版机器码**几乎无法对齐**

我用"规范化机器码哈希"（把 `.rela.text` 指向的 4 字节立即数清零后取 SHA1）做了全量对齐：

```
515: 取 20,703 个函数，唯一骨架 19,729
525: 取 23,185 个函数，唯一骨架 22,302
骨架相同: 1        ← 只有 1 个
对齐率: 0.005%
```

**⇒ 515→525 之间 NVIDIA 重编译了整个 RM**（编译器版本或全量代码变动）。

这条负面结果本身很重要：
- **不可能存在"在 515 的某个函数里插入几行等待代码"这种形态** —— 因为机器码层面全变了，那种对比做不了
- 也解释了为什么前几轮"逐函数 diff"的做法一直不奏效

### 1.5 静态侧的小结

**三条都指向同一件事：525 的内核没有新增"等物理引擎"的机制。**

## 2. 真正的答案：`futex` 105 µs/次

`analysis/onmachine/2026-10-24-runtime/strace-heaven-1080p.txt`（580.126.18，Heaven 1080p 稳态，30 s 窗口）：

```
% time     seconds  usecs/call     calls    errors syscall
 83.10    9.217744         105     87637      5117 futex
 15.24    1.690257          81     20717           clock_nanosleep
  1.00    0.110590          62      1761        10 ioctl
```

### 2.1 三个数字的对照

| 量 | 值 | 来源 |
|---|---|---|
| `futex` 平均阻塞 | **105 µs** | 上表 |
| `n83a` 每对成本 | **121 µs** | 报告 105 实测 |
| 比值 | **1.15** | — |
| `ioctl` 平均耗时 | 62 µs（占 **1.00%**） | 上表 |

**121 与 105 同量级，与 ioctl 无对应关系。**

### 2.2 为什么这不可能是内核

`n83a` 每帧 **100 对**（`swaps_per_frame=100`），`Heaven` 每帧 **268 对**。
如果每对都要进内核一次，`Heaven` 每帧至少 268 次 ioctl。

**实测：10 万次轮询预算下，ioctl 全程只有 1761 次**（30 s 窗口，约 900 帧 ⇒ **约 2 次/帧**）。

⇒ **每帧只进内核 2 次，却要付 268 次 × 121 µs。**
⇒ **这 121 µs 必然发生在用户态。**

### 2.3 futex 是谁和谁在同步

`futex` 是**同进程内线程间**的同步原语（`futex_wait` / `futex_wake`，走共享内存 + 系统调用）。
105 µs 是"一次 wait 到被唤醒"的往返延迟。

与既有结论完全吻合：

| 既有实测 | 报告 |
|---|---|
| 主线程 **83% 时间在等 worker** | 报告 72 |
| `futex` 87,637 次占 **83%** syscall 时间 | 报告 07 / 09 |
| `__GL_YIELD=USLEEP` 后 CPU 130%→32%、**帧率不变** | 报告 07 |
| 主线程 100.2% 单核（自旋） | 报告 07 §4.1 |

**⇒ 一帧的构成：主线程把活交给 worker → `futex_wait` → worker 干完 `futex_wake` → 主线程继续。
这个往返 = 105~121 µs。525 每对都走一次，515 不走。**

### 2.4 那 GPU 在干什么

**GPU 在等命令。** 主线程卡在 futex 上，活没喂上去，所以：
- 功耗只有 48 W（不是满载）
- `GPU-Util 89-93%`（不是 100%，因为有空档）
- SM 时钟满 1911 MHz（没降频，不是功耗墙）

**这三条早就在报告 05 里，当时被解读成"GPU 空转在等米下锅"—— 那个措辞其实是对的，只是没找到"等的是 futex"。**

## 4. 修正后的完整模型

```
525 真机：
  主线程：切状态 → 打包 → 交给 worker → futex_wait …………（105-121 µs）……… 醒来
  worker：收命令 → 写 pushbuffer → 门铃 → GPU 开始画
  ⇒ 每对一次 futex 往返 ⇒ 268 对 = 31.8 ms ⇒ 28.5 fps
  ⇒ GPU 在两次喂活之间空闲 ⇒ 48 W
 
515 真机：
  主线程：切状态 → 打包 → 自己写 pushbuffer → 门铃 → 继续（不交接）
  ⇒ 0.03 µs/对
  ⇒ GPU 持续被喂活 ⇒ 101 fps / 111 W
```

**关键差异不是"驱动等 GPU"，而是"主线程要不要把活交给另一个线程"。**
515 单线程干完，525 拆成两段并用 futex 交接。

**这也解释了为什么所有"改 present / 换 Vulkan / 调 vsync"都无效** ——
那些手段动的是显示路径，而瓶颈是**提交路径上的线程交接**。

## 5. 这个结论的可验证性（以及为什么现在验不了）

| 预测 | 怎么验 | 状态 |
|---|---|---|
| futex 次数 ∝ 对数（不是 ∝ 帧数） | `strace -c -e trace=futex` 跑 n83a，对比 M1 与 M3 的 futex 次数 | **需驱动，当前 <testhost> 无 nvidia** |
| `futex` 105 µs 就是那个固定项 | 把 worker 线程绑到另一个核、降低 futex 唤醒延迟，看 121 µs 是否下降 | 同上 |
| 单线程跑（`__GL_THREADED_OPTIMIZATIONS=0`）应显著改善 | 已有实测：**28 fps（vs 30）**，只降 2 ⇒ **这条与模型不符** | ⚠️ 见下 |

### 5.1 一处不自洽，必须写出来

报告 07 实测 `__GL_THREADED_OPTIMIZATIONS=0` 时帧率 **28 fps**（base 30），**没有改善**。

如果瓶颈是"线程交接"，关掉多线程应该大幅改善。**它没有。**

**⇒ 模型还不完整。** 可能的解释：
- `__GL_THREADED_OPTIMIZATIONS=0` 关的是 GL 的显示列表线程，**不是提交用的 worker**
- 提交 worker 是另一套（`PRIMUS_SLEEP` / display worker / readback worker），关不掉

报告 72 说"主线程 83% 在等 worker"，而报告 67 说"readback worker 等驱动队列 27.0 ms/帧"。

**⇒ 真正该查的是：那个被等的 worker 到底是哪个，以及它为什么慢。**
这比继续挖内核 blob 有意义得多。
