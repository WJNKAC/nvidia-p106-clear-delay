**结论**：**预测正确，而且实际情况比预想更简单 —— 只改 1 个字节就够了。**

| 配置 | `map_p50` | `fps` | `chk` |

## 1. 第 1 步：问题依然存在，且与 525 数值几乎一样

按报告 172 的验证流程，第一步先确认问题是否还在：

| 配置 | `map_p50` | `fps` | `chk` |
|---|---|---|---|
| 580 原版 | **52.195 ms** | 18.98 | 5150 |
| 525 原版（kernel 6.1 上测的） | 52.276 ms | 18.96 | 5150 |

**两个大版本差距（内核 6.1→6.12、驱动 525→580），`map_p50` 只差 0.08 ms（0.15%）。**

> **⇒ 这是同一个问题在多个版本里延续，不是新问题。**
> 这也说明这个"每批 218 µs"的代价与内核版本、驱动版本基本无关，是 glcore 自身的行为。

## 2. 第 2 步：确认命令确实在发

```

```

与 525 完全一致。

## 3. 第 3 步：只改第一处就够了

**运行时验证**（不动文件）：

```bash
PATCH="0xb51c82=eb" LD_PRELOAD=patchpb.so \
  ./n83b_new -M 7 -c 400 -n 400 -f 100 -W 3 -q
```

| 配置 | `map_p50` | `fps` | `chk` |
|---|---|---|---|
| 580 + 补丁 | **3.434 ms** | **259.79** | **5150** |

**⇒ 一次成功，不需要像 525 那样改两处。**

### 3.1 第二处为什么不用管：实测它没被调用

报告 172 里我担心第二处（`0xde855e`，函数 `0xde81e0`）因为"无判据 + 无条件循环发射"不好改。
**实测证明这个担心在当前负载下是多余的：**

| 验证 | 结果 |
|---|---|
| 在 `0xde81e0` 入口下硬件断点，5 秒采样 | **命中 0 次** |
| 补丁后扫 pushbuffer 的 `method 0x3998` | **样本 0 条** |

**⇒ `n83b` 这种负载完全不走第二处。** 补丁后命令一条不剩，说明第一处就是全部。

> **但这不代表第二处永远不走。** 它是另一条路径（可能是别的绘制模式/别的对象类型），
> **其他应用有可能走到**。如果以后遇到"某些程序还是慢"，应先查这个函数是否被调用。

## 6. 本轮踩的坑：NFS `.nfs` 残留导致大文件操作反复失败

### 现象

给 `patch/580.178.04/` 复制 37 MB 的 `.so` 时，`cp` **反复被 SIGTERM 中断**，
`ls` / `stat` 那个目录也返回 137。换 `python3 shutil.copyfile` 也一样。

### 根因

**有进程仍持有目标文件的句柄，NFS 无法真正删除文件**，
于是把它重命名成 `.nfs00000000014497f3...` —— 表面看"删掉了"，
实际上旧的 inode 还在被占用，新建同名文件时又冲突。

`ls -la` 能看到 `.nfs*` 文件即是证据。

### 处理

```bash
rm -f before/.nfs*        # 若无进程持有，会真正删掉
```

或者：**不要"先删再建"，改用原地读写**：
```python
d = bytearray(open(src, "rb").read())
d[off] = new
open(dst, "wb").write(d)      # 直接写，不经过删除
```

> **教训：NFS 上删/覆盖大文件前，先确认没有进程持有该文件。
> 看到 `.nfs*` 文件就说明"假删除"已经发生，`cp` 会一直失败但看不出原因。**

## 7.5 长时间稳定性验证：Heaven 满负载 5 分 28 秒，零错误

用 Heaven 4.0 完整 benchmark（1920×1080 / Quality High / `primusrun`）压测，
**全程无任何 LD_PRELOAD 注入**，即纯静态补丁生效状态。

### 采样数据

| 时刻 | GPU 利用率 | 功耗 | 温度 | SM 时钟 |
|---|---|---|---|---|
| 2 min | 100% | 117–119 W | 54 °C | 1860–1885 MHz |
| 5 min | 99–100% | 118 W | 55 °C | 1885 MHz |
| 5'28"（关闭前） | 95% | 105 W | 54 °C | 1885 MHz |

关闭后回落：**32 W / 48 °C**，无残留进程。

### 错误检查

对启动日志做全文扫描（错误 / Xid / 失败 / 损坏 / 复位关键字），**命中数 = 0**。
全程零 Xid、零错误、无花屏记录。

### 这组数据说明了什么

| 观察 | 含义 |
|---|---|
| **118–119 W** | 原版 580/525 只有 55–70 W（在等延迟）。**118 W 说明 GPU 真在满载渲染**，不是空转 |
| 温度仅 54–55 °C | 散热余量充足，无过热降频 |
| 时钟稳定 1860–1885 MHz | 未触发功耗墙 / 温度墙 |
| 零错误 | 跳过那条命令**没有引入可见副作用** |

### 一个必须说清的局限

Heaven 的 `-benchmark` 模式**不往日志写 FPS**（日志仅 106 行，全是加载信息），
搜 FPS 关键字永远为空。所以：

- **绝对帧率以 `n83b` 的 3.434 ms / 259.79 fps 为准**
- Heaven 侧提供的是**功耗 / 利用率 / 温度 / 错误计数**这四项"是否正常工作"的判据

原则上可以截图读屏幕 FPS，但 benchmark 模式下 Heaven 会隐藏 FPS 叠层，这条路径也走不通
—— **不硬凑数字，用能拿到的证据说话**。
