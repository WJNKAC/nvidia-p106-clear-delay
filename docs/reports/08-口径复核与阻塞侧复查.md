## 2. FUTEX_WAIT 的真实延迟分布（配对 unfinished→resumed 后）

剔掉 1,693 个被"空闲线程停车"污染的 >20 ms 样本：

| 分桶 | 占比 |
|---|---|
| 100–200 µs | 20.2 % |
| 200–400 µs | 23.7 % |
| 400–1000 µs | 4.7 % |
| 1.0–2.5 ms | 15.3 % |
| **EAGAIN（超时未等到）** | 358 次 / 6 s，**全部落在 ~2.05 ms** |

- 中位 **357 µs**，不是 105 µs，也不是 650 µs。
- `FUTEX_WAKE` 本身很便宜：**13 µs**（中位 9 µs）→ 不是唤醒开销大，是**被等的东西到得慢**。
- **存在一族 2 ms 超时的轮询**（358 次/6 s ≈ 2 次/帧），是被证实的"定时器轮询"痕迹，但量级不足以解释 26 ms。

## 3. 睡眠的真实来源：应用，不是驱动

`strace -f -k -e trace=clock_nanosleep`（6.5 k 次调用，63 k 行栈）：

```
libc clock_nanosleep ← nanosleep ← usleep ← libUnigine_x64.so
```

- 含 `libnvidia` 的栈行：**2 / 63,200**
- 含 `libUnigine` 的栈行：**17,595**
- 时长分布：**1 ms × 5,271（79.2%）、10 ms × 1,239（20.8%）**，无 250 µs

→ **驱动在稳态不调用任何 nanosleep**。我之前把"45 次/帧"记在驱动账上是错的。
应用自己在以 1 ms 粒度轮询（约 10 次/帧 ≈ 10 ms/帧），这是 Unigine 引擎自身的行为。

## 4. 阻塞侧的跨版本静态复查（按用户指的正确定方向）

方法：`pltmap.py` 把对 `nanosleep/usleep/sched_yield/pthread_mutex_*` 的 **call/jmp @plt 调用点**，
经 `.eh_frame` 的 FDE 表（580 = 46,990 个函数）映射到所属函数。

| 等待原语 | 515.105.01 | 525.116.03 | 580.126.18 |
|---|---|---|---|
| `nanosleep` | 4 处 / 3 函数 | **4 / 3** | **34 / 20** |
| `usleep` | 6 / 3 | 6 / 3 | 6 / 3 |
| `sched_yield` | 3 / 3 | 3 / 3 | 2 / 2 |
| `pthread_mutex_lock` | 0 | **0** | 6 |
| `pthread_cond_wait` / `_timedwait` | 0 | 0 | **0** |

**两个硬结论：**

1. **`pthread_cond_*` 完全不存在**（三代皆 0）→ 用户假设的"condvar 走 libc 的定时轮询"**这条路不存在**。
2. **515 与 525 在这组原语上逐项相同**；差异全部出现在 580（nanosleep 4→34，mutex 0→6）。
   → 如果"525 也坏"这个前提成立，那**阻塞侧的静态差异解释不了它**；反过来，这个表更像是在说
   **GL 侧的等待机制变化发生在 535/580，而不是 515→525**。

**但这条差异我也不能当因果用**：`0xf860b0`（10 个 nanosleep 点的主函数）引用的字符串是

```
"NVIDIA: could not create file for device %u"
"channel%d"
"/dev/nvidia-caps-imex-channels/channel%d"
"/sys/bus/pci/devices/%04x:%02x:%02x.%1u/rescan"
```

即 **设备文件 / imex channel / GPU 恢复重扫** 的代码路径，不是每帧路径。静态调用点数**不能证明运行时会走到**。

## 5. 门控 bit 的运行时翻转试验（用户提议的 gdb 方案）

### 5.1 先测性质：配置位还是运行时状态

直接读 `/proc/<pid>/mem`（`ptrace_scope=0`，同用户可读）：

```
0x235dec0 : 00 00 00 00   (t0)
            00 00 00 00   (t3)
            00 00 00 00   (t6)
0x235fba0 : 00 00 00 00
0x235dec4 / 0x235fba4 / 0x235fba8 : 全 0
```

**初始化后沉默、每帧不重写 → 判定为配置位，且当前是关的**（与"排空等待确实在跑、占 73% 采样"一致）。

### 5.2 翻转

用 gdb batch 直接改内存（写入被回读确认，且到进程结束都没被改回）：

| 相位 | 操作 | CPU | 功耗 | **FPS** |
|---|---|---|---|---|
| base | — | 126 % | 50.7 W | **30** |
| flip A | `0x235dec0 = 0x01`（跳过排空等待） | 125 % | 48.6 W | **31** |
| flip B | `0x235fba0 = 0x07`（第二道门） | 126 % | 47.0 W | **31** |

### 5.3 判读（落在用户预注册表的"flip 无效"格）

- **帧率不动** —— 与 USLEEP 自洽：自旋本来就不是地板，跳过它当然不改帧率。
- **CPU 也不动（126%）** —— 这一条比帧率更有信息量：如果 `0xae5c59 → 0xb0fd70` 真是那个 126% 自旋的入口，
  门一开 CPU 就该塌。**它没塌 → 那个自旋不是从这条链来的**，是我把 LBR 的层级读错了。
- 结论：**门不是判别器，这条线索判死，不再追。**

## 6. 修正后的定量模型

```
33.3 ms/帧 ≈ 40 次同步往返 × ~350 µs（14 ms）
           + 应用自身 usleep(1000) 轮询 ~10 次（10 ms）
           + 真实渲染/光栅化（1080p 约 7 ms）
           + 其余 CPU 工作
```

支撑：
- 40 次 `FUTEX_WAIT`/帧（实测 1,212/s ÷ 30 fps）
- 每次中位 357 µs（实测分布）
- 应用 1 ms 轮询 ~10 次/帧（实测栈 + 时长分布）
- 渲染量 7 ms（320×200 vs 1080p 的帧时间差反推）
- GPU 在两次往返之间无活可干 → 满频 45 W、util 92%
- Vulkan 批量提交 → 358 fps（不产生这 40 次往返）

**两层都在"轮询"而不是"事件驱动"**：应用 1 ms 粒度、驱动 350 µs 粒度。

## 8. 方法论教训（追加到 07 §6.1）

1. **单条指令高占比可能是 skid 假象**；**调用点数量多寡不能证明运行时走到**；**栈回溯要注意 `<unfinished>/resumed` 配对**（否则阻塞时长会串到别的 syscall 上）。
2. **`objdump` 的输入必须核对架构**：`.../32/libnvidia-glcore.so` 与 64 位同名，混用会让整份对比失效且不报错。
3. **"每帧次数"这类折算，必须按时间窗切分**：启动期（shader 编译、world load）的 syscall 会严重污染总量。
4. `strace -c` 与 `-ff` 在 6.13 互斥；要分线程得用 `-ff -T` 自己求和。
5. 同用户 `ptrace_scope=0` 时，`/proc/<pid>/mem` 可直接读写目标进程内存，无需 sudo 或 gdb 就能验证"配置位 vs 运行时状态"。
