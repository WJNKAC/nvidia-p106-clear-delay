# 36 · N6：直接读驱动自己的计时器（零探针）——队列上下文约 90% 的时间在等

> 2026-10-25 21:40
> 目标（用户指令）：先做 N6（零成本），再决定要不要换 515 跑 N3。
> **方法**：一次 gdb 断点只为取 ctx 地址 → 之后纯 `/proc/PID/mem` 轮询读驱动自记时字段。
> **不挂任何 uprobe、不反复 attach**，对被测进程只有"读内存"一种扰动。

---

## 1. 结论先行

| # | 结论 | 证据强度 |
|---|---|---|
| 1 | **驱动自记时的单位是 µs**（`Δlast_ts ÷ 墙钟 = 1.0063 / 1.0011`，两次独立运行） | 强（自带标定） |
| 2 | **有一个 ctx 约 90~93% 的墙钟时间处于"等待区(state=1)"**，`arr[1]+arr[2]` 闭合到 **100.6% / 100.1%** | 强（内部闭合） |
| 3 | **每次进入等待平均 23~28 ms ≈ 一个帧时间**，约 **1 次/帧** | 中（两次运行差 20%） |
| 4 | **`wcnt` 会递增**（run1 观测到 0→1→2，8 段/10s；run2 全程 0）→ 报告 34 的 **"pathC 恒 0 ⇒ wait_ms 从不返回 0"不成立** | 中（间歇性） |
| 5 | **第二个 ctx 的自记时数组完全不增长**（`arr[1]` Δ=1µs）→ 该计时器只覆盖其中一个上下文 | 强 |
| 6 | 因此 34 的"窗口内 3ms"确实是**裁剪值**：真实等待 ~23~28ms，3ms 只是它与 map 窗口相交的那一段 | 强（与 34 §2.3.1 独立吻合） |

**一句话**：驱动自己记录的数字说——**这个命令队列上下文每帧有约 26ms 是在等，不是在做**。
这与报告 31 的"GPU 只有 48~68W ≈ 空转"、34 的"队列处理器在睡，没人喂 GPU"完全一致，
而且这次是**驱动自己算的**，不是我们推断的。

## 2. 字段定位（已逐条核对，两个版本布局相同）

| 相对 ctx | 525 | 515 | 含义 |
|---|---|---|---|
| `+0x00` int64 | `0x8e0d00` 写于 `123af66` / `123aff2` | `0x55f080` 写于 `c81b30` | 上次取时时间戳（µs） |
| `+0x08` int32 | `0x8e0d08`：`123af6d`=**1**、`123aff9`=**2**、`1237c2d`=**3** | `0x55f088`：`c81aa8`=**1**、`c81b37`=**2** | 状态 |
| `+0x0c` uint8 | `0x8e0d0c`，`cmpb` @`123af28` | `0x55f08c`，`cmpb` @`c81af1` | 非 0 → 跳过累加 |
| `+0x10` float[4] | `0x8e0d10`，`addss` @`123af52` / `123afe2` | `0x55f090`，`addss` @`c81b20` | 按 **state 下标**累加 elapsed |
| `+0x24` int32 | `0x8e0d24`：`123ad47`=0、`123b322`=**+1** | `0x55f0a4`：`c81877`=0、`c81d64`=**+1** | 等待计数 |

累加代码形状（两版同构，这就是"识别信号"）：

```
123af38: movslq 0x8e0d08(%r15),%rcx     ; idx = 当前 state
123af46: sub    0x8e0d00(%r15),%rsi     ; now - last_ts
123af4d: cvtsi2ss %rsi,%xmm0
123af52: addss  0x8e0d10(%r15,%rcx,4),%xmm0   ; arr[state] += elapsed
123af5c: movss  %xmm0,0x8e0d10(%r15,%rcx,4)
123af66: mov    %rax,0x8e0d00(%r15)     ; last_ts = now
123af6d: movl   $0x1,0x8e0d08(%r15)     ; state = 1
```

**语义**（由代码结构确定，不是猜的）：每次累加归属的是"自上次累加以来所处的那一个状态"。
所以 `arr[1]` = 处于 1 的总时长，`arr[2]` = 处于 2 的总时长，二者应覆盖整条时间线。

## 3. 单位标定（这一步不能省）

一开始看到 `last_ts ≈ 3.27e9`、`arr[1] ≈ 3.9e7`，直接猜单位会错。用**驱动自己的时钟**做标定：

```
Δlast_ts / 墙钟  :
  run1 ctx0 = 10,062,404 / 9,999,265 µs = 1.0063
  run1 ctx1 = 10,055,121 / 9,999,265 µs = 1.0056
  run2 ctx0 = 10,010,502 / 9,999,422 µs = 1.0011
  run2 ctx1 =  9,985,159 / 9,999,422 µs = 0.9986
                → 1 单位 = 1 µs（0.1~0.6% 是采样边界效应）
```

`last_ts` 只在累加点推进，但**累加区间首尾相接、覆盖整条时间线**，所以 10s 内的总推进量就是 10s 的驱动时钟。
再交叉验证：`arr[1]` 的增量与 `Δlast_ts` 在 **359 对**样本上逐对相等（同一指令序列里同源写入）→ 同单位。

> **方法论**：读陌生的时间戳字段时，**不要用量级猜单位**。找"该字段在 10s 内推进了多少"，
> 与墙钟一比，单位就自证了。本例若猜 ns，会把 28ms 读成 28µs，整个结论反向。

## 4. 实测结果（两次独立运行）

### run1（`n6c`）

| | ctx0 `0x7f7b38000d40` | ctx1 `0x7f7b6811e040` |
|---|---|---|
| 单位标定 | 1.0063 → µs ✅ | 1.0056 → µs ✅ |
| state 分布 | 1: 4336, 2: 381 | 1: 4208, 2: 491, **3: 18** |
| 进入 state=1 | 328 次/10s = **32.8/s = 0.95 次/帧** | 348 次/10s = 34.8/s |
| `arr[1]` Δ | **9,253,676 µs（92.5% 墙钟）** | 1 µs |
| `arr[2]` Δ | 808,739 µs（8.1%） | −30 µs |
| **arr[1]+arr[2]** | **100.6%** ✅ | −0.0% |
| **每次等待** | **28,212 µs = 28.21 ms** | 0（不累加） |
| `wcnt` | >0 占 4.13%，**8 段/10s，段长 45~55ms，取值到 2** | 3.54%，7 段，取值到 2 |

### run2（`n6d`）

| | ctx0 `0x7f3a1c000d40` | ctx1 `0x7f3a42f1e040` |
|---|---|---|
| 单位标定 | 1.0011 → µs ✅ | 0.9986 → µs ✅ |
| 进入 state=1 | 388 次/10s = **38.8/s = 1.12 次/帧** | 387 次/10s |
| `arr[1]` 占墙钟 | **90.3%** | ~0 |
| `arr[2]` 占墙钟 | 9.8% | ~0 |
| **arr[1]+arr[2]** | **100.1%** ✅ | — |
| **每次等待** | **23,277 µs = 23.28 ms** | 0 |
| `wcnt` | **全程 0** | 全程 0 |

**⚠️ 两次运行差 20%（28.2 vs 23.3 ms），进入率也差 18%（32.8 vs 38.8/s）。**
→ **单次数值不是锚点**；能站住的是**占空比 90~93%** 与**arr[1]+arr[2] 闭合到 100%**。
这与仓库的铁律一致：跨运行比较只能用稳定量，不能用单次中位。

## 5. ★ 这一条推翻了 34 的一个推断

报告 34 §2 的核心推断链是：

> pathC（`123b322: addl $0x1,0x8e0d24`）**0 次命中** → `wait_ms` 从不返回 0 → 每次都是被 signal 唤醒、从不超时。

**直接读内存看到的不是这样**：run1 里 `wcnt` 取值 **0 → 1 → 2**，10 秒内出现 8 段非零（每段 45~55ms，
段内 `state` 恒为 1）。而 `wcnt` **全库只有 3 个写点**：两处清 0（`123ad47`、`12373d4`）、
**一处 +1（`123b322`）**。所以 `123b322` **确实执行过**。

| 34 的说法 | 实测 | 处理 |
|---|---|---|
| pathC 恒 0 | run1 明确递增到 2；run2 全程 0 | **改成"间歇执行"**：不是结构性的"从不"，而是"有时" |
| `wait_ms` 从不返回 0 | 至少 run1 期间返回过 0 | **推断作废**，返回值语义仍未定（见 §7） |
| 升级门（`>$0x14`=20）从不触发 | `wcnt` 峰值只到 **2** | **这条仍然成立**，但理由换了：不是"从不递增"，而是"递增次数太少（最多 2）" |

> **这是第二次踩"探针 0 命中"的坑**（SKILL 里"uprobe fetch 失败时静默"那一行就是这么来的）。
> 教训升级为：**"0 命中"这种阴性结果，必须有一条不依赖探针的旁路（本例：直接读内存）来复核**，
> 否则不能排除"探针根本没挂上"。而旁路往往比探针更便宜——这次就是。

## 6. 这个 23~28ms 在等什么（与既有结论对齐）

把三个独立来源放一起：

| 来源 | 数值 | 说明 |
|---|---|---|
| 驱动自记（本报告） | **23.3 / 28.2 ms 每次**，占墙钟 **90~93%** | 驱动自己算的 |
| uprobe（报告 34 §2.2） | tid 9524 长等待中位 **27.8 ms**（每帧 1 次） | 指令级 |
| uprobe（报告 34 §2.1） | map 窗口内覆盖 **101.4%**（裁剪后求和） | 窗口内重叠量 |

**三者相容**：一次真实 28ms 的等待把 3ms 的 map 窗口整段盖住 → 窗口覆盖率 100% 上下；
而"每帧 3 次 wait"是**窗口内相交的次数**（含另一线程的短等待），不是"每帧只有 3 次等待"。

再对齐功耗：报告 31 说 525 在 Heaven 下只有 48~68W ≈ 空转。
**驱动自记的 90% 等待占空比给出了这个"空转"的机制解释**：队列上下文绝大部分时间没有活干，
不是算得慢，是没人喂它。

> 与 34 §3 的解释一致，但更强的表述是：**"525 慢"的本质不是"多花了一次等待"，而是"这条流水线的生产者每帧只喂一次、消费者等满一帧"。**

## 7. 没定的事（诚实边界）

| 项 | 状态 |
|---|---|
| `wait_ms` 返回值语义（pathC 何时执行） | **未定**。run1 有、run2 无 → 与某些帧段的条件有关 |
| 两个 ctx 的角色映射（谁对应 tid 9524 / 9506） | 未做。断点抓到 2 个 ctx，但没同时抓 tid |
| ctx1 为何完全不累加（却也有 state 1/2/3） | 未解。它设了 state 但从不走累加点，说明它走的是另一条控制流（`1237xxx`） |
| `state=3` 的含义 | 未查（`1237c2d`，另一个函数） |
| 90% 的等待是"等上游喂活"还是"等完成通知" | 未区分。这是**下一步最该回答的**：要看这次等待期间队列是否真的空 |

## 8. 对 N3（换 515）的意义：成本大幅下降

因为 **515 的自记时字段布局与 525 完全相同**（只差基址 `0x55f080` vs `0x8e0d00`），
**N3 不再需要挂 pathA/pathB 全套探针**，同一套 `/proc/mem` 方法直接可用：

- 脚本已写好：`analysis/probes/n3_515_selfclock.sh`（自动识别 515/525、自动选 `base_off`、自动选断点）
- ctx 来源：515 的 ctx 在 `%r13`，断点选**稀有边** `0xc81e6e`（"notify 后仍空 → 续接"，约 1 次/帧），
  **不要**在热点 `0xc81c6b` 下断（几十万次/秒）
- 判读表：

| 515 实测 | 结论 |
|---|---|
| `arr[1]` 占墙钟 **≪ 90%**（例如 <20%） | 515 确实不等 → **坐实"515 靠轮询即时发现完成"**，34/35 的分叉结论闭环 |
| `arr[1]` 也 ~90%、每次也 ~28ms | 分叉点不在"等"，需回头查 ctx 归属或改看 `arr[2]` 的构成 |
| ctx 抓不到 | 515 的处理器可能走另一条入口，改用 `c81e61`/`c81d56` 作断点 |

**换驱动的必要性判断**：N6 已把"525 侧"锁死（驱动自报 90% 等待）。
N3 要回答的是"515 侧是否不同"——**这是唯一还需要换驱动才能回答的问题**，
而且现在只需 ~15min 装驱动 + 1 条命令。

**踩到的两个环境坑**（已写进脚本注释）：

1. **NFS 上 root 被 squash 成 nobody**：`sudo` 的 python 无法直接写 `/data`（`PermissionError`），
   必须先写本机 `/tmp` 再以普通用户搬回。
2. **`sudo python3` 的密码提示会混进 stdout**：用 `printf "desktop\n" | sudo -S` 时，
   提示串会打到网络连接输出里，看起来像脚本输出的一部分；真正的错误在它后面。
