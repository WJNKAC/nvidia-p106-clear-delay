# 22 · 525 复测判决：vsync 开关失效 + swap 内固定阻塞 23.7ms（primus）/ 极端抽搐（dmabuf）

> # ⚠️ 两处表述已被报告 23 修正（2026-10-25 15:35）
> **① "1ms 定时轮询驱动重查" → 错。** 在 wait 调用点下断点实测 **2456 次命中，超时参数全部是 100ms**（`esi=100`）。
> worker 是被 **cond_signal 正常唤醒**的，超时 100ms 从未到期。本文 §6.2/§8 的"轮询圈数 27 圈"叙事**作废**，
> 正确的问题是：**谁该 signal、它为什么晚 16ms**（见报告 23 §0）。
>
> **② "唤醒者是驱动内部的 1ms 轮询线程" → 归错了层。** 稳态的 1ms `clock_nanosleep` 来自
> **Mesa 的 `loader_dri3_swap_buffers_msc`**（libgallium）；glcore 的 `sleep_ms(1)` 只在启动校准期间用。
>
> **仍然有效**：§2 的全部实测数字（vsync 开关失效、swap 段 23.68ms、99.8% 睡眠、CPU 渲染 4.9ms、功耗 58W、
> dmabuf p95/中位 13.9、1.48 次 swap/显示帧）、§1 的三个仪器修复、§7 的 T5 否定结论（present barrier 出局）。
>
> 2026-10-25 15:05
> 目的：按报告 21 §4.1 的判据，用**关 vsync 下的 fps**判决 525 是否有性能回归。
> 方法：515 与 525 同一脚本、同一探头、同一稳态门（GPU util 连续 5 次 ≥50%）、各跑 2 轮。
> **结论（五条）：**
> 1. **525 的 vsync 开关完全失效**：vsync_on 34.6fps / vsync_off 34.7fps（差 0.3%）。515 同开关由 60.1 → 108.7（+81%）。
> 2. **525 在 swap 内部固定阻塞 23.7ms**（515 关 vsync 时仅 1.22ms，**19 倍**），其中 99.8% 是睡眠，且**CPU 渲染反而更少**（4.9 vs 7.4ms）、**功耗只有一半**（~58W vs 116W）。
> 3. **525 的 dmabuf 路径是另一种坏**：中位帧间隔 2.64ms、p95 36.82ms（**p95/中位 = 13.9**），并出现**成对 swap**（1.48 次/显示帧）。515 同路径为 16.61/18.05（1.09）。
> 4. **机制已抓到**（§6/§8）：那 23.7ms 是**主线程等同一个 futex**（无限等待，非 poll/非 DRM 事件），处于"查条件→不满足→再睡"循环（**每帧 2.2 次唤醒**），由**驱动内部的 1ms 定时轮询线程**驱动；525 比 515 多转约 16 圈 ≈ **一个 vblank**。
> 5. **present barrier 假说被否定**（§7）：barrier 管理函数 `0x17c4e40` 与 `waitingAtBarrier` 日志函数 `0x18fb390` 每帧调用 **0 次**，而同一份 trace 里阳性对照 drain 被调 62.8 万次（1859/帧）——**探针有效，0 是真实的**。

## 1. 方法与可重复性

### 1.1 本次修正的三个仪器问题

| 问题 | 后果 | 修法 |
|---|---|---|
| **预热用固定 `sleep 22`** | 525 首次启动需编译全部 shader（新驱动缓存失效），22s 后 GPU 仍 0%/P8，采集窗口落在 LOADING 期（第一份数据已标 `VOID_`） | 改为**稳态门**：等 GPU util 连续 5 次（10s）≥50% 才开始采集；未达成则中止 |
| **`libGLX_nvidia` 的 `glXSwapBuffers` 偏移硬编码 0x76a50** | 该偏移是 515 的；525 是 **0x738f0**，导致 dmabuf 探针 0 次命中 | 按版本登记 `GLXSWP`（515=0x76a50 / 525=0x738f0） |
| **`swap_busy` 用「median(B) − median(sleep)」** | 两个中位数配对不一致时会出现 `sleep > swap 段` 的荒谬值 | 改为**逐帧**算 `max(0, B−sleep)` 再取中位 |

### 1.2 可重复性

| 配置 | 轮次 | fps | 帧间隔中位 | swap 段 |
|---|---|---|---|---|
| 525 primus vsync_off | r1 | 34.7 | 29.38 | 23.68 |
| 525 primus vsync_off | r2 | 34.7 | 29.32 | 24.63 |
| 525 dmabuf vsync_on | r1 | 82.4 | 2.64 | 14.16 |

## 2. 主对照表（515 vs 525，同一脚本同一探头）

### 2.1 primus 路径 · vsync 开关 2×2

| | **515** | **525** |
|---|---|---|
| **vsync ON** fps | 60.1 | **34.6** |
| vsync ON 帧间隔 | 16.64 ms | **29.37 ms** |
| vsync ON swap 段 | 10.90 ms | **23.83 ms** |
| **vsync OFF** fps | **108.7** | **34.7** |
| vsync OFF 帧间隔 | 8.91 ms | **29.38 ms** |
| vsync OFF swap 段 | **1.22 ms** | **23.68 ms** |
| **开关效果（off/on）** | **+81%** | **+0.3%（无效）** |

**515 关 vsync 帧率翻倍；525 关 vsync 毫无变化。** 这是本轮最硬的一条。

### 2.2 那 23.7ms 是什么

525 primus vsync_off 的分解（vsync 已经关了，所以不可能是"等 vsync"）：

| 项 | 值 |
|---|---|
| swap 段 | **23.68 ms** |
| 其中主线程睡眠 | **23.63 ms（99.8%）** |
| 其中主线程 CPU 忙 | 0.06 ms |
| 帧内其余 CPU 忙（渲染） | **4.90 ms** |
| 帧内其余睡眠 | 0.13 ms |
| GPU 功耗 | ~58 W（515 同条件 116 W） |

**它在等，不是在算。** 而且渲染部分的 CPU 时间比 515 更少（4.9 vs 7.4ms），功耗只有一半。

### 2.3 等待的结构：vblank 之后又等将近一整拍

525 primus（vsync_on 与 off 数值几乎相同，以 off 为例）：

```
vblank 落在 swap 内部的帧:  518/520 (99.6%)
pre  (swap_in → vblank):   中位  8.70 ms
post (vblank → swap_out):  中位 15.24 ms   ← post/period = 0.91
(pre+post) / period      = 1.44
```

**vblank 之后还要等 15.24ms ≈ 0.91 个 vblank 周期才返回。**

帧间隔 / period 的分布（三峰）：

| 比值 | 占比 |
|---|---|
| 1.50× | **39.9%** |
| 1.75× | 28.9% |
| 2.00× | 29.5% |
| 平均 | **1.736 拍/帧** |

**这不是"每帧精确等 2 拍"，而是"1.5 / 1.75 / 2.0 拍三峰混合"，平均 1.74 拍。**

### 2.4 dmabuf 路径：另一种坏法

| | **515** | **525** |
|---|---|---|
| fps（按 swap 计数） | 60.0 | **82.4** |
| 帧间隔中位 | 16.61 ms | **2.64 ms** |
| 帧间隔 p95 | 18.05 ms | **36.82 ms** |
| **p95 / 中位** | **1.09** | **13.9** |
| swap 次数 / vblank 数 | 900 / 900 = **1.00** | 1237 / 837 = **1.48** |
| 每帧 vblank 数 | 1.001 | **0.728** |
| GPU 功耗 | ~60 W | ~58 W |

**525 的 dmabuf 是"狂飙 + 抽搐"**：中位 2.64ms（相当于 378fps 的潜力），但 p95 36.82ms。
帧间隔/period 分布：`0.00×` 占 **40.4%**（连续两次 swap 几乎同时），`1.00×` 仅 16.7%，`2.0×` 以上占 14%。

原始时序里能看到**成对的 swap**：

```
SWP_IN 17.024 → SWP_IN 17.824   (间隔 0.8ms)
      ...       VBLANK 30.429
SWP_OUT 31.351 → SWP_OUT 31.413  (间隔 0.062ms)
```

两个 swap 调用一起阻塞，在同一 vblank 后一起返回。**这正是"抽搐"的微观形态**：多个 swap 挤在一起完成，然后突然空闲。
（515 同路径是 900 swap / 900 vblank = 严格 1:1，无成对现象。）

> **诚实标注**：`0x738f0` 是 `nm -D` 给出的 `glXSwapBuffers` 入口（T 符号），但 525 下调用次数比显示帧多 48%。
> 可能是（a）应用/引擎在低帧率下真的多调了；（b）该入口被多条 present 路径共用，某条被走了两次；（c）Xwayland 侧的重复提交。
> **本装置无法区分这三者**，需要栈回溯（uprobe + `$stack`）才能定。这是 T3b 的遗留问题。

## 4. 与 present barrier 假说的吻合

报告 18 发现 525 独有 present barrier 全套模块（515 一条都没有）。现在它成了最自然的解释：

| 观测 | present barrier 预测 | 是否吻合 |
|---|---|---|
| vsync 开关无效 | barrier 是 **buffer 生命周期**语义，与 vsync 无关 | ✔ |
| 等 1.5~2 拍（三峰） | 等"前一 buffer 显示完"，受相位漂移影响，落在 1.5~2 拍之间 | ✔ |
| vblank 之后又等 0.91 拍 | barrier 信号在 vblank 处理链的**后段**发出 | ✔ |
| CPU 渲染不增、功耗减半 | 纯等待，不消耗算力 | ✔ |
| dmabuf 路径表现不同（抽搐而非稳定慢） | barrier 在直渲路径上参与方式不同（无 readback，barrier 更快触发但节拍不稳） | ◐ 待验 |

**这从"猜测"升级为"目前唯一自洽的解释"，但仍是关联而非因果**——需要 T5 验证（见 §6）。

## 6. 机制层补充：那 23.7ms 是一次 futex 等待 + 驱动内部 1ms 轮询（strace 新发现）

§2 只证明了"在等"。本节用 strace 抓到**等的是什么**，这是本轮最有机制价值的一段。

### 6.1 主线程：每帧一次 futex，等同一个锁 27.4ms

`strace -p <主线程> -e trace=futex -v -T`，6 秒：

```
7124 次 futex，最长 27.4ms，且所有 >10ms 的调用都是同一个 uaddr：

futex(0x191181d8, FUTEX_WAIT_BITSET_PRIVATE|FUTEX_CLOCK_REALTIME, 0, NULL, FUTEX_BITSET_MATCH_ANY) = 0 <0.027412>
```

- **`FUTEX_WAIT_BITSET_PRIVATE` + `timeout=NULL`** → 无限等待，纯进程内线程同步
- **同一个 uaddr，260 次 >10ms** → 每帧等的是**同一个锁**
- 该地址在**堆**上（不属于任何 .so 映射，且每次运行地址不同——ASLR，所以不能硬编码）

**这一条直接排除了"等 vblank"和"等 DRM 事件"**：那两种都该是 `poll`/`ioctl`/`clock_nanosleep`，而不是 futex。
poll 在主线程上**没有任何 >1ms 的调用**。

### 6.2 谁在唤醒它：两个 1ms / 10ms 定时轮询线程

同一份 strace 的线程分布：

| 线程 | syscall 构成 | 说明 |
|---|---|---|
| **7447** | **6948 次 `clock_nanosleep(CLOCK_REALTIME, {tv_nsec=1000000})`** | **1ms 定时轮询，约 1158 次/秒** |
| 7446 | 1549 次 `clock_nanosleep({tv_nsec=10000000})` | 10ms 定时轮询，约 258 次/秒 |
| 7424 | 36767 次 futex（最长 0.13s） | 驱动 worker，被反复唤醒 |

**主线程等的那个 futex，是被这些定时轮询线程唤醒的。**

### 6.3 定量关系：525 比 515 多等了约一个 vblank

```
525 主线程单次 futex 等待 ≈ 27.4 ms ÷ 1 ms 轮询周期 ≈ 27 次轮询
515 同路径 swap 内睡眠   ≈ 10.8 ms ÷ 1 ms ≈ 11 次轮询
```

差值 ≈ **16 次轮询 ≈ 16.7ms ≈ 一个 vblank 周期**。

这与 §2.3 从 ftrace 得到的独立结果（`post/period = 0.91`、`(pre+post)/period = 1.44`）**互相印证**：
**525 的完成判定比 515 晚了一个 vblank。**

### 6.4 完整机制图景（关联，非因果）

```
应用 glXSwapBuffers
   ↓
主线程提交 → futex_wait(同一个锁, 无超时)          ← 99.8% 的时间在这里
   ↓
驱动 worker 线程 + 1ms 定时轮询线程
   ↓
轮询判定"完成" —— 525 比 515 晚约 1 个 vblank 才判定
   ↓
唤醒主线程 → swap 返回
```

- **vsync 开关为何无效**：这个等待发生在**驱动内部的完成判定**上，在应用 vsync 语义之下。`vblank_mode=0` 只影响应用层要不要等 vblank，改不了驱动的完成判定。
- **为何 CPU 渲染更少、功耗只有一半**：主线程大部分时间在 futex 睡，GPU 没有新命令可执行。
- **为何与像素量无关**（报告 21）：轮询次数由节拍决定，不由数据量决定。

> **仍未回答**：525 为什么把"完成判定"推迟一个 vblank。**present barrier 假说已被 T5 否定**（见 §7）。

## 7. T5 结果：present barrier 假说被否定（阳性对照有效）

### 7.1 探针与计数

在 525 上（vsync_off，稳态后 10s）挂 4 个 uprobe，只挂 entry 以最小化开销：

| 探针 | 目标 | 次数 | 每帧 |
|---|---|---|---|
| `swpib` | primus `glXSwapBuffers` | 338 | 1.000（基线） |
| **`pbar`** | barrier 管理函数 `0x17c4e40` | **0** | **0.000** |
| **`plog`** | `waitingAtBarrier` 日志格式化 `0x18fb390` | **0** | **0.000** |
| `drio` | **drain `0x1577a90`（阳性对照）** | **628,498** | **1859.5** |

### 7.2 结论

**阳性对照每帧被调用 1859 次，证明探针机制完全有效。**
因此在同一份 trace、同一时刻，barrier 相关函数的 0 次是**真实为零**：

- **`0x17c4e40`（barrier 管理）不在每帧路径上**——报告 18 判定它是"配置期代码"是对的
- **`waitingAtBarrier` 日志从不触发**——说明 barrier 等待逻辑在本机根本没进入
- **present barrier 不是 23.7ms 等待的原因**

### 7.3 这个否定排除了什么

报告 18 发现 525 独有 present barrier 全套模块，一度是最自然的解释（vsync 无关、等 1.5~2 拍、不耗算力——都能对上）。
**现在它被排除**，意味着：

1. 那 23.7ms 的 futex 等待**不是 barrier 语义**
2. 525 独有的另一套模块 **QuadroSync**（帧锁/genlock）也没必要再查——本机单卡，明显不适用
3. 剩下的是**通用提交/完成路径**的差异，而非 525 新增的某个"功能"

### 7.4 一个需要标注的不确定项

本轮 drain 测得 **1859 次/帧**，而报告 20 在 15s 采集里测得 **90~186 次/帧**（差约 10~20 倍）。
两次的差异待查：可能是场景相位不同（相机轻重段）、vsync 模式不同（off vs on）、或 uprobe 密度不同（本次只有 4 个 entry 探针，上次有 p+r 共 5 个）。
**这不影响 §7.2 的结论**（barrier=0 与 drain=大量在同一份 trace 里同时成立，对照有效），但 drain 的绝对频次不要引用本节的数。

## 8. 机制补充二：主线程每帧在"检查—再睡"循环里（含一个观察者效应）

用 `sched:sched_wakeup` + `filter = pid == 主线程` + `stacktrace`，8 秒：

### 8.1 数字

| 项 | 值 |
|---|---|
| swap | 263 次（32.9/s） |
| 主线程被唤醒 | **847 次（105.9/s）= 3.2 次/帧** |
| 每帧唤醒次数 | 中位 **3 次**，83.6% 的帧正好 3 次 |
| 唤醒间隔分布 | `<1ms` 占 63.8%，**`>12ms` 占 31.0%** |

### 8.2 必须扣除的观察者效应（重要）

栈统计里出现：

```
263  __uprobe_trace_func
263  uprobe_dispatcher
263  uprobe_notify_resume
263  asm_exc_int3
```

**263 正好等于 swap 次数。** uprobe 是用 `int3` 断点实现的，每次命中都会让线程进内核再返回——**它自己就在唤醒主线程**。

扣除后：真实唤醒 = 847 − 263 = **584 次 / 263 帧 ≈ 2.2 次/帧**。

> **方法论教训**：用 `sched_wakeup` 研究线程唤醒模式时，**不能同时挂高频 uprobe**。
> 本该用「无 uprobe 的对照组」或改用 `perf` 的独立探针。本轮数据仍可用，但必须做减法。

### 8.3 仍然成立的结论

扣除观察者效应后：

- **每帧 2.2 次唤醒** > 1 → **不是"睡一次被叫醒一次"，而是"检查完成条件 → 不满足 → 再睡"的循环**
- 间隔双峰：`>12ms` 的那一群（262 次 ≈ 每帧 1 次）对应 §6 那次 27ms 的 futex 等待结束；`<1ms` 的短群是循环里的重试
- 与 §6.2 的 **1ms 定时轮询线程** 完全吻合：轮询线程每 1ms 醒一次，若条件不满足则让主线程继续睡

**合并后的机制图景（更新 §6.4）：**

```
应用 glXSwapBuffers
   ↓
主线程: 检查完成条件 → 不满足 → futex_wait(无超时)      ← 99.8% 时间在这
   ↑                                          ↓
   └──── 1ms 轮询线程唤醒、重查 ────────────────┘
                （每帧约 2 次；525 比 515 多转约 16 圈 ≈ 1 个 vblank）
   ↓ 条件满足
swap 返回
```

这比报告 07 的"排空轮询"描述更精确：**轮询不是自旋，是 futex 睡眠 + 1ms 定时器驱动的重查**。
而且它解释了为什么 `__GL_YIELD=USLEEP` 在历史上"只降 CPU、不改帧率"——本来就在睡。
