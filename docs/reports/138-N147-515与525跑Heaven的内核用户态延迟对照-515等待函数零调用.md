# 报告 138 — 515 vs 525 跑 Heaven 的内核/用户态延迟对照（真机 A/B，同一台机器同一场景）

> 编号：138（对应 N147）
> 日期：2026-10-27
> 平台：P106-100 / 内核 6.1.0-50-amd64 / KDE Wayland + Xwayland `:0`
> 方法：整机切换驱动（525.116.03 ↔ 515.105.01），Heaven 4.0 OpenGL 1920×1080 窗口，
> 内核侧 bpftrace / perf，用户态 tracefs uprobe + perf probe
> 前置：报告 136（122 µs 定位）、137（n83a 上内核否证 + 垫片）

---

## 0. 一句话结论（三个数字）

1. **等待函数调用次数：525 = 216,278 次/10 秒（270 次/帧）；515 = 0 次/10 秒。**
   两版同一个函数、逐指令同构（`lea r13,[rax+0x14]` = 睡 20 µs），**515 在 Heaven 里根本不进它**。
2. **ioctl 总耗时：525 = 261.3 ms/10 秒（单次最大 3,959 µs）；515 = 25.8 ms/10 秒（单次最大 110 µs）。**
   525 有 **152 次** ioctl 落在 1~4 ms 区间，515 **一次都没有**。
3. **帧间隔分布：515 单峰（全部 8~32 ms，最长 23 ms，超 40 ms 的帧 = 0）；
   525 双峰（190/478 帧落在 32~64 ms，69 帧 > 40 ms，最长 106 ms）。**

**但功耗是反的**：515 是 65~78 W / utilization 64~75%，525 只有 50~57 W。
**515 干得更重却更顺；525 省电却卡。** 这与报告 134/136 的"525 在等、GPU 空转"完全一致。

**必须说清的一句**：**FPS 两版几乎一样（525 画面 61 / 515 画面 60）**。
差异不在平均帧率，而在**帧时间的稳定性**——525 的卡顿被"快帧"平均掉了。
这也说明：用"平均 FPS"评价这个问题会直接看走眼。

## 1. 环境与方法（为什么这次的数据可信）

### 1.1 切驱动流程

```
systemctl stop sddm → pkill Xorg → modprobe -r nvidia_drm nvidia_modeset nvidia
→ .run --silent --no-questions → systemctl start sddm
```
每次约 **1 分 8 秒**，5 次切换全部 `exit=0`。

### 1.2 测量条件（两版严格对齐）

| 项 | 值 |
|---|---|
| 程序 | `/home/<user>/hv/bin/heaven_x64`（不经启动器，启动器走 Mesa） |
| 参数 | `-video_app opengl -video_width 800 -video_height 450 -video_fullscreen 0 -video_vsync 0` |
| **实际渲染尺寸** | **1920×1080**（cfg 覆盖了命令行，`xwininfo` 实测窗口 1920x1080；屏幕 2560x1080，无缩放） |
| 环境 | `__GLX_VENDOR_LIBRARY_NAME=nvidia`、`__NV_PRIME_RENDER_OFFLOAD=1`、`vblank_mode=0` |
| 垫片 | **无**（`hrun.sh` 里 `unset LD_PRELOAD`，已用 `/proc/PID/maps` grep 复核 = 0） |
| 加载时间 | 525 = 10 s，515 = 10~13 s（相当） |

### 1.3 探针

| 目的 | 手段 | 注意 |
|---|---|---|
| 等待函数调用次数 | tracefs `uprobe_events` 裸地址 | bpftrace **不认裸偏移**（`Could not resolve address`） |
| ioctl 次数/耗时/内核栈 | bpftrace `kprobe/kretprobe:nvidia_ioctl` | 必须 `pid==$P` 过滤 |
| 睡眠判定 | `schedule_timeout` / `msleep` / `sched_switch` 的 `prev_state` | 见报告 137 §56.1 |
| 帧间隔分布 | `uprobe:glXSwapBuffers` 记 `nsecs` 差 | 两条探针挂同一入口会得到 0，必须用 `@last` 变量 |
| 自旋次数（515） | **perf probe**（因 tracefs 被悬空事件堵死） | 见 §5.2 |

## 2. 用户态：等待函数次数 —— 本轮最硬的差异

| | 525.116.03 | 515.105.01 |
|---|---|---|
| 函数地址 | `0x15761b0` | `0xfbcc30` |
| 结构 | `lea r12,[rax+0x14]` → 9×`pause` → 再取时钟 → `cmp/jge` | **逐指令同构** |
| 超时 | 20 µs | 20 µs |
| **10 秒调用次数** | **216,278** | **0** |
| **每帧** | **270 次** | **0** |
| 若按 17.6 µs/次折算 | **≈ 3.8 s / 10 s（38% 墙钟）** | 0 |

**验证探针有效（阳性对照）**：同一窗口内 `glXSwapBuffers` 计数 515 = **601 次/10 s**（= 60 fps），
525 = **801 次/10 s**（= 80 fps）。所以"515 = 0"不是探针没挂上，是**真的没调用**。

> ⚠️ 我在中途有一次数据是错的：`spf.sh` 用 `trace_pipe` 按帧切分，得到"737 帧里 736 帧自旋 0 次、
> 1 帧 220 万次"——那是**多线程下 `trace_pipe` 交错**导致的错误配对。
> 采用的信源是"单探针整窗计数 ÷ 交换次数"，不依赖逐帧配对。

## 3. 内核侧：ioctl 次数与耗时

| 指标 | 525 | 515 | 倍率 |
|---|---|---|---|
| ioctl 次数 / 10 s | 1,328 | 638 | 2.1× |
| **ioctl 总耗时 / 10 s** | **261.3 ms** | **25.8 ms** | **10.1×** |
| **单次最大** | **3,959 µs** | **110 µs** | **36×** |
| ISR（`nvidia_isr` 返回） | 20 | 23 | 相当 |
| `schedule_timeout` | 1 | 0 | 都是 0 量级 |
| `msleep` | 0 | 0 | — |

### 3.1 耗时直方图（µs）

**525**
```
[8,16)     185
[16,32)    217
[32,64)    413
[64,128)   326
[128,256)   22
[512,1K)     1
[1K,2K)    143  ← 慢调用
[2K,4K)      9  ← 慢调用
```
**515**
```
[16,32)      2
[32,64)    589
[64,128)    16
（之外全空）
```

**525 的 152 次 1~4 ms 的 ioctl 吃掉了 261 ms 里的约 240 ms（92%）。**
515 的最大值 110 µs，**整条尾巴是空的**。

> 这 152 次慢 ioctl 在 n83a 上没出现过（n83a M3 单次最大 610 µs）。
> 推测与 Heaven 特有的资源操作（大纹理/着色器/FBO 建立）有关，本轮**未拆解**，标记为待查。

### 3.2 `sched_switch` 的 `prev_state`

| | 525 | 515 |
|---|---|---|
| `prev_state=0`（TASK_RUNNING，让出） | 387 | 71 |
| `prev_state=1`（真睡眠等资源） | 2,565 | 2,476 |

两版都在正常睡眠（等垂直同步/等 GPU 完成/等锁），**数量级相同**。
⇒ **内核不是差异来源**（与报告 137 在 n83a 上的结论一致）。

## 4. 帧时间稳定性 —— 用户感知到的"卡"

`uprobe:glXSwapBuffers` 记录相邻两次交换的时间差，10 秒窗口。

**525（478 帧）**
```
[0]        33
[1]        42
[2,4)      65
[4,8)      83
[8,16)     22
[16,32)    34
[32,64)   190  ← 40% 的帧
[64,128)    8
最长 106 ms；> 40 ms 的帧 = 69 个（14%）
```
**515（598 帧）**
```
[8,16)    123
[16,32)   474
最长 23 ms；> 40 ms 的帧 = 0 个
```

**525 是双峰**：一半帧 4~8 ms，一半帧 32~64 ms。**平均下来仍是 60 fps 上下，所以平均 FPS 看不出问题，
但人眼看到的是"一顿一顿"。** 这就是用户说的"十分抽搐"。

> 需要诚实标注：帧间隔 32~64 ms 这类长帧**不可能**由"每帧 270 次 × 17.6 µs ≈ 5.4 ms"单独解释。
> 更可能是：自旋把 CPU 占住 → 驱动/引擎的另一个线程（如资源流式加载那 152 次慢 ioctl）被推迟，
> 落在某些帧上形成尖峰。**这条因果链本轮未证实**，下面 §6 给了验证方案。

## 5. 功耗与占用：515 干得更重却更顺

| | 525 | 515 |
|---|---|---|
| 功耗（W） | 49.95 ~ 56.86 | **65.10 ~ 77.84** |
| `utilization.gpu` | 未采（P106 上该指标不可靠，见 STATUS） | **64 ~ 75%** |
| FPS（画面数字 / swap 计数） | 61 / 80.1 | 60 / 60.1 |

**525 更省电、帧率不低，但卡；515 更费电、帧率一样，但顺。**
这与报告 136 里 n83a 的结论同源：**525 的时间花在"等"，不是在"算"**。
Heaven 上这个差距没有 n83a 那么夸张（n83a 是 127 ms vs 5 ms），因为 Heaven 的"绑定→draw"密度低得多
（n83a 每帧 1000 对，Heaven 每帧 270 次等待）。

## 6. 与 n83a 的定量衔接（把两个场景放进同一个模型）

| 场景 | 每帧等待函数次数 | 每帧代价（按 17.6 µs） | 帧时间 |
|---|---|---|---|
| n83a M3 | 7,211 | 127 ms | 127 ms（**几乎 100%**） |
| **Heaven 525** | **270** | **4.8 ms** | 12.5~16 ms（约 30~38%） |
| Heaven 515 | **0** | 0 | 12~16 ms |
| n83a M1（无绑定） | 0（不进） | 0 | 7 ms |

**这个模型在同一张卡、两个完全不同的负载上自洽**：
等待函数次数 ∝ "绑定→draw"的对数，代价 ∝ 次数 × 17.6 µs。

**推论（对垫片的直接影响）**：Heaven 每帧只有 270 次转换，即使 dedupe 能吞掉一半，
也只能省 2.4 ms/帧 —— **远不如 n83a M6 那种 18 倍**。
所以在 Heaven 上，垫片的期望收益要按"270 × 冗余率 × 17.6 µs"重算，不要沿用 n83a 的数字。

## 7. 尚未解释的部分（不做过度归因）

| 现象 | 已有解释 | 缺口 |
|---|---|---|
| 525 帧间隔 32~64 ms 的双峰 | 自旋占 CPU（38% 墙钟）+ 慢 ioctl 尖峰 | **哪一类长帧由哪个原因主导，未拆开** |
| 525 那 152 次 1~4 ms 的 ioctl | 未知 | 需按 ioctl 的 `cmd` 号分类（bpftrace 读 `arg1`） |
| 515 为什么完全不进等待函数 | 未知（两版函数同构、阈值同构） | 这是**唯一真正的根因问题**，见下 |

### 下一步（按优先级）

1. **拆那 152 次慢 ioctl**：`kprobe:nvidia_ioctl { @cmd[arg1] = count(); }`，
   配合 `kretprobe` 的耗时，找出是哪个 ioctl 号在 525 上变慢。这是本轮新出现的、n83a 上没见过的信号。
2. **验证长帧归因**：在同一窗口内同时记录"每帧自旋次数"与"帧间隔"，
   用 perf probe 的 per-event 计数（避免 §2 提到的 `trace_pipe` 交错问题），做散点而非直方图。
3. **根因问题不变**：为什么 525 每次"绑定→draw"后要等，515 不等。
   现在多了一个抓手——**515 在 Heaven 里等待函数 0 次**，说明它在真机上确实走了另一条路径，
   不是"进得少"，而是"根本不进"。这比 n83a 的"525 = 108 次/对 vs 515 = 3.84 次/对"更极端、更利于定位。

## 8. 本轮操作记录（代价与教训）

### 8.1 切了 5 次驱动，桌面中断 5 次

| 次序 | 目的 | 结果 |
|---|---|---|
| 1 | 525 → 515 | 成功（1m07s） |
| 2 | 515 → 525 | 成功（1m10s） |
| 3 | 525 → 515 | 成功（1m08s） |
| 4 | 515 → 525 | 成功（1m14s） |
| 5 | 525 → 515 → 525 | 成功（1m15s） |

**为什么比预期多**：第一次采 515 时，`tracefs` 的 uprobe 被 525 时代的**悬空事件**堵死
（事件绑定的是已被删除的 `.so` 的 inode，`uprobe_events` 写入报 `Device or resource busy`），
自旋计数没拿到，只能再切一次用 perf probe 补。
**教训**：**切驱动前必须先 `echo > uprobe_events` 清空**，否则跨版本必踩。

### 8.2 环境状态在切换后变了（脚本必须自适应）

| 项 | 切换前 | 切换后 |
|---|---|---|
| X display | `:1` | **`:0`**（Xwayland 重新分配） |
| xauth 文件 | `xauth_xxx` | **每次重启都变**（`xauth_yZanwE` / `xauth_GgTEAg`…） |
| 一次异常 | — | sddm 起了 Wayland 会话但 **Xorg 进程为 0**，需 `systemctl restart sddm` |

脚本改为：从 `pgrep -a Xwayland` 解析 `:N` 与 `-auth` 路径，不再硬编码。

### 8.3 截图

Xwayland 下 `import -window root` 报 `BadMatch`，`xwd` 输出 0 字节。
可用做法：**`import -window <具体窗口 id>`**（非 root），再用 `convert -crop` 裁右上角读 FPS 数字。

## 9. 复现命令

```bash
# 切驱动（每次约 1 分钟，会中断桌面）
echo <user> | sudo -S /home/<user>/inst-drv.sh 515.105.01
# ⚠ 切之前务必先清空：echo <user> | sudo -S sh -c 'echo > /sys/kernel/debug/tracing/uprobe_events'

# 起 Heaven（无垫片）
/home/<user>/hrun.sh <tag> 800 450        # 等到功耗 >40W 才算进入渲染

# 采集（内核 + 用户态）
echo <user> | sudo -S /home/<user>/htrace.sh 10 0x15761b0 525-heaven   # 525 用 0x15761b0
echo <user> | sudo -S /home/<user>/htrace.sh 10 0xfbcc30  515-heaven   # 515 用 0xfbcc30

# 帧间隔分布
bpftrace -e 'uprobe:<libGLX_nvidia>:glXSwapBuffers /pid==$P/ {
  if (@last) { @h = hist((nsecs-@last)/1000000); @max = max((nsecs-@last)/1000000); }
  @last = nsecs; @n++; } interval:s:10 { exit(); }'

# 若 tracefs 被堵：改用 perf probe
perf probe -x <libnvidia-glcore> 0x15761b0
perf stat -a -e probe_libnvidia:abs_15761b0 -- sleep 10
```
