## A 段：源码里查到的事实（可逐行核对）

### A1. guest 的 BAR0 不是"每次访问都陷入"，而是**映射宿主内存页**

`nv-vgpu-ioctl.h:488-511`：

```c
/* NV_VFIO_VGPU_ADD_MMIO_MAPPING
 * This command specifies the MMIO mapping information required for
 * removing host to guest BAR mapping.            ← 注意：host to guest BAR mapping
 * virtualMMIOStart [IN]   memory mapped address as seen by guest
 * physicalMMIOStart[IN]   corresponding memory mapped address as seen by host
 * mmioSize [IN]
 */
#define NV_VFIO_VGPU_ADD_MMIO_MAPPING     NV_VGPU_IOCTL(0x07)
#define NV_VFIO_VGPU_REMOVE_MMIO_MAPPING  NV_VGPU_IOCTL(0x08)

typedef struct {
    NvU64 virtualMMIOStart;    /* guest 眼中的地址 */
    NvU64 physicalMMIOStart;   /* 宿主眼中的地址 */
    NvU64 mmioSize;
} NV_VFIO_VGPU_MMIO_MAPPING_PARAMS;
```

实现 `nvidia-vgpu-vfio.c:4237`：

```c
ret = remap_pfn_range(vma, virtaddr, (host_addr >> PAGE_SHIFT), req_size, pg_prot);
```

**`remap_pfn_range` 把宿主物理页直接插进 guest 的 BAR0 VMA。**
⇒ **guest 对这块区域的读写是普通内存访问，不是 VM exit。**

### A2. 但只有 **≤5 个窗口**被映射，其余仍然要被 trap

`nv-vgpu-ioctl.h:124`：

```c
#define NV_VGPU_MAX_SPARSE_REGION_COUNT   5
```

`nvidia-vgpu-vfio.c:2330-2350`（校验逻辑）：

```c
if (index == VFIO_PCI_BAR0_REGION_INDEX) {
    for (i = 0; i < vgpu_dev->sparse_count; i++) {
        if (((host_addr - region_info[index].phys_start) == sparse_offsets[i]) &&
            (size == sparse_sizes[i])) {
            status = NV_OK;  goto bar1_map_exit;      /* 在窗口内 ⇒ 允许映射 */
        }
    }
    status = NV_ERR_INVALID_ADDRESS;                   /* 不在窗口 ⇒ 拒绝 */
}
```

`sparse_offsets/sizes` 由 vgpu-mgr 通过 `NV_VFIO_VGPU_BAR_INFO_SET_DATA` (0x17) 下发
（`nv-vgpu-ioctl.h:800-814`）。

**⇒ BAR0 是"稀疏映射"：** 少数热区（门铃/通知窗）直连宿主内存，
其余寄存器访问走 **`NV_VFIO_VGPU_REG_ACCESS_GET_DATA` (0x05) / `SET_DATA` (0x06)** 这条慢路径。

**这就是设计意图**：把每次提交必经的门铃做成直写，把冷寄存器留成 trap。

### A3. guest 的 pushbuffer 不拷贝 —— 宿主拿到 **GFN→PFN 翻译**

`vgpu-devices.c:575-620`（`nv_vfio_vgpu_pin_pages`）：

```c
status = nv_vgpu_copy_from_user(pgpfn_buffer, pParams->pGuestPfnMem, size);
status = nv_vgpu_translate_gfn_to_pfn(pgpfn_buffer, phpfn_buffer,
                                      pParams->pageCount, vgpu_dev, pParams->addrType);
status = nv_vgpu_copy_to_user(pParams->pHostPfnMem, phpfn_buffer, size);
```

**`translate_gfn_to_pfn`：把 guest 物理页号翻译成宿主物理页号，交给 vgpu-mgr。**

⇒ **宿主 RM 拿着 guest 内存的 PFN，可以直接读命令流，不需要每帧拷贝，也不需要每次访问陷入。**

### A4. 完成中断走 KVM irqfd，由宿主注入

`nvidia-vgpu-vfio.c:3252`（`nv_vgpu_inject_interrupt`）：

```c
struct eventfd_ctx *trigger;
...
if (vgpu_dev->intr_info.index == VFIO_PCI_MSI_IRQ_INDEX)
    trigger = vgpu_dev->intr_info.msi_trigger;
else
    trigger = vgpu_dev->intr_info.intx_trigger;
/* … eventfd_signal(trigger, …) */
```

⇒ 宿主 vgpu-mgr 用 **eventfd → irqfd** 给 guest 注入 MSI。
**中断的时机由宿主决定**，不是由物理引擎决定。

### A5. 一张图（全部来自上面的源码）

```
【guest 内】
  app → nvidia 驱动 → 写 pushbuffer 到 guest 内存
                    → 写门铃（落在【被 mmap 的宿主内存页】，普通 store，不 trap）
                              │
                              ▼
【宿主】  vgpu-mgr 看到门铃（轮询/事件）
          ├─ 用 A3 的 PFN 直接读 guest 的 pushbuffer（零拷贝）
          ├─ 用 A1 的映射读写 BAR 窗口
          └─ 用 A4 的 irqfd 决定何时告诉 guest "这批完成了"
                              │
                              ▼
                        物理 GPU（真 P106）
```

## B 段：为什么"没有性能回退" —— 推断，附否证条件

### B1. 真机上那 118.5µs 是"驱动在等物理引擎"

已实测（报告 105，`n83a`，pbuffer 不经过 present）：

```
M1（零状态变更）= 3.316 ms   ← 纯渲染+回读
M3（切 program+draw）= 15.170 ms
⇒ 每对 118.5 µs，GPU 侧 ≈231k 周期 @1911MHz
Heaven 268 对/帧 × 118.5µs = 31.8ms + 3.3ms = 35.1ms ⇒ 28.5fps ≈ 实测 29-30
```

**关键点：这 118.5µs 与几何、像素、变更数都无关**（报告 78 已证）。它是**每批一次的固定代价**。
报告 77 把它的落点定在"统一提交器 → 引擎重新 arming"。

**⇒ 真机的 30fps 不是"算得慢"，是"驱动在等引擎 arming"。**

### B2. vGPU 为什么能绕开它（推断）

结合 A 段的机制，vGPU 上 guest 驱动看到的"完成"**不是物理引擎的完成**：

| | 真机直通 | vGPU |
|---|---|---|
| 门铃写到哪 | **真硅片寄存器** | **宿主内存页**（A1 映射） |
| 谁去编程引擎 | **本机驱动，同步** | **宿主 vgpu-mgr，异步** |
| 完成信号谁发 | 引擎，arming 完才发 | **宿主**，它可以自己决定时机（A4） |
| 每次提交的暴露延迟 | **118.5µs（物理 arming）** | 宿主给的（可以远小于） |
| 多个来源的提交 | 只能串行 | **宿主可以合并**（同一个物理 GPU 服务多个 guest） |

**⇒ 那 118.5µs 的物理代价并没有消失，它只是从 guest 驱动的关键路径上移走了。**
guest 不再对每一次"批次开始"付这个代价；宿主在自己的队列里消化它，并且可以在多个 vGPU 实例间摊薄。

### B3. 这与三项独立观测一致

| 观测 | 解释 |
|---|---|
| 截图 `GPU-Util 99%` + `%SM 99%`（报告 107 重读） | GPU 真忙 —— 宿主一直喂着，不是在等 |
| 用户最早观察"**525/535/570 在 vGPU 下都不回退**" | 因为那 118.5µs 在 vGPU 上不由 guest 驱动承担，**与驱动版本无关** |
| 真机上 primus/zink/换 Vulkan 对 Heaven 全无效 | 它们只动 present 层，而病根在提交层 |

### B4. 否证条件（唯一能判死它的测量）

**在 vGPU guest 里跑 `n83a -M 1 / -M 3`：**

| 结果 | 判读 |
|---|---|
| **≈0.03 µs/对**（像 515） | B2 成立 —— vGPU 消掉了提交惩罚 |
| **≈118.5 µs/对**（像 525） | **B2 死** —— 说明惩罚与 vGPU 无关，得回去找别的解释 |

**现在做不了**：用户已确认客户机不存在（`scsi0` 指向的 WDC 500GB 已不在机器上）。

### B5. 一个反直觉但重要的点

vGPU **理论上应该更慢**：多一层转发、多一次宿主调度、还要过 VM 边界。
但它实测更快 —— 因为**瓶颈根本不是"转发开销"，而是"驱动在等物理引擎"**。

**在一个"等待占 91% 的帧时间"的系统里，把"等"换成"不等"，多出来的转发开销完全被淹没。**
这就是为什么 vGPU 这个看起来更重的架构反而跑得更快。

## C 段：这个结论的边界

| 我说了什么 | 依据强度 |
|---|---|
| BAR0 稀疏映射（≤5 窗口）到宿主内存页 | **源码原文**（`nv-vgpu-ioctl.h:124/488-511`、`nvidia-vgpu-vfio.c:2330-2350/4237`） |
| pushbuffer 零拷贝，靠 GFN→PFN | **源码原文**（`vgpu-devices.c:575-620`） |
| 中断由宿主经 eventfd/irqfd 注入 | **源码原文**（`nvidia-vgpu-vfio.c:3252`） |
| 真机 118.5µs/对、Heaven 账闭合 | **实测**（报告 105，n83a + 角标） |
| **宿主把完成与物理 arming 解耦** | ⚠️ **推断**。blob 不可读，无法证明宿主"提前发完成" |
| **宿主跨 guest 合批** | ⚠️ **推断**，且这对单 guest 场景不是必要条件 |

**⇒ 前三行可以当事实用；后两行必须按"待验假说"对待。**

**但有一条更稳的推论不依赖"宿主提前发完成"**：
既然门铃写是**普通内存写**（A1）、pushbuffer **零拷贝**（A3），
那 guest 驱动就**不会在每次提交上遭遇一次宿主往返** —— 这本身就消除了"每批一次固定延迟"的暴露形态。
宿主何时回完成是次要的。

## 一句话

**vGPU 的路径不是"每次 MMIO 都陷入、宿主转发"那种笨设计，而是：BAR0 里 ≤5 个热窗口被 `remap_pfn_range` 直接映射成宿主内存页（门铃是普通 store，不 trap），
pushbuffer 靠 `translate_gfn_to_pfn` 让宿主零拷贝直读，
完成中断由宿主经 eventfd/irqfd 注入。**

**所以 guest 驱动不会在每次"批次开始"上等物理引擎 —— 而那 118.5µs 正是"等物理引擎 arming"的代价。
真机的 30fps 是等出来的，不是算出来的；vGPU 把"等"从 guest 的关键路径上移走了。**
