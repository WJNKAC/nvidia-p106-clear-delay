> ## ⚠ 报告 166（N175）更正本报告的"等 fence 前进 0x14"表述
>
> 本报告把等待函数描述为"等 fence 前进 `0x14`"。**实测该描述是错的。**
>
> `call [rbp+0x280]` 解析到 `glcore+0xeb8800 → jmp 0xeb2fb0`，而 `0xeb2fb0` 里是
> `imul rax, [rsp], 0xf4240` + 加微秒 —— **这是"取当前时间戳（纳秒）"**。
> 所以 `cmp rax, 起始+0x14` 是**按时间戳自旋至少 20 纳秒**的节流器，**不是等 GPU fence**。
> 实测该路径累计自计时仅 **0.2 ms / 4 秒 ≈ 0%**，确实几乎不耗时。
>
> 该函数还有第二条路径（`[ctx+0x12a0] != 0` 且 `[rbx+0x26e8]==1` 时）：
> 按 `[rbx+0x26ec]` 的间隔限流后 `call [rbp+0x278]` 进 **`sched_yield`** —— 这才是 `GLYield` 的实现点，
> 也是 `perf` 里 515 那 **21.86% `__sched_yield`** 的来源。
>
> **不影响本报告的核心结论**（三个原语两版逐条同构、回归不在等待逻辑），
> 但"常量 0x14"的含义要更正为"20 纳秒"，不是"20 个 fence 单位"。

# N173 — 用户态逆向：515 与 525 的 fence/等待/空间检查三个原语**逐条同构**

**日期**：2026-10-27
**对象**：`libnvidia-glcore.so` 515.105.01（36.77 MB）vs 525.116.03（44.28 MB）
**方法**：纯静态（本地读 `.so`，解析 `PT_GNU_EH_FRAME` 函数边界 + 扫 `call rel32` + capstone 反汇编）

---

## 0. 一句话结论

**此前所有「525 的等待/空间检查逻辑被改坏了」的假设，全部被静态证据否掉。**

两版的三个关键原语 **语义完全一致**，连等待常量都一样：

| 原语 | 525 | 515 | 语义 |
|---|---|---|---|
| fence 寄存器读取 | `0x1569f10` | `0xfb19d0` | 读 MMIO fence |
| fence 访问器（带缓存位） | `0x1572e60` | `0xfbae60` | 有缓存则返回 `[ctx+0x1240/0x11e0]` |
| **等待 fence 前进 N** | `0x15761b0` | `0xfbcc30` | **目标 = 起始 + 0x14（20）**，9 连 `pause` 自旋 |
| **确保 pushbuffer 空间** | `0x1578280` | `0xfbed80` | **逐条指令同构**，等待常量同为 **0x12（18）** |

**⇒ 回归不在这些函数里。差异只能在"它们被调用得多频繁"，即上游的批次/刷写策略。**

这与报告 162 的定律（成本 = 批次数 × 122 µs）完全吻合：
**决定性能的是"切了多少批"，不是"每批怎么等"。**

## 2. 定位方法：用「连续 pause」当指纹

普通手段（字符串、立即数）噪音太大：搜 `0x800000ba` 命中 **909 处**，完全不能用。

**有效指纹：连续 ≥6 个 `F3 90`（`pause`）。** 这是"短时自旋等待"的编译器产物，很稀有：

| 版本 | 命中代码块 | 落在几个函数里 | 函数 |
|---|---|---|---|
| 525 | 4 | **1** | **`0x15761b0`** |
| 515 | 4 | **1** | **`0xfbcc30`** |

**两版各只有一个函数含这种自旋**，直接锁定。

> 方法论：**在巨大的 stripped 二进制里找"某个等待循环"，不要搜常量和字符串，
> 搜编译器为自旋生成的 `pause` 序列。** `pause` 连发只会出现在自旋/退避循环里。

## 3. 等待函数：两版逐条同构（常量都是 0x14）

### 525 `0x15761b0`

```asm
test rdi, rdi / je ...
mov  rbx, [rdi+0x1300]        ; ctx 相关字段
mov  dword [rdi+0x2c], 1      ; 置"在等"标志
call qword [rbp+0x290]        ; ← 读 fence（间接调用，函数表）
mov  r14, rax                 ; r14 = 起始值
lea  r12, [rax+0x14]          ; ★ 目标 = 起始 + 0x14 = 20
mov  edi, 3
call qword [rbp+0x280]
loop:
call qword [rbp+0x290]        ; ← 重读 fence
cmp  rax, r12
jge  exit                     ; 已达目标 → 退出
cmp  rbx, rax
jl   spin                     ; 有进展 → 继续
spin: pause ×9
jmp  loop
exit:
sub  rax, r14                 ; 累计本次等待耗时
add  [r13+0x6f88], rax        ; ★ 自计时器
```

### 515 `0xfbcc30`

```asm
test rdi, rdi / je ...
mov  rbx, [rdi+0x12a0]        ; 偏移不同
mov  dword [rdi+0x10], 1      ; 偏移不同
call qword [rbp+0x280]        ; ← 读 fence（表位置不同）
mov  r14, rax
lea  r13, [rax+0x14]          ; ★ 目标 = 起始 + 0x14 = 20  —— 同一个常量
mov  edi, 3
call qword [rbp+0x270]
loop:
call qword [rbp+0x280]
cmp  rax, r13
jl   spin
spin: pause ×9                ; 同样是 9 连 pause
jmp  loop
exit:
sub  rax, r14
add  [r12+0x6f50], rax        ; ★ 同样是自计时器，偏移不同
```

**结论：同一个算法、同一个常量（0x14=20）、同一套自旋形态、同样自带计时器。
差别只有结构体偏移和函数表槽位。**

这也修正了一个早期误读：这个循环用的是 **`pause` 自旋，不是 `sched_yield`**。
（`sched_yield` 的样本来自别处，见报告 161 —— 且已证明关掉 yield 不影响耗时。）

## 4. 「确保 pushbuffer 空间」：两版逐条同构（常量都是 0x12）

### 525 `0x1578280` / 515 `0xfbed80`（并排对照，只列差异）

| 步骤 | 525 | 515 |
|---|---|---|
| put 指针 | `[rdi+0x1130]` | `[rdi+0x10d0]` |
| `if (put == need)` 时调用 | `[rdi+0x1a90]` | `[rdi+0x1a58]` |
| 读"已消费"指针 | `[rbp+0x1a98]` | `[rbx+0x1a60]` |
| 缓存 fence | `[rbp+0x1240]` | `[rbx+0x11e0]` |
| 快路径 | `call 0x15762d0` | `call 0xfbcd50` |
| **等待** | **`mov esi,0x12` + `call 0x15761b0`** | **`mov esi,0x12` + `call 0xfbcc30`** |
| 等待后重读 | `call qword [rbp+0x1a98]` | `call qword [rbx+0x1a60]` |
| 收尾 | `call 0x1577bc0` → `jmp 0x1576350` | `call 0xfbe6c0` → `jmp 0xfbcdd0` |
| 大等待分支 | `[rbp+0x588]` + `call 0x156c410` | 对应位置同构 |

核心逻辑（两版一致）：

```
free = put - consumed
需要 = put - need
if (free <= 需要)  →  已经有足够空间，直接返回
否则               →  等 fence 前进 0x12(18)，重读 consumed，再判一次（循环）
```

**指令序列、分支结构、常量全部一致。这不是"同源代码"，是同一个函数换了一套结构体偏移。**

### 调用图也一一对应

| 目标 | 525 call 点 / 调用者函数 | 515 call 点 / 调用者函数 |
|---|---|---|
| 等待函数 | **13 / 11** | **13 / 11** |
| fence 读取 | 1 / 1 | 1 / 1 |
| ensure_space | 0 直接调用（走函数指针表） | 0 直接调用 |

**13 对 13、11 对 11** —— 连调用点的形状都对齐了
（两版都有一个"3 处调用"的函数：525 `0x156e2a0`，515 `0xfb5d30`）。

## 5. 这轮否掉了什么

| 曾经的假设 | 现在的结论 |
|---|---|
| 525 把自旋改成了睡眠/插了一次长等待 | ✗ 两版等待函数同构，都用 `pause` 自旋 |
| 525 的等待常量变大了（等更多） | ✗ 常量完全相同（0x14 与 0x12） |
| 525 空间检查更保守 | ✗ 空间检查逐条同构，阈值算式一致 |
| 525 少了某种缓存导致频繁等 | ✗ 缓存位的读取/回退逻辑两版都有（`0x1572e60` / `0xfbae60`） |
| 525 新增了可调的等待策略 | ✗ `__GL_*` 开关 56 vs 56，零差异 |

**⇒ 唯一剩下的解释：上游"什么时候决定切批/刷写"变了，导致这些原语被调用的次数暴涨。**
报告 150 的实测正是这个方向：**525 每帧等 19,181 次，515 只等 6.7 次**（画面校验值相同）。

## 6. 下一步该看哪里（已排除法锁定的范围）

既然原语没问题，问题一定在 **"谁、按什么条件、请求了多少空间"**：

1. **追 `need`（rsi）的实参**。`ensure_space` 走函数指针表，静态拿不到调用者；
   需要动态：在 `0x1578280` 入口打断点，记录 `rsi` 的分布。
   **如果 525 每次只请求很小一块**（例如一条命令一条命令地要），那批次数自然暴涨。
2. **找窗口上限 `[ctx+0x1130]`（525）/ `[ctx+0x10d0]`（515）的写入处**。
   这是"本次可用空间到哪为止"，它的值决定了多久撞一次墙。
   两版这个字段的初始化位置不同，值得对比。
3. **追"切批"的判据**：报告 162 已证明 `glUniform` 不切批、`glUseProgram`/绑定类切批。
   找"哪些 GL 调用会导致刷写"，在 525 里是否比 515 多了条件。
   （525 多出的 21,100 个函数很可能就在这里。）

**优先级：1 > 3 > 2。** 第 1 条最便宜且直接给出"每批请求多大"这个决定性数字。
