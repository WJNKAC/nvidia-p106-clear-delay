**日期**：2026-10-27
**背景**：用户计划切换内核 6.12 + 驱动 580，问能否同样 patch
**方法**：纯静态分析本地已解包的 `580.178.04`，**未改动任何现有环境**

| 问题 | 答案 |

## 1. 静态对比：三个版本

| 判据 | 515.105.01 | 525.116.03 | **580.178.04** |
|---|---|---|---|
| 文件大小 | 35.07 MB | 42.23 MB | 35.35 MB |
| `movabs 0x...20010E66`（那条命令） | **0 处** | **2 处** | **2 处** |
| 实参值 | — | 均为 `0xF0`(240) | **均为 `0xF0`(240)** |
| `cmp byte [rax+0xc18], 0`（判据） | 0 处 | **4 处** | **0 处** |
| `cmp byte [rax+0x20b], 0` | 0 处 | 0 处 | **1 处** |

**⇒ 580 依然会发这条 240 单位的延迟命令，但策略位的结构体偏移从 `0xc18` 变成了 `0x20b`。**

580 体积比 525 小 7 MB（35.35 vs 42.23），说明中间做过重构 —— 这也解释了为什么判据代码的形态变了。

## 2. 第一处发射点（结构同构，可直接套）

`0xb51c84`，所在函数 `0xb51600`（13040 字节，大状态机，对应 525 的 `0x15c2e50`）

```asm
0xb51c74  mov  rax, [r14 + 0x1240]
0xb51c7b  cmp  byte [rax + 0x20b], 0      ; ★ 判据位（525 是 +0xc18）
0xb51c82  je   0xb51cb0                   ; 74 2c  ← ★ 补丁点
0xb51c84  mov  rax, [r14 + 0x80]
0xb51c8b  movabs rcx, 0xF020010E66        ; 实参 0xF0 + 命令头 0x20010E66
0xb51c95  mov  [rax], rcx
0xb51c98  add  rax, 8
0xb51c9c  mov  [r14 + 0x80], rax
```

**与 525 的差异只有两处偏移**：判据位 `0xc18`→`0x20b`，其余指令序列**逐条一致**（`je` 的目标偏移都是 `+0x2c`，即 `74 2c`）。

**候选补丁**：
| 偏移 | 原 | 新 | 含义 |
|---|---|---|---|
| `0xb51c82` | `0x74` | `0xeb` | `je` → `jmp`，无条件跳过发射 |

## 3. 第二处发射点（结构不同，⚠ 不能照搬）

`0xde855e`，所在函数 `0xde81e0`（1728 字节，带 switch 分派的封装）

```asm
0xde8550  mov  rsi, [rbx + 0x68]
0xde8554  cmp  [rbx + 0x60], rsi
0xde8558  je   0xde8860                   ; 空间不足 → 去 0xde8860
0xde855e  movabs rsi, 0xF020010E66        ; ★ 无条件发射
0xde8568  mov  [rax], rsi
0xde856b  mov  eax, 1                     ; 返回 1（表示发了一条）
0xde8570  mov  [rbx + 0x60], rdx
...
0xde8860  mov  [rbx + 0x68], rax
0xde8864  jmp  0xde855e                   ; ★ 跳回来后继续发
```

**与 525 的 `0x1841fb0` 关键差异**：

| | 525 (`0x1841fb0`) | **580 (`0xde81e0`)** |
|---|---|---|
| 策略位判据 | **有**（`cmp [rax+0xc18],0`） | **没有** |
| 前置条件 | 策略位为 0 就返回 | 只有空间检查 |
| 发射行为 | 有条件 | **无条件（循环保证一定发出去）** |
| 返回语义 | 无特殊返回值 | `eax=1` 表示"发了一条" |

### 为什么不能简单改成 `jmp`

`0xde8558` 的 `je` **不是"跳过发射"**，而是"空间不足时去更新指针再跳回来"。
把它改成 `jmp` 会变成"永远跳走 → 永远不发射 → 但 put 指针也不前进"，
与后续 `eax=1` 的返回语义冲突，**极可能让调用方状态错乱**。

### 为什么也不能把它 nop 掉

如果只 nop 掉 `movabs` + `mov [rax],rsi`（10 字节），
后面的 `mov [rbx+0x60], rdx` 仍然会把 put 指针推进 8 字节，
**结果就是 pushbuffer 里留下 8 字节未写入的垃圾**，GPU 会解析出乱码命令。

### 可选的处理方式（都需要实测确认）

| 方案 | 做法 | 风险 |
|---|---|---|
| **A. 改实参（治标）** | `0xde8562`（立即数内 `F0` 的位置）改小 | 仍然每批发，只是延迟变小 |
| **B. 改成 `0f 85`（反转）** | `0xde8558` 的 `0f 84` → `0f 85` | 等长（6 字节），但语义变成"空间够就跳走"，会走进 `0xde8860` 更新指针然后跳回 —— **可能死循环** |
| **C. 从调用方绕过** | 找 `0xde81e0` 的函数指针表槽位，让它不被调用 | 需要先确认它的调用频率和作用 |

**⚠ 我不建议在实测之前对第二处下手。** 它的控制流比 525 复杂，猜错会写坏 pushbuffer。

## 4. 环境前提：6.12 + 580 反而少一个坑

| 项 | 6.1.0-50（当前） | **6.12.113（已装）** |
|---|---|---|
| 内核编译 GCC | `gcc-12 (12.2.0)` | **`gcc-14 (14.2.0)`** |
| 系统默认 gcc | `14.2.0` ❌ 不匹配 | **`14.2.0`** ✅ **匹配** |
| 装驱动要不要 `CC=gcc-12` | **要**（否则 `implicit-function-declaration` 报错） | **不需要**，直接装 |

**⇒ 6.12 下装 580 反而比现在简单。** 之前那个 `dma_is_direct` + GCC 14 的坑不会出现。

已确认：
- `/boot/vmlinuz-6.12.113+deb13-amd64` 存在
- `/usr/src/linux-headers-6.12.113+deb13-amd64` 存在
- `CONFIG_CC_VERSION_TEXT="x86_64-linux-gnu-gcc-14 (Debian 14.2.0-19) 14.2.0"`
- `GRUB_DEFAULT=0`（要确认 0 指向哪个内核）

**⚠ 切换前必须确认**：`grub` 里 6.12 是否已是默认项、`nvidia` 模块在 6.12 下能否正常编译加载、
以及**切换内核后能否回退**（保留 6.1 的启动项）。

## 5. 建议的验证流程（切过去之后按这个走）

### 第 0 步：先确认没有 patch 也能起来
```bash
uname -r                                    # 应显示 6.12.113+deb13-amd64
cat /proc/driver/nvidia/version             # 应显示 580.178.04 + gcc 14.2.0
nvidia-smi                                  # 能出卡信息
```

### 第 1 步：确认"问题是否依然存在"（最关键，不能跳过）
```bash
# 用 n83b 跑与 525 完全相同的负载
cd <workdir>/analysis/n83a
__GLX_VENDOR_LIBRARY_NAME=nvidia __NV_PRIME_RENDER_OFFLOAD=1 \
  ./n83b_new -M 7 -c 400 -n 400 -f 100 -W 3 -q
```
**判读**：
- `map_p50` ≈ 50 ms → 问题存在，与 525 同类
- `map_p50` ≈ 3.4 ms → **580 已经修了，不需要补丁**
- 其他数值 → 是另一个问题，需重新分析

### 第 2 步：确认命令是否每批都发
```bash
# 起长跑，然后扫 pushbuffer 里的 method 0x3998
./n83b_new -M 7 -c 400 -n 400 -f 20000 -W 3 -q &
P=$!; sleep 2
python3 ../tools/pbargs.py $P 0x3998
```
- 抓到大量 `cnt=1 0x000000f0` → 确认每批都发
- 抓不到 → 说明 580 用了别的机制或不同方法号，**需重新定位**

### 第 3 步：只对**第一处**试补丁（运行时，不动文件）
```bash
PATCH="0xb51c82=eb" LD_PRELOAD=<workdir>/analysis/shim/patchpb.so \
  ./n83b_new -M 7 -c 400 -n 400 -f 100 -W 3 -q
```
- `map_p50` 明显下降 + `chk` 不变 → 第一处是主因
- 无变化 → 主因在第二处，需进一步分析

### 第 4 步：若第一处不足，再评估第二处
按 §3 的方案 A/B/C 逐个试，**每次都必须看 `chk` 是否变化**。

### 第 5 步：确认后再固化成文件补丁
流程与 525 完全一致，见 `patch/README.md`。

## 7. 一句话回答用户

**能 patch，而且可能比 525 简单**（`je` → `jmp` 那一处结构完全一样）。
**但 580 的第二处发射点没有了 525 那个策略位判据、变成无条件循环发射，
不能照搬，需要单独设计，且必须先实测确认它是否真的是主因。**

另外 **6.12 内核反而帮了忙** —— 它的 gcc-14 与系统默认一致，省掉了 `CC=gcc-12` 那个坑。
