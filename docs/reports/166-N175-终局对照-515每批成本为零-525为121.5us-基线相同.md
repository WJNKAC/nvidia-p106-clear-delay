# N175 — ★ 终局对照：515 的"每批成本"为零，525 是 121.5 µs；基线完全相同

**日期**：2026-10-27
**平台**：<user>@<testhost>，P106-100，同机整驱动切换（515.105.01 ↔ 525.116.03，均 gcc 12.4.0 编译）
**负载**：`n83b -M 7 -n 400`（固定 400 个 draw，只改"批次数" `-c`）
**方法**：无 ptrace、无 perf 干扰，只读程序自测的外部墙钟

---

## 0. 一句话结论

**同一个二进制、同一个负载、同样 400 个 draw，只改批次数：**

| 批次数 c | 515 total_p50 | 525 total_p50 |
|---|---|---|
| 0 | 4.953 ms | ~4.48 ms |
| 25 | 3.939 | — |
| 50 | 3.812 | — |
| 100 | **3.652** | **16.364** |
| 200 | 3.974 | 28.026 |
| 400 | **4.410** | **52.811** |

**斜率：515 ≈ 0（甚至略负），525 = +121.5 µs/批。**

> **515 根本没有"每批成本"这个东西；525 有，且是 122 µs。**
> **两者在"零批次"处的基线几乎一致（4.95 vs 4.48 ms）——所以不是"525 处处更慢"，是"525 每切一次批就要付一次固定的钱"。**

## 1. 差异全部落在"等 GPU"，不在 CPU

同一次运行的分段（c=400）：

| 分段 | 515 | 525 | 比值 |
|---|---|---|---|
| `submit_p50`（CPU 提交 400 个批次） | **0.713 ms** | **0.577 ms** | **0.81×（525 更快）** |
| `map_p50`（等 GPU 完成、回读） | **3.426 ms** | **52.059 ms** | **15.2×** |
| `total_p50` | 4.410 ms | 52.811 ms | 12.0× |

**CPU 侧提交 525 甚至比 515 还快一点。**
**全部 49 ms 的差距都在 `map` 里 —— 等 GPU 把这一帧画完。**

⇒ **CPU 驱动没有"多做工作"。它把命令发下去之后，GPU 要 52 ms 才完成；515 只要 3.4 ms。**

## 2. 这条对照为什么是决定性的

它一次同时排除了四类解释：

| 解释 | 被排除的理由 |
|---|---|
| "525 的 CPU 提交路径更重" | submit 反而更快（0.577 < 0.713） |
| "525 每个 draw 更贵" | 315 个 draw 是固定的，`-c` 只改分批方式；若按 draw 计费，c 从 0→400 不该变 |
| "525 的初始/固定开销更大" | c=0 时两版几乎相同（4.48 vs 4.95） |
| "515 只是少干活" | `chk` 校验值一致、draw 数一致，画的是同样的东西 |

**唯一剩下的解释：525 每开一个新批次，就要让 GPU 付一次约 122 µs 的固定代价。**

## 4. 对报告 164 的一处更正（重要）

报告 164 说：等待函数在"等 fence 前进 0x14"。**这是错的**，本轮把它读透了。

515 的 `0xfbcc30` 实际有**两条路径**：

```
rbx = [ctx+0x12a0]
if (rbx == 0)                      → 路径 A
else if ([rbx+0x26e8] != 1)        → 也走路径 A
else                               → 路径 B
```

**路径 A（时间戳节流）**

```asm
call [rbp+0x280]          ; ← 这个不是读 fence！是"取当前时间戳(ns)"
mov  r14, rax
lea  r13, [rax+0x14]      ; 目标 = 起始 + 0x14
loop: call [rbp+0x280]
      cmp  rax, r13
      jl   spin           ; pause ×9
```

实测 `[rbp+0x280]` 解析到 `glcore+0xeb8800 → jmp 0xeb2fb0`，而 `0xeb2fb0` 里是

```asm
imul rax, qword ptr [rsp], 0xf4240     ; sec × 1,000,000
add  rax, rdx                          ; → 纳秒
```

**⇒ 它是"按时间戳自旋至少 20 纳秒"的节流器，不是等 GPU fence。**
实测该路径累计自计时只有 **0.18~0.23 ms / 4 秒 ≈ 0%**，确实几乎不花时间。

**路径 B（限流 yield）**

```asm
cmp  dword [rbx+0x26e8], 1        ; 开关
mov  eax, [r12+0x6f74]
mov  dword [rsp+0xc], 0x17        ; 默认值
test eax, eax; jle  → 用默认
sub  rdx, [r12+0x6f78]            ; now - 上次yield时间
cmp  rdx, [rbx+0x26ec]            ; 与间隔比较
jl   → 用默认值
mov  eax, [rbx+0x26f0]            ; 否则用配置值
lea  rsi, [rsp+0xc]
mov  edi, 3
call [rbp+0x278]                  ; ← 进 sched_yield
```

**这就是 `GLYield` 的实现点**（`[rbx+0x26e8]` 开关、`[rbx+0x26ec]` 间隔、`[rbx+0x26f0]` 取值）。
`perf` 也印证了：515 上 **21.86% 的 CPU 时间在 `__sched_yield`**，就是这条路径。

**两版这段代码逐条相同**（只有结构体偏移不同：`ctx+0x6f74/0x6f78` vs 对应位置）。

## 5. 顺带测到的两个数（口径需注意）

用硬件断点统计（注意：ptrace 每次命中都会暂停目标，**跨 run 的"次/秒"不可直接比较**）：

| 项 | 515 | 525 |
|---|---|---|
| wait 函数命中 | 120,310 次/秒 | 98,013 次/秒 |
| wait 的**唯一**调用点 | `0xfbede0`（`ensure_space` 内 `call`） | `0x15782e0`（同位置，同构） |
| `ensure_space` 入口命中 | 249 次/秒 | 19 次/秒 |
| `ensure_space` 的 `rsi` | 每次 +4 递增（0x11b7, 0x11bb, …） | 同规律（0x16b, 0x16f, …） |

`rsi` 每次递增 4 说明它是**命令流里的偏移（每条命令 4 字节）**，不是"请求字节数"。
**⇒ 我原先"测 need 大小"的思路不成立**，这个参数无法回答批次问题。

**只有 wait 的调用点这一个数是可靠的**：两版都只有**一个**热点调用点，都在 `ensure_space`
内部的重试循环里。但 `ensure_space` 入口次数（515 多、525 少）与 wait 次数（525 相对不低）
提示 **525 每次进入后循环更多轮** —— 这一条要用不干扰的方法再测，本报告不作为结论。

## 6. 当前最可能的机制（待验证）

**525 在每个批次边界上，让 GPU 做一次"排空/同步"，使批次之间无法流水重叠。**

支持：
- 成本严格 ∝ 批次数，与批内 draw 数无关（报告 162 + 本报告）
- 成本在 GPU 侧（`map`），CPU 侧不变（本报告）
- GPU 利用率 98%、时钟顶格、功耗反降 → 在执行但不出活（报告 162）

⇒ 自然推论：**515 让相邻批次在 GPU 上重叠执行；525 把它们串行化了。**

**验证方法（下一步）**：抓同一负载（`n83b -M 7 -c 400`）在两版下的 pushbuffer，逐条对比
method 分布。若 525 每批多出 sync/semaphore/fence-write 类命令，机制即坐实。
（报告 140 已对 Heaven 做过同类对比：515 发 48k~50k 条、525 只发 25k~31k 条 ——
**命令更少却更慢**，与"串行化"一致：不是命令多，是命令之间被塞了等待。）

## 7. 工程含义（未变，但现在有直接证据）

- 525 上**每帧批次数就是性能预算**：`base + B × 122 µs ≤ 16.67 ms`。
  base ≈ 4.5 ms 时，**B 必须 ≤ 100 批**才可能 60 fps。
- **`glUniform` 不切批**（报告 162），`glUseProgram` / `glBindTexture` / `glBindFramebuffer` / legacy 状态都切批。
- **515 上不存在这个约束** —— 它可以承受任意多的批次切换。这就是两版最本质的差异。
