# 报告 139 — 内核边界拦截（ioctl 层）：152 次慢 ioctl 的底裤，以及一个自我更正

> 编号：139（对应 N148）
> 日期：2026-10-27
> 平台：P106-100 / 525.116.03 / Heaven 4.0 OpenGL 1920×1080
> 工具：新增 `analysis/shim/nkioctl.c`（LD_PRELOAD 拦 `ioctl()`）
> 前置：报告 137（GL 层垫片）、138（515/525 Heaven 对照）

---

## 0. 三句话结论

1. **挖到底了，但它不重要**：13 秒**稳态渲染**里，全部 NVIDIA ioctl 合计 **599 次 / 30.72 ms = 0.24% 墙钟**。
2. **报告 138 里"152 次 1~4 ms 慢 ioctl 吃掉 240 ms"是错的** —— 那些全在**加载/场景切换期**，不在渲染期。
   稳态渲染期那个 184 字节的慢 ioctl（nr=0x4A）只有 **5 次、平均 70 µs**。
3. **加载期的真凶是另一个**：`nr=0x2B`（RM_ALLOC，分配 GPU 对象）32 次、合计 **3967 ms**，**单次最长 3.96 秒**，
   且这 32 次**全在加载期**，稳态渲染期 0 次。

**所以：用户提议的"在驱动↔内核边界拦截"作为观测手段确实更好（一次 dump 给出全画像），
但作为优化点，它的天花板只有 0.24%。它帮我做的是把这条路彻底排除，而不是修好它。**

---

## 1. 为什么这一层比 GL 层垫片好（结构性理由，不是偏好）

| 维度 | GL 层垫片（报告 137） | **ioctl 层（本报告）** |
|---|---|---|
| 生效方式 | 要拦 PLT + `glXGetProcAddress` + **`dlsym`** 三路 | **只拦 `ioctl()` 一个 libc 符号** |
| 对应用的要求 | 依赖 GL 版本、依赖它怎么取入口 | 无（任何走 libc 的程序都拦得住） |
| 语义风险 | 会改 GL 状态机，可能改画面 | **零**（只观测，参数原样透传） |
| 看到的层次 | GL 语义（program/texture/FBO） | **驱动真正跟内核说的话**（协议字节） |
| 能做实验 | 难 | **能给指定 nr 注入延迟，做因果验证** |

`glcore` 调的是 libc 的 `ioctl`，不是我原先担心的裸 `syscall` 指令 —— 这有实测依据：
bpftrace 抓到的慢 ioctl 用户态栈是 `ioctl+59`。所以 LD_PRELOAD 在这一层是可靠的。

## 2. 工具：`analysis/shim/nkioctl.c`

```bash
gcc -O2 -fPIC -shared -o nkioctl.so nkioctl.c -ldl

NK_MODE=count  LD_PRELOAD=./nkioctl.so ./app         # 只统计（默认，零风险）
NK_MODE=trace  LD_PRELOAD=./nkioctl.so ./app         # 逐条打印解码后的 nr/size/dir
NK_DELAY=0x2a:1200 LD_PRELOAD=./nkioctl.so ./app     # 给 nr=0x2a 注入 1200µs（因果实验）
kill -USR1 <pid>                                     # 随时吐累计统计（可多次，做增量）
```

要点：
- 只处理 `_IOC_TYPE(cmd) == 'F'`（NVIDIA 的 `NV_IOCTL_MAGIC`），其余**原样透传**。
- 自己解码 `_IOC`：`nr = cmd & 0xff`，`size = (cmd>>16) & 0x3fff`。
- 每个 nr 记 `calls / sum / avg / max / 8 段直方图`，并**比对输入区**判断"同一请求重复"。
- 多次 `kill -USR1` 打点 → **两次相减就是增量**，这是分清"加载期 vs 渲染期"的关键（上一轮就是没做这一步）。

### 3.1 结构体身份（用 size 对出来的）

| nr | size | 推断 | 依据 |
|---|---|---|---|
| **0x2a** | **32** | `NVOS54_PARAMETERS`（`NV_ESC_RM_CONTROL`） | 64 位下 hClient(4)+hObject(4)+cmd(4)+flags(4)+params(8)+paramsSize(4)+status(4) = **刚好 32** |
| 0x29 | 16 | `NVOS00`/`NVOS55` 类（free/status，无参） | 16 字节 = 两个 handle |
| 0x2b | 40 | **`NV_ESC_RM_ALLOC` 类**（分配 GPU 对象） | 40 字节 = hRoot+hObject+pAllocParms+paramsSize+status+padding |
| **0x4a** | **184** | **20 字节输入 + 164 字节输出** | glcore 调用点 `r8=in`、`r9=in+0x14`，实测 buf 前 5 个 u32 是输入 |

**RM 的 ESC 符号名（`NV_ESC_RM_*` 枚举）和 `NVOSxx` 结构定义不在任何公开源码里** ——
`kernel-open` 只暴露 OS 层（`NV_IOCTL_BASE = 200`，即 `0xC8` 以上），RM 层全在闭源 blob。
这点必须诚实：**我只能给到"size 与结构吻合 + 行为特征"，给不到官方符号名。**

### 3.2 nr=0x4A 的实际内容（上一轮盯着的东西）

glcore 里 `0xC0B8464A` **全 44 MB 只出现 1 处**（偏移 `0x194c418`），指令是 `mov ecx, 0xc0b8464a`：

```
194c405: lea rax,[rip+0x10ef700]   # 2a3bb0c   ← 全局 fd
194c40d: lea r9,[rdi+0x14]         ← 输出区 = 入参 + 20 字节
194c414: mov r8,rdi                ← 输入区
194c417: mov ecx,0xc0b8464a        ← cmd
194c41c: mov edx,0xb8              ← size = 184
194c421: mov esi,0x4a              ← nr
194c426: mov edi,[rax]             ← fd
194c428: call 19499a0              ← 统一 ioctl 封装
```

实测 buf（每次调用的内容）：

```
+0x00: c1d0002d   +0x04: beef0003   +0x08: 2   +0x0c: 0   +0x10: 0
+0x14 ↓ 输出区（164 字节）
+0x28: 474c0000（慢时） / c1d0002d（快时）
```

`0xBEEF0003` 是 NVIDIA RM 内部句柄的标记pattern，`0xC1D0002D` 是另一个句柄。
**输入 5 个字：两个 handle + 一个类型字(2) + 两个保留。**

**快慢对比的结论（重要）**：同一 cmd、**输入字节完全相同**、耗时却在 77 µs ~ 1200 µs 之间变 15 倍，
只有输出字段不同。⇒ **不是"处理不同量的工作"，是内核/RM 内部在等** —— 与报告 136/138 的"在等，不是在算"同源。

### 3.3 但它属于加载期，不属于渲染期

13 秒**稳态渲染**增量：

| nr | Δcalls | Δms | Δavg | 阶段判断 |
|---|---|---|---|---|
| 0x2a | 517 | 23.48 | 45.4 µs | **渲染期主力**（≈40 次/秒 ≈ 每 1.5 帧一次） |
| 0x29 | 37 | 4.99 | 135 µs | 渲染期 |
| 0x58 | 21 | 1.49 | 71 µs | 渲染期 |
| 0x57 | 5 | 0.22 | 44 µs | 渲染期 |
| 0x4f | 14 | 0.19 | 14 µs | 渲染期 |
| **0x4a** | **5** | **0.35** | **70 µs** | **渲染期几乎不出现** |
| **0x2b** | **0** | **0** | — | **纯加载期** |

**合计 599 次 / 30.72 ms / 13.0 s = 0.24% 墙钟。**

## 4. 自我更正：报告 138 的那个数字是错的

| 报告 138 的说法 | 实际情况 |
|---|---|
| "525 有 **152 次 ioctl 落在 1~4 ms**，吃掉 261 ms 里的约 240 ms" | ❌ 那 20 秒 perf trace 窗口**跨过了 Heaven 的场景切换**，把加载期的 alloc/上传算进去了 |
| "ioctl 总耗时 261.3 ms / 10 s" | ❌ 稳态渲染期只有 **30.72 ms / 13 s（0.24%）** |

**同一个错误犯了第二次**：上一轮是"没清环境残留"，这一轮是"没区分加载期与渲染期"。
共同点都是**把不同阶段的样本混在一个平均值里**。

判决性证据：`0x2b` 在 t=44 s 时已是 32 次 / 3967 ms，到 t=57 s **一次没增加**。
若它真是渲染期现象，13 秒内必然有新样本。

### 对报告 138 结论的影响

- **不影响的**：515 vs 525 的帧间隔分布差异（单峰 vs 双峰）、等待函数调用次数（216,278 vs 0）、
  FPS 相当、功耗反向 —— 这些是独立测量，与本错误无关。
- **影响并已撤回的**：只有"慢 ioctl 吃 240 ms"这一条。

## 5. 加载期那个 4 秒的真凶

| | |
|---|---|
| nr | **0x2B**（RM_ALLOC 类，size=40） |
| 次数 | 32 次 |
| 合计 | **3967.71 ms** |
| **单次最长** | **3964.97 ms** |
| 分布 | 24/32 次 < 100 µs，但**有 1 次接近 4 秒** |
| 阶段 | **全部在加载期**（渲染期 0 次） |

这解释了 Heaven 为什么"要等 11 秒才进渲染" —— **其中 4 秒卡在一次对象分配上**。

这是个独立的问题（加载慢 ≠ 渲染卡），但值得一提：如果目标是"把 Heaven 跑起来更快"，
这个 4 秒的价值比渲染期的 122 µs 大几个数量级。

---

## 6. 对"边界拦截"这个判断的技术评价

用户说"这个边界拦截更好"。**对，但要分清它能干什么**：

| 目的 | 这一层能做吗 |
|---|---|
| 看清驱动跟内核说了什么 | ✅ **最优**（一次 dump 全画像，零语义风险） |
| 做因果实验（注入延迟） | ✅ 唯一可行的地方 |
| **减少渲染期开销** | ⚠️ **上限 0.24%** —— 没有肉 |
| **消除 122 µs 的绑定惩罚** | ❌ **看不见**。那个惩罚在 GPU 侧（报告 136/138），ioctl 层全程只花 30 ms |

**结论：这一层是最好的"听诊器"，但不是"手术刀"。**
它这一轮的真正贡献是**把"ioctl 是元凶"这条假设彻底排除**，从而把矛头锁死在 GPU 侧。

## 7. 下一步（按性价比重排）

1. **`0x2B` 那 4 秒**：唯一还有数量级空间的地方。做法：在加载期打增量、看是哪个 alloc
   （`NVOS21` 的 `pAllocParms` 里有 class 号），再判断能否异步化。**这是应用/驱动层的事，与本项目的 122 µs 无关。**
2. **回到 GPU 侧**：`0x15814a0`（等空间循环）的调用者 —— 谁决定"这里要开新批次"。这是报告 136 留下的唯一空洞。
3. **不要**再在 ioctl 层做优化：0.24% 的上限已经量出来了。
