# 35 · 更正 34：分叉不是"换掉自旋"，而是在**一条边上插入了一次 cond 等待**

> 2026-10-25 23:10
> 触发：重读 515 的 `jne c81a54` 时发现——`je` 和 `jne` **跳到同一个目标**，那不是回边，
> 所以"515 靠 10 万次自旋循环等待"这条描述站不住。顺着查下去，发现 525 **也有**一模一样的 10 万次预算块。
>
> **更正后结论没有变弱，反而变成了一个精确得多的陈述：**
> 两版的轮询预算、放弃标志、ms 收缩、自记时、notify、探测、仍空判定——**逐条同构**；
> 唯一的差别是"队列仍然空"那一条边：
> **525 在这条边上先 `wait_ms(cond, 100ms)`，515 直接 `call *0x270(4)` 继续轮询。**
>
> 一句话：**不是把自旋改写成睡眠，是在同一段代码的一条边上插了一次 cond 等待。**

---

## 1. 报告 34 错在哪（三处，都是同一个根因）

| 34 的写法 | 实际 | 根因 |
|---|---|---|
| "515 在对应位置是 `mov $0x186a0,%r14d` + `sub $0x1,%r14d`（10 万次有界自旋）" | `sub` 后面那条 `jne c81a54` 与 `je c81a54` **同目标**，不是回边；计数器每次"队列空"只减 1，由外层循环反复经过 | 把"递减一次"读成"内层 for 循环体" |
| "525 多了一条 Path B，515 没有" | 525 **也有**完整的 10 万预算块（`123aef0-123af16`），与 515 `c81a30-c81a50` 逐条对应 | 只对比了"调用 `wait_ms` 的那几行"，没把预算块一并对齐 |
| "515 的未完成路径是自旋，525 是睡眠"（二分法） | 两版都有自旋预算；515 在预算耗尽后**也会 sleep**（`c81d56: call *0x2b8(%rbx)`） | 二分法掩盖了"两边都有两种手段，只是优先级不同" |

**教训**：跨版本做"这段代码有没有"的判定时，**必须先把整块控制流画完再下结论**。
本例的错误成本很低（只是措辞），但同一个错法如果用在"某机制只存在于新版本"上，会直接把方向带偏。

## 2. 逐条同构证据（先把"同一段"钉死）

两版的 ctx 偏移段不同（515 `0x55exxx` / 525 `0x8e0xxx`），下表已换算。

| 语义 | 515 | 525 |
|---|---|---|
| 预算变量初始化 = **100000** | `c81844: mov $0x186a0,%r14d` | `123ad17: movl $0x186a0,0x8(%rsp)` |
| ms 变量初始化 = **100** | `c8183c: movl $0x64,0x28(%rsp)` | `123ad0f: movl $0x64,0x28(%rsp)` |
| 放弃标志清 0 | `c818e7: movb $0x0,0x1f(%rsp)` | `123adbf: movb $0x0,0x17(%rsp)` |
| 队列空 → 预算块 | `c81871: je c81a30` | `123ad41: je 123aef0` |
| **预算递减块** | `c81a30 – c81a50` | `123aef0 – 123af16` |
| ├ 预算为 0 则不递减 | `c81a33: je c81a54` | `123aef6: je 123af1a` |
| ├ 递减 | `c81a35: sub $0x1,%r14d` | `123aef8: sub $0x1,%eax` |
| └ **递减后非 0 → 与上面同目标** | `c81a39: jne c81a54` | `123aeff: jne 123af1a` |
| 预算刚好耗尽才走这里：ms **100→25** | `c81a3f: mov $0x19,%eax` | `123af05: mov $0x19,%eax` |
| 同上：置"放弃"标志 | `c81a44: movb $0x1,0x1f(%rsp)` | `123af0a: movb $0x1,0x17(%rsp)` |
| 等待计数 **>20** 升级 | `c81a54: cmpl $0x14,0x55f0a4; ja c81ca0` | `123af1a: cmpl $0x14,0x8e0d24; ja 123b130` |
| 自记时：状态置 **1**（开始） | `c81aa8: movl $0x1,0x55f088` | `123af6d: movl $1,0x8e0d08` |
| 自记时：状态置 **2**（结束） | `c81b37: movl $0x2,0x55f088` | `123aff9: movl $2,0x8e0d08` |
| 发 notify | `c81aba: call *0x2c0(%rbx)` | `123af7f: call *0x2d8(%rbp)` |
| 探测有无活 | `c81ad3: call *0x1a0(%rbx)` | `123af96: call *0x1b0(%rbp)` |
| **"仍然空"判定** | `c81ae4: cmp %rax,0x55ed08; je c81d40` | `123afa7: cmp %rax,0x8e0988; je 123b2f0` |

> ⚠️ **vtable 槽位不能跨版本直译**：515 用 `%rbx` 作基址、525 用 `%rbp`，同一功能的槽号差 `0x10`
> （例如两版的"`call *(4)` 续接"分别是 `*0x270` 与 `*0x280`）。槽号必须按版本各自建表（已有 `t5i_vtable.sh` 的产物）。

## 3. ★ 唯一的分叉点：一条边，一次调用

两版在"发完 notify、探测后队列**仍然空**"时，都跳到各自的目标。**这里就是全部差异：**

**515 —— 继续轮询**

```
c81aeb: je    c81d40                ; 仍然空
...
c81d40: cmpb  $0x0,0x1f(%rsp)       ; 放弃标志？（只在 10 万预算耗尽后才为 1）
c81d45: je    c81e61                ;   ← 未耗尽：跳走，不睡
...
c81e61: mov   0x2c(%rsp),%eax
c81e65: test  %eax,%eax
c81e67: je    c81ec6
c81e69: mov   $0x4,%edi
c81e6e: call  *0x270(%rbx)          ; ★ 续接调用
c81e74: jmp   c81af1                ; ★ 回去继续轮询
```

**525 —— 先睡再续接**

```
123afae: je    123b2f0              ; 仍然空
...
123b2f0: cmpb  $0x0,0x17(%rsp)      ; 三个门（放弃标志 / 0x2c / ctx+0x8e0dc8）
123b2f5: jne   123b309
123b2f7: mov   0x2c(%rsp),%eax
123b2fb: test  %eax,%eax
123b2fd: jne   123b32f              ; 跳过等待，直接续接
123b2ff: cmpb  $0x0,0x8e0dc8(%r15)
123b307: jne   123b32f
123b309: mov   0x8e0950(%r15),%rdi  ; cond = ctx+0x8e0950
123b310: mov   0x28(%rsp),%esi      ; ms（初值 100）
123b314: call  *0x2d0(%rbp)         ; ★ wait_ms —— 515 在这条边上没有
123b31a: test  %eax,%eax
123b31c: jne   123afb4
123b322: addl  $0x1,0x8e0d24(%r15)  ; 等待计数++（pathC，实测恒 0）
123b32f: mov   $0x4,%edi
123b334: call  *0x280(%rbp)         ; ★ 与 515 的 c81e6e 是同一个续接调用
```

**关键对照**：`c81e69: mov $0x4,%edi / call *0x270` 与 `123b32f: mov $0x4,%edi / call *0x280`
是**同一个续接**。525 在它**前面**插了一次 `wait_ms`；515 直接把控制权交回轮询循环（`jmp c81af1`）。

所以准确表述是：

> **两版处理"队列空"的手段集合相同（轮询预算 + 兜底 sleep），
> 525 额外在"notify 之后仍然空"这条边上加了一次 `wait_ms(cond, ms)`。**

这比 34 的"自旋 vs cond 等待"精确得多，也解释了为什么函数只大几十字节、
控制流统计几乎不变——**它就是多了一条 `call`**。

## 4. 这条边为什么会贵（与 31/32/33 的观测对齐）

| 观测（前序报告） | 用本节机制解释 |
|---|---|
| 525 每帧 map 窗口 3ms 被 `wait_ms` 覆盖（33/34） | 就是这条边被走到，且 cond 上等到了 signal |
| 每帧 3 次 wait、路径 pathB 242/s（34） | 这条边的命中率 |
| 98.3% 睡 futex、ioctl 重叠 0.4%（32） | `wait_ms` 内部就是 futex |
| GPU 只有 48~68W ≈ 空转（31） | 队列处理器在这条边上睡着，没人持续推进 |
| 515 全程 map max 0.81ms（29） | 515 走完这条边只是 `call *0x270(4)` + 回轮询，不产生跨线程依赖 |

**为什么"插一次等待"能差 3 倍**：轮询版**发现完成是即时的**（下一圈看到状态字变），
等待版**把发现时刻交给发通知的线程**。通知方自己也在等渲染轮次，于是每次都要多付一段通知链延迟
（34 §2.2 实测：10.4ms 与 27.8ms 各每帧一次，且互相重叠）。

## 5. 副产品：驱动**自己就在记这个等待的时延**

两版在同一段里都有自记时，结构完全一致（这是个可以直接读的证据源）：

| 字段 | 515 | 525 | 含义 |
|---|---|---|---|
| 状态 | `0x55f088` | `0x8e0d08` | 1 = 开始等，2 = 结束等（525 另有 3，见 `1237c2d`） |
| 累计数组 | `0x55f090[]` | `0x8e0d10[]` | **float**，按状态下标累加 elapsed |
| 上次时间戳 | `0x55f080` | `0x8e0d00` | 与 `*0x290`/`*0x280` 取时相减 |
| 等待计数 | `0x55f0a4` | `0x8e0d24` | **>20 触发升级路径** |
| 门控标志 | `0x55f08c` | `0x8e0d0c` | 非 0 则跳过本次累加 |

**这意味着不用挂 uprobe 也能拿到驱动自己统计的等待耗时**：只要拿到 ctx 指针，
读 `ctx+0x8e0d10[1]` / `[2]` 就能得到"它认为自己等了多久"。
→ 可作为下一轮**零扰动**交叉验证：uprobe 测的 3ms 与驱动自记的差多少。

**新增可读窗口**：`0x8e0d24`（等待计数）若长期停在 0（34 实测 pathC=0），说明**升级路径从未被触发**，
即每帧的等待都短于阈值、且都被唤醒——与"从不超时"互为独立佐证。
