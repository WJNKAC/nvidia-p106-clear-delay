# 55 · STOP 实验找到病根：**烧满一核的不是 worker，是另一个线程在跑 20µs 自旋；它与帧率无关**

> 2026-10-26 11:40
> 承报告 54：A 不成立、降分辨率下"自旋"不降。用户要求继续。
>
> **本轮做了三件事，第三件改变了整个结论：**
> 1. **STOP 实验**：冻结最忙线程 → **fps = 0**（它是必需的）
> 2. **限速实验**：cgroup 限速失败（误限了整个进程），绑核+竞争噪声太大、不可用
> 3. **★ 多探针定位**：发现**烧 100% 的线程不是执行 `1238a28` 循环的那个**，而是另一个线程在跑 `0x15761b0` 的 20µs 自旋
>
> **最终结论：那个线程与帧率无关。优化它只能省一个核，不提速。**

## 1. 结论（按证据强度排）

| # | 结论 | 证据强度 |
|---|---|---|
| 1 | **烧 100% 的线程跑的是 `0x15761b0`（20µs 自旋），不是 `1238a28`（队列检查）** | **强**：多探针按 tid 分组，S 100% 落在该 tid，C 为 0 |
| 2 | **该自旋的频率与像素、fps 都无关** | **强**：469,824 次/秒（1080p）→ 511,805 次/秒（640×360），**反而 +9%** |
| 3 | **冻结它 → fps = 0** | **强**：直接实验，恢复后 fps 回到 30+ |
| 4 | **但它不是帧率的决定因素** | **强**：降分辨率 fps 32→42，它纹丝不动（118%→111%） |
| 5 | 它是"必需的、纯空转的"线程 | 由 1–4 推出 |
| 6 | **→ 优化它 = 省一个核，不提速** | 由 4、5 推出 |

**一句话**：**它必须存在（停掉就没帧），但它不决定帧率（帧率变了它不变）。它占着一个核空转，是"必要的浪费"。**

## 2. 关键发现：三个线程各司其职（我前 11 轮搞混了）

`n57_twomode.sh`（4 个探针 + 按 tid 分组，3 秒采集）：

### 2.1 1080p（`-video_mode 6`，fps 32）

| 事件 | 地址 | 总次数 | /秒 | 主 tid | 该 tid 占比 |
|---|---|---|---|---|---|
| **C** 队列检查 | `0x1238a28` | 338,166 | 112,722 | **36541** | **100%** |
| **B** | `0x123b297` | 859,539 | 286,513 | **36525** | **100%** |
| **S** 20µs 自旋 | `0x15761b0` | **1,409,471** | **469,824** | **36542** | **100%** |
| **W** `mb_out` | primus `0x18908` | 95 | 32 | **36541** | 100% |

**线程 CPU：`36542 = 118%`（最忙）、`36525 = 75%`、`36541 = 31%`、`36540 = 25%`**

### 2.2 640×360（`-video_mode 0`，fps 42）

| 事件 | 总次数 | /秒 | 主 tid |
|---|---|---|---|
| **C** | 399,702 | 133,234 | **36862** |
| **B** | 1,127,532 | 375,844 | **36847** |
| **S** | **1,535,415** | **511,805** | **36863** |
| **W** | 127 | 42 | 36862 |

**线程 CPU：`36863 = 111%`（最忙）、`36847 = 93%`、`36862 = 36%`**

### 2.3 三个线程的身份（对应关系一目了然）

```
tid X+1  (36542/36863)  = 118%/111%  → 跑 S（20µs 自旋），C=0，W=0     ← 烧满一核的
tid X    (36541/36862)  =  31%/ 36%  → 跑 C（队列检查）+ W（mb_out）   ← readback worker
tid Y    (36525/36847)  =  75%/ 93%  → 跑 B（0x123b297）              ← 另一个队列处理器
```

**我前 11 轮的错误**：把 `tid X+1`（110%+，跑 S）当成了 `tid X`（31%，跑 C）。
两者 tid 相邻，我在报告 48/51 里都写"同一个线程"——**错了**。

## 3. 为什么"必需"和"无关"能同时成立

### 3.1 STOP 实验（`n52_stop.sh`）

```
基线        : 37.7 fps
STOP 36542  : 0.0 fps      ← 完全没帧
CONT 恢复   : 30.2 fps
```

**冻结它，整个进程停止出帧。**

### 3.2 但它在 fps 变化时纹丝不动

| | fps | S 次数/秒 | 该线程 CPU |
|---|---|---|---|
| 1080p | 32 | 469,824 | 118% |
| 640×360 | **42** | **511,805**（+9%） | 111% |

**fps 涨了 31%，它的工作量反而增加了 9%。**

### 3.3 合起来的意思

它是一个**固定节拍的同步线程**：
- 每帧必须跑（所以停掉就没帧）
- 但它的工作量由**每帧固定的同步次数**决定，不由像素/命令数决定
- 它每秒 ~50 万次循环 ≈ 每 2µs 一次

**它在"陪着"帧走，但不决定帧有多长。**

## 4. 对报告 48 的最终更正

报告 48 我写：

> "readback worker 每帧烧 11.4ms CPU 在问队列空不空"→ **这个归因错了两次**

| 报告 48 说 | 实际 |
|---|---|
| readback worker 烧 11.4ms/帧 | **worker（C 线程）只占 31%** = 9.6ms/帧，量级接近但对象错 |
| 那个 11.4ms 是"空转" | **真正占 1 核的是 S 线程（118%）**，它不跑 C |

**正确的表述**：
- **S 线程**：118% 一个核，跑 20µs 自旋，与负载无关，**必需但不决定 fps**
- **C 线程**（worker）：31%，跑队列检查 + mb_out，与负载相关
- **B 线程**：75%，跑 `0x123b297`

## 6. 明确了什么、还差什么

### 6.1 现在能确定的

1. **烧满一个核的是 S 线程（20µs 自旋）**，不是 worker
2. **它与像素/fps 无关**（两轮实测一致）
3. **它是必需的**（停掉 fps=0）
4. **它不是帧率的决定因素**（fps 变它不变）
5. **→ 优化它只能省一个核，不提速**

### 6.2 这意味着什么

**从报告 44 到 55 这 12 轮，追的是一个"占资源但不决定性能"的线程。**

它的存在、它的 20µs 自旋、它的 50 万次/秒——**全都真实，但和"为什么只有 34fps"没有因果关系**。

**真正的瓶颈仍然在报告 40 的 T_land（跨 GPU 拷贝 30.4ms）和报告 53 的 `display_mode=Disabled`。**

### 6.3 唯一还有价值的两条路

| 方向 | 内容 | 预期 |
|---|---|---|
| **① 省电/省资源** | 把 S 线程的忙等改成阻塞等（如果能改 glcore）→ 省一个核 | **不提速**，但 12 核机器上省 1 核有意义 |
| **★ ② 真正提速** | 回到报告 40：T_land 30.4ms = 跨 GPU 拷 8.29MB。**减少拷贝字节**（如降色深/分块）或**让拷贝更早落地** | 这才是 fps 的唯一杠杆 |

### 7.1 本轮踩的两个方法坑

1. **cgroup v2 `cgroup.threads` 写入失败会静默回退到整个进程。**
   `echo $TID > /sys/fs/cgroup/X/cgroup.threads` 需要 cgroup 是 `threaded` 类型且父级已开 `+cpu`。
   失败后我的脚本 fallback 到 `echo $PID > cgroup.procs`，**结果限了整个进程**，
   fps 掉到 13 是"全进程被限"的结果，与目标线程无关。

2. **Heaven 帧率本身波动大（22~42），单次 8 秒测量信噪比不够。**
   绑核+竞争实验里出现"2 个竞争者时 fps 比基线还高"（40 vs 37），
   说明该实验设计不可用。**因果判定要用"能产生数量级差异"的实验**（如降分辨率 33 倍、STOP 到 0），
   不要用"±20% 期望"的实验。

### 7.2 方法论（最重要的一条）

**`tid N` 和 `tid N+1` 不是同一个线程——这我写进技能库两次了，第三次还是栽在它上面。**

这次的教训更具体：**CPU 占比高 ≠ 它就是你正在观察的那个循环**。
必须用**多探针 + 按 tid 分组**确认"谁在跑哪段代码"，不能靠"tid 相邻"或"CPU 都高"推断。
