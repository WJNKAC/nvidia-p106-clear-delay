# 76 · N86：**代价不在"切换"，在"切换后紧跟的那个 draw"** —— M9 把 1000 次切换 + 1000 个 draw 做成 0 成本

日期：2026-10-26 11:45
驱动：525.116.03（P106-100，1920×1080，直连 NVIDIA，不经 primus）
程序：`analysis/n83a/n83a.c`（模式 1/3/6/7/8/9/10）

---

## 0. 三句话

1. **⚠️ 先更正：报告 75 的 265µs 是错的，真值是 121µs。** 连跑三次得 123.220 / 123.495 / 123.439ms，GPU 恒定 1911MHz / 40°C / 37W；且那次原序列的 `N=0` 也偏大 27%（3.379 vs 2.653）⇒ 那次全程有资源竞争，**整批作废**。
2. **代价不在"切换次数"，也不在"draw 次数"，而在两者【相邻交替】的次数。**
   `M9`：1000 次切换 + 1000 个 draw，但**先全切、再全画**（不相邻）→ **2.640ms，完全免费**。
   `M3`：同样的 1000 次切换 + 1000 个 draw，**交替相邻** → **123.350ms**。
3. **一个"带前置状态变更的 draw" = 121µs，与变更了几个状态无关。**
   `M0`（4 次 legacy 变更 + 1 draw）= 121.6µs，与 `M3`（1 次切换 + 1 draw）= 120.7µs **相同**。

## 1. 关键对照表（N=1000，同一次会话）

| 模式 | 循环体做的事 | 切换 | draw | **map_p50** |
|---|---|---|---|---|
| **M1** | 状态设一次，只画 | 0 | 1000 | **2.640 ms** |
| **M9** | **先 1000 次切换，再 1000 个 draw** | 1000 | 1000 | **2.640 ms** |
| **M10** | **先 1000 个 draw，再 1000 次切换** | 1000 | 1000 | **2.759 ms** |
| **M8** | 1000 次切换，最后只画 1 个 | 1000 | 1 | **2.621 ms** |
| **M3** | **切换 ↔ draw 交替相邻** | 1000 | 1000 | **123.350 ms** |

**切换全是 1000 次，draw 全是 1000 个。唯一的差别是"是否相邻"。**
**结果：不相邻 = 免费；相邻 = 121µs × 1000。**

## 2. 按次计费，且与 draw 总数无关（M7）

固定 **1000 个 draw**，只在中间均匀插入 `c` 次"切换 + 紧跟 draw"：

| c（切换次数） | map_p50 | 增量 / c |
|---|---|---|
| 0 | 2.635 ms | — |
| 1 | 2.626 ms | — |
| 2 | 2.741 ms | — |
| 5 | 3.127 ms | 98 µs |
| 10 | 3.735 ms | 110 µs |
| 20 | 4.948 ms | 116 µs |
| 50 | 8.600 ms | 119 µs |
| 100 | 14.691 ms | 121 µs |
| **124** | **17.603 ms** | **121 µs** |
| 200 | 26.883 ms | 121 µs |
| 500 | 63.120 ms | 121 µs |
| 1000 | 123.360 ms | 121 µs |

**从 c≥5 起逼近 121 µs 上限（见 §3ter 的细扫），c=1 时完全免费。**
（c 很小时偏离，是因为 2~5 次切换的代价被帧间噪声淹没。）

### 2.1 一个反直觉的点：draw 总数完全不影响

`c=0` 时 1000 个 draw = 2.635ms；`c=100` 时 1000 个 draw = 14.691ms。
**draw 数量一样，只多了 100 次"切换+draw"配对，就多 12ms。**

⇒ **代价是"配对"这个事件，不是 draw 的工作量。**

## 3. 一个"带前置状态变更的 draw" = 121µs，与变更几次无关

| 模式 | 每次迭代里的状态变更 | 每次迭代成本 |
|---|---|---|
| **M0** | `glLoadIdentity` + `glTranslatef` + `glScalef` + `glColor3f`（**4 次**） | **121.6 µs** |
| **M3** | `glUseProgram`（**1 次**） | **120.7 µs** |
| **M6** | `glUseProgram` 切到**同一个** program | **121.0 µs** |
| M2 | `glUniform3f`（**1 次**） | 0.041 µs |
| M1 | 无 | 0.020 µs |

**M0 和 M3 一样贵，尽管一个变 4 个状态、一个只变 1 个。**

⇒ **不是"每次状态变更 30µs × 4 = 120µs"**（那是报告 75 的推测，**错**），
而是**"一次 draw 带了 ≥1 个前置状态变更"就付 121µs**。变更 1 个还是 4 个，价格一样。

### 3.1 M6 的附加信息：驱动不做 no-op 检测

`glUseProgram(prog)` 在已经 `UseProgram(prog)` 的情况下再调一次，**实测仍是 121µs**。
⇒ 驱动**不比较新旧值**，只要有调用就当变更。

### 3.2 M2 的附加信息：uniform 不触发

`glUniform3f` 每次改颜色，**0.041µs**，与不变更几乎相同。
⇒ 驱动把 uniform 合并进了 draw 的参数块，**不打断批处理**。

**这是很重要的区分**：状态分两类
- **打断批处理的**：`glUseProgram` / `glBindFramebuffer` / `glBindTexture` / legacy 矩阵与颜色
- **不打断的**：`glUniform*`

## 3bis. N87-D：121µs 与几何/填充**完全无关**（把"提交代价"钉死）

把 M3 的 quad 从 `-s 0.01`（19×19 像素）缩到 `-s 0.0008`（约 1.5×1.5 像素，**面积 ÷160**）：

| quad 半边长 | 近似像素 | map_p50 |
|---|---|---|
| 0.01 | 19×19 ≈ 361 px | **123.265 ms** |
| 0.0008 | 1.5×1.5 ≈ 2 px | **123.287 ms** |

**差 0.02%（22 微秒 / 123 毫秒）。**

⇒ 那 121µs **既不是光栅化、也不是顶点处理、也不是带宽**。
**是一个固定的事件代价：只要"状态变更 + draw"成对出现，就付一次。**

## 3ter. N87-B：小批量有"起步优惠"，c ≈ 40 后饱和到 121µs

M7 细扫（固定 1000 个 draw）：

| c | map_p50 | 相对 c=0 的增量 | 边际成本 |
|---|---|---|---|
| 0 | 2.640 | — | — |
| **1** | **2.625** | **−15 µs** | **免费** |
| 2 | 2.741 | +101 µs | 101 µs |
| 3 | 2.864 | +224 µs | 112 µs |
| 5 | 3.111 | +471 µs | 118 µs |
| 8 | 3.476 | +836 µs | 120 µs |
| 10 | 3.725 | +1085 µs | 121 µs |
| 20 | 4.941 | +2301 µs | 121 µs |
| 40 | 7.375 | +4735 µs | 119 µs |
| 60 | 9.808 | +7168 µs | 120 µs |
| 1000 | 123.360 | +120720 µs | 121 µs |

**两个细节：**

1. **`c=1` 完全免费**（2.625 < 2.640 的基线）。单次"切换+draw"能被当前批次吸收。
2. **从 c=2 开始收费，c≈5 后就逼近 118~121µs 的上限**，到 1000 次仍是 121µs。
   ⇒ **不是"每次新批次有固定成本"，而是"每次越过批处理边界付一次"，且一旦频繁就越无优惠。**

这暗示驱动有**双缓冲的批处理**：第一组状态变更能进当前 batch，第二组起必须开新 batch。

## 4. 机制（这是本轮真正找到的东西）

```
状态变更 → 紧跟 draw   ⇒  121 µs     ← 必须让新状态在 GPU 侧落地，一次独立提交
状态变更 → 没有 draw   ⇒  0          ← 驱动安全丢弃（下帧会重设）
draw（状态不变）        ⇒  0.02 µs   ← 走批量提交，几乎免费
```

### 4.1 为什么"不相邻就免费"是合理的

`M9` 的顺序是：切 1000 次 → 画 1000 个。
那 1000 次切换里，只有**最后一次**对结果有影响，前 999 次是死代码。
**驱动有充分理由把它们全部丢弃** —— 而且它显然做到了（2.640ms = M1 的水平）。

**所以 M9 的"免费"不代表"切换很便宜"，而代表"驱动有能力把无效切换合并掉"。**

一旦每次切换后面跟一个 draw（`M3`），**每次切换都变成"有效"**，无法合并，
于是每次都要走完整的状态落地路径。

### 4.2 这解释了为什么"draw call 便宜"和"状态变更贵"能同时成立

- **同一个状态画 1000 个物体**：0.02µs/个，总量 0.02ms。
- **换 1000 次状态各画 1 个物体**：121µs/次，总量 121ms。

**同样的 1000 个 draw，差 6000 倍。** 差别全在"状态有没有变"。
### 4.3 ★ 这 121µs 在 GPU 侧，不在 CPU 侧

同一批数据里 `submit`（CPU 提交这 1000 次切换+draw 的时间）与 `map`（等 GPU 落地）的对比：

| 模式 | submit（CPU） | map（等 GPU） | 每对 CPU | 每对 GPU |
|---|---|---|---|---|
| M1（不切换） | 0.038 ms | 2.637 ms | 0.04 µs | 0.02 µs |
| **M3（切换+draw 交替）** | **1.471 ms** | **123.254 ms** | **1.47 µs** | **121 µs** |
| M4（切 FBO） | 4.114 ms | 121.586 ms | 4.11 µs | 119 µs |
| M5（切纹理） | 0.137 ms | 123.934 ms | 0.14 µs | 124 µs |

**CPU 侧每对只要 0.14~4.11 µs，GPU 侧要 119~124 µs —— 差 30~900 倍。**

⇒ 那 121µs **不是 CPU 在做什么，是 GPU 每接受一次"带状态变更的 draw"就要花的时间**。
按 1911 MHz 算，121µs ≈ **23 万个 GPU 周期**处理一个 quad（2 像素！）。

**这个量级只可能是"重新配置管线 + 启动新批次"的固定流程，不可能是几何或填充。**

> 附带：M4（切 FBO）的 CPU 侧明显更贵（4.11µs vs 1.47µs），因为切 drawable 要改渲染目标绑定。
> 但它 GPU 侧与 M3/M5 相同（119~124µs）⇒ **GPU 侧走的是同一条路**。

## 5. 用 121µs 重算 Heaven

```
Heaven HIGH  T_land          35.05 ms
减纯回读（M1 的 N=0，8.29MiB） −2.61 ms
──────────────────────────────────
待解释                       32.44 ms

32.44 ms ÷ 121 µs = 268 次「状态变更 + draw」配对 / 帧
```

**268 次/帧** 对 Heaven 这种场景（每个材质要 `glUseProgram` + `glBindTexture`，
每个 pass 要 `glBindFramebuffer`，加阴影/后处理/UI）是**合理的**。

### 5.1 与所有旧结论的相容性

| 旧结论 | 用"配对 121µs"解释 |
|---|---|
| 报告 56：`T_land = 20.39 + 1.335×MiB`，截距与像素无关 | ✅ 配对数与分辨率无关 |
| 报告 73：Heaven **LOW↔HIGH 只差 25%** | ✅ 画质改 shader 内容，**不改 pass/材质数** |
| 报告 73：glxgears **3.0ms** | ✅ 它用**显示列表**，状态在列表里预编译，每帧只 5 次 `glCallList` |
| 报告 07：**~1000 次 GL 调用/帧、26µs/次** | ✅ 26µs 是"混合平均"（其中约 268 次是 121µs 的配对，其余是廉价调用） |
| 报告 62：19ms 窗口内**零 GPU 提交** | ✅ 命令攒在用户态批处理里，只在状态变更点落地 |
| 报告 59/72：autosleep 关掉后 `map` 涨 30ms | ✅ `map` 等的是这 268 次落地完成 |
| 报告 75：三种切换成本相同 | ✅ 它们都属同一类"打断批处理"的变更，走同一路径 |

### 5.2 一个可检验的预测

515 的 `T_land = 11.00ms`。若 Heaven 的配对数也是 268 次/帧：

```
(11.00 − 2.61) ms ÷ 268 = 31.3 µs / 配对
```

**⇒ 预测：515 上 `n83a -M 3 -n 1000` 应给出 map ≈ 2.6 + 1000×0.0313 ≈ 34ms**
（525 是 123ms）。

**这个数字是可以直接测的，而且是硬判据。** 见 §7 N87-A。

## 6. 三条对自己的更正

### 6.1 报告 75 的 265µs 作废

| | 报告 75（11:29） | 本轮（11:42，连跑三次） |
|---|---|---|
| M3 N=0 | 3.379 ms | **2.653 / 2.653 / —** |
| M3 N=1000 | 268.738 ms | **123.220 / 123.495 / 123.439 ms** |
| GPU | 未记录 | 1911 MHz / 40°C / 37 W（全程恒定） |

**`N=0` 就偏大 27%，说明不是 M3 特有，而是整批采集环境有竞争。**
⇒ M3/M4/M5 的 265/254/260µs **整批作废**，真值统一为 **≈121µs**。

（M0/M1/M2 是更早一批采的，其 `N=0` 为 2.610，与现在 2.64 一致，**数据可信**。）

### 6.2 报告 75 的"30.4µs/状态"是错的推导

报告 75 写：
```
121.6 µs / 4 次 legacy 状态 ≈ 30.4 µs / legacy 状态调用
```
**这个除法没有依据。** 本轮 M0（4 次变更）与 M3（1 次变更）**总价相同**，
证明代价不是"每次变更累加"，而是"每个带变更的 draw 一次付清"。

### 6.3 报告 75 的"三种切换成本相同 ⇒ 通用惩罚"结论方向对，但数字错

方向仍成立（都是同一路径），但**证据从"265/254/260 三者相等"变成
"M0(4 次变更)=121.6、M3(1 次)=120.7、M6(no-op)=121.0 三者相等"** ——
**后者更强**：它证明"变更几个"不重要，"有没有变更"才重要。
