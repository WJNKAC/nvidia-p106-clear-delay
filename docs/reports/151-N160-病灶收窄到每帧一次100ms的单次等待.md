## 1. 硬证据一：79.5% 墙钟在退避函数里（自带计数器）

`0x15761b0` 尾部有一条 `add [r13+0x6f88], rax`——**它自己就在累积自己的耗时**（µs）。
读两次即可直接得到占比，不需要任何探针估算：

| 时刻 | `[ctx+0x6f88]` (µs) |
|---|---|
| T1 = 22890.832 | 2,383,596 |
| T2 = 22893.846（+3.013 s） | 4,779,900 |
| **Δ** | **2,396,304 µs** |

**Δ / 墙钟 = 2,396,304 / 3,013,000 = 79.5%**

旁证：同一次读取的 `[ctx+0x6fb0]` 两次差 3,052,986，而墙钟是 3.013 s
⇒ **单位确实是 µs**，换算无误。

**独立交叉验证**：`rpsample2` 采样 3000 次，2390 次（79.6%）停在 `sched_yield` 内。
**79.5% 与 79.6% 来自完全不同的两种方法（自带计数器 vs 随机采样），互相吻合。**

---

## 2. 硬证据二：只有一个热调用者

用 `whocalls`（采样 + 按已知栈帧布局回溯一帧）追踪 `0x15761b0` 的调用者：

```
样本 4000，落在 target 内 3238 次（81%）

落在 target 内的位置（=它停在哪儿）：
    3101  glcore+0x15762a2      ← call [rbp+0x288] 之后（即 sched_yield 里）
      21  glcore+0x157622d
      14  glcore+0x1576227
      ...

target 的调用者（回溯一帧）：
    3233  glcore+0x15782e5      ← 唯一热调用者
       3  other 0x55fc7872c100
       2  other 0
```

`0x15782e5` 就是 `0x1578280`（"等空间"函数）里 `call 0x15761b0`（位于 `0x15782e0`）
的**下一条指令**。

**⇒ 全部 79.5% 的时间，都花在这一个调用点上。**

## 3. 硬证据三：每帧只有 1 次，但这一次耗掉 ~100 ms

`bpcount` 对 `0x1578280` 入口计数（2 秒窗口，两次独立测量一致）：

```
0x1578280  命中 8 次 / 1.00s = 8.0 次/秒
0x1578280  命中 16 次 / 2.00s = 8.0 次/秒
```

同一次运行 `fps = 7.87` ⇒ **8 / 7.87 ≈ 1.02 次/帧**。

> 这个数可信，因为 8 次/秒 **远低于** `bpcount` 的饱和上限（约 3,000 次/秒），
> 不存在报告 149/150 里那种"把工具上限当被测值"的问题。

于是：

```
127 ms/帧 × 79.5% ≈ 101 ms  ← 一帧里这一次等待的时长
```

**一次等待 ≈ 100 ms，而不是 1000 次 × 122 µs。**

### 3.1 这与 M3 的程序结构正好对上

n83b 的 M3 每帧结构是：1000 对 (绑定, draw) → 1 次 swap → `glReadPixels` → **`glMapBuffer`**。

`glMapBuffer` 是唯一的"等 GPU 完成"点，**每帧正好一次**。

⇒ **我们测到的这个等待，就是 `glMapBuffer` 的同步**。
M3 的 127 ms 里，约 101 ms 是 `glMapBuffer` 在等 GPU 把这一帧的 1000 对干完。

### 3.2 而 M1 的同一个 `glMapBuffer` 只等 7 ms

| | 提交内容 | `glMapBuffer` 等多久 |
|---|---|---|
| M1 | 1000 次 draw（不绑定） | **7 ms** |
| M3 | 1000 对（绑定 + draw） | **101 ms** |

**同一个函数、同一个调用点、同一份代码，等的时长差 14 倍。**
差别只在于"GPU 那一侧要执行什么"。

## 4. 硬证据四：等待期间 GPU 的 rp 完全冻结

在退避入口 `0x15782d8` 下断点，取 30 个连续样本，带时间戳：

```
样本 1   t=22838.644380   req=148  rp=145  wp=150
样本 2   t=22838.644681   req=148  rp=145  wp=150
...
样本 30  t=22838.652610   req=148  rp=145  wp=150
```

**跨 8.2 ms，三个值一个都没动。**（单次采样间隔 0.29 ms 是 ptrace 往返开销，非循环周期）

`rp` 是通过 `0x1569f10` → `0x1575990` → **`mov eax,[rax]`（BAR2/3+0xba0）** 真读硬件得到的
（报告 149 已确认 `[ctx+0x21c]=0`，不走缓存）。所以 `rp=145` 就是硬件当前值。

**⇒ GPU 在这 8.2 ms 里一格都没有前进。**

### 4.1 而且采样能抓到那条 MMIO 读指令本身

`rpsample2` 的 RIP 热点里出现 **`glcore+0x15759be`**（9 个样本）——
那正是 `0x15759bc` 的 `mov eax,[rax]` 的第 3 个字节。

**⇒ CPU 确实物理停在这条 BAR 读上**，不是软件层面在空转。

## 5. 所以整幅图现在是这样

```
每帧：
  CPU 提交 1000 对 (绑定, draw)  —— 只要 2 ms（报告 147 的 -R 实测）
  ↓
  glMapBuffer 要等 GPU 把这一帧干完
  ↓
  进入 0x1578280 的重试循环：
      等 20 µs  →  读一次 rp  →  还不够  →  再等 ...
  ↓
  这一次循环持续约 100 ms（占全帧 79.5%）
  ↓
  GPU 在这 100 ms 里的状态：rp 冻结、功耗 ≈ 空闲（37.42 W vs 空闲 36.28 W）
```

**关键矛盾**：CPU 只提交了 2 ms 的命令，GPU 却要 100 ms 才说"我干完了"，而期间功耗等于待机。

### 5.1 唯一自洽的解释

> GPU 不是在"算"，而是在**反复停等**。
> 1000 对 (绑定, draw) 里，每一对都让 GPU 做一次"管道排空 / 等空闲"，
> 每次排空的延迟约 100 µs，期间计算单元无事可做（所以功耗≈待机）。
> 1000 对 × 100 µs ≈ 100 ms。

这条解释与所有已确立的观测一致：

| 观测 | 如何解释 |
|---|---|
| 每次绑定固定 122 µs（报告 136） | ≈ 一次排空延迟 |
| 与分辨率、对象类型无关（136） | 排空与画什么无关 |
| M8（1000 绑 + 1 draw）= 2.97 ms | 前面没有 draw，无需排空 |
| M9/M10（绑定与 draw 分开）快 | 排空被合并到帧末 |
| M1（只 draw）快 | 没有状态写入，无需排空 |
| GPU 功耗 +1.1 W（147） | 排空期间不计算 |
| `-R` 快 63 倍（147） | 不等完成就看不到这 100 ms |
| 切断等待 → `chk=0`（150） | `glMapBuffer` 立即返回，GPU 还没画完 |
| 515 每帧只等 6.7 次（150） | 515 内联状态，不需要排空 |
| 515 每帧 6,653 条 `0xA140` inline 写（140/145） | 内联写不需要排空 |

## 6. 下一步（唯一该做的三件事，按顺序）

### ① 确认「每对之间真的有排空」——直接看命令流

这是现在唯一的缺口。要做的只有一件：**把 1000 对里相邻两对之间的命令 dump 出来**，
找有没有 "wait for idle / sync point / semaphore acquire" 这类命令。

工具已有一半（`wk/dump_pb.py`），但它解出来的还是顶点数据——**命令头判据没收敛**。
必须先修好它。最小可行判据：

- 命令字数 `w`：`op = w>>29 ∈ {1}`（INC_METHOD），`sub = (w>>13)&7 <= 7`，
  `cnt = (w>>16)&0x1fff` 且后续 `cnt` 个参数位置也满足同样约束
- **从 CPU 写指针 `[ctx+0x1130]` 反推**：`wp` 是"下一条命令的写入位置"，
  所以从 `wp - 0x200` 往前回溯，用"倒推 + 正推一致性"校验，比盲扫可靠得多

### ② 如果 ① 找到排空命令：定位它是谁插入的

判据：看那条命令的 method 号，对照 `cla*` 头文件（`0x902D` = 3D class 的方法空间）。
然后在 glcore 里搜这个立即数，找生成点，再对比 515 的同一位置为何不插。

### ③ 工程上的临时缓解（不需要改命令流）

既然 `glMapBuffer` 是唯一同步点，而 515 证明"晚一点同步"没问题：
**改成异步回读**——这一帧 map 上一帧已经完成的 PBO。
- 帧率会接近 `-R`（因为不等当前帧）
- 数据仍然正确（只是延迟一帧）
- `chk` 会低一帧的相位，但这是合法用法，不是作弊

这条不依赖 ① ② 的结论，可以立刻做，并且能直接回答"用户实际能拿到多少 fps"。

## 7. 本轮方法论收获（已写入 SKILL 70）

### 7.1 让被测对象自己报告，比外部估算可靠

`0x15761b0` 里有 `add [ctx+0x6f88], rax`——**函数自己在累计自己的耗时**。
读两次相减，就得到精确的占空比，而且：
- 不受 ptrace 限速影响
- 不受"分子分母条件不同"影响
- 可以与采样法交叉验证（本次 79.5% vs 79.6%）

**排查性能时，先去反汇编里找"统计计数器"（`add [ctx+X], elapsed` 这类模式），
往往有现成的、无干扰的、高精度的答案。**

### 7.2 追调用者要用栈回溯，不要数调用点

20 个调用点里只有 1 个热，靠静态数不出来（都有可能是热点）。
按**已知帧布局**回溯一帧，一次就定位到 `0x15782e5`。

前提是先确认帧布局：
```asm
entry:  [rsp0] = 返回地址
push r14,r13,r12,rbp,rbx   ; 5×8 = 0x28
sub  rsp,0x10              ; 0x10
⇒ 在函数体内，调用者返回地址在 [rsp+0x38]
⇒ 若已停在它调用的更深函数里（又 push 了返回地址），则在 [rsp+0x40]
```

### 7.3 用 `[rsp]` 而不是 `rip` 做触发条件

79% 的样本停在 `sched_yield`（在 libc 里），只看 `rip` 落在 glcore 目标范围内会漏掉 99% 的信号。
改成"`rip` 在目标内 **或** `[rsp]` 指回目标"之后，命中数从 15/3000 变成 3238/4000。

### 7.4 一次等待 100 ms ≠ 一次等待 122 µs × 1000

我前几轮一直默认"每对等一次"，从没验证过"等了多少次"。
`bpcount` 得到 8 次/秒（≈1 次/帧）之后，整个图景完全变了：
**不是 1000 次小等待，而是 1 次大等待。**

教训：**先测"次数"，再谈"每次多久"。** 顺序反了会构造出错误的模型。

## 8. 命令流 A/B：M1 每 draw 3 条，M3 每对 16 条（已解码成功）

修好了 pushbuffer 解码器（`analysis/tools/pbdump.py`）。之前失败的判据问题是
**允许 `cnt=0`**，于是把全零字当成合法命令头。可用判据（沿用报告 140 那版）：

```python
op  = w >> 29                # 必须 ∈ {0,1}
cnt = (w >> 16) & 0x1fff     # 必须 1 <= cnt <= 256   ← 关键是 cnt >= 1
sub = (w >> 13) & 0x7
meth= (w & 0x1fff) << 2
```
锚点：`struct.pack("<II", 0x2001c00d, 0x70000000)` 出现在哪个 `nvidiactl` 映射里，
再用"30 ms 内变化字数最多"筛出活跃 pushbuffer。

### 8.1 M1（8 ms）vs M3（127 ms），同样的 `-n 8`

**M1 每个 draw 只有 3 条：**
```
0x34a8  0x80000000
0x1618  0x5          ← BEGIN（NV9097_BEGIN，draw 起始）
0x0d74  0x0 0x4      ← SET_VERTEX_ARRAY_START
```

**M3 每个 (绑定, draw) 对约 16 条：**
```
0x34a8 0x80000000        0x1450 0x400008   ← SET_PS_WARP_WATERMARKS
0x3998 0xf0              0x196c 0x0        ← SET_ZCULL_BOUNDS
0x1688 0x0               0x13a8 0x11111111 ← SET_PS_SATURATE
0x39d0 0x20              0x37c  0x1        ← SET_RASTER_ENABLE
0x2144 0x30              0x39d0 0x20
0x2490 0x10              0x2044 0x430
0x360  0x20164010 0x20   0x2410 0x10       ← SET_SUBTILING_PERF_KNOB_A
0x2600 0x1               0x228  0x1        ← FLUSH_AND_INVALIDATE_ROP_MINI_CACHE
0x1618 0x5               0xd74  0x0 0x4    ← BEGIN + 顶点
```

方法名来自 OKM 的 `src/common/sdk/nvidia/inc/class/`（class 0x9097 = Tesla/Pascal 3D）。

**所以 M3 每对多写 13 条状态命令**，其中 `SET_PS_WARP_WATERMARKS`、
`SET_SUBTILING_PERF_KNOB_A`、`SET_ZCULL_BOUNDS`、`SET_PS_SATURATE`、`SET_RASTER_ENABLE`
都是**上下文寄存器**——这类寄存器在 Pascal 上通常需要管道排空才生效。

### 8.2 但接着做了 515 的对照，这个解释被推翻了

**515 的 M3 命令流（同参数 `-n 8`）几乎一模一样：**

| 525 | 515 |
|---|---|
| `0x34a8 0x80000000` | `0x34a8 0x80000000` |
| `0x3998 0xf0` | **（无）** |
| `0x1688 0x0` | `0x1688 0x0` |
| `0x39d0 0x20` | `0x39c0 0x20` ← 同一个功能，method 差 0x10 |
| `0x2144 0x30` | `0x2144 0x30` |
| `0x2490 0x10` | `0x2490 0x10` |
| `0x360 0x20164010 0x20` | `0x360 0x20164010 0x20` |
| `0x1450 0x400008` | `0x1450 0x400008` |
| `0x196c 0x0` | `0x196c 0x0` |
| `0x13a8 0x11111111` | `0x13a8 0x11111111` |
| `0x37c 0x1` | `0x37c 0x1` |
| `0x2044 0x430` / `0x2410 0x10` | `0x2044 0x430` / `0x2410 0x10` |
| `0x2600 0x1` / `0x228 0x1` | `0x2600 0x1` / `0x228 0x1` |

525 只是把 515 的 `0x39c0` 拆成了 `0x3998` + `0x39d0`（一条变两条）。

## 9. 最后一个对照：CPU 侧两版完全同构

在 515 上测同一组函数（同样的 n83b 参数）：

| | 等空间函数入口 | 退避循环内调用 | fps |
|---|---|---|---|
| **525** | `0x1578280` = **8 次/秒 ≈ 1.02 次/帧** | `0x15761b0` ≈ 145k/秒（饱和） | 7.87 |
| **515** | `0xfbed80` = **186 次/秒 ≈ 1.40 次/帧** | `0xfbede0` ≈ 141k/秒（饱和） | 133 |

**两版都是"每帧约 1 次等待"，都在 `glMapBuffer` 那个点，CPU 侧结构完全一样。**

区别只在"这一次等多久"：

```
515：帧 7.5 ms，其中等待约 5 ms   → GPU 把这一帧干完要 5 ms
525：帧 127 ms，其中等待约 101 ms → GPU 把这一帧干完要 101 ms
```

## 10. 所以现在的结论是（与之前所有报告都不同）

```
① CPU 提交量        相同（两版都 2 ms 级，报告 147 的 -R）
② CPU 等待结构      相同（都每帧 1 次，都在这一个函数里）
③ 命令流内容        几乎相同（只有 1 条方法被拆分，1 个参数不同）
④ GPU 执行同样流    → 525 慢 17~23 倍
⑤ 期间 GPU 功耗     ≈ 空闲（+1.1 W）
```

**⇒ 病灶在"GPU 执行同一条命令流的速度"，不在 CPU，也不在命令内容。**

这解释了为什么前面所有 CPU 侧尝试（改退避、删函数、伪造 fence）全部无效，
也解释了两版反汇编几乎逐条同构却差 20 倍。

**剩下的唯一可能：GPU 的某种"上下文状态"在 525 下被配成了慢速模式**
（例如上下文切换粒度、ZCull/ROP 的行为、某个 perf knob），
使得同样的状态切换要付更高的代价。

## 11. 下一步（非常具体，两条）

### ① 逐个对照两版命令流里的"参数差异"

已经看到一处：`0x800` 的参数 **525 = `0xe00000`，515 = `0x800000`**。
`0x800` 在 `cl902d.h` 里是 `SET_PIXELS_FROM_CPU_DATA_TYPE`，但这里的用法
（`cnt=2`，第二个参数是 32 位值）更像是"某个 buffer 的大小/上限"。

**做法**：写个脚本把两版完整命令流的 (sub, meth, args) 做多重集合差分，
列出所有"方法相同但参数不同"的项。这是纯静态 + 一次 dump，很便宜。

### ② 检查两版的"上下文切换相关"初始化

候选字段（都在 n83d 能从运行时读到）：
- `[ctx+0x22f2c]` 引擎数（已知都是 1）
- `[ctx+0x5ad]` bit1（`0x1577a90` 里 `test byte [rdi+0x5ad],2`，决定是否走时间检查分支）
- `[ctx+0x22edc]`（`0x1577a90` 里参与 `imul eax, 0xfa` 计算，像"超时倍数"）
- `[ctx+0x6fc0]` / `[ctx+0x6fc8]`（同上函数里的时间比较阈值）

**判据**：两版逐个读值，凡是不相同的，就是"被配成慢速"的嫌疑字段。

## 13. 完整命令流差分结果（两版各 6000 条）

把两版 M3（`-n 8`）的完整 pushbuffer 各解 6000 条，做多重集合差分：

### 13.1 方法集合

| | 数量 |
|---|---|
| **515 独有的方法** | **1 个**：`sub0:0x39c0` |
| **525 独有的方法** | **2 个**：`sub0:0x3998`、`sub0:0x39d0` |
| **计数差 > 1.5 倍的方法** | **0 个** |

⇒ **两版命令流的成分几乎完全一致**，只差"一条方法被拆成两条"。

### 13.2 参数差异

| 方法 | 515 | 525 | 出现次数 |
|---|---|---|---|
| `sub0 0x800`（cnt=2） | `0x1, 0x800000` | `0x1, 0xe00000` | **各 1 次（初始化）** |
| `sub0 0x1b00`（inline data） | 地址/长度不同 | 地址/长度不同 | 内容本就该不同 |
| `sub6 0x0010` | 地址/长度不同 | 地址/长度不同 | 同上 |

`0x800`/`0x804` 在 `cl902d.h` 里是 `SET_PIXELS_FROM_CPU_DATA_TYPE` /
`SET_PIXELS_FROM_CPU_COLOR_FORMAT`。**但这条命令每版只出现 1 次（初始化阶段），
不在每对的循环里，所以它解释不了"每对 100 µs"。**

### 13.3 这个差分结果的意义

**它把"命令内容不同"这条也排除了。**

原本最有希望的解释是"525 每对多插了需要管道排空的命令"。
差分证明：两版每对写的状态寄存器**是同一套**（`0x1688` / `0x39c0` /
`0x2144` / `0x2490` / `0x360` / `0x1450` / `0x196c` / `0x13a8` / `0x37c` /
`0x2600` / `0x228` / `0x1618` / `0xd74` + `0x34a8`），顺序也一致。

⇒ **同样的命令，525 的 GPU 要花 17~23 倍时间执行。**

## 15. 下一步：往 GPU 状态上找，而不是往代码上找

既然命令一样、CPU 一样，那只能是 **GPU 的某种状态在 525 下不同**。可查的入口：

### ① 两版的 GPU 时钟/电源状态是否不同

`nvidia-smi --query-gpu=clocks.gr,clocks.sm,clocks.mem,pstate` 在两个版本下各采一次。
若 525 下 SM 时钟更低，就直接解释了"同样命令更慢"。

> 之前测过 M3 时 SM 时钟 = 1911 MHz（与空闲相同），但那是在同一版本内对比。
> **两版之间的对比还没做过**——这是最便宜、最该先做的一项。

### ② `[ctx+0x22edc]` 与 `[ctx+0x5ad]`

`0x1577a90`（采样里的次热点）里：`imul eax, [rbx+0x22edc], 0xfa`（乘 250），
像是"超时/退避倍数"。`test byte [rdi+0x5ad], 2` 决定是否走时间检查分支。
**两版各读一次，不同就是嫌疑。**

### ③ 检查 525 是否在每次 draw 后插入了隐式的 "wait for idle"

命令流里没看到显式的 `WAIT_FOR_IDLE`(0x110)。
但 Pascal 的上下文切换可以由 **host 侧的 semaphore / method 缓冲**触发，
不在这个 pushbuffer 里。可以查 sub7（`0xC197`，未知类）的 `0x7fc0` 命令——
它在每帧开头出现一次，参数 `0x2004c004`，值得查它是什么。

## 17. GPU 时钟/降频也已排除

525 M3 运行中实测（3 次采样一致）：

```
空闲    : P0, SM 1911 MHz, mem 4006 MHz, 36.29 W, 35 °C
M3 运行 : P0, SM 1911 MHz, mem 4006 MHz, 37.47 / 37.42 / 37.50 W, 35 °C
降频原因: 0x0000000000000000  (sw_power_cap / hw_slowdown / hw_thermal 全部 Not Active)
```

- **P0 = 最高性能档**
- **SM 与显存都是满频**
- **没有任何降频原因**
- 温度只有 35 °C

**⇒ "525 把 GPU 降频了"这条排除。**

而且注意这个组合本身很反常：**满频 + 满负载命令流 + 只有 +1.2 W 超空闲**。
说明 SM 在 95% 以上的时间里**没有在执行任何着色器**。

## 18. 最终收敛的结论（本轮终点）

把所有证据叠在一起，只剩一个自洽的图像：

```
每帧：
  CPU 2 ms 提交完 1000 对（命令流与 515 几乎逐条相同）
  ↓
  glMapBuffer 等 GPU 把这一帧干完（79.5% 墙钟在这一次等待里）
  ↓
  等待期间：GPU 满频、不降频、无 Xid、功耗≈空闲、rp 冻结
  ↓
  105 ms 过去，GPU 才说"完成"
```

**⇒ 525 下，GPU 在每两对 (绑定, draw) 之间都要停一次，
停的时候满频空转、不计算，单次停约 100 µs。**

以现在掌握的手段（用户态 + 静态反汇编），已经看不到更深的一层了，
因为**停止是 GPU 硬件的行为，不在 user-space 代码里**。
要看穿它，需要内核侧视角（RM 是否在每对之间插入 semaphore/context switch）。

### 18.1 工程上现在能做的（不依赖弄清硬件行为）

| 方案 | 预期 | 风险 |
|---|---|---|
| **异步回读**（map 上一帧的 PBO） | 帧率接近 `-R`（~500 fps 提交侧），数据延迟一帧但正确 | 低，是标准做法 |
| 恢复 515 的驱动 | 5.46 ms / 133 fps | 与目标版本冲突 |
| 关掉 525 的逐对同步（`0x157830c` 补丁） | 2 ms，但 `chk=0` | **不可用** |

**结论：在 525 上要拿到"快且正确"，唯一不依赖硬件内部行为的办法是
"不等当前帧、改为等上一帧"** —— 即异步回读。

### 18.2 若还要继续追根因

下一层要看的是 **RM（内核 `nvidia.ko`）在 guest 侧是否对每个 draw 插入 semaphore**。
判据：`strace`/`nkioctl` 观察 M3 下是否有与"每个 draw"同频的 ioctl 或 doorbell 写。
报告 139 测过稳态 ioctl 只占 0.24%，但那是在 Heaven 上；**n83b M3 上没测过**。

这是唯一还没做的一步，且成本不高（`nkioctl` 现成，`NK_MODE=count` 即可）。

## 19. 内核侧（ioctl）也已排除

用 `nkioctl.so`（`NK_MODE=count`）在 **n83b M3** 上统计（此前只测过 Heaven，没测过 M3）：

```
total_p50=127.324  fps=7.85  chk=400   ← 与基线一致，说明 shim 无扰动

=== nkioctl (1.1s, 438 calls) ===
nr     size  calls  sum_ms  avg_us  max_us
0x2a   32      199   13.90    69.9   12346
0x4a   184      69    8.98   130.2    2175
0x2b   40       32    1.05    32.9     401
0x29   16       22    0.45    20.5      75
其余           116    1.06
------------------------------------------
合计           438   25.6 ms
```

- **438 次 / 1.1 s ≈ 490 次/秒 ≈ 62 次/帧**
- **ioctl 总耗时 25.6 ms / 1100 ms = 2.3% 墙钟**
- 一帧有 **1000 对 (绑定, draw)**，而 ioctl 只有 62 次
  ⇒ **提交根本不经 ioctl，走的是 mmap 门铃写**

**⇒ 内核侧不是瓶颈。** 这一层也排除。

## 21. 本轮最终建议

### ⛔ 如果是工程目标（让 Heaven 在 525 上跑顺）

> **本节已被实验否证，见报告 152。**
>
> 我建议的"异步回读（map 上一帧的 PBO）"**实测无效**：
> PBO 深度 2→8，`map_p50` 全部停在 125~126 ms，fps 恒定 7.89；
> 且 `-R`（完全不等回读）的外部墙钟也是 125 ms/帧。
>
> 原因：`glMapBuffer` 等的是 **GPU 全局完成度**，不是该 PBO 的 fence；
> 而 GPU 的真实吞吐就是 7.99 fps。异步回读只能消除"CPU 被阻塞"，
> 不能消除"GPU 慢"——本项目 GPU 是慢的一方，没有重叠空间。
>
> **在 525 上目前已没有"纯软件、现在就能用"的方案。**
> 唯一指向根因的路径见 §15 补充（inline 路径差异）：`sub6:0x0034` 515 每帧 6,653 条、
> 525 只有 16 条，而 515 的绑定代价是 4.6 µs、525 是 115 µs。

### 如果是研究目标（弄清 122 µs）

已知它**不是软件可改的**。可选：
1. 用 NVPerf SDK / Nsight 抓 P106 的 per-engine stall 计数（需确认矿卡是否放行）
2. 换一张支持 vGPU 的卡（P40/P100），对比 vGPU 下是否同样现象 ——
   若 vGPU 下正常，说明是裸机路径特有的行为
3. 接受"515 可用，525 在此场景有硬件层面退化"作为结论，写进文档

**本轮不再继续猜测。** 12 层实验证据已经足够支撑上面的判断。
