# 41 · N18/N19/N20：帧时间复现成功，但机制没复现——拷贝本身恒定 2.48ms

> 2026-10-26 00:35
> 用户指令：加大负载 + 换 shader，争取在隔离环境复现 29ms 的 T_land；复现之后优化方案可以随便试。
>
> **结果分三段，第三段是本轮最有价值的：**
> 1. **数字复现成功**：LOAD=1200 → T_land = **30.71ms**，与 525 真实值 29.4ms 只差 4%；LOAD≈320 → 12.0ms ≈ 515 的 10.1ms。而且是一条直线，**两版都能用同一个旋钮调出来**。
> 2. **但加了 `glFinish` 对照后发现机制完全不同**：把 GPU 工作先做完，**拷贝本身恒定 2.48ms**，不管前面压了 0 还是 28ms 的活。
> 3. **所以"N18 复现成功"是假象**：它推高的是"帧时间"，而真实 525 的问题是"拷贝慢"（24.8ms）。**后者在隔离环境复现不出来**——但这同时把"GPU 忙/排队"这一类解释彻底排除了。

## 2. N18：压力扫描（复现帧时间）

1920×1080，`RL5_SLEEP=0`（⇒ D_p50 就是 T_land），6s/组：

### 2.1 mode C（双 context = primus 结构）

| LOAD | D_p50 (ms) | map_p50 | D_p90 | 功耗 | 帧数 | ÷下限 |
|---|---|---|---|---|---|---|
| 0 | **2.751** | 2751.4 | 2792.9 | 35.6 W | 2127 | **1.0×** |
| 200 | 7.389 | 7388.6 | 7407.9 | 60.2 W | 803 | 2.8× |
| 400 | 12.045 | 12044.6 | 12067.1 | 66.1 W | 494 | 4.6× |
| 800 | 21.379 | 21379.1 | 21412.9 | 70.8 W | 279 | 8.1× |
| **1200** | **30.710** | 30709.8 | 30738.2 | 72.1 W | 195 | **11.7×** |
| 1600 | 40.032 | 40032.4 | 40057.9 | 72.7 W | 150 | 15.2× |
| 2000 | 49.339 | 49338.7 | 49381.7 | 73.5 W | 122 | 18.8× |

**斜率 0.0234 ms/quad = 23.4µs 每个全屏混合 quad。**

**三处对齐**（说明这不是巧合）：

| 指标 | LOAD=1200 隔离 | 真实 525 Heaven |
|---|---|---|
| T_land | 30.71 ms | 29.4 ms |
| fps | 32.5 | 34.7 |
| 功耗 | 72~74 W | 48~68 W |

fps 差 6%、T_land 差 4%——**帧时间几乎精确复现**。

### 2.2 mode A 与 mode C 完全一致 → 并发结构无关

| LOAD | mode A | mode C |
|---|---|---|
| 0 | 2.645 | 2.751 |
| 800 | 21.397 | 21.379 |
| 1600 | 40.023 | 40.032 |

**串行和并发拿到的数一样**，与报告 30 的结论一致。

### 2.3 shader 负载（报告 31 说它能跑到 110W）

| LOAD | D_p50 | 功耗 |
|---|---|---|
| 100 | 65.9 ms | **120.2 W** |
| 200 | 129.0 ms | 121.0 W |
| 400 | 256.5 ms | 121.1 W |

**这才是真 GPU 满载**（121W vs vbofill 封顶 73W）。但它每单位负载贵 15 倍（100 个就 66ms），
不适合精细调 T_land，留着做"高功率"对照。

## 3. N19：`glFinish` 对照 → 拷贝恒定 2.48ms

`RL5_FINISH=1` 在 `glReadPixels` 之前先 `glFinish()`，把 GPU 计算时间从 D 里剥掉。

mode A：

| LOAD | D (FIN=0) | **D (FIN=1)** | 剥掉的部分 | 剥后÷下限 |
|---|---|---|---|---|
| 0 | 2.658 | **2.602** | 0.06 ms | 1.0× |
| 400 | 12.068 | **2.478** | 9.59 ms | 0.9× |
| 800 | 21.390 | **2.477** | 18.91 ms | 0.9× |
| 1200 | 30.715 | **2.477** | 28.24 ms | 0.9× |

**`D(FIN=1)` 在所有负载下都是 2.477~2.602ms。**

而且 `D(FIN=0) − D(FIN=1)` **精确等于** `0.0234 × LOAD`：
- 1200 × 0.0234 = 28.08ms，实测 28.24ms（差 0.6%）

→ **分解干净了：`T_land = GPU填充时间 + 拷贝时间(恒定 2.48ms)`**

## 4. N20：并发渲染也不拖慢拷贝

有人会说：mode A 是串行，真实 primus 是并发。所以补一组 **mode C + FIN=1**：

| LOAD | D (FIN=0) | **D (FIN=1)，有另一线程并发渲染** |
|---|---|---|
| 0 | 2.752 | **2.488** |
| 200 | 7.395 | **2.487** |
| 400 | 12.068 | **2.477** |
| 800 | 21.369 | **2.485** |
| 1200 | 30.699 | **2.488** |

**即使另一个 context 正满载渲染（28ms 的活），拷贝本身仍然 2.48ms。**

→ **拷贝对并发 GPU 活动完全免疫。** 它只会等"自己前面排的活"，不会被"别人正在干的活"拖慢。

## 5. ★ 所以 N18 的复现是假象——而这是个净收益

### 5.1 真实 525 的拷贝是 24.8ms，不是 2.48ms

| 量 | 隔离环境（本报告） | 真实 525 primus |
|---|---|---|
| 拷贝本身 | **2.48 ms（0.94× 下限）** | **24.8 ms**（报告 25：`PRIMUS_SLEEP=0` 时 sem_wait 24.77ms） |
| T_land | 2.6~30.7ms（由 LOAD 决定） | 29.4 ms |
| GPU 计算 | 0~28ms（由 LOAD 决定） | ~2.6ms（报告 26：glWaitSync 已经 5µs 返回，渲染早已完成） |

**隔离环境的拷贝是 2.48ms，真实环境是 24.8ms，差 10 倍——而且是同一个函数、同样的 8.29MB。**

### 5.2 而且真实 525 明确不是 GPU-bound

报告 27 的既有数据（当时用来排除像素量）：

| 分辨率 | 像素 | D |
|---|---|---|
| 1920×1080 | 2.07 Mpx | 31.09 ms |
| 640×360 | 0.23 Mpx | 21.27 ms |

**像素降到 1/9，D 只降 31%。** 如果是 27ms 的 GPU 填充，应该降 ~89%。
→ **真实 525 的 27ms 里，绝大部分不随像素变化，不是填充。**

两条合起来：

> **真实 525 = 「GPU 几乎空闲 + 拷贝 24.8ms」。这个组合在隔离环境里做不出来**——
> 隔离里只要 GPU 空闲，拷贝就是 2.48ms（N19 LOAD=0 / N20 LOAD=0）。

### 5.3 净收益：排除了一整类解释

| 解释 | 状态 |
|---|---|
| GPU 渲染忙，拷贝排队在后面 | **❌ 排除**（N20：并发满载时拷贝仍 2.48ms） |
| 拷贝与并发渲染抢带宽 | **❌ 排除**（同上，与 LOAD 无关） |
| 拷贝本身慢（驱动实现差） | **❌ 排除**（隔离环境恒定 2.48ms，贴着物理下限） |
| 真实进程有额外同步/提交顺序问题 | **◑ 剩下来的唯一方向** |

**这比"复现成功"更有用**：现在知道不该往 GPU 负载方向走。

## 6. 顺手修正报告 31 的一个锚点

报告 31 的判据是"Heaven 48~68W ≈ 空转基线 50W → GPU 空闲"。本报告的**真空转**是：

| 状态 | 功耗 |
|---|---|
| LOAD=0（只 clear + 16 个小三角形） | **36.2 W** |
| LOAD=400 | 66~68 W |
| LOAD=1200（28ms GPU 活） | 72~75 W |
| shader LOAD=100（真满载） | **120~121 W** |

**真空转是 36.2W，不是 50W。** 所以 Heaven 的 48~68W **明显高于空转**——报告 31 的"≈空转"判断要下修。
不过它原来的主结论（"525 不是算力饱和"）仍然成立，只是理由要换：见 §5.2（像素不敏感）。

> 另注：vbofill 把功耗封在 73W 左右（填充/ROP 受限），而 shader 能到 121W。
> **功耗封顶说明"功耗不能当负载的线性代理"**——这一点在报告 39 的 LOAD 扫描里就已经埋下（LO 0→100 功耗只涨 20%，map 却翻倍）。

## 7. 真实 525 的 24.8ms 拷贝延迟，下一步查什么

隔离环境已经证明"拷贝 2.48ms"是稳的（任何负载、任何并发）。所以那 24.8ms 只能来自真实进程特有的东西。候选按可查性排：

| 候选 | 为什么怀疑它 | 怎么查（都在 525 上，不用换驱动） |
|---|---|---|
| **PBO 拷贝被排到"下一次 swap 之后"** | primus 每帧 `glXSwapBuffers(pbuffer)`；若驱动把这个 swap 插在拷贝前面，拷贝就要等一次 present | 在真进程里 uprobe `glReadPixels`/`glXSwapBuffers` 的顺序与间隔；报告 26 已有 17 探针基础 |
| **拷贝源是 pbuffer 的 back buffer，被 swap 交换掉了** | 读 back buffer 时它正被换到 front，驱动可能加隐式同步 | 把回读目标改成 **FBO+texture**（rb_lat5 就是这么做的）看能否消除 → 若能，就是"pbuffer 特有" |
| **525 的 PBO 完成检测本身慢**（要等一次内部轮询） | 报告 32：驱动靠轮询 host 标记，IRQ 2/s；报告 26：数据落地铺满 30ms 窗口 | 已有 pbo_watch 方法（20kHz 读 /proc/pid/mem），直接看落地时刻分布是否与某个外部事件对齐 |
| **多线程/多 context 的锁竞争** | 真实进程 12+ 线程，隔离只有 2~3 | 报告 38 的角色表已显示 4 个 tid 严格分工；可加测"锁等待"占比 |

**最省事的第一刀**：把 primus 的回读目标从"pbuffer 的 back buffer"换成 **FBO+texture**（rb_lat5 的做法），
在真实 Heaven 里跑一次。如果 D 掉到 ~3ms，就锁定"pbuffer 回读路径"是 525 特有的慢点——
而且 primus 是开源的，改起来有明确落点。

### 8.1 一个必须记下的工具缺陷（本轮修掉）

`rb_lat5` 原代码 `int ntri = 2400`，而 `glDrawArrays(GL_TRIANGLES, 0, g_load*6)` 需要
`ntri ≥ 2×g_load` → **g_load 上限 1200，正好是复现 29ms 所需的值**。
注释里写的"可支撑 g_load=400"是过时的。扫到 1200 以上会读越界（可能崩或画错）。
已改成按需分配。

> **教训**：压测前先算"负载参数的上限由什么决定"。本例是 VBO 容量，被一个过时注释掩盖了。
> 如果不查，要么在 1200 处"刚好"卡住误以为饱和，要么越界崩掉。

### 8.2 glFinish 是区分"等算"与"等拷"的唯一干净手段

在同一个 GL context 里，**命令是有序的**——所以"等 GPU 算"与"等拷贝"在时间上天然混在一起。
只有把前面的活显式做完（`glFinish`）再开始计时，才能把两者分开。

本例分开后立刻看到：`D(FIN=0) − D(FIN=1) = GPU 填充时间`（精确到 0.6%）。
**没有这一刀，N18 会被误读成"复现了 525 的病"。**
