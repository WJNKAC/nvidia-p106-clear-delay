# N185 — 与 dartraiden/NVIDIA-patcher 的方案对比：内核白名单 vs 用户态每批延迟

**日期**：2026-10-27
**来源**：<https://github.com/dartraiden/NVIDIA-patcher/issues/3>
**问题**：他们用什么方法把 40 W 提到 100 W+？和我们的方案是不是一回事？

---

## 0. 结论

**是两个完全不同的方案，作用在不同层、改的是不同的东西：**

| | dartraiden/NVIDIA-patcher | 本项目 |
|---|---|---|
| 改哪个文件 | **内核模块** `nv-kernel.o_binary` | **用户态** `libnvidia-glcore.so` |
| 改什么内容 | GPU **设备 ID 白名单**（把矿卡从列表里抹掉） | **每批次延迟命令**的发射条件跳转 |
| 改几个字节 | 每个 ID 4 字节，P1XX 系列 5 个 | 1–2 字节 |
| 生效方式 | 重建内核模块并重新加载 | 改文件，重启程序即可 |
| 额外操作 | `nvidia-smi -g <id> -dm 0` 切驱动模式（仅 Windows 有效） | 无 |
| 可逆性 | 需要重装驱动 / 重启 | `.orig` 备份，随时 `revert` |

**且实测已证实：两者指向同一套机制，内核侧才是上游。**
只打内核补丁（用户态完全不打）时，性能从 52.202 ms 直接降到 **3.668 ms**，
且那条 `method 0x3998` 命令**完全不发了**（样本 0 条）。**我们的用户态补丁在这个条件下是多余的。**

---

## 1. 他们的方法具体是什么

### 1.1 改的是内核模块里的设备 ID 表

他们在 580.95.05 的 `kernel/nvidia/nv-kernel.o_binary` 里找到一张表，把矿卡的条目替换成哨兵值：

**P1XX 系列**（原文）：

```
原始：07 1B 07 00  87 1B 07 00  C7 1B 07 00  07 1C 07 00  09 1C
替换：FF FF 07 00  FF FF 07 00  FF FF 07 00  FF FF 07 00  FF FF
```

**CMP 系列**也是同样的做法（13 个条目里替换掉其中 8 个）。

解读：这些是 32 位小端整数 `0x00071B07`、`0x00071B87`…

- `0x1B07`、`0x1B87`、`0x1BC7`、`0x1C07`、`0x1C09` —— **正是 P104/P106 系列矿卡的 device ID**
- 前缀 `0x0007` 推测是"家族/类别"标记
- 替换成的 `0x0007FFFF` —— device 部分是 `0xFFFF`（无效值），**等于把该卡从表里抹掉**

### 1.2 我们验证了这张表在本机 580 里存在

在本机 `580.178.04` 的 `nv-kernel.o_binary`（112,677,456 字节）中：

```
命中偏移：0x5cfdfcc
内容：... c2 15 07 00 | 07 1b 07 00 | 87 1b 07 00 | c7 1b 07 00 | 07 1c 07 00 | 09 1c 07 00 | 83 1d 07 00 ...
```

**本机 P106-100 的 device ID = `10DE:1C07`**（`lspci` 实测），
对应的条目 `0x00071C07` 就在这张表里（偏移 `0x5cfdfd8`）。

> **⇒ 表在、卡在表里、位置明确。他们没有说错，这个方法在我们这个版本上同样可定位。**

### 1.3 他们的说法

> "it contains a list of GPUs that are **prohibited from switching to WDDM**"

所以这张表的直接用途是**驱动模式切换限制**（TCC ↔ WDDM），这是 Windows 的概念。
Linux 上 `nvidia-smi -dm 0` 本来就不支持，所以那一步可以忽略。

但实际效果（用户反馈）：

> "The power draw used to be stuck around **40W**, but now that cap seems to have vanished."

**⇒ 在 Linux 上这张表还影响功耗/性能，不只是 WDDM 切换。**

## 2. 两套症状高度相似

| | 他们 | 我们 |
|---|---|---|
| 现象 | 功耗卡在 40 W | 功耗卡在 55–70 W |
| 补丁后 | **100 W+** | **118 W** |
| 帧率 | 未给出具体数字 | 18.96 → 259.79 fps |

**两者补丁后都达到 100 W 以上**，而且我们实测 `nvidia-smi` 的
`Power Limit` 是 **N/A**（没有硬功率墙）。

> **⇒ 40–70 W 这个"卡住"不是功率限制器造成的，而是 GPU 在空转等待。**
> 这一点与我们的结论一致：`0x3998 = 240` 让每个批次都白等 218 µs。

## 3. 核心问题：是不是同一个根因？

### 3.1 两种可能

**假设 A：同一个根因（他们在上游）**

```
内核模块的设备表命中矿卡
    → 内核把该卡标记为"受限 SKU"
    → 用户态 glcore 收到这个标记
    → 置位我们追踪的那个策略位（525 是 +0xc18，580 是 +0x20b）
    → 每批次发射 0x3998 = 240 的延迟
    → GPU 空转，功耗卡在 60 W
```

如果 A 成立：**他们的方案是治本，我们的方案是治标。**
他们改完之后，`0x3998` 应该**根本不发**，我们的补丁就多余了。

**佐证**：我们至今**没找到**那个策略位的置位来源。
搜索"写立即数"只找到 2 处，改了也无效（报告 170）——
说明标志位可能来自**内核上报的属性**，而不是 glcore 内部计算出来的。
这与假设 A 吻合。

**假设 B：两套独立的限制（互补）**

内核白名单管的是"时钟/性能档位"，用户态管的是"每批延迟"。
两者都压性能，但互不相干。
如果 B 成立：两个补丁**同时打**效果最好，我们的补丁仍然必需。

### 3.2 一个偏移支持假设 A 的细节

`0x00071C07` 这张表在 **`.rodata`** 段，而且那一段**没有任何独立符号**
（附近最近的符号 `_nv046220rm` 距离 0xe6624c，说明这块是嵌入的二进制 blob）。

也就是说：**这张表不是普通 C 数组，而是嵌进 blob 的资源数据**，
由固件/资源解析代码消费 —— 这类数据**正是"上报给用户态的能力描述"的典型形态**。

## 4. ★ 验证实验：已完成，假设 A 成立

### 4.1 实验矩阵与结果

| 组 | 用户态补丁 | 内核补丁 | `map_p50` | `fps` | `chk` | `method 0x3998` |
|---|---|---|---|---|---|---|
| ① 基线 | 无 | 无 | **52.202 ms** | 18.98 | 5150 | 40+ 条 |
| **② 只打内核** | **无** | **打** | **3.668 ms** | **243.78** | 5150 | **0 条** |
| ③ 只打用户态 | 打 | 无 | 3.434 ms | 259.79 | 5150 | 0 条 |
| ④ 两个都打 | 打 | 打 | 3.667 ms | 246.64 | 5150 | 0 条 |

**② ≈ ③ ≈ ④，而 ① 是它们的 14 倍。**
**⇒ 假设 A 成立：内核设备白名单是上游原因，用户态每批延迟只是它的下游表现。**

② 与 ④ 几乎完全一致（3.668 vs 3.667），说明**用户态补丁在内核补丁之上没有额外收益**。
③ 略快（3.434），差异在运行间波动范围内，不构成"用户态方案更优"的证据。

### 4.2 关键证据：命令消失了

只打内核补丁时，扫 pushbuffer：

```
method 0x3998  样本 0 条
```

**这是最直接的证据** —— 不是"命令还在但被跳过了"，而是**根本没有生成**。
说明那个策略位（525 的 `+0xc18` / 580 的 `+0x20b`）**从未被置位**，
glcore 走的是另一条分支。

### 4.3 这解释了一个一直没解开的谜

我们在报告 170 里承认过：**找不到那个策略位的置位来源**。
搜"写立即数"只找到 2 处，改了完全无效（报告 170 §5.1）。

现在答案清楚了：**它不是 glcore 自己算出来的，是内核告诉它的。**
内核模块把 P106-100 的 device ID `0x00071C07` 命中在受限表里 →
通过某种通道把"受限 SKU"属性传给用户态 → glcore 置位策略位 → 每批次发延迟。

**这同时解释了另一个问题：为什么这个 bug 没有被广泛报告。**
普通 GTX/RTX 卡不在那张表里，**策略位从来不会被置位**，
所以那条延迟命令对它们**根本不生效**。
只有 P1XX / CMP 系列矿卡会踩到 —— 这是一个**针对矿卡的定向限制**。

### 4.4 实施细节

| 步骤 | 内容 |
|---|---|
| 补丁对象 | `/usr/src/nvidia-580.178.04/nvidia/nv-kernel.o_binary`（112,677,456 B） |
| 原 md5 | `caa613d35d8bdfd615cee91e932689b5` |
| 改后 md5 | `f3480248f7a70f7501fd14ac90582ef1` |
| 改动量 | **10 个字节**（5 个条目 × 低 16 位 → `0xFFFF`），`cmp -l` 逐字节核对过 |
| 表位置 | 文件偏移 `0x5cfdfcc`（`.rodata` 段内的嵌入 blob） |
| 重建 | `cd /usr/src/nvidia-580.178.04 && make -j$(nproc)` → `nvidia.ko` |
| 替换 | 停 sddm → 卸载 4 个模块 → 拷贝 `.ko` → `depmod` → 重载 → 起 sddm |
| 备份 | `nv-kernel.o_binary.orig`（原版）、`/lib/modules/.../nvidia.ko.bak_*` |

## 5. 两种方案的实际取舍（实验之后）

| | 内核补丁 | 用户态补丁 |
|---|---|---|
| 侵入性 | 更低（一处常量表） | 稍高（改代码跳转） |
| 副作用范围 | 影响整个驱动栈（所有走该属性的路径） | 只影响"发不发那条命令" |
| 驱动升级后 | 需要重新找表 | 需要重新找跳转 |
| 可验证性 | 只能看功耗/性能（没有像素级校验手段） | **可以用 `chk` 做画面一致性校验** |
| 已知风险 | 未知（厂商可能有意限制该卡做别的事） | 已验证画面不变 |

**我们的方案有一个他们没有的优势：可以证明"画面没变"（`chk` 5150 四组一致）。**
内核补丁改的是设备身份，可能影响我们没验证到的路径。

**他们的方案有一个我们没有的优势：如果假设 A 成立，那才是真正的上游修复。**

---

## 6. 结论

**是不同的方案，但同一个根因，而且他们的更彻底。**

| | dartraiden（内核白名单） | 本项目（用户态跳转） |
|---|---|---|
| 层次 | 内核模块的设备 ID 表 | 用户态 GL 库的发射条件 |
| 改动 | 10 字节（5 个 dword 低 16 位） | 1~2 字节（条件跳转） |
| 性质 | **治本**：解除限制源头 | **治标**：下游拦截 |
| 实测 | 52.202 → 3.668 ms | 52.202 → 3.434 ms |
| 命令是否生成 | **否（根本不发）** | 是（发了但不执行跳转后的写入？见下） |
| 附加风险 | 改设备身份，可能影响未验证路径 | 只影响"发不发这条命令" |

> 注：③ 组（用户态补丁）下命令样本也是 0 条 —— 因为跳转把整段写入跳过了，
> 等价于"不发"。但**代码仍然走进去执行了判据和跳转**，与 ② 的"根本不进入该分支"
> 在语义上不同，性能上无差别。

### 现在的系统状态

**只打了内核补丁**，用户态 `libnvidia-glcore.so` 已恢复原版（md5 `18f43321...`）。
`map_p50 = 3.672 ms`，桌面正常。

### 留给下次的两件事

1. **515 为什么不受影响** —— 515 里这套代码整套不存在（报告 170），
   所以它在任何 device ID 下都不会有这条延迟。这意味着：
   **NVIDIA 是在 520+ 才引入"按 SKU 限制"的机制**。
2. **内核→用户态的通道路径** —— 现在知道方向了（内核报属性、用户态置位），
   但具体是哪个 ioctl / 哪个属性字段，还没定位。
   如果要给 NVIDIA 提一份可复现的报告，这是最后一块拼图。
