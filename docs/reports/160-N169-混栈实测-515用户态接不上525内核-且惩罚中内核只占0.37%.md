# N169 — 混栈实测：515 用户态接不上 525 内核；且 122µs 惩罚里内核只占 0.37%

**日期**：2026-10-27
**驱动**：内核模块 525.116.03（`/proc/driver/nvidia/version` 实测），用户态待换
**起因**：用户提议「内核是 525，用户态库是 515（通过修改版本号可以绕过版本检查，不过估计不可行）」

---

## 0. 一句话结论

**用户猜对了——不可行，但原因不是版本检查。** 版本号 patch 确实绕过了检查（全程没出现 `API mismatch`），
真正堵死这条路的是 **515↔525 的三层接口同时变了**：GLX 私有协议、glcore↔glsi 私有 ABI、EGL 用户态内部判定。
**同时用一个更硬的测量把层次判死了：122µs 惩罚里，内核 ioctl 只占 0.37%。**

---

## 1. 前置：版本串等长替换可行

`515.105.01` 与 `525.116.03` **都是 11 个字符**，可以原地二进制替换，不改结构、不改长度：

| 库 | 替换处数 |
|---|---|
| `libnvidia-glcore.so` | 28 |
| `libnvidia-eglcore.so` | 27 |
| `libGLX_nvidia.so` | 4 |
| `libnvidia-glsi.so` | 4 |
| `libnvidia-tls.so` | 2 |
| `libEGL_nvidia.so` | 3 |

文件名也要一起改（因为库之间用**带版本号的文件名**互相 `dlopen`，
例如 glcore 里硬编码 `dlopen("libnvidia-tls.so.515.105.01")`）。

**验证：patch 后没有出现 `API mismatch: the client has the version ... but this kernel module has ...`。**
→ **版本检查这一关，过了。**

---

## 2. 方向一：515 全套 GLX 客户端 + 525 X server → 建不出 context

做法：把 515 的 `libGLX_nvidia` / `libGL` / `libGLX` / `libGLdispatch` 全部放进 `LD_LIBRARY_PATH`。

```
X Error of failed request:  BadValue (integer parameter out of range for operation)
  Major opcode of failed request:  149 (GLX)
  Minor opcode of failed request:  24 (X_GLXCreateNewContext)
  Value in failed request:  0x0
```

**判读**：GLX 扩展协商过了、fbconfig 列表也拿到了，死在 `glXCreateNewContext`，传下去的 fbconfig 是 **0**。
→ **515 客户端与 525 服务端（`libglxserver_nvidia.so`）之间的 GLX 私有协议不兼容**，
fbconfig 在两侧的编号/编码对不上。

把 515 自带的整套 glvnd（`libGLX.so.0` + `libGLdispatch.so.0`）也加进来，**报错完全一样** ——
所以不是 glvnd 版本配套问题，是 **X server 侧**那一半接不上。

---

## 3. 方向二：只换 glcore（525 管 X 交互，515 管渲染）→ 段错误

思路：惩罚的嫌疑在 glcore（GL 前端 + legacy 状态机），`glsi` 只是 X 交互层，
那就保留 525 的 `libGLX_nvidia` + `glsi`，只把 `glcore` 换成 515 的（改名成 `libnvidia-glcore.so.525.116.03`，让 525 的 GLX 去 `dlopen` 它）。

**结果：`rc=139` 段错误，无任何输出。**

```
bash: 第 1 行： 5058 段错误 （核心已转储）
```

**判读**：`glcore` 与 `glsi` 之间的私有接口（回调表/函数签名）在 515→525 之间**变了**。
525 的 glsi 按 525 的约定调用 515 的 glcore → 直接崩。
→ **两版 glcore 的内部 ABI 不兼容，不能单点替换。**

---

## 4. 方向三：515 的 EGL（绕开 X 的 GLX 私有协议）→ 初始化失败，但内核没拒绝

EGL 的 `device` 平台直接开 `/dev/nvidia*`，不经过 X server 的 GLX 扩展，是最干净的隔离路径。

| | 枚举设备数 | device[0] 扩展 | eglInitialize |
|---|---|---|---|
| **525** | 4 | `EGL_NV_device_cuda` + DRM | **成功**，EGL 1.5 / NVIDIA / GL 3.2.0 |
| **515** | **1** | `EGL_NV_device_cuda` + DRM（同样的串） | **失败** `0x3002` = `EGL_NOT_INITIALIZED` |

**515 找到了正确的设备，但初始化拒绝。**

关键排查：**这不是内核拒绝**。

- `strace` 全程 **52 个 ioctl，返回值全部 0**，没有任何 `EINVAL/ENOTTY/EPERM`；
- 用 `nkioctl.so` 拦截 RM 层：**26 次 `RM_CONTROL` / 7 次 `RM_ALLOC`，`status` 全部 `00000000`**；
- 另外确认 515 EGL **根本没用 `NV_ESC_CHECK_VERSION_STR`（`0xCA`）** ——
  `NV_IOCTL_BASE = 0xC0`，`+10 = 0xCA`，而 515 发的序列里没有它。

→ **所有内核调用都成功，515 的 EGL 是在用户态内部自己判定失败的。**
（最可能是它拿到的某个查询结果字段语义变了，但这条不值得再追：即使追通，也只是重现"515 快"这个已知事实。）

---

## 5. 为什么"改版本号"注定不够 —— 三层全变

| 层 | 515 ↔ 525 是否兼容 | 证据 |
|---|---|---|
| 版本检查（字符串） | ✅ 可绕过 | patch 后无 `API mismatch` |
| **GLX 私有协议**（客户端 ↔ X server） | ❌ | `X_GLXCreateNewContext` BadValue，fbconfig=0 |
| **glcore ↔ glsi 私有 ABI**（用户态内部） | ❌ | 单换 glcore 直接段错误 |
| **EGL 用户态内部判定** | ❌ | 52 ioctl 全 0、26 RM 全 status=0，仍 `NOT_INITIALIZED` |
| 内核 ioctl 编号/结构 | ✅ 基本没变 | `0x2a/0x2b/0x27/0x29` 两版一致，全部 rc=0 |

> **泛化：闭源驱动的大版本之间，"能骗过版本检查"和"能混栈"是两件完全不同的事。**
> 版本检查只是最外层一道门；门后面还有私有的协议、私有的回调表、私有的判定逻辑。
> **验证一个混栈能不能成立，唯一可信的方法是跑起来看，不能靠"版本号对上了"推断。**

---

## 6. 决定性的层次判决：122µs 里内核只占 0.37%

比混栈更直接的问题：**这 122µs 到底是不是内核花掉的？**

测法：`n83b -M 3 -n 1200`（完整 legacy 路径，1200 对/帧，20 帧），
同时用 `nkioctl.so` 累计**每一次 ioctl 的自测耗时**。

| 项 | 数值 |
|---|---|
| 每帧墙钟（`total_p50`） | **152.1 ms** |
| 每帧 ioctl 总耗时 | **565.6 µs** |
| ioctl 占比 | **0.37%** |
| ioctl 调用次数（20 帧合计，含初始化） | 721 |
| 每次平均 | 15.7 µs |

**⇒ 内核在惩罚里只占 0.37%，可以完全排除。**

与已有证据闭合：

- 报告 155/156：**79.5% 的墙钟时间在用户态函数 `0x15761b0` 内部**（它自己累计的计时器 `[ctx+0x6f88]` 与 ptrace 采样互相印证，79.5% vs 79.6%）；
- `0x15761b0` 读的是 **mmap 到用户态的 GPU 寄存器**（引擎 fence），CPU 直接读，**不经过内核**；
- 报告 156：**zink（Vulkan）同一内核下 M3 从 127.90 → 18.59 ms（6.9×）**。

**三条合起来：惩罚 100% 在用户态 glcore 的 GL legacy 前端，内核无责。**

---

## 7. 顺带解决的一个坑：Unigine 不链接 libGL

想做 Heaven 的帧时间直方图，`LD_PRELOAD` 拦 `glXSwapBuffers` **完全拦不到**（文件生成了但是 0 行）。

原因：`readelf -d libUnigine_x64.so` 的 `NEEDED` 里**根本没有 libGL**。

```
libpthread, libX11, libXext, libXrandr, libXinerama, libXrender, libstdc++, libm, libgcc_s, libc
```

它是运行时 `dlopen("libGL.so.1")` + `dlsym` 取函数指针。
→ **对这类程序，LD_PRELOAD 同名符号无效，必须拦 `dlsym`**（`swapts2.c` 已实现，
但 Heaven 通过 glvnd 的 dispatch 走，dlsym 层仍没拦到 —— **遗留问题，待查**）。

> **教训：钩子不生效时，第一件事是查目标库有没有真的链接那个符号。**
> `NEEDED` 列表里没有 libGL/GLX 的，说明它走的是 `dlopen` + `dlsym`/`glXGetProcAddress`，
> 同级符号的 LD_PRELOAD 全部无效。

---

## 8. 结论

1. **515 用户态 + 525 内核：不可行**，且不是版本检查的问题（已绕过），是三层私有接口同时变了。
2. **122µs 惩罚在内核侧只占 0.37%** —— 层次判决完成，不需要再做混栈实验。
3. 要用 515 的性能，唯一办法是**整套换驱动**（内核模块 + 用户态一起），不存在"只换库"的捷径。
4. 遗留：Heaven 的帧时间直方图仍缺（swap 钩子未生效），这是回答"抽搐 ↔ 30fps"的下一步。
