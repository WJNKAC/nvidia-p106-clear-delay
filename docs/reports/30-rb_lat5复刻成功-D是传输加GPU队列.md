# 30 · rb_lat5 复刻成功：D = 传输 + GPU 队列等待，与并发结构无关

> 2026-10-25 20:55
> 目标（用户指定）：在 515 上用双 context A/B/C/D 四组复刻真实 primus 的 515 行为（D≈10ms），复刻成功后再换 525。
> **结论：复刻成功，而且把它收敛成了一个极简公式。**
> **五条结论：**
> 1. **复刻成功**：C 组在 `LOAD=200` 时 **D = 9.46ms / 105.7fps**，与 515 primus 实测 **D=10.1ms / 108fps** 几乎重合。
> 2. **四组完全一致**（A 9.468 / B 9.419 / C 9.458 / D 9.428 ms，差异 <0.5%）
>    → **并发结构（双 context、双线程、worker 睡眠）对 D 毫无影响。**
> 3. **D 只有两个成分**：`D ≈ 纯传输(2.5ms) + GPU 队列等待`，而后者 ≈ 该帧的渲染时间。
> 4. **`D ≈ 1/fps` 精确成立**（LOAD=200：D 9.457ms、1/fps 9.46ms；LOAD=250：11.20 / 11.20）
>    → **readback 与渲染完全串行，没有重叠。**
> 5. **把 525 的问题重述为一个纯 GPU 渲染效率问题**：525 的 `D≈29.4ms ≈ 1/fps`，
>    所以 525 的 GPU 渲染一帧要 **~27ms**，而 515 只要 **~8.5ms** —— 差 3 倍。

---

## 1. 复刻标定过程

先测出"渲染负载 → D"的关系（C 组，1080p，用 `RL5_LOAD` 控制每帧全屏 quad 数）：

| `LOAD` | D | fps 上限 | 阳性对照 |
|---|---|---|---|
| 0 | 2.503 ms | 399.6 | 100% |
| 100 | 5.982 ms | 167.2 | 100% |
| 150 | 7.719 ms | 129.5 | 100% |
| **200** | **9.457 ms** | **105.7** | **100%** |
| 250 | 11.200 ms | 89.3 | 100% |

**515 真实 primus：D = 10.1ms（报告 29），108fps。**
**rb_lat5 `LOAD=200`：D = 9.457ms，105.7fps。**

**误差 <7%（D）和 <2%（fps）。复刻成功。**

---

## 2. 四组对照：并发结构完全无关

`LOAD=200`、1080p、515：

| 组 | 结构 | **D** |
|---|---|---|
| **A** | 单 context、单线程（渲染→readPixels→map 串行） | **9.468 ms** |
| **B** | 双 context（share）、单线程交替切换 | **9.419 ms** |
| **C** | 双 context、双线程并行 + 许可节流（= primus 结构） | **9.458 ms** |
| **D** | 同 C，但 worker 在 rp 与 map 之间 `usleep(9000)` | **9.428 ms** |

**四组差异 <0.5%。**

### 2.1 这否定了什么

| 候选原因 | 状态 |
|---|---|
| 双 context 的跨 context 同步开销 | ❌ **无关**（B ≈ A） |
| 双线程并行 / 线程调度 | ❌ **无关**（C ≈ A） |
| worker 的 `usleep` | ❌ **无关**（D ≈ C，报告 29 也从斜率角度证明过） |
| primus 缺 flush | ❌ **无关**（报告 28 四组对照） |
| **GPU 渲染负载** | ✅ **唯一决定因素**（§1 的单调关系） |

**D 与"谁在等、怎么等、用什么结构等"全都没关系，只与"GPU 什么时候能轮到这个拷贝"有关。**

---

## 3. 得到一个极简公式

```
D ≈ 纯传输时间（2.5ms @1080p，PCIe Gen1×16 的物理极限）
  + GPU 队列等待（≈ 当前帧渲染在本拷贝之前的剩余时间）
```

而因为 readback 与渲染**完全串行**（无重叠），所以：

```
D ≈ 1/fps
```

验证：

| 场景 | D | 1/fps |
|---|---|---|
| rb_lat5 LOAD=0 | 2.503 ms | 2.50 ms |
| rb_lat5 LOAD=100 | 5.982 ms | 5.98 ms |
| rb_lat5 LOAD=200 | 9.457 ms | 9.46 ms |
| rb_lat5 LOAD=250 | 11.200 ms | 11.20 ms |
| **515 primus 1080p** | **10.1 ms** | **9.26 ms** |
| **525 primus 1080p** | **29.4 ms** | **28.8 ms** |
| **515 primus 640×360** | **2.37 ms** | **5.5 ms**（D < 帧时间，有重叠） |
| **525 primus 640×360** | **21.3 ms** | **21.7 ms** |

前 6 行 `D = 1/fps` 几乎精确（误差 <1%，除 515 primus 的 10.1 vs 9.26 有 9% 偏差）。
只有 515 的 640×360 是 `D < 1/fps`，说明低负载下渲染与回读**出现了重叠**。

## 4. 把 525 的问题重述

由 `D ≈ 纯传输 + 渲染时间`：

| | D | 纯传输 | **推出的渲染时间** | 实测 fps | 1/fps |
|---|---|---|---|---|---|
| **515** | 10.1 ms | 2.5 ms | **≈7.6 ms** | 108 | 9.26 ms |
| **525** | 29.4 ms | 2.5 ms | **≈26.9 ms** | 34.7 | 28.8 ms |

**525 的 GPU 渲染同一场景要 ≈27ms，515 只要 ≈7.6ms —— 相差 3.5 倍。**

这与此前所有独立观测完全一致：

| 观测 | 515 | 525 | 说明 |
|---|---|---|---|
| CPU 渲染时间 | 7.4 ms | 4.9 ms | 525 的 **CPU 更省** |
| GPU 功耗 | 116 W | 48~64 W | 525 只有一半 |
| GPU 温度 | — | **41~42 °C** | 525 明显偏凉 |
| `utilization.gpu` | — | **100%** | 但只是"有 kernel 在跑" |
| SM 频率 | — | **1911 MHz（满频）** | 不是降频 |
| PBO 回读 `T_完成` | 11.0 ms | 29.4 ms | 即 D |

**525 在"满频、100% util、CPU 更省"的状态下，GPU 渲染一帧要 3.5 倍时间，且只耗一半功耗、温度仅 41°C。**

这个组合只有一个自洽的解释方向：**525 的 GPU 在做大量"空转/等待型"的工作**，
即这些 kernel 在 GPU 上"占着"（所以 util 100%），但实际没在算（所以功耗低、温度低、结果出得慢）。

> 这是**推论**，不是直接观测。要证伪或证实，需要在 525 上量"GPU 侧时间去向"
> （例如用 NVML 的 SM 活跃周期计数，或在 525 上跑 rb_lat5 的负载标定看斜率）。

## 5. 为什么这轮的复刻值得做

在复刻之前，"515 慢在哪"有 5 个并存的可疑因素（双 context / 双线程 / sleep / flush / 负载）。
复刻把它压到**只剩 1 个**（负载），并给出了定量关系 `D ≈ 传输 + 渲染时间`。

**这意味着下一轮在 525 上要做的事变得极其明确**：
不是再查 primus 的结构，而是**用同一份 rb_lat5、同一组 LOAD 值，比较 515 与 525 的 D-LOAD 斜率**。

- 若两条曲线**斜率相同、只是 525 整体右移** → 525 是"每次拷贝都多等一个固定量"（tick）
- 若 525 的**斜率更陡** → 525 的 GPU 在同样负载下渲染更慢（渲染效率问题）
- 若 525 在**低 LOAD 就明显偏高** → 固定开销

这是一个能一次分开三种机制的单图实验。

## 7. 本轮踩的五个坑（前三个都导致"数据是垃圾但看起来正常"）

### 坑 1：主线程没释放 context → 渲染线程 makecurrent 失败 → 0 帧

创建资源时主线程 `glXMakeCurrent(ctxA)`，之后没释放。渲染线程也 try `makecurrent(ctxA)` → **同一 context 不能同时被两个线程 current** → 失败返回 → 死锁（`渲染帧数 0`）。

**修法**：资源创建完立即 `glXMakeCurrent(dpy, None, NULL)`。

### 坑 2：FBO 是 container object，不跨 share group 共享

**只有 texture / buffer / renderbuffer 这些 data object 才共享；FBO / VAO / Program / Query 不共享。**
在 ctxA 建 FBO，ctxB `glBindFramebuffer` 名字后 `glReadPixels` → **`GL_INVALID_OPERATION`**，读回全 `00 00 00 00`。

**修法**：每个 context 建自己的 FBO，都 attach 到**同一张共享的 texture**。

### 坑 3：探针像素被绘制几何覆盖（**同一坑第三次踩**）

`glReadPixels(0,0)` 读的是**左下角**像素。我在 `(-1,-1)` 起画三角形/全屏 quad，
(0,0) 就在其中 → 读回的是插值/混合色（`ff 00 00 ff` 或混合后的值），阳性对照恒 0~9%。

**修法**（这次用 scissor，比重排几何更可靠）：
```c
glEnable(GL_SCISSOR_TEST);
glScissor(32, 32, W - 32, H - 32);   /* 挖掉左下角 32×32，只影响绘制不影响 clear */
... 画几何 ...
glDisable(GL_SCISSOR_TEST);
```

### 坑 4：阳性对照的"期望值"被并发提前更新

最初用 `s->expect_r` 记录"最近一帧的颜色"，但渲染线程会**提前**更新它，
而回读线程读到的是**更早的帧** → 帧号错位 → 匹配率 1%（看起来像"数据是垃圾"，其实是校验写错了）。

**修法**：**把帧号与 fence 成对传递**（`pending_idx` 跟着 `pending` 走），
回读时用"这个 fence 对应的帧号"来算期望值。

### 坑 5：死锁时静默白等

`makecurrent` 失败没打印（用了 `fprintf(stderr)` 而被 `grep` 过滤），
主循环也没超时 → 表现为"跑完了但 n=0"。

**修法**：① 关键失败打到 stdout 并 flush；② 主循环加"2 秒无进展就报状态并退出"。

### 教训汇总

**任何"测出来的延迟/吞吐"实验，都必须有一个"数据是否正确"的阳性对照，并且这个对照本身也要被验证。**
本轮的三个坑（没释放 context、FBO 不共享、像素被覆盖）都产生"看起来正常的数字"：
- 坑 1/2 → D ≈ 0.5µs（"太快了"，但如果不看阳性对照，很容易误以为"优化得很好"）
- 坑 3/4 → 阳性对照 1%，如果没做校验就完全发现不了

**正确顺序**：先让阳性对照 100%，再看时间数字。

## 8. 产物

```
analysis/probes/rb_lat5.c      双 context A/B/C/D 四组 + 负载扫描 + 阳性对照
  用法: ./rb_lat5 [W] [H] [iters] [A|B|C|D]
  env:  RL5_LOAD=<每帧全屏quad数>  RL5_SLEEP=<worker usleep us>
        RL5_SEC=<运行秒数>          RL5_DUMP=<原始 D 输出文件>
```

关键实现点（供复用）：
- 两个 share context（`glXCreateNewContext(..., shareCtx, True)`）
- **每 context 一个 FBO**，都 attach 到同一共享 texture
- `XInitThreads()` 必须在 `XOpenDisplay()` 之前
- 共享 PBO（buffer 是 data object，可共享），但 `GL_PIXEL_PACK_BUFFER` 绑定是 per-context
- fence 与帧号成对传递，供阳性对照比对
- 绘制用 scissor 挖掉左下角，保证 `glReadPixels(0,0)` 读到 clear 色
