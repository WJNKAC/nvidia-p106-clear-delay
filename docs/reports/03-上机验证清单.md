# 上机验证清单（<testhost>）

- **机器**: <testhost>，ssh 密码 `desktop`
- **现役驱动**: 580.178.04（Linux）
- **硬件注意**: **P106 位于第二 PCIe 槽位**——可能是 x8/x4 通道、供电/散热条件与主槽不同；对比数据时需固定槽位，跨槽位对比无意义
- **原则**: 先只读采集，不做任何写入/刷写操作；驱动切换实验放最后且单独安排

## A. 只读采集（5 分钟，随时可做）

```bash
# 0. 确认 GPU 识别与槽位
nvidia-smi --query-gpu=name,pci.bus_id,power.limit,power.max_limit,power.default_limit --format=csv
lspci -vv | grep -A12 "NVIDIA" | grep -E "Physical Slot|LnkCap|LnkSt"

# 1. 功耗上限与当前状态
nvidia-smi -q -d POWER
#    关注: Power Limit 的 Default / Min / Max / Enforced

# 2. 性能状态与降频原因（性价比最高的一项）
nvidia-smi -q -d PERFORMANCE
#    关注: Clocks Event Reasons 中 SwPowerCap / SwThermalOvershoot 是否 Active

# 3. procfs 行为判据: 525+ 驱动没有 "Power Limits" 段（515 有）
cat /proc/driver/nvidia/gpus/*/information

# 4. 平台 ACPI 是否有 NVPCF（桌面一般没有；有则 NVPCF 路径嫌疑大增）
strings /sys/firmware/acpi/tables/DSDT 2>/dev/null | grep -i nvpcf
ls /sys/firmware/acpi/interrupts/ | grep -i nv

# 5. vBIOS dump（read-only，供报告 02 的固件侧分析）
sudo nvidia-debugdump --dump-rom 2>/dev/null || \
  sudo bash -c 'echo 1 > /sys/bus/pci/devices/<P106的BDF>/rom && \
                dd if=/sys/bus/pci/devices/<P106的BDF>/rom of=/root/p106-vbios.rom bs=1M && \
                echo 0 > /sys/bus/pci/devices/<P106的BDF>/rom'
```

## B. 功耗钳制定位实验（在 A 的结果之后）

```bash
# 6. 试抬功耗上限（root）。接受 → 钳制在 PL 执行下游；报错 → 上游（vBIOS/RM 内部）
sudo nvidia-smi -pl 120

# 7. 3D 负载下观察（游戏/glxgears/FurMark），同时开另一个终端跑:
watch -n1 nvidia-smi --query-gpu=power.draw,clocks.sm,clocks_throttle_reasons.active,clocks_event_reasons.active --format=csv

# 8. CUDA 负载对照（580 起 CUDA 程序默认拉高功耗档，可禁用对比）
CUDA_DISABLE_PERF_BOOST=1 <你的CUDA程序>
```

## C. 驱动版本对照实验（最后做，需重启，单独安排）

1. 采集 580 基线数据（A/B 全部项）
2. 装 525.116.03（`<workdir>/drivers/525.116.03/`，注意新内核兼容性——515 已确认不适配）
3. 重复 A/B 采集，对比：
   - Power Limit Max 是否变化
   - Clocks Event Reasons 是否出现/消失 SwPowerCap
   - procfs "Power Limits" 段有无
4. （可选）如 525 与 580 无差异而 515 有差异，则边界在 515→525 已由静态确认，上机数据用于执行签名验证

## D. 判读矩阵

| 观察 | 结论 |
|---|---|
| SwPowerCap: Active 且功耗远低于 Max PL | 功耗路径被钳（与 NVML 读数矛盾则指向时钟路径） |
| 时钟钉低位、无 SwPowerCap | H3（P-state 钳制）加分，查 `RMForcePstateBug3811584War` |
| `-pl 120` 被拒 | 钳制点在 PL 执行上游（vBIOS Rated TDP / RM 内部策略） |
| `-pl 120` 被接受且功耗上去 | 当前只是默认 PL 低，非硬钳制 |
| DSDT 有 NVPCF | 平台功耗框架介入，需进一步查 nvpcf_dsm_in_gpu_scope 路径 |
