# N176 — ★ 定位到寄存器级：525 每批多发一条 `0x3998 = 0xF0`，值 240 ≈ 118.6µs 的来源

**日期**：2026-10-27
**平台**：<user>@<testhost>，P106-100，整驱动切换（515.105.01 ↔ 525.116.03）
**负载**：`n83b -M 7 -n 400`（400 draw 固定，只改批次数 c）

---

## 0. 一句话结论

**122 µs 是 GPU 侧的时间（`glFinish` 实测），且 525 在每个批次边界多发一条写寄存器的命令
`method 0x3998 = 0xF0(=240)`，而 515 完全没有这条命令。**

```
实测每批耗时 118.6 µs ÷ 240 = 494 ns/单位
```

**515 用 `0x39c0`（值 0x20）做同样的事；525 换成了 `0x39d0`（值 0x20）+ 多一条 `0x3998`（值 0xF0）。**

---

## 1. 第一步：证明那 122 µs 是 GPU 花的，不是 CPU 花的

用 `-G`（`glFinish` 等 GPU 真正完成，不走 PBO 回读路径）测**纯 GPU 时间**：

| 批次数 c | 515 `rp_p50` | 525 `rp_p50` |
|---|---|---|
| 0 | **1.832 ms** | **2.450 ms** |
| 100 | 0.930 | **16.494** |
| 400 | **0.946 ms** | **49.886 ms** |

**斜率：515 ≈ 0（甚至为负）；525 = 118.6 µs/批。**

三点结论：

1. **`glFinish` 在等，说明 GPU 真的"占用"了这段时间**，不是 CPU 空转、不是驱动 sleep。
   （这一条把此前"CPU 在重建状态表""驱动在 yield"等解释彻底排除。）
2. **515 上 400 个批次的 GPU 总时间只有 0.95 ms** —— 平均每批 2.4 µs。
   **525 是 49.9 ms，每批 125 µs。差 52 倍。**
3. 515 甚至 c=400 比 c=0 **更快**（0.946 < 1.832）—— 分批让 GPU 更早开始干活，流水更好。

---

## 2. 第二步：对比 pushbuffer 里"切批时多出来的命令"

方法：抓 `mem !` 中 `nvidia` 可写映射里**正在变化**的 4KB 块（写死的常量和环形缓冲尾巴会稀释统计），
解码命令头（`op=w>>29`、`cnt=(w>>16)&0x1fff`、`sub=(w>>13)&7`、`meth=(w&0x1fff)<<2`），
统计 `sub:meth` 直方图。

### 2.1 两版**共有**的"切批序列"（12 条，完全相同）

```
0:0x37c  0:0x360  0:0x1450  0:0x196c  0:0x13a8  0:0x2490
0:0x2144 0:0x228  0:0x2410  0:0x1688  0:0x2044  0:0x2600
```

这 12 条在**两版的 c=0 时都不出现（或极低），c=400 时都以约 1 次/批 的频率出现**。
⇒ **切批本身要发的状态重设命令，两版是一样的。回归不在这里。**

### 2.2 ★ 唯一的差异：三个寄存器

| method | 515 | 525 | 参数值 |
|---|---|---|---|
| `0x39c0` | **有**（8703 次，最高频） | **无** | **0x20** |
| `0x39d0` | **无** | **有**（2427 次，最高频） | **0x20** |
| **`0x3998`** | **无** | **有**（1213 次） | **`0xF0` = 240** |

**逐条确认**（`pbargs.py` 抓的实参）：

```
515 c=400:
  method 0x39c0  样本40条  全部 cnt=1  0x00000020
  method 0x3998  0 条
  method 0x39d0  0 条

525 c=400:
  method 0x39d0  样本40条  全部 cnt=1  0x00000020
  method 0x3998  样本40条  全部 cnt=1  0x000000f0
  method 0x39c0  0 条
```

**两个观察：**

1. `0x39c0` 与 `0x39d0` **只差 0x10**，参数都是 `0x20`。
   这是同一族相邻寄存器被"挪了位置"（Pascal 3D class 里 method 号变化）。
   **这一条本身不解释性能差异**（参数一样、次数相当）。
2. **`0x3998 = 0xF0` 是 525 独有的，515 一条都不发。**
   而且它在 `c=0` 时也不存在（525 c=0 的 method 表里没有 0x3998），
   **只在分批时出现 ⇒ 严格与"批次边界"绑定。**

### 2.3 那个 240 与 118.6 µs 的关系

```
实测每批 GPU 代价 118.6 µs
寄存器值          0xF0 = 240
118.6 µs ÷ 240 = 494 ns / 单位
```

**240 个单位 × 约 0.5 µs/单位 ≈ 120 µs —— 与实测 118.6 µs 吻合。**

这是**强相关但不构成证明**。要坐实必须做一次干预实验（改这个参数值，看帧时间是否按比例变化），
见 §5。

## 3. 为什么"多发一条写寄存器"会花 118 µs

**写寄存器本身是纳秒级的**（就是 pushbuffer 里 8 个字节）。118 µs 不可能是"写"的代价。

所以只有两种可能：

| 可能 | 说明 | 如何区分 |
|---|---|---|
| **A. 该寄存器是"等待/延迟"控制** | GPU 收到后主动停顿 N 个单位，或等某个条件满足 | 改参数值，看耗时是否线性变化 |
| **B. 该寄存器触发一次批次排空（drain）** | GPU 必须把之前的命令全部执行完、写回、失效缓存，才继续 | 改参数值应当**无效**（只是个模式位） |

**目前证据偏向 A**：参数是 `0xF0` 这种"量"而不是 0/1 的开关，且 240 与实测耗时能对上。

**而 515 的做法（只用 `0x39c0 = 0x20`，不发 `0x3998`）说明：**
这个"排空/延迟"在 515 里**要么不需要，要么用了另一套机制**。
结合报告 140 的观察（Heaven 上 515 发 6653 个 `sub6:0x0034`、525 只发 16 个），
**515 更像是用"内存里的信号量"做细粒度同步，而 525 改用"GPU 内部停顿"来做——精度更粗、代价固定且大。**

## 4. 完整因果链（当前版本）

```
应用每次状态变更 + draw
   ↓
525 驱动在每个批次边界多写一条 0x3998 = 0xF0(240)
   ↓
GPU 侧因此停顿约 118.6 µs（每单位约 494 ns）
   ↓
GPU 无法把相邻批次流水重叠 ⇒ 批次数直接线性叠加到帧时间
   ↓
用 glFinish / glReadPixels 的应用全部被拖慢：
    n83b（400 批/帧）：4.4 ms → 52.8 ms（12×）
    Heaven（批次数少得多）：10 ms → 35 ms（3.5×）
   ↓
GPU 利用率 98%、时钟顶格、功耗反降（在等，不在算）
```

**515 全程没有这一项 ⇒ `T = T_base(N)`，批次数随便加。**

## 5. 下一步（可直接验证，也能直接利用）

### 5.1 验证（干预实验）
在 525 上，用**运行时 pushbuffer 改写**把 `0x3998` 的参数 `0xF0` 改成更小的值（如 `0x10`），
看帧时间是否按比例下降。

- 若**线性下降** → 确认它是"延迟量"，且**这就是唯一的成本来源**
- 若**不变** → 它是模式位/排空触发，需要改的是"是否发这条命令"

**要点**：必须在 pushbuffer 被 GPU 消费**之前**改写。可行路径：
在 `ensure_space` 返回后、kick 之前改写刚写入的那 8 字节。
（本项目已有 `patchpb.c` 的运行时改字节框架，但那是改**代码**，这里是改**数据**，需要新工具。）

### 5.2 利用（不改驱动的方案）
既然成本 ∝ 批次数，**合批就是唯一有效的优化**（报告 166 §6 已给数据：1600 draw 从 1600 批 → 10 批，5→134 fps）。

### 5.3 若要追到"哪个函数发这条命令"
`0x3998` 在 pushbuffer 里的编码是 `meth>>2 = 0xE66`（13 位 method 字段）。
在 glcore 里搜立即数 `0xE66`（配合 `0x3998` 附近的 `0xE74` / `0xE70`），
可以定位到"生成这条命令的代码"。但这是**语义层**的追查，
对"能不能修"没有增量价值 —— 因为修法要么是合批、要么是运行时改数据。

| `analysis/pbwin.sh` | 一键：起负载 → 抓 ctx → 零干扰测窗口 |

### 踩过的坑（值得记）

1. **`bpftrace` 不认裸偏移**：`uprobe:/path/lib.so:0xOFFSET` → `Could not resolve address`。
   `perf probe` 对裸偏移的语法也不兼容（`bad for event name`）。tracefs `uprobe_events` 写入被拒。
   → 退回到 ptrace 硬件断点，但**只用同一 run 内的比值**，不做跨 run 比较。
2. **快照式 pushbuffer 采样会大量漏采**：`c=400` 时程序写得太快，30 ms 间隔只抓到约 7% 的命令。
   → **绝对计数不可用，只有"method 种类集合"和"比例"可用**。
3. **`ctx+0x10d0`（从 `ensure_space` 反汇编推的）不是 put 指针**：实测几乎不推进。
   → 用 `ctxscan.py` 自动扫描才找到真正在涨的字段。**反汇编推的偏移必须实测校验。**
4. 找到一个"累计写入字节计数器"（515 `ctx+0x358`，31 MB/s 稳定推进），
   但它是**历史累计量**不是环形指针（末值已 84 MB），不能直接当 put 用。
5. `perf record` 输出**不要写 `/data`**（`analysis` 目录 others 无写权限，root 也可能被拒），写 `/tmp` 再拷。
