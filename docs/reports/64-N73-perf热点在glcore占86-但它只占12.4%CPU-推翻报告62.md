# 64 · N73：perf 热点确实在 `libnvidia-glcore`（86%），但**它只占 3.82ms/帧** —— 推翻报告 62「整帧占满一核」

> 2026-10-26 10:05
> 用户指令：跑 `perf record -t <渲染线程tid> -g`，看热点落在 glcore / Heaven / malloc；分散则查 CPU 调度。
>
> **两条结论，第二条推翻了报告 62：**
> 1. **热点确实在 `libnvidia-glcore`：86.0% 的栈顶帧**，与 N72 的静态线索吻合。但**极度分散**——549 个不同地址，最高单点只占 2.4%。
> 2. **★ 渲染线程只占 12.4% 的 CPU = 3.82ms/帧**（`/proc` 的 utime 直读，不是采样推断）。**它的 87% 时间睡在 `futex_wait_queue` 上（`state=S`）。**
>    → **报告 62 的「整帧占满一个核、CPU 在生成 GL 命令」是错的。实际上是"在等"，不是"在算"。**

## 1. 先纠正一个目标错误：我一开始采错了线程

第一轮我用"ioctl 最多的 tid"定位渲染线程 → 采到 `libgallium` 39%、`libnvidia-glcore` **0%**。
**那是 Intel 上屏线程，不是渲染线程。**

按 N72 的发现（20 次 ioctl 里 19 次是 Intel DRM），"ioctl 最多的线程"必然是上屏线程。

### 1.1 正确的定位方法：按 cmd 的 type 字节

| tid | ioctl 总数（3s） | cmd 种类 | 归属 |
|---|---|---|---|
| **60144** | **1558** | 6 种，全 `type='d'`（DRM） | **Intel 上屏线程** |
| **60130** | **143** | 7 种，全 `type='F'`（NVIDIA） | **★ 渲染线程** |

NVIDIA 侧的 cmd 明细：

| cmd | 次数（3s） | 折算 |
|---|---|---|
| `c020462a` | 88 | ~0.9 次/帧 |
| `c0b8464a` | 14 | 0.14 次/帧 |
| `c0104629` | 14 | 0.14 次/帧 |
| `c0384657` | 7 | 0.07 次/帧 |
| `c0284658` | 7 | 0.07 次/帧 |
| `c020464f` | 7 | 0.07 次/帧 |

**合计约 1.4 次/帧** —— 与报告 63 的"每帧仅 1 次 NVIDIA ioctl"一致。

**判据固化**：定位"GPU 提交线程"不能按 ioctl 总数（会被 Intel 上屏淹没），必须按 **cmd 的 type 字节**分。

## 2. perf 结果：热点在 glcore，但极度分散

对渲染线程 999Hz × 6s 采样，821 个样本。

### 2.1 栈顶帧归属

| 归属 | 样本 | 占比 |
|---|---|---|
| **`libnvidia-glcore.so.525.116.03`** | **706** | **86.0%** |
| `libc.so.6` | 81 | 9.9% |
| `kernel` | 32 | 3.9% |
| `libGLX_nvidia` | 2 | 0.2% |

**86% 落在 glcore** —— 与 N72 的静态线索（共用库是 glcore、体积 +20.4%）完全吻合。

**注意：`[unknown]` 在这份定点采样里 Self = 0.00%**（Children 41.70%）。
第一轮全进程采样里 `[unknown]` Self 35% 是**别的线程**贡献的（Heaven 引擎的 JIT/匿名映射）。
→ **按 tid 过滤是必须的，否则会被 [unknown] 误导。**

**按用户判据表，这属于「分散、无集中热点」→ 该查 CPU 频率/调度。** 但下一节的数据说明，连"CPU 忙"这个前提都不成立。

## 3. ★★★ 推翻报告 62：渲染线程只占 12.4% 的 CPU

### 3.1 方法：直接读 `/proc/PID/task/TID/stat` 的 utime+stime

不靠采样率推断，直接读内核记账的两个快照相减：

| tid | CPU（% of one core） | 备注 |
|---|---|---|
| **60512** | **18.6%** | 未知（可能是自旋或上屏） |
| 60467 | 16.2% | 主线程（PID） |
| **60498** | **12.4%** | **★ 渲染线程（NVIDIA ioctl）** |
| 60514 | 10.0% | 未知 |
| 60480 | 5.0% | 未知 |
| 其余 5 个 | 1.0–2.0% | — |

**全进程可见线程合计 = 72.6%**（8 核机，理论 800%）→ **整机 CPU 极其空闲，不到一个核。**

**渲染线程 12.4% × 30.84ms 帧时间 = 3.82ms/帧在 CPU 上。**

### 3.2 报告的结论要改

| 轮次 | 结论 | 状态 |
|---|---|---|
| 报告 62 | "渲染线程整帧占满一个核 → CPU 在生成 GL 命令" | **❌ 推翻** |
| 报告 64（本报告） | **渲染线程只占 3.82ms/帧，87% 时间在 futex 上睡** | **✅** |

### 3.3 报告 62 是怎么错的 —— 可复现的方法论错误

报告 62 用 ftrace `sched_switch` 算"切出间隔 ÷ 帧时间 = 0.95"（n27a）/ "0.98"（n27d），据此判"整帧连续在跑"。

**但同一份报告已经量化过 `sched_switch` 有大量丢失**：
`entries-written: 1058146/1058146`（缓冲满），记录到 21846 次 / 8s，而同期 `sys_sched_yield` 有 931k 次。

**丢事件的方向是"间隔变大"** —— 中间那次切换没了，两段被合并。
→ **"间隔 ≈ 帧时间"完全可能是"真实每 4ms 切一次、但记录里每 30ms 才有一条"造成的假象。**

报告 62 里我写过"用比值绕过丢事件是安全的，因为丢事件只会让间隔偏大、结论不会被夸大"。
**那个论证只在"证明它连续在跑"时成立，但反过来用就错了**：
间隔偏大 → 比值接近 1 → 我判"整帧连续"，**而真实情况是"切得很碎"**。
**这个论证方向本身就选错了。**

### 3.4 新的硬判据：`/proc` 的 utime 不可伪造

```
读两次 /proc/PID/task/TID/stat 的 utime+stime，相减 ÷ 墙钟
```
- 不依赖采样率
- 不依赖任何 trace 事件是否丢失
- 是内核自己的记账

**这类"计数器差分"应该优先于"事件间隔推断"。**

## 4. 那它在等什么：`futex_wait_queue`

### 4.1 上下文切换速率

| 指标 | 值 | 折算（帧率 32.4/s） |
|---|---|---|
| 自愿切换 | **92.6 次/秒** | **2.86 次/帧** |
| 非自愿切换 | 19.0 次/秒 | 0.59 次/帧 |

**每帧主动睡 2.86 次** —— 不是被抢占，是自己去睡。

### 4.2 wchan 采样（20 次 × 100ms）

| state | wchan | 次数 |
|---|---|---|
| **`S`** | **`futex_wait_queue`** | **16** |
| `S` | `0` | 2 |
| `R` | `futex_wait_queue` | 1 |
| `R` | `0` | 1 |

**80% 的采样点在 `futex_wait_queue` + `state=S`。**

### 4.3 与 CPU 12.4% 的自洽

```
CPU 12.4%（跑）+ 睡眠 87.6%（等）≈ 100%
每帧 3.82ms 在算 + 27.0ms 在 futex 上等
92.6 次/秒 ÷ 32.4 fps = 2.86 次/帧
27.0ms ÷ 2.86 ≈ 9.4ms/次
```

**三条独立数据（utime、ctxt_switches、wchan）互相闭合。**

### 4.4 这与既有结论的衔接

| 既有结论 | 关系 |
|---|---|
| 报告 57：主线程在 `glXSwapBuffers` 里 `sem_wait(&di.r.relsem)` 等 readback worker 提交 `glReadPixels` | **同一个机制**：`sem_wait` 在 glibc 里就是 `futex` |
| 报告 59：改 swap / 读 BACK 都不影响 | **不矛盾**：改的是"等之前做什么"，不是"等谁" |
| 报告 58：去掉 Intel 上屏只值 1.0ms | 不矛盾：上屏是另一条链 |
| 报告 63：ioctl 只占 0.7% | **自洽**：因为时间都花在 futex 上，不在 syscall 上 |

**所以 27ms 的等待对象是 primus 内部的 sem/cond，不是内核、不是 GPU。**

## 5. 这份 perf 数据的定位

perf 回答了"那 3.82ms 花在哪"：**86% 在 glcore，且分散**。

**但它没有回答"27ms 等谁"** —— 因为等待的时间不产生样本。

**两个问题的分界要说清楚**：

| 问题 | 量 | 工具 | 结论 |
|---|---|---|---|
| CPU 上的 3.82ms 在算什么 | 3.82ms | perf | **86% glcore，分散（正常 GL 代码，无异常热点）** |
| 剩下的 27ms 在等谁 | 27ms | futex 地址追踪 | **未测** |

### 6.1 一个要先排除的可能

primus 的 `sem_wait` 有 8 处（报告 57 已列出）。但要先确认：**这 2.86 次/帧的 futex 是否真在 primus 里**（而不是 glcore 内部的锁）。

- 落在 `libGL.so.1`（primus）的 `.bss` → 是 primus 的 sem
- 落在 `libnvidia-glcore` 的映射 → 是驱动内部锁

### 7.1 方法论（四条，已入技能库）

1. **定位"GPU 提交线程"不能按 ioctl 总数**。会被 Intel 上屏淹没（1558 vs 143）。
   按 **cmd 的 type 字节**分：`'d'`=DRM、`'F'`=NVIDIA。

2. **★ `/proc/PID/task/TID/stat` 的 utime 差分，优先于"事件间隔推断"**。
   本例：sched_switch 推算得"整帧占核"（0.95），utime 实测得 **12.4%**。差 8 倍。
   计数器不受丢事件影响，事件间隔会。

3. **"用比值绕过丢事件"只在特定方向成立**。
   丢事件使间隔偏大 → "间隔 ≥ 帧时间"安全（结论方向与偏置同向）。
   但"间隔 ≈ 帧时间 → 整帧连续"**不安全**：真实切得碎时，丢事件恰好也能造出这个假象。

4. **perf 的 [unknown] 必须按 tid 分解**。
   全进程采样里 `[unknown]` Self 35%，定点采样里 **0%** —— 那 35% 全来自别的线程（Heaven 的 JIT/匿名映射）。
   **不按 tid 过滤会把别人的开销算到目标头上。**

### 7.2 环境坑

- `perf record -- sleep N` 采样的是 sleep 进程本身，**必须 `-p PID`**
- `perf.data` 若被 root 创建而属主变成 `nobody`，`perf report` 要加 `-f`
- 采样 `perf script -f` 第二列在单线程时是 tid，多线程时是 pid —— **要看实际输出格式再写 awk**
