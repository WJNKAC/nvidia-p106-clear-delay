# 报告 101 / N111：580 修好了 Vulkan，但没修 GL —— 所以 zink 在 525 上无效（实测 +8%），在 580 上才是唯一未做的有效实验

- 时间：2026-10-26 15:20
- ⚠️ **2026-10-26 15:35 加注（报告 103）**：本文 §0/§1 的「580 vs 525 差 5.6 倍」**倍数不成立**。
  报告 07 的 358 是 `vkmark -b`（**全套场景综合分**），报告 93 的 64 是 `-b clear`（**单场景 fps**），两者不能相除。
  方向大概率仍对（综合分 358 不可能包含 64fps 的场景），但**必须按同一命令复测**。另：**515 的 Vulkan 从未测过**。详见报告 103。
- 触发：用户两问 ——「580 是修复了 vulkan 吗？」「使用 zink 跑 heaven 会更好吗」
- 性质：**本轮不加新采集，只做数据对齐 + 补齐一处报告遗漏**（zink 实测数据此前从未进报告）

---

## 0. 先给结论

| 问题 | 回答 |
|---|---|
| **580 修好了 Vulkan 吗** | **修好了。** 同一个 `vkmark clear`：580 = **358 fps / 2.79 ms**，525 = **64 fps / 15.6 ms**，差 **5.6 倍**。 |
| **那 580 修好了 Heaven 吗** | **没有。** 580 下 Heaven 仍是 **30 fps / 48-50 W**（报告 05 实测，同一台机器），与 525 的 30-31 fps 一样。 |
| **那 zink 跑 Heaven 会更好吗** | **在 525 上：几乎没用。** 已实测 **33-34 fps @1080p**（原生 primus GL 是 30-31），只 +8%，但功耗从 46-51 W 涨到 **58-68 W**。 |
| **那 zink 到底有没有价值** | **有，但在 580 上。** 这是目前**唯一还没做、且信息量最高**的实验（见 §4）。 |

一句话：**525 有两个病（GL 慢 + Vulkan 慢），580 只治好了后者。zink 的作用是把 GL 负载搬到 Vulkan 上，所以在 525 上是"从一个病搬到另一个病"，在 580 上才是"搬到健康的地方"。**

## 1. 三个版本的完整对账表（全部同一台物理机 <testhost>）

| | **515.105.01** | **525.116.03** | **580.126.18** |
|---|---|---|---|
| **GL 重负载**（Heaven 1080p） | **101-138 fps** / 100-110W | **30-31 fps** / 46-51W | **30 fps** / 48-50W |
| **GL 微基准**（n83a 每对成本） | **0.03 µs** | **121 µs** | 未测 |
| **Vulkan 轻负载**（vkmark clear 1080p） | 未测 | **64-66 fps** / 15.6ms | **358 fps** / 2.79ms |
| 数据来源 | 报告 79 / 05§5 | 报告 79 / 93 | 报告 05 / 07 |

**读法**：
- 515 → 525：**GL 崩了 4000 倍**（每对 0.03 → 121 µs），Vulkan 没测所以不知道。
- 525 → 580：**Vulkan 好了 5.6 倍**，**GL 一点没动**（还是 30fps）。

⇒ **"580 修复了 Vulkan"是准确的；但"580 修复了问题"是错的。**
用户 2 年前看到的 130W 满载，跑的不是 Heaven 这种每帧几百次状态切换的负载，或者跑的是 vGPU（报告 100 已证明那条路不可用 PCI 伪装复现）。

---

## 2. 为什么 580 的 Vulkan 好而 GL 不好 —— 两条不同的等待

这不是"同一个 bug 修了一半"，是**两个独立机制**：

| | GL 的 121 µs/对 | Vulkan 的每帧 13.3 ms |
|---|---|---|
| 触发条件 | **"状态切换 + 紧跟 draw"的配对**（M9 先切后画完全免费） | 与 draw 数/像素数**无关**的每帧固定项（320×240 也要 13.3ms） |
| 525 有 | 有（4000× 于 515） | 有 |
| 580 有 | **有**（Heaven 仍 30fps） | **没有**（358fps） |
| 落点 | 统一命令提交器 `glcore+0x1238920`，GPU 侧 ≈231k 周期 | 提交/呈现路径的排空轮询 |

两条机制在报告里都已定位，但**只有 Vulkan 那条在 580 被移除**。这说明 525→580 之间 NVIDIA 动了 Vulkan 的呈现路径，没动 GL 的提交器。

## 3. zink 的实测（此前从未进报告，本轮补上）

### 3.1 数据在哪、为什么漏了

`analysis/traces/n70/n70b.log` + `analysis/onmachine/n70-zink-fps3.png`、`n70-m0-fps3.png`。
这批数据 2026-10-26 09:28-09:40 采的（`n70_zink_heaven.sh`），**但只作为"zink 无效"的一句断言出现在报告 63/67 的表格里，数字从没写进任何报告**。这是记录漏洞，本轮补。

### 3.2 实测（525.116.03，`MESA_LOADER_DRIVER_OVERRIDE=zink`，`VK_ICD_FILENAMES=nvidia_icd.json`）

| 配置 | FPS | 功耗 | 利用率 | SM 时钟 |
|---|---|---|---|---|
| **zink + Heaven 1920×1080** | **32-34** | **58.6-67.7 W** | 99-100 % | 1911 MHz |
| 原生 primus GL 1920×1080（对照） | 30-31 | 46-51 W | 89-93 % | 1911 MHz |
| **zink + Heaven 640×360** | **58** | — | — | — |
| 原生 primus GL 640×360（报告 05，580 下） | 36 | 42 W | — | — |

**确认 zink 确实跑在 P106 的 Vulkan 上，不是核显**：`nvidia-smi` 全程 99-100% / 1911 MHz / 58-68W。若走 Intel ANV，功耗会是 6-10W、利用率 0%。

（Heaven 自身报 `GLRender::GLRender(): Unknown NVidia GPU` —— 它认不出这是 NVIDIA，因为 zink 报的是 Mesa 的 renderer 串。不影响渲染，但说明这条路径不在 NVIDIA 的预期内。）

### 3.3 判读：+8% 且更费电，为什么

**zink 并没有换掉 glcore，它只是换了个入口。**

报告 95 已证明：NVIDIA 的 Vulkan ICD `library_path = libGLX_nvidia.so.0`，`NEEDED libnvidia-glcore`。所以：

```
原生 GL :  Heaven → libGL(glvnd) → libGLX_nvidia → glcore → 提交器(121µs/对) → 30fps
zink    :  Heaven → Mesa zink → libvulkan → libGLX_nvidia → glcore → 提交器(Vulkan 模式) → 33fps
                                  └─────────── 同一个 glcore ───────────┘
```

zink 换来的是**提交模式**（Vulkan 的 batch 提交 vs GL 的 per-pair 惩罚），代价是 Mesa 层的 GL→VK 翻译。

在 525 上：
- 省下：268 对 × 121 µs ≈ 32 ms 的配对惩罚
- 付出：Vulkan 的每帧 13.3 ms 固定等待 + zink 翻译开销 + 每帧一次的 present 交接

净收益 ≈ +8%。功耗反而涨 30%，因为 **GPU 时间没减少，只是等待的位置从"每对一次"变成"每帧一次集中等"**，忙等更集中 → 功耗更高。

640×360 下 zink 的 58 fps 明显好于 GL 的 36 fps，因为那个档位配对惩罚占比最大（像素量极小，惩罚是纯浪费）；但**仍不到 515 的零头**，也没到 60fps。

### 3.4 所以「用 zink 跑 Heaven 会更好吗」

**在 525 上：不建议。** 33 fps 换 60-68W，相对 30 fps / 48W，性价比为负，而且引入了 Mesa 版本依赖、Heaven 认不出 GPU、截图角标不可信等杂音。

## 4. ★ 真正值得做的实验：**580 + zink**

这是本轮唯一的新建议，理由是它能把三条已知事实串成一个可测量的预测。

### 4.1 为什么这个实验信息量最高

**Heaven 4.0 没有 Vulkan 渲染器**（它只有 DX9/DX11/GL）。所以在 580 上，"Heaven 走 Vulkan 能跑多少"这个问题，**除了 zink 没有别的办法测**。

而 580 的 Vulkan 是健康的（358 fps / 2.79 ms）。于是：

| 若 580 + zink 跑出 | 结论 |
|---|---|
| **≥ 80 fps** | GL 前端就是唯一瓶颈，**zink 是 580 上的实用绕行方案**；同时证明"525 的 zink 无效"纯粹是因为 525 的 Vulkan 也病 |
| **≈ 30-35 fps** | zink 自身的翻译开销（Mesa GL→VK，Heaven 每帧上千次状态切换是 zink 最不擅长的形态）就是瓶颈，和驱动版本无关 ⇒ **zink 这条路彻底出局**，不用再试 |

**两种结果都能收口一整条分支**，这是当前最高性价比的一个实验。

### 4.2 怎么做（可直接复用现成脚本）

```bash
# 机器切到 580.126.18 后
MESA_LOADER_DRIVER_OVERRIDE=zink \
VK_ICD_FILENAMES=/etc/vulkan/icd.d/nvidia_icd.json \
  ./heaven_x64 -project_name Heaven -data_path ../ \
    -engine_config ../data/heaven_4.0.cfg -system_script heaven/unigine.cpp \
    -sound_app openal -video_app opengl -video_fullscreen 0 -video_mode 6
```

脚本已在 `analysis/probes/n70_zink_heaven.sh`（含 `nvidia-smi` 稳态采样与截图）。**只要把驱动换回 580 再跑一次，其余零改动。**

### 4.3 先验概率（我的判断）

**偏低，约 30%。** 理由：zink 对"每帧大量 `glUseProgram`/`glBindTexture`/`glDraw*` 交替"的场景翻译开销很重（每次都要翻译成 Vulkan 的 descriptor set / pipeline bind），而 Heaven 正是这种形态。参考公开数据，zink 跑 Windows 游戏移植类重负载通常只有原生 GL 的 50-80%。

若 580 的 VK 提交是 2.79ms、Heaven 纯渲染量 7ms（报告 07 的拟合），则理论上限 ≈ 1/(0.0028+0.007+zink开销)。zink 开销若能压到 5ms，就是 67fps；压不到 20ms，就还是 30fps。

**但仍必须做**——因为它同时是"zink 路线"和"GL 是唯一瓶颈"这两个判定的唯一实测入口。

## 5. 本轮不做的事（以及为什么）

| 想法 | 为什么不做 |
|---|---|
| 换 515 + zink | 515 的 GL 本来就 101fps，zink 只可能更慢。无信息量。 |
| 525 下调 zink 参数（`ZINK_DESCRIPTORS`、`zink_kopper` 等） | 即使调优到 +20%，也还是 36fps，**离 101fps 差 3 倍**，不改变结论。 |
| 用 `DRI_PRIME=1` 强制 zink 走 P106 | **已经走的是 P106**（99% / 1911MHz / 58-68W 已证）。 |
| 580 下用 DXVK/vkd3d 跑 Heaven | Heaven 4.0 的 DX11 后端要经 DXVK → 同样是 VK，但多一层 D3D 翻译，不如 zink 直接。除非 zink 失败后想交叉验证。 |

## 7. 一句话回答用户

1. **580 修好了 Vulkan（358 vs 64 fps，5.6×），但没修 GL（Heaven 还是 30fps）。**
2. **zink 在 525 上实测只 +8%（33fps），还多耗 30% 电，因为 525 的 Vulkan 本身也病。**
