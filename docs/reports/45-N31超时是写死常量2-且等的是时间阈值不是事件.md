# 45 · N31：2.065ms 是写死的 `mov $0x2,%esi`，不是按字节算——且它等的是时间/阈值，不是事件

> 2026-10-26 03:05
> 用户指令：先做 N31（纯静态，几分钟），定位 `pthread_cond_timedwait` 的调用点，看 2.065ms 是写死常量还是按字节算；
> 它的结果会影响 N32 的判读。
>
> **答案：写死。`mov $0x2,%esi`，全库只有两处，共 2 个字节。**
> 而且动态验证把 map 用的那一处也钉死了，还顺带发现**它等的是"时间/阈值"而不是"事件"**——
> **这直接改动 N32 的收益判断：修 signal routing 对这里无效。**

---

## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **glcore 里唯一真正的 "cond timedwait + ms" 只有 `0x146d280`（`wait_ms`）** | 17 处 `0xf4240`(1e6) 中只有 3 处是 ms→ns 换算，另两处是 `usleep`→`nanosleep` 和时间格式化余数 |
| 2 | **`wait_ms` 的超时值 = 参数 `ms`，函数内无写死** | `146d284: movslq %esi` → `imul $0x10624dd3`（/1000）+ `imul $0xf4240`（×1e6） |
| 3 | **全库只有 2 处传 `ms=2`**：`0x1238acc` 和 `0x163b437` | 都是 `mov $0x2,%esi` + `call *0x2d0` |
| 4 | **动态：`wait_ms` 的 ms 参数只有 2 和 100 两个值**（2 出现 3157 次，100 出现 2264 次） | N31a 实测 |
| 5 | **★ map 用的是 `0x1238acc`**（A 处），`0x163b437`（B 处）**执行 0 次** | N31b：A=2789 / B=0；A 的 2689 次来自 map worker 自己 |
| 6 | **★ A 处等的是 `ctx+0x8e0908`，而且是在一个"队列 + float 阈值"循环里，用 2ms 轮询等条件满足** | 静态 `1238a28-1238af2` |
| 7 | 所以 **2.065ms = 2ms 硬编码 + 65µs timespec 归一化/调度开销** | 2.000 → 实测 2.065 |
| 8 | **★ 它等的是"时间/阈值"，不是"某事件发生" → 修 signal routing 对这里无效** | 由 6 推出；详见 §5 |

**一句话**：**2.065ms 是硬编码的 2ms。而且这里从来就没打算用 signal——它在轮询一个时间/阈值条件，2ms 是设计好的采样间隔。**

## 2. 静态：先证明"唯一候选"

### 2.1 `0x146d280` 就是 `wait_ms(cond, ms)`

```
146d284: movslq %esi,%r13              ; r13 = ms (int 参数)
146d291: imul   $0x10624dd3,%r13,%r13  ; 魔数除法 → ms/1000 = tv_sec
146d2ab: sar    $0x26,%r13
146d29b: imul   $0xf4240,%ebp,%r14d    ; ms*1000000 → tv_nsec 部分（0xf4240 = 1e6）
146d2f8: mov    %r13,(%rsp)            ; timespec.tv_sec = ms/1000
146d2fc: mov    %rax,0x8(%rsp)         ; timespec.tv_nsec = (ms%1000)*1e6
146d301: call   gettimeofday@plt
146d30b: add    (%rsp),%rdx            ; tv_sec += now.tv_sec
146d318: add    0x8(%rsp),%rax         ; tv_nsec += now.tv_usec*1000
146d321: cmp    $0x3b9ac9ff,%rax        ; nsec > 999999999 ?
146d327: jg     146d360                ;   → 146d360: sub $0x3b9aca00 (1e9); add $1 to sec
146d33e: call   *(%rax)                ; ★ pthread_cond_timedwait(cond, mutex, &ts)
```

**函数体内没有任何写死超时**——`ms` 完全由调用者决定。

### 2.2 为什么能确定只有它

搜 `0xf4240`（1,000,000，ms↔ns 换算的指纹）共 17 处，其中**只有 3 处是 `imul`（真正的换算）**：

| 地址 | 用途 | 是 cond 等待吗 |
|---|---|---|
| `0x146d29b` | `wait_ms` 的 timespec 构造 | **是** |
| `0x146d713` | 后面是 `nanosleep@plt` → 这是 `usleep(us)` | 否 |
| `0x14701b0` | magic `0x431bde82d7b634db` 除法取余 → 时间格式化 | 否 |

→ **glcore 里"cond timedwait + ms"只有 `wait_ms` 一个出口。**

### 2.3 两处传 ms=2

```asm
; A: 0x1238acc
1238ac5: mov    0x8e0908(%rbx),%rdi     ; cond = ctx+0x8e0908
1238acc: mov    $0x2,%esi               ; ★ 2
1238ad1: call   *0x2d0(%rbp)            ; wait_ms

; B: 0x163b437
163b430: mov    0x1c0(%rbx),%rdi        ; cond = ctx+0x1c0
163b437: mov    $0x2,%esi               ; ★ 2
163b43c: call   *0x2d0(%r13)            ; wait_ms
```

**全库仅此两处。** 没有按字节算、没有变量、没有公式。

## 3. 动态验证：ms 只有 2 和 100

`n31_msprobe.sh`（uprobe `0x146d280` 读 `%esi`，PRIMUS_SLEEP=0，8s）：

| ms 值 | 次数 |
|---|---|
| **2** | **3157** |
| **100** | **2264** |

**没有第三个值。** 且 `ms=2` 的调用集中在 map worker（tid 22075 共 3068 次 wait_ms，约 **11.7 次/帧**）。

（`ms=100` 是报告 35 分析过的队列处理器 Path B 的那个初值。）

---

## 4. 钉死是 A 还是 B 处

`n31b_site.sh`（分别 uprobe 两个 `mov $0x2` 的位置 + map 边界）：

| 调用点 | 全局命中 | map worker 命中 | map 窗口内出现 |
|---|---|---|---|
| **A `0x1238acc`** | **2789** | **2689** | **143/262 窗口** |
| B `0x163b437` | **0** | 0 | 0 |

**B 处一次都没执行**（它是另一条队列路径，当前场景不经过）。

→ **map 里的 2.065ms 就是 A 处的 `wait_ms(cond@ctx+0x8e0908, 2ms)`。**

## 5. ★ A 处等的是什么：不是事件，是时间/阈值

```
1238a28: mov 0x8e0a00(%rbx),%rdx     ; 队列尾
1238a2f: mov (%rbx),%rax             ; 队列头
1238a32: cmp %rax,%rdx
1238a35: je  1238b48                  ; 队列空 → 另一分支
1238a3b: testb $0x1,0x30(%rbx)        ; 某个状态位
1238a3f: jne 1238ab1                  ; 置位 → 跳过下面的阈值判断，直接去等
        ; ---- 阈值判断（全是 float） ----
1238a41: movss 0x8e0e00(%rbx),%xmm1   ; f = ctx+0x8e0e00
1238a49: movss <0x1c52238>,%xmm3      ; 常量
1238a51: movss 0x8e0c60(%rbx),%xmm0   ; g = ctx+0x8e0c60
1238a59: comiss %xmm1,%xmm3
1238a5c: jbe  1238b08                 ; 未达阈值 → 另一分支
1238a62: (再取 f)
1238a6a: comiss <0x195d5c8>,%xmm1     ; 与 10.0 比较
1238a71: jbe  1238b08
1238a77: (再取 f)
1238a7f: mulss <0x1c5223c>,%xmm1      ; f * 10000.0
1238a87: comiss %xmm1,%xmm0           ; g 与 f*10000 比较
1238a8a: jbe  1238b08
1238a8c: comiss <0x1ad8748>,%xmm0     ; 与 1000000.0 比较
        ; ---- 真正去等 ----
1238aa0: mov $0x7,%esi
1238aa5: mov %rbx,%rdi
1238aa8: call 12386d0                 ; 其他工作
1238ac5: mov 0x8e0908(%rbx),%rdi      ; cond = pair C signal 侧
1238acc: mov $0x2,%esi                ; ★ 2ms
1238ad1: call *0x2d0(%rbp)            ; wait_ms
1238ad7: mov 0x1b8(%rbp),%rax         ; 可选的额外钩子
1238aee: call *%rax
1238af0: test %al,%al
1238af2: jne  1238a28                 ; ★ 循环回去，重新检查
```

读到的浮点常量（ELF 直读）：

| 地址 | 值 |
|---|---|
| `0x195d5c8` | **10.0** |
| `0x1c5223c` | **10000.0** |
| `0x1ad8748` | **1000000.0**（= 1e6，微秒→秒的量级） |

**这三个常量 + 两个 float 字段（`0x8e0e00` / `0x8e0c60`）+ 一个循环**
→ 这不是"等某个事件发生"，而是 **"每 2ms 醒一次，检查队列/时间/阈值条件是否满足"**。

### 5.1 这对 N32 意味着什么（关键）

用户的判断是"N32 修 signal routing 能拿到数量级收益"。**现在必须修正**：

| 情形 | 修 signal routing 有收益吗 |
|---|---|
| 等待是"数据就绪 → signal 叫醒我" | ✅ 有，且可能是数量级的 |
| **等待是"时间/阈值到了没" → 轮询检查** | ❌ **没有**。这种条件本来就没有"事件"可发 |

**A 处是第二种。** 所以：

> **修 signal 路由**让这个循环提前退出——**因为退出的条件不是"收到通知"，而是"阈值满足"。**

**真正的杠杆变成了：那两个 float 阈值（`0x8e0e00` / `0x8e0c60`）和循环退出条件是什么、能不能调。**

### 5.2 但别急着推翻 N32：还有一个可能

`wait_ms(cond@0x8e0908, 2)` 用的 cond 是 **pair C 的 signal 侧（`0x908`）**。
而报告 43 验证过 pair C 内部两槽指向**同一个对象**（`0x908` 与 `0x948` 相等），
且 `0x1238d9c` 的 signal 也打在这个对象上。

**所以理论上 signal 是能提前唤醒它的。** 只是当前代码逻辑**没依赖**这个唤醒——
它醒来后仍然要重新检查阈值（`jne 1238a28` 循环回去）。

→ **即使 signal 立刻到达，循环也不会退出**，因为退出取决于阈值判断，不是"是否被唤醒"。

**这就是 92.9% 超时的直接解释：signal 来了也只省掉当次 2ms，下一轮照样按阈值继续等。**

## 6. 一个必须标注的边界

A 处的循环里还有一个分支我没解完：

```
1238a59-1238a8a: 三个 float 比较，jbe 的都跳到 1238b08
1238b08: comiss 0x1ad8748(=1e6),%xmm0
1238b0f: jbe 1238b2a
...
```

`1238b08` 之后的逻辑（阈值不满足时走哪条、会不会也是 wait）本轮没读完。
**它可能是"短等"和"长等"两个分支**——若有另一个分支带更大的超时值，能解释默认配置下的行为差异。

**不影响 §1 的核心结论**（2 是写死的、map 走 A 处），但影响"怎么改"。

### 8.1 一个方法论收获

**"参数是常量还是公式"这个问题，动态比静态快。**
静态只能证明"没有立即数常量"，但参数可能是从变量来的；一次 uprobe 读寄存器（`ms=%si:s32`）
就拿到 5421 个样本的两个取值（2 / 100），比继续读汇编快得多。

**顺序建议**：静态定位**候选**（本例 2 处 `mov $0x2,%esi`）→ 动态**验证取值与归属**（本例 A/B 谁真跑）。
两步都做完才敢说"是写死的"。
