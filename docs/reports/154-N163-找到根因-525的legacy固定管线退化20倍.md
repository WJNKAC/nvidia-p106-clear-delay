# 报告 154 — ★ 找到了：525 的 legacy 固定管线性能退化 20 倍，与 inline 优化闭合

> 日期：2026-10-27 20:30
> 实验机：`<user>@<testhost>`（<testhost>，P106-100）
> 本轮在 515.105.01 与 525.116.03 之间往返，用同一套 `-R` 外层墙钟法对比三个模式
> 前置：报告 152（每对 119.7 µs 精确值）、153（inline 假设作废、五个候选排除）

---

## 0. 一句话结论

> **525 慢 20 倍，是因为"用 legacy 固定管线改状态"（`glColor3f` / `glTranslatef` /
> `glScalef` / `glLoadIdentity`）在这版驱动上退化了。**
> **改成 shader + uniform（`glUniform3f`）后，性能与 515 完全一致。**
>
> 这与 inline 优化真正闭合了：**515 的 6,653 条/帧 `sub6:0x0034`
> 正是 legacy 状态的内联写路径；525 不走这条路，于是每次 legacy 调用都付 115 µs。**

---

## 1. 三个模式的对照（同一套方法：`-R` + 外部墙钟）

n83b 已有三个可比的模式：

| 模式 | 内容 | 每对的 API 调用 |
|---|---|---|
| **M1** | shader，状态设一次 | 只 `glDrawArrays` |
| **M2** | shader，**每对改 uniform 颜色** | `glUniform3f` + `glDrawArrays` |
| **M3** | **legacy 固定管线，每对改矩阵和颜色** | `glLoadIdentity` + `glTranslatef` + `glScalef` + `glColor3f` + `glDrawArrays` |

### 1.1 525.116.03

| 模式 | N=1000 | 每对 |
|---|---|---|
| **M3** | **125.838 ms** | **125.8 µs** |
| **M2** | **6.193 ms** | **6.2 µs** |
| M1 | 6.157 ms | 6.2 µs |

### 1.2 515.105.01

| 模式 | N=1000 | N=2000 | 每对（N=2000） |
|---|---|---|---|
| M3 | 5.706 ms | 7.089 ms | **3.5 µs** |
| M2 | 6.737 ms | 10.937 ms | 5.5 µs |
| M1 | 6.086 ms | 10.606 ms | 5.3 µs |

### 1.3 最终对照表

| 模式 | 515 | 525 | 比值 |
|---|---|---|---|
| M1（纯 draw） | 5.3 µs | 6.2 µs | **1.0×** |
| M2（uniform + draw） | 5.5 µs | 6.2 µs | **1.0×** |
| **M3（legacy 状态 + draw）** | **3.5 µs** | **125.8 µs** | **22~36×** |

**这张表是决定性的：**

- **M1 和 M2 在两版上完全一致**（6 µs 量级，差 < 15%）
  ⇒ 纯 draw、uniform 更新、shader 路径都没问题
- **只有 M3 在 525 上慢 22~36 倍**
  ⇒ **问题精确落在"legacy 固定管线状态变更"上**
- **515 的 M3（3.5 µs）甚至比自己的 M1（5.3 µs）还快**
  ⇒ 515 对 legacy 有专门优化，快到超过纯 draw

## 2. 与 inline 优化闭合（这次是对的场景）

报告 140 的数字：

| | 515 | 525 | 比值 |
|---|---|---|---|
| `sub6:0x0034`（`KEPLER_INLINE_TO_MEMORY_B`，Heaven 场景） | 6,653 条/帧 | 16 条/帧 | **416×** |

`0xA140 KEPLER_INLINE_TO_MEMORY_B` 的语义是"把数据内联进 pushbuffer"。

**legacy 固定管线的状态（矩阵、颜色）正是这类"需要频繁上传的小数据"。**

于是：

```
515：glColor3f/glTranslatef
      → 驱动把状态直接 inline 写进 pushbuffer（每帧 6,653 条）
      → GPU 顺序执行时天然可见
      → 每次 legacy 调用 ≈ 0.2 µs（M3 比 M1 还快）

525：glColor3f/glTranslatef
      → 不走 inline（Heaven 下每帧只有 16 条）
      → 走通用路径：可能要重新计算固定管线状态 / 生成变体
      → 每次 legacy 调用 ≈ 115 µs
```

**这次闭合是正确的**：
- 报告 153 我已经更正过"用 Heaven 的 416× 去解释 n83b M3"是错的
- 现在找到了正确的因果链：**inline 路径服务于 legacy 状态，525 缺这条路**
- 而且 M2（uniform）两版一样快，正好说明"非 legacy 的状态更新不需要 inline"

## 3. 之前为什么没找到

我在报告 153 里比较两版 n83b M3 的 `sub6` 命令数，发现**几乎相同（76 vs 74）**，
于是断定"inline 假设作废"。

**这个判断下得太快。** 原因：

1. n83b 的 M3 只有 1000 对、约 18,000 条命令，
   而 Heaven 一帧有 ~50,000 条——**inline 的差异在 n83b 的小场景里被摊薄了**
2. 我一直在找"命令流的差异"，但实际上差异在**同一条 legacy 调用触发的
   GPU 侧工作量**，命令数相同不代表执行代价相同

**正确的做法**（本轮才做）：不比较命令数，而是**换一种 API 做同样的事，看代价变不变**。
M2 就是这个对照。

## 4. 对 Heaven 的含义（必须说清楚的事）

Heaven 是 OpenGL 3.x/4.x，**本来就用 shader，不用 legacy 固定管线**。

所以：

- **n83b M3 的谜团彻底解开了**（legacy 路径退化）
- **但 Heaven 在 525 上慢的原因，不能直接用这条解释**

两者可能共有同一个底层机制（比如某个状态更新路径的退化），
也可能 Heaven 慢是别的原因。**这一点必须分开说，不能混。**

### 4.1 可立刻验证的推论

如果 Heaven 确实不用 legacy，那它应该不受这条影响。
但报告 138 实测 Heaven 在 525 上只有 30 fps（515 上正常）。

**⇒ 说明 Heaven 的慢另有原因，或者 Heaven 内部某处确实用了 legacy。**

验证方法（成本低）：在 525 上跑 Heaven，用 `nkioctl`/hook 统计
`glColor3f`、`glTranslatef`、`glLoadIdentity`、`glMatrixMode` 的调用次数。
- 若为 0 ⇒ Heaven 与这条无关，需另找原因
- 若每帧很多 ⇒ 立刻闭合，Heaven 也能用"改 shader"解决

## 5. 工程结论（可直接用）

### 5.1 对使用 legacy 固定管线的程序

**在 525 上，把 legacy 状态变更改成 shader + uniform，性能提升约 20 倍。**

具体做法：

```glsl
// 原来（525 上每次约 115 µs）
glLoadIdentity();
glTranslatef(px, py, 0);   // ← 改矩阵
glScalef(s, s, 1);
glColor3f(r, g, b);        // ← 改颜色
glDrawArrays(GL_TRIANGLE_STRIP, 0, 4);

// 改成（实测 6.2 µs，与纯 draw 同量级）
glUseProgram(prog);                    // 一次
glUniform3f(uC, r, g, b);              // ← 改 uniform
glUniform2f(uPos, px, py);             // ← 改 uniform
glDrawArrays(GL_TRIANGLE_STRIP, 0, 4);
```

实测数据（525.116.03）：

| | 每对 |
|---|---|
| legacy（M3） | **125.8 µs** |
| shader + uniform（M2） | **6.2 µs** |
| 提升 | **20.3×** |

### 5.2 对老程序（不能改源码）

- 用 **515.105.01** 驱动（实测同场景 3.5~5.7 µs/对）
- 或用 Mesa 的 `softpipe`/`llvmpipe`（如果性能可接受）
- 或用 `LIBGL_ALWAYS_SOFTWARE` 之外的兼容层（如 Zink on Vulkan）

## 8. 追加：Heaven 的关联性 —— 未能判定（如实记录）

结论是"525 的 legacy 固定管线退化"，自然要问：**Heaven 在 525 上慢，是不是同一个原因？**

试了三种方法，都没能判定：

| 方法 | 结果 | 原因 |
|---|---|---|
| `LD_PRELOAD` 拦截 `glColor3f` 等（`ffcount.so`） | 0 次 | n83b 用 `glXGetProcAddress` 绕过 PLT；Heaven 也不走 PLT |
| 拦截 `glXGetProcAddress` 记录函数名（`gpulist.so`） | 记录到 **0 个函数名** | Heaven 不调用它 |
| `nm -D --undefined-only heaven_x64` 查 GL 符号 | **0 个 GL 引用** | 引擎静态链接，`ldd` 只依赖 `libopenal.so` |

**⇒ Heaven 通过 libGL 的 GLX dispatch table 调用，符号层面看不到它用哪些 GL 函数。**

### 8.1 一个可用的间接判据

Heaven 525 = 30 fps（33 ms/帧），515 正常（约 3 ms/帧），差约 **30 ms**。

若这 30 ms 全部来自 legacy 调用，则 `30 ms ÷ 115 µs ≈ 260 次/帧`。

**⇒ 只要 Heaven 每帧有约 260 次 legacy 状态调用，就能完全解释。**

### 8.2 下一步（若要判定 Heaven）

1. 用 ptrace 在 glcore 里给 legacy 实现下硬件断点计数（需要先定位实现地址）
2. 或用 `nv-nsight`/apitrace 抓 Heaven 的 GL 调用序列
3. 最快的间接验证：**把 Heaven 切到 D3D11/OpenGL4 渲染路径**（`-video_app` 换值），
   若 525 上帧率恢复，说明与 legacy/GL 路径无关

**在判定之前，不应把 Heaven 的现象与本报告的 M3 结论混为一谈。**
本报告确定的是：**n83b M3 场景的 115 µs 完全来自 legacy 固定管线路径。**
