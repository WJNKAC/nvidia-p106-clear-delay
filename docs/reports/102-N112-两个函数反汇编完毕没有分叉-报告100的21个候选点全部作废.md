## 0. 先说两个我自己的错

### 错 1：`objdump --start-address` 用错了地址空间（本轮现犯）

`.o` 里有三套地址：

| 用途 | 取值来源 | 关系 |
|---|---|---|
| 符号值（`nm` 输出） | VMA，`.text` 段 VMA = 0 | — |
| **`objdump --start-address`** | **要 VMA** | **= `nm` 的值，直接用** |
| 在文件里 `seek` 读字节 | 文件偏移 | **= `nm` 值 + `0x40`** |

我上一轮扫描得到的是**文件偏移**（0xb11ed1），却直接喂给了 `objdump --start-address`。
结果反汇编出来的根本不是那个位置（差 0x40 = 64 字节 = 十几条指令），**我一度以为"前面根本不是那个 idiom"**。
`n111b_symmap.py` 当时是对的（它做了 `off - 0x40`），错的只是我手敲的 objdump 命令。

### 错 2：报告 100 §9 的「21 个候选点」全部是假阳性 —— **整节作废**

那些点是靠"扫 `and r32, 0x00030000`"找来的。问题是：
**`0x30000` 在 RM 里是"某个 32 位描述符的 bit 17:16"这个通用位置的常见掩码**，
而"把 2 位字段搬到 bit 17:16"这个动作在 PTE 组装、PCI 配置字拼装、内存描述符构造里随处可见。

**判定"它是不是 PMC_BOOT_1"的唯一标准，不是掩码等于 0x30000，而是"这个值是不是从寄存器偏移 0x4 读出来的"。**
我跳过了这一步，直接按掩码形状猜，猜错了。

## 1. `_nv035724rm` 是什么：NVSwitch，`and 0x30000` 是 PTE 的 bit 38:37

先看它自己的断言串（`.rodata+0x269a65c`）：

```
NVSwitch: Assertion failed
```

再看 `+0x4e1` 所在那段（正确 VMA，`0xb11e91`）：

```asm
b11e84:  shl    $0xc,%ecx        ; ecx << 12
b11e87:  shl    $0x10,%eax       ; eax << 16
b11e91:  and    $0x30000,%ecx    ; (ecx<<12) & 0x30000  = (ecx & 0x30) << 12
b11e97:  and    $0x30000,%eax    ; (eax<<16) & 0x30000  = (eax & 0x3)  << 16
b11e9c:  shr    $0x10,%r12d
b11ea4:  or     %esi,%eax
b11ea6:  or     %ecx,%r12d
b11ea9:  shl    $0x15,%rax       ; << 21  ⇒ bit 17:16 落到 bit 38:37
b11ead:  shl    $0x15,%r12
b11eb1:  mov    %rax,0x30(%rdx)  ; 写进描述符
b11eb8:  mov    %r12,0x38(%rdx)
b11e65:  shl    $0x27,%rbx       ; 另一路 << 39
b11e69:  movq   $0x0,0x28(%rdx)
```

**这是 64 位页表项（PTE）的组装**：物理地址高位 << 39、属性位 << 21 落到 bit 38:37、其余字段按位塞进 `0x28/0x30/0x38` 三个 qword。
`shl 21` 之后再 `and 0x30000` 得到的 0x30000 掩码，语义是"PTE 的 bit 38:37"，**和 `PMC_BOOT_1[17:16]` 是巧合**。

它调用的符号也印证：`nvswitch_os_memset`、`nvswitch_os_assert_log`。

**⇒ 这个候选点彻底出局。**

## 2. `_nv016286rm` 的 4 处：内存描述符 bit 17:16 的读-改-写，**零条件跳转**

四处（`+0x3370 / +0x33e9 / +0x3749 / +0x37b9`）是**逐字节相同的同一段代码**：

```asm
mov    0xfc(%rbp),%edx       ; 取一个 32 位值（来自下面的 getter）
mov    0x138(%rbx),%eax      ; 读当前描述符
shl    $0x10,%edx
and    $0x30000,%edx         ; 值的 bit 1:0  →  描述符的 bit 17:16
and    $0xfffcffff,%eax      ; 清掉目标 bit 17:16
or     %eax,%edx
mov    %edx,0x138(%rbx)      ; 写回
```

**整段没有一条 `cmp`/`test`/`jcc` 作用在这个 2 位值上。** 它是纯粹的"把 A 的 bit1:0 抄到 B 的 bit17:16"。

那个 32 位值来自 getter `.text+0x1ac38c`（在 `_nv015749rm` 内，`+0xd50` 起）：

```asm
1ac394:  cmp    $0x2,%edi
1ac397:  je     1ac3c0          ; ==2 → *rsi = 2
1ac399:  ja     1ac3b0          ; > 2 → 走下面
1ac39b:  xor    %eax,%eax
1ac39d:  test   %edi,%edi
1ac39f:  setne  %al
1ac3a2:  mov    %eax,(%rsi)     ; 0→0, 1→1
...
1ac3b0:  cmp    $0x3,%edi
1ac3b3:  jne    1ac3d0          ; >3 → NV_ERR assert
1ac3b5:  movl   $0x3,(%rsi)     ; 3→3
```

**这是一个 2 位枚举的恒等映射（0→0、1→1、2→2、3→3，>3 报错）。**
输入来自 `[rbx+0x1f0]`（`1bc950: mov 0x1f0(%rbx),%edi`）。

**⇒ 4 处都是无条件赋值。既不分叉，也不读寄存器。这个候选点出局。**

## 3. 为什么"P40-2B 与 P106 分叉"在结构上不可能

三条独立理由，任何一条都足够：

### 3.1 `P40-2B` 不是代码路径，是一条配置记录

`GRID P40-2B` 是 vGPU **profile 名**：`2` = 2 GB 帧缓存、`B` = 图形类。它对应 `NVA081_CTRL_VGPU_INFO` 里的一行
（`vgpuName="GRID P40-2B"`、`profileSize=2GB`、`bar1Length`、`vdevId/pdevId`…），由**宿主**的 vGPU 管理器消费。

驱动代码里**不存在** `if (profile == P40_2B)` 这种分支——只有宿主 vGPU 管理器按 profile 切显存、算 bar1。

### 3.2 device id 在 `.text` 里零真比较（报告 100 §1）

`0x1c07` 全库 0 处真立即数比较；`0x1b38` 仅 1 处（在 vGPU 类型查询路径上）。
device id 唯一用途是 `rm_is_supported_pci_device()` 的白名单 bool。

### 3.3 P40 与 P106 共享 `GPU_ARCHITECTURE_PASCAL = 0x0130`（报告 100 §6）

HAL 分派粒度是 arch。命令提交器、pushbuffer 格式、`SEMAPHORE_*` 语义、`kchannel` 调度，
对 GP102 与 GP106 是**同一份代码**。

## 4. 真正的答案：差异在**设备边界**，不在代码里

这是本轮要落下的核心认知。

vGPU 里 guest 驱动跑的确实是"同一个" nvidia.ko，但它面对的设备不是硅片：

```
物理机直通                         vGPU guest
─────────────                      ────────────────────────────
nvidia.ko                          nvidia.ko
  ↓ MMIO 直写 BAR0                   ↓ MMIO 触发 VM exit
硅片的 PGRAPH/PFIFO 寄存器         宿主 nvidia-vgpu-v2 截获并转发
  ↓                                 ↓ 宿主 RM 真正编程硅片
引擎真的重新 arming                （宿主可能替多个 VM 合批）
```

**所以"vGPU 下 130W、物理机 30fps"不是驱动走了另一条分支，而是驱动在对一个不同的设备说话。**
guest 侧那 121 µs/对（= 约 231k GPU 周期、与几何/负载/变更数全无关的固定项）
是**物理引擎重新 arming 的代价**；在 vGPU 里这一步由宿主代做，且不按 guest 的每次 draw 对齐。

**这解释了所有观察，且预测"找不到分叉"——这正是我们实测到的。**

也解释了为什么 525/535/570 在 vGPU 下都不回退（用户最早的质疑）：**因为那条路径压根没被这些版本改动过**，
它被 vGPU 整个替换掉了。

## 5. 判决：要不要 580

### 5.1 先摆事实（全部已有实测，不新采集）

> ⚠️ **2026-10-26 15:35 加注（报告 103）**：下表"Vulkan · vkmark clear"一行里，
> **580 的 358 fps 是 `-b`（全套综合分）**，525 的 64 fps 是 `-b clear`（单场景），**两者不可直接相比**；
> 且 580 那次的原始输出没有留档。⇒ **"580 修好 Vulkan 5.6×"降级为弱证据**，
> 并且 **515 的 Vulkan 一格是空的、从未测过**。§5.2 决策表中"580 的 GL 还是 30fps"不受影响（那是报告 05 的实测）。

| | 515.105.01 | 525.116.03 | 580.126.18 |
|---|---|---|---|
| GL · Heaven 1080p | **101-138 fps** | 30-31 fps | **30 fps** |
| GL · n83a 每对 | 0.03 µs | 121 µs | 未测 |
| Vulkan · vkmark clear | 未测 | 64-66 fps | **358 fps** |

**580 修好了 Vulkan，没修 GL。** 所以：

### 5.2 决策表

| 你的目标 | 要不要装 580 | 理由 |
|---|---|---|
| **让 Heaven / 老 GL 游戏跑起来** | **不要** | 580 的 GL 还是 30fps（报告 05 实测）。留在 **515** 才是唯一解。 |
| **验证 zink 这条路值不值** | **要** | 580 + zink 是"Heaven 走 Vulkan 能跑多少"的**唯一**测法（Heaven 4.0 没有 VK 渲染器）。一次实验能收口整条分支（报告 101）。 |
| **日常用这张卡 + 需要新驱动** | **要，但先测 zink** | 若 zink 在 580 上 ≥80fps，580+zink 就是"新驱动 + 可用性能"的唯一组合；否则只能钉在 515。 |
| **继续查 121µs 的根因** | **不要** | 580 与 525 的 GL 表现一致，换过去不产生新信息。 |

### 5.3 我的建议：**先做 vGPU 实验，580 排在后面**

理由是比较成本：

| 实验 | 成本 | 能回答什么 |
|---|---|---|
| **vGPU 复现**（报告 100 §8） | 装 `-vgpu-kvm` 宿主包 + 配 unlock + 起一台 VM，约 1-2 小时，需重启 | **121µs 到底是不是"物理提交"的代价** —— 这是本案最后一块拼图 |
| **580 + zink**（N111-A） | 换驱动 + 跑一条命令，约 20 分钟 | zink 路线死活（先验 ~30% 有效） |

**vGPU 实验回答的是"为什么会这样"，zink 回答的是"有没有绕法"。**
前者是一次性的根因确认，后者只是一个可用性选项。而且——
**如果 vGPU 实验证明 121µs 就是物理提交的固有代价，那"钉在 515"就是唯一正解，zink 那条分支也不用试了**（zink 在 525 上已经证明救不了）。

所以顺序：**vGPU 实验 → 若结论为"固有代价"则收口并钉 515；若结论为"可绕"再考虑 580+zink。**

若你不想折腾 vGPU（要重启、要装宿主包），那就直接 580 + zink，20 分钟拿到一个 yes/no。
