# 44 · N27 就地观测：map 的 30ms = 15 次 × 2.065ms 的 futex 超时轮询，通知几乎从不来

> 2026-10-26 02:20
> 用户指令：N27 就地观测，不改被测软件，只在真实进程里挂探针，看那 30ms 里 worker 到底在干什么。
> 预注册判读表：98% 睡 futex → 追 waker；running 烧 CPU → 看自旋循环；有 poll/ioctl(X) → 等 X server；off-CPU 非 futex → 被调度走。
>
> **结果直接命中第一行，而且比它更精确：不是"等通知"，是"超时轮询"——93% 的等待是 ETIMEDOUT，通知几乎从不来。**
> 并且第一次量化出了那个固定量：**单次 futex 超时 = 2.065ms（p10–p90 只差 24µs）**。

## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **map 期间 worker 93.0%（默认）/ 70.4%（nosleep）的时间睡在 futex 上** | 503 / 2803 次 WAIT 配对 |
| 2 | **窗口内 0 次 ioctl、0 次 read/write/poll/sendmsg** → 不与 X server、不与内核驱动交互 | 269 窗口全查 |
| 3 | **★ PRIMUS_SLEEP=0 时：每窗口 15 次 WAIT，92.9% 是 ETIMEDOUT** | 2603/2803 |
| 4 | **★ 单次超时 = 2.065ms，p10 2.054 / p90 2.078（跨度 24µs）→ 固定常量** | 2603 个样本 |
| 5 | **★ `15 × 2.065 = 30.98ms ≈ map 的 30.403ms`** → map 就是 N 次固定超时的累加 | 算得上 |
| 6 | 默认配置下同理：`1 次超时(2.07) + 1 次被唤醒(0.887) = 2.96ms ≈ map 2.986ms` | 一致 |
| 7 | `sched_switch` 里 worker 切出时 **prev_state = S（主动睡）1184 次 / R（被抢占）2 次** | 1186 次切出 |
| 8 | 全进程 `sched_yield` **113,363 次/秒**，其中 tid 20259 一个线程占 830,721 次 | 8s 采样 |

**一句话**：**map 不是在等一个"会来的通知"，而是在**每 2.065ms 醒一次**看数据到了没；一帧 30ms 就是醒 15 次。通知在 92.9% 的轮次里根本没来。**

## 2. 一个必须记下的探针坑（本轮第二次踩）

第一次分析得出"窗口内 0 个 syscall → 用户态自旋"，**这是错的**。

原因：报告 24 就已记录过——**ftrace 合并格式下事件名是 `sys_futex`，不是 `sys_enter_futex`**。
`t8_*` 脚本用的是后者（那是 t8 时代的事件名），我沿用后**匹配到 0 条**，
而 `Counter` 不会报错，直接输出"没有 syscall"。

**修正后立刻看到 503 次 WAIT。**

> 教训强化：**"窗口内没有 X"这类阴性结论，必须先打印该事件名的总计数**。
> 若总计数为 0，说明事件名/过滤器错了，而不是"真的没有"。

原始 trace 里一眼就能看出来（一个完整 map 窗口）：

```
mb_in
sys_futex(uaddr: ...d80, op: 81)        ← 0x81 = WAKE|PRIVATE，叫醒别人
sys_futex -> 0x1
sys_futex(uaddr: ...d40, op: 189, ...)  ← 0x189 = WAIT_BITSET|PRIVATE|CLOCK_REALTIME
  sched_switch: prev_state=S            ← 睡下
sys_futex -> 0xffffff92                 ← ★ -110 = ETIMEDOUT，等了 2086µs
sys_futex(uaddr: ...9e00, op: 81)       ← 再叫醒别人
sys_futex -> 0x0
sys_futex(uaddr: ...d40, op: 189, ...)  ← 再等一次
  sched_switch: prev_state=S
sys_futex -> 0x0                        ← 这次被唤醒，990µs
mb_out
```

## 3. 两组对比（同一脚本，只差 PRIMUS_SLEEP）

### 3.1 默认 autosleep=90

| 指标 | 值 |
|---|---|
| map 窗口 | 269 个，中位 **2.986 ms** |
| 窗口内 futex WAIT | **503 次** = 每窗口 **2 次**（中位 2，max 2） |
| 被唤醒 (0) | 253（**50.3%**） |
| **超时 ETIMEDOUT** | 250（**49.7%**） |
| **超时耗时** | 中位 **2.070 ms**，p10 2.056 / p90 2.076 |
| 被唤醒耗时 | 中位 0.887 ms，p10 0.468 / p90 1.127 |
| WAIT 总时长占窗口 | **93.0%** |
| 窗口内 ioctl / read / write / poll | **0 / 0 / 0 / 0** |

### 3.2 PRIMUS_SLEEP=0（map = T_land）

| 指标 | 值 |
|---|---|
| map 窗口 | 267 个，中位 **30.403 ms** |
| 窗口内 futex WAIT | **2803 次** = 每窗口 **15 次**（中位 15，max 16） |
| 被唤醒 (0) | 193（6.9%） |
| **超时 ETIMEDOUT** | **2603（92.9%）** |
| **超时耗时** | 中位 **2.065 ms**，p10 2.054 / p90 2.078 |
| 被唤醒耗时 | 中位 0.717 ms |
| WAIT 总时长占窗口 | **70.4%** |

### 3.3 两组合起来看

```
默认：      1 次超时 2.070 + 1 次唤醒 0.887 = 2.96 ms   ≈ map 2.986  ✅
nosleep：  14 次超时 × 2.065 + 1 次唤醒 0.717 = 29.6 ms ≈ map 30.403 ✅
```

**同一个 2.065ms 常量，在两种配置下都成立。** 差别只是"要醒几次"：

- 默认：`usleep` 已经等掉 27.75ms，拷贝快落地了 → map 只需醒 2 次；
- nosleep：`usleep=0`，全部 30.4ms 都要靠 map 自己醒 → 醒 15 次。

**→ 那个"5.1 倍差距"（autosleep 的 9× 放大）的真相是：它把"醒 15 次"换成"醒 2 次"。**
`map` 的时长 = **⌈剩余等待时间 / 2.065ms⌉ × 2.065ms**。

## 4. 按用户判读表逐行对

| 预注册判读 | 实测 | 判决 |
|---|---|---|
| 98% 睡 futex → 驱动内部等完成通知，追 waker | **93.0% / 70.4% 睡 futex** | **✅ 命中（方向对）** |
| running 烧 CPU → 驱动自旋等 DMA | `prev_state`: S=1184 / R=**2** | ❌ 不是自旋 |

**所以四个候选里选中的是第一个：驱动内部等**。而且不涉及 X、不涉及双 Display、不涉及 CPU 竞争。

**但比"等通知"更进一步**：`92.9% 是 ETIMEDOUT` —— **通知在绝大多数轮次里根本没来**。
这不是"通知来晚了"，是"通知基本不发"。

## 5. 这个 2.065ms 是什么

### 5.1 它是 glibc 的 `pthread_cond_timedwait`

```
op = 0x189 = 0x100(CLOCK_REALTIME) | 0x80(PRIVATE) | 0x09(WAIT_BITSET)
val = 0x4c0            ← bitset
utime = <一个 timespec 指针>
返回 -110 (ETIMEDOUT)  ← 睡满超时值
```

`WAIT_BITSET + CLOCK_REALTIME + 带 timespec` 正是 `pthread_cond_timedwait` 的实现形态
（与报告 24 在 glcore `0x146d340` 处看到的 cond 等待同构）。

### 5.2 值是 2.065ms —— 极可能是"2ms 超时 + 65µs 唤醒/调度开销"

`p10=2.054 / p90=2.078`，跨度 **24µs**（1.2%）。这个集中度只可能来自**固定常量超时**。

### 5.3 它与报告 28/29 的"1ms 量化"什么关系

报告 28 在 `rb_lat2`（另一条路径）上测到 640×360 三簇 **1.05 / 2.1 / 3.0ms，间距 1.0ms**。

- **2.1ms 那一簇 = 本报告的单次超时 2.065ms** ✅ 对得上
- 但 1.05ms 簇（半程）与"1.0ms 间距"**用 2.065ms 常量解释不了**

两种可能：
1. `rb_lat2` 走的是另一条内部实现（它的 map 可能不经过同一段 glcore 代码）；
2. 那次的分辨率/像素量不同，超时值本身是**按数据量算的**（例如 `ceil(bytes/带宽)`）。

**→ "1ms 量化"应改成"存在一个固定超时轮询，其值在本次测量中是 2.065ms"。**
在下结论之前需要在 `rb_lat2` 上重做一次同样的 futex 解码（N29）。

### 5.4 地址归属：没能落地（诚实标注）

`uaddr` 每次运行都变（n27a `7f48…`、n27d `7f66…`），是动态分配的。
本轮想用 `/proc/PID/maps` 反查它落在 `libnvidia-glcore.so` 的 `.bss` 还是匿名映射，
但 **`sudo cp` 到 NFS 失败**（root 被 squash），maps 没保存下来。

不影响主结论（超时的集中度已足够说明是固定常量），但**归属仍需补测**（N30）。

## 6. 这直接指向"修"的落点

### 6.1 为什么"通知几乎不来"

报告 38 已给出一半答案：`123af7f` 的 notify 发的是 **pair-C（`ctx+0x948`）**，
而队列处理器等的是 **pair-B（`ctx+0x950`）**——**两个不同的 cond 对象**。

本报告补上另一半：**map 里等的是又一个不同的 futex**（uaddr 每次变、与 ctx 里那三对 cond 都不同族）。

→ **926 次超时意味着：这些等待对象上的 signal 从来没有被正确发出。**

### 6.2 可动的三个杠杆（按可行性排）

| 杠杆 | 做法 | 预期 |
|---|---|---|
| **★ 缩短超时值** | 2.065ms → 0.5ms，map 从 30.4 → ~7.5ms（醒 15 次变 60 次，但每次更短）；总等待 = 落地时刻，不会更快 —— **但能减少"醒得太晚"的损失** | 需要 patch 那个常量（在 glcore 里，静态可定位） |
| **★ 让通知真的发到** | 修 cond 路由（signal 发到 wait 的那个对象） | 最优解：map 直接掉到 ~0（落地即返回）；但需要找到两边的对应关系 |
| **减小 autosleep** | 已证无效（报告 26：`PRIMUS_SLEEP=0` 只快 2ms） | ❌ 别试 |

**注意**：缩短超时**不会**减少总等待（数据落地要那么久就是那么久），
它的价值在于**减少"落地了但还在睡"的浪费**。
默认配置下这个浪费 = `2.070（超时）− 实际落地时刻`；如果落地发生在 sleep 期间，浪费 ≈ 0。
**所以缩短超时对当前场景收益有限**——真正的杠杆是"让通知发对"。

### 6.3 与"11 倍空间"的关系（报告 40）

报告 40 说真实 `T_land` = 30.4ms，是物理下限的 11.2 倍，且**隔离环境贴着下限（2.48ms）**。
本报告说明：

**那 11 倍不是"传输慢了"，而是"传输完了但没人告诉它"。**
隔离环境里 `glMapBuffer` 是自家写的，写完就返回；真实进程里 glcore 的 PBO 完成通知走错了对象，
只能靠 2.065ms 一轮的超时发现。

**→ 这正好解释了为什么隔离环境永远复现不出来（8 项结构差全消，报告 43）：
差异不在 GL 调用结构，而在 glcore 内部的通知路由。**

### 8.1 三个操作细节

1. **`sched_switch` 的 filter 必须同时包含 `prev_pid` 和 `next_pid`**：
   ```bash
   echo '(prev_pid >= P && prev_pid <= M) || (next_pid >= P && next_pid <= M)'
   ```
   只写 `prev_pid` 会漏掉"被调入"事件，导致 off-CPU 时间算成 **120%**（>100% 就是算式错的信号）。
2. **`PRIMUS_SLEEP=0` 的 trace 有 1146 万行 / 826MB**：`sched_yield` 每秒 11 万次把它冲爆。
   分析前先 `grep -E "mb_in:|mb_out:|sys_futex"` 裁剪到 64 万行。
3. **`prev_state` 是判断"睡 vs 抢占"的关键**：`S`=主动睡、`R`=被抢占、`D`=不可中断。
   本报告 `S=1184 / R=2` → 立刻排除"CPU 竞争"这个候选。
