# 报告 128 / N137：**实锤 —— 改 1 个 bit，127.09 ms → 1.42 ms（85×）**

> 时间：2026-10-27
> 环境：<user>@<testhost>（`<testhost>`），P106-100，headless X `:2`
> 触发：用户指定「只做第 1 步静态定位 rp 来源 + 第 3 步强行改内存」
> 结果：**两步都做成了，而且是决定性的。**

---

## 0. 三条结论

**① `rp` 的真正来源找到了：`0x1572e60`（525），一个有快慢两条路径的函数。标志位 `[ctx+0x320]` 的 bit0 决定走哪条。**

**② 525 实测 `bit0 = 0` ⇒ 每次取 `rp` 都要走慢路径，而那是一条 MMIO 读（`mov (%rax),%eax` 直接读 BAR 映射空间）。**

**③ 把 bit0 强制置 1 后：`total_p50` 从 127.09 ms 掉到 1.42 ms，帧率 7.87 → 703.95 fps。85 倍。**

---

## 1. 第 1 步：静态定位 rp 的来源

### 1.1 先拿 vtable 槽的实际值

`call *0x1a98(%rbp)` 是间接调用，静态看不出目标。用 tracefs 在调用前读槽（`0x157829c` 处）：

```
h1a90 = 0x7fab5bb72c30  → 库内偏移 0x1572c30
h1a98 = 0x7fab5bb72e60  → 库内偏移 0x1572e60   ← 取 rp 的函数
```

### 1.2 这个函数有快慢两条路径

```asm
0000000001572e60:
1572e61: mov    %rdi,%rbx
1572e64: testb  $0x1,0x320(%rdi)     ; ★ 测试 bit0
1572e6b: je     1572e80              ; bit0==0 → 慢路径
1572e6d: mov    0x1240(%rdi),%rax    ; bit0==1 → 直接返回 [ctx+0x1240]（缓存值）
1572e74: pop    %rbx
1572e75: ret

1572e80: call   1569f10              ; ← 慢路径：真查询
1572e85: mov    0x1130(%rbx),%rcx
...
```

**`[ctx+0x1240]` 就是我在报告 127 里测到的 `wp-1`（恒定值）。**
**⇒ bit0=1 时返回一个恒定缓存值，永远满足 `rp >= sz`，零开销。**

### 1.3 慢路径 `0x1569f10` 做了什么

```asm
1569f1b: mov    0x21c(%rdi),%eax     ; 状态位
1569f21: mov    0x22f2c(%rdi),%r14d  ; 通道数 n
1569f28: test   %eax,%eax
1569f2a: je     1569f50              ; 为 0 → 走下面
...
1569f50: mov    $0x800000ba,%esi     ; ★ MMIO 寄存器号
1569f55: call   1575990              ; ★ 读它
1569f60: call   1581460
1569f65: cmp    $0x1,%r14d           ; 通道数 > 1 ?
1569f69: jle    1569f37              ; n=1 → 不做遍历
    ...
1569f80: 循环: call 1575990 / cmp %ebx,%r12d（取最大）/ add $1,%ebp  ← 多通道遍历
1569f37: mov    %r12d,%eax
1569f3c: mov    %rax,0x1128(%r13)    ; 顺手缓存到 ctx+0x1128
```

**`0x1575990` 确认就是 MMIO 读**：

```asm
1575990: mov    %esi,%eax
1575992: shl    $0x4,%eax            ; 寄存器号 → 字节偏移
1575995: and    $0xe0000000,%esi     ; 选 BAR
157599b: je     15759c0
15759af: mov    0x1548(%rdi),%rdx    ; BAR 基址
15759b8: add    0x58(%rdx),%rax      ; + 用户态映射基址
15759bc: mov    (%rax),%eax          ; ★★ 直接从映射内存读一条 MMIO
15759be: ret
```

**实测通道数 `n = 1`、状态位 `s21c = 0`** ⇒ 遍历循环不执行，慢路径每次只做**一次 MMIO 读**。

> 顺带闭环：报告 127 的 `cycles:u` 采样里 `0x15759be` 占 1.90% —— 正是这条 `mov (%rax),%eax`。

### 1.4 与 515 的结构差异（用户要求的一半）

| | 515 | 525 |
|---|---|---|
| `rbp` 是什么 | **库内静态 vtable 表**（`lea 0x156f14a(%rip),%rbp`） | **ctx 本体**（`mov %rdi,%rbp`） |
| 取 rp 的调用 | `call *0x270(%rbp)` → 库内偏移 **0xeb7e60** | `call *0x1a98(%rbp)` → **0x1572e60** |
| 该函数结构 | **无 flag 判断**，直接转发 `0x278` 槽 | **有 flag**，bit0 决定缓存/MMIO |
| 取时钟的调用 | `call *0x280(%rbp)` → 0xeb8800（跳板→0xeb2fb0） | `call *0x1a90(%rbp)` |

**515 没有这条"缓存 vs MMIO"的岔路** —— 它无条件走同一条路，没有"用旧值凑合"的选项。

## 2. 第 3 步：强行改内存

### 2.1 做法

```bash
# 1) 启动，让它进入自旋
./n83a -M 3 -n 1000 &

# 2) 用 tracefs 拿到本次运行的 ctx 地址
echo 'p:flg $SO:0x1572e64 c=%di f320=+0x320(%di):u8' >> uprobe_events
# → c=0x556278254dc0  f320=0

# 3) gdb attach，把 bit0 置 1
gdb -q -p $PID -batch \
    -ex "set {unsigned char}0x5562782550e0 = 1" \
    -ex "printf \"f320=%d\\n\", *(unsigned char*)0x5562782550e0"
# → 注入后 f320=1
```

### 2.2 结果

| | total_p50 | fps | 帧时间 |
|---|---|---|---|
| 基线 #1 | **127.091 ms** | 7.87 | — |
| 基线 #2 | **127.208 ms** | 7.86 | — |
| **注入 `bit0=1`** | **1.421 ms** | **703.95** | — |

**85 倍加速。**

### 2.3 这个 1.42 ms 意味着什么

**125.7 ms（127.09 − 1.42）全部花在"每次取 rp 都发一次 MMIO 读"上。**

而且 1.42 ms **比 515 的 5.27 ms 还快** —— 因为快路径连 MMIO 都不发，直接用恒定缓存值，
所以它比 515 的"正常路径"更极端。

**⇒ 这是"能跑多快"的下界证明：只要不发那条 MMIO 读，105 ms 的差距瞬间消失。**

## 3. 因果链完整了

```
525 的 [ctx+0x320] bit0 = 0
        ↓
每次「取读指针」走慢路径 0x1569f10
        ↓
发一条 MMIO 读（0x800000ba，mov (%rax),%eax 直读 BAR 映射）
        ↓
每次约 1~2 µs 的 PCIe 往返（且期间 CPU 只能自旋等）
        ↓
M3 场景下这个查询要做 108 次/对（报告 126）
        ↓
108 × ~1.18 µs ≈ 127 µs/对 = 127 ms/帧
        ↓
【注入 bit0=1】改用恒定缓存值 [ctx+0x1240]
        ↓
127.09 ms → 1.42 ms
```

**用户最初的两个猜测，最终答案是第三个：**
- 不是"疯狂往队列塞"（每帧只预留 1.17 次，报告 127）
- 不是"消费指针完全不推"（`rp` 在推，只是每次都要为取它付一次 PCIe 读）
- **是"每取一次读指针就发一次 MMIO 读"，而 M3 场景下每对要取 108 次**

---

## 4. 仍待回答的一个问题

**注入实验证明"这条路径占 125.7 ms"，但没有回答"为什么 525 要查 108 次而 515 只查 3.84 次"。**

bit0 只决定"单次查询多贵"，不决定"查几次"。**次数差异是另一个独立问题**（可能与报告 127 的 `sz` 增长/饱和有关，`sz` 单位仍未定）。

**所以现在有两个可分开的靶点：**
1. **单价**：bit0（已证明，改它立刻 85×）—— 但这需要改驱动/编译器，用户侧改不了
2. **次数**：为什么 525 在 M3 下需要查 108 次 —— 这才是用户能通过"减少批次"影响的部分

## 5. 各条证据强度

| 结论 | 强度 | 依据 |
|---|---|---|
| `rp` 来源函数 = `0x1572e60`（525） | **强** | vtable 槽动态读取 + base 换算 |
| 该函数有 flag 快慢两路，bit0 决断 | **强** | 反汇编 + 实测 bit0=0 |
| 慢路径 = 一次 MMIO 读（`0x800000ba`） | **强** | `0x1575990` 的 `mov (%rax),%eax` + BAR 基址计算 |
| 实测 n=1、s21c=0，遍历循环不执行 | **强** | 探针读数 |
| **注入 bit0=1：127.09 → 1.42 ms（85×）** | **强** | 两次基线 + 一次注入，同机同场景 |
| 515 无此岔路，`rbp` 是静态 vtable 表 | **强** | 两版反汇编对比 |
| 105 ms 差距全部来自这条 MMIO 路径 | **强** | 时间闭合 |
| **为什么 525 查 108 次而 515 查 3.84 次** | **未知** | bit0 只决定单价，不决定次数 |

---

## 6. 一句话

**你的判断是对的，而且比"判死刑"更精确：不是驱动不更新读指针，是驱动选择了一种"每次取读指针都发一次 PCIe MMIO 读"的方式。**
**这个选择由 `[ctx+0x320]` 的一个 bit 控制。525 是 0，515 根本没这个岔路。**
**我把 525 的那个 bit 改成 1，`total_p50` 从 127.09 ms 掉到 1.42 ms —— 85 倍，一次 gdb 写字节。**
**代价是它用的是缓存值而不是真实读指针，所以那 105 ms 是"为正确性付的钱"；但这笔钱在 M3 场景下被收了 108 次/对，才变得不可接受。**
**剩下唯一没答的是"为什么是 108 次"——那才是用户侧能通过减批次影响的部分。**
