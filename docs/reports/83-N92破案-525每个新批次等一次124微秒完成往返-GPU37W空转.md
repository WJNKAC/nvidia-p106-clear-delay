# 83 · N92 破案：525 每个「新批次」要等一次 124µs 的完成往返（GPU 37W 空转）

日期：2026-10-26 13:30
驱动：**525.116.03**（用户装回）；对照 515.105.01 的数据见报告 79/81
方法：libc uprobe 计数（glcore 挂不上，改数 libc 的 `sched_yield`/`usleep`/`pthread_cond_timedwait`）
+ 最小复现器 `pair_flush`（自写，可切"legacy 状态"与"program 切换"两种配对）+ nvidia-smi 同步采样

---

## 0. 五条结论（这是本案第一次把机制钉到"批次"粒度）

1. **525 上每帧 42,338 次 `sched_yield`**（M1 只有 964 次），`usleep`/`pthread_cond_timedwait` **全 0**
   ⇒ 每对（1000 对/帧）约 **42 次 yield 的自旋等待**，不是睡 cond。
2. **最小复现成立，触发条件精确**：

| 525，N=1000 对，1080p | map_p50 | 每对 |
|---|---|---|
| **legacy 状态**（`glColor3f`+draw） | **2.577 ms** | **免费** |
| **program 切换**（`glUseProgram`+draw） | **124.155 ms** | **124 µs** |

   ⇒ **不是"任何状态变更"，是"管线状态失效"（program 绑定）** 才收费。
   （与报告 76 的 M9 一致：不相邻的切换免费 ⇒ 收费的是"**新批次**"，不是调用本身。）
3. **这 124µs 是 GPU 侧空转，不是计算**：跑 program 切换负载时
   **util 100% 但功耗仅 37.5W / 37°C / 满频 1911MHz**（空闲 6W，真算力 100W+）
   ⇒ util 100% 是"有 kernel 在等"，与报告 31 的 Heaven 签名（48~64W）同源，且更极端。
4. **不是"驱动异步等待"**：每对插 `glFinish` 后总时长 136.2ms（vs 不插 125.3ms）
   ⇒ GPU 确实**每批占用 124~136µs**，插不插同步都在那儿。
5. **机制**：525 的批次是**同步**的——每个新批次开始前等上一批完成，**完成往返 ≈124µs**；
   515 是异步流水（报告 79：同样 1000 对 2.539ms、0.03µs/对）。
   **Heaven 对账**：268 批/帧 × 124µs = **33.2ms** → 30~34fps ✓。

## 1. 关键证据：libc 侧计数（525）

`glcore` 的 uprobe 两版都挂不上（报告 77/81），但**驱动最终落到 libc 的等待原语可以数**：

```bash
perf probe -x /usr/lib/x86_64-linux-gnu/libc.so.6 sched_yield
perf probe -x /usr/lib/x86_64-linux-gnu/libc.so.6 usleep
perf probe -x /usr/lib/x86_64-linux-gnu/libc.so.6 pthread_cond_timedwait
```

| 模式 | frames | fps | yield | usleep | condwait | **yield/帧** |
|---|---|---|---|---|---|---|
| M1（1000 draw，0 对） | 2000 | 375.5 | 1,927,529 | 0 | 0 | **963.8** |
| **M3（1000 对）** | 40 | **8.00** | **1,693,520** | 0 | 0 | **42,338** |
| M1（复测） | 2000 | 375.5 | 1,815,372 | 0 | 0 | 907.7 |

- M3 每帧 42,338 ÷ 1000 对 = **42.3 次 yield/对**；
- 124µs ÷ 42.3 ≈ **2.9µs/yield**（一次真实让出的成本，合理）；
- **`usleep` 与 `cond_timedwait` 都是 0** ⇒ 这条等待**不是**报告 44 的 `wait_ms(cond,2ms)` 路径，是**纯自旋 + yield**（对应报告 52 的 `0x15761b0`：9×pause + 20µs deadline + yield）。

## 2. 最小复现器（`analysis/probes/pair_flush.c`）

同一进程、同一 FBO/PBO、每帧 1000 对，只改"对"的内容：

| kind | 每对做的事 | mode=0 map | mode=2（每对 glFinish）整帧 |
|---|---|---|---|
| 0 | `glColor3f` + 1 quad | **2.577 ms** | 12.558 ms（12.6µs/对） |
| **1** | **`glUseProgram`（两个 program 交替）+ 1 quad** | **124.155 ms** | **136.186 ms** |

两条关键读数：
- **kind=0 免费** ⇒ 排除"每对/每 draw 都有固定税"；
- **kind=1 mode=2 = 136ms** ⇒ 即使每对强制等 GPU 完成，总时长仍在 136ms（不是"驱动偷偷异步"）⇒ **GPU 每批真的占用 ~124µs**。

## 2bis. ★ 批次大小扫描：成本精确线性于「批次数」（不是"对数"）

`pair_flush` 加 `k` 参数：每 k 对才切一次 program（其余对只 draw）。

| k（每 k 对切一次） | 批次数/帧 | map_p50 | 124µs × 批次数 + 2.6ms 基线 | 实测−预测 |
|---|---|---|---|---|
| **1** | 1000 | **124.209 ms** | 124.0 + 0.2 | −0.0 |
| **2** | 500 | **63.390 ms** | 62.0 + 0.2 | +1.2 |
| **5** | 200 | **27.002 ms** | 24.8 + 2.6 | −0.4 |
| **10** | 100 | **14.762 ms** | 12.4 + 2.6 | −0.2 |
| **100** | 10 | **3.813 ms** | 1.24 + 2.6 | −0.03 |
| **1000** | 1 | **2.700 ms** | 0.12 + 2.6 | −0.02 |

**六个点全部落在 `124µs × 批次数 + 2.6ms` 上（最大偏差 1.2ms，出现在 k=2 的 500 批）。**

⇒ **成本 = 每个新批次 124µs，与批内有多少对/draw 完全无关。**
这条同时把「每对固定税」「每 draw 固定税」「每次状态变更固定税」全部排除：
**收税的是"批次开始"这个事件本身。**

## 3. 这 124µs 是空转：功率证据

`pair_flush 60 1000 0 1920 1080 1` 运行中，每秒采一次：

```
100 %, 37.63 W, 1911 MHz, 37 °C
100 %, 37.53 W, 1911 MHz, 37 °C
100 %, 37.53 W, 1911 MHz, 37 °C
100 %, 37.35 W, 1911 MHz, 37 °C
```

**满频 + util 100% + 37.5W**：这是"kernel 在等"的功率，不是算力饱和（同卡真负载 110W+，Heaven 48~64W）。
⇒ **GPU 每个批次结束后没有活干，却在等 ~124µs 才被喂下一批。**

## 4. 完整因果链（本案收口版）

```
Heaven 每帧 ~268 次「管线状态绑定 + draw」（报告 76/78 推算）
        ↓
525：每次绑定都强制开一个新批次（报告 76 的 M9：不相邻的绑定不收费）
        ↓
新批次开始前，驱动自旋等上一批完成：每对 ~42 次 sched_yield（本报告 §1）
        ↓
完成往返 ≈124µs（GPU 在此期间 util 100% 但只有 37W —— 在等，不在算）
        ↓
268 × 124µs = 33.2ms/帧  →  30~34fps（Heaven 实测 32.4ms / 34fps ✓）

515：同样的绑定不强制新批次（或批次之间异步流水）→ 0.03µs/对 → 回读窗口 2.6ms → 101fps
```

**"为什么 525 要等"仍是最后一问**，但问题已经从"26ms 在哪"缩到"**为什么批次是同步的**"：
候选是批边界处的那个等待条件（报告 52 的 `0x15761b0` 20µs deadline 自旋 + yield），
以及报告 37 找到的 `ThreadControl` 系列 regkey（bit5 会同时门控 signal，置位后 fps 38→3，不能直接用）。
