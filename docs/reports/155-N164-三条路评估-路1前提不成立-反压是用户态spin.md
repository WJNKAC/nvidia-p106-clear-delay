> ## ⚠ 报告 162（N171）已更正本报告 §8 的机理表述
>
> 本报告 §8 的「只要上下文里存在 legacy 固定管线状态，每一次 `glDrawArrays` 都会触发约 18 次状态机重建」
> **已被更精确的实验取代**：
>
> | 本报告原表述 | 实测（报告 162） |
> |---|---|
> | 是 legacy 专属 | ✗ 纯 shader 的 `-M 3`（零 legacy 调用）一样慢 12 倍；`-M 6` 切到**同一个** program 也一样慢 |
> | 每个 draw 都触发 | ✗ 400 个 draw 在同一批次里完全免费（4.46 ms） |
> | 是 CPU 重建状态表 | ✗ 去掉回读后 CPU 只花 0.586 ms / 400 批次（1.5 µs/批） |
>
> **正确表述**：每次「状态变更之后紧跟一个 draw」会开启一个新的 GPU 批次，
> 每个批次固定多花 **~122 µs 的 GPU 时间**（`T = T_base(N) + B × 122 µs`，拟合 R² = 1.000000）。
> 成本与批内 draw 数无关、与切换的状态种类无关；`glUniform` 豁免（可作为内联数据写入）。
>
> 「18 次/对」仍是正确的**观测**（某状态机函数被调到的频次），但**不是成本来源** ——
> 与报告 161 里把 `sched_yield` 误读成调度开销是同一类错误：**高频 ≠ 成本**。
>
> 另：本报告 §4「跳过 `0x15c2790` 后帧时间不变」的结论**依然成立**，
> 因为 `0x15c2790` 是 CPU 侧工作，本来就不是成本来源。

## 1. 本轮最重要的发现：n83b 自己的计时器低估真实帧时间 93 倍

这是在追路 1 的过程中挖出来的，**它推翻了此前多份报告的时间归因基础**。

### 1.1 现象

`-R` 模式（跳过回读和 map），外部墙钟 vs 程序自报：

| 帧数 | 外部墙钟 | 程序自报 `total_p50` |
|---|---|---|
| f=10 | 1.868 s | 1.431 ms |
| f=30 | 4.258 s | 1.076 ms |
| f=50 | 6.742 s | 1.337 ms |

**斜率（真实每帧时间）= (6.742 − 1.868) / 40 = 121.9 ms/帧**
**程序自报 = 1.3 ms/帧**
**差 93 倍。**

### 1.2 而 `now_ms()` 用的确实是墙钟

```c
static double now_ms(void) {
    struct timespec ts;
    clock_gettime(CLOCK_MONOTONIC, &ts);   // ← 墙钟，无问题
    return (double)ts.tv_sec * 1000.0 + ts.tv_nsec / 1e6;
}
```

`t0` 在循环头（347 行），`t1` 在 1000 对 draw 之后（467 行），中间没有其他代码。
**`t1 − t0` 应当覆盖那 1000 对 draw 的全部墙钟时间。**

### 1.3 那 121.9 ms 到底在哪：用户态 spin-wait

| 测量 | 结果 |
|---|---|
| `strace -c`（f=10，136,541 次 syscall） | **syscall 总耗时 0.228 s**，程序运行 1.868 s |
| 进程状态采样（40 次，50 ms 间隔） | **R=40 / S=0 / D=0** |
| CPU tick 增长 | Δ209 ticks = **2090 ms** / 2000 ms 墙钟 = **100%** |
| `wchan` | 0 |

**⇒ 系统调用只占 12%，剩下 1.6 秒 CPU 100% 在用户态运转。**

这是 **spin-wait（忙等）**：
- 不是 `sched_yield`（实测 0 次）—— 所以 CPU 100%
- 不是 futex/ioctl 等待 —— syscall 只占 12%
- 不是在 `t1−t0` 覆盖的范围里 —— 但帧与帧之间其实没有代码

> 第 4 条至今没有完全解释通。可能与 GL 驱动的延迟 flush 时机有关
> （命令在缓冲里堆积，实际提交发生在驱动内部的某个时机点，而该时点落在
> `glDrawArrays` 返回之后、下一个 `glDrawArrays` 之前的间隙）。
> **但不管机制如何，下面的实验结果是确定的。**

## 2. 路 1 的实验：把最大的 CPU 消费者完全移除，帧时间不变

### 2.1 找到最大的 CPU 消费者

`-R` 模式采样 1210 个样本，按地址聚合：

| 地址 | 占比 | 内容 |
|---|---|---|
| `0x15c288d` | 16.6% | `rep stos`（memset 512 字节状态表） |
| `0x15c2855` | 14.6% | 同上，第二个 memset |
| `0x15c2bae` | 4.5% | 同函数 |
| `0x15c2b9e` | 2.7% | 同函数 |
| **合计（函数 `0x15c2790`）** | **38.5%** | 状态跟踪表重建 |

这个函数的调用频率：**152,582 次/秒**（≈ 每帧 16,585 次 = 每对 16.6 次）。
唯一调用者：`glcore+0x15c3030`（`callers2` 采样 500/500 全指向它），
位于一个 **11,856 字节**的 legacy 状态机总入口函数中。

### 2.2 把它整个跳过

补丁：`0x15c3030: e8 5b f7 ff ff`（`call`）→ `b0 01 90 90 90`（`mov al,1` + nop）

**补丁确认生效**：
```
[patchpb] 0x15c3030  原文 e85bf7ffff  ->  b001909090   [已改写]
0x15c2790 调用频率：152,582 次/秒  →  0 次/秒
```

**帧时间（两帧数相减，消除初始化开销）**：

| 配置 | f=20 | f=60 | 真实 ms/帧 |
|---|---|---|---|
| 基线 | 3.18 s | 8.18 s | **124.936** |
| 跳过状态表重建 | 3.10 s | 8.18 s | **127.177** |

**完全不变。**

### 2.3 结论

> **把占 CPU 采样 38.5% 的工作彻底移除，帧时间一点没变。**

这只有一种解释：**CPU 少做的部分，会立刻被"等待"吸收掉。**
即存在一个反压机制，**CPU 跑得再快也要等**。而且这个等待是 **用户态 spin**，
所以 CPU 显示 100% 忙。

**⇒ "绕过等待"这条路，不能通过"减少 CPU 工作"或"改某个循环的退出条件"来实现。**
反压点不在那些我们找得到的热点里。

### 2.4 顺带否掉的两个候选（本轮实测）

| 候选 | 实验 | 结果 |
|---|---|---|
| 强制走 fence 缓存路径 | `0x1569f2a: 74→75`（je→jne） | **挂死**（缓存值落后于已提交） |
| 异步回读（PBO 深度 8） | 报告 152 | **无效**（125.7 ms 不变） |

## 3. 一个必须记录的假信号（方法教训）

在 §2.2 的第一次实验中，程序自报 `total_p50=0.967, fps=1034`，
看起来"快了 130 倍"。

**这是假的。** 原因：我只用 `total_p50` 算 fps，而它**只覆盖 `t0~t1`**，
真实墙钟是 125.9 ms（外部墙钟可证）。

**⇒ 这是同一个坑的第三次（报告 147 的 498 fps、152 的 179、本轮的 1034）。**

纪律（已写入 SKILL 71.3）：
> **任何帧率结论必须用外部墙钟，且必须用"两个帧数相减"消除初始化开销。**

因为单次运行的墙钟里包含 X11/GL 初始化（本机约 1.8~3 秒），
20 帧的运行时间可能小于初始化，直接除会得到完全错误的结果。

## 4. 路 2 的评估：方向对，但工程量比想象小得多

### 4.1 已实测的事实

| 模式 | 每对做的事 | 525 实测 |
|---|---|---|
| M1 | 只 `glDrawArrays` | 6.2 µs |
| **M2** | `glUniform3f` + draw | **6.2 µs** |
| M3 | `glColor3f`+`glTranslatef`+`glScalef`+`glLoadIdentity` + draw | **125.8 µs** |

**M2 证明：每对改状态本身不贵（和纯 draw 一样）。贵的是 legacy 那四个函数。**

### 4.2 工程量修正

用户说"工程量大得离谱"。实际拆开看，**比想象小**：

需要拦的 legacy API 其实是有限的一组（按报告 154 的 M3 源码）：

```
glLoadIdentity / glTranslatef / glScalef     → 矩阵 → 2~3 个 uniform
glColor3f                                     → 颜色 → 1 个 uniform
```

**三个矩阵操作 + 一个颜色，映射到 4 个 uniform。** 不需要实现整个固定管线。

> 真正的难点不在"翻译"，在 **Heaven 里到底有多少 legacy 调用**——
> 而这一点**还没判定**（报告 154 §8：Heaven 静态链接、走 GLX dispatch table，
> `nm -D` 0 个 GL 引用、`glXGetProcAddress` 拦截 0 个函数名）。

### 4.3 所以路 2 的正确顺序是

**先判定 Heaven 是否真的走 legacy，再决定要不要写 shim。**

判定方法（成本递增）：

1. **换渲染后端对比**（最便宜）：`-video_app` 换 D3D11 / 其他值，
   看 525 上帧率是否恢复。若恢复 ⇒ 与 GL 路径无关，路 2 无意义。
2. **ptrace 断在 glcore 的 legacy 实现上**（需先定位实现地址）：
   统计每帧调用次数。若有约 260 次/帧，就与 30 ms 的差距吻合。
3. **`apitrace` 抓调用序列**（需安装）：最直接，成本最高。

**在第 1 步做完之前，写 shim 是盲目的。**

## 6. 诚实的现状总结

### 6.1 已经确定的

1. **525 的 legacy 固定管线在 CPU 侧退化约 20 倍**（125.8 vs 6.2 µs/对）
2. **换 shader + uniform 能恢复**（实测 20.3 倍）
3. **存在一个用户态 spin-wait 反压**：移除 38.5% 的 CPU 工作不影响帧时间，
   syscall 只占 12%，CPU 100% 忙
4. **反压点没有被定位到**（不在 fence 轮询、不在状态表重建、不在 ioctl）

### 6.2 做不到的

- **无法通过改单个函数/循环来"绕过"这 122 ms** —— 试了 8 种补丁，全部无效或更慢
- **无法让 CPU 侧"跳过等待"而不影响正确性** —— 跳过 → `chk=0`

### 6.3 唯一确定可落地的

**M2 那条路（shader + uniform）**，20.3 倍。前提是目标程序愿意改。

对闭源程序（Heaven），**必须先判定它是否走 legacy**（§4.3 第 1 步，最便宜）。

## 8. ★ 最终机理：一旦用了 legacy，**每次 draw** 就触发 18 次状态重建

这是本轮最有价值的发现，它把"legacy API 慢"这个模糊说法精确成了可操作的机理。

### 8.1 关键对照

| 配置 | 状态机 `0x15c2e50` 频率 | 帧时间 |
|---|---|---|
| M3，4 个 legacy 调用（`LoadIdentity`+`Translatef`+`Scalef`+`Color3f`） | **152,409 次/秒** | 121.9 ms/帧 |
| M3，**只 1 个** `glColor3f`（`-1` 省掉 3 个矩阵调用） | **145,277 次/秒** | 123.9 ms/帧 |
| **变化** | **-4.7%** | **+1.7%（没变）** |

**把 legacy 调用从 4 个减到 1 个，状态机调用次数只降 4.7%，帧时间不变。**

### 8.2 所以触发源是 draw，不是 legacy API

```
4 个 legacy 调用 → 152k 次/秒 ÷ 8 fps ≈ 19,000 次/帧 ÷ 1000 对 ≈ 18.4 次/对
1 个 legacy 调用 → 145k 次/秒 ÷ 8 fps ≈ 18,200 次/帧 ÷ 1000 对 ≈ 18.2 次/对
```

**两种配置都是"每对约 18 次"**，与 legacy 调用是 4 个还是 1 个无关。

⇒ **只要上下文里存在 legacy 固定管线状态，每一次 `glDrawArrays` 都会触发约 18 次状态机重建。**

对比 M2（shader + uniform，无 legacy 状态）：

| | 状态机频率 | 折算每对 |
|---|---|---|
| M3（有 legacy 状态） | 152,409 次/秒（÷8 fps） | **18.4 次** |
| **M2（无 legacy 状态）** | **6,584 次/秒（÷161 fps）** | **0.04 次** |

**差 460 倍。** 而每对成本差 20 倍 —— 与"18.4 vs 0.04 次 × 6.8 µs"完全吻合。

### 8.3 这条精确机理解释了此前所有失败

| 之前的尝试 | 为什么必然失败 |
|---|---|
| 减少 legacy 调用数（4→1） | 触发源是 draw，不是 legacy API 本身 |
| 跳过状态表重建（`0x15c2790`） | 只砍掉状态机的**一个子函数**，外层 18 次调用照做 |
| 改退避函数 / 伪造 fence | 与这条路径完全无关 |
| 异步回读 / 加深 PBO | 与 CPU 侧无关 |

### 8.4 唯一有效的解法（已被数据和机理双重支持）

**让上下文完全不持有 legacy 固定管线状态。** 即：

- 用 shader（`glUseProgram` + uniform / attrib）
- **不要调用任何** `glMatrixMode` / `glLoadIdentity` / `glTranslatef` / `glScalef` /
  `glColor*` / `glBegin` / `glVertex*` / `glEnableClientState` / `glVertexPointer`

**关键判据（本轮实测）**：只要这些调用出现过，之后**每一次 draw** 都要付 18 次状态重建；
把调用次数从 4 降到 1 **没用**，必须降到 **0**。

**⇒ 这就是路 2 的精确形式，也是它唯一可行的原因。**
