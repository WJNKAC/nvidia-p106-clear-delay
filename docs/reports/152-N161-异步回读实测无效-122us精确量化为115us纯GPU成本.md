## 0. 三句话结论

1. **异步回读实测无效。** 双 PBO 到 8 级 PBO 环形队列，`map_p50` 全部停在 125~126 ms，fps 恒定 7.89。
2. **因为 map 等的是 GPU 全局完成度，不是该 PBO 的 fence。** 深度加到 8（map 7 帧之前的 PBO）仍等 125 ms。
3. **而且 `-R`（完全不等回读）的墙钟也是 125 ms/帧。** 所以**报告 147 的"`-R` 快 63 倍"是错的**——
   那只是 CPU 侧不再阻塞，GPU 的真实吞吐一直是 7.99 fps。

## 1. 实现：n83b 新增 `-A` / `-L n`

在 `<workdir>/analysis/n83a/n83b.c` 里加了异步回读模式（原文件已备份为 `n83b.c.bak_async`）：

```c
/* -A        : 2 级（双 PBO ping-pong）
 * -L n      : n 级环形队列（2..8）
 * 本帧 glReadPixels 写 pbo[cur]；map pbo[(cur + n - 1) % n]，即 n-1 帧之前那一帧
 */
if (ASYNCMODE) {
    p_BindBuffer(GL_PIXEL_PACK_BUFFER, pbo2[async_cur]);
    glReadPixels(0, 0, W, H, GL_BGRA, GL_UNSIGNED_BYTE, (void*)0);
    double ta2 = now_ms();
    t_sub[f] = t1 - t0;
    t_rp[f]  = ta2 - t1;
    t_map[f] = 0;
    t_all[f] = ta2 - t0;

    if (async_fill >= ASYNCDEPTH - 1) {
        int prev = (async_cur + ASYNCDEPTH - 1) % ASYNCDEPTH;
        p_BindBuffer(GL_PIXEL_PACK_BUFFER, pbo2[prev]);
        void *pp = p_MapBuffer(GL_PIXEL_PACK_BUFFER, GL_READ_ONLY);
        double ta3 = now_ms();
        if (!pp) { fprintf(stderr, "!! [A] glMapBuffer(prev) 返回 NULL\n"); return 5; }
        sum += ((unsigned char*)pp)[0] + ((unsigned char*)pp)[W*H*4/2];
        p_UnmapBuffer(GL_PIXEL_PACK_BUFFER);
        t_map[f] = ta3 - ta2;      /* ← 关键指标 */
        t_all[f] = ta3 - t0;
    }
    p_BindBuffer(GL_PIXEL_PACK_BUFFER, 0);
    async_cur = (async_cur + 1) % ASYNCDEPTH;
    if (async_fill < ASYNCDEPTH) async_fill++;
    continue;
}
```

编译：`gcc -O2 -o n83b_new n83b.c -lX11 -lGL`

## 2. 实测：深度从 2 加到 8，`map` 一动不动

`-M 3 -f 16 -n 1000 -W 3`，每档单独跑：

| PBO 深度 | `map_p50` (ms) | `total_p50` (ms) | fps | chk |
|---|---|---|---|---|
| 2 | 125.694 | 126.733 | 7.89 | 900 |
| 3 | 125.641 | 126.718 | 7.89 | 850 |
| 4 | 125.473 | 126.740 | 7.89 | 800 |
| 6 | 125.183 | 126.754 | 7.89 | 700 |
| 8 | **125.179** | 126.701 | **7.89** | 600 |

**深度 ×4，`map_p50` 只降了 0.4%（125.69 → 125.18）。**

（`chk` 随深度线性下降是正常的：跳过的帧数变多，`chk` 只累加被 map 到的帧）

### 2.1 这说明什么

深度 8 时，map 的是 **7 帧之前**的 PBO——那是约 7 × 127 ms = **890 ms 之前**提交的
`glReadPixels`。按常理早就该写完了，map 应该 0.001 ms 量级。

**但它仍然等 125 ms。**

⇒ **`glMapBuffer` 在这里等的是"GPU 完成度"这个全局条件，而不是"该 PBO 的 fence"。**
NVIDIA 驱动对 `GL_STREAM_READ` 的 PBO map 做了保守处理（无法保证该 buffer 数据只依赖单一 fence）。

**这一条直接解释了报告 151 里"79.5% 时间在 fence 等待"为什么改不动。**

## 3. 决定性一击：连 `-R`（完全不等）也是 125 ms/帧

前面的 fps 都是用程序自报的 `total_p50` 算的，**容易误导**（异步模式下 `t_all` 的语义变了）。
改用**外部墙钟**测量，42 帧（含 2 帧 warmup）：

| 模式 | 墙钟 | 每帧 | 真实吞吐 |
|---|---|---|---|
| SYNC（同步回读） | 5.410 s | 128.81 ms | **7.76 fps** |
| ASYNC(深度8) | 5.382 s | 128.13 ms | **7.80 fps** |
| **NOREAD `-R`（完全不等）** | **5.260 s** | **125.23 ms** | **7.99 fps** |
| FINISH `-G`（glFinish） | 5.282 s | 125.75 ms | 7.95 fps |

**四种模式的真实吞吐几乎相同（7.76 ~ 7.99 fps）。**

> ## ⛔ 更正报告 147
>
> 报告 147 我写"`-R` 快 63 倍（7.83 → 498.89 fps）"。
> **那是 CPU 侧不再阻塞造成的假象，不是真实帧率。**

## 4. 顺带得到 122 µs 的精确值：线性拟合

既然 `-R` 模式的墙钟纯粹由 GPU 吞决定，那就用它做线性拟合——**不受 CPU 侧任何干扰**。

### 4.1 M3（绑定 + draw），`-R` 模式

| N | 墙钟/帧 (ms) | 每对 (µs) |
|---|---|---|
| 100 | 17.85 | 178.5 |
| 250 | 36.72 | 146.9 |
| 500 | 64.33 | 128.7 |
| 1000 | 126.05 | 126.0 |

最小二乘拟合：

```
帧时间 = 5.87 ms + N × 119.7 µs
```

| N | 实测 | 拟合 | 误差 |
|---|---|---|---|
| 100 | 17.85 | 17.84 | 0.0% |
| 250 | 36.72 | 35.80 | 2.5% |
| 500 | 64.33 | 65.73 | 2.2% |
| 1000 | 126.05 | 125.58 | 0.4% |

**R² = 0.99955**

### 4.2 M1（只 draw，不绑定），`-R` 模式

| N | 墙钟/帧 (ms) |
|---|---|
| 500 | 4.156 |
| 1000 | 6.268 |
| 2000 | 10.901 |
| 4000 | 20.165 |

拟合：

```
帧时间 = 1.87 ms + N × 4.57 µs
```

### 4.3 结论：一次绑定 = 115 µs 的纯 GPU 成本

```
M1（纯 draw）        : 1.87 ms + N × 4.57  µs
M3（绑定 + draw）    : 5.87 ms + N × 119.7 µs
                     ─────────────────────────
每次绑定多花         :         N × 115.1 µs
```

**⇒ 那个流传了很久的"122 µs"，精确值是 115.1 µs，
而且它是 GPU 执行时间，与 CPU 侧完全无关（这个测量里 CPU 根本没在等）。**

以 1000 对算：115.1 µs × 1000 = **115.1 ms**，加固定开销 5.87 ms ≈ **121 ms**，
与实测 126 ms 吻合（差 4%，在 M1/M3 固定开销分别拟合的误差内）。

## 5. 所以"异步回读"这个方案被实验否证了

> ## ⛔ 更正报告 151 §21
>
> 报告 151 我建议"异步回读是 525 上唯一现在就能用且正确的方案"。
> **实测无效。** 8 级 PBO 深度、外部墙钟，吞吐与同步模式无差别。
>
> 原因：**异步回读只能消除"CPU 被阻塞"，不能消除"GPU 慢"。**
> 而这里 GPU 本身就是瓶颈（每对 115 µs，纯硬件执行时间）。
> 当 CPU 提交速度（2 ms/帧）远快于 GPU 消费速度（126 ms/帧）时，
> CPU 迟早会撞上 driver 队列上限，那时的等待是隐式的、无法通过 PBO 深度绕开。

### 5.1 它什么时候才有用

**只有当 GPU 吞吐 >> CPU 处理速度时**（例如读回数据要做耗时的图像处理），
异步回读才能把"CPU 处理"与"GPU 渲染"重叠起来。
本项目里 GPU 是慢的一方，所以没有任何重叠空间。

## 6. 那么现在还剩什么可做

### 唯一还有意义的方向：让 515 的 inline 路径生效

现有的对比证据（报告 140/145）：

| | 515 | 525 |
|---|---|---|
| `sub6:0x0034`（`KEPLER_INLINE_TO_MEMORY_B` 内联写） | **6,653 条/帧** | **16 条/帧** |
| M3 每次绑定代价 | ≈ 4.6 µs（与纯 draw 同量级） | **115 µs** |

**515 的绑定几乎不要钱，525 的绑定要 115 µs。**
两者命令流字节内容几乎相同（报告 151 §13），差别在**状态写入走的是 inline 还是 buffer**。

所以真正该追的是：**525 为什么不用 inline 路径。**

这在报告 145 已经定位到一个开关：`[ctx+0x21c]` / `[ctx+0x1fc]`（"缓存 fence"标志）。
但报告 149 实测两版都是 0。所以开关不在那里，**而在"选择 inline 还是 buffer"的上层决策**。

### 具体下一步

1. 在 515 上断在 `sub6:0x0034` 的**生成点**（那个 `0xA140` 类的 inline 写函数），拿到调用栈
2. 反查 525 同一逻辑位置的代码，看它是**分支走向另一边**还是**根本没被调用**
3. 判据：515 每帧 6,653 条，525 只有 16 条 —— 差 400 倍，一定有个明确的开关

**这是纯静态 + 一次断点，成本不高，而且是唯一指向根因的路径。**

报告 147 的"498.89 fps"就是这么来的：`-R` 模式下 `t_all` 只包含 CPU 提交时间（2 ms），

## 8. 追加：515 的同一套测量，绑定成本 ≈ 0

用完全相同的方法（`-R` 跳过回读、外部墙钟、线性拟合）在 515.105.01 上测：

### 8.1 515 M3（绑定 + draw）

第一轮 N=250 出现异常点（8.069 ms，比 N=500 还高），是 GPU 时钟爬升导致。
把暖机从 2 帧加到 4 帧后重测两轮：

| N | 轮 1 (ms) | 轮 2 (ms) |
|---|---|---|
| 250 | 2.508 | 2.260 |

| 2000 | 6.633 | 6.792 |

拟合（轮 2）：`帧时间 = 1.61 ms + N × 2.6 µs`，**R² = 0.99860**
（轮 1：`1.96 ms + N × 2.4 µs`，R² = 0.99612）

### 8.2 515 M1（纯 draw）

| N | 墙钟/帧 (ms) |
|---|---|
| 1000 | 7.062 |
| 2000 | 11.417 |

拟合：`帧时间 = 2.71 ms + N × 4.36 µs`

### 8.3 最终对照表

| 版本 | M1（纯 draw） | M3（绑定 + draw） | **绑定的额外成本** |
|---|---|---|---|
| **515** | 4.36 µs / 个 | **2.6 µs / 对** | **≈ 0（甚至更低）** |
| **525** | 4.57 µs / 个 | **119.7 µs / 对** | **+115.1 µs** |

**差距 47 倍。**

515 的 M3 斜率（2.6 µs）甚至比 M1（4.36 µs）**还低** ——
因为 M1 是 1000 个独立 draw（每个都有 per-draw 固定开销），
而 M3 的 draw 紧跟状态写入、被驱动合并得更高效。

### 8.4 这张表的含义

**两个版本的"纯 draw"成本几乎相同（4.36 vs 4.57 µs，差 5%）。**
**但"绑定"的成本差 47 倍。**

⇒ **问题 100% 在"绑定"这个动作上，与 draw、与分辨率、与对象类型都无关。**

这与报告 136 的 M8（1000 绑 + 1 draw = 2.97 ms 正常）完全一致：
绑定本身在 515 上是免费的，在 525 上却要 115 µs，而 M8 只做 1 次 draw 所以不暴露。

## 9. 与 inline 上传证据的最终闭合

| 量 | 515 | 525 | 比值 |
|---|---|---|---|
| `sub6:0x0034`（`KEPLER_INLINE_TO_MEMORY_B` 内联写） | **6,653 条/帧** | **16 条/帧** | **416×** |
| 每次绑定（GPU 时间） | **2.6 µs** | **119.7 µs** | **46×** |
| 每次纯 draw（GPU 时间） | 4.36 µs | 4.57 µs | 1.05× |

**三行数据指向同一件事：**

```
515：状态用 inline 直接写进 pushbuffer（每帧 6,653 条）
     → GPU 顺序执行天然可见，绑定不需要任何同步 → 2.6 µs

525：状态写进显存缓冲（inline 只有 16 条）
     → 每次绑定前要确认"写已到达" → 每次多付 115 µs
```

**416× 的 inline 差异 ↔ 46× 的绑定代价差异。**
这不是巧合，是同一机制的两个投影。

### 9.1 所以剩余的唯一问题

**525 为什么不走 inline 路径？**

- 报告 145/149 已排除：`[ctx+0x21c]` / `[ctx+0x1fc]` 两版都是 0（缓存开关不是它）
- 报告 151 已排除：命令流字节内容几乎相同（那 6,653 条 inline 是 515 特有的，
  但两版的**每对**命令字节一致——说明 inline 发生在别的地方，或 525 把它换成了别的方式）

**下一步（唯一有意义的）：**
1. 在 515 上断在 `sub6:0x0034` 的生成点（`0xA140` 类的 inline 写函数），拿调用栈
2. 反查 525 同一逻辑位置：是分支走了另一边，还是根本没被调用
3. 判据：515 每帧 6,653 条 vs 525 16 条，差 416 倍，一定有个明确的开关
