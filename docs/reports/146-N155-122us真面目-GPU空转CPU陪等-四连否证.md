# 报告 146 — 122 µs 的真面目：不是 CPU 自旋，是「GPU 空转 + CPU 陪等」

> 日期：2026-10-27 13:00
> 实验机：`<user>@<testhost>`（<testhost>，P106-100，525.116.03）
> 前置：报告 145（subchannel 否证、20 µs 自旋否证、inline 上传差异）

## 0. 这一轮要回答的问题

用户给的工程目标：**"在用户态伪造 fence 已完成"**，分析路径是
`glMapBuffer` → 提交器 → `rp` 检查 → `0x1569f10`（读 `0x800000ba`）→ 伪造返回值。

我按这条链逐段核实，结论是：**这条链的前半段全部成立，但终点不是"fence 更新慢"，
而是"GPU 根本没在干活"。** 因此"伪造 fence"能提高 fps，但不能让 GPU 变快——
这两件事必须分开说清楚。

## 2. `0x1569f10`：确实是读 fence，返回"多引擎最小值"

### 2.1 完整语义

```asm
1569f10  push r14/r13/r12/rbp/rbx
         r13  = ctx
         eax  = [ctx+0x21c]          ; ← 开关 A
         r14d = [ctx+0x22f2c]        ; ← 引擎个数 N
         je   1569f50                ; 开关 A == 0 → 走 MMIO

; ---- 快路径（开关 A != 0）：读内存里的缓存副本 ----
1569f2c  rax  = [ctx+0x3c0]
1569f33  r12d = [rax+0x48]           ; 纯内存读，零 MMIO
         goto 1569f37

; ---- 慢路径（开关 A == 0）：真 MMIO ----
1569f50  esi = 0x800000ba
1569f55  call 0x1575990              ; ← BAR 寄存器读
1569f5d  r12d = eax                  ; 第 1 个引擎的 fence
1569f60  call 0x1581460              ; 读后维护（见 §2.3）
1569f65  cmp  r14d, 1
1569f69  jle  1569f37                ; 只有 1 个引擎 → 直接返回
1569f6b  sub  r14d, 0x7fffff46       ; ★ 等价于 add r14d, 0x800000ba（见下）
1569f72  ebp = 0x800000bb
1569f80 loop:
           call 0x1575990            ; 读 0x800000bb, 0xbc, ...
           ebx = eax
           call 0x1581460
           cmp  r12d, ebx
           cmovns r12d, ebx          ; r12d = min(r12d, ebx)
           ebp += 1
           cmp  ebp, r14d
           jne  loop
1569fa3  jmp  1569f37

1569f37  eax = r12d
1569f3c  [ctx+0x1128] = rax          ; 缓存下来
         ret                          ; 返回 r12d
```

### 2.2 一处必须纠正的读法：`sub r14d, 0x7fffff46`

这一条很容易被读成"减去一个大数"，但它其实是**编译器把 `add r14d, 0x800000ba`
优化成了减补数**：

```
0x800000ba + 0x7fffff46 = 0x100000000  →  mod 2³² = 0
⇒ -0x7fffff46 ≡ 0x800000ba
⇒ sub r14d,0x7fffff46  ==  add r14d,0x800000ba
```

于是 `r14d = N + 0x800000ba`，而 `ebp` 从 `0x800000bb`（= `0x800000ba + 1`）起，
循环上界正好是 `0x800000ba + N`。**语义完全闭合：读第 2..N 个引擎的 fence。**
配合 `cmp r14d,1; jle`（N=1 就跳过循环），可以确认 **`[ctx+0x22f2c]` 就是引擎个数**。

### 2.3 返回值语义

**返回的是 fence/同步点序号（32 位单调递增），不是布尔。**
取多个引擎的**最小值** = "所有引擎都至少推进到这里"。

`0x1575990` 确认是 BAR 读原语：

```asm
1575990  eax = esi;  eax <<= 4          ; 寄存器号 → 字节偏移
1575995  esi &= 0xe0000000              ; 选 BAR
15759af  rdx = [ctx+0x1548]             ; BAR2/3 基址
15759b8  rax += [rdx+0x58]
15759bc  mov  eax,[rax]                 ; ← 真正的 MMIO 读
```

`0x800000ba << 4` 在 32 位下 = `0xba0`，所以是 **BAR2/3 + 0xba0**。

`0x1581460`（每次读后调用）是**读后一致性维护**：

```asm
eax = [ctx+0x12b0]        ; ← 开关 B（位域）
test ah,0x80 ; je ret     ; bit15 = 有 fence 缓存机制
test ah,0x40 ; jne ...    ; bit14 = 缓存总是有效
             rdx=[ctx+0x380]; edx=[rdx+0x48]   ; 取缓存值
test ah,0x10 ; je ret     ; bit12 = 需要 clflush
             clflush [ctx+0x22fb7]             ; ← 刷缓存行
```

## 3. `0x1572e60`：rp 的出口，带两个"免 MMIO"开关

```asm
1572e60  test byte [ctx+0x320], 1     ; ← 开关 C
         je   1572e80
1572e6d  rax = [ctx+0x1240]           ; 快：直接返缓存
         ret
1572e80  call 0x1569f10               ; 慢：MMIO 读 fence
1572e85  rcx  = [ctx+0x1130]          ; 64 位：高 32 = 上界，低 32 = 基准
1572e8d  edx  = eax                   ; fence
1572e92  rax  = rcx >> 32
1572e96  cmp  edx, ecx
1572e98  esi  = eax - 1
1572e9b  cmova rax, rsi               ; fence 超过基准 → 上界回退 1
1572e9f  rax <<= 32
1572ea3  or   rax, rdx                ; 拼回 64 位 {上界, fence}
         ret
```

**返回 64 位复合值，低 32 位是 fence。** 这是"读 rp 并处理回绕"的标准写法。

> 注意：`0x2b`/`0x2a` 都读过了，**没有直接 call 者** ——
> `0x1572e60` 是通过函数指针表调用的（`call [reg+off]`），这解释了为什么静态搜 call 是 0 条。

## 4. 提交器里确实有一个"等 wp == rp"的死循环——但它不是病灶

`0x12386d0`（592 B）内部：

```asm
1238743  rax = [ctx+0x8e0a00]         ; wp（CPU 写到哪）
123874a  cmp rax, [ctx+0x0]           ; vs rp（GPU 消费到哪）
123874e  je  1238779                  ; 相等 → 退出
1238760  edi = 4
1238765  call [glcore_tbl+0x280]      ; ← 每次迭代推进一次
123876c  rax = [ctx+0x8e0a00]
1238773  cmp rax, [ctx+0x0]
1238777  jne 1238760                  ; ← 死等，无超时
```

**这是全代码里最像病灶的地方**：无超时、纯忙等。

**实测：把两处 `cmp rax,[rbp+0]` 改成 `cmp rax,rax`（恒等，一次都不进循环）→
`127.733 → 127.560 ms`，fps `7.83 → 7.84`。零变化。**

⇒ 这条循环也不是。

## 5. 决定性实验：`-R`（不等完成）vs 完整

n83b 有 `-R`：跳过 `glReadPixels`/`glMapBuffer`，只测提交。

| 场景 | total_p50 | fps | 说明 |
|---|---|---|---|
| **M3 完整** | 127.733 ms | 7.83 | |
| **M3 `-R`** | **2.004 ms** | **498.89** | **提交 1000 对只要 2 ms** |
| M1 完整 | 7.956 ms | 125.69 | |
| M1 `-R` | 0.032 ms | 31437 | |
| **M3 `-G`（用 glFinish 代替回读）** | **124.694 ms** | 8.02 | `rp` 段 123.58 ms |

**三条结论：**

1. **CPU 提交 1000 对只花 2 ms**（M3-R）。提交侧完全不慢。
2. **125.8 ms 全部在"等完成"**。`glMapBuffer` 和 `glFinish` 等的一样久（125.8 vs 123.6 ms）
   ⇒ **与回读路径无关，与"等 GPU 追上"有关**。
3. **"-R" 就是用户要的"伪造 fence 已完成"的效果**：fps 7.83 → 498.89（**63 倍**）。
   代价是 `chk` 归零、数据未就绪。

## 6. 但功耗说：GPU 在等的时候并没有在算

| 场景 | GPU 功耗（中位） | 相对空闲 | total |
|---|---|---|---|
| 空闲 | 36.28 W | — | — |
| **M1（1000 draw）** | **52.84 W** | **+16.6 W** | 7.96 ms |
| **M3（绑定+draw 交替）** | **37.42 W** | **+1.1 W** | 127.24 ms |

**M1：GPU 真在算（+16.6 W），7.96 ms 干完。**
**M3：GPU 几乎不耗电（+1.1 W），却要 127.24 ms。**

**⇒ M3 的 123.6 ms 里，GPU 没有在执行渲染工作。它在上电空转，同时 CPU 在等它。**

这一条把"122 µs 是 GPU 算得慢"排除掉了，只留下
**"GPU 在等一个信号，而这个信号靠超时推进"**。

## 7. CPU 到底在干什么：11,329 次 `sched_yield`/帧

perf 被 `perf_event_paranoid` 挡住，改用自写的 ptrace RIP 采样器
（`analysis/onheap/rpsample.c`，不需要 perf 权限）：

```
[rpsample] libc base=0x7fbf01c54000  yield=[0x7fbf01d4c640,0x7fbf01d4c661)
次数   rip                     归属
 224   0x7fbf01d4c647          libc+0xf8647  → __sched_yield 内（syscall 返回点）
 224   0x7fbefff762a2          glcore+0x15762a2  ← 调用者
```

`libc+0xf8647` 用 objdump 确认为 `__sched_yield` 里的 `cmp rax,-4095`。
返回地址 `glcore+0x15762a2` 正对 `0x15761b0` 内部的：

```asm
1576297  mov edi,3
157629c  call [rbp+0x288]      ; ← 74% 的样本停在这条 call 里面
15762a2  jmp  1576203          ; ← 返回地址
```

`strace -c` 量化：

```
% time   seconds  usecs/call    calls   syscall
100.00    0.0605       1.78     33986   sched_yield     (3 帧)
```

**11,329 次/帧 ÷ 1000 对 = 11.3 次 yield/对；每次 1.78 µs；
总 yield 时间 60.5 ms / 381 ms = 16% 墙钟。**

### 7.1 一处必须更正的旧结论

报告 145 我写"20 µs 自旋是伴随现象"。**结论对，理由错了。**

真正的原因是：**M3 走的是 `[rbx+0x2850]==1` 那条分支（`0x1576260`），
它压根不看我改的那个 `lea r12,[rax+0x14]` deadline**——
它直接 `call [rbp+0x288]`（sleep/yield），然后 `jmp 1576203` 才回到 deadline 检查。

所以"改 0x14 无效"不是因为它不重要，而是**那条路径没被执行**。

## 8. 连续三次"掐掉等待点"全部无效——这是本轮最重要的方法论结论

| 实验 | 补丁 | 结果 | 结论 |
|---|---|---|---|
| ① 20 µs deadline → 0 | `0x15761e9: 14→00` | 127.33 → 127.27 | 无效（走另一分支） |
| ② 睡眠时长 0x17 → 0 | `0x1576267: c744240c00000000` | 126.98 | 无效 |
| ③ 睡眠调用 → nop | `0x157629c: 6×90` | 127.18 | 无效 |
| ④ **整个 `0x15761b0` → `ret`** | `0x15761b0: 31c0c3` | **127.07** | **无效** |
| ⑤ wp==rp 死等循环 → 恒等 | `0x123874a/73: 4839c090` | 127.56 | 无效 |

**④ 是最强的否证：把那个"74% 时间都停在里面"的函数整个删掉，性能一点不变。**

> **方法论结论：`rip 采样显示某函数占 N% 时间` ≠ `该函数是瓶颈`。
> 它可能只是在"陪等"。判断瓶颈必须用"删掉它，看总时间变不变"，而不是看占比。**

这一条和"等红灯时你在玩手机"是同一个道理：关掉手机不会让你更快到目的地。
**184 ms 的等待发生在别处（GPU 侧 / MMIO / 硬件信号），CPU 只是把这段时间花在了 yield 上。**

## 9. 那么 122 µs 到底是什么

把所有已排除项和已知项排开：

| 环节 | 实测 | 结论 |
|---|---|---|
| CPU 提交 1000 对 | 2.0 ms | 快 |
| ioctl（报告 139） | 0.24% 墙钟 | 快 |
| CPU 自旋/yield | 16% 墙钟，删掉无变化 | 陪等 |
| 命令条数（报告 140） | 525 更少 | 负相关 |
| subchannel 绑定（报告 145） | 两版相同 | 无差异 |
| **等完成（`-R` 对照）** | **125.8 ms** | **病灶在这** |
| **GPU 功耗** | **+1.1 W（空转）** | **GPU 没在算** |

**唯一自洽的解释：**

```
525 每提交一个 (绑定, draw) 之后，驱动插入了一个"等 GPU 追上"的同步点。
GPU 侧收到这条同步后，并没有立刻完成，而是在等一个它看不到更新的信号，
靠内部超时（约 122 µs）推进一格。
CPU 在 glMapBuffer/glFinish 里陪着等，表现为 sched_yield 轮询。
⇒ 1000 对 × 122 µs ≈ 122 ms ≈ 实测 127 ms
```

**与 515 的差异（报告 140/145）仍然指向 inline 上传：**
`0xA140 = KEPLER_INLINE_TO_MEMORY_B`，515 每帧发 6,653 条 inline 写下，
525 只发 16 条。515 把状态直接 inline 进 pushbuffer，**GPU 顺序执行天然可见，不需要同步点**；
525 写进显存缓冲，**draw 前必须确认"写已到达"，于是每对都吃一次 122 µs**。

## 10. 对用户工程目标（伪造 fence）的正式回答

**能做，而且已经用 `-R` 验证了等效效果（fps 7.83 → 498.89，63 倍）。**

但必须分清两件事：

| | 伪造 fence 已完成 | 让 GPU 真的变快 |
|---|---|---|
| fps | **会暴涨（已验证）** | 取决于是否修好同步 |
| 画面正确性 | **错**（读到未完成数据） | 正确 |
| 是否解决根因 | **否**，只是把等待藏起来 | 是 |

**所以"122 µs 完全来自等 fence 更新"这个判断——成立**，但要注意
**fence 不是"更新得慢"，而是"GPU 根本没在推进，靠超时走"**。

如果目标只是让 Heaven 的 fps 数字好看，`-R` 那套（跳过 map 等待）就够了。
如果要真正修好，必须解决 §9 的同步点。

## 11. 下一步（唯一一条能真正闭环的实验）

**给 MMIO 读计时。**

理由：`0x1575990` 是**直接读 BAR 映射内存**，**不走 ioctl**——
所以报告 139 的 `nvidia_ioctl` 探针**根本看不到它**。这是统计盲区。

做法：
1. tracefs `uprobe` 同时挂 `0x1575990` 的入口(p)和返回(r)，记录时间戳
2. 跑 M3 少量帧，算每次 MMIO 读的耗时分布
3. 若单次 ≈ 100 µs 且每帧约 1000 次 ⇒ **闭环：122 µs 就是一次被 GPU 拖延的 MMIO 读**
4. 若是几 µs ⇒ 那 122 µs 在别处，需要转而给 semaphore 命令计时

配套：`wk/rpsample.c` 已有 ptrace 采样能力，可扩展成"在 `0x1575990` 上打硬件断点、
数命中次数"作为交叉验证（不需要 tracefs 权限）。
