# 43 · N25：双线程也不复现——结构差清单穷尽，病根不在 GL 调用结构

> 2026-10-26 01:45
> 承报告 42：pbuffer+swap+FRONT 串行测出 2.602ms，不能复现真进程的 30.4ms。
> 用户指令"继续" → 执行 N25：给 rb_lat6 加**双线程模式**，严格复刻 primus 的 swap/交活结构。
>
> **结果：双线程下 map 仍是 2.486ms，与负载、finish 全无关。结构差清单到此刻穷尽。**
> 附带发现一个**探针缺陷**：多 context 并发时 `GL_TIMESTAMP` query 不能用来测单条命令耗时（污染达 11 倍）。

## 2. 双线程实现（严格照 primus）

```c
// 主线程
render(); [glFinish()];
glXSwapBuffers(dpy, pb);
fence_ = glFenceSync(...);
sem_post(acq);
sem_wait(rel);            // ← 与 primus 一致

// worker（自己的 context，与主 context share）
sem_wait(acq);
glWaitSync(fence_, ...);
glReadBuffer(GL_FRONT);   // ← 与 primus 一致
glReadPixels(...→PBO);
sem_post(rel);            // ★ 在 rp 之后立刻放主线程（primus 就是这样）
glMapBuffer(...); glUnmapBuffer(...);
```

**这个结构相对 N23（串行）多了两件事**：
1. 主线程在 worker 还在 `map` 时就能渲染并 **swap 下一帧** → 覆盖"swap 发生在拷贝飞行期间"；
2. 两个 context 在同一个 pbuffer 上 `makeCurrent`，与 primus 同构。

### 2.1 单次复跑（LOAD=0，FINISH=1）

```
主线程渲染帧数 2341 / worker 回读帧数 2341        ← 严格 1:1，并发成立
首像素=76  （全屏 clear (0.1,0.2,0.3) → B≈76）    ← 阳性对照有效
readpixels(提交) p50=0.004 ms
*D=map_wait     p50=2.486 ms   min 2.265 / max 2.766
```

**2.486ms，比串行版（2.602）还略快**（少了 swap 后的 FRONT 读等待）。

## 3. ★ 16 组矩阵：map 不动，gpu_copy 疯涨

| mode | LOAD | FINISH | **map p50** | gpu_copy p50 | 比值 |
|---|---|---|---|---|---|
| mt_front | 0 | 1 | **2.486** | 2.534 | 1.02× |
| mt_front | 0 | 0 | **2.486** | 2.532 | 1.02× |
| mt_front | 200 | 1 | **2.534** | 7.177 | 2.83× |
| mt_front | 200 | 0 | **2.567** | 7.184 | 2.80× |
| mt_front | 400 | 1 | **2.530** | 14.057 | 5.56× |
| mt_front | 400 | 0 | **2.563** | 14.061 | 5.49× |
| mt_front | 800 | 1 | **2.529** | 27.771 | **10.98×** |
| mt_front | 800 | 0 | **2.544** | 27.782 | 10.92× |
| mt_back | 800 | 0 | **2.555** | 27.752 | 10.86× |

**`map` 一整列在 2.486~2.568 之间（波动 3%），`gpu_copy` 涨了 11 倍。**

### 3.1 为什么 gpu_copy 是错的

`gpu_copy` 的测法：

```c
glQueryCounter(q1, GL_TIMESTAMP);
glReadPixels(...);            // 提交拷贝
glQueryCounter(q2, GL_TIMESTAMP);
gpu_copy = t2 - t1;
```

`GL_TIMESTAMP` 记录的是"**该 query 命令在 GPU 上被处理的时刻**"。
两个 context 的命令在 GPU 队列里**可以交错**——`q2` 排在**本 context** 的拷贝之后，
但**另一个 context 的渲染命令可以插在中间**。

于是 `gpu_copy` 测到的是"q1 到 q2 之间 GPU 整体忙了多久"，= 拷贝 + 别人插进来的渲染。

**验证**：`gpu_copy − map ≈ LOAD × 0.0315ms/quad`（800×0.0315 = 25.2ms，实测 27.77−2.53 = 25.24）——
**正好是渲染时间**。说明这项测量已经把另一个 context 的工作算进来了。

> ⚠️ **这影响到既有报告**：报告 26/27/30 都用了 `gpu_copy(GPU轴)` 这个量（当时结论是
> "gpu_copy ≈ D，说明 D 就是拷贝在 GPU 上的执行时间"）。那时的环境是**单 context**，
> 所以没有污染、结论仍然成立。但**它的适用范围必须注明：只在单 context 下有效**。

## 4. 结构差清单（穷尽）

| # | 结构差 | 消掉的方式 | 结果 |
|---|---|---|---|
| 1 | FBO vs pbuffer | rb_lat6 严格 pbuffer | 2.487 vs 2.602（差 0.115） |
| 2 | 读 BACK vs FRONT | 两种都测 | 2.487 vs 2.487（串行）/ 2.486 vs 2.486（双线程） |
| 3 | swap / 不 swap | 都测 | 2.487 → 2.602（+0.115） |
| 4 | 单 / 双缓冲 | dbuf 0/1 | 无差别 |
| 5 | 并发 GPU 负载 0~28ms | 单线程加压 + glFinish 剥离（报告 41） | 恒 2.48 |
| 6 | **swap 在 FRONT 拷贝飞行期间** | **双线程（本报告）** | **恒 2.49** |
| 7 | finish / 不 finish | LOAD×FIN 矩阵 | 无差别（≤0.04ms） |
| 8 | 两个 context 共享 pbuffer/PBO | 双线程 share context | 同上 |

**8 项全消。** 真进程仍然是 30.4ms（`PRIMUS_SLEEP=0` 时 map=30.289ms）。

## 5. 剩下的差异，以及该怎么做

### 5.1 已经不可能的解释

- ❌ "拷贝本身慢"——隔离里它贴物理下限（0.94×）
- ❌ "GPU 忙/排队/抢带宽"——8 项结构差 + 负载 0~28ms 全无关
- ❌ "pbuffer/FRONT/swap 特有"——严格复刻 2.60ms
- ❌ "并发 swap 冲突"——双线程 2.49ms

### 5.2 剩下的（都在真进程环境里）

| 候选 | 为什么还没排除 | 怎么查 |
|---|---|---|
| **两个 X Display 连接**（`adpy`=NVIDIA 渲 pbuffer，`ddpy`=Intel 上屏）+ display worker 用 `di.pixeldata` 做 `glTexSubImage2D` | 隔离只有一个 Display、没有第二个 GPU | 看真进程里 worker 的 map 期间是否在等 X（`poll`/`ioctl(X)`/futex） |
| **双 PBO 交替 + `GL_STREAM_READ` orphaning** | 隔离只有 1 个 PBO，且 readPixels/map 严格串行 | 加"双 PBO 交替"变体；或让 readPixels 与 map 真正重叠 |
| **12+ 线程争抢** | 隔离只有 2~3 线程 | 看 map 期间 worker 的 sched 状态 |
| **Heaven 的渲染内容**（纹理/深度/大量 draw call） | 隔离只用纯色 clear + quad | 隔离里加纹理/深度/多 draw call 负载 |

### 5.3 ★ 方法转向：不要再"复现"，要"就地观测"

已经用了 3 轮（N18/N23/N25）在隔离环境里加结构，每次都是 2.5ms。
**继续加结构是低效的**——因为隔离环境与真进程的差异已不在"GL 调用顺序"这一层。

**下一步（N27）应该是**：在真进程、`PRIMUS_SLEEP=0` 条件下，追踪 map 那 30ms 里 worker 线程在干什么：

```
探针：
  mb_in / mb_out        （已有，0x18902 / 0x18908）
  sys_enter_futex       看是否睡 futex（报告 32 的方法）
  sched_switch          看 worker 是 running 还是 sleeping
  sys_enter_poll / ioctl 看是否在等 X server
  trace_marker          在 mb_in 处打标记，方便对齐
```

**判读**：

| 观察 | 结论 | 下一步 |
|---|---|---|
| map 期间 98% 睡 futex | 驱动内部在等一个完成通知（与报告 32 同构，但这次是 30ms 而非 3ms） | 追是谁该唤醒它（报告 38 的方法） |
| map 期间 worker **running 烧 CPU** | 驱动在自旋等 DMA | 看是 glcore 的哪个循环 |
| map 期间有 `poll`/`ioctl(X)` | **在等 X server / 显示端** → 与双 Display 有关 | 排除 `ddpy` 的影响（把 display worker 停掉试） |
| map 期间 worker **off-CPU 但非 futex**（如 `sched_switch` 到别的线程） | 被调度走了 | 看 CPU 竞争 |

**这一步不需要新建探针**——报告 32 的 `t8_*` 脚本已经做过同样的事（当时测的是 3ms 的 map），
只要换成 `PRIMUS_SLEEP=0` 重跑。

### 7.1 本轮的操作细节

- `glReadBuffer` 是 **context 状态**，worker 必须在自己 `makeCurrent` 之后单独设一次
  （主线程设过也不会继承——第一版漏了这行会导致 worker 读错 buffer）。
- sem 配对必须严格 1:1（主线程 `post(acq)` 后 `wait(rel)`；worker `wait(acq)` 后 `post(rel)`），
  否则会像 `rb_lat5` 那样死锁（报告 30 踩过）。
- 退出时 `m.stop=1` 后要**再 `post(acq)` 一次**把 worker 从 `sem_wait` 里放出来，否则 `pthread_join` 挂死。
