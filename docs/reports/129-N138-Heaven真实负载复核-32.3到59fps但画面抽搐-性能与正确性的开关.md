## 2. 注入测试的做法

**同一套参数**（从启动器抄的，见 §1），只加 `-benchmark`：

```bash
sudo -u <user> -E ./heaven_x64 <启动器的全部参数> -benchmark
```

- 用 `sudo -u <user>` 保持用户身份（root 连不上 Xwayland 的 xauth）
- **PID 必须用 `pgrep -x heaven_x64` 找，不能用 `$!`** —— `sudo` 会让 `$!` 变成 sudo 自己的 pid
  （我踩过一次，perf 采样的对象错了，拿到 `<not counted>`）
- 探针：`glXSwapBuffers`（`libGL.so.1:0x45710`）计帧 + `0x1572e64` 读 ctx/flag
- 等进入渲染（swap > 5 fps）后，读 ctx、`gdb -p` 把 `[ctx+0x320]` 置 1

**注入成功确认**：

```
=== 场景开始，注入 ===
  0x7f4948008ad0 -> f=1
```

## 4. 为什么抽搐：这是功能代价，不是 bug

`bit0=1` 时，驱动返回的"读指针"是：

```asm
1572e6d: mov 0x1240(%rdi),%rax     ; = [wp-1]，一个恒定的缓存值
```

**它不是一个真实推进的读数，而是"上次写入位置减一"的静态值。**

于是 pushbuffer 的"还剩多少空间"判断变成：

```
rp(假的, 恒定) >= sz(真实的, 在增长)   ← 永远成立
```

**驱动会以为空间永远够，把命令一直往后堆，而 GPU 实际还没消费到那儿。**

⇒ 结果就是：**命令覆盖尚未执行的区域 / 提交了不完整的状态** ⇒ 画面闪烁、抽搐、几何错乱。

**这就是驱动为什么默认走 MMIO 读真实值**：不是为了慢，是为了不把画面画错。

**n83a 之所以能到 1.42 ms 还看不出问题，是因为它不检查画面正确性**（只算 chk 校验和，不比对视觉结果）。
这是上一轮结论的一个重要修正：85 倍不是"免费的午餐"。

## 5. 对原始问题（525 比 515 慢）的最终定位

现在可以把整条链拆成两个**互相独立**的因子：

| 因子 | 515 | 525 | 是否可优化 |
|---|---|---|---|
| **单价**：取读指针走不走 MMIO | 走（无岔路，直接转发） | 走（`bit0=0` 走慢路径） | ❌ 不能靠改 bit（会抽搐） |
| **次数**：每对查几次 | **3.84 次** | **108.3 次** | ✅ 这是真正的靶点 |

**⇒ 105 ms 的差距 = 105 次额外查询 × 1.18 µs，而"单价"两版其实一样（都是 MMIO）。**

**所以驱动没有"摆烂"。真正的问题是：为什么 525 在 M3 场景下要查 108 次，而 515 只查 3.84 次。**

这个数在报告 127 里已经指向 pushbuffer 饱和（写入 1.5× / 等待 16.7× 的超线性），
但 `sz` 的单位还没定出来，所以"为什么饱和"仍未有定论。

## 7. 一句话

**Heaven 证实了提速是真的（32.3 → 59 fps），也证实了这个 bit 不能用 —— 画面抽搐。**
**两者其实是同一件事：那个"缓存值"根本不反映真实消费进度，所以既快又错。**
**驱动选 MMIO 读真值，是为了画对；它慢，但它对。**
**真正的靶点回到次数上：为什么 525 每对要查 108 次，515 只查 3.84 次。**
