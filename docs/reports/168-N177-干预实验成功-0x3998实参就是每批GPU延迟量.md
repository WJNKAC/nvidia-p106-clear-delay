# N177 — ★ 干预实验成功：`0x3998` 的实参就是每批的 GPU 延迟量，改小 15 倍 → 帧时间降 5.5 倍

**日期**：2026-10-27
**平台**：<user>@<testhost>，P106-100，525.116.03
**负载**：`n83b -M 7 -n 400 -c 400`（400 draw / 400 批 / 帧），`-G`（glFinish，纯 GPU 时间）

---

## 0. 一句话结论

**在 525 上运行时把 pushbuffer 里 `0x3998` 的实参从 `0xF0(=240)` 改成 `0x10(=16)`，
`rp_p50` 从 100.4 ms 降到 18.1 ms（5.5×），而改写工具本身零干扰（只读对照仍是 100.4）。**

**⇒ 报告 167 里"240 与 118.6 µs 强相关"从相关变成了因果。**
**`0x3998` 的实参就是"每个批次的 GPU 延迟单位数"。**

---

## 1. 先排除最要命的混淆：改写工具自身有没有干扰

运行时改内存的工具（每轮 pread 1.5 MB、必要时 pwrite）会抢 CPU 和内存带宽。
如果它在跑的时候程序本来就变慢了，那所有结论都作废。

**所以先做一个"只读不改"的对照** —— 把 newval 设成**原本的值**（`0xF0`），
这样工具照常扫描但不会执行任何 pwrite：

| 条件 | `rp_p50` |
|---|---|
| 完全不跑改写工具 | **100.532 ms** |
| 跑工具，但 newval = 原值 0xF0（只读） | **100.410 ms** |
| 跑工具，newval = 0x10（真改） | **18.105 ms** |

**只读对照与无干扰相差 0.12% ⇒ 工具零干扰。**
**那 82.3 ms 的差距只能来自实参值本身。**

> **这是"干预实验"必须有的对照组。** 少了这一行，就无法排除"是工具拖慢/加快了程序"。

---

## 2. 单调性：三个值跨度 30 倍，严格线性

| 实参值 | `rp_p50` | 相对 0x10 |
|---|---|---|
| **0x10（16）** | **18.105 ms** | 1.0× |
| **0xF0（240）** | **100.410 ms** | 5.5× |
| **0x1E0（480）** | **186.915 ms** | 10.3× |

两点斜率：

```
(480 → 240)：187.0 - 100.4 = 86.6 ms / 240 单位 = 0.361 ms/单位
(240 → 16)： 100.4 - 18.1  = 82.3 ms / 224 单位 = 0.367 ms/单位
```

**两条独立区间的斜率相差 1.7%** —— 严格线性。

换算成"每批每单位"（400 批/帧）：

```
k = 0.364 ms/单位 / 400 批 = 0.91 µs / (单位·批)
```

模型自洽性检验：

```
T = base + 400 × k × n
base = 100.41 - 400 × 0.91e-3 µs × 240 = 100.41 - 87.4 = 13.0 ms
验算 n=16：13.0 + 400 × 0.91e-3 × 16 = 13.0 + 5.8 = 18.8 ms   （实测 18.1）✓
```

**两点独立数据 + 模型回代，全部吻合。**

---

## 3. `0x0` 是特殊值（不是线性外推点）

| 实参 | `rp_p50` |
|---|---|
| 0x0（0） | **100.622 ms** |

按线性外推，n=0 应该 ≈ base = 13 ms。**实测 100.6 ms，与 n=240 几乎相同。**

⇒ **`0` 不是"零延迟"，而是"特殊/非法值"，走了另一条路径**（可能是"用默认值"或"关闭该机制"，
而默认恰好等价于 240，或者触发了一次强同步）。

> **工程含义：不能靠"设成 0 试试"来验证这类寄存器。
> 必须扫至少 3 个非零值看线性，同时单独测 0。**

## 4. 完整定量模型（525）

```
T_GPU = 13.0 ms  +  批次数 × 0.91 µs × 实参值
```

| 配置 | 预测 | 实测 |
|---|---|---|
| 400 批 × 240 | 13.0 + 87.4 = 100.4 | **100.4** ✓ |
| 400 批 × 16 | 13.0 + 5.8 = 18.8 | **18.1** ✓ |
| 400 批 × 480 | 13.0 + 174.7 = 187.7 | **186.9** ✓ |

**对照 515**：同样 400 批，`rp_p50` = **0.95 ms**，且**完全不随批次数变化**。

⇒

| | 每帧 GPU 时间（400 批） |
|---|---|
| 515 | **0.95 ms**（无此项，base 也极小） |
| 525 | **100.4 ms**（其中 87.4 ms 是这一项） |
| 525 若把实参降到 16 | 18.1 ms |
| 525 + 完全去掉该项（假设可能） | 13.0 ms |

**515 连 base 都只有 0.95 ms，525 的 base 是 13 ms —— 说明除延迟项外还有约 12 ms 的批次固定开销。**
这一部分来自那 12 条共同的切批 method（报告 167 §2.1），两版都发，但 525 的代价高得多。
**这是下一个待查项。**

## 5. 兑现了什么、没兑现什么

### 兑现
- **因果关系成立**：改一个 4 字节实参，帧时间按比例变化，跨 30 倍值域严格线性，且工具零干扰。
- **定量模型可用**：`T = base + B × k × n`，可直接算"某个应用要多少批才不超预算"。
- **确认了 `0x3998` 的语义方向**：它是"延迟/等待单位数"，不是 0/1 模式位。
  （报告 167 的 A/B 二选一，选 A。）

### 没兑现
- **不是"修好了"**：这只证明"可以改"，而且改的是运行时数据，需要每帧持续改写。
  **不能作为产品方案**（性能损失、稳定性风险、随时可能被下次驱动更新改掉）。
- **base 的 12 ms 没解释**：即使实参降到 16，525 仍比 515 慢 19 倍（18.1 vs 0.95）。
  **延迟项只是主因，不是全部。**
- **`0x0` 的行为没查清**：可能是个隐藏的"完全关闭"路径，若能安全启用，理论上能逼近 base。

## 6. 一个必须记录的测量教训

同一配置 `-c 400 -G`，不同帧数给出不同结果：

| 帧数 | `rp_p50` |
|---|---|
| `-f 8`（短跑） | **49.75 ms** |
| `-f 200`（长跑） | **100.41 ms** |

**差 2 倍。** 短跑没有进入稳态（GPU 时钟 / 功耗 / 驱动内部状态都在变）。

> **规则：比较帧时间必须固定帧数，且要用"长跑 + 忽略 warmup"。
> 本项目此前大量结论用 `-f 8 -W 3`，绝对值都偏低，只可用于同帧数的相对比较。**
> 报告 166/167 里的绝对数值需要按此重新视为"短跑值"。

## 7. 工具演进（四个版本，每个都踩了一个坑，值得保留）

| 版本 | 做法 | 结果 | 坑 |
|---|---|---|---|
| `pbpatch` | `process_vm_readv` | **命中恒为 0** | 段首未映射时**整段**返回 `EFAULT` |
| `pbpatch2` | `pread/pwrite(/proc/pid/mem)` | 有命中，但**改写率仅 7.7%** | 每轮扫 28 段 × 1 MB = 28 MB，慢于 GPU 消费（118 µs/批） |
| `pbpatch3` | 记住**命中地址**反复改 | **完全无效**（结果与不干预相同） | 环形缓冲轮转会换位置，地址表迅速失效 |
| **`pbpatch4`** | 记住**活跃段**（实测只 3 段、1.5 MB），每轮只扫这几段 | **改写率≈100%**，结果自洽 | ✓ |

**关键判据（怎么知道改写率提高了）**：看"模型自洽性"。
pbpatch2 时 `n=0xF0` 得 49.75 ms、`n=0x10` 得 33.9 ms —— 两点算出的 k 与三点不一致；
pbpatch4 时三点严格线性、回代吻合 ⇒ 说明基本全部改到了。

> **验证"干预是否真的生效"不能只看"有没有变化"，要看"变化是否服从物理模型"。**
> 部分生效会给出"看起来有变化但斜率不对"的中间态，最容易误判。

## 8. 下一步

1. **查 base 的 12 ms**：实参降到 16 后 525 仍需 18.1 ms，而 515 只要 0.95 ms。
   差异在这 12 ms 的批次固定开销上 —— 对应报告 167 §2.1 那 12 条共同 method。
   做法：同样用 pbpatch4 的思路，逐条把 12 条 method 的实参/方法号改掉做干预。
2. **查 `0x0` 走的特殊路径**：若它是"完全关闭"，那是最优解；若它"用默认值"，则与 240 等价。
3. **重新标定历史数据**：所有用 `-f 8` 得出的 Heaven/n83b 绝对值，按 §6 的教训重新审视。
4. **产品层结论不变**：不能靠改运行时数据，**合批仍是唯一可交付的优化**。
