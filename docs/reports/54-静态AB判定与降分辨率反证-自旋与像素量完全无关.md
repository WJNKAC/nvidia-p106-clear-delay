# 54 · 静态 A/B 判定 + 降分辨率反证：**20µs 自旋与像素量完全无关**

> 2026-10-26 10:40
> 用户给出三步走：①静态对比 vtable 写入点（可能直接定 A/B）；②525 降分辨率看自旋是否随像素降；③才上 515。
>
> **两步都做完了，结果是：A 不成立，B 也被反证。**
> **自旋线程的 CPU 在 1080p 和 640×360 下都是 ~100%**，而降分辨率后 **worker 的 CPU 从 63.2% 掉到 1.5%（42 倍）**。
> **→ 那个自旋与"命令数/像素量"无关，是另一个完全独立的环路。**

---

## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **515 的分发器与 525 逐条一致** | `sched_yield` 在 515 是 `0xeb8278`、525 是 `146ccc0`；`usleep(250)`、跳转表结构、`cmp $0x5` 全部对应 |
| 2 | **515 的 vtable 构造器也是无条件写入** | 515: `0x2fa200-0x2fa240` 连续写 `0x270/0x280/0x288/0x290`，与 525 的 `0x383f3b-0x383f6c` 同构 |
| 3 | **→ A 不成立**：两版等待策略相同 | 由 1、2 推出 |
| 4 | **★ 降分辨率：自旋 CPU 不降** | 1080p **101.6%** → 640×360 **100.1%** |
| 5 | **★ 但 worker CPU 降了 42 倍** | **63.2% → 1.5%** |
| 6 | **→ B 也不成立**：自旋与命令数/像素量无关 | 由 4、5 推出 |
| 7 | **那个烧满一核的线程不是 worker** | 两者 CPU 曲线完全不同（一个恒 100%，一个随像素变） |

**一句话**：**A 不成立（两版相同），B 也不成立（自旋不随像素变）。烧满一个核的是另一个环路，它和 PRIME 拷贝、和命令数都无关。**

## 2. 第一步：静态对比 vtable 写入点 → A 不成立

### 2.1 525 的槽写入点

不是一个函数，是 **`_nv011glcore` 的 vtable 构造器**（`0x1470f5c-0x1470ffb`）：

```asm
1470f63: lea 0x146c470,%rax
1470f6a: mov %rax,0x128(%rbx)
1470f71: lea 0x146c860,%rax       ; ★ 0x280 的候选
1470fba: mov %rax,0x280(%rbx)     ; ★ 写 0x280
1470fc1: call 14701e0             ; ← 0x288 的值是这个调用的返回值
1470fd1: mov %rax,0x288(%rbx)     ; ★ 写 0x288
1470fe6: lea 0x146d240,%rax       ; ★ 微秒时钟
1470fed: mov %rax,0x290(%rbx)     ; ★ 写 0x290
```

**关键**：这一整段是**线性代码，没有任何条件分支**。
在 `0x383f3b-0x383f6c` 先写静态桩（`0x380b90/0x37e8d0/0x37c160`），
到这里再覆盖成真实现。**两次都是无条件写入。**

### 2.2 515 的槽写入点：同构

```asm
2fa200: lea 0x2f6d70,%rax ; mov %rax,0x270(%rbx)
2fa20e: lea 0x2f6d80,%rax ; mov %rax,0x280(%rbx)    ← 静态桩
2fa21c: lea 0x2f6d90,%rax ; mov %rax,0x288(%rbx)    ← 静态桩
2fa22a: lea 0x2f2420,%rax ; mov %rax,0x290(%rbx)
2fa238: lea 0x2f2430,%rax ; mov %rax,0x278(%rbx)
```

**同样是无条件线性写入，同样的槽顺序（`0x270→0x280→0x288→0x290`）。**

### 2.3 分发器：逐条一致

`0x288` 指向的分发器，两版完全对应：

| 525 (`0x146cc80`) | 515.105 (`0xeb8230`) | 语义 |
|---|---|---|
| `146cc8a: cmp $0x5,%edi` | `eb8237: cmp $0x5,%edi` | 一级分发 |
| `146cc8f: lea 0x1d3f140,%rdx` | `eb823f: lea 0x17514a0,%rdx` | 一级跳转表 |
| `146cc9f: jmp *%rax` | `eb824f: jmp *%rax` | 分发 |
| `146cca1: mov 0x270(%rcx),%eax` | `eb8258: mov 0x270(%rcx),%eax` | 二级分发（**同一字段偏移**） |
| `146ccb0: lea 0x1d3f158,%rdx` | `eb8263: lea 0x17514b8,%rdx` | 二级跳转表 |
| **`146ccc0: jmp sched_yield@plt`** | **`eb8278: jmp sched_yield@plt`** | ✅ 完全一致 |
| `146cd20: mov $0xfa,%edi; jmp usleep` | `eb8280: mov $0xfa,%edi; jmp usleep` | **usleep(250)** ✅ |
| `146cd30: mov $0x3e8,%edi; jmp usleep` | （同位置，待核） | usleep(1000) |

**→ A 不成立。515 和 525 用完全相同的等待策略。**

## 3. ★ 第二步：降分辨率 → B 也不成立

### 3.1 先说方法上的坑（踩了两次）

**第一次**用 `-video_width 640 -video_height 360`（带 `-video_mode 6`）：
三次运行的日志全是 `Set 1920x1080`，fps 全是 32 → **分辨率根本没变**（报告 21/27 的老坑）。

**第二次**去掉 `-video_mode` 只留宽高：**还是 1920×1080**。

**第三次**枚举 `-video_mode`：

```bash
$ bash enum_mode.sh 0
  video_mode=0 → Set 640x360      ← ★ 这才是有效办法
```

`-video_mode` 是**预设档位**，不是"模式"，改分辨率只能换档位。

### 3.2 实测结果

| `-video_mode` | 实际分辨率 | fps | **最忙线程 CPU** | **worker CPU** |
|---|---|---|---|---|
| 6 | 1920×1080 | 32 | **101.6%** | **63.2%** |
| 0 | 640×360 | 45 | **100.1%** | **1.5%** |

（每档 8 秒，C110S 核心数 12，零高頻探针、只开 1 秒低频 `mb_out` 认线程）

### 3.3 这组数据的三个含义

**① 自旋线程与像素量无关**
像素降到 1/9，fps 从 32 涨到 45（+41%），但**自旋线程仍是 100%**。
→ 它的工作量**不随渲染负载变**。

**② worker 的负载才与像素量强相关**
`63.2% → 1.5%`，**42 倍**。这个比例比像素比（1/9 = 9 倍）还大，
符合"拷贝数据量下降 + 每次拷贝更快"的双重效应。

**③ 两个线程是两条完全独立的曲线**

```
自旋线程:  1080p 101.6%  →  640x360 100.1%   （平）
worker  :  1080p  63.2%  →  640x360   1.5%   （崩）
```

**→ 报告 53 §7 猜"20µs 轮询是每命令一次"，这条被推翻了。**
若真是"每命令一次查队列"，像素降到 1/9 它就该降。
**它不降，说明它的触发源不是命令、不是像素。**

## 4. 那么这个自旋到底在等什么（新的问题定义）

| 已知 | 取值 |
|---|---|
| deadline | `t0 + 20µs` |
| 每次实际耗时 | ~6.6µs |
| 频率 | ~152,000 次/秒（**与 fps、与像素都无关**） |
| 与 worker 关系 | **无关**（两条独立曲线） |
| 与版本 | 515/525 相同 |

**152,000 次/秒 ≈ 每 6.6µs 一次，与帧率无关 = 一个固定节拍的轮询。**

这更像：
- 一个**常驻的看门狗/心跳线程**（固定周期）；
- 或一个**按 6.6µs 输出的定时器循环**；
- 而**不是**"应用每帧提交 N 条命令"驱动的。

**注意**：报告 53 说它跑在"readback worker 同一线程且相邻 tid"——
但本轮数据显示这两个 tid 的 CPU 曲线完全不同，**应该重新确认它们是不是同一个线程**。

## 5. 对三个可能性的最终判定

| 可能 | 状态 | 依据 |
|---|---|---|
| **A. 20µs 轮询只存在于 PRIME 路径（525 新增）** | **❌ 不成立** | 515 有同构的 vtable 构造器 + 逐条一致的分发器 |
| **B. 设计相同，但 P106 上 20µs 内完不成** | **❌ 不成立（部分）** | "完不成"应有 20µs 超时痕迹；但**自旋 CPU 完全不随像素变** → 它的循环次数不由拷贝量决定 |
| **C. 自旋是独立心跳环路，与 PRIME 拷贝解耦** | **✅ 新假设** | CPU 恒 100%、152k 次/秒、与 fps/像素/worker 全无关 |

**C 的含义很重要**：
如果那 100% CPU 是**一个独立常驻环路**，那它和"上屏慢"是**两个并行的问题**，
不是同一个因果链的两端。

**→ 报告 48 说"11.4ms CPU/帧 空转导致慢"这个因果，需要重新审视。**
更可能是：**它只是一直在烧 CPU（占了一个核），并未直接拖慢 map**。
（12 核机器上烧掉 1 核 → 若其他线程不被它挤，就不影响帧时间。）

## 6. 明确结论

| 项 | 结论 |
|---|---|
| A/B 判定 | **A 不成立；B 也被反证**（自旋与像素无关） |
| 是否需要上 515（N50） | **不需要了** —— 两个静态对比已经证明两版同构；而"515 不烧 CPU"的谜，答案可能不在驱动版本，而在**它跑的场景不同**（有输出的卡不走 PRIME 拷贝，但那也不该影响这个独立环路…） |
| 对提速的意义 | **那 100% CPU 可能根本不是帧时间的组成部分**。之前把它当成"11.4ms/帧 的浪费"可能是个错误归因 |
| 下一步 | 不是继续挖这个自旋，而是**重新确认因果**：把它杀掉/让它睡，看 fps 变不变 |

---

## 7. 唯一剩下的一条（有决定性）

**把那个烧 100% 的线程 `SIGSTOP`，看 fps 变不变。**

- 若 **fps 不变** → **它和性能无关**，前面从报告 44 到 54 这 11 轮都是"追一个不影响结果的量"，
  **必须回到报告 40 的 T_land（跨 GPU 拷贝）**
- 若 **fps 掉了** → 它确实是瓶颈，继续挖它的触发源

**这是唯一能把"因果"钉死的一刀，而且是零成本的（`kill -STOP`）。**

### 8.1 三个方法论要点

1. **`-video_mode` 是档位不是模式。** 改 Heaven 分辨率只能换档位（0→640×360，6→1920×1080），
   `-video_width/height` 会被忽略。**每次都必须用日志 `Set WxH` 复核**（本轮复核两次才发现没生效）。

2. **"两个量强相关"必须做负载敏感性测试。** 本轮降分辨率一次性把
   "自旋 ↔ 命令数"这个假设否掉了：真相关的量会跟着负载走（worker 63%→1.5%），
   不相关的量纹丝不动（自旋 101%→100%）。

3. **同 tid 相邻 ≠ 同一线程，同 CPU 占比 ≠ 同一曲线。**
   必须用"负载变化"或"负载敏感性"来区分两个线程，不能只看某一时刻的数值。
