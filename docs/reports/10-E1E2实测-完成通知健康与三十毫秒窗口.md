# 10 · E1/E2 实测：完成通知不慢，慢的是"到点才去看"

> 2026-10-25 00:30–01:05
> 起点：用户把全案收敛为一个物理量——"谁、在什么时刻，把序列号推进了"，并给出 E1–E4 的优先级
> 结论：**E1 判定"传输健康"；E2 拿到硬数：GPU 2.64 ms 就干完，驱动 30.24 ms 后才收；自旋者是 GL swap 线程本身。**
> 同时**推翻我自己在报告 09 §4.2 的一个关键断言**（主线程 99% 自旋在 `0xae5d44`）——那里不是热点。

## 0. 先补方法学：用户指出的采样盲区成立，已用 schedstat 关闭

我在报告 09 里用"18 线程 100% S"排除了"用户态写者"。用户指出：50 ms 间隔（20 Hz）的**状态快照**看不见一个"每秒醒 30 次、每次跑 100 µs"的线程——它的 R 占空比只有 0.3%，20 Hz 采样命中概率 ≈ 0.3%。

这条批评成立，且比表面更严重：**只看 state 字段时，连"谁在跑"都无法量化**。本轮改为两条互补通道：

| 通道 | 频率 | 看得见什么 |
|---|---|---|
| `/proc/<tid>/stat` 的 state | 425 Hz | 瞬时驻留状态（仍看不见 100 µs 级） |
| `/proc/<tid>/schedstat` 的 `sum_exec_runtime`（ns 精度） | 425 Hz | **累计 CPU 时间增量**——100 µs 的醒来也会被记进账本 |

`sum_exec_runtime` 在线程被换出（dequeue）时会由 `update_curr()` 结账，所以"跑完 100 µs 又睡回去"的线程一定会在下一次采样里体现为 runtime 增量。**这比抓瞬时状态可靠一个量级。**

判读结果（15 s 窗口，19 线程）：

| tid | CPU 占比 | 说明 |
|---|---|---|
| **35985 / 36380** | **99.3%** | 唯一自旋者（每次运行 tid 不同） |
| 35961（主） | 15.2% | 应用侧工作 |
| 35976 | 6.4% | — |
| 其余 16 个 | ≤1.3% 各自 | 真休息 |

**不存在"低占空比用户态写者"**：除自旋线程外，没有任何隐藏线程在消耗 CPU。这条盲区关闭。

## 1. E1：CUDA 完成往返 —— 判定"传输健康"，判据远低于 50 µs 门槛

### 1.1 工具链的一处绕道

主机无 torch；有 `/usr/local/cuda-12.9`，但 **CUDA 12.9 头文件与 glibc 2.43 冲突**
（`mathcalls.h` 的 `cospi/sinpi` 异常规格与 `crt/math_functions.h` 不兼容，`nvcc` 直接报错）。

改走**驱动 API + 手写 PTX**（与原 `/tmp/burn.c` 同一路数），只用 `dlopen("libcuda.so.1")` + `gcc`，不依赖 nvcc：

```ptx
.version 6.4
.target sm_61
.address_size 64
.visible .entry nop() { ret; }
```

另有一处必须改：**不要固定 `range(20000)`**。若单次真是 27 ms，20000 次要跑 9 分钟。
改为**时间预算循环**（默认 3 s/模式），自适应计次。

### 1.2 结果

空闲（无 GL 负载）：

| 模式 | n | 均值 | 最小 | 最大 |
|---|---|---|---|---|
| A 提交（异步不等） | 2,610,256 | **1.1 µs** | 1.0 | 180 |
| B 提交+ctxSync（背靠背） | 618,837 | **4.8 µs** | 4.5 | 186 |
| C 提交→空闲 30 ms→Sync | 100 | — | **3.2 µs** | **33.3 µs** |
| D 8 kernel + 1 Sync | 241,834 | 12.4 µs | 11.6 | 196 |
| E 独立 stream 提交+Sync | 645,369 | 4.6 µs | 4.4 | 134 |

Heaven 渲染期并存（GPU 93% / 48.5 W）：

| 模式 | 均值 | 最小 | 最大 |
|---|---|---|---|
| A | 1.6 µs | 1.0 | 1527 |
| B | 76.1 µs | 4.5 | 1782 |
| **C 空闲 30 ms 后 Sync** | — | **7.0 µs** | **26.0 µs** |
| D | 202.4 µs | 11.8 | 1792 |
| E | 74.8 µs | 4.4 | 1790 |

### 1.3 判读

- **C 模式是关键**：先让 GPU 空转 30 ms（正是本案的帧间隔形态），再同步——完成通知送达仍是 **7–26 µs**，与空闲态同量级。
- 背靠背 B 在 GL 并存时升到 76 µs（争用），但 min 仍是 4.5 µs，说明不是路径变慢，是排队。
- 按用户预注册判据 `< 50 µs → 传输健康`：**命中**。

> **结论：GPU→CPU 的完成通知机制没有回归。** 27~30 ms 不是"通知传得慢"，只能是 GL 前端"什么时候去看"。
> 这与 Vulkan 358 fps 的间接证据一致，但现在是从另一条 API 路径直接测出来的。

## 2. E2：seq(t) 曲线 —— 先纠正一个会白费一下午的前提

### 2.1 `*0x1900(%rbx)` 是函数指针，不是序列号

用户方案写的是 `SEQ_ADDR = rbx+0x1900`，然后用 `/proc/pid/mem` 轮询它。
但按 580.126.18 的反汇编，那是**间接调用**：

```
ae5d30: mov  %rbx,%rdi
ae5d33: call *0x1900(%rbx)     ← 调用表中第 0x1900 字节处的函数指针
ae5d3c: mov  %rax,%rbp          ← 返回值才是"序号"
```

轮询 `rbx+0x1900` 只会读到一个**代码地址**（常数），永远不变。
真正的"序号"是**返回值**，而它的来源在那张调用表指向的函数里。这一点如果不先纠正，E2 会跑出一个平坦直线然后被判成"seq 不推进"。

### 2.2 更糟的是：那个循环根本不是热点

我按 09 §4.2 的理解，把断点下在 `0xae5d44`（`cmp %r14,%rbp`），gdb **等了 90 秒没命中**（`gdb` 停在 `do_sys_poll`）。

于是改做一次场景期 perf（本次才第一次在 580.126.18 + 场景相位下取 LBR）：

```
21.18%  [vdso] __vdso_clock_gettime
 6.93%  glcore 0xb0fde5        ← 0xb0fd70 内，扫待完成数组处
 6.30%  libc   clock_gettime
 2.50%  glcore 0xa1ad39
 2.42%  [unknown] 0x7f8381fcb525
 2.22%  glcore 0xa1ad53
```

调用链（同一线程）：

```
glXSwapBuffers (glcore+0xb1af1)
  └ 0x82440
     ├ 12.0% → 0xb1029a → 0xae5c59 → 0xb0fd70+0x98 → clock_gettime → vdso   (0xb0fe08 `call *0x290`)
     ├  8.9% → 0xb10292 → 0x1058900+0x77 → clock_gettime → vdso
     └  3.1% → 0xb10292 → 0x1058900+0x2d → clock_gettime → vdso
```

**热循环是 `0xb10140 ↔ 0xb102a8`**，不是 `0xae5d44`。`0xae5c30/0xae5d44` 只在被调用时经过一次（各 0.6%）。报告 09 §4.2 那段"主线程 99% 在 `0xae5c80` 里 `kick→get_seq→cmp→js`"**是错的**，作废。

### 2.3 真正的完成标记找到了

`0xb10140` 块在扫一个数组 `ctx+0x1418`，每项是"基址"，加 `r14`（这次 = 0x10）后：

```
b1017f: movzwl 0xe(%rdx),%edx
b10183: cmp   $0xffff,%dx      ← 等于 0xffff = 这一项做完了
```

反过来清零在 `0xb101e3` / `0xb1020c`（写 0）。**这就是那个物理量**：
`*(u16*)(arr[i] + r14 + 0xe) == 0xffff` 表示完成。

gdb 单次停点取得真实地址（本次运行 `arr[0]=0x7fe76c4ec000`、`r14=0x10`、`marker=arr[0]+0x1e`），
并且发现命中它的是 **4 号工作线程**，不是主线程。

### 2.4 seq(t) 曲线：每帧恰好一次

用 5 kHz（实际 3.76 kHz）轮询该 u16，15 s 得 907 个跳变事件：

| 取值 | 次数 |
|---|---|
| 0xffff | 454 |
| 0 | 453 |

**取值只有两个，严格交替。** 454 次/15 s = **30.3 次/秒，正好等于帧率（HUD 31）**。
→ 每帧恰好一次完成、一次清零。不存在"每帧多次小步进"，也不存在"每帧一个大步进 vs 多个微批"的分歧——
**粒度就是 1 次/帧**。

### 2.5 两段延时（本轮最硬的数）

| 区间 | 含义 | n | 中位 | p10 | p90 | max |
|---|---|---|---|---|---|---|
| `fall→rise` | 标记清零 → GPU 写回 0xffff（**GPU 干活+上报**） | 453 | **2.64 ms** | 2.11 | 3.86 | 10.63 |
| `rise→fall` | 0xffff → 驱动发现并清零（**"去看"的延迟**） | 453 | **30.24 ms** | 30.01 | 30.61 | 30.93 |
| `fall→fall` | 帧周期 | 452 | 32.87 ms | 32.30 | 34.20 | 40.74 |

**GPU 2.64 ms 就干完了；驱动过 30.24 ms 才去看。**
`rise→fall` 的分布紧到 ±0.3 ms（p10 30.01 / p90 30.61），这不是"负载抖动"，是**定时行为**。

### 2.6 谁在跑（schedstat 归因）

按 200 个窗口逐段累加各线程 `sum_exec_runtime` 增量：

| 区间 | 自旋线程 | 主线程 | 第三线程 |
|---|---|---|---|
| `rise→fall`（30 ms 等待段） | **27.83 ms/窗口** | 3.00 ms | 1.26 ms |
| `fall→rise`（2.64 ms GPU 段） | 1.19 ms | 1.73 ms | 1.28 ms |

**等待段的 CPU 几乎全部由那个自旋线程烧掉，而且它就烧在"等"里面。**
→ 排除了"等待期间 CPU 在干别的活"这一解释：它不是没空去看，它一直在看。

### 2.7 中断账本：没有每帧中断

`/proc/interrupts` 里 nvidia 相关计数：**15 s 内 27 次 = 1.8 次/秒**，而完成是 30 次/秒。
→ **0xffff 不是靠中断送达的**，是 GPU 直接写宿主机内存；驱动靠轮询看见。
所以"中断/通知延迟"这条分支彻底排除，与 E1 互相印证。

## 3. 一个差点写错的机制（自查记录）

`0xb0fd70` 里读时钟后与 `ctx+0x6e48` 比较，而 `ctx+0x6e48` 由 `0xb0fec0` 写成：

```
b0fec0: imul $0xfa,0x22e0c(%rbx),%eax    ; 250 * N
b0feca: movb $0,0x6e41(%rbx)
b0fed1: sub  $0xfa,%eax                   ; 250*(N-1)
b0fed6: add  %rax,%rdx                    ; deadline = now_ms + 250*(N-1)
```

我第一反应是"30 ms = 250×(N−1) ⇒ N≈121，pacer 回来了"。**实测否证**：

```
N(0x22e0c) = 12          → 250×(12−1) = 2750
deadline − now = 2634 ms
```

2634 vs 2750 吻合（差 116 ms 是 deadline 在 116 ms 前设置），但**量级是秒，不是毫秒**。

→ 这条语义是：**"等够 250 ms × 挂起数之后，放弃等待并强制 kick"的退避**（`0x6e41` 计到 >3 次转 `0xb0ff30` 强制踢），
**跟逐帧节拍无关**。N=12 时它是 2.75 秒，只在卡死时兜底。

**如果我没去测 N，就会把"250 µs pacer 复活"作为结论发出去。**这是本案第三次同类错误（前两次见 README 铁律）。

`0x1058900` 也顺带澄清：它是 `t0+0x14`（20 ns）的 `pause` 自旋，
把耗时累加到 `ctx+0x6e10`（实测仅 1823 ns，说明通常第一次检查就满足）——**单次极便宜，但被调用了几百万次**。

## 4. E3：gap 直方图（用 E2 的数据直接裁决）

用户要求："gap 常年 1–2 → 每提交同步；gap 大且随渲染量走 → 帧末排水。"

实测：**kicks/frame = 1.00**（454 次完成 / 453 个帧周期），帧周期中位 32.87 ms，p10 32.30、p90 34.20。

→ **每帧一次同步，一帧一个等待。**既不随渲染量切分，也不在帧内多次排水。
这正是"帧末排水 + 单次同步"的形态，与 `0xb10140` 那个 `while (pending > 0)` 循环一致。

同时裁决 GPU 利用率 92% 的两种读法：
- (a) 帧被切成 N 个微批，间隙不被 `utilization.gpu` 识别 → **否**，粒度是 1 次/帧；
- (b) SM 上驻留一个自旋等待 kernel → **是**（mem 6%、47 W 同步支持）。

## 5. 更新后的模型

```
一帧 32.87 ms
├── GPU 真正干活并上报        2.64 ms   (6%)
├── 驱动"没去看"的窗口       30.24 ms   (94%)  ← 分布紧至 ±0.3 ms
└── 两者之间，自旋线程烧掉   27.83 ms   (在"等"里自旋，2 次 clock_gettime/迭代)

GPU 侧：SM 92% / mem 6% / 47 W / 满频 / 无降频 / 1.8 IRQ/s
        → 驻留但空转（自旋 kernel），不是算得慢
CPU 侧：唯一自旋者 = 发起 glXSwapBuffers 的 GL 线程（99.3%）
        其余 18 线程含主线程（15.2%）都没有隐藏占用
```

**已排除**：功耗墙、温度、频率、显存带宽、完成通知传输（E1 直接测得 7–26 µs）、中断路径（1.8/s）、worker 交接（渲染期无）、隐藏低占空比写者（schedstat 账本）。

**仍未定**：那 30.24 ms 为什么是 30.24 ms。已知它不是 250×(N−1)（那是秒级退避），不是中断，不是负载抖动（±0.3 ms），且等待期间 CPU 就烧在这个循环里。

## 6. 下一步（只剩一个判据）

**分离"刻意定时"与"CPU 真忙"**——三个互斥读数，一次运行即可：

1. **改场景复杂度、固定分辨率**：同一脚本换 `world_load` 的另一张图（或 `-video_width 320` 已做：帧周期 27 ms）。
   若 30.24 ms 随帧周期等比缩（27→~25 ms）→ 它是"帧末排水"，是 CPU 侧工作量决定；
   若它保持 30.24 不变 → 是硬编码定时/节拍。
2. **读 `ctx+0x6e10` 的每秒增量**：这是 `0x1058900` 累计的 20 ns 自旋总时长。
   若它 ≈ 0 而 CPU 仍 99% → 时间花在别处；若它 ≈ 30 ms/帧 → 就是这个微自旋被调用了几百万次。
3. **在 `0xb102a8`（回跳处）数命中次数/秒**（用 `perf probe` 或一次 `perf stat -e` 软件事件）：
   直接给出每帧循环迭代次数。若 >10⁵，则"2 次时钟读/迭代 × 10⁵"本身就是 30 ms 的来源。

三个数字出来后，"谁让这 30 ms 发生"只剩一种解释。

## 9. 本轮方法学增量（已并入 README 铁律配套规则）

1. **轮询目标必须是"真实地址"，且先反汇编确认它是数据还是函数指针。**（`*0x1900(%rbx)` 是 call）
2. **断点不命中就是结论**：gdb 等 90 s 未命中，比任何 perf 图都更早地否掉了"那是热点"。
3. **线程占空比要用 `schedstat` 的 ns 精度累计量，不要用 state 快照。**（20 Hz 看不见 0.3% 占空比）
4. **凡从常数推断出的机制（250×N），必须实测那个 N。**否则会把秒级退避当成毫秒级节拍。
