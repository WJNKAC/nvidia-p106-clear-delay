# 79 · N87-A 判决：515 的每对成本是 0.03µs，525 是 121µs —— 差 4000 倍，案子收口

日期：2026-10-26 12:35
驱动：**515.105.01**（用户装好，机器重启后 4 分钟起测）；对照数据来自报告 78 的 525.116.03
工具：`analysis/n83a/n83a.c`（`-S` 单进程扫描 + 全程自计数，同一二进制、同一环境变量）
机器：P106-100，1920×1080，直连 NVIDIA（`__GLX_VENDOR_LIBRARY_NAME=nvidia`）

## 0. 结论（一句话）

**525 的 121µs/对 在 515 上不存在——不是变小，是 0.03µs，差 4000 倍。**

| | 515.105.01 | 525.116.03 | 比值 |
|---|---|---|---|
| M1 基线（无配对） | **2.604 ms**（N=0..2000 全程平） | 2.625 ms | 1.0× |
| M3 切 program，1000 对 | **2.539 ms** | **123.454 ms** | 49× |
| **每对成本** | **0.03 µs** | **120.81 µs** | **4000×** |
| M6 no-op 切，每对 | 0.03 µs | 120.78 µs | 4000× |
| M0 4 次 legacy，每对 | 0.12 µs | 121.67 µs | 1000× |
| M2 uniform，每对 | 0.07 µs | 0.02~0.04 µs | ≈1× |

**报告 78 的预测（515 ≈ 34ms / 31.3µs/对）被推翻——方向对，但量级差了两个数量级：515 根本不付这笔钱。**
这比"3.9 倍"更强：**3 倍的整帧差距，全部来自 525 单方面新增的每对 121µs。**

## 1. 三条曲线的原始数据（515，单进程内扫完）

### M1 基线：与 525 完全一致 ⇒ 纯带宽项不变

```
N        map_p50(ms)    pairs/frame
0        2.604          0.00
100      2.574          0.00
200      2.578          0.00
500      2.583          0.00
1000     2.614          0.00
2000     2.627          0.00
```

`map ≈ 2.60ms` 恒定，2000 个纯 draw 只多 0.02ms ⇒ **8.29MiB 回读的带宽成本两版相同**（525：2.625）。

### M3 切 program：每对 0.03µs（525 是 121µs）

```
N        map_p50(ms)    pairs/frame      us/pair_vs_N0
0        2.513          0.00             0.00
100      2.525          100.00           0.12
200      2.535          200.00           0.11
500      2.537          500.00           0.05
1000     2.539          1000.00          0.03
2000     2.531          2000.00          0.01
斜率(N=1000→2000): -0.01 us/对
```

**1000 对只让 map 从 2.513 涨到 2.539（+0.026ms）。** 同一份代码在 525 上：123.454ms。

自计数自检通过：`pairs/frame = 100.00 / 200.00 / 500.00 / 1000.00 / 2000.00`（精确等于 N）。

**CPU 侧仍在提交**：`submit_p50 = 1.036ms @ 1000 对`（1.04µs/对），与 525 的 0.14~4.11µs/对同量级
⇒ **差的不在提交，在 GPU 侧**（与报告 76 的判据一致）。

### M6 / M0 / M2：所有配对类型都免费

```
M6 (no-op 切): 1000 对 → 2.529ms  (0.03µs/对, 斜率 0.00)
M0 (4 legacy): 1000 对 → 2.624ms  (0.12µs/对, 斜率 0.05)
M2 (uniform) : 1000 对 → 2.574ms  (0.07µs/对, 斜率 0.01)
```

⇒ 525 上"变 0 个/变 1 个/变 4 个都收 121µs"的那个**批次开始惩罚**，在 515 上对任何变更都不存在。

## 2. 对账：Heaven 的 3 倍差距全部落地

| | 525 | 515 |
|---|---|---|
| 每对成本 | 121 µs | 0.03 µs |
| Heaven 配对数（报告 76/78 推算） | 268 对/帧 | 268 对/帧 |
| 配对总成本 | **32.4 ms** | **0.008 ms** |
| 回读窗口 T_land | 2.61 + 32.4 = **35.0 ms** | 2.60 + 0.008 = **2.61 ms** |
| 实际帧时间 | 32.4 ms（回读窗口成瓶颈）→ **34 fps** | 9.9 ms（渲染为瓶颈）→ **101 fps** |

**525 的回读窗口（35ms）超过渲染时间，变成节拍器；515 的回读窗口（2.6ms）远低于渲染时间，不是瓶颈。**
这与 515 既有实测（`vblank_mode=0` 101fps）和 525 的 34.7fps 完全对齐，无需任何额外假设。

> 注意：515 上 268 对仍要付 CPU 提交时间（1.04µs/对 ≈ 0.28ms/帧），但这点开销藏在渲染里，不影响节拍。

## 3. 为什么这个判决是干净的

1. **同一二进制**：`n83a` 在 11:57 编好，525 上跑过 M1/M3/M6/M0/M2 全套（报告 76/78），515 上原样再跑，没有重编译。
2. **同一环境**：`__GLX_VENDOR_LIBRARY_NAME=nvidia __NV_PRIME_RENDER_OFFLOAD=1`，DISPLAY=:1（plasmashell 继承），GL_VERSION 打印确认 `4.6.0 NVIDIA 515.105.01`。
3. **单进程内扫描**（`-S`）：driver/ctx/FBO/PBO 全程不变，排除了报告 76 的"批间污染"。
4. **自计数自检**：`pairs/frame` 精确等于 N，`swaps_total=12000 / draws_total=12000`（12 帧 × 1000）。
5. **基线互证**：两版 M1 都是 2.60~2.63ms，说明测量装置本身没有版本偏差。
6. **机器状态**：重启后 4 分钟、GPU 空闲 6.02W、无其他实验进程。

**唯一需要说明的**：515 的 M0 有轻微上升趋势（2.502→2.677 @ N=2000，0.05~0.09µs/对），
这是 4 次 legacy 调用的 CPU 提交开销（4×0.027µs ≈ 0.1µs，报告 74 的 submit 实测），与 GPU 无关。

## 4. 现在的完整因果链（跨 53 份报告收束）

```
525 引入的改动（报告 34/35：命令队列处理器"notify 之后队列仍空"这条边上插入 wait_ms）
  → 每批命令开始时走统一提交器 glcore+0x1238920（报告 77：内含 sfence + 重试回环里的 wait_ms）
  → 每次"状态调用 + 紧跟 draw"的配对触发一次批次开始，付 121µs ≈ 231k GPU 周期（报告 76/77）
  → Heaven 每帧 268 对 → 32.4ms 加进回读窗口
  → 回读窗口 35ms 成为节拍器 → 34fps（用户看到的"3D 性能下降"）

515 上这条链不存在：同样的配对 0.03µs，回读窗口 2.6ms，节拍由渲染决定 → 101fps
```

**"121µs 与版本无关"的备选（报告 78 §6 第二种判读）已被排除。靶点不再是"配对数"，而是 525 的批次开始路径。**
