# 74 · N83-A：**纯 draw call 几乎免费（0.02µs/个）**——"T_land ∝ draw call 数"被推翻；但挖出 legacy 路径 121µs/次的异常

驱动：525.116.03（P106-100，1920×1080，直连 NVIDIA 不经 primus）
程序：`analysis/n83a/n83a.c`（自写，draw call 数可调）

> ## ➡️ 本报告的悬案已在 **报告 75** 中解决
>
> - **§4 的 (a) 支（Heaven 有大量 legacy 调用）已否定**：`libUnigine_x64.so` 里 19 个 legacy 函数名

>   ⇒ **Heaven 100% 走 shader，不用固定管线。**
> - **(b) 支已定位到具体内容**：报告 75 用同一程序加了三个模式，测出
>   **每次 GL 状态切换（shader / FBO / 纹理）成本 254~265µs，是不切换时的 13000 倍**。
>   `32.44ms ÷ 260.9µs = 124 次切换/帧`，量级合理。
> - **§3.3 那个 121µs（legacy）不是靶点**，它只是"较快的慢路径"（30.4µs/状态）；
>   真正的靶点是 260µs 的**切换**路径。
> - 另外：§4 那句"1067 次 ≈ 1000 次可能只是巧合"**确认是巧合**（因为 (a) 已否定）。

## 0. 结论（先说不好的部分）

**N83-A 的核心结果是否定性的：draw call 数量不是那 35ms 的原因。**

| 路径 | 斜率 | 说明 |
|---|---|---|
| **shader + 小 quad + 无状态变更** | **0.020 µs / call** | **2000 个 draw call 只花 0.043ms** |
| shader + 每次改一个 uniform | 0.058 µs / call | 也很便宜 |
| shader + 大 quad（0.35 NDC） | 4.514 µs / call | 这项是**填充**，不是调用 |
| **固定管线（每次 4 个 legacy 状态调用）** | **121.7 ~ 126.0 µs / call** | **异常到不正常** |

**两条结论：**

1. **执行全文最轻量的路径下（shader、状态不变、quad 只有 19×19 像素），一个 draw call 只要 20 纳秒。**
   ⇒ 报告 73 的"`T_land` ∝ 场景规模（draw call 数）"**不成立**。Heaven 的 35ms 不可能来自"上千次 draw call 的提交"。
2. **但固定管线路径慢 6000 倍**（121.7µs vs 0.020µs）。这**不能**用来解释 Heaven（Heaven 是 Unity，走 shader），
   但它本身是一个**刺眼的异常数字**：正常驱动的 GL 状态调用应该是 1~5µs，这里是 **30µs/次**（见 §3）。

## 1. 程序设计与四组实验

### 1.1 为什么直连 NVIDIA

```
__GLX_VENDOR_LIBRARY_NAME=nvidia __NV_PRIME_RENDER_OFFLOAD=1
```
不经 `primusrun`。理由：primus 会包装 `glReadPixels`/`glMapBuffer` 并插入 `usleep`，
使 `T_land = usleep + map` 被 autosleep 逻辑混淆。**要测 NVIDIA 驱动本身，就必须绕过 primus。**

确认生效：`GL_RENDERER = NVIDIA P106-100/PCIe/SSE2`、`GL_VERSION = 4.6.0 NVIDIA 525.116.03`。

### 1.2 每帧的四个计时点

```
t0 → t1 : N 个 glDrawArrays            (submit = CPU 提交)
t1 → t2 : glReadPixels → PBO           (rp)
t2 → t3 : glMapBuffer                  (map = 等待数据落地 = T_land)
t0 → t3 : 合计
```

- 渲染到 **FBO**，之后读该纹理的像素 ⇒ draw call 不会被驱动优化掉
- 每个 quad 位置/颜色不同 ⇒ 无法合并
- 固定 1920×1080、RGBA8、PBO 回读 8.29 MiB

### 1.3 四组 + 一组补充

| 组 | mode | quad 半边长 | 每次 draw call 的状态操作 |
|---|---|---|---|
| A | 0 固定管线 | 0.35 | `glLoadIdentity` + `glTranslatef` + `glScalef` + `glColor3f` |
| B | 0 固定管线 | **0.01** | 同上（quad 面积缩小 **2300 倍**）|
| C | 1 shader | 0.35 | **无**（状态只设一次）|
| D | 1 shader | **0.01** | **无** |
| E | 2 shader | 0.01 | 每次 `glUniform3f`（改颜色）|

**A/B 与 C/D 的设计目的**：分别改变"填充面积"和"每 call 的状态操作量"，
看 121µs 到底属于哪一项。

## 3. 三个判读

### 3.1 填充不是原因（A vs B）

quad 边长从 `0.35` 缩到 `0.01`：面积从 **451,584 px** 降到 **368 px**，缩小 **1227 倍**。

```
A: 126.039 µs/call
B: 121.662 µs/call      差 −3.5%
```

**面积差 1227 倍，斜率只差 3.5%** ⇒ 那 121µs **与光栅化/填充无关**。

反过来验证：C 组（shader/0.35）的 4.514 µs/call 才是填充 ——
`1000 call × 451584 px = 452 Mpx`，`4.514ms` ⇒ **100 Gpx/s**，正是 P106 这个量级的填充率。

**⇒ A/B 里那 121µs 是"每 call 的状态处理"，C/D 的差异是"填充"。两者被清楚地分开了。**

### 3.2 纯 draw call 几乎免费（D 组）

``` 
D: 0.020 µs/call   ⇒  2000 个 draw call 合计 0.043 ms
```

同期 CPU 提交是 `submit = 0.063ms`（2000 次，即 **31ns/次**）。
**GPU 侧 20ns + CPU 侧 31ns，一个 draw call 的全部成本不到 0.1µs。**

⇒ 报告 73 的推断（"`T_land` ∝ draw call 数"）**被直接证伪**。
8.29MiB 回读的 2.61ms 截距，才是所有场景的共同底价。

### 3.3 固定管线慢 6000 倍 —— 这是最刺眼的数字

```
D（shader，无状态变更）:  0.020 µs/call
B（固定管线，4 个状态调用 + 1 个 draw）: 121.662 µs/call
                          比值 = 6083×
```

把 B 拆开（draw 本身按 D 的 0.020µs 计）：

```
121.662 − 0.020 ≈ 121.642 µs / 4 次状态调用 ≈ 30.4 µs / legacy 状态调用
```

**30.4 µs 一次 `glLoadIdentity`/`glTranslatef`/`glScalef`/`glColor3f` —— 这个数字不正常。**

对照：E 组每次 `glUniform3f` 只要 **0.058 µs**。同为"改变量"，差了 **524 倍**。

**⇒ 525 的 legacy（兼容 profile 固定管线）状态路径存在严重低效。**
这可能有两个来源：
- 每次 legacy 状态变更触发一次"legacy → shader 程序重生成/重绑定"
- 或每次触发一次命令缓冲区刷新（flush）

**这一条与 Heaven 无关**（Heaven 用 shader），**但它是本案第一次抓到一个"每次调用几十 µs"的实物。**

## 4. 那 Heaven 的 32ms 是什么？（诚实的边界）

```
Heaven HIGH  T_land = 35.05 ms
减截距（纯带宽）      −2.61 ms
────────────────────────────
待解释               32.44 ms
```

按 §3.3 的 30.4µs/次 反推，32.44ms 对应 **1067 次 legacy 状态调用** ——
与报告 07 独立估出的"**~1000 次 GL 调用/帧、26µs/次**"**精确吻合**（误差 3%）。

**但这个吻合不能直接采信**，因为有一个反证：

> **如果 Heaven 的 1000 次调用是 shader 路径（D/E 组），按 0.02~0.06µs/次只能解释 0.06ms，不是 32ms。**

所以只有两种可能，**当前数据分不开**：

| 可能 | 含义 | 如何验证 |
|---|---|---|
| **(a) Heaven 里确实有大量 legacy 调用**（GUI/HUD/文字/后处理） | 那 32ms 就是这 1000 次 × 30.4µs，**靶点已找到** | `apitrace` 看 Heaven 的调用类型分布 |
| **(b) Heaven 全走 shader，32ms 是别的东西**（多 pass、纹理带宽、几何量） | 那 30.4µs 这条线**与本案无关**，只是恰好数值接近 | 同上，且需要按 pass 分解 |

**必须承认**：§3.3 那个"1067 次 ≈ 1000 次"的吻合，在 (b) 成立时纯属巧合。
**它是线索，不是结论。**

## 5. 我这一轮设计上的错误（要记住）

**第一版基准只有 A 组（固定管线）。** 如果就此收工，我会得出：

> "每 draw call 126µs，Heaven 上千次 draw call ⇒ 126ms"
> —— 然后拿它去解释 35ms，**差 3.6 倍却看不出来**，因为数字"同量级"。

是**加了 C/D 组（shader + 无状态变更）**才暴露出 A 组的 126µs 里有 99.98% 是 legacy 状态开销、与 draw call 无关。

**规矩**：
- 基准程序**每一档必须有两个变量同时被控制**：本例是「状态操作量」×「填充面积」。
  只扫 N 而不控制这两项，得到的斜率是一个**混合量**，无法归因。
- **必须有一档"最小状态"对照组**（这里 D 组：状态一次都不变）。
  没有它，"每 call 成本"这个数字没有意义。

## 6. 对报告 73 的更正

| 报告 73 的说法 | 现状 |
|---|---|
| 「`T_land` ∝ 场景规模（draw call 数）」 | ❌ **推翻**。纯 draw call 0.020µs/个，2000 个仅 0.043ms |
| 「glxgears 3.0ms 说明回读通路健康」 | ✅ 仍成立（2.61ms 截距 = 纯带宽，与所有组一致） |
| 「glxgears↔Heaven 差 11.7 倍是因为 draw call 数量级」 | ⚠️ **归因错误**。glxgears 用**显示列表**（`glNewList`/`glCallList`），每帧只 5 次调用；它便宜是因为**调用次数极少**，不是因为"draw call 便宜" |
| 「Heaven LOW↔HIGH 只差 25% ⇒ 与 shader 复杂度弱相关」 | ✅ 仍成立 |
| 「20.39ms 固定项 = 命令流处理」 | ⚠️ **降级为待验证**。可能是 legacy 状态开销（§4a），也可能是别的（§4b） |

**glxgears 那条尤其要改**：报告 73 拿它当"最小 draw call 场景"的对照，但它每帧只有 5 次显示列表调用，
**从来没有测过"上千个 draw call"**。这是一个我本应早发现的混淆（`glxgears` 源码里明确用 `glNewList`）。
