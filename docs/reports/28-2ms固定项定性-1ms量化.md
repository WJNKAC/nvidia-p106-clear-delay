> 详见报告 29。

> "为什么 525 的拷贝在 usleep 期间不完成"仍未解 —— 但已排除 flush。

> 方法：按计划第 1/2 刀，在 525 上做隔离实验（新写 `rb_lat4.c`），并对 primus 已有 trace 做细粒度直方图分析。
> **不换驱动。**
> **六条结论：**
> 1. **第 2 刀否掉了我上一轮的假设**：flush 不是必要的。隔离环境里 `none`/`flush`/`query`/`finish` 四组的 map 全是 **3~7µs** —— 拷贝**不需要 flush 就会自己完成**。
> 2. **第 1 刀（落地时刻）已由逻辑定死**：primus 的 map 要 2864µs，而"数据已到"的缓冲 map 只需 3~7µs（§3 实测）。**所以那 26ms 睡眠里数据根本没到。报告 26 的"84% 在 usleep 中段落地"是 10ms 量化的伪影。**
> 3. **隔离环境给出了"拷贝是否已开始"的定量指纹**（窗口扫描）：0ms→2473µs，1ms→1429µs，2ms→424µs，**≥3ms→~2µs**。
> 4. **★ 决定性发现：primus 的 `glMapBuffer` 耗时被 1ms 量化。** 640×360 呈三簇 **1.1 / 2.1 / 3.0ms（间距 1.0ms）**，簇间（1.4–1.8、2.4–2.7）几乎为空；1080p 收敛到单簇 3.0–3.1ms。
> 5. **"2.05ms 固定项"的真实含义 = 2 个 1ms tick**；"0.51ms/Mpx 斜率"不是带宽，而是**多需要一拍 tick 的概率**。
> 6. **静态佐证**：`imul $0x10624dd3`（ms→秒，毫秒精度超时）在 **525 有 3 处、515 有 0 处**。515 没有毫秒精度的等待原语 → 1ms 量化很可能是 525 独有。

## 1. 第 2 刀：四组 flush 对照——判据落在「都不变」

`rb_lat4.c` 新增 `RL4_ACTION` 四组：`none`（复刻 primus，rp 后什么都不做）/ `flush` / `query`（`glQueryCounter`）/ `finish`。
每组都在 rp 与 map 之间插 26ms（复刻 primus 的自适应睡眠），1080p，25 轮：

| 组 | rp 后动作 | `rp后动作` CPU 耗时 | **`map_wait`** |
|---|---|---|---|
| A `none` | 无 | 0.024 µs | **6.86 µs** |
| B `flush` | `glFlush()` | 0.93 µs | **5.53 µs** |
| C `query` | `glQueryCounter` | 0.51 µs | **6.59 µs** |
| D `finish` | `glFinish()` | **2491 µs** | **5.72 µs** |

**四组的 map_wait 全在 3~7µs。** D 组的 `glFinish` 花了 2.49ms（等拷贝完成），之后 map 也是 5.7µs。

→ 按计划判读表：**A/B/C/D 都不变** → "2ms 在 map 本身或驱动轮询里"这一支。

> **但必须诚实标注一个更强的事实**：这四组**根本没复现出 primus 的 2.9ms**。
> 隔离环境里哪怕完全不 flush（A 组），26ms 窗口足够让拷贝自己完成。
> **所以"primus 不 flush 导致拷贝没 kick off"这个假设（报告 25/27 的推断）被否掉了。**

## 2. 第 1 刀：数据到底什么时候到（逻辑已定死，附定量指纹）

### 2.1 窗口扫描：隔离环境的"拷贝是否已开始"指纹

`RL4_ACTION=none`（rp 后不做任何事），改变 rp→map 之间的窗口长度，看 map 耗时怎么衰：

| 窗口 | `map_wait` 中位 | 含义 |
|---|---|---|
| 0 ms | **2473 µs** | 拷贝刚发出，map 必须等它 |
| 1 ms | 1429 µs | 已走掉约 1ms |
| 2 ms | 424 µs | 差不多完成了 |
| 3 ms | **1.84 µs** | 已完成，map 白拿 |
| 5 ms | 1.89 µs | 同上 |
| 10 ms | 5.92 µs | 同上 |
| 26 ms | 6.64 µs | 同上 |

**这条曲线是"拷贝有没有跑"的定量指纹**：map 耗时 ≈ 0 就意味着"数据早到了"。

### 2.2 用它反推 primus：数据在 26ms 里没到

primus 实测（`c1_clean.script`，n=520）：

```
us_out → mb_in           5 µs      ← map 调用本身的进入开销可忽略
mb_in  → mb_out       2864 µs      ← 全部时间在 map 内部
```

按 §2.1 的指纹：如果是"数据早到了"，map 应该是 **几微秒**。既然是 **2864µs**，就是"数据没到，map 在等"。

**→ 那 26.4ms 的 usleep 期间，primus 的拷贝一直没有完成。**
**→ 报告 26 §4.2「84% 的帧在 usleep 中段落地」一定是 `/proc/uptime` 10ms 量化的伪影**（其 16.5±10ms 覆盖 [6.5, 26.5]，正好能把"26ms 才到"伪装成"中段到"）。

### 2.3 顺手否掉一个我自己的旧推断

报告 27 §7 我推断"primus 的 worker 在 usleep 期间不 flush → 拷贝没开始 → map 才 flush"。
**§1 的 A 组否掉了这个推断**：不 flush，拷贝也会自己完成（26ms 后 map 只需 6.86µs）。

所以"没 flush"不是原因。**原因在别处**（见 §3）。

### 3.3 判读

**1ms 的量化颗粒，只在"完成检测靠周期定时器"时才会出现。**

物理图像：
```
拷贝真正完成（GPU 侧，时间 T ∝ 像素）
   ↓  驱动不在完成瞬间得知，而是由 1ms 周期的东西去发现
下一次 1ms 边界才被注意到
   ↓
map 返回（再 +0.1~0.2ms 的返回路径）
```

这**直接印证报告 23 的观测**：525 的 glcore 里有线程在做 `clock_nanosleep(1ms)`（1158 次/秒）。

### 3.4 "2.05ms 固定项"的重新解释

原拟合（报告 27 §3）：`map_time = 2.05ms + 0.51ms/Mpx`

按 1ms 量化重读：

| 量 | 原解释 | 正确解释 |
|---|---|---|
| **2.05ms 固定项** | 某个固定同步开销 | **≈ 2 个 1ms tick** |
| **0.51ms/Mpx 斜率** | 回读带宽 | **多需要一拍 tick 的概率**（像素越多，T 越大，越容易跨过下一拍） |

**这解释了为什么降分辨率救不了**：从 1080p 降到 640×360，真实拷贝时间从 ~2.5ms 降到 ~0.3ms，
但 tick 从 3 拍降到 1~2 拍（中位 2 拍）—— **收益被"按整拍计费"吃掉了**。

## 4. 静态佐证：515 可能没有毫秒精度的等待原语

报告 25 留下的静态对比（三版 glcore 的 `imul $0x10624dd3`，即 ms→秒 的换算，构造 `pthread_cond_timedwait` 的 timespec 必须用到）：

| 版本 | `imul $0x10624dd3` | `$0x3b9aca00`(1e9, ns 归一) |
|---|---|---|
| **515.105.01** | **0** | 16 |
| **525.116.03** | **3** | 14 |
| 580.178.04 | **0** | — |

**515 用 ns 精度做超时，525 引入了 ms 精度的 `wait_ms`/`sleep_ms` 封装。**
而 1ms 量化的完成检测，正是"毫秒精度超时 + 1ms 周期检查"这一族设计的自然产物。

→ **1ms 量化很可能是 515→525 引入的**（不是 580 之后一路延续，因为 580 也是 0 处）。

> 这是**关联证据**，不是因果证明。要确认，需要看 515 的 map 耗时是否也有 1ms 簇（见 §6 优先级 1）。

## 5. 与已有结论的整合（当前最完整的图景）

```
应用 glXSwapBuffers（主线程）
   ↓
glFenceSync + sem_post(r.acqsem)          ← 叫醒 readback worker
sem_wait(r.relsem)                        ← 主线程在 57µs 后被 worker 解锁（它只等"许可"）
   ↓ 主线程立刻去渲染下一帧（占住 GPU）
readback worker：
   glWaitSync   5µs       ← fence 早已完成（报告 26）
   glReadPixels 119µs     ← 只是把拷贝命令推给驱动
   usleep 26.4ms          ← 自适应睡眠（= 9×map_time，是果不是因）
   glMapBuffer  2.86ms    ← ★ 全部时间在这里，且被 1ms 量化
   ↓
   一轮 D = 29.4ms → fps 34
```

**为什么那 26ms 睡眠期间拷贝没完成？** 本报告没有定论，但已排除：
- ❌ 没 flush（§1 A 组：不 flush 也会完成）
- ❌ GPU 队列被后续渲染堵住（报告 27 §5：burden 19.5ms，D 不变）
- ❌ 像素量/带宽（§3.4：按 tick 计费）（报告 27）
- ❌ vblank 锁（报告 24 相位均匀）

剩下最可能的是：**`map` 之前的某一步没有把拷贝真正提交**，而提交发生在 map 内部；
提交后又要等 1ms 级的完成检测。这两件事叠起来正好是"2~3 拍 tick"。

### 7.1 本轮踩的四个仪器坑（都很隐蔽）

1. **`now_us` 输出被当成 ms 读**：`rb_lat4` 所有时间量是**微秒**，第一次误读成"11ms 的 readPixels"。
   **看到可疑的大数先换算单位。**
2. **目标像素被几何污染**：我在 (0,0) 位置画了三角形，而 (0,0) 是三角形的覆盖区 —— 那个像素是插值色，永远不等于 clear color，落地检测恒为 0。
   **要检测某个像素值，就别让它被几何覆盖。**
3. **相邻帧目标值太近**：`target = i%200` 相邻差 1，配上 ±2 容差 → **上一帧的颜色永远匹配当前帧**，产生"0.17ms 就落地"的假命中。
   **目标值必须大步跳变（本例改成 `(i*97)%200`），容差要小于步长。**
4. **轮询位置放错**：在 `usleep` 之后才开始轮询，只能回答"睡醒时到了没"，不能回答"窗口内何时到"。
   想要窗口内时刻，要么忙等替代 sleep（会改变调度），要么用独立线程。
   **本报告改用"扫不同窗口长度"绕开了这个问题**，代价是多跑几组。

### 7.2 一个必须记住的负结果

**隔离环境（pbuffer 源）无法模拟 primus 的回读**：
pbuffer（无论是否 swap）实测"数据从不落地、map ~3µs"，`gpu_copy` 恒为 0.15ms 且不随像素量变化
→ **这不是真的 DMA 路径**（`glReadPixels` 从 pbuffer 可能走内部拷贝/缓存）。
所以**不能拿 pbuffer 隔离测试去反推 primus 的行为**（primus 虽然读 pbuffer，但在它自己的双 context/多线程语境下才是真 DMA）。
