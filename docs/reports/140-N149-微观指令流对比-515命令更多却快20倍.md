# 报告 140 — 微观指令流对比：515 发的命令比 525 多 60%，却快 20 倍

> 编号：140（对应 N149）
> 日期：2026-10-27
> 平台：P106-100 / Heaven 4.0 OpenGL 1920×1080 / 整机切驱动
> 方法：抓 `/dev/nvidiactl` mmap 里的 pushbuffer（GPU 指令流），解码方法头，对比 method 分布

---

## 0. 一句话结论

**同一个 Heaven 程序，两版驱动生成的 GPU 指令流不一样，而且方向是反的：**

> **515 发 48,000~50,000 条命令（会波动），525 只发 25,000~31,000 条（完全静态）。
> 命令少的那个反而慢 20 倍。**

这一刀彻底切断了"525 因为发太多命令才慢"的假设，也再次指向同一个结论：
**525 的代价不在命令数量，在每条命令落到 GPU 上之后的时间。**

### 最悬殊的三个 method

| method | 515 中位 | 525 中位 | 比值 |
|---|---|---|---|
| **`sub6:0x0034`** | **6,653** | **16** | **416×** |
| **`sub0:0x1b00`** | **3,855** | **34** | **113×** |
| `sub0:0x1618` | 2,800 | 1,631 | 1.72× |
| `sub0:0x17dc` | 2,627 | 1,577 | 1.67× |
| `sub0:0x17c8` | 2,622 | 1,559 | 1.68× |
| `sub0:0x0220` | 915 | **1,345** | **0.68×**（525 更多） |

## 1. pushbuffer 怎么找到的（可复用）

### 1.1 走过的两条弯路

| 尝试 | 结果 |
|---|---|
| 按"命令字特征"（opcode 在 bit[31:29]）扫描 | ❌ **全零块被判 100% 命中**（`w=0` 时 op=0、cnt=1 天然合法） |
| 按视口尺寸 `0x780/0x438` 找 | ❌ 命中的全是 **VBO/常量缓冲**（数据是 IEEE 754 浮点：`0x3f800000`=1.0f） |

**教训：判据必须能排除平凡值。** 任何"位域合法"类判据，都要先跳过 `w==0`。

### 1.2 最后靠历史 anchor 一击命中

```python
ANCHOR = struct.pack("<II", 0x2001c00d, 0x70000000)
```

在 214 个含 anchor 的块里，用"30ms 内变化字数"排序，取第一名。命中后立刻自证：

```
20060202 07800000 04380000
         ↑1920    ↑1080      ← count=6 的 INC 命令，正好 6 个参数
```

**这个"命令头 + 参数个数 + 已知视口尺寸"三件套对齐**，才算确认是渲染命令流。

### 1.3 定位结果

| | 525 | 515 |
|---|---|---|
| pushbuffer 基址 | 每次不同（ASLR） | 同 |
| 大小 | **2 MB**（两个版本一致） | 2 MB |
| 解码结果 | 25,028 / 31,156 条 | 48,156~50,037 条 |

## 2. 命令数：反直觉的核心事实

8 次采样（间隔 0.35 s，跨 2.45 s）：

```
515: [48156, 48601, 48950, 49335, 49441, 49402, 50037, 49855]
525: [31156, 31156, 31156, 31156, 31156, 31156, 31156, 31156]
```

再加一组跨 5 秒的复测（525）：`25028 × 6 次，完全一致`。

**两个事实：**

1. **515 的命令数比 525 多 60~100%**，但 515 的帧时间只有 1/20（报告 138）。
   ⇒ **命令数量与性能是负相关的**，525 的问题绝不是"发得太多"。
2. **525 的 pushbuffer 内容是静态的**（5 秒内 6 次采样一字不差），515 有 ±2% 波动。
   ⇒ 525 把整个场景的命令流编码一次然后反复重放；515 每帧有动态重编码。
   **但这没有帮到 525。**

> ⚠️ 诚实标注：525 采到两个不同的恒值（25028 和 31156），是因为 Heaven 有多个 pushbuffer 块、
> 我的"最活跃块"选择在两次运行间落到了不同块。**这不影响"恒定"这个结论**，
> 但绝对数不能跨次直接比。跨版本对比我只用**同一次运行内的 method 分布**。

## 3. method 集合差异：两版走了不同的代码路径

| | 数量 |
|---|---|
| 两版共有 method | **171** |
| 515 独有 | **31** |
| 525 独有 | **65** |

共有 method 的**核心骨架相同**（0x34a8 / 0x1618 / 0x17dc / 0x17c8 / 0x0220 等都在），
说明画的是同一个东西；但**每条的量差 1.6~1.7 倍，且各有独有 method**。

### 3.1 最悬殊：`sub6:0x0034`

| | 515 | 525 |
|---|---|---|
| 中位计数 | **6,653** | **16** |
| 占比 | 13.5% | 0.05% |

**subchannel 6 在 525 上几乎不用**（整个 pushbuffer 里 sub6 只有 16 条），515 用了 6,653 条。
subchannel 是 GPU 的独立命令流通道，硬件上并行。**515 把大量工作分流到了 subchannel 6。**

### 3.2 次悬殊：`sub0:0x1b00`

| | 515 | 525 |
|---|---|---|
| 中位计数 | **3,855** | **34** |

`0x1b00` 落在 3D class 的 method 空间（0x1b00-0x1bff 段）。515 每帧用 3,855 次，525 几乎不用。

### 3.3 `0x39c0` vs `0x39d0`

- 515 的 top2 是 `0:0x39c0`（4,079）
- 525 的 top2 是 `0:0x39d0`（2,978）

**同一个功能，method 偏移差 0x10。** 这类"相邻 method"通常是同一个寄存器块的不同字段，
说明两版对同一功能的打包方式不同。

### 3.4 525 也有更多的：`0x0220`

515 = 915，525 = 1,345（525 多 47%）。0x0220 在 method 空间低段（全局/管线段）。

## 4. 这些差异说明什么（能说与不能说）

### 能说的

1. **两版对同一个 OpenGL 程序生成了不同的 GPU 指令流** —— 这是实测，不是推断。
   171 个共有 + 31/65 个独有，且核心量差 1.6 倍。
2. **命令数量与性能负相关** —— 命令少的（525）慢 20 倍。
   ⇒ 任何"减少命令数"的优化（包括我之前做的 GL 层垫片）对本问题的收益上限都很低。
3. **515 用了更多但更细的命令**，并大量使用 subchannel 6 分流。
   这与"515 的 GPU 在真干活（65~78 W）、525 在等（50~57 W）"（报告 138）一致：
   **细粒度命令流让 GPU 保持忙碌；粗粒度命令流让 GPU 停下来等。**
4. **525 的命令流是静态可重放的**，515 每帧重编码。
   ⇒ 525 明显在做"命令流缓存"这类优化，但它换来的静态性没有抵消掉每次执行的长等待。

### 不能说的（诚实边界）

| 项 | 为什么 |
|---|---|
| `0x1b00` / `0x0034` 的**语义名称** | NV90F0 的 method 名表在闭源 blob 里，nouveau 只覆盖一小部分；本项目无可信来源 |
| subchannel 6 绑定的是什么 class | 同上 |
| **这个差异是"因"还是"果"** | 完全可能：因为 525 走了慢路径 → 引擎反馈压力 → 驱动改用粗粒度批量提交。
**相关性已经实测，因果方向未定。** |

**第 3 条尤其重要**：如果 525 是因为"每次绑定都慢"（报告 136 的 122 µs）而不得不批量提交，
那指令流差异就是**结果**而不是原因。这与报告 136/138 的 GPU 侧结论一致。

## 5. 与已有结论的关系

| 已有结论 | 本报告的作用 |
|---|---|
| 122 µs 在 GPU 侧（136/138） | ✅ **加强**：命令更少却更慢，只能是执行侧问题 |
| 515 等待函数零调用（138） | ✅ **吻合**：515 用细粒度命令流，不需要等批次空间 |
| 垫片收益上限 = 冗余率；Heaven 上只有 ~2.4 ms（137/138） | ✅ **加强**：命令数本身不是瓶颈 |
| ioctl 层只占 0.24%（139） | ✅ **加强**：三层（ioctl / 命令数 / 执行）里，只有执行层有肉 |

**三层归因现在是闭合的：**

```
ioctl 层    0.24% 墙钟          ← 报告 139 排除
命令流层    数量负相关（525 更少）  ← 本报告排除
GPU 执行层  122 µs × 270 次/帧    ← 报告 136/138 剩下的唯一嫌疑
```

## 6. 下一步（唯一有意义的两个）

1. **把 `0x1b00` 和 `sub6:0x0034` 的行为对上**：用 uprobe 在 glcore 里找哪个函数生成这两类命令，
   再对比 515/525 该函数的分支。这是唯一能把"指令流差异"翻译成"驱动代码差异"的路径。
2. **停止在命令数量上做优化**。本报告证明方向是反的。

## 7. 复现命令

```bash
# 定位 + 抓取（自动找最活跃的含 anchor 块）
sudo python3 /home/<user>/pbmul.py <pid> 8      # 8 次采样，输出 method 分布 JSON

# 单独抓一次带解码
sudo python3 /home/<user>/pbdiff.py <pid> 150   # 150ms 增量 + 解码前 40 条

# 解码任意 dump
python3 /home/<user>/decpb.py /home/<user>/pbd_<pid>.bin
```

解码器（`pbmul.py` 内）：
```python
w = u32(buf, i*4)
if (w >> 29) in (0, 1):          # INC_METHOD
    cnt  = (w >> 16) & 0x1fff    # 参数个数（不是 size-1，实测这个位域才对）
    sub  = (w >> 13) & 0x7       # subchannel
    meth = (w & 0x1fff) << 2     # method 偏移
    args = buf[i+1 : i+1+cnt]
```

⚠️ 注意：`cnt = (w>>16)&0x1fff` 是**试出来的**，与 nouveau 的 `(size-1)<<18` 不同。
判据是"1920×1080 那条命令的 cnt 必须等于 6"——**用已知数据反推位域，不要照抄文档。**
