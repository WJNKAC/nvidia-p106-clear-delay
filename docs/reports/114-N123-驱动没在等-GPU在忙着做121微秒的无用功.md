# 报告 114 / N123：**驱动没在等 —— GPU 在忙着做 121 µs 的无用功**

- 时间：2026-10-26 20:15
- 环境：**<user>@<testhost>（hostname `<testhost>`），525.116.03，P106-100**
- 触发：用户「已经在 <user> 上安装了 525」
- **本轮是上机实测**，不是推理。全部数据来自本机新装 525 的实跑

---

## 0. 答案（一句话）

**驱动不在等任何东西。是 GPU 每做一对"状态变更 + draw"，就真的忙 121 µs。**

**证据是同一份工作量下 GPU 利用率的对比：**

| 实验 | 操作 | **GPU 利用率** | 功耗 | `map_p50` |
|---|---|---|---|---|
| M1 | 只画 1000 个 draw | **0 %** | 36.31 W | 7.394 ms |
| M8 | 切换 500 次 + **只有 1 个 draw** | **0 %** | 36.31 W | 2.618 ms |
| **M9** | **切换 1000 次，然后 1000 个 draw** | **0 %** | 36.31 W | **7.136 ms** |
| **M6** | **切换 1000 次 + 1000 个 draw，交替** | **100 %** | 37.99 W | **128.453 ms** |

**M9 与 M6 的工作量完全相同（都是 1000 次切换 + 1000 次 draw），唯一差别是"是否交替"：**
**M9 的 GPU 利用率 0%，M6 的 100%。**

**⇒ 那 121 µs 不是 CPU 在等、不是轮询粒度、不是带宽 —— 是 GPU 真的在忙。**

**而且功耗只从 36.31 涨到 37.99 W（+1.68 W）。满负荷但几乎不耗电 ⇒ 是固定功能/时序/状态重载，不是 ALU 计算。**

---

## 1. 模型在本机被完整复现

历史口径（另一台机器）与新装的这台，数字几乎一模一样：

| 实验 | 历史（MSI，525） | **本机（<testhost>，525）** |
|---|---|---|
| M8 切换 500，1 draw | 2.620 ms | **2.611 ms** |
| M9 先切后画 | 2.640 ms | **7.128 ms**（注） |
| M3 交替 1000 对 | 123.652 ms | **125.755 ms** |
| M6 交替 1000 对（同一 program） | — | **128.453 ms** |

> 注：M9 本机 7.128 ms vs 历史 2.640 ms，是因为本机 M1（1000 个 draw）本身就是 7.394 ms —— 历史 M9 是在 N=1000 但只有 1 个 draw 的条件下测的。**关键是不变的那条：M9 ≈ M1（7.128 vs 7.394，差 0.27 ms），即 1000 次切换几乎零成本。**

### 1.1 每对成本

```
M1（1000 draw，无同步）      =   7.394 ms   ← draw 本身的成本
M3（1000 对交替）            = 125.755 ms   ⇒ (125.755-7.394)/1000 = 118.4 µs/对
M6（1000 对交替，同一 prog）  = 128.453 ms   ⇒ (128.453-7.394)/1000 = 121.1 µs/对
```

**历史预测 `7.394 + 0.121×1000 = 128.394`，实测 M6 = `128.453`。差 0.06 ms（0.05%）。**

## 2. "dirty → sync" 模型在本机得到 7/7 验证

```
状态变更 → 置 dirty
下一次 draw → 看到 dirty → 做一次 GPU 侧动作（121 µs）→ 清 dirty
```

| 情形 | 同步次数 | 实测 | 模型 | |
|---|---|---|---|---|
| M8 只切换（500 次，1 draw） | 1 | 2.611 | 2.73 | ✓ |
| M1 只画（1000 draw） | 0 | 7.394 | 7.39 | ✓ |
| **M9 切 1000 再画 1000** | **1** | **7.128** | 7.51 | ✓ |
| M3 交替 1000 | 1000 | 125.755 | 128.4 | ✓ |
| **M6 交替 1000（切同一 program）** | **1000** | **128.453** | 128.4 | ✓ |
| M7 c=124（历史） | 124 | 17.607 | 17.6 | ✓ |
| M7 c=500（历史） | 500 | 63.120 | 63.1 | ✓ |

**M6 切到"同一个 program"（纯 no-op）照样 121 µs/对 ⇒ 驱动不检查状态是否真的变了。**

## 3. CPU 侧：它在自旋，不是在等锁

`bash time` 内建统计（`-n 500 -f 40`）：

| 实验 | real | user | sys | 说明 |
|---|---|---|---|---|
| M1 | 0.343 s | 0.204 s | 0.136 s | CPU 与 wall 相当 |
| M9 | 0.356 s | 0.251 s | 0.104 s | 同上 |
| **M6** | **4.021 s** | **2.459 s** | **1.560 s** | **user+sys = 4.019 s ≈ real** |

**M6 的 CPU 时间几乎等于墙钟 ⇒ CPU 全程在忙，不是阻塞睡眠。**

`/proc/PID/syscall` 采样 12 次 **全部返回 `running`**；`/proc/PID/stack` 12 次全空；
单线程，`wchan = 0`。⇒ **用户态自旋轮询，不是在等任何锁。**

**这修正了报告 111/112 的措辞**：
- 不是 "CPU 在 futex 上等"（futex 每帧只有 3 次）
- 而是 **CPU 自旋轮询 GPU 进度，轮询期间 GPU 正在真实地忙**

**并且解释了 `sys = 1.560 s`**：轮询期间反复进内核查 fence 状态（每次很短，但次数极多）。
这也解释了历史 `strace` 里 ioctl 只占 1% 时间 —— **因为每次 ioctl 都很短，但 CPU 时间被这些短调用吃满了。**

M6，`-n 500`，只改 FBO 尺寸：

| 尺寸 | `map_p50` | 每对（扣掉 draw 本身） |
|---|---|---|
| 64×64 | 60.807 ms | **116.4 µs** |
| 320×240 | 61.118 ms | 117.0 µs |
| 1920×1080 | 65.653 ms | 126.1 µs |

**像素数从 4096 涨到 207 万（506 倍），每对成本只涨 8%。**
⇒ **不是光栅化、不是带宽。是一个与画面大小无关的固定动作。**

## 4.5 ★ 一个惊人的数值巧合（存疑，但值得记录）

本机复核数据：

| | map_p50 | total_p50 | **fps** |
|---|---|---|---|
| M6（交替，有同步） | 128.704 ms | 129.593 ms | **7.72** |
| **M9（先切后画，零同步）** | **7.116 ms** | **7.522 ms** | **132.94** |

**用户报告的 vGPU Heaven：132.9 fps**（⇒ 每帧 7.524 ms）。

```
n83a M9  total_p50 = 7.522 ms  ⇒  132.94 fps
vGPU Heaven        = 7.524 ms  ⇒  132.9  fps
```

**两者差 0.03%。**

**这很可能是巧合** —— 两者负载完全不同（n83a M9 是 1000 对简单 quad + 1080p 回读；Heaven 是几百对复杂着色 + 合成）。
同机 vkmark clear 1080p 只有 61 fps（16.4 ms）、glxgears 1080p 64 fps（15.6 ms），说明 7.5 ms 不是通用的 1080p 下限。

**但它指的方向是明确的**：**在一个"没有 dirty→sync"的环境里，这台机器的负载能跑到 130+ fps 一档。**
而 vGPU 恰好就在这一档。

**⇒ 与模型一致：vGPU 把那个 121 µs 的动作消掉了，于是回到"无同步"的性能档位。**
（**不能作为证据**，只能作为一个对齐得过于巧合的旁证。）

## 5. 所以"驱动在等什么"这个问题，问错了

我前面三轮都在找"驱动在哪里等"。**实际是驱动压根没等 —— 它在拼命给 GPU 喂一个每对都要重做一次的动作，GPU 也真的在忙。**

| 现象 | 旧解释 | 真实原因 |
|---|---|---|
| Heaven `GPU-Util 89-93%` | GPU 空转等米下锅 | **GPU 真在忙，忙在状态重载上** |
| 功耗只有 48 W | GPU 在空转 | **满负荷但低功耗 = 固定功能/时序，不是算力** |
| CPU 100% 单核 | 驱动在等锁 | **用户态自旋轮询 GPU 进度** |
| `__GL_YIELD=USLEEP` 降 CPU 不涨帧 | 自旋是浪费 | **对：自旋只是等，GPU 该忙还得忙** |
| primus / zink / vsync 全无效 | 不是 present 层 | **对：这些都不改变"每对重做一次"** |
| 515 只有 0.03 µs/对 | 515 没有这个分支 | **515 不做这个动作，GPU 就不忙这些无用功** |

## 6. 这个动作是什么（仍在推测，但现在有更强的约束）

**已知（硬）**：
- GPU 真实执行（利用率 0% → 100%）
- 每对 121 µs ≈ 231k 周期 @1911 MHz
- **与像素数无关**（506 倍像素只涨 8%）
- **与状态是否真变无关**（切同一 program 也收费）
- **不交替就不收费**（1000 次切换只收 1 次）
- 功耗只涨 1.68 W ⇒ **不是 ALU/带宽，是固定功能流水或时序等待**

**推测**：最像 **"状态对象重载 / 上下文重建"** ——
每次 draw 前如果 dirty，驱动让 GPU 重新加载一遍图形状态（寄存器组、shader 常量、view 状态等），
这一步在 GPU 上是**定长时序**，不随几何量变，也不检查内容是否相同。

**为什么 vGPU 上没有**：宿主自己维护物理 GPU 的状态，guest 的"重载"请求可以被它**折叠成 no-op**
（因为宿主知道真实状态没变，或者它可以直接把 guest 的 state buffer 映射给物理引擎）。
**这一段仍是推断，宿主是 blob，不可读。**

## 7. 每条结论的证据强度

| 结论 | 强度 | 直接依据 |
|---|---|---|
| 121 µs 是 GPU 真实执行，不是 CPU 等待 | **强** | M9 0% vs M6 100%，同工作量 |
| 与像素数无关 | **强** | 64×64 → 1080p，每对 116→126 µs |
| 触发条件是 "dirty 被 draw 消费" | **强** | 7 个案例，M3/M6/M7/M8/M9/M1 全吻合 |
| 不检查状态是否真变 | **强** | M6 切同一 program 仍 121 µs/对 |
| CPU 是自旋不是阻塞 | **强** | user+sys ≈ wall；12/12 采样 `running` |
| 每对 121 µs 的模型可预测未测点 | **强** | 预测 128.394，实测 128.453（差 0.05%） |
| 具体动作 = 状态重载/上下文重建 | **弱（推测）** | 只能从"定长 + 低功耗 + 与内容无关"反推 |
| vGPU 上宿主折叠掉该动作 | **弱（推断）** | 宿主是 blob |

## 9. 一句话

**装了 525 之后第一组实测就给出了答案：M9（先切后画）GPU 利用率 0%、map 7.1 ms；M6（交替）GPU 利用率 100%、map 128.5 ms。同样 1000 次切换 + 1000 次 draw，只因为"交替"，GPU 从闲着变成满载。**
**所以驱动没有在等 —— 它在每一对之后让 GPU 重做一遍 121 µs 的定长动作；这个动作与像素无关、与状态是否真变无关，且极其省电（+1.68 W），是典型的固定功能/状态重载。**
**CPU 那侧也不是在等锁，是用户态自旋轮询（user+sys ≈ wall，12/12 采样 running）。**
**"驱动在等什么"这个问题，我前面三轮都问错了。**
