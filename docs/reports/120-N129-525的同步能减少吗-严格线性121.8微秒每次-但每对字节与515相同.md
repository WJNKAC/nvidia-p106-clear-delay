# 报告 120 / N129：**525 的同步能减少吗 —— 能，严格线性，没有批量折扣**

> 时间：2026-10-26
> 环境：<user>@<testhost>（`<testhost>`），P106-100，Gen1 x16
> 方法：**headless X（`Xorg :2`）**，绕开桌面会话，515 与 525 在同一套装置上对测
> 触发：用户「已经安装 515。525 同步能够减少吗？」

---

## 0. 三句话

**① 能减少，而且账单是严格线性的：每帧总时间 = 5.15 ms + K × 121.8 µs（K = 每帧"状态变更后紧跟 draw"的次数）。从 K=10 到 K=1000，十个点全部落在一条直线上，没有任何批量折扣。**

**② 但"每对字节数"这条线彻底断了：515 和 525 每对传的字节几乎一样（8.7 KB vs 7.8 KB），差的是传输方式 —— 515 是持续流 1650 MB/s，525 是稀疏突发、平均只有 60 MB/s。**

**③ 所以 525 的问题不是"传得多"，是"同样的 8 KB 传了 23 倍的时间"。减少同步次数是唯一有效手段，换 515 则直接归零。**

---

## 1. 先给用户问题的答案：K 扫描

工具：`n83a -M 7 -n 1000 -c K` —— **固定 1000 个 draw，均匀插入 K 次 program 切换**（K 从 1 到 1000）。

### 1.1 525.116.03

```
     K  total_ms    map_ms      fps
     1     7.202     7.131   138.84
     2     5.056     4.999   197.79
     5     5.874     5.815   170.23
    10     6.039     5.971   165.60
    20     7.268     7.191   137.58
    50    10.994    10.853    90.96
   100    17.172    16.961    58.23
   250    35.614    35.287    28.08
   500    66.069    65.527    15.14
  1000   126.988   125.950     7.87
```

**线性拟合（K ≥ 50，四个点）：**

```
斜率 = (126.988 − 66.069) / (1000 − 500) = 0.12184 ms/次  = 121.8 µs/次
截距 = 66.069 − 500 × 0.12184 = 5.15 ms
```

**回代验算：**

| K | 公式 5.15 + 0.12184·K | 实测 | 误差 |
|---|---|---|---|
| 100 | 17.33 | 17.172 | −0.9% |
| 250 | 35.61 | 35.614 | **0.0%** |
| 500 | 66.07 | 66.069 | **0.0%** |
| 1000 | 126.99 | 126.988 | **0.0%** |
| 50 | 11.24 | 10.994 | −2.2% |
| 20 | 7.59 | 7.268 | −4.2% |
| 10 | 6.37 | 6.039 | −5.2% |

**K ≤ 20 时实测略低于线性外推**（最多 5%），说明极低同步次数下有一点"免费额度"，
但 **K ≥ 50 之后完全线性，一点折扣都没有。**

### 1.2 515.105.01（同一台机、同一套 M7、同一天）

```
     K   total_ms     map_ms        fps
     1      7.086      7.017     141.12
     5      5.264      5.203     189.98
    10      4.816      4.752     207.65
    50      4.862      4.757     205.66
   100      4.922      4.761     203.16
   250      5.095      4.767     196.28
   500      5.204      4.652     192.17
  1000      5.270      4.107     189.75
```

**完全平坦。K 从 1 涨到 1000，总时间 4.8~5.3 ms，没有变化。**

同样 K=1000：**515 = 5.270 ms，525 = 126.988 ms，24.1 倍。**

### 1.3 阈值：要多少 fps，就得把 K 压到多少

解 `5.15 + 0.12184·K = 1000/fps`（单位 ms）：

| 目标 fps | 预算 ms/帧 | K 上限（每帧同步次数） |
|---|---|---|
| 30 | 33.33 | **231** |
| 60 | 16.67 | **94** |
| 90 | 11.11 | 49 |
| 120 | 8.33 | **26** |
| 144 | 6.94 | 15 |

**Heaven 实测每帧 268 对** ⇒ `5.15 + 268 × 0.12184 = 37.8 ms` ⇒ **26.5 fps**（实测 30 fps，同量级）。
**要让 Heaven 到 60 fps，必须把每帧 268 次压到 94 次以下 —— 砍掉 65%。**

## 2. 第二个发现：每对字节数没变，变的是传输方式

这是本轮最反直觉的一条，也把前两份报告的猜测 **全部推翻**。

### 2.1 525 的 tx 是稀疏尖峰，不是持续流

`nvidia-smi dmon -s pucvmet -d 1`，M7 K=1000 连跑两次（30.4 秒，31 个采样点）：

```
tx = 3 3 3 445 3 3 3 445 3 3 3 3 3 3 445 3 3 3 3 3 445 3 3 3 3 3 3 3 3 3 3
```

**31 个采样点里只有 4 个是 445 MB/s，其余全是 3 MB/s。总和 1861 MB，平均 60 MB/s。**

### 2.2 515 的 tx 是持续流

同样的 dmon，M3 n=1000 连跑 8 次（515 上只用 5 秒就跑完）：

```
tx = 1652 1655 1778 1634 1655 1778      （六个连续采样点，没有一个是 3）
平均 ≈ 1659 MB/s
```

### 2.3 折算到"每对字节"：两者几乎一样

| | 515（M3） | 525（M7 K=1000） |
|---|---|---|
| fps | 190.38 | 7.87 |
| 对/秒 | 190,380 | 7,870 |
| 平均 tx | **1659 MB/s** | **60 MB/s** |
| **每对字节** | **8,714 B ≈ 8.7 KB** | **7,624 B ≈ 7.8 KB** |
| 每对耗时 | **5.25 µs** | **121.8 µs** |
| 等效速率 | **1.65 GB/s** | **64 MB/s** |

**每对字节差 11%，每对耗时差 23 倍。**

**⇒ 525 不是"多写了 52.6 KB"，是"同样的 8 KB 花了 23 倍的时间"。**

### 2.4 这推翻了什么

| 之前的说法 | 出处 | 现状 |
|---|---|---|
| 525 每对写 52.6 KB | 报告 118 §0 | **⛔ 错**：52.6 KB 是用"445 MB/s"除出来的，而 445 是尖峰值，不是平均值 |
| 515 不产生这 52.6 KB 流量 | 报告 118/119 | **⛔ 错**：515 产生更多（1659 vs 60），只是快 |
| PCIe 流量是成本来源 | 报告 118 §4 | **⛔ 错**：515 流量大 27 倍，却快 24 倍 |
| 515 是"流式"、525 是"攒批" | 本轮初判 | **⚠️ 方向对但结论反**：525 攒批反而更慢 |

**唯一还站着的是报告 119 的两条**：① 同步 ⇒ 有 PCIe 流量、不同步 ⇒ 0（这里要改成"有流量但量相同"）；
② **121 µs 这条路确实在 PCIe 上**（争用实验 +16.8%，M1 不动）。

## 3. 现在能说的机制（以及不能说的）

### 3.1 能说的

```
525 每帧时间 = 渲染(5.15 ms，与 515 相同) + K × 121.8 µs
                                    ↑
                        每次"变更后紧跟 draw"的固定代价
```

三条硬约束同时成立：

1. **严格线性、无折扣** ⇒ 是"每次一次"的动作，不是"每次一点"的累积。
2. **传输字节与 515 相同（~8 KB）** ⇒ 不是数据量问题。
3. **争用 PCIe 时涨 17%、对照模式不动** ⇒ 这个动作确实占用 PCIe 通道。

**最省的解释**：525 把 515 用**一次 DMA** 完成的 8 KB，拆成了**一串小事务**（每次几百字节），
每个事务都要等一次链路往返。按 n128a 实测的往返定价 5.5 µs 算，`121.8 / 5.5 ≈ 22` 次。

**⚠️ 这是假说，不是结论。** 我没有直接观测到那 22 次事务。

### 3.2 不能说的

- 那 8 KB 里装的是什么（状态块？UBO？描述符？）
- 为什么 525 要拆成小事务（代码路径改了？还是 515 用了更高效的提交方式？）
- **为什么 dmon 看到的是"每 5~6 秒一次 445 MB/s 尖峰"而不是"每对一次小流量"**
  —— 这一条最扎眼。若每对都传 8 KB，平均该是 60 MB/s 的**连续**流，不该是尖峰。
  可能是 dmon 的采样窗口行为，也可能 525 真的在攒批刷显存。**我没有解释，留在这里。**

## 4. 对"有输出的 Pascal 为什么没事"的更新

**仍然不能解释。** 而且本轮数据把之前那条"Gen3 快 8 倍"的边界估算也削弱了：

既然 515 和 525 每对字节相同（8 KB），那"Gen3 带宽大"就不是区分因素 ——
真正区分的是"525 把 8 KB 拆成了 22 次往返"，而**往返延迟在 Gen3 上只比 Gen1 好约 2 倍**。

按 2 倍算：每对 ~60 µs，268 对 = 16.1 ms，**正好压在 60 fps 的 16.67 ms 预算上**。
这与"社区没人大规模报告"勉强相容，但**只是边界估算，不是机制**。

## 5. 工程结论（可以直接用）

### 5.1 若留在 525

**唯一有效手段是把每帧的"变更-绘制对"次数压到目标 fps 对应的 K 以下。**

| 目标 | 每帧允许的同步次数 | 相对现在 268 次要砍掉 |
|---|---|---|
| 60 fps | 94 | 65% |
| 90 fps | 49 | 82% |
| 120 fps | 26 | 90% |

**注意：合并"切换"本身没用**。M8（切 500 次 + 只画 1 次）= 2.98 ms，M9（先切 1000 次再画 1000 次）= 7.54 ms
—— 说明**只要不交替，切换全免费**。必须减少的是**交替的段数**，也就是**渲染状态的批次**。

报告 92 已经实测过这条路：按材质排序把 500 批降到 8 批，**64 倍**。
按本轮公式验算：`5.15 + 8 × 0.12184 = 6.12 ms` ⇒ **163 fps**，与实测方向一致。

### 5.2 若换 515

**不需要减少任何东西。** 同一组 M7，K 从 1 到 1000，总时间 4.8~5.3 ms 全程不变。

## 6. 方法记录：headless X 让驱动 A/B 不再依赖桌面会话

本轮能干净地对测 515/525，靠的是绕开桌面：

```sh
# 1) 停图形会话（否则 Xwayland 持有 /dev/nvidia0，装不了驱动）
sudo systemctl isolate multi-user.target

# 2) 装驱动
sudo bash drivers/525.116.03/install-525.sh

# 3) 起一个 headless X（P106 无输出，需要 AllowEmptyInitialConfiguration）
sudo sh -c "setsid nohup Xorg :2 -config /tmp/xorg-nv.conf -logfile /tmp/x.org >/dev/null 2>&1 </dev/null &"

# 4) 直接测
DISPLAY=:2 __GLX_VENDOR_LIBRARY_NAME=nvidia ./n83a -M 7 -n 1000 -c 100
```

`/tmp/xorg-nv.conf` 关键三行：

```
Driver "nvidia"
BusID "PCI:1:0:0"
Option "AllowEmptyInitialConfiguration" "true"
```

**两个坑（都踩了）**：
1. **必须 `setsid nohup`**，否则 `sudo sh -c "... &"` 的子进程随 sudo 退出被杀，Xorg 日志是空的、`pgrep` 查不到。
2. **`isolate multi-user.target` 之后，`sddm` 的 autologin 配置指向一个不存在的用户（`User=tablet`），
   恢复 `graphical.target` 会停在登录界面**。headless X 完全不依赖它，所以实验能继续。

**验证 FBO 可用性**：headless X 下若 `glCheckFramebufferStatus` 返回 `0x8cdd`（`GL_FRAMEBUFFER_UNSUPPORTED`），
n83a 会直接退出、GPU 保持 6 W / 139 MHz 空转 —— **这时候测到的全是 0，看起来"很快"，其实是没跑**。
判据：`nvidia-smi --query-gpu=utilization.gpu,power.draw --format=csv` 必须是 100% / 37 W 一档。

| 515/525 每对字节相同（8.7 vs 7.8 KB） | **中强** | 两边 dmon 独立测量，差 11%；但 dmon 采样窗口行为未摸清 |
| 525 的 tx 是稀疏尖峰（31 点里 4 个 445） | **强** | 长采样原始序列 |

## 8. 一句话

**你问能不能减少 —— 能，而且账很好算：`5.15 ms + K × 121.8 µs`，K 是每帧"改状态后紧跟绘制"的次数。**
**要 60 fps 就得把 K 从 268 压到 94（砍 65%），要 120 fps 得压到 26（砍 90%）。**
**但真正该说的是：515 上同样的事一分钱不收（K=1000 也只要 5.27 ms）。**
**至于 525 为什么收这笔钱 —— 我把"每对多写 52.6 KB"这条彻底否掉了：两个版本每对传的字节一样多（~8 KB），**
**525 只是把它传了 23 倍的时间。**
