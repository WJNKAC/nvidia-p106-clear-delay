# 32 · 定案：525 的 3ms 在用户态，nvidia 内核驱动完全没参与

> 2026-10-25 21:40
> 问题（用户提出）：现在能否判定"内核态还是用户态"？**能，而且结论很干净。**
> 方法：在 525 + Heaven 上，用 ftrace 同时记录 map 窗口的 uprobe 和全进程 syscall，
> 按 uaddr 做 futex 配对，逐层追唤醒链。
> **五条结论：**
> 1. **map 的 3ms 里，worker 98.3% 的时间睡在 `futex` 上。**
> 2. **期间 nvidia 内核驱动完全没参与**：全进程 ioctl 只有 **0.4%** 的窗口有活动，**>1ms 的 ioctl = 0.0%**；worker 自己全程 **0 次 ioctl**。
> 3. **唤醒链是两个用户态线程互相握手成环**：5609 等 `0x...d44` ← 5610 唤醒；5610 等 `0x...d84` ← 5609 唤醒。**两个 uaddr 相差 0x40，同一结构体。**
> 4. **报告 23 的"驱动内部的 1ms 轮询线程"是错的**：那个 1ms `usleep(1000)`（周期 1091µs）来自 **`libUnigine_x64.so+0x26a7fd`**，是引擎自己的线程。
> 5. **glcore 的 4 个 `nanosleep@plt` 调用点命中全 0** —— 说明等待不走 nanosleep，而是 futex。

## 1. map 窗口内到底在等什么（决定性表）

在 525 + Heaven（1080p，稳态）上采 8 秒，264 个 map 窗口：

| 指标 | 值 |
|---|---|
| map 窗口数 / 中位时长 | 264 / **3038 µs** |
| 窗口内 worker 的 **futex 累计** | 中位 **2987 µs = 窗口的 98.3%** |
| 长 futex（>500µs） | 478 次，中位 **2054 µs** |
| **窗口与任何 ioctl 重叠** | **1/264 = 0.4%** |
| **窗口与 >1ms 的 ioctl 重叠** | **0/264 = 0.0%** |
| worker 自身的 ioctl | **0 次** |
| worker 自身的 `clock_nanosleep`（窗口内） | **0 次** |

**全进程 ioctl 统计**（同期）：4645 个，中位 **1 µs**、p95 46µs。
主要来自 tid 5608（4379 次）和 5592（266 次）—— **都不是 map worker，且都极短**。

### 1.1 判读

| 候选 | 判定 |
|---|---|
| nvidia 内核驱动（`nvidia.ko`）在做长操作 | ❌ **排除**：无 >1ms 的 ioctl，worker 零 ioctl |
| GPU 在算（等 GPU） | ❌ 排除：报告 31 已证明 Heaven 下 GPU 功耗 ≈ idle |
| 内核 futex 子系统 | ◐ **只是载体**：futex 是通用同步原语，里面没有驱动逻辑 |
| **用户态代码里的线程间同步** | ✅ **主因** |

**`futex` 这个词容易误导**：它是"用户态同步原语的内核支持"。
真正决定等多久的**不是内核**，而是**另一个用户态线程什么时候来 WAKE**。

## 2. 唤醒链：两个用户态线程互相握手成环

按 uaddr 配对 WAKE，逐层往上游追：

```
L0  tid 5609（primus readback worker，调 glMapBuffer）
      等 uaddr 0x7fd2f0000d44  （484 次）
      ← tid 5610 唤醒 349 次（100%）

L1  tid 5610（glcore 内部线程）
      等 uaddr 0x7fd2f0000d84  （396 次）
      ← tid 5609 唤醒 396 次（100%）
      → 成环，链条终止
```

### 2.1 两个 uaddr 相差 0x40

```
0x7fd2f0000d44
0x7fd2f0000d84   ← 高 0x40 = 64 字节
```

**同一结构体（或相邻的两个成员）里的两把锁/两个条件变量。**
典型的"双向握手"布局：A 等 B 的完成位，B 等 A 的释放位，两者放在一个 64 字节的 ctx 里。

### 2.2 WAKE 的时刻精确对齐 mb_out

| 项 | 值 |
|---|---|
| 窗口结束 ±5ms 内有 WAKE 的窗口 | 257/264 = **97.3%** |
| **WAKE 相对 `mb_out` 的时刻** | **中位 −10 µs**（范围 −99 ~ +85） |

**5610 在 map 返回前 10µs 唤醒 5609** —— 因果方向明确：先 WAKE，后 map 返回。

### 2.3 这解释了什么

```
5609 想拿数据 → 发现没准备好 → 等 0x...d44
5610 在做真正的活（提交/查询驱动）→ 做完 → WAKE 0x...d44
5609 醒来 → 但 5610 又在等 0x...d84（等 5609 释放上一批）
→ 两者互相等，形成按轮次的握手
```

**"2 个 1ms tick"不是内核定时器，而是这个握手环一圈的时长。**

## 3. 修正报告 23：那个 1ms 轮询不是驱动的

报告 23 我写过"唤醒者是**驱动内部**的 1ms 定时轮询线程"。**错了。**

实测 `usleep` 调用者归属（挂 libc `usleep`，取返回地址归库）：

| usleep 参数 | 次数 | 调用者 |
|---|---|---|
| **1000 µs** | 5518 | **`libUnigine_x64.so+0x26a7fd`** |
| 10000 µs | 595 | `libUnigine_x64.so+0x15abcc` |
| ~28600 / ~29600 µs | 各 2 | `libGL.so.1+0x18895`（primus 自适应睡眠） |

- 那个 **1000µs 的 usleep 全部来自 Unigine 引擎**，线程 tid 6699，**周期 1091µs**
- 它出现在 100% 的 map 窗口内 —— 但那只是**共现**（它一直在跑），不是因果
- **glcore 的 4 个 `nanosleep@plt` 调用点（0x146d742 / 0x19499f7 / 0x194e04c / 0x194e060）命中全部为 0**

### 3.1 一个容易踩的调用链陷阱

`ns` = `us` = `cn` = 6306（三个数完全相同）。
因为 libc 的调用链是：**`usleep()` → `nanosleep()` → `clock_nanosleep()` → 系统调用**。
同一批调用被三层探针各记一次。

**如果只看 `nanosleep` 的调用者会判成"没人调"**（glcore 的 4 个点全 0），
而真相是它走的是 `usleep`。

> **教训**：查"谁在 sleep"时，要同时挂 `usleep` / `nanosleep` / `clock_nanosleep` 三个，
> 并注意它们会**互相嵌套记录同一批调用**（数值相同就是嵌套，不是三次独立调用）。

## 4. 结论：问题范围被切到"glcore 用户态的线程握手"

### 4.1 可以直接划掉的

| 方向 | 状态 |
|---|---|
| nvidia 内核驱动（`nvidia.ko`） | ❌ **划掉**：零长 ioctl、worker 零 ioctl |
| GPU 算力 / 显存带宽 | ❌ 划掉：报告 31 的功耗证据 + 报告 29 的分辨率扫描 |
| PCIe 传输 | ❌ 划掉：两版相同 2.5ms |
| primus 的自适应睡眠 | ❌ 划掉：报告 29 的 `PRIMUS_SLEEP=99` 实验 |
| 并发结构（双 context / 双线程） | ❌ 划掉：报告 30 四组 <0.5% |
| **glcore 用户态的 `5609 ↔ 5610` 握手** | ✅ **唯一剩下的** |

### 4.2 具体靶点

```
uaddr 0x7fd2f0000d44   ← worker(5609) 等它
uaddr 0x7fd2f0000d84   ← glcore 线程(5610) 等它
两者相差 0x40，同一结构体
```

**下一步就是查：这两个 futex 属于 glcore 的什么对象、5610 为什么晚 2 轮才 WAKE。**

可用的手段：
- gdb 在 5610 的 WAIT 前下断点，抓它当时在跑 glcore 的哪个函数（`bt`）
- 或在 5610 的 `FUTEX_WAKE` 前下断点，看它刚做完什么（`bt` 会给出 glcore 内部位置）
- 拿到函数地址后，用 `symoffset.py` 转成文件偏移，与 515 静态对比

### 4.3 为什么这解释了两版差异

515 的 map 是 1 个 tick、525 是 3 个。既然都在这条握手链上，
差异只能是**握手的轮次**：515 每轮更快返回，525 需要 2~3 轮。

而"轮"的节拍由 `5610` 决定 —— 它是一个 glcore 用户态线程。
**所以回归点在 glcore 的用户态同步逻辑，不在内核。**

## 5. 本轮踩的四个解析坑（都导致"看起来没数据"）

| 坑 | 症状 | 修法 |
|---|---|---|
| **ftrace 事件名是 `sys_futex`，不是 `sys_enter_futex`** | grep `sys_enter_futex` 得 0，误以为没采到 | 用 `sys_futex`；且行内是 `(uaddr: ..., op: ...)`，值无 `0x` 前缀 |
| **uprobe 事件名在 trace 行的位置不同** | ftrace 里是 `mb_in: (0x...)`，perf script 里是 `probe_libGL:mb_in:` | 两处都要兼容 |
| **rows 存成 `(t, tid, uaddr, op)` 丢了事件名** | `n == 'mb_in'` 永远不成立（第三元素是 0） | 存 5 元组，明确带 name |
| **`Counter(t for t,tid,...)` 取了时间戳当 tid** | worker tid 变成 `823929103.0`（一个时间戳） | 解包时注意变量顺序 |

> 第四个坑特别隐蔽：`Counter` 里写错一个变量名，输出的是一个"看起来像 ID"的大数（时间戳），
> 而不是报错。**任何"tid 是个奇怪的大数"都要怀疑取错了字段。**
