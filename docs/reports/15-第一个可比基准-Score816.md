驱动 525.116.03，显示路径 `primusrun`（用户日常方式）。

**`Score = FPS × 25.185`**（816 / 32.4 = 25.19）。Score 不是独立物理量，只是 FPS 的固定缩放。
→ 以后统一报 **FPS**，不必再提 Score。

## 2. 这可能解释"60 vs 30"的全部矛盾——包括推翻我自己

`Max 63.7 / Avg 32.4 / Min 23.9`：帧率是**双峰分布**。

- 相机路径的**轻场景段**跑到 60~64（Max 63.7 超过 60，说明**没有硬性 60 Hz 上限**）
- **重场景段**掉到 23~25（Min 23.9）

而我的做法一直是"进场景后 +N 秒截一张 HUD"。**那个时刻几乎总在路径前段的轻场景**，
所以我连读到：

```
61 61 61 60 60     ← run1
60 61 60 32 61     ← run2   （第 4 张正好落在重段）
61 61 59 60 22     ← run3   （第 5 张正好落在重段）
```

**那些 60 不是"帧率"，是路径轻段的瞬时值；那些 22/32 是重段的瞬时值。**
真实值只有整条路径的 Avg = 32.4。

### 2.1 后果：报告 11 的核心结论作废

报告 11 写的是：

> 515@1080p = **60 fps**（无地板） vs 580@1080p = **31 fps**（有地板）
> → 版本边界坐实

**这个对比不成立。** 两次采样落在相机路径的不同相位，一个撞在轻段、一个撞在重段，
差异可以完全由相位解释，不需要任何版本差异。

这违反了我自己在 README 里立的铁律："**任何跨版本比较必须同一探针、同一脚本、同一相位验证方式**"。
我换了探针（截图时刻），却把它当成同一口径。

**修正后的现状**：515 是否也有地板，**未知**。它可能也是 ~32。
若是，"525+ 引入地板"这个前提本身就不存在。

## 3. 投诉是真的：慢了 2~2.5 倍

P106-100 就是 **GTX 1060 6GB 同芯片**（GP106 / 1280 CUDA / 6 GiB GDDR5 / 192-bit）。

Heaven 4.0 @ 1920×1080、Quality High、Tessellation Disabled 的参照量级约为 **FPS 70~85**
（GTX 1060 6GB 的公开成绩，Windows 原生输出）。

实测 **32.4** → **慢 2~2.5 倍**。

所以用户"正常跑就是 30fps"不是错觉、不是机位、不是核显。**地板真实存在。**

## 4. 两个疑点已排除

### 4.1 `Unknown GPU (256MB)` 不是显存问题

```
lspci:      Region 1: Memory at e0000000 (64-bit, prefetchable) [size=256M]
nvidia-smi: 6144 MiB
primusrun glxinfo: Dedicated video memory: 6144 MB
```

**256 MB 是 BAR 窗口大小**，Heaven 把它当作显存报了出来。真实显存 6 GiB，健康。
这是 Heaven 在 primus/libGL 包装下探测 GPU 信息的局限，**无害**。

### 4.2 PCIe Gen1 是卡片固有限制，不是配置错误

```
LnkCap:  Port #0, Speed 2.5GT/s, Width x16
LnkSta:  Speed 2.5GT/s, Width x16
```

`LnkCap`（**能力**）本身就是 2.5 GT/s = Gen1。GP106 芯片本应 Gen3，
但这张 Gigabyte P106 矿卡的固件只宣告 Gen1。

- 不是插槽问题（`00:01.0` 是 Haswell 的 PCIe 3.0 x16 控制器）
- 不是降速协商（能力上限就写着 1）
- **不可通过驱动修正**

Gen1 x16 ≈ 4 GB/s 理论。primus 每帧要 readback 1080p×4B = 8.3 MB，
32 fps 时约 265 MB/s，**远未饱和**。所以它不是当前 30fps 的主因，
但它会放大任何跨 PCIe 的传输开销。

**功率限制 120 W（max 140 W），也不是瓶颈。**

## 5. 下一步：决定性的 A/B，比换驱动便宜得多

现在有两个互斥假说，用**同一个基准、只改显示路径**就能分开：

| 假说 | 预测 | 显示路径 |
|---|---|---|
| **A. primus 是地板** | dmabuf 路径 Score 显著更高（可能 2 倍） | `__GLX_VENDOR_LIBRARY_NAME=nvidia` |
| **B. 驱动/GL 本身慢** | 两条路径 Score 接近 | — |

`primusrun` 每帧做 `glReadPixels` + 跨线程 blit 回内存，再由 Intel 显示；
这是一个**与 GPU 算力无关的固定开销**，在高分辨率下很容易把帧率压在 30~40。

**如果 A 成立**：地板来自 primus 的 readback 架构，与驱动版本无关，
整个"525+ 引入回归"的案子要重写；解决方案是改用 dmabuf/PRIME 或直接让 N 卡输出。
**如果 B 成立**：才轮到换驱动版本做 E4。

### 5.1 关于那条路径会抽搐

dmabuf 路径在 Xwayland 下不稳（用户实测"60Hz 场景不断抽搐"）。
但**抽搐不影响 Score 的准确性**——benchmark 是按时间戳统计帧数，不依赖肉眼观感。
所以这个 A/B 可以做，只是期间别看画面。

## 7. 方法论增量

- **闭源 benchmark 的"帧率"必须以完整运行为准**，因为相机路径本身是负载曲线。
  单帧/瞬时截图只能用来判断"是否在渲染"，不能用来比较版本。
- 判"是否真在渲染"的廉价指标：**GPU mem util**。
  本例：正确加载 12~17%，错误参数启动 6%（空世界）。
- 结果面板里的 `Min/Avg/Max` 本身就是一条负载曲线摘要，**应先看这三者的比值**：
  Max/Avg = 1.97 意味着存在 2 倍的重段，任何单点采样都不可信。
