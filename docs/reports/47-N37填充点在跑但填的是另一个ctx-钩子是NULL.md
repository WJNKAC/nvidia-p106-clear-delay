# 47 · N37：`f` 的填充点确实在跑，但**填的是另一个 ctx**——map 循环守着一个永远为 0 的字段

> 2026-10-26 04:40
> 用户指示：带着"修了 map 会不会变快"的疑问做 N37；如果 `1237e01` 是断链 bug，修它可能闭环；
> 如果它本来就是条件路径，2ms 循环只是"等活来"的正常机制，就转向 `1238ae7` 的钩子 `0x1b8`。
> **顺手看了那个钩子。**
>
> **结论：两条线索都断了，而且断得很干净。**
> `1237e01` 在正常执行（262/8s），但它填的是**另一个 ctx**；map 循环守着的那个 ctx 的 `f` 恒为 0。
> `0x1b8` 钩子**是 NULL**，从未安装 → `1238aee` 一次都没被调用。

---

## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **`1237e01` 不是死代码，它在正常执行** | uprobe 命中 **262 次 / 8s** |
| 2 | **但它写的是另一个 ctx**：`0x7f127091e040`，而 map 循环守的是 `0x7f1244000d40` | 两个 ctx 的 `%rbx` 分布完全不同 |
| 3 | **两个 ctx 的字段值截然不同** → 一个在被维护，一个被弃置 | 见 §3 表 |
| 4 | **`1238a28` 循环在两个 ctx 上都跑**：弃置的那个 **985,722 次**、被维护的那个 2,064 次 | 8s 采样 |
| 5 | **`0x1b8` 钩子 = NULL**（静态在 `.bss`，运行时确认 0）→ `1238aee` 一次都没调用 | 静态 + 动态双证 |
| 6 | **`HOOK=0` 实测**与 5 一致 | uprobe 0 次 |
| 7 | **→ 不是"断链 bug"，是"两个 ctx 走了不同的生命周期"** | 由 1-6 推出 |

**一句话**：**map 循环守着的那个 ctx，`f` 永远是 0（没人填）；而同一个函数在另一个 ctx 上把 `f` 正常维护到了 719。所以这条阈值分支对"map 那个 ctx"确实是死的——但原因是 `f` 没被填，不是代码断链。**

## 2. 静态：`1237c50` 没有直接调用者，只在 vtable 里

```bash
grep "call   1237c50"   → 0 处
```

它的地址以 8 字节形式出现在两处数据区：

| 位置 | 内容 |
|---|---|
| `0x29ff08` | `0x1237c50`，前后是 `0x1237be0` / `0x2a25d88` / `0x8` → **方法表描述**（函数指针 + 表地址 + 项大小 8） |
| `0x2a25d80` | 在一条连续的 code 指针数组里：`... 1237be0, 1237c50, 1238680, 1238690, 12386d0, 1237290 ...` → **vtable** |

**注意 `0x12386d0` 也在这张 vtable 里**——就是报告 46 里"处理一批"的那个函数。
两个函数是同族方法，通过同一个对象分发。

> 这说明这套队列处理器是**多态**的：同一组方法表挂在不同 ctx 上，行为由 ctx 内部状态决定。

## 3. 动态：两个 ctx，两种命运

`n37b.sh`（uprobe `0x1237e01` 与 `0x1238a28`，各读 `%bx`）：

### 3.1 ctx 分布

| 探针 | ctx `0x7f1244000d40` | ctx `0x7f127091e040` |
|---|---|---|
| **`1237e01`（f 的填充点）** | **0 次** | **191 次** |
| **`1238a28`（循环入口）** | **985,722 次** | 2,064 次 |

### 3.2 字段实测

| 字段 | `0x7f127091e040`（被维护） | `0x7f1244000d40`（map 循环那个） |
|---|---|---|
| `f` (`0x8e0e00`) | **719.00** | **0.00** |
| `counter` (`0x8e0dc0`) | **719.00** | **0.00** |
| `g` (`0x8e0c60`) | 2,462.00 | 2,157.00 |
| 循环命中 | 2,064 | **985,722** |

**同一个函数（`0x1237c50`）在 A 上把 `counter` 累到了 719，在 B 上一次都没执行。**

### 3.3 这解释了报告 46 的矛盾

报告 46 说"`F=0` 所以 f 从未填充"——那是**当时只挂了一个探针、没区分 ctx**。
现在挂上 `%bx` 才看到：**填充点在工作，只是服务另一个对象**。

> ⚠️ **这是我第二次在同一件事上翻车**（46 把"从未填充"下早了）。
> 教训：**多 ctx 的驱动里，任何"某字段恒为 X"的结论必须先按 ctx 分开统计。**
> 单看全局计数会把"另一个 ctx 在正常工作"误当成"整个功能没启用"。

## 4. `0x1b8` 钩子：NULL，从未安装

`1238ae7` 的代码：

```asm
1238ad7: mov    0x1b8(%rbp),%rax    ; rbp = _nv014glcore 基址 0x2a6e7e0 → 槽 = 0x2a6e998
1238ade: test   %rax,%rax
1238ae1: je     1238a28             ; NULL → 回循环
1238ae7: lea    0x8e0e40(%rbx),%rdi
1238aee: call   *%rax               ; 只有非 NULL 才调
```

| 检查 | 结果 |
|---|---|
| ELF 静态 | 该地址在 `.bss`，文件里无内容 → 初始必为 0 |
| 运行时 | **`0x0000000000000000`** → **NULL** |
| uprobe `0x1238aee` | **0 次** |

**结论：这个钩子从未被安装，`1238aee` 是死点。**

用户猜它是"更直接的线索"——**但它也是空的**。

## 5. 那么"等活来"这个假设成立吗

用户的问题："如果它本来就是条件路径，2ms 循环只是'等活来'的正常机制，优化它没意义。"

**现在的证据支持这个判断**，理由是：

| 观察 | 含义 |
|---|---|
| `PROC=0`（`call 12386d0` 一次没走） | 循环体内没有任何实质处理 |
| `WAIT=3896`、`map=30.8ms` | 纯等 |
| `f=0` 在该 ctx 上恒定 | 阈值分支对该 ctx 永久失效 |
| 但**同一函数在另一 ctx 上正常工作**（f=719、counter 在涨） | 说明代码本身没坏，是**这个 ctx 没被"激活"** |

**所以最可能的图景是**：`0x7f1244000d40` 是一个**已停用/未启用**的队列处理器实例，
它的 2ms 轮询循环还在跑（因为线程没停），但阈值条件永远不会满足 → 空转。

**关键疑问（也是决定"修了会不会变快"的）**：这个空转的循环**占不占 CPU / 阻不阻塞别人**？

- 若它只是在**独立的空闲线程**上空转 → **修它不会让 map 变快**，只是省电。
- 若它**持锁/占着与 map 同一把锁** → 修它可能有效。

**这一点还没测，是下一步最该做的**（见 §6 N40）。

### 7.1 方法论（本轮最大教训）

**多 ctx 驱动里，任何"某字段恒为 X"的结论，必须先按 ctx 分开统计。**

我连续两轮在这上面出错：
- 46：单探针读到 `f=0` → 下结论"从未填充"
- 47：加上 `%bx` 才看到 **填充点在工作，只是服务另一个 ctx**

**判据（写进技能库）**：uprobe 命中计数若可能来自多个对象，
**必须在事件里带上对象指针**（`p:probe/F 0xADDR ctx=%bx`），并**按指针分组统计**。
只看全局总计数，等于把"N 个对象的行为"平均成一个数，最容易得出相反结论。
