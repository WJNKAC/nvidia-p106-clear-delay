# N178 — ★ Heaven 前台复现：525 基准 25 FPS，把 `0x3998` 从 240 改成 16 → **71 FPS（2.84×）**

**日期**：2026-10-27
**驱动**：525.116.03（P106-100）
**程序**：Unigine Heaven 4.0，1920×1080，Quality High，`primusrun` 呈现
**方法**：**代码补丁**（改驱动里那条命令的立即数），非运行时数据改写 —— 零开销

---

## 0. 结论（用户要的前台复现）

| 配置 | **FPS（屏幕读数）** | GPU 功耗 |
|---|---|---|
| **基准（实参 240）** | **25** | 70.9 W |
| **补丁（实参 16）** | **71** | **102.7 W** |

**⇒ 2.84 倍，且功耗从 70.9 W 涨到 102.7 W —— GPU 从"空转等待"变成"真在渲染"。**

这个数字与用户自己的观测（"能跑到 100fps+" vs "限制在 60fps"）方向一致，
但注意本次是 **25 → 71**，因为这里用的是 `primusrun` + 全高画质，且两轮都未被 60fps 节流压住。

---

## 1. 根因（已闭环，用户表述完全正确）

**525 在 pushbuffer 里每批次发一条 `0x3998` 命令，实参 `0xF0`（240）。**

命令编码（从 pushbuffer 实测）：

```
header  0x20010E66   (op=1 INC_METHOD, cnt=1, sub=0, meth=0x3998)
arg     0x000000F0   ← 240
```

驱动是**一条 64 位 movabs 一次性写入**这两件事：

```asm
movabs rcx, 0xF020010E66     ; 高32位 = 实参 0xF0，低32位 = 命令头
mov    [rax], rcx
```

两处，分别在 `glcore+0x15c3767` 与 `glcore+0x1842131`。

**换算：**

```
240 × 0.91 µs ≈ 218 µs / 批
400 批 × 218 µs ≈ 87 ms
```

与我们此前测到的每批 118.6 µs（短跑）及长跑稳态下的更大值一致。
**这就是那堵墙。**

> 用户给的 `240 × 0.91µs ≈ 218µs`、`400 批 ≈ 87ms` 完全正确。
> 补充：报告 167 里 118.6 µs/批 是**短跑值**（`-f 8`）；
> 长跑（`-f 200`）下每批代价更大，所以 218 µs 这个数才是稳态口径。

## 2. 补丁内容（两个字节）

| 文件 | 虚拟地址 | 原字节 | 新字节 |
|---|---|---|---|
| `libnvidia-glcore.so.525.116.03` | `0x15c376d` | `F0` | `10` |
| 同上 | `0x1842137` | `F0` | `10` |

运行时用 `patchpb.so` 打（`PATCH="0x15c376d=10;0x1842137=10"`），不改原文件。

## 3. 正确性验证（关键：不是"快了但画错了"）

用 `n83b -M 7 -c 400` 的回读模式（会真正 `glReadPixels` 并累加像素值作为 `chk`）：

| 配置 | `map_p50` | `total_p50` | **`chk`（画面校验）** |
|---|---|---|---|
| 基准(240) | 52.465 ms | 53.128 ms | **5150** |
| 补丁(240)（只读对照） | 52.514 | 53.007 | **5150** |
| 补丁(64) | 16.778 | 17.260 | **5150** |
| 补丁(16) | **7.038** | **7.606** | **5150** |

**`chk` 四组完全一致（5150）⇒ 画面正确。**
**补丁(240) 与基准(240) 也几乎相同 ⇒ 补丁机制本身零开销。**

⇒ **那 240 个单位是过度的保守等待，不是正确性必需的。** 这是本项目首次证明这一点。

Heaven 侧同样验证：截图对比两轮画面，场景相同、无花屏/撕裂（见 `fps_base.png` / `fps_patched.png`）。

## 4. 为什么这次 A/B 可信，而之前那轮不可信

| 轮次 | 手段 | 结果 | 可信度 |
|---|---|---|---|
| 早前 | 运行时改 **pushbuffer 数据**（pbpatch4） | 命中数基本不变 | ❌ **改写率仅 ~2%**，Heaven 命令流速太快，6 个活跃段扫不过来 |
| **本次** | 改 **驱动代码里的立即数** | 25 → 71 FPS | ✅ 一次性生效、零运行时开销 |

**判据**：在 patcher 运行期间采样实参，40 条里只有 1 条变成 `0x10` —— 这直接证明数据改写不可行。
**代码补丁没有这个问题。**

## 5. 测量过程中踩的坑（都记下来，因为每个都花了不少时间）

### 5.1 Heaven 的 FPS 只显示在屏幕上，不写日志
`grep -i fps` 日志永远 0 条。**必须截图读像素。**

### 5.2 截图：Wayland 下 `import` / ffmpeg x11grab 都拿不到内容
- `import -window root` → 报错
- `ffmpeg -f x11grab` → 能出文件，但**全黑**（X root 里没有内容，画面在 Wayland surface）
- **`spectacle -b -n -o <path>` 正确** —— 它走 KWin 的截图接口，能拿到真实合成结果

**需要的环境变量**（我一开始漏了，导致 spectacle 取不到正确目标）：
```bash
export XDG_RUNTIME_DIR=/run/user/1000
export WAYLAND_DISPLAY=wayland-0
export DISPLAY=:0 XAUTHORITY=/run/user/1000/xauth_XXXX
```

### 5.3 `pkill -f heaven_x64` 会杀掉自己
命令行里含 `heaven_x64` 字符串，`-f` 全匹配把自己的 shell 也杀了。
**必须用 `pkill -9 -x heaven_x64`（精确进程名）。**

### 5.4 Heaven `-benchmark` 要跑完 26 个场景才出结果
约 3~4 分钟，且 `timeout` 打断后会是 `double free` 崩溃、没有任何 FPS 输出。
**不要用它做快速 A/B；用"普通模式 + 截图"更快。**

### 5.5 `entryst` 在 Heaven 上会卡死
Heaven 多线程 + `0x15761b0` 调用极频繁，硬件断点让目标慢到无法完成初始化。
**多线程热函数上不要用 ptrace 硬件断点。**

## 6. 兑现与遗留

### 兑现
- **根因定量闭环**：240 单位 × 0.91 µs × 批次数，用户表述正确。
- **正确性保持**：`chk` 四组一致，证明这 240 是过度保守。
- **前台可视复现**：Heaven 25 → 71 FPS，功耗 70.9 → 102.7 W。

### 遗留（必须说清）
1. **这不是可用方案。** 改的是驱动二进制的立即数，需要 patch 文件；驱动一升级就失效；
   且我们只验证了"画面对"，没有做长时间稳定性测试（Xid / 长时间跑 / 其他应用）。
2. **71 FPS 不等于 515 的水平。** 515 在同负载下没有这一项，理论上还能更高；
   而且补丁后 525 仍有 `base` 那部分开销未解释（报告 168 §5）。
3. **`0x3998 = 0` 仍是特殊值**（实测等价于 240），没有找到"完全关闭"的路径。
4. **Heaven 的 FPS 会随场景变化**（本报告是同一场景、同一时刻的对比，非全程平均）。
   要严格的全程平均，需要用 `-benchmark` 跑完整套（3~4 分钟）并解析最终 Score。

## 7. 对"能不能用"的判断

**短期**：如果要在这台机器上跑 525，且能接受 patch，可用 `patchpb.so` + 两个字节地址。
**长期**：不可靠。真正的交付路径仍是：
- **要么整套用 515**（本项目已证明 515 无此问题）；
- **要么在 525 上合批**（把批次数压到预算内，报告 166 §6 给了定量关系）。
