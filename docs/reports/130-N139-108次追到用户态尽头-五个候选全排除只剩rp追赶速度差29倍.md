# 报告 130 / N139：**"108 次"追到用户态尽头 —— 提交量、判据、取 rp 路径两版完全一致，只有 rp 追赶速度差 29 倍**

> 时间：2026-10-27
> 环境：<user>@<testhost>，P106-100，headless X `:2`（515 与 525 各测一轮）
> 触发：用户「之前卡在一个画面上，后续 GPU 功耗只有 7W。继续查 108 次这个问题」
> 结果：**把"108 次"的成因从 5 个候选收敛到 1 个，并把 glcore 用户态代码全部排除。**

---

## 0. 先记下一个重要观察（用户提供）

**注入 `bit0=1` 后，画面卡在一个画面上不动，GPU 功耗掉到 7W 左右。**

这补齐了报告 129 缺的那块：

| 阶段 | 现象 |
|---|---|
| 注入瞬间 | 帧率从 32.3 跳到 59 fps（我测到的那段） |
| 随后 | **画面冻结，GPU 功耗 7W（几乎空闲）** |

**⇒ 注入后不是"一直快"，而是"先快一下然后彻底挂起"。**
**⇒ 那个"缓存读指针"让驱动以为可以无限写，命令队列错乱后 GPU 无事可做。**
**⇒ 我报告的 59 fps 只代表"出错初期还能动"，不代表注入版的真实结局。**

## 1. 五种候选，逐个用数据排除

追"为什么 525 每对要查 108 次"，可能的成因有五个。全部实测：

| # | 候选 | 实测 | 结论 |
|---|---|---|---|
| 1 | **提交的工作量不同** | W 增量：515 = 525（556/834 逐档相同） | ⛔ 排除 |
| 2 | **批次数不同** | req：两版都是 140（1.17/帧） | ⛔ 排除 |
| 3 | **判据阈值不同** | `W - sz = 2`：两版相同 | ⛔ 排除 |
| 4 | **rp 落后程度不同** | `gap = W-rp = 5`：两版相同 | ⛔ 排除 |
| 5 | **取 rp 的路径不同** | 两版 bit0=0、同样 MMIO 读 `0x800000ba`、实现对构 | ⛔ 排除 |

**⇒ 五个候选全排除。剩下的只有"rp 追赶的速度"。**

## 2. 数据一：W 增量两版完全相同

`[ctx+0x1130]`（525）/ `[ctx+0x10d0]`（515）—— 我把这个量记作 W，初始化为 1 / 0，每帧推进。

| 模式 | req（两版） | W 增量 515 | W 增量 525 |
|---|---|---|---|
| M1 只画 | 140 | **556** | **556** |
| M2 改 uniform | 140 | **556** | **556** |
| M3 切不同 prog | 140 | **834** | **834** |
| M6 切同一 prog | 140 | **834** | **834** |
| M8 只切不画 | 140 | **556** | **556** |
| M9 先切后画 | 140 | **556** | **556** |

n 扫描（M3）：

| n | 515 W 增量 | 525 W 增量 | 515 total | 525 total |
|---|---|---|---|---|
| 100 | **556** | **556** | 2.84 ms | 15.09 ms |
| 300 | **556** | **556** | 3.51 ms | 40.22 ms |
| 500 | **695** | **695** | 4.01 ms | 64.95 ms |
| 1000 | **834** | **834** | 5.28 ms | 127.26 ms |

**两版的 W 首尾值都完全相同（16→572 / 18→852）。**

**而且 `556 = 4×139`、`695 = 5×139`、`834 = 6×139`** —— 离散三档，139 ≈ req 次数。
⇒ **每次预留函数调用推进 4 / 5 / 6 个位置单位**，与 n 无关，只与"是否饱和"有关。

**⇒ 提交量、批次结构、位置推进，两版一模一样。**

## 3. 数据二：判据与 rp 落后量也相同

在循环点读三个量：

**515（M3 n=300）**：
```
gap = W - rp = 5    W - sz = 2      ← 5 <= 2 不成立，不通过
```

**525（报告 127，M3 n=200）**：
```
rp=559  W=564  sz=562   → gap=5, W-sz=2   ← 同样不通过
```

**两版的 `gap` 都是 5，`W - sz` 都是 2。判据完全相同，都不会通过。**

## 4. 数据三：取 rp 的代码路径完全同构

### 4.1 515 的取 rp 函数 = `0xfbae60`

从 `ctx+0x1a60` 动态读出：

```asm
fbae60: testb $0x1,0x300(%rdi)    ; bit0
fbae67: je    fbae78              ; 0 → 慢路径
fbae69: mov   0x11e0(%rdi),%rax   ; 1 → 返回缓存
fbae78: call  fb19d0              ; 慢路径
```

### 4.2 525 的取 rp 函数 = `0x1572e60`

```asm
1572e64: testb $0x1,0x320(%rdi)
1572e6b: je    1572e80
1572e6d: mov    0x1240(%rdi),%rax
1572e80: call   1569f10
```

**逐条同构，偏移统一差 0x20。**

### 4.3 实测 bit0：**两版都是 0**

| | 515 | 525 |
|---|---|---|
| bit 位置 | `[ctx+0x300]` | `[ctx+0x320]` |
| M1 | **f=0** | **f=0** |
| M3 | **f=0** | **f=0** |
| M8 | **f=0** | **f=0** |
| 缓存值 | 573 | 571 |

**⇒ 两版都不走缓存，都走真查询。**

### 4.4 慢路径也同构

**515 `0xfb19d0`** / **525 `0x1569f10`**：

```
读 [ctx+0x1fc]（状态位）
读 [ctx+0x22e5c]（通道数 n）
发 $0x800000ba 给 MMIO 读函数
通道数 > 1 则遍历 0x800000bb.. 取最大值
把结果缓存到 [ctx+0x10c8] / [ctx+0x1128]
```

**寄存器号完全相同（`0x800000ba`），遍历逻辑相同，缓存位置只差 0x60。**

### 4.5 MMIO 读实现也逐字节同构

**515 `0xfbc490`**：
```asm
mov %esi,%eax ; shl $0x4,%eax ; and $0xe0000000,%esi
mov 0x1520(%rdi),%rdx ; add 0x58(%rdx),%rax ; mov (%rax),%eax
```

**525 `0x1575990`**：同样 `shl $0x4`、同样 `mov (%rax),%eax`，只有 BAR 结构偏移差 0x28。

**⇒ 从 bit0 判断、慢路径、到 MMIO 读的每一条指令，两版都是同一份代码。**

## 5. 那 24 倍差在哪：rp 追赶速度

| | 515 | 525 | 倍数 |
|---|---|---|---|
| 每次预留的循环圈数 | **3,162** | **92,564** | **29×** |
| 单价 | 1.177 µs | 1.177 µs | 1× |
| 每帧总等待 | 3.7 ms | 109 ms | 29× |
| **rp 前进 3 个单位需要读几次** | **~1,054** | **~30,855** | **29×** |

**同样的判据、同样的落后 5 个单位、同样的 MMIO 读同一条命令，525 要读 29 倍多次才能等到 rp 前进 3 个单位。**

**⇒ 只能是一个原因：525 那条命令流被 GPU 消费的速度慢 29 倍。**

**但 W 增量相同（提交量相同），这是矛盾。**

**⇒ 唯一自洽的解释：525 提交的不是"同样内容的命令流"，而是"同样的位置推进量、但每条命令更重/含同步点"。**

**W 只是"提交位置"，不反映"命令内容"。这一点我无法从用户态再往下确证。**

## 6. 诚实的边界

**我已经把 glcore 用户态能提供的信息用尽了。**

用户态代码层面，515 与 525 在整条"取 rp → 判断 → 等待"链路上**完全相同**：
- 同样的 bit0=0
- 同样的慢路径（MMIO 读 0x800000ba）
- 同样的 MMIO 读实现
- 同样的判据（gap=5 vs W-sz=2）
- 同样的提交量（W 增量）

**差异一定在下面两层之一：**

| 层 | 需要什么手段 | 预期能查到什么 |
|---|---|---|
| **pushbuffer 内容** | 抓 `[ctx+0x1128]` 缓冲区，反解命令序列 | 525 是否插入了额外的同步/fence 命令 |
| **内核驱动** | 看 `nvidia.ko` 的 fence/notify 逻辑 | GPU 写完为什么更新 rp 慢 29 倍 |

**这是我能给出的最远结论。再往下不靠猜是做不到的。**

## 8. 一句话

**五个候选全部实测排除：提交量、批次数、判据、rp 落后量、取 rp 路径 —— 515 和 525 一模一样，连每条指令都同构。**
**唯一剩下的差异是：rp 前进 3 个单位，515 只要读 1,054 次，525 要读 30,855 次。**
**⇒ 差在"525 提交的命令流被 GPU 消化的速度"，不在 glcore 用户态。**
**另外你那个 7W 的观察很关键：注入版不是"一直快 59 fps"，是先快一下然后彻底挂起 —— 我报告里那个数字只代表出错初期。**
