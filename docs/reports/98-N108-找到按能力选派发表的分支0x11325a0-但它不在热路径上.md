## 1. 先排掉一条死路：设备 ID 立即数

`.text`（`0x2fc000`–`0x1952ee1`，vaddr==offset）内搜 `0x1C07`（P106-100 的 device ID）：

| 偏移 | 前 2 字节 | 判定 |
|---|---|---|
| `0x36c9ec` | `e8 a1` | `call rel32` 位移 → **假** |
| `0x36c9fa` | `e8 33` | `call rel32` 位移 → **假** |
| `0x3b0ca5` | `0f 84` | `je rel32` 位移 → **假** |
| `0x73acf5` | `0f 87` | `ja rel32` 位移 → **假** |
| `0x7437a0` | `0f 84` | `je rel32` 位移 → **假** |
| `0x107811e` / `0x1078161` / `0x10781a1` / `0x1078612` / `0x1078652` | `e9 xx` | `jmp rel32` 位移 → **假** |
| `0x3c12b5` | `48 8d 0d` | `lea rcx,[rip+0x15a1c07]` → **假**（0x15a**1c07** 是位移）|
| `0x3d133d` | `48 8d 35` | 同上 → **假** |
| `0xb9f295` | `e8 07` | `call rel32` 位移 → **假** |
| `0x10cadd8` / `0x125e846` / `0x125e98b` | `8d 44` | `lea` 位移 → **假** |
| `0x1617be2` / `0x19075f3` | — | 非指令边界 → **假** |
| **`0xe12782`** | `be 07 1c 00 00` | **`mov esi,0x1c07`** ← **唯一真立即数** |

`0xe12780` 处：
```asm
e12780: push rbp
e12781: mov  esi,0x1c07          ; ★ 作为参数传给下面的调用
e12786: mov  rbp,rdi
e12789: call e02c40
e1278e: mov  esi,[rbp+0x4]
```
**这是一个把 `0x1c07` 当参数传的函数**，不是"设备 ID 分支"。

**⇒ 设备 ID 不是以立即数形式出现在比较里。** 它在运行时从内核读（glcore 只有 8 处 `call ioctl@plt`，
且附近没有 `mov reg,imm32` 形式的 NV_ESC 命令号 —— 说明 GPU 信息的获取经 `libnvidia-glsi`，
或者命令号是动态算的）。**按立即数搜设备 ID 这条路基本可以放弃。**

## 2. 真正的发现：8 份派发表 + 一个选择器

### 2.1 8 份派发表在 `.data.rel.ro`

沿用报告 71 的脚本（`n80b_runs.py`，在 `R_X86_64_RELATIVE` 重定位里切连续 8 字节块）：

```
run#0: start=0x29e7800  n=1977  span=0x3dc8
run#1: start=0x29eb5e0  n=1977  span=0x3dc8
run#2: start=0x29ef3c0  n=1977  span=0x3dc8
run#3: start=0x29f31a0  ...
run#4: start=0x29f6f80
run#5: start=0x29fad60
run#6: start=0x29feb40
run#7: start=0x2a02920
```

**8 份 × 1977 项，间隔 `0x3de0`（每份 1977×8 = 0x3dc8，加对齐）。**

### 2.2 在 `.text` 里搜"谁引用这些表基址"

结果（RIP-relative `lea`/`mov` 且位移正好指向表首）：

| 表 | 引用数 | 引用位置 |
|---|---|---|
| `0x29eb5e0`（#1） | 1 | `0x11325c0` |
| `0x29ef3c0`（#2） | 2 | `0x11325b8`、`0x123c46a` |
| `0x29feb40`（#5） | 1 | `0x12e2339` |
| `0x2a02920`（#7） | 5 | `0x12df718`、`0x12dfad9`、`0x12dfcc5`、`0x136a788`、`0x1632b6d` |

**`0x11325b8` 与 `0x11325c0` 相隔 8 字节，分别指向 #2 和 #1 —— 这就是一个二选一。**

### 2.3 选择器本体（`0x11325a0`）

```asm
11325a0: test   rdi,rdi
11325a3: je     11325b8                  ; rdi == NULL → 默认
11325a5: mov    rax,QWORD PTR [rdi]      ; rax = *rdi（内层对象）
11325a8: test   rax,rax
11325ab: je     11325b8
11325ad: movzx  eax,BYTE PTR [rax+0x5c]  ; ★ 读能力/标志字节
11325b1: and    eax,0x21                 ; ★ mask = bit0 | bit5
11325b4: cmp    al,0x1                   ; ★ 等于 1（bit0 置位 且 bit5 清零）
11325b6: je     11325c0
11325b8: lea    rax,[rip+0x18bce01]      ; → 0x29ef3c0（表 #2，默认）
11325bf: ret
11325c0: lea    rax,[rip+0x18b9019]      ; → 0x29eb5e0（表 #1，能力满足）
11325c7: ret
```

**这是一个干净的"按能力选派发表"函数：**
- 判据 = `(*(uint8_t*)(obj + 0x5c)) & 0x21 == 1`
- 满足 → **表 #1**；否则 → **表 #2**

### 2.4 两份表的差别：**全部 1977 槽都不同**，而且差在"间接层级"

```
两份表在 1977 个槽中，有 1977 个槽指向不同实现（100%）
```

**表 #2 的目标（如 `0x2db0e0`，在 `.nvtext` 段）**：
```asm
2db0e0: lea  rax,[rip+0x27936d9]     # 2a6e7c0 <_nv025glcore>
2db0e7: mov  rax,[rax+0x10]          ; 取全局字段
2db0eb: add  rax,fs:0x0              ; 加 TLS 偏移
2db0f4: mov  rax,[rax]               ; 再解一次
2db0f7: jmp  QWORD PTR [rax]         ; ★ 两级间接，跳 [rax+0]
```

**表 #1 的目标（如 `0x1378450`，在 `.text`）**：
```asm
1378450: mov  rax,[rip+0x1653c09]    # 29cc060 <_nv001tls>
1378457: mov  rax,fs:[rax]           ; 取 TLS 上下文
137845b: jmp  QWORD PTR [rax+0xbba8] ; ★ 一级间接，每函数固定偏移
```

**⇒ 表 #2 走"两级间接 + 每次多读一个全局"，表 #1 走"一级间接"。**
这是一个**真实的、按运行时标志选择的、代价不同的两条派发路径。**

## 3. 运行中 attach 抓不到它（后来补做启动挂，见 §3bis）

用 gdb 在 `glcore+0x11325a0` 下断点，跑 `n83a -M 3 -n 500`（重负载，8 秒）：

```
glcore base = 0x7f8353400000
=== 命中记录 ===
（空）
```

**命中 0 次。**

⇒ **这个选择器在我们的渲染负载里从未被调用。**
它更可能是**上下文/配置档初始化时**调用一次（决定整个 context 用哪套派发表），
之后所有 GL 调用直接 `jmp [table + slot*8]`，不再经过选择器。

**这带来两个后果：**
1. **"谁选了哪套表"这件事在初始化时就定了** —— 与 `nv_get_hypervisor_type` 缓存在字段里是同一种设计模式（报告 97）。
2. **想验证它对性能有没有影响，必须在"创建 context 之前"就 hook，而不是运行中 hook**（我这次是运行中 attach，抓不到）。

## 3bis. 补做：从启动就挂 gdb，抓到了实际选择 + 强制切换会崩

报告初稿写"运行中 attach 命中 0 次"。**补做 `gdb --args` 从启动挂断点后，抓到了 1 次命中**，
并且做了一次强制切换实验。结果比预期更有信息量。

### 3bis.1 物理机上实际选的是**表 #2**

```
GLCO-BASE=0x7ffff4a00000  SELECTOR=0x7ffff5b325a0
HIT
  inner=0x55555572c050
  b5c=0x00   and21=0x00        ← 不等于 1
```

`(0x00 & 0x21) == 0 ≠ 1` ⇒ **走默认分支 ⇒ 表 #2（两级间接，`.nvtext`）**。

**⇒ 物理机 + 525 上，GL 派发走的是"两级间接"那一套。**
（这条是事实，不是推断。）

### 3bis.2 强制切到表 #1 → **SIGSEGV**

gdb 里把 `rax` 改成表 #1 的地址、`pc` 设为该函数的 `ret`，让选择器"返回表 #1"：

```gdb
break *0x7ffff5b325a0
commands
  silent
  set $rax = 0x7ffff73b5e0     # 表#1（一级间接）
  set $pc  = 0x7ffff5b325bf     # 该函数的 ret
  continue
end
```

结果：

```
Breakpoint 2 at 0x7ffff5b325a0
Program received signal SIGSEGV, Segmentation fault.
0x00007ffff7f675e9 in glGetString ()
```

**崩溃发生在 `glGetString` 里。**

⇒ **两套表不是"同一件事的两种实现"，不能互换。**
它们对应**两类不同的对象/模式**，选错的那套会让派发指向不适用于当前模式的实现。

**这直接改变了对这个分支的解释：**

| 我原来的猜测 | 实测结论 |
|---|---|
| 表#1=快路径、表#2=慢路径，有可能通过切换提速 | ❌ **错**。互换会崩溃 ⇒ 不是性能开关，是**类型/模式判别** |

`[obj+0x5c] & 0x21` 更可能区分的是：
- core profile vs compatibility profile；
- 或 direct rendering vs indirect rendering；
- 或 客户端 context vs 服务端 context。

**不管哪一种，它都不是"按 GPU 设备 ID 选快慢路径"的开关。**

### 3bis.3 由此得到的确定结论

**用户问的那个"按 GPU 设备 ID / 能力 选提交路径"的分支：**

- ✅ **存在一个按能力选派发表的分支**（`0x11325a0`，判据 `[obj+0x5c] & 0x21`）
- ✅ **物理机 525 上走表 #2**
- ❌ **它不是性能开关**（强制切另一套直接崩）
- ❌ **`[obj+0x5c]` 的位是否来自 GPU 设备 ID，仍未证明**

**⇒ 这条线索到此为止，继续挖它的性价比很低。**

## 4. 尚未证明的关键一环

用户的问题是「**GPU 设备 ID / 能力** 选提交路径」。本轮只证明了：

- ✅ 存在"按能力选派发表"的分支（`[obj+0x5c] & 0x21`）
- ✅ 两套表的派发代价不同（一级 vs 两级间接）
- ❌ **没证明 `[obj+0x5c]` 的那些位来自 GPU 设备 ID / 架构**

要补这一环，必须找到 `[obj+0x5c]` 的写入点并回溯到 GPU 信息。本轮搜了 `mov byte [reg+0x5c], imm` 的 12 种形态，

工作量很大且容易误判（`+0x5c` 在不同结构体里含义完全不同）。

## 7. 教训（已入技能库）

1. **★★★ 立即数搜设备 ID / 特征值，命中里绝大多数是位移字节。**
   `0x1C07` 19 处命中里 18 处是 `call/jmp/jcc rel32` 或 `lea [rip+disp]` 的位移。
   **判据**：看命中前 2 字节 —— `0f 80..8f`（Jcc）、`e8`（call）、`e9`（jmp）、`8d XX`（lea）
   都是位移；只有 `b8..bf`（mov reg,imm32）之类的才是真立即数。
2. **★★ 找"按能力分叉"不要去搜值，要搜"表基址的引用"。**
   能力值来自运行时（PCI config / ioctl），不会以立即数出现；
   但**"选哪张表"一定体现为"代码里出现多个表基址，且相邻出现"**。
   本例 `0x11325b8` 与 `0x11325c0` 相隔 8 字节分别指向两张表 —— 这就是分叉点的指纹。
3. **★★★ 断点命中 0 次 ≠ 机制不存在，而是"它在初始化阶段"。**
   本例选择器在 context 创建时调用一次，运行中 attach 抓不到。
   **判据**：改派发表这种"全局配置"的东西，几乎一定是**初始化时决定一次**。
   **正确做法：`gdb --args` 从进程启动就挂，而不是 `-p` attach 到运行中的进程。**
4. **★ 两套派发表"全部槽都不同"时，看它们的**目标在哪个段**比逐个比对更有信息量。**
   本例：一套指向 `.text`（一级间接），一套指向 `.nvtext`（两级间接）——
   **段的位置本身就说明了"这是两类不同性质的实现"**。
