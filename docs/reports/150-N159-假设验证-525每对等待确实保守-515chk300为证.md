## 0. 三个结论

1. **你的判断成立。** 515 每帧只等 **6.7 次**，得到 `chk=300`（与 525 完全相同的正确画面）；
   525 每帧等 **19,181 次**，也是 `chk=300`。**同样的正确性，2,863 倍的等待次数。**
2. **你担心的"覆盖未消费命令"没有发生。** 实测 `wp - rp = 6`（流水窗口很浅但没满），
   切断等待后 **无 Xid、GPU 状态正常**。`chk=0` 的原因不是覆盖，是"回读时 GPU 还没画完"。
3. **同时也证明"完全不等"不行**：切断后 `chk=0`。所以最优解在中间——
   **6.7 ~ 19,181 之间存在一个既正确又快的点，而 515 就在那个点上。**

## 2. 你担心的风险：实测没有发生

### 2.1 流水窗口有多深

在 525 的退避入口 `0x15782d8` 下硬件断点，采样 25 次，
**25 个样本完全一致**：

```
req (r12)     = 154   ← 请求 GPU 消费到这个位置
rp  (rbx)     = 150   ← GPU 实际消费到
wp  (0x1130)  = 156   ← CPU 已提交到
```

于是：

| 量 | 值 | 含义 |
|---|---|---|
| `wp - rp` | **6** | 未消费的只有 6 个位置 |
| `req - rp` | **4** | 距离目标的差距是 4 |
| `wp - req` | **2** | 请求点离写指针只有 2 |

**25 次采样一模一样，说明这是个稳态：CPU 最多只领先 GPU 6 个位置。**

### 2.2 切断等待后没有 Xid

补丁：`0x157830c: 77 ca`（`ja` 回循环）→ `90 90`（不重试，直接返回）

结果：

```
[patchpb] 0x157830c  原文 77ca  ->  9090   [已改写]
total_p50 = 1.998 ms   fps = 500.61   chk = 0
```

`dmesg` 检查：

```
NVRM: loading NVIDIA UNIX x86_64 Kernel Module  525.116.03
[drm] Initialized nvidia-drm 0.0.0 ... on minor 1
（无任何 Xid）
```

`nvidia-smi`：`36.09 W, 1911 MHz`，模块正常。

**⇒ 覆盖未消费命令的事没有发生。** 原因就是 §2.1 的窗口只有 6，
即使不等，接下来要写的量也远小于"6 之外还有多少空位"。

### 2.3 那 `chk=0` 是怎么来的

不是数据被覆盖，而是**回读时 GPU 还没算完**：

`map_p50` 从基线 **125.8 ms** 掉到 **0.001 ms** —— `glMapBuffer` 立即返回，
PBO 里还是空的，所以 `chk=0`。

**⇒ 这个函数的真实作用是"节流阀"，不是"防溢出的护栏"。**

这是本轮最重要的认知修正：

| 原来的理解 | 实测 |
|---|---|
| 等是因为"pushbuffer 空间不够，不等会覆盖" | **空间够（窗口 6，没满）；等是为了让 CPU 不要跑太快** |
| 不等 → 覆盖 → Xid | **不等 → 无 Xid，但回读读到空** |

## 3. 所以"保守"体现在哪：窗口深度

把三个配置画成流水线深度：

```
515：CPU 可以领先 GPU 很多（每帧只同步 6.7 次）→ GPU 一直有活干 → 5~7 ms
525：CPU 只能领先 GPU 6 个位置 → 每对都要同步 → GPU 反复饿肚子 → 127 ms
```

**这解释了报告 147 那个最反直觉的数据：**

> M3 时 GPU 功耗只有 37.42 W（≈ 空闲 36.28 W），而 M1 是 52.84 W。

因为 525 每次提交后立刻等，**等的时候 CPU 不提交新命令，GPU 就把手里那点活干完然后空转**。
功耗低不是"GPU 没算"，而是"GPU 没活可干"——**被 CPU 的节流卡住了**。

形成恶性循环：

```
每对等 GPU → CPU 停手 → GPU 干完手头的就空转 → 消费更慢 → CPU 等更久 → 更慢
```

而 515 正好相反：不等 → CPU 持续喂 → GPU 连续执行 → 消费快 → 更少需要等。

**同一个循环，两个方向，18 倍差距。**

## 4. 调用结构：数量相近，频率差 1000 倍

`0x1578280` 这个"等空间"函数通过函数指针调用，被装在 **`[ctx+0x1aa0]`**：

```asm
14c7a94  mov  [rsi+0x1a90], edx
14c7a9a  lea  rdx,[rip+0xb07df]      ; = 0x1578280
14c7aa1  mov  [r14+0x1aa0], rdx      ; ← 装进槽位
```

两版对照：

| | 槽位 | `call [ctx+槽位]` 的调用点数量 |
|---|---|---|
| 525 | `[ctx+0x1aa0]` | **10** |
| 515 | `[ctx+0x1a68]` | **8** |

**调用点数量相近（10 vs 8）。**

⇒ **不是"525 多了几条路径"，而是某一条路径被走了 1000 次/帧。**

这跟报告 149 的结论一致：515 上 13 个退避调用点里**只有 1 个活跃**（`0xfbede0`，6.7 次/帧）。
525 应该是某个点被 (绑定, draw) 循环反复触发。

**下一步就是把 525 那 10 个调用点逐个计数**（用 `bpcount`，1 秒窗口），
找出被走 ~1000 次/帧的那个点，再看它前面的门控条件。

### 7.1 修掉的三个工具 bug（都已写入 SKILL）

1. 原 `fielddump` 在 `PTRACE_DETACH` **之后**才读字段 → `GETREGS` 必然失败，

2. `ctx` 不一定在 `rdi`：在 `0x15782d8` 处 `ctx` 在 **`rbp`**（`mov rbp,rdi` 之后

3. 断点必须在**硬件执行断点**上，且要先做阳性对照（断已知高频函数），
   否则无法区分"函数没被调用"和"工具坏了"。

## 8. ⚠️ 重要自我更正：§4 的推理链有误

写完 §4 之后我继续验证，发现**"525 每对都调用等空间函数"这个说法是错的**。

### 8.1 实测频率

用硬件断点直接数两个函数的入口（`bpcount`，2 秒窗口，525 M3）：

| 函数 | 含义 | 频率 | 折算每帧 |
|---|---|---|---|
| `0x1578280` | **"等空间"**（装进 `[ctx+0x1aa0]`） | **8 次/秒** | **≈ 1 次/帧** |
| `0x1572e60` | **"取 rp"**（装进 `[ctx+0x1a98]`） | **187,896 次/秒** | **≈ 23,876 次/帧** |

**"等空间"函数每帧只被调用 1 次，不是 1000 次。**

### 8.2 所以 §4 和 §3 的表述要改

| 原表述（错） | 更正后 |
|---|---|
| 525 每对 (绑定,draw) 都调用"等空间"函数 | 525 每帧只调用 **1 次**"等空间"函数 |
| 19,181 次 poll 来自等空间循环 | 23,876 次**取 rp** 来自**别处**（20 个调用点之一） |
| 瓶颈是"每次绑定后同步等 GPU" | 瓶颈是"**每写一条命令就要真读一次 rp**" |

### 8.3 但 §1~§3 的核心结论不受影响

仍然成立的部分（都有独立证据）：

- **515 chk=300 与 525 chk=300 完全一致**，而 515 每帧只等 6.7 次 ⇒ 525 的等待极度冗余
- **切断等待 → 无 Xid、`chk=0`** ⇒ 不是命令被覆盖，是回读时 GPU 没画完
- **`wp - rp = 6`（25 次采样一致）** ⇒ 流水窗口很浅，空间没满
- **帧时间 ≈ poll 次数 × 8 µs** 这个量级关系（报告 149）

### 8.4 更正后的病灶描述

```
525：写入每条 pushbuffer 命令时，都真读一次 BAR0 的 fence 寄存器（约 8 µs）
     ⇒ 每帧 2 万多次 × 8 µs ≈ 127 ms

515：同样写命令，但每帧只读 588 次 rp
     ⇒ 588 × 8 µs ≈ 5 ms
```

**⇒ 真正的问题是"取 rp 的调用频率"，而不是"等空间"。**

### 8.5 为什么这更符合所有观测

| 观测 | 用"每条命令都读 rp"解释 |
|---|---|
| 与分辨率无关 | 命令条数与分辨率关系不大 |
| 与对象类型无关 | 只要写命令就查空间 |
| M1（只 draw 不绑）快 | draw 批量提交，命令写入路径不同 |
| M8（1000 绑 + 1 draw）快 | 绑定本身不写命令 |
| 77% CPU 时间在 `sched_yield` | 读 rp 后发现不够，就退避等 |
| GPU 功耗只有 +1.1 W | CPU 在等/读，GPU 没活干 |
| 515 每帧只 588 次 | 515 用缓存/批量，不逐条读 |

### 8.6 下一步（修正后）

**目标改成：找出 20 个 `call [ctx+0x1a98]` 里被调用最频繁的那个。**

难点：`bpcount` 对高频函数会限速（`ptrace` 往返开销），拿不到真实比值。
两个可行办法：

1. **静态对比**：把 525 的 20 个调用点与 515 的 17 个调用点按上下文配对，
   找出"525 有、515 没有"或"在同一函数里 525 多一次"的位置
2. **栈采样**：在 `0x1572e60` 入口高频采样（不是断点），统计 `[rsp]` 的返回地址分布

方法 2 不需要断点，不改变行为，是下一步首选。

### 8.7 本轮工具的一个坑（新增）

`bpcount` 原来在"未命中"时 `usleep(300)`，导致**上限只有约 3,300 次/秒**。
我第一次测出 `0x1572e60 = 2,613 次/秒`，差点当成真实值。
改成 `sched_yield()` 后同一函数测出 187,896 次/秒（仍是被限速的下界）。

**纪律：任何"计数"工具都必须先测自己的饱和上限**（拿一个已知最高频的目标打满它），
否则会把工具的上限误当成被测对象的频率。

## 9. 静态配对：找到了最可疑的函数（3 个取 rp vs 1 个）

`bpcount` 对高频函数会限速，拿不到 20 个调用点的真实比值。
于是改用**静态配对**：把每个调用点换算成"所属函数 + 函数内偏移"，
按（函数长度, 偏移）在两版之间对齐。

### 9.1 配对结果

| 525 函数 | 长度 | 取 rp 调用点（函数内偏移） | 515 对应函数 | 长度 | 取 rp 偏移 |
|---|---|---|---|---|---|
| `0x1578280` | 208 B | 0x1c, 0x68, 0xb9 | `0xfbed80` | 208 B | 0x1c, 0x68, 0xb9 ✓ **全同** |
| — | 112 B | 0x1f | — | 112 B | 0x1f ✓ **全同** |
| — | 32 B | 0x4 | — | 32 B | 0x4 ✓ **全同** |
| — | 256 B | 0x2b | — | 256 B | 0x2b ✓ **全同** |
| — | 160 B | 0x4b | — | 160 B | 0x53（差 8） |
| — | 384 B | 0xf1, 0x120 | — | 368 B | 0xe1, 0x110（差 0x10） |
| — | 1120 B | 0x1eb | — | 1104 B | 0x1e5 |
| **`0x1456940`** | **1616 B** | **0x196, 0x47f, 0x513** | **`0xea2510`** | **1472 B** | **仅 0x4c8** |

**最后一行是唯一的显著结构差异：同样功能的函数，525 里有 3 个取 rp 调用点，
515 里只有 1 个。**

而且 525 的退避调用点 `0x1456e4a`（偏移 0x50a）**也在这个函数里**，
515 的退避点 `0xea29d0`（偏移 0x4c0）同样在对应函数里。
⇒ 这个函数确实是"写命令 + 查空间 + 不够就退避"的主路径。

### 9.2 这个函数是什么

`0x1456940`（1616 B）的开头：

```asm
1456940  push r15/r14/r13/r12/rbp/rbx; sub rsp,0x38
1456951  rbx = 0x2a71780 (一个全局表)
1456958  al = [rbx+0xeb0]                    ; 某开关
1456963  [rbx+0xea4] += 1                    ; 计数器
1456972  if ([rbx+0xeac] > 1) {
1456990      call [0x2a6ec20 + 0x10]         ; 回调
14569a0      [rbx+0x30] += ...
14569aa      call [0x2a6ec10]
14569ac      [rbx] += 1                     ; 计数器
14569b7      [rbx+0x40] = rdx
         }
14569bb  r12d = [rbp+0x9e4]                 ; ctx 字段
14569c5  if (r12d != 0) goto 0x1456d40
```

开头一大段**统计/计数**（`[rbx+0xea4]++`、`[rbx]++`、`[rbx+0x30]`、`[rbx+0x40]`），
像"绘制调用统一入口 + 计时埋点"。

**还没读到 3 个取 rp 那三段的上下文**（分别在 0x196 / 0x47f / 0x513，
即 `0x1456ad6` / `0x1456dbf` / `0x1456e53`），这是下一步最该看的地方。

### 9.3 下一步（下一步唯一该做的事）

反汇编 `0x1456ad6`、`0x1456dbf`、`0x1456e53` 三处各自的**前 20 条指令**，
看它们分别在什么条件下触发：

- 若其中某一个是"每写一条命令都过"，就是 2 万次/帧的来源

同时对比 515 的 `0xea2510` 里唯一的那个调用点（偏移 0x4c8）的上下文，
看 515 为什么只需要查一次。

**这一步纯静态，不需要上机，可以立刻做。**

## 10. 本轮净结论（去掉被自我否证的部分）

**成立：**

1. **515 用 6.7 次等待/帧拿到 `chk=300`，与 525 的 19,181 次完全相同** ⇒ 525 的等待冗余 2,863 倍

## 11. ⚠️ 第二次自我更正：§9 的"3 个调用点"和"次数×8µs"都有问题

### 11.1 三个调用点是互斥分支，不是"查 3 次"

反汇编 `0x1456ad6` 与 `0x1456dbf` 的上下文：

```asm
1456aba  cmp  r13, rcx
1456abf  r15 = [r13 + rax*8 + 0x6cf8]      ; 从数组取一个对象
1456ac7  je   1456dbb                      ; ← 相等就跳到另一条路
1456ad2  rdi = r13
1456ad5  call [r13+0x1a98]                 ; 分支 A：取 rp

1456dbb  rdi = r13                          ; ← je 跳到这里
1456dbe  call [r13+0x1a98]                 ; 分支 B：取 rp（同一逻辑的 else）
```

**这两处是 `if/else` 的两条互斥分支，一次执行只走一条。**

所以我不能因为"525 这个函数有 3 个调用点、515 只有 1 个"就说 525 多查了几次。
**§9 的推理作废。** 那个函数（`0x1456940` / `0xea2510`）仍需对比，
但必须逐分支看，不能数调用点个数。

### 11.2 更严重：「次数 × 8 µs」这个验证是循环论证

报告 149 里我算"每帧次数"用的是：

```
每帧次数 = (bpcount 测到的 次/秒) ÷ (无干扰运行时的 fps)
```

**问题**：`bpcount` 用 ptrace 在每次函数调用时打断目标进程，这会**显著降低 fps**。
而我除的是**没有 bpcount 干扰时的 fps**。

两个数来自不同条件，相除没有意义。

所以：

| 数据 | 状态 |
|---|---|
| `0x1578280` = 8 次/秒 | **可信**（远低于工具上限，且干扰极小） |
| `0x1572e60` = 187,896 次/秒 | **只能当下界**（受 ptrace 往返限速） |
| "19,181 次/帧 / 23,876 次/帧" | **不可信**（分母用了无干扰 fps） |
| "次数 × 8 µs ≈ 实测总时间" | **循环论证，不能作为证据** |

报告 149 的"帧时间 ≈ poll 次数 × 8 µs"这个漂亮模型，**目前没有站得住的证据支撑**。

### 11.3 但以下结论是干净的无干扰测量，仍然成立

| 结论 | 为什么干净 |
|---|---|
| 515 M3 `chk=300`，与 525 相同 | 直接读回读数据，无探针 |
| 515 M3 = 7.5 ms / 525 M3 = 127 ms | 程序自报计时，无探针 |
| 切断等待 → `chk=0`、无 Xid | 只有一次字节补丁，无 ptrace |
| `wp - rp = 6`（25 次一致） | **有 ptrace 干扰，但读的是内存快照，不改变逻辑** |
| `req > rp`（确实没追上） | 同上 |
| 两版 fence 读取代码逐条同构 | 纯静态 |
| 运行时标志两版相同（缓存关、1 引擎） | 内存快照 |

**最硬的一条仍然是：515 每帧只 6.7 次等待（8 次/秒这个数是可信的），
却拿到与 525 完全一致的 `chk=300`。**
⇒ **525 的等待次数确实极度冗余，你的判断成立。**

### 11.4 要拿到可信的"每帧次数"，正确做法

| 方法 | 说明 |
|---|---|
| **同时测 fps 和次数** | bpcount 运行期间自己数 swap 次数（uprobe 或读进程计数器），不要用外部 fps |
| **用 CPU 时间归因代替计数** | `perf`/`ptrace` 采样，算某函数占用 CPU 时间的比例（不受限速影响） |
| **降低探针密度** | 只在函数入口采样（rpsample2 那样随机采），不每次打断 |
| **静态数循环** | 找到"每写一条命令就查一次"的那层循环，直接数代码结构 |

**我倾向于第四条**：静态上把 `0x1456940` 的完整控制流画出来，
找出它被"每条命令"调用还是"每帧"调用——这不需要任何探针。

### 11.5 一条方法论教训（已写入 SKILL）

> **任何用 ptrace 断点做的"计数"，都不能除以"无干扰条件下的 fps"。**
> 探针会把被测对象拖慢几倍到几十倍，两个数不在同一条件下，相除得到的是噪声。
> 要么在同一条件下同时测两者，要么改用"时间占比"而非"次数"。

这一条我连犯两次（报告 149 的 19,181、本报告的 23,876），
都是先算出漂亮数字、再去找解释。顺序反了。
