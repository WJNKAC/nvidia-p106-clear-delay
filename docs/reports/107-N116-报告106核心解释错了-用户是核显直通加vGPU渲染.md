## 0. 先认错

**报告 106 的核心解释是错的，而且是"没读证据就推机制"这个老毛病。**

我在报告 106 里写：

> vGPU 里 guest 看到的是一个**完整的虚拟 GPU**，它自己就是显示拥有者（虚拟 CRTC），
> present 就是把帧写进自己的 framebuffer，完成事件**立即**由虚拟驱动返回，不等任何物理合成器。

**这个"虚拟 CRTC 自己输出"的推理没有任何证据支撑，而且与用户的实际情况相反。**

## 2. ★★★ 6016MiB：这是本轮最重要的新事实

**`646.0MiB / 6016MiB` —— 这个实例拿到了整张卡的 6GB 显存。**

而 `GRID P40-2B` 这个 profile 名里的 **`2B` 表示 2GB 帧缓存、图形类**。
如果真是标准的 P40-2B，这里应该显示 `/ 2048MiB`（或按 profileSize 切分后的值）。

**⇒ 实际形态是：借 `GRID P40-2B` 的 type id 与名字，但 profileSize 被 override 成整卡。**
这正是 `vgpu_unlock` 的做法：**伪造 device id / vGPU type 让它通过校验，然后自行指定 profile 参数**。

这解释了报告 99 那个谜：
> "P106(0x1c07) 在 vGPU 类型表里出现 0 次 ⇒ 必须伪装成 P40"

**伪装的代价是"名字变成 P40-2B"，但显存是 6016MiB 而不是 2048MiB ⇒ 参数是改过的。**
所以**不能用 `GRID P40-2B` 这个名字去反推它的 vGPU 配置**（我报告 106 §1 之前就想这么干，幸好没写进去）。

### 2.1 `Disp.A: Off` 意味着什么

`Disp.A` = Display Active。它 **Off** 说明：**这个 vGPU 实例当前没有驱动任何显示输出。**

配合用户说的"核显输出"：
- **P106（vGPU 实例）：只渲染，不输出**
- **核显（直通）：输出**

**⇒ 和真机的 `card1`(nvidia, 0 connector) + `card0`(i915, HDMI) 结构完全同构。**

**⇒ "present 语义不同"这个解释彻底不成立。**

## 4. 既然 present 一样，那差别只能在提交层

真机与 vGPU 的同构部分（都被我之前的框架误判为"差异"）：

| | 真机 | vGPU（用户实际配置） |
|---|---|---|
| 渲染卡有无连接器 | 无（`Display Mode: Disabled`，0 connector） | 无（`Disp.A: Off`） |
| 谁输出 | 核显 i915 | **核显（直通）** |
| present 是否跨设备 | **是** | **是** |
| 合成器 | KWin + Xwayland | 无（Xorg 直出 + X11 forwarding） |

**⇒ present 层不是真机与 vGPU 的差异所在。报告 106 的核心论点作废。**

那剩下的差异只能是**提交层**，也就是报告 78/79 测到的那 **118.5 µs/对**：

| 假说 | 为什么可信 | 怎么验 |
|---|---|---|
| **H1：vGPU 的 MMIO 被宿主代理，可以合批/异步化** | guest 的每次寄存器写都要 VM exit，宿主聚合后批量下发，**批次开始的固定代价（引擎 re-arming）被摊掉** | vGPU 里跑 `n83a -M 1/-M 3`，看是否 ≈0.03µs |
| **H2：vGPU guest 驱动是精简版，提交路径不同** | 报告 95 已证 GL/Vulkan 都汇合在 glcore，但 **glcore 的提交器可能读 vGPU 标志走另一分支** | 对比 guest 版 glcore 与物理版 glcore 的 hash/提交器反汇编 |
| **H3：550 本身修了病 B** | 550 从未在物理机上测过 121µs | 装 550 到真机跑 `n83a -M 3` |

**H3 是有历史依据的**：报告 96 发现 `LOGVGPU` 是 515→525 新增，而用户截图是 **550.90.07**。
但 525/535/570 在 vGPU 下都不回退（用户最早的观察）⇒ **不能简单归因到版本**。
**⇒ H1/H2 更可能，H3 需要单独实验排除。**

## 5. 我还欠一个直接证据：Xorg vs Xwayland

真机现在跑的是 **KWin + Xwayland（合成器路径）**；用户的 VM 跑的是 **Xorg 直出 + X11 forwarding**。

这两者的 present 路径不同：
- **Xwayland + KWin**：应用 present → Xwayland → KWin 合成 → i915 KMS
- **Xorg 直出**：应用 present → Xorg →（如果 P106 没有 CRTC，仍要拷给核显）

**后者少一跳（没有独立合成器进程），而且 X11 forwarding 场景下 Xorg 可能走"软件读回"而不是 DMA-BUF。**

**这是一个可以立刻在真机上验证的对照**：真机也有一个跑着的 Xorg `:0`（vt2/sddm，Intel 输出）。
在 `:0` 上跑 vkmark，看帧率是否比 `:1`（Xwayland）高。

**如果 `:0` 也慢 ⇒ 排除"Xwayland/KWin 合成器"这个因素，H1/H2 更确定。**
**如果 `:0` 快 ⇒ 那就是合成器路径的问题，与 vGPU 无关。**

这条实验零成本（不需要换驱动、不需要重启），应该立刻做。
