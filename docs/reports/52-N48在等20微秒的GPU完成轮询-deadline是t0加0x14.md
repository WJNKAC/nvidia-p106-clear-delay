# 52 · N48：`0x15761b0` 在等的是"**20 微秒的 GPU 完成轮询**"—— deadline 是 `t0 + 0x14`

> 2026-10-26 08:40
> 承报告 51：栈显示 glcore 在 `0x15761b0` 做有界自旋（`9×pause + 取时 + 比 deadline`）。
> 本轮读出 deadline 的来源，并查明三个 vtable 槽的真实实现。
>
> **答案：`deadline = t0 + 0x14`（20 微秒）。**
> 而 `t0` 来自一个**真正的时钟**（`146d240`，微秒精度）。
> **这不是"超时上限"，是"20 微秒内没等到就 `sched_yield` 让出"** —— 也就是一个**极短的 GPU 完成轮询**。

---

## 1. 结论

| # | 结论 | 证据 |
|---|---|---|
| 1 | **deadline = `t0 + 0x14`（20 µs）** | `15761e6: lea 0x14(%rax),%r12` |
| 2 | `t0` 来自真时钟，**微秒精度** | `*0x290 → 0x146d240`：`call 1467690` + magic `0x20c49ba5e353f7cf`（÷1000） |
| 3 | **`*0x280` / `*0x288` / `*0x290` 在运行时都不是默认桩** | 静态默认是 `0x380b90/0x37e8d0/0x37c160`（全是 `ret 0/1`）；**运行时实测是 `0x146c860/0x146cc80/0x146d240`** |
| 4 | `*0x280` = `146c860`：**设 `type=0` 并转给 `*0x288`** | `movl $0x0,0xc(%rsp)` → `call *0x288(%rax)` |
| 5 | `*0x288` = `146cc80`：**按 `edi`（type 0-5）查跳转表分发**，含 `sched_yield` / `usleep(250)` / `usleep(1000)` | 跳转表 `0x1d3f140`（type）/ `0x1d3f158`（二级） |
| 6 | **所以那 98.8% 是"每 20µs 醒一次看 GPU 完成没，没完成就 `sched_yield`"** | 由 1-5 推出 |

**一句话**：**这是一个 20 微秒粒度的 GPU 完成轮询**，不是锁竞争，也不是"从未满足的阈值"。

## 2. deadline 的确切来源（`0x15761b0`）

```asm
15761b0: push %r14/r13/r12/rbp/rbx; sub $0x10,%rsp
15761b4: mov  %rdi,%r13                  ; r13 = 参数（对象指针）
15761c8: lea  0x...(%rip),%rbp           ; rbp = _nv014glcore（vtable 基址）
15761cf: mov  0x1300(%rdi),%rbx          ; rbx = obj+0x1300（某个子对象）
15761d6: movl $0x1,0x2c(%rdi)            ; obj+0x2c = 1（标记"正在等"）
15761dd: call *0x290(%rbp)               ; t0 = now_us()
15761e3: mov  %rax,%r14                  ; r14 = t0
15761e6: lea  0x14(%rax),%r12            ; ★ r12 = deadline = t0 + 20µs
15761ef: cmpl $0x1,0x2850(%rbx)          ; 子对象状态 == 1 ?
15761f6: je   1576260                    ;   是 → 走"已有超时值"分支
15761f8: mov  $0x3,%edi
15761fd: call *0x280(%rbp)               ; ★ 等待：type=3 → usleep(1000)
1576203: mov  %r14,%rbx
1576206: jmp  1576227
1576210: pause × 9                       ; 自旋
1576227: call *0x290(%rbp)               ; now = now_us()
157622d: cmp  %r12,%rax                  ; now >= deadline ?
1576230: jge  1576237                    ;   是 → 退出循环
1576232: cmp  %rax,%rbx
1576235: jl   1576210                    ;   否 → 继续 pause
1576237: sub  %r14,%rax                  ; elapsed = now - t0
157623f: cmovs %rdx,%rax                 ; 负值归零
1576248: add  %rax,0x6f88(%r13)          ; ★ 累加到 obj+0x6f88（统计总等待时长）
```

**这是"最多自旋 20µs，然后计入统计"的标准形态。**

### 2.1 另一条分支（`1576260`）：有"外部超时值"

```asm
1576260: mov  0x6fac(%r13),%eax          ; 某个计数
1576267: movl $0x17,0xc(%rsp)            ; 默认超时 = 0x17 (23)
1576273: mov  0x2854(%rbx),%eax          ; 子对象里的阈值
157627c: sub  0x6fb0(%r13),%rdx          ; elapsed = now - 某基准
1576283: cmp  %rax,%rdx
1576286: jl   1576292                    ; 未超阈值 → 用默认 0x17
1576288: mov  0x2858(%rbx),%eax          ; 超了 → 用子对象里的值
1576292: lea  0xc(%rsp),%rsi
1576297: mov  $0x3,%edi
157629c: call *0x288(%rbp)               ; type=3 + 超时值参数
15762a2: jmp  1576203                    ; ★ 这正是 bt 里 #1 = 0x15762a2 的落点
```

**`#1 = 0x15762a2` 就是这条分支的 `jmp`** → 说明运行时走的是"有外部超时值"这条路，
超时值 **默认 `0x17`（23）**，若超过 `0x2854(%rbx)` 阈值则用 `0x2858(%rbx)`。

## 3. 三个 vtable 槽：静态默认桩 vs 运行时真实现

静态初始化（`0x383f3b-0x383f6c`）把这三个槽指到**全是 `ret` 的桩**：

| 槽 | 静态默认 | 实现 |
|---|---|---|
| `*0x280` | `0x380b90` | `xor %eax,%eax; ret` → 返回 0 |
| `*0x288` | `0x37e8d0` | `xor %eax,%eax; ret` → 返回 0 |
| `*0x290` | `0x37c160` | `mov $0x1,%eax; ret` → 返回 1（**恒定！**） |

**运行时实测（`n48_vtable.sh`，读 `/proc/PID/mem`）：**

| 槽 | 运行时值 |
|---|---|
| `0x280` | **`0x146c860`** |
| `0x288` | **`0x146cc80`** |
| `0x290` | **`0x146d240`** |

**三个都被换成了真实现。** 这解释了为什么用默认桩推导会完全错：
若真用 `0x37c160`（返回 1），`t0 = 1`、`deadline = 0x15`，`now` 永远远大于它 → 循环一次都不转。

### 3.1 `*0x290` = `146d240`：微秒时钟

```asm
146d240: sub  $0x8,%rsp
146d244: call 1467690                    ; 取原始时间（ns 或 TSC）
146d24d: movabs $0x20c49ba5e353f7cf,%rdx  ; magic
146d257: mov  %rax,%rcx
146d25a: imul %rdx
146d25d: sar  $0x3f,%rcx
146d261: sar  $0x7,%rdx
146d265: mov  %rdx,%rax
146d268: sub  %rcx,%rax                  ; rax = raw / 1000  ⇒ 微秒
146d26b: ret
```

**magic `0x20c49ba5e353f7cf` + `sar $0x7`** = 除以 1000。
→ **`t0` 是微秒**，`deadline = t0 + 20` = **20 微秒后**。

### 3.2 `*0x280` = `146c860`：设 type=0 转发

```asm
146c860: sub  $0x18,%rsp
146c864: lea  _nv014glcore,%rax
146c86b: movl $0x0,0xc(%rsp)             ; ★ out 参数 = 0
146c873: lea  0xc(%rsp),%rsi
146c878: call *0x288(%rax)               ; 转发给 *0x288
146c87e: add  $0x18,%rsp
146c882: ret
```

### 3.3 `*0x288` = `146cc80`：按 type 分发的等待

```asm
146cc80: lea  0x29a3200,%rax             ; 全局对象
146cc87: mov  (%rax),%rcx
146cc8a: cmp  $0x5,%edi                  ; type > 5 ?
146cc8d: ja   146cca1
146cc8f: lea  0x1d3f140,%rdx             ; 一级跳转表
146cc98: movslq (%rdx,%rdi,4),%rax
146cc9c: add  %rdx,%rax
146cc9f: jmp  *%rax                      ; ← 按 type 分发
...
146cca1: mov  0x270(%rcx),%eax           ; 否则读全局对象里的 type
146cca7: cmp  $0x5,%eax
146ccaa: ja   146cd50
146ccb0: lea  0x1d3f158,%rdx             ; 二级跳转表
146ccbe: jmp  *%rax
```

**跳转表解出来的目标（`0x1d3f140` 相对偏移）：**

| type | 目标 | 动作 |
|---|---|---|
| 0 | `0x146cca1` | 读全局 type 再分发 |
| 1 | `0x146ccd0` | 读 `0x274(rcx)` 再分发 |
| 2 | `0x146cce0` | 读 `0x278(rcx)` 再分发 |
| 3 | `0x146ccf0` | 读 `0x27c(rcx)` 再分发 |
| 4 | `0x146cd00` | 读 `0x280(rcx)` 再分发 |
| 5 | `0x146ccc8` | 读 `0x284(rcx)` 再分发 |

**二级表里的实际行动（`146ccc0` 起）：**

```asm
146ccc0: jmp sched_yield@plt             ; ← 这就是 bt 的 #0
146cd10: test %rsi,%rsi ; je 146ccc0     ; 无参数 → sched_yield
146cd15: mov (%rsi),%edi ; jmp usleep@plt ; 有参数 → usleep(值)
146cd20: mov $0xfa,%edi ; jmp usleep@plt  ; usleep(250)
146cd30: mov $0x3e8,%edi ; jmp usleep@plt ; usleep(1000)
```

**→ 这是一套"可配置的等待策略"**：type 决定用 `sched_yield` 还是 `usleep(250µs)` 还是 `usleep(1000µs)`。

## 4. 所以"98.8% 一个核"是怎么来的

把链条接起来：

```
0x15761b0 想等 GPU 完成，最多等 20µs
  ├ 20µs 内完成 → 直接退出（很短的路径）
  └ 20µs 超时 → 累加统计到 obj+0x6f88，返回"超时"
        ↓ 上层不断重入
  每次都做：9×pause + 取时 + 比较，然后可能 sched_yield
        ↓
  一帧 30.9ms ÷ 20µs ≈ 1545 次这样的尝试
  × 每次的实际开销（pause 序列 + 取时 + 函数进出 + sched_yield 系统调用）
```

**它不是"等一个永远不来的条件"，而是"用 20µs 的粒度反复检查"。**
`sched_yield` 让出 CPU 后又立刻被调度回来——**CPU 时间全记在它自己头上**。

### 4.1 这解释了报告 51 里那个矛盾

报告 51 看到 `state=R` 却频繁 `sched_yield`：**因为它每轮都在"让出→立刻拿回"。
`yield` 在 Linux 上常常相当于"标记需要调度但不一定切走"，所以状态一直是 `R`。**

## 5. 对"能不能改"的判断

| 问题 | 答案 |
|---|---|
| deadline 是"GPU 完成 + 超时上限"吗？ | **是**。`t0 + 20µs` 是**超时上限**，不是期望等待时长 |
| 是"条件总不满足"吗？ | **不是**。它是"每次只等 20µs 就放弃"，**上一层的循环再重试** |
| 有 bug 吗？ | **没有明显 bug**。20µs 是刻意的轮询粒度 |
| 能优化吗？ | **理论上可以，但要动 glcore 的行为**：把 20µs 改成事件驱动（等 GPU 完成的真通知）。**这是驱动设计选择，不是修 bug** |

**关键判断**：**这是"设计如此"的轮询，不是缺陷。**
改它等于改变 NVIDIA 驱动的等待策略——可以做实验，但不算"修 bug"。

## 6. 明确结论

| 项 | 结论 |
|---|---|
| `0x15761b0` 在等什么 | **GPU 完成，每次最多等 20µs**，超时就返回并累加统计（`obj+0x6f88`） |
| 那 98.8% CPU | **20µs 粒度的轮询 + `sched_yield`**，一帧约 1545 次尝试 |
| 是 bug 吗 | **不是**。是驱动刻意的轮询策略 |
| 改记账 | **不做**（且已确认记账不在这一层） |
| 这条支线 | **走到头了**：不是"某处写错了"，是"驱动选择了 20µs 轮询" |

## 7. 如果要继续，唯一有意义的方向

**不是改 20µs，而是改"20µs 轮询之上"的东西。**

上层（`#7 = 0x123b297` 队列处理器）**为什么一帧要进来约 1545 次**。
- 若上层本来就该每帧只等一次 GPU 完成 → **1545 次是多余的**，那是真问题
- 若上层确实有 1545 个独立的等待点（每 PBO/每 region）→ 设计如此

**这与报告 49 的"N43 答案"是同一个问题的另一面**：
报告 49 说"每写完一条命令查一次队列（4700 次/帧）"，
本轮说"每 20µs 轮询一次 GPU 完成（1545 次/帧）"。

**两者可能是同一件事的两个视角**（4700 次查队列 ↔ 1545 次轮询）。
**要确认这一点，需要把"命令数"和"轮询次数"对起来看**——那是 N49。
