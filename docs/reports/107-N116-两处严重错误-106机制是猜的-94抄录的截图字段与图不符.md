## 0. 我犯的两个错

我在报告 106 §4 写：

> vGPU 里 guest 看到的是一个**完整的虚拟 GPU**，它自己就是显示拥有者（虚拟 CRTC），

## 2. 那"vGPU 更快"这个结论还站得住吗

**站得住，但依据换了。**

| 论据 | 状态 |
|---|---|
| ~~130W 满载~~ | ⛔ **撤回，图上无此数字** |
| **`GPU-Util 99%` + `%SM 99%` + `%CPU 112.7`** | ✅ **成立**（图上明确） |
| **`GRID P40-2B` + `Disp.A Off`** | ✅ 成立，确认是 vGPU、是渲染卡 |
| **6016MiB 整卡** | ✅ 成立 |
| Heaven 进程持续占用（TIME 0:17 且 %SM 99） | ✅ 成立 |

**`%SM = 99%` 本身就是一个强证据**：它说明 GPU 的 SM 流水线在持续满负荷，**不是在等。**
这与真机 525 的 `48W / 89-93% util` 形成对比 —— 但**这个对比现在缺了"功耗"这一半**，
只能靠 utilization 与 SM 占用，**不能用 130W 说事**。

**⚠️ 报告 105/106 里凡引用"130W"的段落，全部失去依据。**

## 3. 既然 present 同构，差异只能在提交层

真机与 vGPU **同构**的部分（我之前误当成差异的）：

| | 真机 | vGPU（用户实际） |
|---|---|---|
| 渲染卡有无连接器 | 无（`Display Mode: Disabled`，0 connector） | 无（`Disp.A: Off`） |
| 谁输出 | 核显 i915 | **核显（直通）** |
| present 是否跨设备 | **是** | **是** |
| present 卡点 | `poll → xcb_wait_for_special_event`（实测） | 未测，但结构相同 |

**⇒ present 层不是差异所在。**

剩下的候选（按可验证性排序）：

| 假说 | 内容 | 怎么验 |
|---|---|---|
| **H1（最可能）** | vGPU 的 MMIO 被宿主代理，guest 的寄存器写被**合批/异步化**，那 118.5µs 的"批次开始/引擎 re-arming"被摊掉 | **在 vGPU 里跑 `n83a -M 1 / -M 3`**，看是否 ≈0.03µs |
| **H2** | vGPU guest 驱动是精简版，glcore 的提交器读到 vGPU 标志走另一分支 | 对比 guest 与物理机 glcore 的 hash + 提交器反汇编 |
| **H3** | 550 本身修了病 B | 把 550 装到真机跑 `n83a -M 3` |
| ~~H4~~ | ~~present 语义不同~~ | ⛔ **本轮否证** |

**H3 有先验阻力**：用户最早的观察是「525/535/570 在 vGPU 下都不回退」——
如果是 550 修的病，535/570 不该也好。**⇒ H1/H2 更可能，但 H3 要用实验排除，不能靠推理。**

## 4. 报告 94 为什么会错 —— 以及怎么防

### 4.1 错法

我看到用户贴了一张 nvidia-smi 截图，**没有逐像素核对就把"常见的 vGPU 满载形态"写了下来**：
`130W / 120W`、`64C`、`6144MiB`、`Bus 03:00.0`、`Compute M: N/A`。
这些数字**每个都符合"vGPU 满载"的直觉模板**，但没有一个是图上真实内容。

**这是最危险的编造形式：不是随机胡说，而是"符合预期的合理化补全"。**
它不会被"看起来对不对"发现，只能靠逐字符核对原图。

### 4.2 防法（写进纪律）

1. **抄录截图字段，必须同时保存放大切片并写下切片路径。**
   本轮补做了：`user-shots/smi-top.png`、`smi-b.png`，报告里引用它们。
2. **每个数字后面标注"来自哪个切片"**，没有切片的数字不许出现在报告里。
3. **`N/A` 是重要信息，不是缺失。** 图上 `Pwr`、`Temp`、`Fan` 全是 `N/A` ——
   这本身就是"虚拟设备"的强证据，而我上一轮把它替换成了 130W/64C，正好把证据丢了。
4. **一个反复引用的关键数字，必须能追溯到一手文件。** 「130W」被 5 份报告引用过，从未核过原图。
