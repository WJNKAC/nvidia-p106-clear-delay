# 86 · N95：GPU 侧 timer 把停顿钉在「draw 段」——bind 0.9µs / **draw 155µs** / 对间空隙 0.8µs

日期：2026-10-26 14:00
驱动：525.116.03
方法：`pair_gput`（每对插 3 个 `GL_TIMESTAMP`，把 GPU 时间轴切成「bind 段 / draw 段 / 对间空隙」）+ 插延迟对照 + shader 规模对照

---

## 0. 结论（四条）

1. **停顿整段落在 draw 上**（N=64，1080p，kind=1 切 program）：

| 段 | GPU 侧中位 |
|---|---|
| bind（`glUseProgram`） | **0.9 µs** |
| **draw（紧跟的 1 个 quad）** | **155.1 µs** |
| 对间空隙（上一对 draw → 本对 bind） | 0.8 µs |

   对照 kind=0（legacy `glColor3f`）：bind 0.8 / draw **0.8** / 空隙 0.8 µs。

   ⇒ **`glUseProgram` 本身在 GPU 上不花钱；花钱的是"绑定之后紧跟的那个 draw"。**
   这与报告 76 的 M9/M8（先切后画、切而不画都免费）完全一致，
   也把"驱动在 bind 处插入等待命令"这个假说排除——**bind 段是干净的 0.9µs**。

2. **不是"等异步数据到达"**：在 bind 与 draw 之间插 `nanosleep`：

| 间隔 | draw 段 |
|---|---|
| 0 | 155.0 µs |
| 50 µs | 154.8 µs |
| 200 µs | 154.4 µs |
| 1000 µs | 153.8 µs |

   插到 1ms 也**完全不减**。若 GPU 在等某个后台写（shader/常量上传、通知），
   给足时间它就该变短——没有。⇒ **停顿是 draw 自身执行时产生的，与外部时序无关。**

3. **不是 shader 二进制大小**：unroll 1 / 50 语句 → draw **155.1 / 155.4 µs**（不变）；
   unroll 400 / 1200 → 169.0 / 197.6 µs（增加部分与"大 shader 的真实执行时间"同量级）。
   ⇒ 固定项 ~155µs 与代码规模无关。

4. **累计排除（含本轮）**：CPU 提交、ioctl、命令字、等 GPU 完成、GPU 忙、ThreadControl 32 位、
   shader 复杂度、shader 缓存、回读 PBO、主机调度、**bind 段插入等待**、**异步数据到达**、**shader 规模**。

## 0bis. ★ 停顿期间显存利用率 = 0%

同一负载（`pair_only kind=1 N=1000`）运行中采样：

```
util.gpu=99%   util.memory=0%   37.70 W   1911 MHz
util.gpu=99%   util.memory=0%   37.70 W   1911 MHz
util.gpu=98%   util.memory=0%   37.70 W   1911 MHz
```

**显存控制器完全空闲。** 这把"等数据"整类再削一刀：

| 若是 | 应该看到 | 实测 |
|---|---|---|
| 等 shader/常量从显存取 | mem util > 0 | **0%** |
| 等 CE 拷贝/上传完成 | mem util > 0、CE 忙 | **0%** |
| 等 DMA/回读 | mem util > 0 | **0%** |
| **等一个事件/信号量（非数据）** | util 高、mem 0、功耗低 | **✓ 吻合** |

⇒ **GPU 在等"某个事件"，不是在搬数据。** 而事件只能来自：①另一引擎的完成信号；②主机侧的写。
若是 ②（主机写一个信号量），PCIe 读流量不计入 `util.memory`，所以本观测无法排除它——
但报告 85 的"CPU 满载 ±1%"和本报告 §0.2 的"插 1ms 延迟无变化"都指向**不是主机时序**。

## 1. 这张图现在长什么样

```
应用线程                          GPU 时间轴
---------                         -----------
glUseProgram(prog)   ────────────  [bind 段 0.9µs]  ← 几乎为零
quad draw            ────────────  [draw 段 155µs] ← ★ 全部成本在这里
                                     ↑ 批次在这里被"断开并重启"，GPU 停 155µs
(下一对)             ────────────  [空隙 0.8µs]
```

- 停顿在 **draw** 里，且是 **GPU 时间轴上的停顿**（timer query 夹住的就是 GPU 自己的时钟）；
- GPU 期间 util 100% 但只有 **37.5W**（报告 83）⇒ 在等，不在算；
- 应用线程同时在做 42 次/对 的 `sched_yield` 自旋（报告 83）⇒ 它在等这批被消费。

**⇒ 现在的问题只剩一句：这个"新批次的第一条 draw"在 GPU 上为什么要 155µs？**

---

## 2. 为什么这不是"驱动在 bind 时插了等待命令"

报告 81 曾假设"525 在批次开始写了一条等事件的命令"。本报告的 bind 段 = 0.9µs 直接否掉了
"绑定处插等待"的形式。若真有等待命令，它只可能挂在**draw 命令**上，且**由 draw 触发批次重启**。
这缩小了静态搜索范围：**要看的是 draw 路径在"批次脏"时写的那几个字节**，而不是 bind 路径。

## 3. 静态侧：抓 push buffer 的两次尝试与卡点

| 手段 | 结果 |
|---|---|
| `perf probe` 挂 glcore | 两版都 0 命中（报告 77/81） |
| gdb 在 `0x1238920` 下断点 | **断点插不进去**（与 uprobe 同源：glcore 的代码页不接受写入） |
| gdb 读 TLS 里的 ctx（`_nv000tls`） | 读到 0x5abcdfeed，不是合法指针 ⇒ 该 TLS 符号经 gdb 解析后不是 `fs:` 相对的真实地址 |

**结论**：glcore 的代码/数据都不能按常规手段写或断点，抓 push buffer 需要另找锚点。
下一步可行方案：**扫描进程的匿名 rw 区找 ctx**——判据是"偏移 +0 处的指针指向一块大 rw 映射（push buffer），
且 +0x8e0d10 处有一组单调递增的 float（驱动自记时，报告 36）"。
