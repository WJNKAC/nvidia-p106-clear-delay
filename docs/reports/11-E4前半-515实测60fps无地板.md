# 11 · E4 前半：515 实测 —— 60 fps，无地板；版本边界坐实

> # ⚠️ 本报告的 FPS 结论已作废（2026-10-25 10:55）
>
> **"515 = 60 fps / 580 = 31 fps" 不成立。**
> 后续实测（报告 15）证明 Heaven 的帧率是**双峰分布**：完整基准 `Avg 32.4 / Min 23.9 / Max 63.7`。
> 本报告用"进场景 +N 秒截一张 HUD"采样，捕捉到的是**相机路径轻场景段的瞬时值**，不是平均帧率。
> 两次采样落在路径不同相位，差异可完全由相位解释，不需要版本差异。
>
> **修正后：515 是否也有地板，未知。** 须以完整基准 Avg FPS 重测（报告 15 §6）。
> 仍然有效的部分：E1 数据（§3）、GPU 签名（§4）、静态锚点（§5）。

> 2026-10-25 07:22–08:05
> 环境：**内核 6.1.0-50-amd64 + 驱动 515.105.01**（用户新装，uptime 3 min）
> 相位：全部沿用 580 轮的同一套脚本（`analysis/probes/`），仅换版本
> 结论：**515@1080p = 60 fps，580@1080p = 31 fps。地板是 525+ 引入的，515 没有。**

## 1. 环境变更带来的一个静默陷阱

重启后 Xwayland 换了新的 xauth 文件名：

```
旧: /run/user/1000/xauth_JUkEFb   →  新: (名字变化)
```

不显式设 `XAUTHORITY` 时 `glxinfo` 报 `Authorization required`，而 Heaven 会**直接起不来但退出码不显眼**。
所有脚本已改为自动取最新 xauth：

```bash
export XAUTHORITY=$(ls -t /run/user/1000/xauth_* | head -1)
```

另一处：新内核把 `kernel.perf_event_paranoid` 重置为 **3**（旧会话是 1），
perf 因此完全采不到样，只吐一句 `To make the adjusted perf_event_paranoid setting permanent...`。
测量期间临时降到 1，结束已恢复为 3。

> 这两条都属于 README 铁律「同一相位验证方式」的范畴：换内核/重启会让**权限与显示授权**这两层前提悄悄变化，
> 而它们只影响测量工具、不影响被测程序——所以症状是"数据全是 0"，不是报错。

## 2. 核心 A/B：同一脚本、同一相位、只换版本

| 项 | 515.105.01 | 580.126.18 |
|---|---|---|
| 内核 | 6.1.0-50-amd64 | 同机旧内核 |
| Heaven 1920×1080 `vsync=0` | **60 fps** | **31 fps** |
| Heaven 320×200 | **61 fps** | **37 fps** |
| 帧时间 | 16.7 ms | 32.3 ms |

帧率同样取自 Heaven 右上角 HUD 截图（`f515_1080.png` / `f515_320.png` 存证），
进场景判定同样用窗口截图体积（>40 KB）。

**515 在两种分辨率下都顶在 ~60**，说明 GL 路径存在一个 ~60 Hz 的 present 上限（Xwayland rootless 合成器）。
因此严格表述是：**515 的地板 < 16.7 ms**，其真值被这个上限遮住；而 **580 的地板 = 32.9 ms**，远在上限之下。
这不影响 A/B 结论的方向：580 掉到了上限的一半以下，515 没掉。

## 3. E1（CUDA 完成往返）在 515 上

| 模式 | 515 空闲 | 515 GL 并存 | 580 空闲 | 580 GL 并存 |
|---|---|---|---|---|
| A 提交（异步） | 1.0 µs | 1.6 µs | 1.1 µs | 1.6 µs |
| B 提交+ctxSync（背靠背） | **4.7 µs** | **8.7 µs** | 4.8 µs | **76.1 µs** |
| C 空闲 30 ms 后 Sync | 最小 **2.7** / 最大 15.7 µs | **8.2 / 40.9 µs** | 3.2 / 33.3 | 7.0 / 26.0 |
| D 8 kernel+1 Sync | 11.7 µs | 21.4 µs | 12.4 | 202.4 |
| E 独立 stream | 4.6 µs | 8.3 µs | 4.6 | 74.8 |

两版**空闲态几乎一致**（4.6~4.8 µs），说明完成通知在两版都健康。
差别在"GL 并存"时：515 的背靠背往返 **8.7 µs**，580 是 **76 µs**（差 8.7 倍）。

→ 580 在跑 GL 时，GPU 上**有东西长期占着**，连一个空 kernel 的往返都被拖慢；
515 没有这个占用。这与下面 §4 的 GPU 签名完全一致。

## 4. GPU 签名：这是最能一眼分辨两版的一组数

| 场景 | 515 | 580 |
|---|---|---|
| 1080p | util **40%** / mem 11% / **58–70 W** / 1911 MHz | util **92%** / mem **6%** / **47 W** / 1911 MHz |
| 320×200 | util **35%** / mem 17% / **12–14 W** / **708 MHz** | util **91%** / mem **2%** / **41 W** / 1911 MHz |

三条独立线索同时指向同一件事：

1. **515 会在 320×200 下把 SM 降到 708 MHz、显存降到 810 MHz，只吃 12–14 W。**
   时钟调节器认为 GPU 真的空闲了——这是"干完就歇"的特征。
2. **580 在同样 320×200 下仍钉在 1911 MHz / 4006 MHz，util 91%，耗 41 W。**
   时钟调节器认为 GPU 一直忙——因为 SM 上确实驻留着东西，只是不搬数据（mem 2%）。
3. **515 在 1080p 上功耗更高（58–70 W）、util 更低（40%）**；
   580 反过来（47 W / 92%）。同样的画面，580 用一半的功率跑一半的帧——
   **它把时间花在驻留而不是计算上**，这与 `utilization.gpu` 只统计"有 kernel 驻留"的定义吻合。

## 5. 静态侧：一条线索被彻底关闭

我在报告 10 §3 记录过 `deadline = now_ms + 250×(N−1)`，并实测 `N=12` → 2750 ms 的秒级退避。
本轮确认 **N 在两版都是硬编码常量 12**：

```
515: 0xf57380: movl $0xc,0x22e0c(%rdi)
580: 0xa7bc25: movl $0xc,0x22e0c(%r14)
```

→ 退避参数**没有变**。"525 改了这个退避"这个可能性关闭。

同时确认 515 的这套轮询代码**结构与 580 逐项对应**（只是偏移/槽位不同）：

| 元素 | 515 | 580 |
|---|---|---|
| 门位 | `testb $0x2,0x54d(%rdi)` | `testb $0x2,0x565(%rdi)` |
| 挂起计数 | `ctx+0x22e0c` | `ctx+0x22e0c` |
| 完成谓词 | `call 0xfbe540` → 读 `ctx[0x1490]+0x6e == 0xffff` | `0xae5c30` → 读 `ctx[0x1418…]` |
| 全局门 | `0x251f840 & 7` | `0x235fba0 & 7` |
| deadline | `ctx+0x6f90` | `ctx+0x6e48` |
| 重试计数 | `ctx+0x6f89`（>3 放弃） | `ctx+0x6e41`（>3 放弃） |
| 时钟槽 | `call *0x280(%rax)` | `call *0x290(%rax)` |

**所以"515 没有这段代码"这个解释不成立**——代码在，而且 gdb 确认 `0xfbe5b0` 在渲染期确实被主线程调用。

差别只在**它跑多久**：

| | 515 | 580 |
|---|---|---|
| 场景期最忙线程 perf 榜首 | **1.13%**（样本散在几百个地址） | **21.18%**（`__vdso_clock_gettime`）+ 6.93%（`0xb0fde5`） |
| 等待链占 CPU | 无集中热点 | **约 21%** 集中在"读时钟 → 比 deadline → 扫数组" |

→ **同一段代码，在 515 上每次调用很快返回；在 580 上每帧烧掉 27.8 ms。**
这正好把问题从"哪段代码被改了"逼到"**为什么 580 的那次等待没有及时结束**"。

## 6. 未完成的一步（诚实记录）

我尝试在 515 上复现报告 10 的两段式测量（GPU 段 vs 驱动发现段），**没有成功**：

| 尝试 | 结果 |
|---|---|
| 全内存扫 `u16==0xffff` 候选 | 132 MB 扫出 20000 个候选（撞上限），前 20000 个**无一翻转** |
| 断 `0xfbe58b`（数组循环内的标记比较） | 40 s **未命中** |
| 断 `0xfbe565`（首个标记比较，读 `ctx[0x1490]+0x6e`） | 命中，但该对象 `+0x6e` 在 12 s 内**恒为 0**，从未变成 0xffff |

结论：515 的完成信号**不在** `ctx[0x1490]+0x6e` 这个我沿用的位置，
或者它的"置位—清零"快于 3.2 kHz 采样。**515 侧的两段式拆分暂缺**，不影响 A/B 方向。

（顺带：这几轮 gdb 附着时 `nvidia-smi` 读到 100% / 95–99 W，明显被调试器扰动，
不采用；采用的 40%/65 W 是干净运行时的读数。）

## 7. 现在能确定与不能确定的

**能确定**

1. **版本边界是真的**：515@1080p 60 fps vs 580@1080p 31 fps，同机同脚本同相位。
   "525+ 都坏"从回忆变成了**有 515 锚点的实测**。
2. **不是功耗墙/温度/频率/显存带宽**（沿用报告 10 的排除，515 侧新增：它在 320×200 下自愿降到 708 MHz）。
3. **完成通知机制两版都健康**（E1 空闲态 4.6~4.8 µs）。
4. **580 的 GPU 是"驻留但空转"**：util 92% / mem 6% / 47 W / 满频，且拖慢任何并发的 CUDA 往返（76 µs vs 8.7 µs）。
5. **退避参数 N=12 两版相同**，不是差异点。
6. **同一段等待代码在 515 上不热**（榜首 1.13%）**在 580 上占 21%**。

**不能确定**

- 515 的真实地板（被 60 Hz 上限遮住，只知 < 16.7 ms）。
- **525 是好是坏**——这正是 E4 还差的那一格。
- 580 那 30.24 ms 的成因（报告 10 已排除中断/通知/退避/负载抖动）。

## 8. 下一步

**E4 后半只差 525。** 需要再换一次驱动（重启）。判据（用户预注册）：

- **525 ≈ 515（60 fps）** → 案件重锚到 **535+**。此时 `pthread_mutex_*` 恰好 535 才进入 glcore = 线程化在 535 引入，与社区抱怨的时间点一致；525 的 RM/NVPCF 重构对本案无罪。
- **525 坏（≈31 fps）** → 原时间线成立，报告 10 §6 的"驱动侧投递"分支优先。

测什么：同一套脚本，`Heaven FPS(1080p/320)` + `E1 空闲/并存` + `GPU 签名`。约 5 分钟机时。

**如果 525 也坏**，那么 515→525 之间就有一个可用于静态对比的明确目标，
且这次比对有语义（"为什么等待不及时结束"），不再是上一轮那种无锚点的指令 diff。
